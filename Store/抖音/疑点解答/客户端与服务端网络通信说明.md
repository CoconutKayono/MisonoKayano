# 客户端与服务端网络通信说明

本文档帮助理解客户端与服务端之间的网络通信，并重点解释消息层中的两个基本概念：

- 事件：发生了一次什么事情；
- 状态：当前系统是什么样子。

内容包括 TCP、UDP、KCP 的基础概念，抖音虚拟世界平台的网络抽象，DSTemplate 中 CS/SC 的通信链路，以及在实际开发中如何判断一个数据应该设计成事件还是状态。

> 重要结论：CS 和 SC 表示通信方向，不表示 TCP 或 UDP。当前可见的 DSTemplate Lua 代码只能确认它们使用 DouyinRemoteEvent 进行封装，无法仅凭 CS/SC、JSON 序列化或 FireServer/FireClient 判断底层一定是 TCP、UDP 或 KCP。

## 1. 网络通信分层

一次业务通信通常可以拆成以下几层：

~~~text
业务层
  成就解锁、购买商品、同步状态、玩家移动
      ↓
消息层
  C2S / S2C、RemoteEvent、RemoteFunction、同步变量
      ↓
协议层
  packetType、version、data、Pack / Unpack、JSON
      ↓
传输层
  TCP、UDP、KCP、QUIC 或平台自定义传输
      ↓
网络链路
  Wi-Fi、5G、路由器、运营商网络、服务器
~~~

各层解决的问题不同：

| 层次 | 主要问题 |
| --- | --- |
| 业务层 | 这次操作是否合法，是否重复，最终状态是什么 |
| 消息层 | 消息发给谁，是单向还是双向，是事件还是状态 |
| 协议层 | 字段怎么定义，如何序列化、反序列化和分发 |
| 传输层 | 如何把字节送到对端，是否可靠、有序、低延迟 |
| 网络链路 | 延迟、抖动、丢包、断线、带宽变化 |

需要区分以下概念：

- CSUnLockAchievement 是业务协议包；
- C2S 是 Client to Server，表示客户端到服务端的方向；
- S2C 是 Server to Client，表示服务端到客户端的方向；
- DouyinRemoteEvent 是平台提供的消息抽象；
- 同步变量是平台提供的状态同步抽象；
- TCP、UDP、KCP 属于更底层的传输机制。

## 2. TCP、UDP 和 KCP

### 2.1 TCP

TCP 是面向连接的可靠字节流协议，通常提供：

- 可靠传输；
- 按序到达；
- 丢包重传；
- 重复数据过滤；
- 流量控制；
- 拥塞控制；
- 连接状态管理。

TCP 的可靠不代表永远不会断线。连接断开、超时或进程退出时，尚未成功送达的数据仍然可能丢失。

TCP 的主要问题是队头阻塞：

~~~text
TCP 数据包 1 丢失
    ↓
后续数据包即使已经到达
    ↓
接收方也可能要等待数据包 1 重传
    ↓
后续数据被阻塞
~~~

因此，聊天、订单、登录、存档等业务通常适合 TCP；实时移动、物理状态和高频输入则需要根据延迟要求选择更合适的方案。

### 2.2 UDP

UDP 是无连接的数据报协议，本身不保证：

- 一定到达；
- 按序到达；
- 自动重传；
- 自动去重；
- 拥塞环境下的稳定性。

UDP 的优势是延迟低，不会因为一个旧包丢失而自动阻塞所有后续包。实时状态可以使用“新状态覆盖旧状态”的方式处理，例如位置、速度和朝向。

应用可以在 UDP 之上自行增加：

- 序列号；
- ACK；
- 超时重传；
- 去重；
- 乱序缓存；
- 可靠/不可靠消息分类；
- 拥塞控制；
- 前向纠错。

### 2.3 KCP

KCP 通常指构建在 UDP 之上的低延迟可靠传输机制。它会在 UDP 之上增加：

- 序列号；
- ACK；
- 快速重传；
- 超时重传；
- 滑动窗口；
- 按序交付；
- 丢包恢复。

可以简单理解为：

~~~text
TCP：可靠字节流
UDP：低层数据报
KCP：在 UDP 上实现的一套偏低延迟的可靠传输机制
~~~

KCP 不是 UDP 的别名。是否使用 KCP、KCP 承担哪些通道、是否区分可靠和不可靠消息，都要看具体 SDK 或平台实现。

## 3. TCP 中的黏包和拆包

TCP 面向连续字节流，不理解应用层消息边界。

应用层发送两次：

~~~text
发送：HELLO
发送：WORLD
~~~

接收方可能读到：

~~~text
HELLOWORLD
~~~

也可能读到：

~~~text
HEL
LOWOR
LD
~~~

这就是黏包和拆包。它不是 TCP 出错，而是 TCP 的正常行为。

在 TCP 之上必须设计应用层分帧，常见方式包括：

### 3.1 固定长度

每个消息固定占用 N 个字节。解析简单，但不适合消息长度差异很大的场景。

### 3.2 长度前缀

消息格式：

~~~text
[消息长度][消息体]
~~~

接收方先读取固定长度的长度字段，再读取对应长度的消息体。

### 3.3 分隔符

消息格式：

~~~text
message-1
message-2
~~~

适合文本协议，但需要处理消息体本身包含分隔符的情况。

### 3.4 自描述包头

~~~text
[魔数][版本][类型][序列号][长度][数据][校验]
~~~

游戏和业务系统常用这种方式。

UDP 通常保留数据报边界，但仍要关注 MTU、IP 分片、业务批量封装和平台自定义协议。KCP 也需要自己的片段、序列和确认机制。应用层是否按消息交付，要看 KCP 外层如何封装。

## 4. 消息层：消息发给谁、单向还是双向、事件还是状态

消息层至少要回答三个问题：

1. 消息发给谁？
2. 消息是否需要返回结果？
3. 消息表达的是一次发生，还是当前状态？

### 4.1 消息发给谁

常见目标有：

| 目标 | 含义 | 例子 |
| --- | --- | --- |
| Client → Server | 客户端发送给服务端 | 请求解锁成就、请求购买商品 |
| Server → Client | 服务端发送给客户端 | 返回奖励结果、推送玩家数据 |
| Server → 指定 Client | 服务端通知某个客户端 | 私人订单状态、个人提示 |
| Server → All Clients | 服务端广播给所有客户端 | 游戏开始、全场公告 |
| Player → Owner | 发给网络对象主权方 | 请求主权方修改对象 |
| Player → Target | 发给指定玩家 | 播放一个动作、发送社交消息 |

抖音虚拟世界中可以使用：

~~~text
DouyinRemoteEvent
  FireServer
  FireClient
  FireAllClients

DouyinRemoteFunction
  InvokeServer
  InvokeClient

同步变量
  SetValue
  GetValue
  OnValueChange
~~~

### 4.2 单向还是双向

单向消息适合“通知”：

~~~text
发送方 → 接收方
发送方不等待业务返回
~~~

例如：

- 播放一个动作；
- 播放一个音效；
- 发送一次表现通知；
- 广播游戏开始。

双向调用适合“请求并等待结果”：

~~~text
请求方 → 接收方
请求方 ← 结果
~~~

例如：

- 请求查询数据；
- 请求确认某个操作；
- 服务端向客户端请求一次输入；
- 需要立即知道成功或失败的功能。

但“有返回值”不等于“业务一定可靠”。RemoteFunction 的回调仍可能因为网络异常、对端退出或超时而无法返回。关键业务仍需要请求 ID、幂等和状态恢复。

### 4.3 事件还是状态

这是消息层中最重要的设计问题：

~~~text
事件：过去发生过一次什么事情
状态：现在系统处于什么情况
~~~

例如：

| 业务含义 | 事件写法 | 状态写法 |
| --- | --- | --- |
| 宝箱 | OpenChest(chestId) | chestOpened = true |
| Buff | AddBuff(buffId) | 当前 Buff 列表 |
| 成就 | UnlockAchievement(id) | achievementUnlocked = true |
| 门 | OpenDoor(doorId) | doorState = "open" |
| 游戏阶段 | StartGame() | gameState = "running" |
| 玩家位置 | MoveTo(position) | currentPosition = position |

## 5. 如何判断应该使用事件还是状态

可以使用下面的判断顺序。

### 5.1 第一个问题：这个信息描述“发生过”，还是描述“现在是”？

如果语义是“某件事发生了一次”，优先考虑事件：

- 玩家点击了一次按钮；
- 玩家发射了一枚子弹；
- 玩家打开了一个宝箱；
- 玩家触发了一次爆炸；
- 玩家开始播放一个动作；
- 服务端收到了一次购买请求。

如果语义是“当前仍然成立”，优先考虑状态：

- 宝箱现在是否已打开；
- 门现在是否开启；
- 玩家当前有多少金币；
- 当前游戏阶段是什么；
- 当前持有哪些 Buff；
- 玩家当前的位置和血量。

判断口诀：

~~~text
问“发生了什么” → 事件
问“现在是什么” → 状态
~~~

### 5.2 第二个问题：新加入的玩家是否必须知道？

如果新加入玩家必须知道结果，不能只发送事件，应保存成状态：

- 宝箱已经打开；
- 游戏已经开始；
- 门已经打开；
- 某个 Buff 当前仍存在；
- 玩家当前分数；
- 当前比赛阶段。

原因是新玩家通常只能获得当前可同步状态，不能自动补收很久以前已经发送过的一次性消息。

### 5.3 第三个问题：丢掉这条消息后，后续状态能否恢复？

如果丢掉一次消息后，下一条或下一次同步可以恢复，就可以考虑状态：

~~~text
位置包 101 丢失
位置包 102 到达
    ↓
使用位置 102
~~~

如果丢掉后会导致业务永久不一致，就不能只依赖无确认事件：

- 扣款；
- 发奖；
- 订单确认；
- 成就解锁；
- 关键结算；
- 物品消耗。

这类业务应使用请求 ID、服务端幂等、回包和最终状态。

### 5.4 第四个问题：消息是否允许重复执行？

事件通常可能被重复执行，因此要检查幂等性：

- 打开宝箱是否重复发奖励；
- 扣除金币是否重复扣除；
- 发射子弹是否允许重复生成；
- 订单发货是否重复增加道具。

如果重复执行有严重后果，事件处理必须带唯一 ID，并在接收端去重。

状态更新通常可以设计成幂等：

~~~text
设置 chestOpened = true
设置 gameState = "running"
设置 coin = 100
~~~

相同状态重复收到，最终结果仍然相同。

### 5.5 第五个问题：接收方需要完整历史，还是只需要最新结果？

如果接收方需要完整历史，事件更合适，但要提供：

- 序列号；
- ACK；
- 重传；
- 去重；
- 持久化事件日志；
- 断线后的事件补发。

如果接收方只需要当前结果，状态更合适：

- 保存最新值；
- 使用版本号；
- 定期发送快照；
- 重连后重新发送；
- 新值覆盖旧值。

## 6. 事件代码示例：一次性动作通知

下面使用抖音虚拟世界的 DouyinRemoteEvent 演示“玩家开始跳舞”的事件。

这个需求的语义是：

~~~text
玩家在某个时间点开始了一次舞蹈动作
~~~

它不是一个需要长期保存的状态。接收方收到后播放动作即可。

### 6.1 客户端发送事件

~~~lua
-- 客户端脚本
local DanceEvent = DouyinRemoteEvent("PlayerStartDance")

function OnClickDance(danceId)
    if DouyinApplication.isServer then
        return
    end

    local actor = DouyinActorService.GetLocalActor()
    if actor == nil then
        return
    end

    -- 发送一次性事件：我开始播放 danceId
    DanceEvent:FireServer(danceId)
end

function OnDestroy()
    if DanceEvent ~= nil then
        DanceEvent:Dispose()
        DanceEvent = nil
    end
end
~~~

### 6.2 服务端接收并广播事件

~~~lua
-- 服务端脚本
local DanceEvent = DouyinRemoteEvent("PlayerStartDance")

function Start()
    if not DouyinApplication.isServer then
        return
    end

    DanceEvent.onServerEvent:AddListener(OnPlayerStartDance)
end

function OnPlayerStartDance(player, danceId)
    if player == nil or player.isServer then
        return
    end

    -- 服务端重新校验参数
    if type(danceId) ~= "number" then
        return
    end

    -- 可以在这里校验玩家是否允许播放该动作
    DanceEvent:FireAllClients(player.playerOpenID, danceId)
end

function OnDestroy()
    if DouyinApplication.isServer then
        DanceEvent.onServerEvent:RemoveListener(OnPlayerStartDance)
    end

    if DanceEvent ~= nil then
        DanceEvent:Dispose()
        DanceEvent = nil
    end
end
~~~

### 6.3 客户端接收并播放动作

~~~lua
-- 客户端脚本
local DanceEvent = DouyinRemoteEvent("PlayerStartDance")

function Start()
    if DouyinApplication.isServer then
        return
    end

    DanceEvent.onClientEvent:AddListener(OnPlayerStartDance)
end

function OnPlayerStartDance(playerOpenID, danceId)
    local actor = FindActorByOpenID(playerOpenID)
    if actor == nil then
        return
    end

    PlayDance(actor, danceId)
end

function OnDestroy()
    if not DouyinApplication.isServer then
        DanceEvent.onClientEvent:RemoveListener(OnPlayerStartDance)
    end

    if DanceEvent ~= nil then
        DanceEvent:Dispose()
        DanceEvent = nil
    end
end
~~~

### 6.4 这个事件示例的局限

如果这条事件丢失：

- 其他客户端可能看不到这次动作；
- 新加入的玩家不会自动知道之前已经开始过的动作；
- 如果动作只持续几秒，之后可能无法补救。

这通常是可以接受的，因为动作表现不是长期权威状态。

如果“当前玩家正在跳舞”本身需要被后来加入的玩家看到，就应该另外保存一个状态：

~~~text
事件：PlayerStartDance(danceId)
状态：currentDance = danceId，danceStartTime = xxx
~~~

也就是说，事件和状态可以同时使用：

- 事件负责立即触发低延迟表现；
- 状态负责晚到、丢包和重连后的恢复。

## 7. 状态代码示例：当前门是否打开

下面使用抖音虚拟世界的同步变量演示状态同步。

这个需求的语义是：

~~~text
这扇门当前是否处于打开状态
~~~

门的状态需要满足：

- 所有人看到一致结果；
- 新加入玩家能看到当前结果；
- 某次变化消息丢失后，后续仍有机会恢复；
- 不能因为重复收到同一个值而重复执行开门逻辑。

### 7.1 声明同步变量

~~~lua
-- 挂载在网络对象上的脚本
---@varSync doorOpened:bool=false
---@end
~~~

同步变量只能由网络对象的主权方修改，不能像普通 Lua 字段一样直接使用等号赋值。

### 7.2 主权方修改状态

~~~lua
function OnNetSpawned()
    doorOpened:OnValueChange(function(currentValue, previousValue)
        ApplyDoorState(currentValue, previousValue)
    end)
end

function OpenDoor()
    if not DouyinScript.HasOwnership() then
        -- 没有主权时，应按业务决定是否请求主权，
        -- 或把请求发送给当前主权方。
        DouyinScript.RequestOwnership()
        return
    end

    -- 写入当前事实，而不是发送一个不可恢复的“开门动作”
    doorOpened:SetValue(true)
end

function CloseDoor()
    if not DouyinScript.HasOwnership() then
        return
    end

    doorOpened:SetValue(false)
end

function ApplyDoorState(currentValue, previousValue)
    if currentValue == true then
        DoorPlayOpenAnimation()
    else
        DoorPlayCloseAnimation()
    end
end
~~~

### 7.3 其他客户端监听状态变化

~~~lua
function OnNetSpawned()
    doorOpened:OnValueChange(function(currentValue, previousValue)
        ApplyDoorState(currentValue, previousValue)
    end)

    -- 初始化时也主动读取一次当前值。
    -- 这样即使监听注册前状态已经是 true，也能正确显示。
    ApplyDoorState(doorOpened:GetValue(), nil)
end

function ApplyDoorState(currentValue, previousValue)
    if currentValue then
        DoorPlayOpenAnimation()
    else
        DoorPlayCloseAnimation()
    end
end
~~~

这里的关键不是“每次都收到一条开门事件”，而是所有客户端最终都能读取到：

~~~text
doorOpened = true
~~~

状态变化通知只是提示“请重新读取当前值”。真正的业务依据是同步变量当前保存的值。

### 7.4 状态示例为什么更适合这扇门

如果客户端错过了某次 doorOpened=true 的变化通知，但稍后：

- 网络对象重新同步；
- 玩家断线重连；
- 客户端重新读取同步变量；
- 主权方再次发送当前快照；

客户端仍然可以得到 doorOpened=true。

即使同一个状态被重复同步多次：

~~~text
doorOpened = true
doorOpened = true
doorOpened = true
~~~

结果仍然是同一个最终状态，不会像重复执行 OpenDoor() 那样天然产生多次业务副作用。

## 8. 状态为什么比事件更抗丢包

这里的“状态更抗丢包”不是说同步变量底层一定可靠，也不是说状态消息绝对不会丢失，而是说状态具有更强的恢复能力。

### 8.1 事件通常是一次性信息

事件表示：

~~~text
在时间 T 发生了一次动作
~~~

如果事件包在 T 时刻丢失，接收方通常不知道这件事曾经发生过：

~~~text
T1：OpenChest 事件发送
T1：事件丢失
T2：没有后续消息
结果：接收方一直不知道宝箱已经打开
~~~

事件的有效期往往很短，错过之后就无法仅凭下一帧判断发生了什么。

### 8.2 状态可以被反复读取和覆盖

状态表示：

~~~text
在当前时刻，系统的事实是 X
~~~

例如：

~~~text
chestOpened = true
doorOpened = true
gameState = "running"
coin = 100
~~~

状态可以通过以下方式再次获得：

- 新玩家加入时发送当前快照；
- 断线重连时重新同步；
- 定期发送状态；
- 收到状态变化通知后主动读取；
- 服务端响应查询请求；
- 主权转移时由新的主权方继续维护；
- 版本号发现落后后请求补齐。

因此，状态不要求“某一条特定消息必须成功到达”，而是允许接收方在之后重新获得最新值。

### 8.3 状态更新通常可以幂等

事件：

~~~text
OpenDoor()
~~~

重复执行可能导致：

- 重复播放动画；
- 重复发奖励；
- 重复扣除资源；
- 重复生成对象；
- 重复触发后续逻辑。

状态：

~~~text
doorOpened = true
~~~

重复应用通常仍然得到 true。即使收到旧值和新值，也可以使用版本号过滤：

~~~lua
function ApplyState(incomingVersion, incomingState)
    if incomingVersion < self.currentVersion then
        return
    end

    self.currentVersion = incomingVersion
    self.state = incomingState
    self:RefreshView()
end
~~~

### 8.4 状态能让新加入者直接收敛

事件只描述过去的一次动作，新玩家通常无法补收历史事件。

状态描述当前事实，新玩家只要得到当前快照即可：

~~~text
老玩家已经打开宝箱
新玩家加入
服务端发送 chestOpened = true
新玩家直接显示宝箱已打开
~~~

这就是状态比事件更适合房间共享世界的原因。

### 8.5 状态仍然需要正确的同步机制

状态更抗丢包不等于可以不做可靠性设计。仍然需要考虑：

- 状态快照是否会重发；
- 重连时是否重新同步；
- 状态是否带版本号；
- 多个主权方是否可能同时修改；
- 状态变化是否会乱序；
- 状态是否应该采用全量还是增量；
- 状态是否需要服务端保存；
- 状态变化是否需要 ACK。

如果状态只发送一次、只存在于内存、没有重连同步，那么它也可能因为丢包而永久不一致。

## 9. 状态同步的典型处理方式

### 9.1 最新值覆盖旧值

适合位置、速度、朝向、当前血量等数据：

~~~text
state version 10：position = A
state version 11：position = B
state version 12：position = C
~~~

如果版本 11 丢失，收到版本 12 后直接使用 C。

接收方应避免用旧包覆盖新包：

~~~lua
function OnPositionState(version, position)
    if version <= self.lastPositionVersion then
        return
    end

    self.lastPositionVersion = version
    self.actor:SetPosition(position)
end
~~~

### 9.2 定期全量快照

除了发送变化，还可以每隔一段时间发送完整状态：

~~~text
变化包：doorOpened = true
变化包：gameState = running
变化包丢失
    ↓
定时快照：doorOpened = true, gameState = running
    ↓
客户端恢复
~~~

### 9.3 重连后主动拉取

断线重连后，客户端不要假设自己拥有完整历史。可以主动请求：

~~~text
客户端：我的状态版本是 20，请同步缺失内容
服务端：当前版本是 23，返回版本 21～23 的变化或直接返回最新快照
~~~

DSTemplate 中的玩家数据重同步就是这种思想：客户端携带已知版本或缺失域，服务端返回变化的数据域和最新版本。

### 9.4 状态版本号

状态应尽量带版本号或时间戳：

~~~lua
{
    version = 12,
    doorOpened = true,
}
~~~

接收时：

- 版本小于当前版本：丢弃；
- 版本等于当前版本：可以忽略重复数据；
- 版本大于当前版本：应用；
- 中间有缺口：根据业务决定请求补发还是直接使用最新全量状态。

### 9.5 只同步必要状态

不要把所有内部字段都变成同步状态。应该同步能够让其他客户端重建表现的最小数据：

~~~text
不推荐：每帧同步所有内部计算变量
推荐：同步初始位置、速度和必要状态
~~~

同步太多数据会增加流量、延迟和状态冲突概率。

## 10. 事件和状态的组合设计

很多成熟系统不是二选一，而是事件和状态同时存在。

通用模式：

~~~text
事件：立即通知发生了变化
状态：保存变化后的最终事实
重连/晚到：重新发送或读取状态
~~~

例如打开宝箱：

~~~text
事件：ChestOpened(chestId)
状态：chestOpened[chestId] = true
~~~

例如添加 Buff：

~~~text
事件：BuffAdded(actorId, buffId)
状态：当前 Buff 实例列表、过期时间和扩展数据
~~~

例如成就解锁：

~~~text
事件：AchievementUnlocked(achievementId)
状态：achievementUnlocked[achievementId] = true
~~~

例如游戏开始：

~~~text
事件：GameStarted(roundId)
状态：gameState = "running", roundId = xxx
~~~

事件用于低延迟触发效果，状态用于恢复和校验。事件丢失时，可以通过状态补救；状态更新时，可以让客户端最终收敛。

## 11. 事件和状态的对比

| 对比项 | 事件 | 状态 |
| --- | --- | --- |
| 表达含义 | 过去发生过一次什么事 | 当前是什么情况 |
| 是否有历史语义 | 有 | 通常只保留最新事实 |
| 是否适合一次性动作 | 适合 | 不一定适合 |
| 是否适合长期共享结果 | 不适合单独使用 | 适合 |
| 新玩家加入 | 可能错过 | 可发送当前快照 |
| 丢包后的恢复 | 需要重传或事件日志 | 可重发、重读或重同步 |
| 重复接收 | 通常需要去重 | 通常可幂等覆盖 |
| 典型例子 | 播放动作、爆炸、点击请求 | 门状态、Buff 列表、分数 |
| 主要风险 | 丢失或重复执行 | 版本冲突、旧值覆盖新值 |
| 常用补救 | ACK、重传、唯一 ID、幂等 | 版本号、快照、重连同步、最新值覆盖 |

## 12. 抖音虚拟世界平台中能够确认的内容

### 12.1 Shared Mod 网络模式

现有平台文档介绍，抖音虚拟世界使用 Shared Mod 模式进行网络同步：

- 网络对象在所有客户端上都存在；
- 每个网络对象有主权方；
- 主权方负责修改网络对象的属性并同步给其他玩家；
- 同步变量用于同步持续存在的状态；
- 消息互通用于玩家之间发送消息；
- 玩家位置、动画状态机参数和语音等内容有平台默认同步能力。

因此，开发者需要重点理解：

~~~text
谁拥有对象主权
    ↓
谁可以修改同步变量
    ↓
谁负责让其他客户端获得最新状态
~~~

### 12.2 平台消息 API 的公开语义

平台文档公开了：

~~~text
DouyinRemoteEvent
  FireServer
  FireClient
  FireAllClients

DouyinRemoteFunction
  InvokeServer
  InvokeClient

同步变量
  SetValue
  GetValue
  OnValueChange

主权
  HasOwnership
  GetOwner
  RequestOwnership
  SetOwner
~~~

平台资料同时说明：

- DouyinRemoteEvent 和 DouyinRemoteFunction 不保证消息百分之百到达；
- DouyinRemoteEvent 是异步单向通信；
- DouyinRemoteFunction 支持请求和返回结果，但不能把它理解为绝对可靠的业务事务；
- RemoteEvent 和 RemoteFunction 参数主要支持基础类型；
- 同步变量由主权方修改，其他玩家通过变化事件获得更新；
- 断线重连会触发相应断线、重连和玩家离开事件。

### 12.3 事件和同步变量的使用建议

在当前公开语义下，建议：

| 需求 | 推荐方式 |
| --- | --- |
| 播放一次动作 | RemoteEvent |
| 播放一次音效或特效 | RemoteEvent |
| 请求服务端执行操作 | C2S 事件或协议包，服务端幂等 |
| 返回一次操作结果 | S2C 协议包 |
| 当前门是否打开 | 同步变量 |
| 当前 Buff 列表 | 同步变量或可重同步状态 |
| 当前游戏阶段 | 同步变量或状态快照 |
| 玩家位置和朝向 | 平台默认同步或状态同步 |
| 订单是否已发货 | 服务端持久化状态和 S2C 推送 |
| 成就是否已解锁 | 服务端持久化状态和客户端镜像 |

## 13. DSTemplate 中 CS/SC 的实际链路

根据当前可见的 Assets/DSTemplate/Scripts 源码，客户端网络模块创建了两个 RemoteEvent：

~~~lua
local clientToServerRemote = DouyinRemoteEvent("C2S")
local serverToClientRemote = DouyinRemoteEvent("S2C")
~~~

客户端发送 C2S：

~~~lua
function ClientEventNetwork.FireServer(networkPacketType, serializedMessage)
    clientToServerRemote:FireServer(
        networkPacketType,
        serializedMessage
    )
end
~~~

服务端接收 C2S：

~~~text
DouyinRemoteEvent("C2S")
    ↓
ServerEventNetwork.OnC2SEventHandle(player, ...)
    ↓
读取 packetType 和 serializedMessage
    ↓
NetPacketManager.CreatePacket(type)
    ↓
packet:Deserialize(message)
    ↓
NetPacketManager.Handle(type, player, packet)
    ↓
对应 Server Manager
~~~

服务端发送 S2C：

~~~lua
function ServerEventNetwork.FireClient(player, packetType, ...)
    S2CEvent:FireClient(player, packetType, ...)
end
~~~

服务端业务处理完成后，DSTemplate 使用统一三段式回包：

~~~lua
packet.data = {
    code = code or 0,
    msg = msg or "",
    data = dataPayload or {},
}
~~~

客户端收到 S2C 后：

~~~text
DouyinRemoteEvent("S2C")
    ↓
ClientEventNetwork.OnS2CEventHandle(...)
    ↓
读取 packetType 和 serializedMessage
    ↓
创建网络包并 Deserialize
    ↓
NetPacketManager.Handle(type, packet)
    ↓
ClientPacketRegister 找到对应 Client System
~~~

### 13.1 DSTemplate 中 CS/SC 是 TCP 还是 UDP

当前源码能确认：

- CS/SC 使用平台的 DouyinRemoteEvent 高层抽象；
- 业务包有 packetType、version、data；
- BaseNetPacket 使用 JSON 序列化；
- 模板没有实现裸 TCP recv 循环；
- 模板没有暴露 TCP、UDP、KCP 的 socket、端口或连接参数；
- RemoteEvent 的公开语义是不保证百分之百到达。

当前源码不能确认：

- RemoteEvent 底层一定是 TCP；
- RemoteEvent 底层一定是 UDP；
- RemoteEvent 底层一定是 KCP；
- C2S 和 S2C 一定使用同一种传输方式；
- 不同消息是否有不同可靠等级。

因此：

~~~text
CS/SC 是方向命名，不是传输协议命名。
~~~

packet:Deserialize 解决的是业务协议反序列化，不是在 Lua 层解决 TCP 黏包。底层分帧和可靠性由平台网络层负责，模板使用平台已经封装好的消息边界。

## 14. 如何判断 CS/SC 使用 TCP、UDP 还是 KCP

### 14.1 查找底层源码

搜索：

~~~text
TCP、UDP、KCP、QUIC
socket、connect、listen、send、recv
Transport、Channel、Reliable、Unreliable
ACK、Sequence、Retransmit、Window
~~~

常见线索：

- TcpClient、TcpListener、SocketType.Stream，倾向 TCP；
- UdpClient、SocketType.Dgram、sendto、recvfrom，倾向 UDP；
- Kcp、KcpClient、ikcp_send、ikcp_update、conv，倾向 KCP；
- Reliable、Ack、sn、una、wnd、fastresend，可能表示自定义可靠层或 KCP 类实现。

如果只看到：

~~~text
DouyinRemoteEvent("C2S")
DouyinRemoteEvent("S2C")
FireServer(...)
FireClient(...)
~~~

只能确认平台消息抽象，不能确认底层协议。

### 14.2 查阅平台或 SDK 文档

重点查找：

- 网络传输协议；
- RemoteEvent 可靠性等级；
- 是否按顺序交付；
- 是否自动重传；
- 消息大小限制；
- 是否支持可靠/不可靠通道；
- 网络统计 API。

如果官方资料未公开底层协议，应写成：

~~~text
平台传输协议对创作者 Lua 层未公开，无法确认是 TCP、UDP 还是 KCP。
业务代码应按照平台公开语义设计，而不是依赖对底层协议的猜测。
~~~

### 14.3 运行时观察和抓包

在自己控制的客户端或服务端进程上，可以使用：

- Windows Get-NetTCPConnection；
- Windows Get-NetUDPEndpoint；
- netstat -ano；
- Wireshark；
- tcpdump；
- Unity Profiler 或平台网络统计工具。

但要注意：

- 看到 HTTPS/TCP 连接，不等于游戏实时同步也走 TCP；
- 看到 UDP 端口，不等于某个 CS/SC 就走 UDP；
- 一个进程可能同时使用 HTTP、WebSocket、TCP、UDP、QUIC 等多个连接；
- 加密、NAT、中继、代理和平台网关可能让抓包无法直接对应到业务消息；
- 必须确认连接属于目标进程、目标房间和目标业务。

### 14.4 通过实验观察公开语义

| 实验 | 可以观察什么 | 不能直接证明什么 |
| --- | --- | --- |
| 弱网丢包 | 消息是否容易丢、是否重试 | 不能单独证明 UDP |
| 增加延迟 | 是否出现业务超时、队头等待 | 不能单独证明 TCP |
| 乱序测试 | 平台是否保证顺序 | 不能单独证明 KCP |
| 重复请求 | 业务是否幂等 | 不能证明底层是否去重 |
| 断线重连 | 是否自动重同步 | 不能证明底层传输协议 |
| 抓包 | 端口、连接和包形态 | 加密或中继时可能无法确认业务归属 |

## 15. 网络问题排查顺序

发生客户端没有收到、服务端没有处理或状态不一致时，建议按以下顺序排查：

1. 确认发送端代码是否执行；
2. 确认参数类型符合平台支持范围；
3. 确认通道名称、协议类型和包字段一致；
4. 确认服务端是否收到 C2S；
5. 确认 NetPacketManager 是否成功创建并反序列化包；
6. 确认 C2S Handler 是否注册；
7. 确认服务端业务校验是否拒绝请求；
8. 确认服务端是否发出 S2C；
9. 确认客户端 S2C Handler 是否注册；
10. 确认客户端 System 是否收到并处理回包；
11. 确认 Model 或同步变量是否更新；
12. 确认 View 是否监听变化并刷新；
13. 如果发生断线，确认重连后的状态重同步是否执行；
14. 如果是重复请求，确认业务是否实现幂等；
15. 最后再使用抓包或系统连接工具判断底层传输。

## 16. 最终决策清单

设计一条消息时，可以按下面的规则快速决定：

- 只想让别人立即播放一次动作：使用事件；
- 结果需要被后来加入的人看到：保存为状态；
- 丢失后下一次状态可以恢复：优先状态；
- 丢失后会造成奖励、扣款或结算错误：使用可靠请求、幂等和最终状态；
- 只需要知道当前值，不需要完整历史：使用状态；
- 需要处理完整历史记录：使用事件日志或可靠事件；
- 同一个消息重复执行会有副作用：增加唯一 ID、去重和幂等；
- 需要兼顾低延迟和断线恢复：事件触发即时表现，状态负责最终收敛；
- 使用抖音虚拟世界同步变量时：由主权方修改，其他端监听变化并读取当前值；
- 不要因为状态比事件更抗丢包，就省略版本号、快照、重连同步和主权管理。

## 17. 总结

~~~text
事件回答：发生过什么？
状态回答：现在是什么？

事件适合一次性动作和即时通知；
状态适合长期事实、共享结果和重连恢复。

事件丢失后，通常需要重传、ACK、事件日志或业务重试；
状态丢失后，可以通过重发最新值、读取快照、版本同步和重连恢复。

在抖音虚拟世界中：
RemoteEvent / RemoteFunction 负责平台消息调用；
同步变量负责网络状态同步；
主权决定谁可以修改状态；
CS/SC 表示消息方向；
BaseNetPacket 负责业务包结构和序列化；
幂等、重试和重同步负责业务层的一致性。
~~~



## 18. 通用状态同步：不依赖 varSync 如何实现

前面的同步变量只是平台已经提供好的状态同步工具。即使完全不使用它，状态同步仍然可以自己实现。最核心的模型是：

~~~text
服务端维护权威状态
    ↓
状态变化时增加版本号
    ↓
发送状态快照或增量
    ↓
客户端保存本地镜像
    ↓
客户端按版本应用
    ↓
丢包、乱序、断线时重新请求快照
~~~

例如门对象的状态：

~~~text
DoorState
├─ doorId
├─ isOpen
├─ stateVersion
└─ serverTick
~~~

服务端保存最终事实，客户端保存镜像。客户端镜像只用于显示和预测，不能决定门是否真的打开。

### 18.1 通用状态消息

~~~json
{
  "messageType": "StateSnapshot",
  "entityType": "Door",
  "entityId": "door-001",
  "stateVersion": 12,
  "serverTick": 5600,
  "payload": {
    "isOpen": true
  }
}
~~~

增量消息可以是：

~~~json
{
  "messageType": "StateDelta",
  "entityType": "Door",
  "entityId": "door-001",
  "stateVersion": 13,
  "baseVersion": 12,
  "payload": {
    "isOpen": false
  }
}
~~~

字段含义：

- messageType：快照、增量或重同步请求；
- entityType：对象类型；
- entityId：对象唯一 ID；
- stateVersion：当前状态版本；
- baseVersion：增量所依赖的旧版本；
- serverTick：服务端逻辑帧或时间戳；
- payload：状态内容。

## 19. 服务端维护权威状态

下面是与平台无关的 C# 示例，核心思想也适用于 Java、Go、C++ 和其他语言。

### 19.1 服务端状态对象

~~~csharp
public sealed class DoorState
{
    public string DoorId { get; }
    public bool IsOpen { get; private set; }
    public long StateVersion { get; private set; }
    public long ServerTick { get; private set; }

    public DoorState(string doorId)
    {
        DoorId = doorId;
        IsOpen = false;
        StateVersion = 1;
    }

    public bool SetOpen(bool value, long serverTick)
    {
        if (IsOpen == value)
        {
            return false;
        }

        IsOpen = value;
        StateVersion++;
        ServerTick = serverTick;
        return true;
    }
}
~~~

重点：

- 状态保存于服务端；
- 只有真实变化才递增版本号；
- 重复设置相同值不会无意义地产生新版本；
- 状态版本号和底层网络包序号不是同一个概念。

### 19.2 服务端处理请求并广播状态

~~~csharp
public void OnOpenDoorRequest(Player player, string doorId)
{
    DoorState door = doorManager.Get(doorId);

    if (door == null)
    {
        SendError(player, "door_not_found");
        return;
    }

    if (!player.CanOpenDoor(door))
    {
        SendError(player, "permission_denied");
        return;
    }

    bool changed = door.SetOpen(true, serverClock.Tick);

    if (changed)
    {
        BroadcastDoorState(door);
    }
    else
    {
        SendDoorSnapshot(player, door);
    }
}

public void BroadcastDoorState(DoorState door)
{
    network.Broadcast(new StateSnapshotMessage
    {
        EntityType = "Door",
        EntityId = door.DoorId,
        StateVersion = door.StateVersion,
        ServerTick = door.ServerTick,
        Payload = new
        {
            IsOpen = door.IsOpen
        }
    });
}
~~~

客户端发送的是“请求打开”，而不是要求所有客户端直接执行 OpenDoor。服务端完成权限检查并修改权威状态后，再广播当前状态。

## 20. 客户端保存和应用状态

### 20.1 客户端状态镜像

~~~csharp
public sealed class ClientDoorState
{
    public string DoorId { get; }
    public bool IsOpen { get; private set; }
    public long StateVersion { get; private set; }

    public ClientDoorState(string doorId)
    {
        DoorId = doorId;
        StateVersion = 0;
    }

    public bool ApplySnapshot(long version, bool isOpen)
    {
        if (version <= StateVersion)
        {
            return false;
        }

        IsOpen = isOpen;
        StateVersion = version;
        return true;
    }
}
~~~

### 20.2 接收状态并刷新界面

~~~csharp
public void OnDoorSnapshot(StateSnapshotMessage message)
{
    ClientDoorState door =
        clientDoorStates.GetOrCreate(message.EntityId);

    bool changed = door.ApplySnapshot(
        message.StateVersion,
        message.Payload.IsOpen
    );

    if (changed)
    {
        RefreshDoorView(door);
    }
}

public void RefreshDoorView(ClientDoorState door)
{
    if (door.IsOpen)
    {
        doorView.PlayOpen();
    }
    else
    {
        doorView.PlayClose();
    }
}
~~~

如果同一个版本的快照收到两次，第二次会被忽略。重复同步不会重复发奖励，也不会重复触发核心业务。

## 21. 为什么状态比事件更抗丢包

这里的“更抗丢包”不是说状态底层一定可靠，而是说状态具有更强的恢复能力。

### 21.1 事件是一次性事实

事件表达：

~~~text
在时间 T 发生了一次动作
~~~

如果 OpenChest 事件在 T 时刻丢失，而且之后没有任何消息，接收方无法仅凭这条丢失的事件知道宝箱曾经打开。

### 21.2 状态是可以重新获得的当前事实

状态表达：

~~~text
在当前时刻，系统的事实是 X
~~~

例如：

~~~text
chestOpened = true
doorOpened = true
gameState = running
coin = 100
~~~

这个状态可以在之后通过以下方式再次获得：

- 新玩家加入时发送当前快照；
- 断线重连时重新同步；
- 定期发送完整快照；
- 客户端主动请求当前状态；
- 服务端发现版本落后后补发；
- 主权转移后由新的权威方继续发送。

因此，状态不要求某一条特定消息必须成功到达，只要求系统之后仍然有机会提供最新状态。

### 21.3 状态更新通常可以幂等

事件：

~~~text
OpenDoor()
~~~

重复执行可能重复播放动画、发奖励、生成对象或触发后续逻辑。

状态：

~~~text
doorOpened = true
~~~

重复应用通常仍然得到同一个最终结果。再结合版本号：

~~~csharp
public void ApplyState(long incomingVersion, bool isOpen)
{
    if (incomingVersion <= currentVersion)
    {
        return;
    }

    currentVersion = incomingVersion;
    currentIsOpen = isOpen;
    RefreshView();
}
~~~

旧状态不会覆盖新状态，重复状态也不会重复产生副作用。

### 21.4 状态更适合新加入和断线恢复

老玩家已经打开宝箱：

~~~text
状态：chestOpened = true
~~~

新玩家加入时直接收到这个状态即可，不需要知道之前具体发生过哪一次 OpenChest 事件。

## 22. 事件和状态如何选择

使用下面的问题判断：

| 判断问题 | 更适合事件 | 更适合状态 |
| --- | --- | --- |
| 语义 | 发生了一次什么事 | 当前是什么情况 |
| 新玩家需要知道吗 | 通常不需要 | 通常需要 |
| 丢失后能否靠下一次值恢复 | 通常不能 | 通常可以 |
| 是否只关心最新结果 | 通常不是 | 通常是 |
| 重复执行是否有副作用 | 需要唯一 ID 和去重 | 版本覆盖通常可幂等 |
| 是否需要完整历史 | 事件日志或可靠事件 | 不适合单独保存历史 |
| 例子 | 播放动作、爆炸、点击通知 | 门状态、Buff 列表、分数 |

判断口诀：

~~~text
问“发生了什么” → 事件
问“现在是什么” → 状态
~~~

常见对应关系：

| 业务 | 事件 | 状态 |
| --- | --- | --- |
| 宝箱 | OpenChest(chestId) | chestOpened = true |
| Buff | BuffAdded(actorId, buffId) | 当前 Buff 实例列表 |
| 成就 | UnlockAchievement(id) | achievementUnlocked[id] = true |
| 游戏阶段 | StartGame(roundId) | gameState = running |
| 玩家位置 | Move(position) | currentPosition = position |
| 门 | OpenDoor(doorId) | doorState = open |

## 23. 不使用 varSync 时的快照、增量和重同步

### 23.1 全量快照

全量快照包含当前完整状态：

~~~json
{
  "entityId": "player-001",
  "stateVersion": 20,
  "payload": {
    "position": [10, 2, 8],
    "health": 80,
    "currentBuffs": ["speed", "shield"]
  }
}
~~~

适合：

- 新玩家加入；
- 断线重连；
- 客户端没有本地状态；
- 发现增量版本缺口。

### 23.2 增量更新

增量只传输变化字段：

~~~json
{
  "entityId": "player-001",
  "stateVersion": 21,
  "baseVersion": 20,
  "payload": {
    "health": 75
  }
}
~~~

客户端当前版本不是 baseVersion 时，不能盲目应用：

~~~csharp
public void OnStateDelta(StateDeltaMessage message)
{
    ClientState state = states.GetOrCreate(message.EntityId);

    if (message.BaseVersion != state.Version)
    {
        RequestStateSnapshot(
            message.EntityType,
            message.EntityId,
            state.Version
        );
        return;
    }

    state.ApplyDelta(message);
}
~~~

### 23.3 推荐组合

~~~text
平时：发送增量
定期：发送全量快照
新加入：发送全量快照
重连：发送全量快照或按版本补齐
发现版本缺口：请求全量快照
~~~

状态抗丢包的关键就在这里：增量丢失后，可以用全量快照重新建立基线。

## 24. TCP、UDP、KCP 下分别如何实现

### 24.1 TCP

TCP 已经提供可靠有序的字节流，但仍要自己实现：

- 应用层分帧，解决黏包和拆包；
- 状态版本号，防止重连或业务旧数据覆盖；
- 断线重新连接；
- 重连后发送最新快照。

典型流程：

~~~text
TCP 连接建立
    ↓
客户端认证并加入房间
    ↓
服务端发送全量 StateSnapshot
    ↓
服务端发送 StateDelta
    ↓
客户端按版本应用
    ↓
断线重连后再次发送 StateSnapshot
~~~

TCP 只能保证当前连接中的字节流可靠有序，不能保证断线前未送达的业务状态在新连接中自动出现。

### 24.2 UDP

UDP 不提供可靠、有序和去重，需要应用层决定：

- 是否使用序列号；
- 是否接受旧包；
- 是否发送 ACK；
- 是否超时重传；
- 是否定期发送快照；
- 是否把某些状态设计为“只保留最新值”。

实时位置通常使用：

~~~text
位置包带 sequence
只应用 sequence 更大的包
中间包丢失不重传
下一次位置覆盖旧位置
定期发送完整位置
~~~

重要状态可以使用：

~~~text
状态带 stateVersion
服务端保存最新快照
客户端发送 ACK
超时重传快照
版本不连续时请求快照
断线重连后发送快照
~~~

### 24.3 KCP

KCP 在 UDP 之上补充 ACK、重传和有序交付，可以减少应用层编写可靠传输代码的工作量。

但 KCP 仍然不能替代：

- 状态版本；
- 全量快照；
- 新玩家初始化；
- 断线重连；
- 服务端权威；
- 业务幂等；
- 多方修改冲突处理。

KCP 解决的是传输层问题，状态同步系统解决的是业务状态如何收敛的问题。

## 25. 事件和状态的组合方式

实际项目通常不是二选一，而是两者同时使用：

~~~text
事件：立即通知，触发低延迟表现
状态：保存最终事实，用于校验、晚到和重连恢复
~~~

例如打开宝箱：

~~~text
事件：ChestOpened(chestId)
状态：chestOpened[chestId] = true
~~~

例如添加 Buff：

~~~text
事件：BuffAdded(actorId, buffId)
状态：当前 Buff 实例列表、过期时间和扩展数据
~~~

例如游戏开始：

~~~text
事件：GameStarted(roundId)
状态：gameState = running，roundId = xxx
~~~

事件丢失时，客户端可以通过状态快照恢复；事件到达时，可以立即播放动画或特效。

## 26. 通用实现检查清单

- [ ] 服务端保存唯一权威状态；
- [ ] 状态真实变化时递增版本号；
- [ ] 客户端保存本地镜像；
- [ ] 客户端拒绝旧版本和重复版本；
- [ ] 增量带 baseVersion；
- [ ] 发现版本缺口时请求全量快照；
- [ ] 新玩家加入时发送快照；
- [ ] 断线重连时重新认证并同步快照；
- [ ] UDP 场景按需要实现 ACK、重传和定期快照；
- [ ] TCP 场景实现应用层分帧；
- [ ] 关键业务使用唯一请求 ID 和幂等；
- [ ] 事件只表达一次性动作；
- [ ] 长期事实保存成状态；
- [ ] 状态同步不等于服务端授权，最终结果仍由权威服务端决定。



## 27. TCP 长度前缀和拆包代码

TCP 只提供字节流，所以状态同步消息仍然需要应用层分帧。常见格式是：

~~~text
[4 字节消息长度][消息体]
~~~

发送端：

~~~csharp
public async Task SendFrameAsync(
    Stream stream,
    byte[] payload)
{
    byte[] lengthBytes =
        BitConverter.GetBytes(payload.Length);

    await stream.WriteAsync(
        lengthBytes,
        0,
        lengthBytes.Length
    );

    await stream.WriteAsync(
        payload,
        0,
        payload.Length
    );
}
~~~

接收端不能假设一次 Read 就能拿到完整数据，必须循环读取到指定长度：

~~~csharp
public async Task<byte[]> ReadExactAsync(
    Stream stream,
    int length)
{
    byte[] buffer = new byte[length];
    int offset = 0;

    while (offset < length)
    {
        int read = await stream.ReadAsync(
            buffer,
            offset,
            length - offset
        );

        if (read == 0)
        {
            throw new EndOfStreamException();
        }

        offset += read;
    }

    return buffer;
}
~~~

读取一帧：

~~~csharp
public async Task<byte[]> ReadFrameAsync(Stream stream)
{
    byte[] header = await ReadExactAsync(stream, 4);
    int bodyLength = BitConverter.ToInt32(header, 0);

    if (bodyLength < 0 || bodyLength > 1024 * 1024)
    {
        throw new InvalidDataException(
            "invalid frame length"
        );
    }

    return await ReadExactAsync(stream, bodyLength);
}
~~~

这里解决的是 TCP 的黏包和拆包，不是业务状态的丢包恢复。TCP 连接一旦断开，客户端仍然需要重新认证并获取最新状态快照。

## 28. UDP 下的序列号、ACK 和重发

对于需要最终到达的状态，可以在 UDP 之上增加 ACK 和超时重发：

~~~csharp
public sealed class PendingState
{
    public string PlayerId { get; init; }
    public long StateVersion { get; init; }
    public byte[] Payload { get; init; }
    public DateTime LastSendTime { get; set; }
}

public void SendState(
    string playerId,
    long stateVersion,
    byte[] payload)
{
    udp.Send(playerId, payload);

    pendingStates.Add(new PendingState
    {
        PlayerId = playerId,
        StateVersion = stateVersion,
        Payload = payload,
        LastSendTime = clock.UtcNow
    });
}

public void OnStateAck(
    string playerId,
    long stateVersion)
{
    pendingStates.Remove(
        playerId,
        stateVersion
    );
}

public void TickResend()
{
    foreach (PendingState pending in pendingStates)
    {
        TimeSpan elapsed =
            clock.UtcNow - pending.LastSendTime;

        if (elapsed >= resendTimeout)
        {
            udp.Send(
                pending.PlayerId,
                pending.Payload
            );

            pending.LastSendTime = clock.UtcNow;
        }
    }
}
~~~

但位置这类“只关心最新值”的状态通常不需要这样重传旧包。位置包丢了以后，发送新的位置即可。是否 ACK 和重传，取决于状态是否允许丢失旧版本。

## 29. 版本缺口时请求快照

~~~csharp
public void OnStateDelta(StateDeltaMessage message)
{
    ClientState state =
        states.GetOrCreate(message.EntityId);

    if (message.BaseVersion != state.Version)
    {
        RequestStateSnapshot(
            message.EntityType,
            message.EntityId,
            state.Version
        );
        return;
    }

    state.ApplyDelta(message);
}
~~~

服务端收到请求后，直接发送当前完整状态：

~~~csharp
public void OnSnapshotRequest(
    Player player,
    string entityType,
    string entityId,
    long clientVersion)
{
    object currentState =
        stateManager.Get(entityType, entityId);

    SendSnapshot(player, currentState);
}
~~~

如果状态不复杂，发现版本缺口后直接发送全量快照，通常比保存很长的增量历史更简单可靠。

## 30. 一个最实用的判断流程

设计网络消息前，可以按以下顺序判断：

1. 这个数据是在描述一次动作，还是描述当前事实？
2. 新加入的玩家是否必须知道？
3. 丢掉一次消息后，下一次状态能不能恢复？
4. 重复执行是否会造成发奖、扣款或生成对象等副作用？
5. 接收方需要完整历史，还是只需要最新结果？
6. 是否允许使用快照覆盖本地旧数据？
7. 是否需要版本号、ACK、重传或重连补偿？

可以归纳为：

~~~text
发生一次动作，且错过后无须补看
    → 事件

当前事实，后来加入者也必须知道
    → 状态

既要立刻播放，又要断线恢复
    → 事件 + 状态

必须保证业务结果
    → 可靠请求 + 幂等 + 最终状态
~~~

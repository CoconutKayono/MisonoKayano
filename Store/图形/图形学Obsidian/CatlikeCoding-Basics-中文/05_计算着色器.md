# 计算着色器（Compute Shaders）

*渲染一百万个立方体（Rendering One Million Cubes）*

> 本教程由 Catlike Coding 的 [Jasper Flick](https://catlikecoding.com/) 撰写，原文地址：[Compute Shaders](https://catlikecoding.com/unity/tutorials/basics/compute-shaders/)。本文为简体中文翻译版，代码保留原文，仅翻译讲解文字。

- 把位置存储在计算缓冲区里。
- 让 GPU 完成大部分工作。
- 程序化地绘制大量立方体。
- 把整个函数库复制到 GPU。

这是关于学习 Unity 基础知识的系列教程中的第五篇。这次我们将使用计算着色器，显著提高图表的分辨率。

本教程使用 Unity 2020.3.6f1 制作。

![一百万个移动的立方体。](https://catlikecoding.com/unity/tutorials/basics/compute-shaders/tutorial-image.jpg)

## 把工作移到 GPU

图表的分辨率越高，CPU 和 GPU 要做的工作就越多——计算位置和渲染立方体。点的数量等于分辨率的平方，所以把分辨率翻倍会显著增加工作量。在分辨率 100 时我们也许能达到 60FPS，但我们能推到多远？如果遇到瓶颈，能不能通过换一种方法突破它？

### 分辨率 200

让我们先把 `Graph` 的最大分辨率从 100 翻倍到 200，看看性能如何。

```diff
	[SerializeField, Range(10, 200)]
	int resolution = 10;
```

![分辨率设为 200 的图表。](https://catlikecoding.com/unity/tutorials/basics/compute-shaders/moving-work-to-the-gpu/resolution-200-inspector.png)

现在我们渲染 40,000 个点。以我的情况，BRP 构建的平均帧率降到 10FPS，URP 构建降到 15FPS。这对流畅体验来说太低了。

![在分辨率 200、无 VSync 下分析构建产物，BRP 和 URP。](https://catlikecoding.com/unity/tutorials/basics/compute-shaders/moving-work-to-the-gpu/resolution-200-profiler-drp.png)

分析构建产物会发现，所有事情都花了大约四倍的时间，这说得通。

### GPU 图表

对 40,000 个点做排序、批处理，然后把变换矩阵发送给 GPU，要花很多时间。一个矩阵由十六个 `float` 数字组成，每个四字节，所以每个矩阵总共 64B。对于 40,000 个点，那就是 256 万字节——大约 2.44MiB——每次绘制点时都要复制到 GPU。URP 每帧要这么做两次，一次用于阴影，一次用于常规几何。BRP 至少要做三次，因为它多一个仅深度通道，此外每多一盏主方向光之外的灯还要再加一次。

> **MiB 是什么？**
>
> 因为计算机硬件用二进制数字来寻址内存，所以它按 2 的幂来划分，而不是 10 的幂。MiB 是 mebibyte 的后缀，即 2<sup>20</sup> = 1,024<sup>2</sup> = 1,048,576 字节。这最初被称为兆字节——用 MB 表示——但现在 MB 应该表示 10<sup>6</sup> 字节，与官方对“百万”的定义一致。然而，MB、GB 等仍经常被用来代替 MiB、GiB 等。

一般来说，最好尽量减少 CPU 和 GPU 之间的通信与数据传输。因为我们显示点只需要它们的位置，理想情况下这些数据只存在于 GPU 一侧。那会消除大量数据传输。但那样 CPU 就不再能计算位置了，必须由 GPU 来做。幸运的是，GPU 相当适合这个任务。

让 GPU 计算位置需要不同的方法。我们让当前图表保持原样用于对比，然后创建一个新的。复制 `Graph` C# 资源文件，重命名为 `GPUGraph`。从新类里移除 `pointPrefab` 和 `points` 字段。然后移除它的 `Awake`、`UpdateFunction` 和 `UpdateFunctionTransition` 方法。我只把新类里删除的代码标出来，而不是把所有东西都标成新代码。

```diff
using UnityEngine;

public class GPUGraph : MonoBehaviour {

-	//[SerializeField]
-	//Transform pointPrefab;

	[SerializeField, Range(10, 200)]
	int resolution = 10;

	[SerializeField]
	FunctionLibrary.FunctionName function;

	public enum TransitionMode { Cycle, Random }

	[SerializeField]
	TransitionMode transitionMode = TransitionMode.Cycle;

	[SerializeField, Min(0f)]
	float functionDuration = 1f, transitionDuration = 1f;

-	//Transform[] points;

	float duration;

	bool transitioning;

	FunctionLibrary.FunctionName transitionFunction;

-	//void Awake () { … }

	void Update () { … }

	void PickNextFunction () { … }

-	//void UpdateFunction () { … }

-	//void UpdateFunctionTransition () { … }
}
```

然后移除 `Update` 末尾调用那些现已缺失的方法的代码。

```diff
	void Update () {
		…

-		//if (transitioning) {
-		//	UpdateFunctionTransition();
-		//}
-		//else {
-		//	UpdateFunction();
-		//}
	}
```

我们新的 `GPUGraph` 组件是一个被掏空了的 `Graph` 版本，暴露同样的配置选项，只是没有 prefab。它包含从一个函数过渡到另一个函数的逻辑，但除此之外什么都不做。用这个组件创建一个游戏对象，分辨率 200，设为循环、瞬时过渡。停用原来的图表对象，只让 GPU 版本保持激活。

![GPU 图表组件，设为瞬时过渡。](https://catlikecoding.com/unity/tutorials/basics/compute-shaders/moving-work-to-the-gpu/gpu-graph-component.png)

### 计算缓冲区

要把位置存储在 GPU 上，我们需要为它们分配空间。做法是创建一个 `ComputeBuffer` 对象。给 `GPUGraph` 添加一个位置缓冲区字段，并在新的 `Awake` 方法里创建该对象，通过调用 `new ComputeBuffer()`——这被称为构造方法。它就像分配一个新数组，但针对的是对象或结构体。

```diff
+	ComputeBuffer positionsBuffer;

+	void Awake () {
+		positionsBuffer = new ComputeBuffer();
+	}
```

我们需要把缓冲区的元素数量作为参数传入，也就是分辨率的平方，就像 `Graph` 的 positions 数组一样。

```diff
		positionsBuffer = new ComputeBuffer(resolution * resolution);
```

计算缓冲区包含任意的无类型数据。我们必须通过第二个参数指定每个元素的精确字节大小。我们需要存储 3D 位置向量，由三个 `float` 数字组成，所以元素大小是三乘以四字节。因此 40,000 个位置需要 0.48MB 或大约 0.46MiB 的 GPU 内存。

```diff
		positionsBuffer = new ComputeBuffer(resolution * resolution, 3 * 4);
```

这样我们就得到了一个计算缓冲区，但这些对象无法在热重载后存活，这意味着如果我们在运行模式下改代码，它会消失。我们可以通过把 `Awake` 方法替换为 `OnEnable` 方法来处理这一点，`OnEnable` 在组件每次被启用时调用。它发生在组件唤醒之后——除非它被禁用——以及热重载完成之后。

```diff
	void OnEnable () {
		positionsBuffer = new ComputeBuffer(resolution * resolution, 3 * 4);
	}
```

除此之外，我们还应该加一个配套的 `OnDisable` 方法，它在组件被禁用时调用，图表被销毁时以及热重载之前也会发生。让它通过调用缓冲区的 `Release` 方法来释放它。这表明该缓冲区占用的 GPU 内存可以立即被释放。

```diff
+	void OnDisable () {
+		positionsBuffer.Release();
+	}
```

因为在这之后我们不再使用这个特定的对象实例，显式地把字段设为引用 `null` 是个好主意。这样如果图表在运行模式下被禁用或销毁，该对象就可以在 Unity 内存垃圾回收下次运行时被回收。

```diff
	void OnDisable () {
		positionsBuffer.Release();
+		positionsBuffer = null;
	}
```

> **如果我们不显式释放缓冲区会怎样？**
>
> 如果没有任何东西持有对该对象的引用，它最终会在垃圾回收器回收它时被释放。但什么时候发生是任意的。最好尽快显式释放它，避免堵塞内存。

### 计算着色器

要在 GPU 上计算位置，我们必须为它写一个脚本，具体就是一个计算着色器。通过 *Assets / Create / Shader / Compute Shader* 创建一个。它将成为我们 `FunctionLibrary` 类的 GPU 等价物，所以也命名为 *FunctionLibrary*。虽然它被称为着色器并使用 HLSL 语法，但它作为通用程序运行，而不是用于渲染东西的常规着色器。因此我把资源放在 *Scripts* 文件夹里。

![Function library 计算着色器资源。](https://catlikecoding.com/unity/tutorials/basics/compute-shaders/moving-work-to-the-gpu/compute-shader-asset.png)

打开资源文件，移除它的默认内容。计算着色器需要包含一个称为内核（kernel）的主函数，通过 `#pragma kernel` 指令加一个名字来指明，就像我们表面着色器的 `#pragma surface`。把这条指令作为第一行、也是当前唯一一行，使用 `FunctionKernel` 这个名字。

```diff
+#pragma kernel FunctionKernel
```

在指令下面定义函数。它是一个 `void` 函数，最初没有参数。

```diff
#pragma kernel FunctionKernel

+void FunctionKernel () {}
```

### 计算线程

当 GPU 被指示执行计算着色器函数时，它把工作划分成组（group），然后调度它们独立并行地运行。每个组又由若干线程（thread）组成，这些线程执行相同的计算但输入不同。我们必须通过给内核函数添加 `numthreads` 属性来指定每个组应有多少线程。它需要三个整数参数。最简单的选项是三个参数都用 1，这让每个组只运行一个线程。

```diff
+[numthreads(1, 1, 1)]
void FunctionKernel () {}
```

GPU 硬件包含计算单元，它们总是以固定数量的线程步调一致地运行。这些被称为 warp 或 wavefront。如果一个组的线程数少于 warp 大小，有些线程会空闲运行，浪费时间。如果线程数反而超过 warp 大小，那么 GPU 会为每个组使用更多 warp。一般来说 64 个线程是好的默认值，因为这匹配 AMD GPU 的 warp 大小，而 NVidia GPU 是 32，所以后者会为每个组使用两个 warp。实际上硬件更复杂，能对线程组做更多事，但这与我们简单的图表无关。

`numthreads` 的三个参数可以用于把线程组织成一维、二维或三维。例如，(64, 1, 1) 给我们一维的 64 个线程，而 (8, 8, 1) 给我们同样的数量，但呈现为 2D 的 8×8 方形网格。因为我们基于 2D UV 坐标来定义点，所以用后一个选项。

```diff
[numthreads(8, 8, 1)]
```

每个线程由一个三元素无符号整数向量标识，我们可以通过给函数添加一个 `uint3` 参数来访问它。

```diff
void FunctionKernel (uint3 id) {}
```

> **什么是无符号整数？**
>
> 它是一种没有数字符号指示的整数，因此是无符号的。无符号整数要么是零要么是正数。因为无符号整数不需要用一位来表示符号，所以它们能存储更大的值，但这通常不重要。

我们必须显式表明这个参数是线程标识符。做法是在参数名后写一个冒号，后面跟 `SV_DispatchThreadID` 着色器语义关键字。

```diff
void FunctionKernel (uint3 id: SV_DispatchThreadID) {}
```

### UV 坐标

如果我们知道图表的步长，就可以把线程标识符转换为 UV 坐标。为它添加一个名为 *_Step* 的计算着色器属性，就像我们给表面着色器添加 *_Smoothness* 那样。

```diff
+float _Step;

[numthreads(8, 8, 1)]
void FunctionKernel (uint3 id: SV_DispatchThreadID) {}
```

然后创建一个 `GetUV` 函数，接收线程标识符作为参数，返回作为 `float2` 的 UV 坐标。我们可以使用在 `Graph` 里循环点时应用的相同逻辑。取标识符的 XY 分量，加 0.5，乘以步长，再减一。

```diff
float _Step;

+float2 GetUV (uint3 id) {
+	return (id.xy + 0.5) * _Step - 1.0;
+}
```

### 设置位置

要存储位置，我们需要访问 positions 缓冲区。在 HLSL 中，计算缓冲区被称为结构化缓冲区（structured buffer）。因为我们要写入它，所以需要启用读写的版本，也就是 `RWStructuredBuffer`。为它添加一个名为 *_Positions* 的着色器属性。

```diff
+RWStructuredBuffer _Positions;

float _Step;
```

这种情况下，我们必须指定缓冲区的元素类型。位置是 `float3` 值，我们直接把它写在 `RWStructuredBuffer` 后面、尖括号之间。

```diff
RWStructuredBuffer<float3> _Positions;
```

要存储一个点的位置，我们需要基于线程标识符给它分配一个索引。为此我们需要知道图表的分辨率。所以添加一个 *_Resolution* 着色器属性，用 `uint` 类型来匹配标识符的类型。

```diff
RWStructuredBuffer<float3> _Positions;

+uint _Resolution;

float _Step;
```

然后创建一个 `SetPosition` 函数，给定标识符和要设置的位置来设置位置。对于索引，我们用标识符的 X 分量加上它的 Y 分量乘以图表分辨率。这样我们就把 2D 数据顺序地存储在 1D 数组里。

```diff
float2 GetUV (uint3 id) {
	return (id.xy + 0.5) * _Step - 1.0;
}

+void SetPosition (uint3 id, float3 position) {
+	_Positions[id.x + id.y * _Resolution] = position;
+}
```

![3×3 网格的位置索引。](https://catlikecoding.com/unity/tutorials/basics/compute-shaders/moving-work-to-the-gpu/3x3-grid-indices.png)

我们必须意识到一件事：我们的每个组计算一个 8×8 点的网格。如果图表的分辨率不是 8 的倍数，那么最后一行和一列的组会计算一些越界的点。那些点的索引要么落在缓冲区之外，要么与有效索引冲突，从而损坏我们的数据。

![越界。](https://catlikecoding.com/unity/tutorials/basics/compute-shaders/moving-work-to-the-gpu/3x3-grid-indices-out-of-bounds.png)

可以通过只在 X 和 Y 标识符分量都小于分辨率时才存储位置，来避免无效位置。

```diff
void SetPosition (uint3 id, float3 position) {
+	if (id.x < _Resolution && id.y < _Resolution) {
		_Positions[id.x + id.y * _Resolution] = position;
+	}
}
```

### 波函数

现在我们可以在 `FunctionKernel` 里获取 UV 坐标，并用我们创建的函数设置位置。先用零作为位置。

```diff
[numthreads(8, 8, 1)]
void FunctionKernel (uint3 id: SV_DispatchThreadID) {
+	float2 uv = GetUV(id);
+	SetPosition(id, 0.0);
}
```

我们最初只支持 *Wave* 函数，它是我们库里最简单的。要让它动起来，我们需要知道时间，所以添加一个 *_Time* 属性。

```diff
float _Step, _Time;
```

然后从 `FunctionLibrary` 类复制 `Wave` 方法，插到 `FunctionKernel` 上方。要把它变成 HLSL 函数，移除 `public static` 限定符，把 `Vector3` 替换为 `float3`，把 `Sin` 替换为 `sin`。

```diff
+float3 Wave (float u, float v, float t) {
+	float3 p;
+	p.x = u;
+	p.y = sin(PI * (u + v + t));
+	p.z = v;
+	return p;
+}
```

唯一还缺的是 `PI` 的定义。我们通过为它定义一个宏来添加。做法是写 `#define PI` 后面跟数字，我们用 `3.14159265358979323846`。这比 `float` 值能表示的精度高得多，但我们把选择合适的近似值交给着色器编译器。

```diff
+#define PI 3.14159265358979323846

float3 Wave (float u, float v, float t) { … }
```

现在在 `FunctionKernel` 里用 `Wave` 函数计算位置，而不是用零。

```diff
void FunctionKernel (uint3 id: SV_DispatchThreadID) {
	float2 uv = GetUV(id);
	SetPosition(id, Wave(uv.x, uv.y, _Time));
}
```

### 派发计算着色器内核

我们有了一个计算并存储图表点位置的内核函数。下一步是在 GPU 上运行它。为此 `GPUGraph` 需要访问计算着色器，所以给它添加一个可序列化的 `ComputeShader` 字段，然后把资源连接到组件上。

```diff
+	[SerializeField]
+	ComputeShader computeShader;
```

![已分配计算着色器。](https://catlikecoding.com/unity/tutorials/basics/compute-shaders/moving-work-to-the-gpu/compute-shader-assigned.png)

我们需要设置计算着色器的几个属性。为此我们需要知道 Unity 为它们使用的标识符。这些是整数，可以通过用名字字符串调用 `Shader.PropertyToID` 来获取。这些标识符按需获取，在应用或编辑器运行期间保持不变，所以我们可以直接把标识符存储在静态字段里。从 *_Positions* 属性开始。

```diff
+	static int positionsId = Shader.PropertyToID("_Positions");
```

我们永远不会改变这些字段，可以通过给它们加 `readonly` 限定符来表明这一点。除了让字段的意图更清晰，这也指示编译器：如果我们在别处给它赋值，就产生错误。

```diff
	static readonly int positionsId = Shader.PropertyToID("_Positions");
```

> **我们难道不应该也把 FunctionLibrary.functions 标记为 readonly 吗？**
>
> 虽然这有道理，但 `readonly` 对引用类型不太适用，因为它只强制字段值本身不被改变。对象——这里是数组——本身仍然可以被修改。所以它能防止赋一个完全不同的数组，但不能防止修改它的元素。我倾向于只对像 `int` 这样的原始类型使用 `readonly`。

还要存储 *_Resolution*、*_Step* 和 *_Time* 的标识符。

```diff
	static readonly int
		positionsId = Shader.PropertyToID("_Positions"),
+		resolutionId = Shader.PropertyToID("_Resolution"),
+		stepId = Shader.PropertyToID("_Step"),
+		timeId = Shader.PropertyToID("_Time");
```

接下来，创建一个 `UpdateFunctionOnGPU` 方法，计算步长，并设置计算着色器的 resolution、step 和 time 属性。做法是对 resolution 调用 `SetInt`，对其他两个属性调用 `SetFloat`，以标识符和值作为参数。

```diff
+	void UpdateFunctionOnGPU () {
+		float step = 2f / resolution;
+		computeShader.SetInt(resolutionId, resolution);
+		computeShader.SetFloat(stepId, step);
+		computeShader.SetFloat(timeId, Time.time);
+	}
```

> **着色器的 resolution 属性不是 uint 吗？**
>
> 是的，但只有设置普通整数的方法，没有设置无符号整数的方法。这没问题，因为正的 `int` 值等价于 `uint` 值。

我们还必须设置 positions 缓冲区，它不复制任何数据，而是把缓冲区链接到内核。做法是调用 `SetBuffer`，它和其他方法类似，只是需要额外一个参数。它的第一个参数是内核函数的索引，因为一个计算着色器可以包含多个内核，缓冲区可以链接到特定的内核。我们可以通过在计算着色器上调用 `FindKernel` 来获取内核索引，但我们唯一的内核总是索引零，所以可以直接用这个值。

```diff
		computeShader.SetFloat(timeId, Time.time);

+		computeShader.SetBuffer(0, positionsId, positionsBuffer);
```

设置缓冲区之后，我们可以运行内核，通过对计算着色器调用 `Dispatch`、传四个整数参数。第一个是内核索引，另外三个是要运行的组数，同样按维度划分。所有维度都用 1 意味着只计算第一组 8×8 的位置。

```diff
		computeShader.SetBuffer(0, positionsId, positionsBuffer);

+		computeShader.Dispatch(0, 1, 1, 1);
```

因为我们固定的 8×8 组大小，X 和 Y 维度上所需的组数等于分辨率除以八、向上取整。我们可以执行一个 `float` 除法，把结果传给 `Mathf.CeilToInt`。

```diff
+		int groups = Mathf.CeilToInt(resolution / 8f);
		computeShader.Dispatch(0, groups, groups, 1);
```

要最终运行我们的内核，在 `Update` 末尾调用 `UpdateFunctionOnGPU`。

```diff
	void Update () {
		…

+		UpdateFunctionOnGPU();
	}
```

现在我们每帧都在运行模式下计算图表的所有位置，尽管我们还没注意到，也还没对这些数据做任何事。

## 程序化绘制

位置在 GPU 上可用了，下一步就是绘制点，而无需从 CPU 向 GPU 发送任何变换矩阵。因此着色器必须从缓冲区获取正确的位置，而不是依赖标准矩阵。

### 绘制大量网格

因为位置已经存在于 GPU 上，我们不需要在 CPU 一侧跟踪它们。我们甚至不需要为它们创建游戏对象。相反，我们通过一条命令指示 GPU 用一个特定材质多次绘制一个特定网格。要配置画什么，给 `GPUGraph` 添加可序列化的 `Material` 和 `Mesh` 字段。我们最初用已有的 *Point Surface* 材质——那是我们之前用 BRP 画点用的。网格我们用默认立方体。

```diff
+	[SerializeField]
+	Material material;

+	[SerializeField]
+	Mesh mesh;
```

![已配置材质和网格。](https://catlikecoding.com/unity/tutorials/basics/compute-shaders/procedural-drawing/material-mesh.png)

程序化绘制通过调用 `Graphics.DrawMeshInstancedProcedural` 来完成，以网格、子网格索引和材质作为参数。子网格索引用于网格由多个部分组成的情况，我们不是这种情况，所以用索引零。在 `UpdateFunctionOnGPU` 末尾做这件事。

```diff
	void UpdateFunctionOnGPU () {
		…

+		Graphics.DrawMeshInstancedProcedural(mesh, 0, material);
	}
```

> **难道我们不应该用 DrawMeshInstancedIndirect 吗？**
>
> `DrawMeshInstancedIndirect` 方法用于你不在 CPU 一侧知道要绘制多少实例的情况，而是通过缓冲区用计算着色器提供那个信息。

因为这种绘制方式不使用游戏对象，Unity 不知道绘制发生在场景的哪里。我们必须通过提供一个包围盒（bounding box）作为额外参数来表明这一点。这是一个轴对齐的盒子，表示我们所绘内容的边界。Unity 用它来确定绘制能否被跳过，因为它落在了相机的视野之外。这被称为视锥体裁剪。所以现在不再逐点评估边界，而是对整个图表一次性完成。这对我们的图表是合适的，因为我们的意图就是整体地观察它。

我们的图表位于原点，点应该保持在一个大小为 2 的立方体内。我们可以通过调用 `Bounds` 构造方法、以 `Vector3.zero` 和放大两倍的 `Vector3.one` 作为参数，为它创建一个 bounds 值。

```diff
+		var bounds = new Bounds(Vector3.zero, Vector3.one * 2f);
		Graphics.DrawMeshInstancedProcedural(mesh, 0, material, bounds);
```

但点也有大小，其一半可能朝所有方向戳出边界。所以我们应该相应地增大边界。

```diff
		var bounds = new Bounds(Vector3.zero, Vector3.one * (2f + 2f / resolution));
```

我们必须传给 `DrawMeshInstancedProcedural` 的最后一个参数是要绘制多少个实例。这应该匹配 positions 缓冲区里的元素数量，我们可以通过它的 `count` 属性获取。

```diff
		Graphics.DrawMeshInstancedProcedural(
			mesh, 0, material, bounds, positionsBuffer.count
		);
```

![重叠的单位立方体。](https://catlikecoding.com/unity/tutorials/basics/compute-shaders/procedural-drawing/unit-cubes.png)

> **为什么进入运行模式现在会完全冻结 Unity，或不显示立方体？**
>
> 此时的行为取决于 Unity 版本。继续下去，一旦一切设置正确、着色器用上了位置，它就应该能工作。

进入运行模式时，我们现在会看到位于原点的一个纯色单位立方体。是同一个立方体被每个点渲染一次，但变换矩阵是单位矩阵，所以它们全部重叠。性能比以前好多了，因为几乎不需要向 GPU 复制数据，所有点用一次绘制调用就画完了。另外，Unity 不必为每个点做任何裁剪。它也不按视空间深度对点排序——它通常会这么做，好让离相机最近的点先画。深度排序使不透明几何体的渲染更高效，因为它避免了过度绘制，但我们的程序化绘制命令只是简单地一个接一个渲染这些点。然而，被消除的 CPU 工作和数据传输，加上 GPU 以全速渲染所有立方体的能力，足以弥补这一点。

### 获取位置

要获取我们存储在 GPU 上的点位置，我们必须创建一个新着色器，最初用于 BRP。复制 *Point Surface* 着色器，重命名为 *Point Surface GPU*。把它的着色器菜单标签也改成一致。另外，因为我们现在依赖计算着色器填充的结构化缓冲区，把着色器的 target 级别提高到 4.5。这不是严格必需的，但表明我们需要计算着色器支持。

```diff
Shader "Graph/Point Surface GPU" {

	Properties {
		_Smoothness ("Smoothness", Range(0,1)) = 0.5
	}

	SubShader {
		CGPROGRAM
		#pragma surface ConfigureSurface Standard fullforwardshadows
		#pragma target 4.5

		…
		ENDCG
	}

	FallBack "Diffuse"
}
```

> **target 级别 4.5 是什么意思？**
>
> [它表明我们至少需要 OpenGL ES 3.1 的能力。](https://docs.unity3d.com/Manual/SL-ShaderCompileTargets.html) 它对老式的 DX11 之前的 GPU 无效，对 OpenGL ES 2.0 和 3.0 也无效。这也排除了 WebGL。WebGL 2.0 有一些实验性的计算着色器支持，但 Unity 目前不支持。
>
>
> 在支持不足时运行 GPU 图表，最好的结果也只是所有点重叠，就像现在这样。所以如果你面向这样的平台，就必须坚持旧方法，或者两者都包含，并在需要时回退到分辨率低得多的 CPU 图表。

程序化渲染的工作方式类似 GPU 实例化，但我们需要指定一个额外选项，通过添加 `#pragma instancing_options` 指令来表明。这种情况下，我们必须跟在它后面写 `procedural:ConfigureProcedural` 选项。

```diff
		#pragma surface ConfigureSurface Standard fullforwardshadows
+		#pragma instancing_options procedural:ConfigureProcedural
```

这表明表面着色器需要为每个顶点调用一个 `ConfigureProcedural` 函数。它是一个没有任何参数的 `void` 函数。把它加到我们的着色器里。

```diff
+		void ConfigureProcedural () {}

		void ConfigureSurface (Input input, inout SurfaceOutputStandard surface) {
			surface.Albedo = saturate(input.worldPos * 0.5 + 0.5);
			surface.Smoothness = _Smoothness;
		}
```

默认情况下这个函数只会在常规绘制通道被调用。要也在渲染阴影时应用它，我们必须表明需要一个自定义阴影通道，通过在 `#pragma surface` 指令里加 `addshadow`。

```diff
		#pragma surface ConfigureSurface Standard fullforwardshadows addshadow
```

现在添加与我们在计算着色器里声明的相同的 positions 缓冲区字段。这次我们只读取它，所以给它 `StructuredBuffer` 类型而不是 `RWStructuredBuffer`。

```diff
+		StructuredBuffer<float3> _Positions;

		void ConfigureProcedural () {}
```

但我们只应该对专门为程序化绘制编译的着色器变体这么做。当 `UNITY_PROCEDURAL_INSTANCING_ENABLED` 宏标签被定义时，就是这种情况。我们可以通过写 `#if defined(UNITY_PROCEDURAL_INSTANCING_ENABLED)` 来检查。这是一个预处理器指令，指示编译器只在标签被定义时才包含后面几行的代码。这持续到只含 `#endif` 指令的那一行。它像 C# 里的条件块，只不过代码是在编译期间被包含或省略。最终代码里不存在分支。

```diff
+		#if defined(UNITY_PROCEDURAL_INSTANCING_ENABLED)
+			StructuredBuffer<float3> _Positions;
+		#endif
```

我们对将放进 `ConfigureProcedural` 函数的代码也必须做同样的事。

```diff
		void ConfigureProcedural () {
+			#if defined(UNITY_PROCEDURAL_INSTANCING_ENABLED)
+			#endif
		}
```

现在我们可以通过用当前正在绘制的实例的标识符索引 positions 缓冲区，来获取点的位置。我们可以通过全局可访问的 `unity_InstanceID` 访问它的标识符。

```diff
		void ConfigureProcedural () {
			#if defined(UNITY_PROCEDURAL_INSTANCING_ENABLED)
+				float3 position = _Positions[unity_InstanceID];
			#endif
		}
```

### 创建变换矩阵

一旦有了位置，下一步是为该点创建对象到世界的变换矩阵。为保持尽可能简单，我们把图表固定在世界原点，不旋转也不缩放。调整 *GPU Graph* 游戏对象的 `Transform` 组件不会有任何效果，因为我们不使用它做任何事。

我们只需要应用点的位置和缩放。位置存储在 4×4 变换矩阵的最后一列，而缩放存储在矩阵对角线上。矩阵的最后一个分量总是设为 1。对我们来说其他所有分量都是零。

![带位置和缩放的变换矩阵。](https://catlikecoding.com/unity/tutorials/basics/compute-shaders/procedural-drawing/transformation-matrix.png)

变换矩阵用于把顶点从对象空间转换到世界空间。它通过 `unity_ObjectToWorld` 全局提供。因为我们程序化绘制，它是一个单位矩阵，所以我们必须替换它。先把整个矩阵设为零。

```diff
				float3 position = _Positions[unity_InstanceID];

+				unity_ObjectToWorld = 0.0;
```

我们可以通过 `float4(position, 1.0)` 构造位置偏移的列向量。我们可以把它设为第四列，通过赋给 `unity_ObjectToWorld._m03_m13_m23_m33`。

```diff
				unity_ObjectToWorld = 0.0;
+				unity_ObjectToWorld._m03_m13_m23_m33 = float4(position, 1.0);
```

然后给我们的着色器加一个 `float _Step` 着色器属性，并把它赋给 `unity_ObjectToWorld._m00_m11_m22`。这正确地缩放了我们的点。

```diff
+		float _Step;

		void ConfigureProcedural () {
			#if defined(UNITY_PROCEDURAL_INSTANCING_ENABLED)
				float3 position = _Positions[unity_InstanceID];

				unity_ObjectToWorld = 0.0;
				unity_ObjectToWorld._m03_m13_m23_m33 = float4(position, 1.0);
+				unity_ObjectToWorld._m00_m11_m22 = _Step;
			#endif
		}
```

还有一个 `unity_WorldToObject` 矩阵，包含逆变换，用于变换法线向量。当应用非均匀变形时，需要它来正确变换方向向量。但因为这不适用于我们的图表，我们可以忽略它。不过我们应该通过给实例化选项 pragma 加 `assumeuniformscaling`，把这一点告诉我们的着色器。

```diff
		#pragma instancing_options assumeuniformscaling procedural:ConfigureProcedural
```

现在创建一个使用这个着色器、启用了 GPU 实例化的新材质，并把它赋给我们的 GPU 图表。

![使用 GPU 材质。](https://catlikecoding.com/unity/tutorials/basics/compute-shaders/procedural-drawing/using-point-surface-gpu-material.png)

要让这正确工作，我们必须设置材质的属性，就像之前设置计算着色器一样。在 `UpdateFunctionOnGPU` 里、绘制之前，对材质调用 `SetBuffer` 和 `SetFloat`。这种情况下我们不必为缓冲区提供内核索引。

```diff
+		material.SetBuffer(positionsId, positionsBuffer);
+		material.SetFloat(stepId, step);
		var bounds = new Bounds(Vector3.zero, Vector3.one * (2f + 2f / resolution));
		Graphics.DrawMeshInstancedProcedural(
			mesh, 0, material, bounds, positionsBuffer.count
		);
```

40,000 个带阴影的立方体，用 BRP 绘制。

进入运行模式时我们再次看到图表，但现在它的 40,000 个点以稳定的 60FPS 渲染。如果我关掉编辑器游戏窗口的 VSync，它飙到 245FPS。我们的程序化方法显然比每个点一个游戏对象快得多。

![在 VSync 下分析 BRP 构建产物。](https://catlikecoding.com/unity/tutorials/basics/compute-shaders/procedural-drawing/profiler-drp-vsync.png)

分析构建产物会发现，我们的 `GPUGraph` 组件几乎无事可做。它只是指示 GPU 运行一个计算着色器内核，然后告诉 Unity 程序化地绘制大量点。这不会立即发生。计算着色器被调度，会在 GPU 空闲时运行。程序化绘制命令随后由 BRP 发送给 GPU。该命令被发送三次，一次用于仅深度通道，一次用于阴影，一次用于最终绘制。GPU 会先运行计算着色器，只有等它完成之后才能绘制场景，之后它才能运行下一次计算着色器调用。对 40,000 个点，Unity 做这个毫无问题。

### 冲向一百万

既然它处理 40,000 个点这么轻松，让我们看看 GPU 图表能不能处理一百万个点。但在此之前，我们必须意识到异步着色器编译。这是 Unity 编辑器的特性，构建产物没有。编辑器只在需要时才编译着色器，而不是提前编译。这在编辑着色器时能节省大量编译时间，但意味着着色器并不总是立即可用。发生这种情况时，会临时使用一个统一的青色占位着色器，直到着色器编译过程完成——编译是并行进行的。这通常没问题，但占位着色器不适用于程序化绘制。它会显著拖慢绘制过程。如果这在尝试渲染一百万个点时发生，很可能会冻结然后崩溃 Unity，甚至可能连带着整台机器。

我们可以通过项目设置关掉异步着色器编译，但这只是我们的 *Point Surface GPU* 着色器的问题。幸运的是，我们可以通过给特定着色器加 `#pragma editor_sync_compilation` 指令，告诉 Unity 对它使用同步编译。这会强制 Unity 在着色器第一次被使用前停顿并立即编译它，避免占位着色器。

```diff
		#pragma surface ConfigureSurface Standard fullforwardshadows addshadow
		#pragma instancing_options assumeuniformscaling procedural:ConfigureProcedural
+		#pragma editor_sync_compilation
		#pragma target 4.5
```

现在把 `GPUGraph` 的分辨率上限增加到 1000 是安全的。

```diff
	[SerializeField, Range(10, 1000)]
	int resolution = 10;
```

让我们试试最大分辨率。

![分辨率设为 1,000。](https://catlikecoding.com/unity/tutorials/basics/compute-shaders/procedural-drawing/resolution-1000-inspector.png)

在小窗口里看它不好看——因为点太小，会出现摩尔纹——但它能跑。对我而言，一百万个动画点以 24FPS 渲染。编辑器和构建产物性能相同。此时编辑器开销微不足道，GPU 才是瓶颈。另外，我的情况下开不开 VSync 没有明显区别。

![分析渲染一百万个点、无 VSync 的构建产物。](https://catlikecoding.com/unity/tutorials/basics/compute-shaders/procedural-drawing/profiler-drp-million-no-vsync.png)

禁用 VSync 后很清楚，player loop 的大部分时间花在等待 GPU 完成上。GPU 确实是瓶颈。我们可以给 CPU 加相当多的工作而不影响性能。

注意，我们渲染的一百万个点带阴影，对 BRP 来说需要每帧绘制它们三次。禁用阴影把我的平均帧率提高到约 65FPS（无 VSync）。

当然，如果你觉得帧率不够，不需要把分辨率一直提到 1,000。降到 700 可能就已经能在开启阴影时跑到 60FPS，而且看起来基本一样。但我会从今往后一致地使用分辨率 1,000。

### URP

要看 URP 表现如何，我们也需要复制 *Point URP* 着色器图，重命名为 *Point URP GPU*。着色器图不直接支持程序化绘制，但我们可以用一点自定义代码让它工作。为了让这更容易、也复用一些代码，我们创建一个 HLSL include 文件资源。Unity 没有这个的菜单选项，所以直接复制一个表面着色器资源，重命名为 *PointGPU*。然后用你系统的文件浏览器把资源的文件扩展名从 *shader* 改成 *hlsl*。

![PointGPU HLSL 脚本资源。](https://catlikecoding.com/unity/tutorials/basics/compute-shaders/procedural-drawing/point-gpu-hlsl-asset.png)

清空文件内容，然后把 *Point Surface GPU* 里 positions 缓冲区、缩放和 `ConfigureProcedural` 函数的代码复制到它里面。

```csharp
#if defined(UNITY_PROCEDURAL_INSTANCING_ENABLED)
	StructuredBuffer<float3> _Positions;
#endif

float _Step;

void ConfigureProcedural () {
	#if defined(UNITY_PROCEDURAL_INSTANCING_ENABLED)
		float3 position = _Positions[unity_InstanceID];

		unity_ObjectToWorld = 0.0;
		unity_ObjectToWorld._m03_m13_m23_m33 = float4(position, 1.0);
		unity_ObjectToWorld._m00_m11_m22 = _Step;
	#endif
}
```

现在我们可以通过 `#include "PointGPU.hlsl"` 指令，在 *Point Surface GPU* 着色器里包含这个文件，之后原始代码就可以从它里面移除了。

```diff
+		#include "PointGPU.hlsl"

		struct Input {
			float3 worldPos;
		};

		float _Smoothness;

-		//#if defined(UNITY_PROCEDURAL_INSTANCING_ENABLED)
-		//	StructuredBuffer<float3> _Positions;
-		//#endif

-		//float _Step;

-		//void ConfigureProcedural () { … }

		void ConfigureSurface (Input input, inout SurfaceOutputStandard surface) { … }
```

> **我们能在 CGPROGRAM 着色器里包含 HLSL 文件吗？**
>
> 能。`CGPROGRAM` 块和 `HLSLPROGRAM` 块之间的唯一区别是，前者默认包含一些文件。这个区别与我们无关。

我们将使用一个 *Custom Function* 节点把 HLSL 文件包含到我们的着色器图里。思路是节点调用文件里的一个函数。虽然我们不需要这个功能，但代码只有连接到图里才会被包含。所以我们给 *PointGPU* 加一个格式正确的占位函数，它只是原样传递一个 `float3` 值。

给 *PointGPU* 加一个 `void ShaderGraphFunction_float` 函数，带两个名为 `In` 和 `Out` 的 `float3` 参数。函数只是把输入赋给输出。参数名按惯例大写，因为它们将对应着色器图里使用的输入和输出标签。

```diff
+void ShaderGraphFunction_float (float3 In, float3 Out) {
+	Out = In;
+}
```

这假定 `Out` 参数是输出参数，我们必须通过在它前面写 `out` 来声明。

```diff
void ShaderGraphFunction_float (float3 In, out float3 Out) {
	Out = In;
}
```

函数名的 `_float` 后缀是必需的，因为它表明函数的精度。着色器图提供两种精度模式，`float` 或 `half`。后者是前者的一半大小，所以是两字节而不是四字节。节点使用的精度可以显式选择，或设为继承（默认）。为确保我们的图在两种精度模式下都能工作，还要添加一个改用半精度的变体函数。

```diff
void ShaderGraphFunction_float (float3 In, out float3 Out) {
	Out = In;
}

+void ShaderGraphFunction_half (half3 In, out half3 Out) {
+	Out = In;
+}
```

现在给我们的 *Point URP GPU* 图添加一个 *Custom Function* 节点。它的 *Type* 默认设为 *File*。把 *PointGPU* 赋给它的 *Source* 属性。*Name* 用 *ShaderGraphFunction*，不带精度后缀。然后把 *In* 加到 *Inputs* 列表，把 *Out* 加到 *Outputs* 列表，两者都作为 *Vector3*。

![通过文件的自定义函数。](https://catlikecoding.com/unity/tutorials/basics/compute-shaders/procedural-drawing/custom-function-file.png)

要把我们的代码集成到图里，必须把节点连接到图上。因为顶点阶段需要它，把它的输出连接到 *Vertex* 节点的 *Position*。然后添加一个设为对象空间的 *Position* 节点，把它连接到我们自定义节点的输入。

![通过我们函数传递的对象空间顶点位置。](https://catlikecoding.com/unity/tutorials/basics/compute-shaders/procedural-drawing/vertex-position.png)

现在对象空间顶点位置穿过了我们的占位函数，我们的代码也被包含进生成的着色器。但为了启用程序化渲染，我们还必须包含 `#pragma instancing_options` 和 `#pragma editor_sync_compilation` 编译器指令。这些必须直接注入生成的着色器源代码，它们不能通过单独的文件包含。所以再添加一个 *Custom Function* 节点，输入输出与之前相同，但这次把它的 *Type* 设为 *String*。把它的 *Name* 设为合适的名字——比如 *InjectPragmas*——然后把指令放进 *Body* 文本块。body 充当函数的代码块，所以我们在这里也必须把输入赋给输出。

![通过字符串注入 pragma 的自定义函数。](https://catlikecoding.com/unity/tutorials/basics/compute-shaders/procedural-drawing/custom-function-string.png)

为清晰起见，这是 body 的代码：

```diff
+#pragma instancing_options assumeuniformscaling procedural:ConfigureProcedural
+#pragma editor_sync_compilation

+Out = In;
```

把顶点位置也穿过这个节点，可以在另一个自定义函数节点之前或之后。

![带 pragma 的着色器图。](https://catlikecoding.com/unity/tutorials/basics/compute-shaders/procedural-drawing/with-pragmas.png)

创建一个启用了实例化、使用 *Point URP GPU* 着色器的材质，赋给我们的图表，然后进入运行模式。开启阴影时，我现在在编辑器和构建产物里都得到 36FPS。这比 BRP 快 50%。

![分析 URP 构建产物。](https://catlikecoding.com/unity/tutorials/basics/compute-shaders/procedural-drawing/profiler-urp-million-no-vsync.png)

同样，VSync 对平均帧率没有影响。禁用阴影把它提高到 69FPS，与 BRP 大致相同，只是 player loop 花的时间略少。

### 可变分辨率

因为我们目前总是为缓冲区里的每个位置绘制一个点，在运行模式下降低分辨率会让一些点固定在原地。这是因为计算着色器只更新落在图表内的点。

![降低分辨率后卡住的点。](https://catlikecoding.com/unity/tutorials/basics/compute-shaders/procedural-drawing/stuck-points.png)

计算缓冲区不能被调整大小。我们可以每次分辨率改变时创建一个新的，但另一个更简单的做法是，总是为最大分辨率分配缓冲区。那会让在运行模式下改变分辨率变得轻松。

先把最大分辨率定义为一个常量，然后在 `resolution` 字段的 `Range` 属性里使用它。

```diff
+	const int maxResolution = 1000;

	…

	[SerializeField, Range(10, maxResolution)]
	int resolution = 10;
```

接下来，缓冲区元素数量总是用最大分辨率的平方。这意味着无论图表分辨率如何，我们总是占用 12MB——大约 11.44MiB——的 GPU 内存。

```diff
	void OnEnable () {
		positionsBuffer = new ComputeBuffer(maxResolution * maxResolution, 3 * 4);
	}
```

最后，绘制时使用当前分辨率的平方，而不是缓冲区元素数量。

```diff
	void UpdateFunctionOnGPU () {
		…
		Graphics.DrawMeshInstancedProcedural(
			mesh, 0, material, bounds, resolution * resolution
		);
	}
```

在 10 到 1,000 之间改变分辨率。

## GPU 函数库

现在我们的 GPU 方案已完全可用，让我们把整个函数库移植到计算着色器。

### 所有函数

我们可以像复制并调整 `Wave` 那样复制其他函数。第二个是 `MultiWave`。它与 `Wave` 唯一显著的区别是它包含 `float` 值。f 后缀在 HLSL 中不存在，所以应该从所有数字中移除。为表明它们都是浮点值，我给它们都显式加了小数点，例如 `2f` 变成 `2.0`。

```diff
+float3 MultiWave (float u, float v, float t) {
+	float3 p;
+	p.x = u;
+	p.y = sin(PI * (u + 0.5 * t));
+	p.y += 0.5 * sin(2.0 * PI * (v + t));
+	p.y += sin(PI * (u + v + 0.25 * t));
+	p.y *= 1.0 / 2.5;
+	p.z = v;
+	return p;
+}
```

对其余函数做同样的事。`Sqrt` 变成 `sqrt`，`Cos` 变成 `cos`。

```diff
+float3 Ripple (float u, float v, float t) {
	float d = sqrt(u * u + v * v);
+	float3 p;
	p.x = u;
	p.y = sin(PI * (4.0 * d - t));
	p.y /= 1.0 + 10.0 * d;
	p.z = v;
	return p;
}

+float3 Sphere (float u, float v, float t) {
	float r = 0.9 + 0.1 * sin(PI * (6.0 * u + 4.0 * v + t));
	float s = r * cos(0.5 * PI * v);
+	float3 p;
	p.x = s * sin(PI * u);
	p.y = r * sin(0.5 * PI * v);
	p.z = s * cos(PI * u);
	return p;
}

+float3 Torus (float u, float v, float t) {
	float r1 = 0.7 + 0.1 * sin(PI * (6.0 * u + 0.5 * t));
	float r2 = 0.15 + 0.05 * sin(PI * (8.0 * u + 4.0 * v + 2.0 * t));
	float s = r2 * cos(PI * v) + r1;
+	float3 p;
	p.x = s * sin(PI * u);
	p.y = r2 * sin(PI * v);
	p.z = s * cos(PI * u);
	return p;
}
```

### 宏

我们现在必须为每个图表函数创建一个单独的内核函数，但那是大量重复代码。我们可以通过创建着色器宏来避免，就像之前定义 `PI` 那样。先在 `FunctionKernel` 函数上面一行写 `#define KERNEL_FUNCTION`。

```diff
+#define KERNEL_FUNCTION
	[numthreads(8, 8, 1)]
	void FunctionKernel (uint3 id: SV_DispatchThreadID) { … }
```

这些定义通常只适用于同一行写在它们后面的内容，但我们可以通过在除最后一行外的每一行末尾加 `\` 反斜杠，把它扩展到多行。

```diff
#define KERNEL_FUNCTION \
	[numthreads(8, 8, 1)] \
	void FunctionKernel (uint3 id: SV_DispatchThreadID) { \
		float2 uv = GetUV(id); \
		SetPosition(id, Wave(uv.x, uv.y, _Time)); \
	}
```

现在当我们写 `KERNEL_FUNCTION` 时，编译器会把它替换为 `FunctionKernel` 函数的代码。要让它对任意函数都工作，我们给宏加一个参数。这像函数的参数列表，但没有类型，而且左括号必须紧挨宏名。给它一个 `function` 参数，用它代替对 `Wave` 的显式调用。

```diff
#define KERNEL_FUNCTION(function) \
	[numthreads(8, 8, 1)] \
	void FunctionKernel (uint3 id: SV_DispatchThreadID) { \
		float2 uv = GetUV(id); \
		SetPosition(id, function(uv.x, uv.y, _Time)); \
	}
```

我们还要改内核函数的名字。我们用 `function` 参数作为前缀，后面跟 `Kernel`。不过我们必须让 `function` 标签保持独立，否则它不会被识别为着色器参数。要合并两个词，用 `##` 宏拼接运算符连接它们。

```diff
	void function##Kernel (uint3 id: SV_DispatchThreadID) { \
```

现在五个内核函数都可以通过写带适当参数的 `KERNEL_FUNCTION` 来定义了。

```diff
#define KERNEL_FUNCTION(function) \
	…

+KERNEL_FUNCTION(Wave)
+KERNEL_FUNCTION(MultiWave)
+KERNEL_FUNCTION(Ripple)
+KERNEL_FUNCTION(Sphere)
+KERNEL_FUNCTION(Torus)
```

我们还必须把单个内核指令替换为每个函数一个，顺序与 `FunctionLibrary.FunctionName` 匹配。

```diff
#pragma kernel WaveKernel
+#pragma kernel MultiWaveKernel
+#pragma kernel RippleKernel
+#pragma kernel SphereKernel
+#pragma kernel TorusKernel
```

最后一步是在 `GPUGraph.UpdateFunctionOnGPU` 里用当前函数作为内核索引，而不是总是用零。

```diff
+		var kernelIndex = (int)function;
		computeShader.SetBuffer(kernelIndex, positionsId, positionsBuffer);

		int groups = Mathf.CeilToInt(resolution / 8f);
		computeShader.Dispatch(kernelIndex, groups, groups, 1);
```

分辨率 1,000 下的所有函数，带一个显示阴影的平面。

计算着色器跑得如此之快，显示哪个函数都无所谓，所有函数的帧率都一样。

### 变形函数

支持从一个函数变形到另一个稍微复杂一些，因为每个独特的过渡都需要一个单独的内核。先给计算着色器加一个过渡进度属性，我们用它来混合函数。

```diff
float _Step, _Time, _TransitionProgress;
```

然后复制内核宏，重命名为 `KERNEL_MORPH_FUNCTION`，给它两个参数：`functionA` 和 `functionB`。把函数名改为 `functionA##To##functionB##Kernel`，用 `lerp` 基于进度对它们计算出的位置做线性插值。我们也可以在这里用 `smoothstep`，但我们会改为在 CPU 上每帧只算一次。

```diff
#define KERNEL_MORPH_FUNCTION(functionA, functionB) \
	[numthreads(8, 8, 1)] \
	void functionA##To##functionB##Kernel (uint3 id: SV_DispatchThreadID) { \
		float2 uv = GetUV(id); \
+		float3 position = lerp( \
+			functionA(uv.x, uv.y, _Time), functionB(uv.x, uv.y, _Time), \
+			_TransitionProgress \
+		); \
		SetPosition(id, position); \
	}
```

每个函数可以过渡到所有其他函数，所以每个函数有四个过渡。为所有这些添加内核函数。

```diff
KERNEL_FUNCTION(Wave)
KERNEL_FUNCTION(MultiWave)
KERNEL_FUNCTION(Ripple)
KERNEL_FUNCTION(Sphere)
KERNEL_FUNCTION(Torus)

+KERNEL_MORPH_FUNCTION(Wave, MultiWave);
+KERNEL_MORPH_FUNCTION(Wave, Ripple);
+KERNEL_MORPH_FUNCTION(Wave, Sphere);
+KERNEL_MORPH_FUNCTION(Wave, Torus);

+KERNEL_MORPH_FUNCTION(MultiWave, Wave);
+KERNEL_MORPH_FUNCTION(MultiWave, Ripple);
+KERNEL_MORPH_FUNCTION(MultiWave, Sphere);
+KERNEL_MORPH_FUNCTION(MultiWave, Torus);

+KERNEL_MORPH_FUNCTION(Ripple, Wave);
+KERNEL_MORPH_FUNCTION(Ripple, MultiWave);
+KERNEL_MORPH_FUNCTION(Ripple, Sphere);
+KERNEL_MORPH_FUNCTION(Ripple, Torus);

+KERNEL_MORPH_FUNCTION(Sphere, Wave);
+KERNEL_MORPH_FUNCTION(Sphere, MultiWave);
+KERNEL_MORPH_FUNCTION(Sphere, Ripple);
+KERNEL_MORPH_FUNCTION(Sphere, Torus);

+KERNEL_MORPH_FUNCTION(Torus, Wave);
+KERNEL_MORPH_FUNCTION(Torus, MultiWave);
+KERNEL_MORPH_FUNCTION(Torus, Ripple);
+KERNEL_MORPH_FUNCTION(Torus, Sphere);
```

我们定义内核，让它们的索引等于 `functionB + functionA * 5`，把不过渡的内核当作从同一函数过渡到同一函数。所以第一个内核是 *Wave*，后面是四个从 *Wave* 过渡到其他函数的内核。之后是从 *MultiWave* 开始的函数，其中第二个是不过渡的内核，依此类推。

```diff
#pragma kernel WaveKernel
+#pragma kernel WaveToMultiWaveKernel
+#pragma kernel WaveToRippleKernel
+#pragma kernel WaveToSphereKernel
+#pragma kernel WaveToTorusKernel

+#pragma kernel MultiWaveToWaveKernel
#pragma kernel MultiWaveKernel
+#pragma kernel MultiWaveToRippleKernel
+#pragma kernel MultiWaveToSphereKernel
+#pragma kernel MultiWaveToTorusKernel

+#pragma kernel RippleToWaveKernel
+#pragma kernel RippleToMultiWaveKernel
#pragma kernel RippleKernel
+#pragma kernel RippleToSphereKernel
+#pragma kernel RippleToTorusKernel

+#pragma kernel SphereToWaveKernel
+#pragma kernel SphereToMultiWaveKernel
+#pragma kernel SphereToRippleKernel
#pragma kernel SphereKernel
+#pragma kernel SphereToTorusKernel

+#pragma kernel TorusToWaveKernel
+#pragma kernel TorusToMultiWaveKernel
+#pragma kernel TorusToRippleKernel
+#pragma kernel TorusToSphereKernel
#pragma kernel TorusKernel
```

回到 `GPUGraph`，添加过渡进度着色器属性的标识符。

```diff
	static readonly int
		…
		timeId = Shader.PropertyToID("_Time"),
+		transitionProgressId = Shader.PropertyToID("_TransitionProgress");
```

如果我们正在过渡，就在 `UpdateFunctionOnGPU` 里设置它，否则不用管。我们在这里应用 smoothstep 函数，这样就不必在 GPU 上为每个点都做一次。这是个小优化，但它是免费的，还避免了很多工作。

```diff
		computeShader.SetFloat(timeId, Time.time);
+		if (transitioning) {
+			computeShader.SetFloat(
+				transitionProgressId,
+				Mathf.SmoothStep(0f, 1f, duration / transitionDuration)
+			);
+		}
```

要选择正确的内核索引，给它加上过渡函数的五倍，如果不在过渡则加上同一函数的五倍。

```diff
		var kernelIndex =
			(int)function + (int)(transitioning ? transitionFunction : function) * 5;
```

连续随机变形。

对我而言，新增的过渡仍然不影响帧率。显然瓶颈是渲染，而不是位置的计算。

### 函数数量属性

要计算内核索引，`GPUGraph` 需要知道有多少个函数。我们可以给 `FunctionLibrary` 添加一个返回它的 `GetFunctionCount` 方法，而不是在 `GPUGraph` 里硬编码。这样做的好处是，如果我们添加或删除函数，只需要改两个 *FunctionLibrary* 文件——类和计算着色器。

```diff
+	public static int GetFunctionCount () {
+		return 5;
+	}
```

我们甚至可以移除常量值，返回 `functions` 数组的长度，进一步减少以后要改的代码。

```diff
	public static int GetFunctionCount () {
		return functions.Length;
	}
```

函数数量是转成属性（property）的好候选。要自己创建一个，从 `GetFunctionCount` 移除 `Get` 前缀，也移除它的空参数列表。然后把 return 语句包进一个嵌套的 `get` 代码块。

```diff
	public static int FunctionCount {
+		get {
			return functions.Length;
+		}
	}
```

这定义了一个 getter 属性。因为它唯一做的事就是返回值，我们可以通过把 `get` 块缩减为表达式主体来简化它，做法是用 `get => functions.Length;` 替换它。

```diff
	public static int FunctionCount {
+		get => functions.Length;
	}
```

因为没有 `set` 块，我们可以通过省略 `get` 进一步简化属性。这把属性缩减为一行。

```diff
	public static int FunctionCount => functions.Length;
```

这也适用于合适的方法，这里是 `GetFunction` 和 `GetNextFunctionName`。

```diff
	public static Function GetFunction (FunctionName name) => functions[(int)name];

	public static FunctionName GetNextFunctionName (FunctionName name) =>
+		(int)name < functions.Length - 1 ? name + 1 : 0;
```

在 `GPUGraph.UpdateFunctionOnGPU` 里用新属性代替常量值。

```diff
		var kernelIndex =
			(int)function +
			(int)(transitioning ? transitionFunction : function) *
+		FunctionLibrary.FunctionCount;
```

本篇文章主要围绕抖音虚拟世界的“Shared Mod”和“Dedicated Server”两种开发模式进行说明。主要涉及以下内容：

* 两种开发模式的简单说明
* 两种开发模式中的共通核心概念
* Shared Mod 开发模式介绍
* Dedicated Server 开发模式介绍
* 两种模式的关系与迁移说明

# 一、开发模式说明
> 当前抖音虚拟世界面向创作者提供了两种开发模式：Shared Mod 开发模式和 Dedicated Server 开发模式。


* **Shared Mod 开发模式**：世界逻辑分散运行在每个客户端上，也即是每个客户端承载部分服务器角色，由客户端来更新网络对象的状态，并通过房间服务器同步至其他客户端。
* **Dedicated Server 开发模式**：在 Shared Mod基础上，引入了独立的服务器节点（平台专属服务器进程），允许将部分世界逻辑运行在平台专属服务器上。

# 二、两种模式共通核心概念
## 1、网络对象
**本质：** 场景中所有玩家都需要看到"状态完全一致"的游戏实体。凡是需要多人共享同一状态的物体，都必须是网络对象；仅在单个玩家设备上可见或生效的物体（本地特效、单人UI等）则不需要网络化。
**关键特性：**

* 所有挂载 DouyinNetworkGuid 脚本的 GameObject 即可认定为网络对象（挂载 DouyinScript 时默认添加DouyinNetworkGuid 脚本）
* 状态（位置，旋转，大小等）自动同步到所有在线玩家设备，无需手动推送
* 支持使用平台提供的API来动态创建（`NetSpawn`）与销毁（`NetDestroy`），不可使用 Unity 原生API（`Instantiate` / `Destroy`）来动态创建与销毁
* 网络对象在断线重连时不会触发 `OnNetSpawned`

**使用场景：** 玩家操控的角色、可拾取的道具、门/开关等多人可见的交互物体，以及需要全局数据同步的业务逻辑对象，均应设计为网络对象。
## 2、主权与控制权
> 主权和控制权可以分离，也可以绑定在同一方。


* 主权：是"谁有资格修改该对象状态"的权限
* 控制权：是"谁在操作该对象"的权限

**关键特性：**
| **维度** | **主权** | **控制权** |
| --- | --- | --- |
| 核心作用 | 只有主权方才能修改同步变量的值 | 只有控制权方才能操控对象（如玩家操作角色） |
| 转移时机 | 主动请求 / 房间自动调度 / 获得控制权时自动获得 | 主动请求 / 持有方授权 / 强交互自动获取（拾取 / 坐下） |
| 释放时机 | 玩家断线 /玩家退房/ 切后台 / 主动转让 | 退房自动释放 / 持有方主动释放/玩家退房 |
| 获取方式 | 主动获取/房间自动调度/获得控制权自动获得 | 主动获取/持有方授权/强交互时自动获取（拾取/坐下） |
在修改同步变量前，需要使用`HasOwnership`来判断是否拥有主权，因为只有主权方才能修改用不变量。

## 3、网络同步能力
> 平台提供了3种网络同步能力，分别适用于不同的同步场景。

**关键特性：**
| **通信方式** | **特点** | **适用场景** | **注意事项** |
| --- | --- | --- | --- |
| 同步变量 | * 同步变量值变化时自动同步 <br> * 定时同步，存在70ms-120延迟 | 持续存在的状态值 <br> （生命值、得分、道具数量） | * 写前必须确认主权 <br> * 平台侧确保数据的最终一致性，即使客户端网络异常，重进房后将拉取最新数据 |
| RPC 调用（DouyinScript.SendMessageToXXX） | * 事件驱动，主动调用 <br> * 实时性高，即时发送 <br> * **不保证接收方一定能收到** | 次要通知类消息 <br> （非核心业务勿用） <br>  | * 基于TCP实现，可靠传输 <br> * 如需确保数据一致性，请务必使用同步变量 <br> * 接收方网络断开时，平台侧不补发消息 |
| RemoteEvent <br> RemoteFunction <br>  | * 事件驱动，C↔S双向 <br> * 实时性高，即时发送 | DS 模式下客户端向服务端提交操作指令、服务端下发结果通知 <br>  | * 基于TCP实现，可靠传输 <br> * 只用于DS模式 <br> * 如需确保数据一致性，请务必使用同步变量 <br> * 接收方网络断开时，平台侧不补发消息 <br> * 不要在方法中定义DouyinRemoteEvent/DouyinRemoteFunction的变量，因为当方法结束时，会将变量进行垃圾回收，这会导致当异步双向通信调用回调时变量报nil |
**使用场景：** 核心业务状态（血量、得分、物品状态）优先使用同步变量；临时通知（游戏开始提示）可使用 RPC，但需考虑接收方网络断开导致无法送达的可能性；DS模式下跨端的指令传递（客户端触发操作 → 服务端校验执行 → 服务端广播结果）使用 RemoteEvent；
## 4、开发API
**本质：** 平台上层 API 在两种模式下高度兼容
**关键特性：**

* 绝大多数上层 API（角色服务DouyinPlayer、对象服务DouyinActor、数据存储DataStore等）在两种模式下完全通用
* DS 模式新增专属 API：`DouyinDedicatedServer专属API集合`，且存在严格的 C/S API 边界约束

# 三、Shared Mod 开发模式介绍
## 1、逻辑运行规则
**本质：** 所有玩法逻辑在客户端上执行，开发者在创作过程中感知不到“服务器”。房间服务器仅负责消息转发和数据存储，不参与任何业务运行计算。
**关键特性：**

* 不同玩家的设备均会执行相同的业务逻辑代码，通过同步变量和 RPC 维持状态一致
* 房间服务器只提供数据与消息的中继转发服务，不做任何合法性校验，因此Shared 模式防外挂能力较弱

## 2、主权分配规则
**本质：** 第一个进入房间的玩家（房主）会持有大多数公共对象（场景内摆放好的网络对象）的主权。随着玩家进出，房间内的网络对象的主权将逐步分散到房间内各个客户端上。
**关键特性：**

* 场景中无人持有的公共物体（如公共 NPC、道具箱），主权由房间统一调度分散到房间内多个客户端
* 主权方异常断线会导致其持有主权的对象暂时无法被修改，直到服务器感知到断线并完成主权转移

## 3、开发成本与周期

* 有一定理解成本，但开发门槛不高，单人即可完成从开发到上线的全流程
* 开发周期比 DS 模式短 
* 调试仅需一个客户端视角，整体不复杂

## 4、适合的玩法场景

* 休闲社交、虚拟装扮、剧情互动
* 低难度小游戏（跑酷竞速、休闲解谜、简单的合作等）
* 不涉及公平性竞争的多人协作玩法
* 无虚拟资产奖励、无付费内容的纯体验型玩法
* 对数据存储要求不高的玩法

# 四、Dedicated Server 开发模式介绍
## 1、逻辑运行规则
**本质：** 在Shared模式基础上引入了服务端，服务端是官方托管的独立进程。客户端可分布式运行与服务端交互相关的业务逻辑，强烈建议将所有关键玩法/关键逻辑在服务端执行，客户端不参与任何涉及安全风险的核心判定。
**关键特性：**

* 服务端同时运行服务端脚本（DouyinServerRoot节点下的对象所挂载的脚本）与客户端脚本（其他脚本），客户端只会运行客户端脚本
* 服务端脚本和服务器对象（DouyinServerRoot节点下的对象）对客户端完全不可见，核心参数（掉落概率、伤害系数、反作弊阈值）无法被客户端读取或篡改
* 房间内公共对象主权由服务端持有，可用于承载全局性业务逻辑（如全局倒计时、全局积分面板）

## 2、主权分配规则
**本质：** 服务端拥有所有网络对象的默认主权（除玩家角色Actor）；客户端可通过相关接口请求对象的主权/控制权，客户端断线/退房后，主权/控制权归还服务端。
**关键特性：**

* 服务端网络状态始终稳定，DS模式为业务层提供了一个稳定的逻辑执行端
* 服务端允许创建公共对象，也允许创建服务端专属的服务器对象（客户端不可见）
* 对于公共对象，可基于同步变量实现数据通信；对于服务器对象（客户端不可见），需通过RemoteEvent机制实现C/S通信

## 3、适合的玩法场景

* 强竞技类玩法，需要严格公平性保障
* 抽奖/扭蛋玩法，随机结果必须由可信方生成
* 排行榜奖励玩法，积分来源需经服务端校验防刷
* 虚拟资产交易、道具付费购买等商业化核心流程
* 任何"玩家获益行为"均需经服务端授权的玩法
* 对数据存储有高要求的玩法

# 五、两种模式的关系与迁移说明
## 1、模式关系
Shared Mod 模式和 DS 模式不是互相替代的关系，而是不同场景下的选型：

* 玩法初期验证可以用 Shared 模式快速开发上线，验证用户反馈后再考虑是否升级到 DS 模式
* 已经上线的 Shared 模式玩法如果出现作弊问题或需接入商业化能力，可以迁移到 DS 模式解决

## 2、迁移说明
Shared Mod 模式升级到 DS 模式**不是一键切换，需要对核心业务逻辑进行改造**，平均改造工作量约为原有开发工作量的 30%～50%，主要改造点包括：

* **逻辑分层改造**：将原来写在客户端的核心逻辑（数值计算、判定、奖励发放等）拆分出来，迁移到服务端执行
* **权限校验改造**：针对所有客户端提交的核心操作，考虑在服务端增加合法性校验，避免非法输入
* **全局逻辑改造**：原来由客户端托管执行的全局逻辑，建议改为由服务端执行后同步到客户端
* **调试流程改造**：需要同时调试客户端和服务端逻辑，掌握 DS 模式专属的调试工具使用

## 3、迁移步骤建议

* **第一步**：在原 Shared 模式玩法中做好逻辑分层，提前将核心逻辑和表现逻辑拆分，降低后续迁移成本
* **第二步**：在场景中添加 `DouyinServerRoot` 节点启用 DS 模式
* **第三步**：逐步将核心逻辑迁移到服务端，保留客户端表现逻辑不变
* **第四步**：使用 DS 调试工具验证多端逻辑一致性，完成上线

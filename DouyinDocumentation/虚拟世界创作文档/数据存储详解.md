## **第一部分：使用原生 API 需要处理的问题和逻辑**
在使用平台原生 DataStore API 实现数据存储时，需要处理以下问题和逻辑：
### **1. 基本概念：Name、Scope、Key**
在使用 DataStore API 之前，需要理解三个核心概念：
**Name（游戏名称）：**

* 用于标识不同的游戏或应用
* 通常使用统一的英文名称，如 "sim_game"
* 所有 DataStore 操作都需要指定 gameName

**Scope（作用域）：**

* 用于区分数据的作用范围
* 默认使用玩家作用域，数据属于特定玩家，如玩家个人数据

**Key（键）：**

* `storeKey`：存储键，用于标识某个功能或模块的数据存储空间，如 "player_12345"、"bag_12345"
* `dataKey`：数据字段名，用于标识具体的数据字段，如 "coin"、"level"、"player_data"
* 完整的键结构：`gameName` + `storeKey` + `dataKey` 唯一标识一条数据

**键设计示例：**

* 账号级数据：`gameName="sim_game"`, `storeKey="player_"..playerOpenID`, `dataKey="coin"`
* 小火人级数据：`gameName="sim_game"`, `storeKey="pet_"..petOpenID`, `dataKey="exp"`

### **2. DATASTORE 代码块要求**
平台原生 DataStore API 要求所有操作必须在 `DATASTORE(function() ... end)` 代码块内执行，否则会返回错误码 -10034。
**需要处理的问题：**

* 所有 DataStore 相关操作（获取 DataStore 对象、读取数据、写入数据）都必须在 DATASTORE 代码块内执行
* 代码块是异步执行的，需要注意变量作用域和回调处理

### **3. 错误码处理**
平台定义了多种错误码，需要在每个操作后判断并处理。
**需要处理的错误码：**

* `0`：操作成功
* `-10001`：数据不存在（新号场景），需要业务层初始化默认数据
* `-10005`：DataStore 名称为空
* `-10012`：键名（dataKey）超出长度限制（128字符）
* `-10013`：值大小超出限制（约6000字符）
* `-10014`：DataStore key 数量超过限制（1000个）
* `-10034`：未在 DATASTORE 块内执行
* `-10050`：DataStore 暂时不可用（网络问题），需要重试

**需要处理的逻辑：**

* 每个操作后都需要判断错误码
* 不同错误码需要不同的处理策略（重试、初始化、报错等）

### **4. 新号场景处理**
新号场景下，GetData 会返回错误码 -10001，需要业务层判断并初始化默认数据。
**需要处理的逻辑：**

* 检测新号场景（错误码 -10001）
* 初始化默认数据
* 保存默认数据到 DataStore

### **5. 网络异常处理**
网络异常时需要实现重试机制，包括重试次数、延迟策略和降级方案。
**需要处理的逻辑：**

* 识别网络异常（错误码 -10050）
* 实现重试机制（最多重试 3 次）
* 使用指数退避策略（1s → 2s → 4s）
* 提供降级方案（本地缓存等）

### **6. 数据一致性保障**
多次写入操作需要考虑顺序问题，相同 key 的写入需要串行执行，不同 key 可以并行。
**需要处理的逻辑：**

* 相同 key 的写入操作需要串行执行，保证写入顺序
* 不同 key 的写入操作可以并行执行，提高性能
* 同一 key 的多次写入只保留最新版本，旧任务自动丢弃
* 实现版本管理机制

### **7. JSON 编解码**
平台 DataStore 存储的是字符串类型，需要将 Lua 表序列化为 JSON 字符串后写入，读取后反序列化。
> 可使用平台提供的序列化和反序列化接口
> dkjson.encode()
> dkjson.decode()

**需要处理的逻辑：**

* 保存时：将 Lua 表序列化为 JSON 字符串
* 读取时：将 JSON 字符串反序列化为 Lua 表
* 处理序列化/反序列化失败的情况

### **8. 容量与限制**
平台对 DataStore 有严格的容量和长度限制，需要在写入前进行校验。
**Name（游戏名称）的限制：**

* 必须是非空字符串
* 建议使用统一的英文名称，如 "sim_game"

**Scope（作用域）的限制：**

* 默认使用玩家作用域，所有数据属于特定玩家

**Key（键）的限制：**

* `storeKey` 最大长度：128 字符
* `dataKey` 最大长度：128 字符
* 单个 DataStore 最大 key 数量：约 1000 个
* 超过 key 数量限制后，新增 key 的写入操作会失败（错误码 -10014），已有 key 的更新不受影响

**Value（值）的限制：**

* 单个 value 最大长度：约 6000 字符（JSON 序列化后）
* 超过限制时写入会失败（错误码 -10013）
* 需要在写入前校验数据大小

**QPS（每秒查询数）的限制：**

* QPS（Queries Per Second）是指每秒可以执行的查询操作数量
* 单个 DataStore 的 QPS 限制：需要根据平台具体规定
* 超过 QPS 限制可能导致请求被限流或失败（返回错误码或请求被拒绝）
* 需要实现请求频率控制，避免短时间内大量请求
* 建议：合理控制读写频率，避免频繁操作同一 DataStore

**总容量的限制：**

* 总容量是指单个 DataStore 中所有 key 的 value 数据总和
* 单个 DataStore 的总容量限制：需要根据平台具体规定
* 所有 key 的 value 总和不能超过总容量限制
* 超过总容量限制可能导致新的写入操作失败
* 需要合理设计数据存储结构，避免单个 DataStore 容量过大
* 建议：采用"一玩家一 storeKey"的拆分方式，分散数据存储

**Metadata（元数据）的限制：**

* Metadata（元数据）是 DataStore 存储的附加信息，用于描述数据的基本属性
* Metadata 包含数据的创建时间、修改时间、版本号等信息
* Metadata 由平台自动管理，开发者无需手动设置
* Metadata 的大小和数量也受到平台限制
* 需要注意 Metadata 的存储开销，避免影响主要数据的存储
* 建议：了解 Metadata 的存在，但主要关注 value 数据的存储限制

**需要处理的逻辑：**

* 写入前校验数据大小（value 长度、key 数量等）
* 超过限制时需要拆分存储或压缩数据
* 采用"一玩家一 storeKey"的拆分方式，避免单 DataStore 键数过多
* 实现请求频率控制，避免超过 QPS 限制
* 合理设计数据存储结构，避免超过总容量限制

### **8. ID 选择与键设计**
需要根据业务场景选择使用 playerOpenID 或 petOpenID，并合理设计键结构。
**需要处理的逻辑：**

* 账号级数据使用 playerOpenID（总金币、关卡解锁、账号成就等）
* 小火人级数据使用 petOpenID（属性、经验、专属外观等）
* 合理设计 gameName、storeKey、dataKey 的结构

### **9. DataStore 实例管理**
每次读写都需要获取 DataStore 对象，需要实现缓存机制避免重复创建。
**需要处理的逻辑：**

* 实现 DataStore 对象缓存机制
* 相同 storeKey 的多次操作复用同一 DataStore 实例
* 避免重复创建，提高性能

```Lua
local function HandleDataStoreError(ok, operation)
    if ok == 0 then
        return true  -- 成功
    end
    
    local errorMsg = ""
    if ok == -10001 then
        errorMsg = "数据不存在（新号场景）"
    elseif ok == -10005 then
        errorMsg = "DataStore 名称为空"
    elseif ok == -10012 then
        errorMsg = "键名超出长度限制（128字符）"
    elseif ok == -10013 then
        errorMsg = "值大小超出限制（约6000字符）"
    elseif ok == -10014 then
        errorMsg = "DataStore key 数量超过限制（1000个）"
    elseif ok == -10050 then
        errorMsg = "DataStore 暂时不可用（网络问题）"
    elseif ok == -10034 then
        errorMsg = "未在 DATASTORE 块内执行"
    else
        errorMsg = string.format("未知错误码：%d", ok)
    end
    
    print(string.format("[%s] 操作失败：%s", operation, errorMsg))
    return false
end
```

### **4. 网络异常处理实现**
#### **4.1 重试机制实现**
```Lua
local function SaveDataWithRetry(gameName, storeKey, dataKey, value, maxRetries, callback)
    maxRetries = maxRetries or 3
    local retryCount = 0
    local retryDelays = {1, 2, 4}  -- 指数退避：1s, 2s, 4s

    local function TrySave()
        -- 步骤1：获取 DataStore 对象
        local store = nil
        DATASTORE(function()
            local ok, dataStore = DouyinDataService.GetDataStore(gameName, storeKey, false)
            if ok ~= 0 then
                if ok == -10050 and retryCount < maxRetries then
                    -- 网络问题，需要重试
                    retryCount = retryCount + 1
                    local delay = retryDelays[retryCount] or 10
                    print(string.format("网络异常，%d秒后重试（第%d次）", delay, retryCount))
                    CS.UnityEngine.MonoBehaviour.StartCoroutine(function()
                        CS.UnityEngine.WaitForSeconds(delay)
                        TrySave()
                    end)
                    return
                end
                callback(false, ok)
                return
            end
            store = dataStore
        end)

        if not store then
            return
        end
        
        -- 步骤2：写入数据
        DATASTORE(function()
            local ok, message = store:SetData(dataKey, tostring(value), nil)
            if ok == -10050 and retryCount < maxRetries then
                -- 网络问题，需要重试
                retryCount = retryCount + 1
                local delay = retryDelays[retryCount] or 10
                print(string.format("保存失败，%d秒后重试（第%d次）", delay, retryCount))
                CS.UnityEngine.MonoBehaviour.StartCoroutine(function()
                    CS.UnityEngine.WaitForSeconds(delay)
                    TrySave()
                end)
                return
            elseif ok == 0 then
                callback(true, 0)
            else
                -- 其他错误，不再重试
                callback(false, ok)
            end
        end)
    end

    TrySave()
end
```

### **5. 数据一致性保障实现**
#### **5.1 写入队列管理实现**
```Lua
local ProcessingTasks = {}  -- 正在处理的任务（key = queueKey, value = 任务对象）
local PendingTasks = {}     -- 等待处理的任务（key = queueKey, value = 任务对象，只保留最新版本）

-- 处理队列（交换机制：将等待处理的任务移到正在处理）
local function ProcessQueue(queueKey, gameName, storeKey, dataKey)
    -- 如果当前 key 正在处理，等待完成（串行保证）
    if ProcessingTasks[queueKey] then
        return
    end

    -- 获取等待处理的任务
    local waitingTask = PendingTasks[queueKey]
    if not waitingTask then
        return
    end
    
    -- 交换：将等待处理的任务移到正在处理
    ProcessingTasks[queueKey] = waitingTask
    PendingTasks[queueKey] = nil
    
    -- 获取 DataStore 对象并写入数据（所有逻辑都在 DATASTORE 块内，异步执行）
    DATASTORE(function()
        -- 步骤1：获取 DataStore 对象
        local ok, dataStore = DouyinDataService.GetDataStore(gameName, storeKey, false)
        if ok ~= 0 then
            -- 获取失败，保留当前任务并重试（需要检查版本，只保留最新版本）
            ProcessingTasks[queueKey] = nil  -- 清除标记，允许重试
            local currentPendingTask = PendingTasks[queueKey]
            -- 只有当前任务版本 >= 等待队列中的版本时，才放回（只保留最新版本）
            if not currentPendingTask or waitingTask.version >= currentPendingTask.version then
                PendingTasks[queueKey] = waitingTask  -- 重新放入等待队列
            end
            if waitingTask.callback then waitingTask.callback(false, ok) end
            return
        end
        
        -- 步骤2：在实际写入之前，检查等待处理的任务是否有更新的版本（swap 机制）
        local currentTask = ProcessingTasks[queueKey]
        local newerWaitingTask = PendingTasks[queueKey]
        if newerWaitingTask and newerWaitingTask.version > currentTask.version then
            -- 等待处理的任务版本更高，使用最新的数据
            currentTask.version = newerWaitingTask.version
            currentTask.value = newerWaitingTask.value
            currentTask.callback = newerWaitingTask.callback
            PendingTasks[queueKey] = nil  -- 清除等待任务（已合并到当前任务）
        end
        
        -- 步骤3：写入数据
        local ok2, message = dataStore:SetData(dataKey, tostring(currentTask.value))
        ProcessingTasks[queueKey] = nil  -- 清除正在处理的任务
        
        if ok2 == 0 then
            if currentTask.callback then currentTask.callback(true, 0) end
        else
            -- 写入失败，保留当前任务并重试（需要检查版本，只保留最新版本）
            local currentPendingTask = PendingTasks[queueKey]
            -- 只有当前任务版本 >= 等待队列中的版本时，才放回（只保留最新版本）
            if not currentPendingTask or currentTask.version >= currentPendingTask.version then
                PendingTasks[queueKey] = currentTask  -- 重新放入等待队列
            end
            if currentTask.callback then currentTask.callback(false, ok2) end
            return
        end
        
        -- 继续处理等待的任务
        ProcessQueue(queueKey, gameName, storeKey, dataKey)
    end)
end

local function SaveData(gameName, storeKey, dataKey, value, callback)
    local queueKey = string.format("%s_%s_%s", gameName, storeKey, dataKey)

    -- 获取当前最大版本号
    local maxVersion = 0
    local currentProcessingTask = ProcessingTasks[queueKey]
    if currentProcessingTask and currentProcessingTask.version > maxVersion then
        maxVersion = currentProcessingTask.version
    end
    local currentPendingTask = PendingTasks[queueKey]
    if currentPendingTask and currentPendingTask.version > maxVersion then
        maxVersion = currentPendingTask.version
    end
    local newVersion = maxVersion + 1
    
    -- 创建新任务对象
    local newTask = {
        value = value,
        callback = callback,
        version = newVersion
    }
    
    -- 如果正在处理，则更新等待处理的任务（比较版本，只保留最新版本）
    if ProcessingTasks[queueKey] then
        -- 正在处理，新任务放入等待队列（直接替换，只保留最新版本）
        PendingTasks[queueKey] = newTask
        return
    end
    
    -- 没有正在处理，直接设置为等待处理
    PendingTasks[queueKey] = newTask
    
    -- 尝试处理
    ProcessQueue(queueKey, gameName, storeKey, dataKey)
end
```

#### **7.2 键数量限制**

* **平台限制**：单个 DataStore 最多约 1000 个 key
* **超过上限后的行为**：新增 key 的写入操作会失败（错误码 -10014），已有 key 的更新不受影响
* **拆分策略**：采用"一玩家一 storeKey"的拆分方式，避免单 DataStore 键数过多
   * **正确示例**：
      * `player_12345`（玩家数据）
      * `bag_12345`（背包数据）
      * `ranking_12345`（排行榜数据）
   * **错误示例**：
      * `all_players_data`（所有玩家数据放在一个 DataStore 里，容易超过限制）

**容量限制总结：**

* 单个 value 最大长度：约 6000 字符（JSON 序列化后）
* 单个 dataKey 最大长度：128 字符
* 单个 DataStore 最大 key 数量：约 1000 个
* 建议：采用"一玩家一 storeKey"的拆分方式，确保每个 DataStore 的 key 数量在合理范围内

商业化快速上手
系统定位​
这套商业化代码负责承接抖音支付成功后的服务端发货流程，目标是把「支付侧订单」稳定地转换为「游戏内实际到账」。​
当前实现覆盖了飞行器商店的星光币购买链路，但框架本身是可扩展的，已经把以下职责拆开：​
  • 客户端发起购买​
  • 服务端接收支付回调​
  • 基于 productId 路由到具体发货 Handler​
  • Handler 将订单翻译成业务请求并执行发货​
  • 服务端缓存订单结果，处理重试、补单、退款​
目录与职责​
​
Commercial/​
├── ServerCommercialManager.lua # 支付回调入口、订单去重、回执写入、ConfirmOrder​
├── ServerCommercialDeliverManager.lua # 根据 productId -> type 路由到具体 Handler​
├── AircraftShopDeliverHandler.lua # 当前已接入的商店发货实现（飞行器商店）​
​
Client/System/CommercialSystem/​
├── CommercialSystem.lua # 客户端购买入口、购买结果回调、GM 调试入口​
└── CommercialSystemRegister.lua # 客户端商业系统注册​
​
Common/Config/​
├── CommercialDataLib.lua # productId -> deliverType 路由表​
└── ShopDataLib.lua # 商店配表，维护 productId -> shopRow 的业务映射​
​
Server/Data/​
└── ServerReceiptData.lua # 订单缓存域，负责读取、缓存、终态订单过期清理​
​
核心角色​
客户端入口​
  • CommercialSystem:GetProductInfos()/CommercialSystem:GetProductPage()是客户端统一获取商品信息入口，在CommercialSystemRegister中调用。​
  • CommercialSystem:PurchaseProduct(productId, productNum, orderData) 是客户端统一购买入口。​
客户端只负责发起购买和展示购买结果，不参与最终发货判定。真正的到账以服务端支付回调后的发货结果为准。​
服务器支付回调入口​
ServerCommercialManager.OnOrderPaymentCallBack(sequenceId, receiptInfo) 是服务端统一入口，主要做 5 件事：​
    校验玩家聚合对象是否存在​
    校验 receiptData 是否已加载完成​
    检查该订单是否已经进入终态，避免重复发货​
    调用 ServerCommercialDeliverManager.DeliverHandle 执行真实发货​
    把结果写入 receiptData，再调用 DouyinMarketingService.ConfirmOrder​
这里的 receiptInfo.productId 按框架约定始终按 string 使用，相关代码里也都做了 tostring(...) 归一化。​
发货路由层​
ServerCommercialDeliverManager 不关心具体业务内容，只做两件事：​
  • 从 CommercialDataLib.ProductMappingDic 读取 productId -> type​
  • 根据 type 找到已注册的 Handler 并执行​
这样做的好处是支付路由和业务发货解耦。支付侧只认 productId，而业务侧可以自行维护自己的配表主键。​
业务 Handler​
业务 Handler 继承 BaseDeliverHandler，至少需要实现两个方法：​
  • IsComplete(playerOpenId)：确认发货所依赖的聚合缓存是否已经准备好​
  • Deliver(receiptInfo, callback, targetPlayer)：执行真实发货​
当前 AircraftShopDeliverHandler 的做法是：​
  • 先用 ShopDataLib.GetByProductId(productId) 把支付订单反查成商店行​
  • 再组装 requestData = { shopPK, goodsPK }​
  • 最后调用 ServerShopManager.HandleShopStarPurchase 复用已有商店发货能力​
订单缓存域​
ServerReceiptData 是订单状态缓存，结构如下：​
​
{​
[orderId] = {​
code = 0,​
receiptInfo = {​
purchaseOrder = "...",​
playerOpenId = "...",​
productId = "...",​
productNum = 1,​
orderPrice = "0",​
purchaseTime = "1710000000",​
}​
}​
}​
​
它的核心作用有三点：​
  • 防重：同一订单重复回调时，直接返回之前的终态结果​
  • 补单/退款：保存上次处理状态，便于平台重试时做幂等处理​
  • 清理：加载时会清理过期终态订单，避免缓存无限增长​
订单状态与错误码约定​
receipt code​
订单最终通过 DouyinMarketingService.ConfirmOrder(sequenceId, receiptInfo, receiptCode) 回传平台，当前约定如下：​
  • 0：发货成功​
  • 1：补单，表示本次没有成功到账，等待平台后续重试​
  • -1：退款​
发货层 errorCode​
业务 Handler 的失败分两类：​
  • errorCode == -10000：不可恢复错误，支付层直接走退款​
  • 其它错误码或 nil：视为可重试错误，支付层走补单​
当前商店链路里，ServerShopManager.HandleShopStarPurchase 已经约定：​
  • 已拥有重复购买​
  • 顺序权威校验失败​
这类不可恢复场景返回 -10000，从而触发退款而不是无限补单。​
完整时序​
正常购买​
    客户端调用 CommercialSystem:PurchaseProduct​
    平台支付成功后回调服务端 OnOrderPaymentCallBack​
    服务端检查聚合对象与 receiptData 是否已加载​
    服务端检查订单是否已处理过​
    ServerCommercialDeliverManager 通过 CommercialDataLib 找到业务 Handler​
    Handler 做缓存就绪校验，并执行真实发货​
    服务端写入 receiptData​
    服务端调用 ConfirmOrder(0) 确认发货成功​
失败重试​
若发货失败：​
  • 不可恢复错误：写入 code = -1，平台退款​
  • 可恢复错误：写入 code = 1，平台后续补单重试​
若平台再次回调同一订单：​
  • 若订单已经是终态（code <= 0），直接返回历史结果​
  • 若之前是补单态（code = 1），则重新进入发货流程​
当前已接入业务​
当前接入的是飞行器商店购买：​
  • 路由配置：CommercialDataLib.ProductMappingDic[productId].type = "shop"​
  • 业务反查：ShopDataLib.GetByProductId(productId)​
  • 实际发货：ServerShopManager.HandleShopStarPurchase(player, requestData)​
当前框架采用的是：​
  • CommercialDataLib 只维护支付路由​
  • 具体业务配表自己维护 productId​
  • Handler 负责把支付订单翻译成业务请求​
这是一个比较清晰的单一事实源设计，避免在多个表里重复维护 itemId / shopPK 等业务字段。​
快速开始​
本文说明如何在当前商业化框架下接入一个新的「支付成功后服务端发货」业务。​
适合以下场景：​
  • 新增一种商业化商品类型​
  • 支付成功后，需要走一段服务端权威发货逻辑​
  • 希望复用现有的订单去重、补单、退款、平台回执能力​
如果你只是给现有商店增加一个新商品，且仍然走 type == "shop" 链路，通常只需要补配置，不需要新增 Handler。​
先理解接入点​
接入一个新业务，通常只需要关心 4 个位置：​
    CommercialDataLib.lua​
    业务自己的配置表​
    新的 Deliver Handler​
    ServerCommercialDeliverManager.lua​
它们的职责分别是：​
  • CommercialDataLib：维护 productId -> type​
  • 业务配置表：维护 productId -> 业务行​
  • Deliver Handler：把支付订单翻译成业务发货请求​
  • DeliverManager：把 type 注册到具体 Handler​
接入步骤​
第 1 步：在CommercialDataLib.ProductMappingDic 里增加支付路由：​
​
CommercialDataLib.ProductMappingDic = {​
["114278400002"] = { type = "shop" },​
["114278499999"] = { type = "gift_pack" },​
}​
​
推荐规则：​
  • type 要表达业务语义，而不是具体商品名​
  • 一个 type 对应一个 Handler​
  • 同一类商品尽量复用同一个 Handler​
注意：​
  • productId 必须按字符串维护​
  • CommercialDataLib 只负责支付路由，不要在这里冗余业务发货字段​
第 2 步：在业务配置表维护 productId 到业务行的映射​
推荐让业务自己的配置表维护真实发货信息，例如：​
​
GiftPackDataLib.Packs = {​
[1001] = {​
pk = 1001,​
productId = "114278499999",​
rewardList = {​
{ itemId = "diamond", count = 100 },​
{ itemId = "ticket", count = 2 },​
}​
}​
}​
​
同时提供一个反查方法：​
​
function GiftPackDataLib.GetByProductId(productId)​
if not productId or productId == "" then​
return nil​
end​
-- 这里可以做惰性索引，也可以直接遍历，取决于你的配置规模​
end​
​
推荐这样做的原因是：​
  • CommercialDataLib 不关心具体业务字段​
  • 真实发货数据只保留在业务配置表，避免双重维护​
第 3 步：实现新的 Deliver Handler​
新建一个 Handler，例如 GiftPackDeliverHandler.lua：​
​
GiftPackDeliverHandler = BaseClass:DefineClass("GiftPackDeliverHandler", BaseDeliverHandler)​
​
function GiftPackDeliverHandler:__init()​
end​
​
--- 校验发货依赖缓存是否就绪​
--- @param playerOpenId string​
--- @return boolean​
function GiftPackDeliverHandler:IsComplete(playerOpenId)​
local agg = ServerPlayerDataManager.Get(playerOpenId)​
if not agg then​
return false​
end​
--@TODO 判断需要写入的数据缓存，是否存在​
end​
​
--- 真实发货​
--- @param receiptInfo table​
--- @param callback fun(success:boolean, msg:string|nil, errorCode:number|nil)​
--- @param targetPlayer table​
function GiftPackDeliverHandler:Deliver(receiptInfo, callback, targetPlayer)​
--@TODO 发货逻辑​
end​
​
return GiftPackDeliverHandler​
​
实现时建议遵守规则：​
  • IsComplete 只判断发货依赖是否已加载，不在这里做业务校验。​
  • Deliver 只负责把订单翻译成业务调用，并把结果透传给支付层。这样做的好处在于金币购买、星光购买都可以走同一套逻辑。​
第 4 步：在 DeliverManager 注册 Handler​
在 ServerCommercialDeliverManager.Start() 中注册：​
​
function ServerCommercialDeliverManager.Start()​
if not DouyinApplication.isServer then​
return​
end​
​
DeliverHandlerDic["shop"] = AircraftShopDeliverHandler.New()​
DeliverHandlerDic["gift_pack"] = GiftPackDeliverHandler.New()​
end​
​
到这里，服务端路由就打通了：​
  • 支付回调拿到 productId​
  • CommercialDataLib 返回 type = "gift_pack"​
  • ServerCommercialDeliverManager 找到 GiftPackDeliverHandler​
  • Handler 执行真实发货​
第 5 步：客户端发起购买​
客户端仍然统一走：​
​
local commercialSystem = IOCContainer:GetSystem("CommercialSystem")​
commercialSystem:PurchaseProduct("114278499999", 1, "gift_pack_test")​
​
参数说明：​
  • 第 1 个参数：抖音侧商品 productId​
  • 第 2 个参数：购买数量​
  • 第 3 个参数：业务自定义透传字段 orderData​
注意：​
  • PurchaseProduct 只负责发起购买​
  • 实际到账结果以后端支付回调链路为准​
框架帮你做了什么​
新业务接入后，以下能力默认复用，不需要自己重写：​
  • 订单幂等：同一 purchaseOrder 重复回调不会重复发货​
  • 平台回执：自动调用 ConfirmOrder​
  • 补单：可恢复错误自动返回 1​
  • 退款：不可恢复错误返回 -10000 时自动转成 -1​
  • 订单缓存：订单结果自动写入 receiptData​
所以大多数业务真正需要写的代码只有：​
  • 一份业务配置映射​
  • 一个 Handler​
  • 一处注册​
何时返回退款，何时返回补单​
这是接入时最重要的约定之一。​
应该退款的情况​
这类错误通常不可恢复，应返回 -10000：​
  • productId 找不到业务配置​
  • 玩家已经永久拥有该商品，重复购买无意义​
  • 业务规则明确判定这是非法或无效订单​
应该补单的情况​
这类错误通常是临时性问题，可以不传 -10000：​
  • 依赖服务短暂异常​
  • 临时写库失败​
  • 外部模块暂时不可用​
支付层会把这些情况视为补单，等待平台后续重试。​

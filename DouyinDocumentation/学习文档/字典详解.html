01 / 概念

字典是“键 → 值”的映射

字典用一个 key（键）找到对应的 value（值）。例如系统名称对应系统实例、玩家 ID 对应玩家数据、物品 ID 对应配置行。键的用途是标识条目；值才是你要保存和取得的内容。

keyvalue表达的关系
"UISystem"UI 系统实例按名称取得系统
1000成就配置行按 ID 取得配置
"player-17"玩家档案按玩家标识取得数据

字典是一种映射能力，哈希表是一种实现方式。也可以用树实现映射；例如 C# 的 Dictionary<TKey,TValue> 和 SortedDictionary<TKey,TValue> 都提供键值映射，但底层结构、排序行为和成本不同。本文重点讲哈希表。

数组通常按位置访问：第 0 个、第 1 个。字典按标识访问：ID 为 1000 的条目。选择哪种结构，先看你的操作是“按位置读取”，还是“按标识查找”。

“键唯一”由相等规则决定。如果大小写不敏感，"UI" 和 "ui" 可以是同一个键；大小写敏感时，它们是两个键。两个不同键可以存同一个 value。

02 / 原理

一次哈希表查找分成几步

① 取得哈希从 key 计算或读取 hash
② 定位桶用 hash 找到候选区域
③ 检查候选比较哈希及键是否相等
④ 返回结果找到 value，或报告不存在

哈希函数把键映射成一个整数。它的作用是让数据分布到不同位置，从而缩小查找范围。哈希值不是键的唯一编号，也不是把原字符串修改成了一个整数。

如果有 8 个桶，教学示例可以使用 bucket = hash % 8。真实实现可能使用取模、位运算或优化过的计算方式。桶里还需要保留键或能够比较键的信息，因为位置相同不代表键相同。

同一个 key 必须产生兼容的哈希；不同 key 可以产生相同哈希。如果两个对象按比较器被认为相等，它们的哈希也必须相等。反过来，相同哈希不保证两个对象相等。

所谓碰撞包括：两个哈希值完全相同，或者两个不同哈希值最终定位到同一个桶。处理方式可以是沿候选链继续检查，也可以是在表内继续探测其他位置。碰撞处理和负载情况，决定了需要检查多少候选条目。

04 / 成本模型

“平均 O(1)”究竟固定了什么？

先定义三个量：n 是字典条目数量，L 是查询字符串长度，c 是本次查询检查的候选数量。不要把 n 和 L 混成同一个规模。

T(query) = T(hash, L) + T(bucket) + Σ T(compare, candidate)
候选数量分布良好，且哈希与比较视为常数时：期望查询成本 O(1)
分析范围常见结论前提
只考虑 n 的增长平均 / 期望 O(1)哈希分布良好，键处理成本固定
普通字符串每次完整计算哈希平均总成本 O(L)候选数量期望为常数；计入字符处理
已有哈希，键也能常数时间判等平均总成本 O(1)例如复用已驻留的短字符串对象
大量条目碰撞候选检查可退化为 O(n)一次查询可能检查许多条目

已有哈希不等于整个查询一定与 L 无关。两个不同的长字符串对象即使内容相同，判断内容相等仍可能检查 O(L) 个字符。若候选很多且每次比较也昂贵，成本还会组合增长。

对于固定键 "UISystem"，L 始终为 8。相对于 n，把它看成常数是合理的。因此“平均 O(1)”和“字符串哈希要处理字符”可以同时成立。

O(1) 描述增长趋势，不描述多少纳秒。函数调用、哈希计算、访问内存、分支和比较，即使都按常数计算，也各有实际成本。两段 O(1) 的代码可能相差很大。

“平均”和“摊销”也有区别：平均查找关注候选分布；摊销插入则把偶尔出现的扩容成本，分配到一串操作中。它们都不能保证每一次操作耗时相同。

05 / Lua 与 C#

字符串哈希是每次算，还是第一次算？

这由运行时、字符串对象和比较器决定。字符串不可变，意味着缓存哈希在逻辑上可行；它不意味着所有实现都会缓存。以下对照标准 Lua 5.3 与当前 .NET 源码，不把某个实现当成语言规范。

Lua 5.3：缓存保存在字符串对象上

短字符串在驻留时计算并保存哈希，相同内容可以复用同一个对象。table 查询已有短字符串时使用保存的哈希，并可用对象身份判等。长字符串通常在首次需要哈希时计算，然后保存结果。

反复执行同一段代码中的 GetSys("UISystem")，会复用已有的字符串常量。动态拼接或外部传入数据则不同：构造 / 驻留过程仍可能计算哈希或比较内容。缓存针对对象，不能理解成“相同文字在所有路径上只处理一次”。

lstring.c：驻留与哈希缓存ltable.c：查询路径

版本细节不能省略。标准 Lua 5.3 的长字符串哈希采用抽样，不能笼统断言其首次哈希一定扫描全部 L 个字节；Lua 5.4 的实现不同。创建长字符串和比较不同对象的内容仍可能与长度有关。

Lua 5.3 哈希循环Lua 5.4 哈希循环

.NET：存储条目的哈希，不等于缓存查询字符串的哈希

当前 .NET 的普通字符串 Dictionary 查询通常会调用比较器，为传入的 key 计算哈希。条目自身保存的 hashCode 用于候选筛选；它不能直接替代对任意查询 key 的处理。

普通字符串哈希路径通常仍读取字符，即使传入的是同一个字符串对象。字符串驻留、字典条目保存哈希、缓存查询结果，是三件不同的事。自定义比较器可以有不同策略；Unity 的 Mono / IL2CPP 还应以目标运行时为准。

06 / 空间与写入

字典为什么比“只存键和值”更占空间？

哈希表还要保存定位信息：桶、条目、哈希、冲突关联，以及尚未使用的容量。预留空间有助于减少频繁扩容，但会占用更多内存。查询更快与内存更省，并不总是同一个目标。

负载因子通常表示条目数量与桶数量的比值。它用来描述表有多拥挤，但“达到 0.75 就扩容”不是所有字典都遵循的规则。链式结构和开放寻址对负载的要求也不同。

扩容通常要分配更大的存储，并把已有条目重新安排到新位置。位置变了，不一定要重新计算每个字符串的哈希；有的实现可以使用保存的哈希。也有因切换哈希策略而重新计算的情况。

在键处理视为常数、容量按几何增长的模型下，单次触发扩容的插入可达到 O(n)，一串插入的摊销成本仍可为 O(1)。这解释了为什么连续写入大批数据时，会出现某一次操作比其他次慢很多。

C# · 已知大致数量时，在构造时指定容量
var players = new Dictionary<int, PlayerData>(capacity: 1000);

// capacity 是预留能力，不表示已经有 1000 条数据。
// 此时 players.Count 仍然是 0。

目标框架支持时，也可以使用 EnsureCapacity。在 Unity 工程中先检查 API Compatibility Level 和实际可用 API，不直接照搬最新版 .NET 的所有方法。

07 / 键设计

什么样的 key 更适合查找？

场景常见选择要明确的规则
物品、成就配置稳定的整数 ID是否允许 ID 复用；数字与字符串 ID 是否混用
IOC 系统注册固定的短名称拼写、大小写、是否有重名
玩家档案平台提供的稳定标识不要用可修改昵称当身份标识
多个维度共同标识明确的组合键字段边界和相等规则必须明确

整数键的处理成本通常较小，但“把所有字符串换成整数”不是必然值得做的优化。若转换本身还需要查另一张字典，你可能只是增加了一层查找。

相等规则和哈希规则必须一起设计

自定义键的哈希可以碰撞，但相等的键必须有一致的哈希。对象存入字典后，参与哈希和相等判断的字段应保持稳定；修改这些字段，可能让对象被存入的位置与后续查询位置不一致。

C# · 系统名称明确使用大小写敏感的序数比较
var systems = new Dictionary<string, object>(StringComparer.Ordinal);

// 如果业务确实要求 "UI" 与 "ui" 表示同一个键：
var names = new Dictionary<string, int>(StringComparer.OrdinalIgnoreCase);

组合字符串要避免拼接歧义，例如 1 .. 23 与 12 .. 3 都会变成 "123"。整数维度可以采用有明确分隔符的 "1:23"；任意文本则需要处理转义，或使用结构化组合键。

08 / 基本操作

Lua 和 C# 的使用差异

Lua：table 提供映射能力

LUA
local counts = {}

counts[1000] = 3        -- 写入
local count = counts[1000] -- 读取
counts[1000] = 4        -- 覆盖
counts[1000] = nil      -- 删除

local flags = { done = false }
print(flags.done ~= nil) -- true：键存在

C#：使用明确的字典类型

C#
var counts = new Dictionary<int, int>();

counts.Add(1000, 3);    // 重复 key 会抛异常
if (counts.TryGetValue(1000, out int count))
{
    Console.WriteLine(count);
}
counts[1000] = 4;       // 写入或覆盖
counts.Remove(1000);    // 删除

Lua 普通 table 中，值为 nil 就表示这个键没有条目；false 是可以保存的值。如果要判断“是否存在”，用 value ~= nil，不能只用 if value then。使用了元表 __index 的 table，普通读取还可能执行额外逻辑。

Lua 的 1000 和 "1000" 是不同键。普通 table 的稠密整数键可以使用数组部分，其他键使用哈希部分；并不是所有 table 访问都走同一条路径。不要用 #table 当任意字典的条目总数，也不要依赖 pairs 的遍历顺序。

Lua 的值与 table长度运算符数组 / 哈希两部分

C#：需要 value 时，优先一次 TryGetValue

C# · 避免 ContainsKey 后再索引造成两次查询
// 两次查询。
if (counts.ContainsKey(1000))
{
    Use(counts[1000]);
}

// 一次查询，明确处理不存在。
if (counts.TryGetValue(1000, out int count))
{
    Use(count);
}

不存在的键通过索引器读取会抛异常。TryGetValue 返回是否找到，并把结果放入输出参数；不存在时输出的是 TValue 的默认值。因此应检查返回的 bool，而不是仅凭输出值是否为 0 / null 判断是否找到。

示例里的 PlayerData、Use 代表你的业务类型和方法，不是 .NET 内置 API。

09 / 回到工程

把 ui 放到函数外，省掉了什么？

在这次工程中，GetSys("UISystem") 最终读取的是 Lua table：_systems[systemName]。因此，C# Dictionary 的字符串哈希行为，不能直接用来解释这一次查询。

A · 仅保存本次调用的查询结果
function AchievementSystem:CloseView()
    local ui = GetSys("UISystem")
    if ui then ui:CloseUI("UI_AchievementView") end
end
B · 变量移到外面，但每次依旧查询
local ui = nil

function AchievementSystem:CloseView()
    ui = GetSys("UISystem")
    if ui then ui:CloseUI("UI_AchievementView") end
end

A 和 B 每次都调用 GetSys。无论字符串哈希是否缓存，它们都没有减少这次 table 查询。区别是 A 用函数局部变量保存引用；B 用被函数捕获的外部局部变量，也就是 upvalue，保存引用。

local ui 不表示每次在堆上新建一个 UISystem 对象。它只是保存已有对象的引用，函数局部槽位由调用机制管理。B 会跨调用保留引用，并在模块内共享；是否更快必须结合编译器与运行时测量，不能用“少声明一个 local”直接推断。

C · 真正减少重复查询：仅在尚未缓存时查找
function AchievementSystem:GetUI()
    if self.ui == nil then
        self.ui = GetSys("UISystem")
    end
    return self.ui
end

C 是一种缓存示意。首次取得对象后，后续可以绕过 IOC 查找，但仍有方法调用和字段访问成本。如果 UISystem 会被移除或替换，就需要清除旧引用；如果首次查询返回 nil，后续会再次尝试。

先确认调用频率，再决定缓存。偶尔关闭一次界面，代码简洁通常更重要。如果每帧有大量重复依赖查询，再测量查找成本，考虑在明确的初始化阶段取得依赖。

这一节是对给定代码的成本分析，没有宣称 A、B 或 C 在所有 Lua / xLua 环境下都有固定的速度排名。局部变量与 upvalue 的作用域规则见 Lua 手册。

10 / 工程验证

怎样测量，才不会比较错东西？

先明确要测的层级：是纯字典查找，还是包含 GetSys 包装调用，或包含整个 UI 关闭过程？如果把 UI 操作放在循环里，测到的很可能主要是 UI 生命周期，而非字符串哈希。

  1. 控制 key 的来源。分别测试固定常量、复用已有字符串、每次动态生成字符串。动态生成的分配与构造成本应单独报告。
  2. 区分命中与未命中。两种路径不一定检查相同数量的候选。固定 n 后，再改变 L，避免只测一种很短的键。
  3. 把扩容和查询分开。先构建字典，再测查找；若要测写入，另测预留容量和扩容阶段。
  4. 固定运行条件。使用目标运行时和目标构建方式；JIT 环境需要预热，多轮比较，记录波动和分配，而非仅凭一次耗时。
  5. 避免测量代码干扰。循环内部不要打印、拼接日志或创建无关对象；使用或累积查询结果，避免把无用计算当成真实业务。

Unity 中应区分 Editor、Mono 和 IL2CPP 构建。标准 .NET 的微基准结果可以帮助理解，但不能直接当成 Unity 目标设备上的性能结论。本文交互实验显示的是操作步骤，不是实测性能数据。

优化的收益还要乘上调用频率：一次差异很小的查找，每帧执行数万次可能值得关注；每天只执行几次，则未必值得增加缓存与生命周期管理。

11 / 理解检查

用这几个问题检查自己是否理解

相同 hashCode 是否意味着相同 key？

不意味着。哈希会碰撞；还需要根据比较器判断 key 是否相等。相等的 key 必须有兼容哈希，但反方向不成立。

Dictionary 已保存条目哈希，为什么还要处理查询 key？

调用者可以传入任何键。查找必须先知道它应去哪个桶；条目哈希只在已经找到候选区域后帮助筛选候选。查询字符串自身是否缓存哈希，是另一项机制。

字符串哈希需要 O(L)，为什么字典仍被称为平均 O(1)？

常见描述是相对于条目数量 n，并把键处理成本固定。L 可变且需要完整处理时，应把字符串成本也计入；固定键的长度则可以视为常数。

把 ui 声明在函数外，就等于缓存 GetSys 的结果吗？

只有后续跳过 GetSys、直接复用之前结果时，才减少了查询。每次仍执行 ui = GetSys(...)，就仍有同样的查找。

Lua 中 value 为 false，是否表示这个 key 不存在？

不表示。false 是可保存的值；普通 table 中用 value ~= nil 判断存在。带元表的读取还要考虑 __index。

扩容后，是否必然重新计算所有字符串哈希？

不必然。条目的桶位置需要重新安排，但有的实现可以利用已保存的哈希；是否重算取决于实现和是否更换哈希策略。

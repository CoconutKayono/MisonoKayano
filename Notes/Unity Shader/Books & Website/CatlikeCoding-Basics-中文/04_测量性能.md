## 分析 Unity

Unity 持续渲染新帧。要让任何移动的东西显得流畅，它必须渲染得足够快，使我们把图像的序列感知为连续运动。通常每秒 30 帧——简称 FPS——是要达到的最低目标，而 60FPS 是理想值。这些数字经常出现，是因为许多设备的显示刷新率是 60 赫兹。在不关闭 VSync 的情况下，你无法比这更快地绘制帧，而关闭 VSync 会导致画面撕裂。如果无法稳定达到 60FPS，那么次优的速率是 30FPS，也就是每两次显示刷新一次。再低一档是 15FPS，这对流畅运动来说是不够的。

> **其他常见的显示器刷新率有哪些？**
>
> 75Hz、85Hz 和 144Hz 在桌面显示器上也很常见。在竞技游戏领域还有更高的刷新率。所以如果你的应用能稳定达到 85FPS，那么在所有显示器上开启 VSync 都会表现良好。如果只能达到 60FPS，那么 75Hz 显示器会降到一半速率，即 37.5FPS，85Hz 会减半到 42.5FPS，144Hz 会降到三分之一，即 48FPS。不过这假设性能是恒定的。实际上，帧率可能在刷新率的倍数之间波动。

能否达到目标帧率，取决于处理单个帧需要多长时间。要达到 60FPS，我们必须在不到 16.67 毫秒内更新并渲染每一帧。30FPS 的时间预算是其两倍，即每帧 33.33ms。

当图表运行时，我们可以通过简单观察来判断它的运动有多流畅，但这是非常不精确的性能测量方式。如果运动看起来流畅，那么它可能超过 30FPS；如果看起来卡顿，那可能低于这个值。由于性能不一致，它也可能这一刻流畅、下一刻卡顿。这可能由我们应用自身的变化引起，也可能由同一设备上运行的其他应用引起。Unity 编辑器根据它在做什么，也可能有前后不一致的性能。如果我们勉强达到 60FPS，最终可能快速地在 30FPS 和 60FPS 之间来回切换，尽管平均 FPS 很高，却会感觉抖动。所以要弄清发生了什么，我们必须更精确地测量性能。Unity 有几个工具可以帮助我们。

### 游戏窗口统计

游戏窗口有一个 *Statistics* 覆盖面板，可以通过它的 *Stats* 工具栏按钮激活。它显示上一渲染帧的测量值。它告诉我们的信息不多，但它是我们能用来了解情况的最简单工具。在编辑模式下，游戏窗口通常只在某些东西改变后偶发地更新。在运行模式下它每一帧都刷新。

以下统计针对的是使用环面函数、分辨率 100 时的图表，使用默认的内置渲染管线——从现在起我把它简称为 BRP。我为游戏窗口开启了 VSync，所以刷新与我的 60Hz 显示器同步。

![BRP 的统计。](https://catlikecoding.com/unity/tutorials/basics/measuring-performance/profiling-unity/stats-default.png)

统计显示的是这样一帧：CPU 主线程用了 31.7ms，渲染线程用了 29.2ms。根据你的硬件和游戏窗口的屏幕尺寸，你得到的结果很可能不同。以我的情况，它表明整个帧用了 60.9ms 来渲染，但统计面板报告的是 31.5FPS，与 CPU 时间吻合。FPS 指标似乎取最坏的时间，并假设那对应帧率。这是一种过度简化，只考虑了 CPU 一侧，忽略了 GPU 和显示器。真实帧率很可能更低。

> **什么是线程？**
>
> 线程是一个子进程，这里是 Unity 应用的子进程。同一时刻可以有多个线程并行运行。统计显示的是 Unity 主线程和渲染线程在上一帧中运行了多长时间。

除了时长和 FPS 指标，统计面板还显示关于渲染内容的各种细节。有 30.003 个批次，批处理节省的显然为零。这些是发送给 GPU 的绘制命令。我们的图表包含 10,000 个点，所以看起来每个点被渲染了三次：一次用于深度通道，一次用于阴影投射体——也单独列出——还有一次用于渲染最终的立方体，每个点各一次。另外三个批次是独立于我们图表的额外工作，比如天空盒和阴影处理。还有六次 set-pass 调用，可以理解为 GPU 被重新配置成以不同方式渲染，比如使用不同的材质。

![URP 的统计。](https://catlikecoding.com/unity/tutorials/basics/measuring-performance/profiling-unity/stats-urp.png)

如果我们改用 URP，统计就不同了。它渲染得更快。原因很容易看出来：只有 20.002 个批次，比 BRP 少了 10.001 个。这是因为 URP 对方向光阴影不使用单独的深度通道。它的 set-pass 调用确实更多，但看起来不是问题。

尽管 *Saved by batching* 报告没有批处理，URP 默认使用 SRP Batcher，但统计面板不认识它。SRP Batcher 不会消除单个绘制命令，但能让它们高效得多。为了说明这一点，选中我们的 *URP* 资源，在其 Inspector 底部的 *Advanced* 部分禁用 *SRP Batcher*。确保 *Dynamic Batching* 也被禁用。

![URP 高级设置。](https://catlikecoding.com/unity/tutorials/basics/measuring-performance/profiling-unity/urp-advanced.png)

禁用 SRP Batcher 后，URP 的性能差得多。

![禁用 SRP Batcher 的 URP 统计。](https://catlikecoding.com/unity/tutorials/basics/measuring-performance/profiling-unity/stats-urp-no-batcher.png)

### 动态批处理

除了 SRP Batcher，URP 还有另一个动态批处理开关。这是一项旧技术，它动态地把小网格合并成一个更大的网格，然后渲染这个合并后的网格。为 URP 启用它会把批次减少到 10.024，统计面板表明消除了 9.978 次绘制。

![启用动态批处理的 URP 统计。](https://catlikecoding.com/unity/tutorials/basics/measuring-performance/profiling-unity/stats-urp-dynamic-batching.png)

以我的情况，SRP Batcher 和动态批处理的性能相当，因为我们图表点的立方体网格是动态批处理的理想候选。

BRP 没有 SRP Batcher，但我们可以为它启用动态批处理。这种情况下，开关在 *Player* 项目设置的 *Other Settings* 部分，就在我们把颜色空间设为线性处再往下一点。只有在不使用任何可编程渲染管线设置时它才可见。

![启用动态批处理的 BRP 统计。](https://catlikecoding.com/unity/tutorials/basics/measuring-performance/profiling-unity/stats-default-dynamic-batching.png)

动态批处理对 BRP 高效得多，消除了 29.964 个批次，把它们减少到只有 39 个，但看起来帮助不大。

### GPU 实例化

另一种提高渲染性能的方法是启用 GPU 实例化（GPU instancing）。这使得可以用一条绘制命令，告诉 GPU 用同一个材质绘制一个网格的许多实例，并提供一个变换矩阵数组以及可选的其他实例数据。这种情况下，我们必须为每个材质启用它。我们的材质有一个 *Enable GPU Instancing* 开关。

![启用了 GPU 实例化的材质。](https://catlikecoding.com/unity/tutorials/basics/measuring-performance/profiling-unity/material-gpu-instancing-enabled.png)

URP 更偏好 SRP Batcher 而不是 GPU 实例化，所以要让它对我们的点生效，必须禁用 SRP Batcher。然后我们能看到批次数量减少到只有 46，比动态批处理好得多。稍后我们会发现这种差异的原因。

![启用 GPU 实例化的 URP 统计。](https://catlikecoding.com/unity/tutorials/basics/measuring-performance/profiling-unity/stats-urp-gpu-instancing.png)

我们可以从这些数据得出结论：对 URP 来说，GPU 实例化最好，其次是动态批处理，然后是 SRP Batcher。但差异很小，所以对我们的图表来说它们实际上差不多。唯一明确的结论是，应该使用 GPU 实例化或 SRP Batcher 其中之一。

对 BRP 来说，GPU 实例化产生的批次比动态批处理多，但帧率略高一点。

![启用 GPU 实例化的 BRP 统计。](https://catlikecoding.com/unity/tutorials/basics/measuring-performance/profiling-unity/stats-default-gpu-instancing.png)

### 帧调试器

统计面板能告诉我们使用动态批处理不同于使用 GPU 实例化，但不会告诉我们为什么。为了更好地理解发生了什么，我们可以使用帧调试器，通过 *Window / Analysis / Frame Debugger* 打开。通过它的工具栏按钮启用后，它会显示游戏窗口上一帧发送给 GPU 的所有绘制命令的列表，按性能分析样本分组。这个列表显示在它左侧。右侧显示所选中的某个具体绘制命令的详细信息。另外，游戏窗口会显示渐进式的绘制状态，直到紧接所选命令之后。

> **为什么我的电脑突然发烫？**
>
> Unity 使用了一个技巧，需要一遍又一遍地渲染同一帧，来显示绘制一帧的中间状态。只要帧调试器处于激活状态，它就会一直这么做。确保在不需要时禁用帧调试器。

在我们的情况下，我们必须处于运行模式，因为那时我们的图表才会被绘制。启用帧调试器会暂停运行模式，让我们能够检查绘制命令的层级。先对 BRP 这么做，不使用动态批处理也不使用 GPU 实例化。

![BRP 的帧调试器。](https://catlikecoding.com/unity/tutorials/basics/measuring-performance/profiling-unity/frame-debugger-default.png)

我们看到总共 30.007 次绘制调用，比统计面板报告的还多，因为还有不计入批次的命令，比如清除目标缓冲。我们点的 30,000 次绘制被单独列为 *Draw Mesh Point(Clone)*，分别在 *DepthPass.Job*、*Shadows.RenderDirJob* 和 *RenderForward.RenderLoopJob* 之下。

如果我们启用动态批处理再试一次，命令结构保持不变，只是每组 10,000 次绘制被减少为十二次 *Draw Dynamic* 调用。在 CPU-GPU 通信开销方面，这是显著的改善。

![启用动态批处理的 BRP。](https://catlikecoding.com/unity/tutorials/basics/measuring-performance/profiling-unity/frame-debugger-default-dynamic-batching.png)

而如果我们使用 GPU 实例化，那么每组被减少为 20 次 *Draw Mesh (Instanced) Point(Clone)* 调用。同样是大改善，但方法不同。

![启用 GPU 实例化的 BRP。](https://catlikecoding.com/unity/tutorials/basics/measuring-performance/profiling-unity/frame-debugger-default-gpu-instancing.png)

对 URP 我们能看到同样的现象，但命令层级不同。这种情况下点被绘制两次，先在 *Shadows.Draw* 下，又在 *RenderLoop.Draw* 下。一个显著的差异是，动态批处理似乎对阴影贴图不起作用，这就解释了为什么它对 URP 效果较差。我们最终得到 22 个批次而不是只有十二个，这表明 URP 材质比标准 BRP 材质依赖更多的网格顶点数据，所以单个批次里能容纳的点更少。与动态批处理不同，GPU 实例化对阴影确实起作用，所以这种情况下它更优。

![不使用任何优化、动态批处理、以及 GPU 实例化的 URP。](https://catlikecoding.com/unity/tutorials/basics/measuring-performance/profiling-unity/frame-debugger-urp.png)

最后，启用 SRP Batcher 后，绘制 10,000 个点被列为 11 条 *SRP Batch* 命令，但要记住这些仍然是单独的绘制调用，只是非常高效而已。

![启用 SRP Batcher 的 URP。](https://catlikecoding.com/unity/tutorials/basics/measuring-performance/profiling-unity/frame-debugger-urp-srp-batcher.png)

### 一盏额外的灯

到目前为止我们得到的结果针对的是：我们的图表，带一个方向光，以及我们使用的其他项目设置。让我们看看往场景里加第二盏灯会发生什么，具体是通过 *GameObject / Light / Point Light* 加一盏点光源。把它的位置设为零，并确保它不投射阴影，这是它的默认行为。BRP 支持点光源阴影，但 URP 仍然不支持。

![原点处无阴影的点光源。](https://catlikecoding.com/unity/tutorials/basics/measuring-performance/profiling-unity/point-light.png)

有了额外的灯，BRP 现在会把所有点再绘制一次。帧调试器显示 *RenderForward.RenderLoopJob* 渲染的量是之前的两倍。更糟的是，动态批处理现在只对深度和阴影通道起作用，对前向通道不起作用。

![不使用任何优化和动态批处理的 BRP。](https://catlikecoding.com/unity/tutorials/basics/measuring-performance/profiling-unity/point-light-nothing.png)

发生这种情况是因为 BRP 每盏灯绘制每个对象一次。它有一个与单个方向光配合的主通道，之后额外的通道被渲染叠加在它上面。这是因为它是老式的前向叠加（forward-additive）渲染管线。动态批处理无法处理这些不同的通道，所以没有被使用。

GPU 实例化也是如此，只不过它对主通道仍然有效。只有额外的灯光通道无法从中受益。

![启用 GPU 实例化的 BRP。](https://catlikecoding.com/unity/tutorials/basics/measuring-performance/profiling-unity/point-light-gpu-instancing.png)

第二盏灯对 URP 似乎没有影响，因为它是一种现代的前向渲染器，在单个通道里应用所有光照。所以命令列表保持不变，即使 GPU 每次绘制需要执行更多光照计算。

这些结论针对的是影响所有点的单盏额外灯。如果你加更多灯并移动它们，使不同点受不同灯影响，事情会变得更复杂，使用 GPU 实例化时批次可能会被拆分。对简单场景成立的，对复杂场景未必成立。

> **那延迟渲染呢？**
>
> BRP 和 HDRP 同时有前向和延迟渲染模式，URP 目前没有。延迟渲染的思想是，对象只被绘制一次，把它们的可见表面属性存储到 GPU 缓冲区中。之后一个或多个光照通道只对可见内容应用光照。与前向渲染相比，它有利有弊，但本教程系列不涉及它。

### 性能分析器

为了更好地了解 CPU 一侧发生了什么，我们可以打开性能分析器（profiler）窗口。关掉点光源，通过 *Window / Analysis / Profiler* 打开窗口。它会在运行模式下记录性能数据，并存储下来供之后检查。

性能分析器分为两个部分。它的上半部分包含一个模块列表，显示各种性能图表。最上面的是 *CPU Usage*，这是我们要关注的。选中该模块后，窗口下半部分显示某一帧的详细分解，我们可以在图表中选中这一帧。

![显示 CPU 使用时间线的性能分析器，BRP 和 URP。](https://catlikecoding.com/unity/tutorials/basics/measuring-performance/profiling-unity/profiler-default.png)

CPU 使用情况的默认底部视图是时间线。它可视化一帧内时间花在了什么上面。它显示每一帧从 *PlayerLoop* 开始，而它大部分时间花在调用 *RunBehaviourUpdate* 上。再往下两步，我们看到那主要是在调用我们的 `Graph.Update` 方法。你可以选中一个时间线块来查看它的完整名称和以毫秒为单位的时长。

在最初的 player loop 片段之后是一段简短的 *EditorLoop* 部分，之后是另一个 player 片段，对应帧的渲染部分，CPU 在那里告诉 GPU 要做什么。工作被分配在主线程、渲染线程和几个 job 工作线程之间，但 BRP 和 URP 的具体做法不同。这些线程并行运行，但当一个线程必须等待另一个线程的结果时，也有同步点。

在渲染部分之后——如果使用 URP，渲染线程此时仍然繁忙——是另一个 editor 片段，之后下一帧开始。线程也可能看起来跨越了帧边界。这是因为 Unity 可以在渲染线程完成之前，就在主线程上启动下一帧的更新循环，利用并行性。我们将在下一节回到这一点。

如果你对线程的精确时序不感兴趣，可以通过左侧的下拉列表把 *Timeline* 视图替换为 *Hierarchy* 视图。层级视图把同样的数据显示在一个可排序的列表中。这个视图更容易看出什么耗时最长，以及内存分配发生在哪里。

![显示层级的性能分析器。](https://catlikecoding.com/unity/tutorials/basics/measuring-performance/profiling-unity/profiler-hierarchy.png)

### 分析构建产物

性能分析器清楚地表明，编辑器给我们的应用增加了大量开销。因此，分析独立运行的构建产物要有用得多。为此我们必须构建我们的应用，特别是用于调试的构建。我们可以在 *Build Settings* 窗口里配置应用如何构建，通过 *File / Build Settings...* 打开。如果你还没配置过，*Scenes in Build* 部分是空的。这没关系，因为默认会使用当前打开的场景。

你可以选择目标平台，对你来说当前机器最方便。然后启用 *Development Build* 和 *Autoconnect Profiler* 选项。

![用于分析的开发构建。](https://catlikecoding.com/unity/tutorials/basics/measuring-performance/profiling-unity/development-build.png)

要最终创建独立应用——通常称为构建产物——按 *Build* 按钮，或按 *Build and Run* 让构建过程一结束就立即打开应用。你也可以通过 *File / Build and Run* 或所示快捷键触发另一次构建。

> **构建过程要多久？**
>
> 第一次构建最久，使用 URP 时可能要忙上几分钟。之后 Unity 会尽可能复用之前生成的构建数据，显著加快进程。除此之外，项目越大耗时越长。

构建产物一旦独立运行，过一会儿退出它，切回 Unity。性能分析器现在应该包含它性能表现的信息。第一次构建后这不一定会发生，如果没有，就再试一次。还要记住，附加到构建产物时，性能分析器不会清除旧数据，即使启用了 *Clear on Play* 也一样，所以如果你只运行了应用几秒钟，要确保查看的是相关帧。

![分析构建产物，BRP 和 URP。](https://catlikecoding.com/unity/tutorials/basics/measuring-performance/profiling-unity/profiler-default-build.png)

因为没有编辑器开销，构建产物应该比 Unity 编辑器里的运行模式表现更好。性能分析器确实不再显示 editor loop 部分了。

## 显示帧率

我们并不总是需要详细的性能分析信息，一个大致的帧率指标往往就够了。另外，我们——或其他人——可能在没有 Unity 编辑器的地方运行我们的应用。对于这些情况，我们能做的是在应用内部测量并显示帧率，做成一个小覆盖面板。这样的功能默认没有，所以我们要自己创建。

### UI 面板

一个小覆盖面板可以用 Unity 的游戏内 UI 来创建。我们还要用 *TextMeshPro* 来创建显示帧率的文本。*TextMeshPro* 是一个单独的包，包含高级文本显示功能，优于默认的 UI 文本组件。如果你还没安装它的包，通过包管理器添加它。这也会自动安装 *Unity UI* 包，因为 *TextMeshPro* 依赖它。

> **为什么不用 UI Toolkit？**
>
> *UI Toolkit* 目前只用于编辑器 UI。有一个用于运行时的包，但它仍处于预览阶段，所以我不用它。

### 更新显示

要更新计数器，我们需要一个自定义组件。为 `FrameRateCounter` 组件新建一个 C# 脚本资源。给它一个可序列化的 `TMPro.TextMeshProUGUI` 字段，用来持有对用于显示数据的文本组件的引用。

```diff
+using UnityEngine;
+using TMPro;

+public class FrameRateCounter : MonoBehaviour {

+	[SerializeField]
+	TextMeshProUGUI display;
+}
```

把这个组件加到文本对象上，并连接好 display。

![帧率计数器组件。](https://catlikecoding.com/unity/tutorials/basics/measuring-performance/showing-the-frame-rate/frame-rate-counter-component.png)

要显示帧率，我们需要知道上一帧到当前帧之间过了多少时间。这个信息可以通过 `Time.deltaTime` 获得。然而，这个值受时间缩放影响，时间缩放可能用于慢动作、快进或完全停止时间。我们需要改用 `Time.unscaledDeltaTime`。在 `FrameRateCounter` 新的 `Update` 方法开头获取它。

```diff
+	void Update () {
+		float frameDuration = Time.unscaledDeltaTime;
+	}
```

下一步是调整显示的文本。我们可以通过调用它的 `SetText` 方法并传入文本字符串参数来实现。先提供我们已有的那个占位文本。字符串写在双引号之间，换行用特殊的 `\n` 字符序列来写。

```diff
		float frameDuration = Time.unscaledDeltaTime;
+		display.SetText("FPS\n000\n000\n000");
```

`TextMeshProUGUI` 有接受额外 `float` 参数的 `SetText` 变体。把帧时长作为第二个参数加进去，然后把我们字符串里第一个三零行替换成花括号里的一个零。这表明 `float` 参数应该插入字符串的什么位置。

```diff
		display.SetText("FPS\n{0}\n000\n000", frameDuration);
```

帧时长告诉我们流逝了多少时间。要以每秒帧数来显示帧率，我们必须显示它的倒数，也就是 1 除以帧时长。

```diff
		display.SetText("FPS\n{0}\n000\n000", 1f / frameDuration);
```

这会显示一个有意义的数值，但会有很多位数字，比如 59.823424。我们可以通过在零后面加冒号和期望的位数，指示文本四舍五入到小数点后指定位数。我们四舍五入到整数，所以加零。

```diff
		display.SetText("FPS\n{0:0}\n000\n000", 1f / frameDuration);
```

显示上一帧的帧率。

### 平均帧率

显示的帧率最终会快速变化，因为相邻帧之间的时间几乎从来不完全相同。我们可以通过显示帧率平均值而不是只显示上一帧的速率，让它不那么杂乱。做法是记录已经渲染了多少帧以及总时长，然后显示帧数除以它们的合计时长。

```diff
+	int frames;

+	float duration;

	void Update () {
		float frameDuration = Time.unscaledDeltaTime;
+		frames += 1;
+		duration += frameDuration;
		display.SetText("FPS\n{0:0}\n000\n000", frames / duration);
	}
```

这会让计数器运行得越久，越趋向一个稳定的平均值，但这个平均值针对的是我们应用的整个运行时长。因为我们想要的是最近的信息，我们必须频繁地重置并重新开始，采样新的平均值。我们可以通过添加一个可序列化的采样时长字段来让它可配置，默认设为一秒。给它一个合理的范围，比如 0.1–2。时长越短，结果越精确，但它变化得更快，也就更难读。

```diff
	[SerializeField]
	TextMeshProUGUI display;

+	[SerializeField, Range(0.1f, 2f)]
+	float sampleDuration = 1f;
```

![采样时长设为一秒。](https://catlikecoding.com/unity/tutorials/basics/measuring-performance/showing-the-frame-rate/sample-duration.png)

从现在起，我们只在累计时长等于或超过配置的采样时长时，才更新显示。我们可以用 `>=` 大于等于运算符来检查。更新显示之后，把累计的帧数和时长都设回零。

```diff
	void Update () {
		float frameDuration = Time.unscaledDeltaTime;
		frames += 1;
		duration += frameDuration;

+		if (duration >= sampleDuration) {
			display.SetText("FPS\n{0:0}\n000\n000", frames / duration);
+			frames = 0;
+			duration = 0f;
+		}
	}
```

一秒内的平均帧率。

### 最好与最差

平均帧率会波动，因为我们应用的性能并不恒定。它有时会变慢，要么是因为暂时有更多工作要做，要么是因为同一台机器上运行的其他进程碍事。为了了解这些波动有多大，我们还要记录并显示采样期间出现的最好和最差帧时长。把最好时长默认设为 `float.MaxValue`，这是最糟糕的可能的“最好时长”。

```diff
	float duration, bestDuration = float.MaxValue, worstDuration;
```

每次更新时，检查当前帧时长是否小于迄今的最好时长。如果是，就让它成为新的最好时长。还要检查当前帧时长是否大于迄今的最差时长。如果是，就让它成为新的最差时长。

```diff
	void Update () {
		float frameDuration = Time.unscaledDeltaTime;
		frames += 1;
		duration += frameDuration;

+		if (frameDuration < bestDuration) {
+			bestDuration = frameDuration;
+		}
+		if (frameDuration > worstDuration) {
+			worstDuration = frameDuration;
+		}

		…
	}
```

现在我们把最好帧率放在第一行，平均帧率放在第二行，最差帧率放在最后一行。我们可以通过给 `SetText` 加两个参数、给字符串加更多占位符来实现。它们用索引表示，第一个数字用 0 表示，第二个用 1，第三个用 2。之后还要重置最好和最差时长。

```diff
		if (duration >= sampleDuration) {
			display.SetText(
				"FPS\n{0:0}\n{1:0}\n{2:0}",
+				1f / bestDuration,
				frames / duration,
+				1f / worstDuration
			);
			frames = 0;
			duration = 0f;
+			bestDuration = float.MaxValue;
+			worstDuration = 0f;
		}
```

最好、平均和最差帧率。

注意，最好帧率可以超过显示刷新率，即使开启了 VSync 也一样。同样，最差帧率也不一定是显示刷新率的倍数。这是可能的，因为我们测量的不是显示帧之间的时长。我们测量的是 Unity 帧之间的时长，即其更新循环的迭代。Unity 的更新循环并不与显示器完美同步。当性能分析器显示下一帧的 player loop 在当前帧的渲染线程仍繁忙时启动时，我们已经瞥见了这一点。而渲染线程结束后，GPU 还有工作要做，之后还要过一段时间显示器才刷新。所以我们显示的 FPS 不是真实的帧率，而是 Unity 告诉我们的帧率。理想情况下它们相同，但要做到准确很复杂。有一篇 [Unity 博客文章](https://blogs.unity3d.com/2020/10/01/fixing-time-deltatime-in-unity-2020-2-for-smoother-gameplay-what-did-it-take/)讲了 Unity 如何在这方面改进，但那也没有讲全。

### 帧时长

每秒帧数是衡量感知性能的好单位，但在尝试达到目标帧率时，显示帧时长更有用。例如，在移动设备上尝试实现稳定的 60FPS 时，每一毫秒都很重要。所以让我们给帧率计数器加一个显示模式配置选项。

在 `FrameRateCounter` 内部为 FPS 和 MS 定义一个 `DisplayMode` 枚举，然后添加一个该类型的可序列化字段，默认设为 FPS。

```diff
	[SerializeField]
	TextMeshProUGUI display;

+	public enum DisplayMode { FPS, MS }

+	[SerializeField]
+	DisplayMode displayMode = DisplayMode.FPS;
```

![可配置的显示模式。](https://catlikecoding.com/unity/tutorials/basics/measuring-performance/showing-the-frame-rate/display-mode.png)

然后当我们在 `Update` 里刷新显示时，检查模式是否设为 FPS。如果是，就做我们已经在做的事。否则把 FPS 标题替换为 MS，并使用倒数参数。再把它们乘以 1000，把秒转换为毫秒。

```diff
		if (duration >= sampleDuration) {
+			if (displayMode == DisplayMode.FPS) {
				display.SetText(
					"FPS\n{0:0}\n{1:0}\n{2:0}",
					1f / bestDuration,
					frames / duration,
					1f / worstDuration
				);
+			}
+			else {
+				display.SetText(
+					"MS\n{0:0}\n{1:0}\n{2:0}",
+					1000f * bestDuration,
+					1000f * duration / frames,
+					1000f * worstDuration
+				);
+			}
			frames = 0;
			duration = 0f;
			bestDuration = float.MaxValue;
			worstDuration = 0f;
		}
```

帧时长通常以十分之一毫秒为单位来测量。我们可以把数字四舍五入从 0 增加到 1，把显示的精度提高一位。

```diff
				display.SetText(
					"MS\n{0:1}\n{1:1}\n{2:1}",
					1000f * bestDuration,
					1000f * duration / frames,
					1000f * worstDuration
				);
```

![帧时长。](https://catlikecoding.com/unity/tutorials/basics/measuring-performance/showing-the-frame-rate/precise-frame-duration.png)

### 内存分配

我们的帧率计数器完成了，但在继续之前，让我们检查它对性能的影响有多大。显示 UI 需要每帧更多绘制调用，但那其实没什么影响。在运行模式下使用性能分析器，然后找一帧我们更新文本的帧。结果表明这花不了多少时间，但它确实分配了内存。这通过层级视图、按 *GC Alloc* 列排序最容易检测。

![性能分析器层级中显示的分配。](https://catlikecoding.com/unity/tutorials/basics/measuring-performance/showing-the-frame-rate/profiler-hierarchy-allocations.png)

文本字符串是对象。当我们通过 `SetText` 创建一个新的时，会产生一个新的字符串对象，这造成了 106 字节的分配。Unity 的 UI 刷新随后把它增加到 4.5 千字节。虽然这不多，但它会累积，在某个时刻触发内存垃圾回收过程，导致不希望出现的帧时长尖峰。

意识到临时对象的内存分配、并尽可能消除反复出现的分配，是很重要的。幸运的是，`SetText` 和 Unity 的 UI 更新只在编辑器里执行这些内存分配，原因有很多，比如更新文本输入字段。如果我们分析构建产物，会发现一些初始分配，之后就没有了。所以分析构建产物至关重要。分析编辑器的运行模式只适合做初步印象。

## 自动切换函数

现在我们知道了如何分析应用，就可以比较它显示不同函数时的性能。如果某个函数需要更多计算，CPU 就要做更多工作，这可能降低帧率。不过，点如何计算对 GPU 没有区别。如果分辨率相同，GPU 要做的工作量相同。

最大差异在波函数和环面函数之间。我们可以通过性能分析器比较它们的 CPU 使用。我们既可以比较两次配置了不同函数的独立运行，也可以在运行模式下分析并在运行中切换。

![从环面切换到波时的尖峰。](https://catlikecoding.com/unity/tutorials/basics/measuring-performance/automatic-function-switching/spike-during-switch.png)

CPU 图显示，从环面切换到波之后负载确实下降了。切换发生时还有一个巨大的帧时长尖峰。这是因为通过编辑器做修改时，运行模式被暂时暂停了。之后由于取消选中和编辑器焦点变化，也出现了一些较小的尖峰。

这些尖峰属于 *Other* 类别。CPU 图可以通过切换左侧的类别标签来过滤，这样我们只看到相关数据。禁用 *Other* 类别后，计算量的变化更明显。

![不显示 Other 类别。](https://catlikecoding.com/unity/tutorials/basics/measuring-performance/automatic-function-switching/others-not-shown.png)

> **剩下的小尖峰是什么？**
>
> 那是碰巧激活的垃圾回收器。

由于那些暂停，通过 Inspector 切换函数来做性能分析很别扭。更糟的是，分析不同函数必须重新构建。我们可以通过给图表添加在 Inspector 之外切换函数的能力来改进——要么自动，要么通过用户输入。本教程我们选择第一种方案。

### 循环遍历函数

我们将自动循环遍历所有函数。每个函数显示固定时长，之后显示下一个。要让函数时长可配置，给 `Graph` 添加一个可序列化字段，默认一秒。再通过给它 `Min` 属性，把最小值设为零。时长为零会导致每一帧都切换到不同函数。

```diff
	[SerializeField]
	FunctionLibrary.FunctionName function;

+	[SerializeField, Min(0f)]
+	float functionDuration = 1f;
```

![函数时长。](https://catlikecoding.com/unity/tutorials/basics/measuring-performance/automatic-function-switching/function-duration.png)

从现在起，我们需要记录当前函数已激活多久，并在需要时切换到下一个。这会让 `Update` 方法变复杂。它当前的代码只负责更新当前函数，所以我们把它移到一个单独的 `UpdateFunction` 方法里，让 `Update` 调用它。这保持代码有条理。

```diff
	void Update () {
+		UpdateFunction();
+	}

+	void UpdateFunction () {
		FunctionLibrary.Function f = FunctionLibrary.GetFunction(function);
		float time = Time.time;
		float step = 2f / resolution;
		float v = 0.5f * step - 1f;
		for (int i = 0, x = 0, z = 0; i < points.Length; i++, x++) { … }
	}
```

现在添加一个时长字段，并在 `Update` 开头把它增加——可能被缩放的——delta time。然后如果时长等于或超过配置的时长，就把它重置回零。之后是 `UpdateFunction` 的调用。

```diff
	Transform[] points;

+	float duration;

	…

	void Update () {
+		duration += Time.deltaTime;
+		if (duration >= functionDuration) {
+			duration = 0f;
+		}
		UpdateFunction();
	}
```

我们很可能永远不会精确达到函数时长，而是会稍微超过它。我们可以忽略这一点，但为了与函数切换的预期时机保持合理同步，我们应该把多出的时间从下一个函数的时长里扣除。做法是从当前时长里减去期望时长，而不是把它设为零。

```diff
		if (duration >= functionDuration) {
			duration -= functionDuration;
		}
```

要循环遍历函数，我们给 `FunctionLibrary` 添加一个 `GetNextFunctionName` 方法，它接收一个函数名并返回下一个。因为枚举是整数，我们可以直接给它的参数加一并返回。

```diff
+	public static FunctionName GetNextFunctionName (FunctionName name) {
+		return name + 1;
+	}
```

但我们也必须循环回第一个函数，而不是越过最后一个，否则最终会得到一个无效的名字。所以只有当提供的名字小于环面时，我们才增加它。否则返回第一个函数，即波。我们可以用 if-else 块来实现，每个块返回相应的结果。

```diff
+		if (name < FunctionName.Torus) {
			return name + 1;
+		}
+		else {
+			return FunctionName.Wave;
+		}
```

我们可以让这个方法与函数名无关，把名字——作为 int——与 functions 数组长度减一比较，后者对应最后一个函数的索引。如果我们在末尾，也可以返回零，即第一个索引。这种做法的好处是，以后如果我们改函数名，就不用调整这个方法了。

```diff
		if ((int)name < functions.Length - 1) {
			return name + 1;
		}
		else {
			return 0;
		}
```

也可以用 `?:` 三元条件运算符把方法体缩减为单个表达式。它是一个 if-then-else 表达式，用 `?` 和 `:` 分隔各部分。两个分支都必须产生相同类型的值。

```diff
	public static FunctionName GetNextFunctionName (FunctionName name) {
+		return (int)name < functions.Length - 1 ? name + 1 : 0;
	}
```

在 `Graph.Update` 里使用这个新方法，在合适时切换到下一个函数。

```diff
		if (duration >= functionDuration) {
			duration -= functionDuration;
+			function = FunctionLibrary.GetNextFunctionName(function);
		}
```

循环切换函数。

现在我们可以通过分析构建产物，依次看到所有函数的性能。

![分析循环切换函数的构建产物。](https://catlikecoding.com/unity/tutorials/basics/measuring-performance/automatic-function-switching/profiler-build-looping-functions.png)

以我的情况，所有函数的帧率相同，因为它从没降到 60FPS 以下。差异被等待 VSync 抹平了。在开启 VSync 的情况下分析构建产物，会让差异更明显。或者，在性能分析器里只显示脚本。

![只显示脚本。](https://catlikecoding.com/unity/tutorials/basics/measuring-performance/automatic-function-switching/profiler-build-looping-functions-only-scripts.png)

结果是 *Wave* 最快，其次是 *Ripple*，然后是 *Multi Wave*，之后是 *Sphere*，*Torus* 最慢。这与我们了解代码后的预期一致。

> **VSync 难道不应该在性能分析器里以黄色单独显示吗？**
>
> 应该，但在 Unity 2020 里我没有看到。它反而和渲染合并在一起了。

### 随机函数

让我们让图表更有趣一点，加一个选项来随机切换函数，而不是循环固定序列。给 `FunctionLibrary` 添加一个 `GetRandomFunctionName` 方法来支持这一点。它可以通过调用 `Random.Range`、以零和 functions 数组长度作为参数来随机选一个索引。选中的索引是有效的，因为这是该方法的整数版本，其提供的范围是含头不含尾的。

```diff
+	public static FunctionName GetRandomFunctionName () {
+		var choice = (FunctionName)Random.Range(0, functions.Length);
+		return choice;
+	}
```

我们可以更进一步，确保永远不会连续两次得到同一个函数。做法是把新方法重命名为 `GetRandomFunctionNameOtherThan`，并添加一个函数名参数。把 `Random.Range` 的第一个参数增加到 1，这样索引零就永远不会被随机选中。然后检查选择是否等于要避免的名字。如果是，就返回第一个名字，否则返回选中的那个。这样我们就用零替代了被禁止的索引，而不引入选择偏差。

```diff
	public static FunctionName GetRandomFunctionNameOtherThan (FunctionName name) {
		var choice = (FunctionName)Random.Range(1, functions.Length);
		return choice == name ? 0 : choice;
	}
```

回到 `Graph`，为过渡模式加一个配置选项，要么循环（cycle）要么随机（random）。再次用自定义枚举字段来做。

```diff
	[SerializeField]
	FunctionLibrary.FunctionName function;

+	public enum TransitionMode { Cycle, Random }

+	[SerializeField]
+	TransitionMode transitionMode;
```

挑选下一个函数时，检查过渡模式是否设为循环。如果是，调用 `GetNextFunctionName`，否则调用 `GetRandomFunctionNameOtherThan`。因为这让挑选下一个函数变复杂了，我们也把这段代码放到单独的方法里，保持 `Update` 简单。

```diff
	void Update () {
		duration += Time.deltaTime;
		if (duration >= functionDuration) {
			duration -= functionDuration;
-			//function = FunctionLibrary.GetNextFunctionName(function);
+			PickNextFunction();
		}
		UpdateFunction();
	}

+	void PickNextFunction () {
+		function = transitionMode == TransitionMode.Cycle ?
+			FunctionLibrary.GetNextFunctionName(function) :
+			FunctionLibrary.GetRandomFunctionNameOtherThan(function);
+	}
```

![随机挑选函数。](https://catlikecoding.com/unity/tutorials/basics/measuring-performance/automatic-function-switching/transition-mode-random.png)

### 插值函数

我们通过让函数之间的过渡更有趣来结束本教程。不再突然切换到另一个函数，而是把图表平滑地变形到下一个函数。这对性能分析也很有意思，因为在过渡期间它需要同时计算两个函数。

先给 `FunctionLibrary` 添加一个 `Morph` 函数，它将处理过渡。给它与函数方法相同的参数，再加两个 `Function` 参数和一个控制变形进度的 `float` 参数。

```diff
+	public static Vector3 Morph (
+		float u, float v, float t, Function from, Function to, float progress
+	) {}
```

我们使用 `Function` 参数而不是 `FunctionName` 参数，因为这样 `Graph` 可以每次更新按名字获取函数一次，而不必每个点访问两次 functions 数组。

> **为什么要在 `Graph` 里每次更新都获取函数？**
>
> 我们也可以把函数存储在 `Graph` 的字段里，而不是每次更新获取。我们不这么做，是因为类型为 `Function` 的字段值无法在热重载后存活，而 `FunctionName` 字段可以。另外，每次更新获取一两个函数对性能没有实质影响。但每个点每次更新都获取，会是不必要的大量额外工作。
>
>
> Unity 的 `UnityEvent` 类型是可序列化的，所以我们本可以用它们，但它们增加了我们不需要的开销和功能。它们通常用于把方法挂接到 UI 事件上。

进度是一个 0–1 的值，我们用它从第一个提供的函数插值到第二个。我们可以用 `Vector3.Lerp` 函数，把两个函数的结果和进度值传给它。

```diff
	public static Vector3 Morph (
		float u, float v, float t, Function from, Function to, float progress
	) {
+		return Vector3.Lerp(from(u, v, t), to(u, v, t), progress);
	}
```

*Lerp* 是线性插值（linear interpolation）的缩写。它会在函数之间产生一个直线、匀速的过渡。我们可以通过让进度在开始和结束附近变慢，让它看起来更平滑一些。做法是把原始进度替换为对 `Mathf.Smoothstep` 的调用，以零、一和进度为参数。它应用的是 `3x^2-2x^3` 函数，通常称为 smoothstep。`Smoothstep` 的前两个参数是这个函数的偏移和缩放，我们不需要，所以用 0 和 1。

![0–1 的 Smoothstep 和线性。](https://catlikecoding.com/unity/tutorials/basics/measuring-performance/automatic-function-switching/smoothstep.png)

```diff
		return Vector3.Lerp(from(u, v, t), to(u, v, t), SmoothStep(0f, 1f, progress));
```

`Lerp` 方法会钳制它的第三个参数，使它落在 0–1 范围内。`Smoothstep` 方法也这么做。我们把后者配置成输出 0–1 的值，所以 `Lerp` 额外的钳制就不需要了。对于这种情况，有一个替代的 `LerpUnclamped` 方法，所以我们改用那个。

```diff
		return Vector3.LerpUnclamped(
			from(u, v, t), to(u, v, t), SmoothStep(0f, 1f, progress)
		);
```

### 过渡

函数之间的过渡期需要一个时长，所以给 `Graph` 加一个配置选项，最小值和默认值与函数时长相同。

```diff
	[SerializeField, Min(0f)]
	float functionDuration = 1f, transitionDuration = 1f;
```

![过渡时长。](https://catlikecoding.com/unity/tutorials/basics/measuring-performance/automatic-function-switching/transition-duration.png)

我们的图表现在可以处于两种模式，要么在过渡，要么不在过渡。我们用布尔字段来记录，其类型是 `bool`。我们还需要记录我们正从哪个函数过渡过来。

```diff
	float duration;

+	bool transitioning;

+	FunctionLibrary.FunctionName transitionFunction;
```

`UpdateFunction` 方法用于显示单个函数。复制它，把新方法重命名为 `UpdateFunctionTransition`。修改它，让它获取两个函数并计算进度，即当前时长除以过渡时长。然后让它在循环里调用 `Morph` 而不是单个函数。

```diff
+	void UpdateFunctionTransition () {
		FunctionLibrary.Function
+			from = FunctionLibrary.GetFunction(transitionFunction),
+			to = FunctionLibrary.GetFunction(function);
+		float progress = duration / transitionDuration;
		float time = Time.time;
		float step = 2f / resolution;
		float v = 0.5f * step - 1f;
		for (int i = 0, x = 0, z = 0; i < points.Length; i++, x++) {
			…
			points[i].localPosition = FunctionLibrary.Morph(
+			u, v, time, from, to, progress
+		);
		}
	}
```

在 `Update` 末尾检查我们是否正在过渡。如果是，调用 `UpdateFunctionTransition`，否则调用 `UpdateFunction`。

```diff
	void Update () {
		duration += Time.deltaTime;
		if (duration >= functionDuration) {
			duration -= functionDuration;
			PickNextFunction();
		}

+		if (transitioning) {
+			UpdateFunctionTransition();
		}
+		else {
			UpdateFunction();
+		}
	}
```

一旦时长超过函数时长，我们就进入下一个函数。在挑选下一个函数之前，表明我们正在过渡，并让过渡函数等于当前函数。

```diff
		if (duration >= functionDuration) {
			duration -= functionDuration;
+			transitioning = true;
+			transitionFunction = function;
			PickNextFunction();
		}
```

但如果我们已经在过渡，就必须做别的事。所以先检查我们是否正在过渡。只有不在过渡时，才需要检查是否超过了函数时长。

```diff
		duration += Time.deltaTime;
+		if (transitioning) {}
+		else if (duration >= functionDuration) {
			duration -= functionDuration;
			transitioning = true;
			transitionFunction = function;
			PickNextFunction();
		}
```

如果我们正在过渡，就必须检查是否超过了过渡时长。如果是，从当前时长里扣除过渡时长，并切回单函数模式。

```diff
		if (transitioning) {
+			if (duration >= transitionDuration) {
+				duration -= transitionDuration;
+				transitioning = false;
+			}
		}
		else if (duration >= functionDuration) { … }
```

在函数之间过渡。

如果我们现在分析，能看到在过渡期间 `Graph.Update` 确实明显花更多时间。具体花多少，取决于它在哪两个函数之间混合。

![显示过渡带来额外脚本工作的性能分析器构建产物。](https://catlikecoding.com/unity/tutorials/basics/measuring-performance/automatic-function-switching/profiler-build-showing-transitions.png)

值得再强调一次，你得到的性能分析结果取决于你的硬件，可能与本教程中展示的例子大不相同。开发自己的应用时，要决定你支持的最低硬件规格，并用那些来测试。你的开发机器只用于初步测试。如果你面向多个平台或硬件规格，那就需要多台测试设备。

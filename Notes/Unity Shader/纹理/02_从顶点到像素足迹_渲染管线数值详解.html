怎样找到纹理上的颜色？

从模型顶点到片元 UV，再算出细长的 Pixel Footprint

常见网格贴图流程中，位置决定三角形落在屏幕哪里，UV 是顶点的另一份属性。光栅化利用投影后的位置确定插值权重，再做透视正确插值，给片元算出 UV。片元着色器用这个 UV 采样纹理；光照与后续处理再决定最终显示颜色。

先把三个“位置”分开

屏幕位置 (xs, ys)、物体表面位置 (X, Y, Z)、纹理坐标 (u, v) 属于不同空间。它们通过几何投影和表面参数化建立关系，但普通 UV 贴图不是把某一个 position 直接塞给采样器。

下文先假设一个普通不透明三角形、没有 MSAA、没有遮挡和后处理。数学例子采用屏幕原点在左下、y 向上、相机朝 +Z 的约定；这是为了方便计算，不是宣称 Unity 各后端都采用这套坐标符号。

1　先直接回答：到底根据哪个坐标采样？

通常，根据插值后的 UV 采样。采样器并不需要知道这个 UV 来自模型空间、世界空间还是别处。它收到的是纹理坐标、过滤设置，以及用于过滤尺度估计的导数或显式 LOD。

位置这一路
顶点 positionOS
↓ M
世界 positionWS
↓ V、P
裁剪 positionCS
↓ 除以 w、视口变换
屏幕三角形
属性这一路
顶点 UV / Mesh.uv
↓ 顶点着色器传递
三顶点的 UV
↓ 利用屏幕权重与 clip.w
片元的插值 UV
↓ Sample
过滤后的纹理颜色
两路在光栅化与插值时关联：屏幕位置决定插值权重，顶点 UV 提供插值内容。

例如，同一张网格的顶点位置完全不变，只把某个顶点的 UV 从 (1, 0) 改成 (2, 0)，物体轮廓不会因此改变，贴图却会改变。这说明 UV 不是由顶点 XYZ 唯一决定的。UV 通常由建模软件展开后保存，或由程序写入；Unity 的 Mesh.uv 就是第一通道纹理坐标。

你在使用的方式采样 UV 从哪里来？
普通模型 UV 贴图模型顶点自带的 UV，经透视正确插值得到。
世界空间平面投影Shader 主动计算，例如 uv = positionWS.xz / 4。
模型空间投影Shader 主动从 positionOS 生成；物体移动时图案随模型移动。
屏幕空间贴图 / 后处理从屏幕位置或全屏几何生成 UV，通常再按渲染目标尺寸归一化。

后三种都可以做，但属于你选择的映射方式；不能据此认为普通网格 UV 必须从 position 实时反算。

2　颜色是在渲染管线的什么时候算的？

在常见的光栅化渲染中，可以把逻辑过程理解为以下顺序。实际硬件会重叠执行工作，并可能提前做深度测试。

  1. 读取网格。每个顶点有位置，也可以有 UV、法线、顶点色等相互独立的属性。
  2. 顶点着色器（Vertex Shader）。把位置变换到裁剪空间，并把需要插值的 UV 等属性输出。
  3. 裁剪、透视除法与视口变换。得到屏幕上的三角形；越过裁剪边界时也可能生成新的顶点及相应属性。
  4. 光栅化与插值（Rasterization / Interpolation）。确定哪些采样位置被三角形覆盖，并计算这些位置的属性。
  5. 片元 / 像素着色器（Fragment / Pixel Shader）。常见做法是在这里采样纹理，计算材质属性；前向渲染通常也在这里计算光照。
  6. 深度、模板、混合及后续处理。决定结果是否、如何写入目标；再经其他 Pass、色调映射等得到显示图像。

“采到的纹理 RGB”不一定等于“最终屏幕 RGB”。Unlit Shader 可以直接输出它；受光照材质会把它当作 Base Color 等输入；延迟渲染可以先写 G-buffer，再在后面的阶段计算光照。

“一个像素执行一次片元着色器”也有例外

同一屏幕像素可能被多个三角形覆盖；MSAA 可以涉及多个覆盖样本；还有辅助调用、过度绘制及采样频率着色。因此像素、片元、采样点、着色器调用不是严格的一一对应关系。本文先研究一个三角形内部的常规采样位置。

3　算例 A：一个三角形如何投影到屏幕？

这一组例子专门讲网格已有 UV 时的插值。设画面为 800 × 800，焦距 f = 400 像素，对应垂直视场角 90°，主点为 (400, 400)。相机位于世界坐标 (10, 0, 0)，朝本文定义的 +Z 方向。

模型矩阵 M 只把物体沿 X 轴平移 +10；观察矩阵 V 把相机位置减掉。因此本例中模型空间坐标与相机空间坐标数值相同，世界空间坐标的 X 多 10。这样既能展示变换，也不会让矩阵运算掩盖 UV 插值。

顶点模型位置 positionOSUV
A(−0.74875, −0.74875, 1)(0, 0)
B(0.50250, −1.49750, 2)(1, 0)
C(−2.99500, 1.00500, 4)(0, 1)

这些略带小数的位置是特意反推出来的，为的是投影后落在整齐的像素中心坐标上。以 A 为例：

模型空间 A = (−0.74875, −0.74875, 1)
世界空间 A = (9.25125, −0.74875, 1)
相机空间 A = (−0.74875, −0.74875, 1)

本例透视投影的相关分量为 xclip = X、yclip = Y、wclip = Z。近、远裁剪面取 0.1、100，采用深度范围 0…1，可令 zclip = (100/99.9)Z − 10/99.9。于是 A 的裁剪坐标为：

positionCS(A) = (−0.74875, −0.74875, 0.9009009, 1)

先除以 w 得到 NDC，再进行视口变换：

xNDC = xclip/wclip，yNDC = yclip/wclip

4　算例 A：屏幕点 P 的 UV 是多少？

取像素 (300, 250) 的中心 P = (300.5, 250.5)。P 位于上面这个屏幕三角形内部。

先求屏幕重心坐标（Barycentric Coordinates）。它描述 P 在屏幕三角形中的相对位置：

λB = (300.5 − 100.5)/400 = 1/2
λC = (250.5 − 100.5)/400 = 3/8
λA = 1 − 1/2 − 3/8 = 1/8

如果直接用这些屏幕权重平均顶点 UV，会得到 (0.5, 0.375)。但这是屏幕空间仿射插值，本例透视投影下不是正确答案。

默认的透视正确插值，会对每个顶点使用它的 clip.w：

D = Σ(λi/wi)
UV(P) = Σ(λi · UVi/wi) / D
顶点屏幕权重 λclip.wλ / w归一化后 β
A1/811/8 = 4/324/15
B1/221/4 = 8/328/15
C3/843/323/15
D = 15/32
u(P) = (1/4)/(15/32) = 8/15 ≈ 0.533333
v(P) = (3/32)/(15/32) = 3/15 = 0.2

所以传给常见片元着色器的 UV 是 (0.533333, 0.2)。屏幕位置确实参与了计算，因为它决定 λ；但采样坐标来自顶点 UV 的透视正确插值，不是把屏幕 XY 直接当作纹理 UV。

用同一组 β 插值相机空间位置，可得到 (−0.530667, −0.797333, 2.133333)。再投影回屏幕，恰好得到 P。这说明“P 对应物体表面上的某一点”和“P 获得一个 UV”是同一表面映射的两个描述。实际光栅化通常直接插值属性，无须为每个片元先做一次射线与三角形求交。

屏幕三角形 → 插值 UV点选左侧三角形，或使用预设；拖动也可更新

UV 图中的实点表示透视正确结果，空心方块表示仿射结果。交互位置是连续的教学采样点；只有恰好落在 n + 0.5 的点才是本文规则下的像素中心。

为什么要先插值 UV/w 和 1/w，再相除？

因为透视投影里屏幕坐标包含除以深度的操作。表面上等距离的点，在屏幕上不再等距离。普通表面属性在三角形上的线性关系，经投影后变成分式关系。UV/w 与 1/w 可以按屏幕重心权重插值，再相除恢复 UV。使用 noperspective 等限定符时，才会主动选择不同的插值规则。

5　算例 A：从 UV 到四个纹素，再到 RGB

现在取一张 1024 × 1024 的二维纹理。为隔离问题，先固定第 0 级 Mipmap，使用双线性过滤；稍后再讨论自动 LOD 与足迹。

在常见的归一化二维采样约定下，第 i 个纹素中心位于 (i + 0.5)/W。因此换到“整数表示纹素中心”的索引坐标：

s = uW − 0.5 = (8/15) · 1024 − 0.5 = 545.633333
t = vH − 0.5 = 0.2 · 1024 − 0.5 = 204.3

所以周围四个纹素索引是 (545, 204)、(546, 204)、(545, 205)、(546, 205)。小数权重为 fx = 0.633333、fy = 0.3。假设它们解码后的线性 RGB 如下：

纹素 (s, t)线性 RGB双线性权重
(545, 204)(1, 0, 0)，红(1 − fx)(1 − fy) = 0.256667
(546, 204)(0, 1, 0)，绿fx(1 − fy) = 0.443333
(545, 205)(0, 0, 1)，蓝(1 − fx)fy = 0.110000
(546, 205)(1, 1, 1)，白fx · fy = 0.190000
采样 RGB = 0.256667(1,0,0) + 0.443333(0,1,0)
　　　　　+ 0.11(0,0,1) + 0.19(1,1,1)
　　　　= (0.446667, 0.633333, 0.300000)

如果 Shader 是 Unlit 并直接返回这个采样值，它就是这次片元输出。若教学用的简单光照因子是 0.8，乘完得到 (0.357333, 0.506667, 0.240000)。真实 PBR 还会涉及法线、光源、BRDF 等；显示前的色彩变换也可能继续改变数值。

本节 −0.5 是“纹素中心索引坐标”的约定。讨论覆盖长度与导数时，也常用 S = Wu、T = Hv；两者只差常量平移，不影响长度、偏导数和足迹形状。

// 接近 Unity / HLSL 的流程示意，省略资源声明与具体管线包含文件
Varyings vert(Attributes input) {
    Varyings output;
    float4 positionWS = mul(M, float4(input.positionOS, 1));
    output.positionCS = mul(VP, positionWS); // 用于投影、覆盖与透视插值
    output.uv = input.uv;                   // 独立传递模型 UV
    return output;
}

float4 frag(Varyings input) : SV_Target {
    // input.uv 是插值结果；普通隐式 Sample 可利用其屏幕导数
    float4 baseColor = texture.Sample(samplerState, input.uv);
    return baseColor; // 这里只演示 Unlit；不是完整的受光照材质
}

以上为伪代码，Attributes / Varyings 类型、M / VP 矩阵、纹理及采样器需在实际 Shader 中声明；若只想复现本节固定第 0 级的手算，应改用显式 SampleLevel(..., 0) 和对应双线性采样器。

6　算例 B：一个像素为什么覆盖 1 米长、5 厘米宽的地面？

下面是另一组独立场景，专门解释像素足迹。相机位于 (0, 1, 0)，离水平地面 1 米，水平朝 +Z 看。地面为 Y = 0；仍是 800 × 800 画面、f = 400 像素、主点 (400, 400)，远裁剪面设得足够远。

对地面点 (X, 0, Z)，相机空间坐标是 (X, −1, Z)。于是：

xs = 400 + 400X/Z
ys = 400 − 400/Z

反过来，某个屏幕位置落在地面哪里？解这两式：

Z = 400 / (400 − ys)
X = (xs − 400) / (400 − ys)

取屏幕像素 (400, 380)，它的方格边界是 xs ∈ [400, 401]、ys ∈ [380, 381]，中心是 (400.5, 380.5)。注意，地平线是 ys = 400，数值越接近它，地面距离越大。

像素方格角点屏幕 (xs, ys)地面 X / 米地面 Z / 米
近侧左角(400, 380)020
近侧右角(401, 380)0.05000020
远侧左角(400, 381)021.052632
远侧右角(401, 381)0.05263221.052632
同一个 1 × 1 屏幕像素，对应的地面区域长约 1.0526 米，宽约 0.05 米

真实边界是一个细长梯形：近端宽 5 厘米，远端宽约 5.2632 厘米，纵深跨度约 105.2632 厘米。它不是相机“给地面点加了宽度”，而是这个屏幕方格的四条边界投到地面后张开的区域。

只算中心点，也可以得到一个精确位置：(X, Z) ≈ (0.025641, 20.512821)。但屏幕像素有面积，不只是它的中心点；中心周围的许多表面位置最终要由这一个显示像素代表，这就引出了过滤。

上面的反投影计算是为解释几何关系。正常的光栅化 Shader 不必真的为方格四角各发射一条射线；插值得到的 UV 及其导数已经能提供局部覆盖范围的估计。

7　把地面区域换算成纹理足迹

给地面设置 UV：每 4 米重复一次 1024 × 1024 的纹理，即 u = X/4、v = Z/4。既可以主动做世界空间投影，也可以在一个足够大的平面网格的各顶点写入同样的 UV；正确插值后，本例平面上的映射一致。

纹素密度 = 1024 / 4 = 256 纹素 / 米
近端宽 = 0.05 × 256 = 12.8 纹素
远端宽 = 0.05263158 × 256 ≈ 13.473684 纹素
纵深跨度 = 1.05263158 × 256 ≈ 269.473684 纹素

于是，那个屏幕像素在纹理上的覆盖区域，大约有 269 纹素长、13 纹素宽。中心 UV 是 (0.006410256, 5.128205128)。v 大于 1 不奇怪，因为地面纹理重复；Repeat 地址模式会在采样时处理它。

这就是“细长足迹”的具体来源

地面透视让一个像素纵向跨过约 1.05 米、横向只跨过约 5 厘米；再乘同一个纹素密度，变成纹理中的约 269 × 13 纹素。这里没有凭空增加 UV，也不是纹理图片真的被拉长了。

8　GPU 怎样知道附近 UV 变化多大？

在常见片元着色中，屏幕导数来自相邻调用组成的 2 × 2 Quad 的差分。下面仍按本文 y 向上的坐标定义，列出四个相邻像素中心的未做 Repeat 折返的 UV：

中心屏幕 (xs, ys)uv
P00(400.5, 380.5)0.0064102565.128205128
P10(401.5, 380.5)0.0192307695.128205128
P01(400.5, 381.5)0.0067567575.405405405
P11(401.5, 381.5)0.0202702705.405405405

以 P00 所在的一行、一列做差，可得到一个教学用的局部差分：

ΔUVx = P10 − P00 = (0.012820513, 0)
ΔUVy = P01 − P00 = (0.000346500, 0.277200277)
乘上 1024 后：
gx ≈ (13.128205, 0) 纹素 / 像素
gy ≈ (0.354816, 283.853084) 纹素 / 像素

也就是说，向右一个屏幕像素，纹理坐标约跨 13 个纹素；朝地平线方向走一个像素，约跨 284 个纹素。差别非常大。实际 ddx/ddy 的方向符号、粗细差分选择和 Quad 细节与 API、编译器及执行方式有关；这里是对应关系清楚的一组数值差分，不声称所有设备都必须逐位返回这些值。

为什么这里是 283.85，而前面一个像素的跨度是 269.47？

因为它们不是同一个量。269.47 是像素边界 y ∈ [380, 381] 映射到地面的精确跨度；283.85 是两个像素中心 y = 380.5 与 381.5 之间的变化。映射包含 1/(400 − y)，不是线性的，所以不同区间的变化量不同。

若在中心 y = 380.5 计算数学上的瞬时导数，纹理纵向变化率为 102400/(19.5²) ≈ 269.296515 纹素 / 像素。它与该像素的精确跨度较接近。GPU 的邻域差分和局部椭圆，本来就是对面积变化的估计；不能把“精确边界”“微分”“有限差分”当成完全相同的数字。

采样器可用这些导数决定 Mipmap 层级和各向异性过滤范围。应用也可以用显式梯度或 LOD 指令提供相关信息。普通 Shader 中写一条 Sample(..., uv)，并不意味着 GPU 只知道一个孤立的 UV 点。

不要为了 Repeat 随手先对 UV 做 frac 再求导：跨过整数边界时，折返会制造突变。常见做法是传入连续 UV，让采样器的地址模式处理重复。特殊 Shader 的不连续映射需要额外处理导数。

9　为什么要平均，而不能只看中心纹素？

设纹理纵向是黑、白交替的细条纹，单个纹素宽。一个屏幕像素若覆盖约 269 个这样的纹素，画面已经无法把它们逐条显示出来。此时只查看中心附近的黑或白，会把大量未被解析的高频内容误当成一个确定颜色。

相机轻微移动后，中心可能从白条跨到黑条，像素颜色突然变化，就可能出现闪烁或摩尔纹。若在适当范围内进行加权平均，黑白条纹通常会趋向中间灰，随运动的变化也更平稳。实际灰度受边界、滤波核、相位等影响，不必恰好等于 0.5。

过滤方式面对约 269 × 13 纹素的足迹
只看中心 / 很小范围无法代表纵向大量条纹，容易漏采和混叠。
大范围各向同性过滤抑制纵向混叠，但也过度平均了横向原本可保留的细节。
各向异性过滤沿长方向覆盖更大的区域，在短方向尽量保留较高分辨率。

“对这一片区域加权平均”描述的是过滤目标。实时 GPU 通常不会逐一遍历原始图像中所有被覆盖纹素，而是借助预滤波的 Mipmap、多次过滤探针以及采样器硬件近似完成。Feline 就是其中一条经典思路。

本例中心处，按局部微分估计，各向异性比约为 20.51。普通各向同性缩小的层级估计约 log₂(269.3) = 8.07；若能分别保留短方向信息，对应短方向的尺度约 log₂(13.13) = 3.71，再沿长方向组合。这里只比较局部尺度，不是承诺某款 GPU 精确选择这两个 LOD；过滤核约定、最大 AF、层级偏置等都会影响结果。

10　模型空间、世界空间、裁剪空间，各自该怎么记？

空间 / 属性主要作用能不能用于生成纹理坐标？
模型空间 Object Space描述物体自身的几何坐标。可以，需 Shader 主动定义投影；普通 Mesh UV 不等于 positionOS.xy。
世界空间 World Space用于物体之间的位置关系、光照等。可以，例如地面 world XZ 投影；物体移动时相对世界图案可能滑动。
相机空间 View Space以相机为参照，方便投影。可以，但一般会随相机变化，不等于普通模型 UV。
裁剪空间 Clip Space顶点投影输出，包含齐次分量 w。可参与投影式贴图；通常还需除以相应 w 等处理，不能把 clip.xy 当成已归一化 UV。
屏幕空间 Screen Space覆盖判定、插值位置、屏幕效果。可以，后处理经常使用；不是普通 Mesh UV 的默认来源。
顶点 UV描述表面与纹理的对应关系。经插值后，就是常见材质采样所使用的输入。
回到最初的问题

常见流程不是“挑某种 position，自动变成 UV”。更准确的是：网格给出位置和 UV → 位置经过投影决定屏幕三角形 → 屏幕采样位置决定插值权重 → clip.w 参与透视修正 → 得到 UV → 根据 UV 和足迹过滤纹理 → 计算片元颜色。

你也可以明确选择“从世界位置生成 UV”，但那是另一种参数化方式，应该由 Shader 的代码来定义。

11　资料与计算约定

  1. Unity：Mesh.uv，网格 UV 属性。
  2. Microsoft：HLSL 插值限定符，默认插值与 noperspective 等选项。
  3. Microsoft：光栅化规则，覆盖、属性插值、MSAA 与 Quad 差分。
  4. Microsoft：Texture.Sample，采样坐标与采样器设置。
  5. PBRT：纹理采样与抗混叠，图像采样位置与纹理参数的面积关系。

两组数值场景、颜色与交互由本文构造并计算。屏幕 y 向上只是教学约定；本文不照搬某个 Unity 后端的 Y 翻转或反向 Z。RGB 示例使用线性值；坐标单位、Mipmap 级别与纹素中心约定均在相关章节单独声明。

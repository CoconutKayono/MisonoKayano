# C 阶段检查点｜解释像素形成、数据寿命与成本

本阶段覆盖 C01—C08：从深度拒绝、透明合成、附件与 MSAA，到 Load/Store、同步、动画顶点和性能判断。目标是能预测一次修改的结果，并区分画面证据、API 语义和硬件性能证据。

文件已生成不等于 Unity 实测通过，也不等于个人已掌握。以下实验尚未在 Editor 编译或实机验证；不提供虚构的 GPU 时间。无需 Python 学习实验。

## 2. 先完成四个可观察反例

### 旧内容不是自动有效

C05 依次选择 Preserve、ClearBlack、Discard。前两种分别预测左红/左黑且右绿；第三种只预测右绿，左边不保证。即使左边仍红，也要能解释为什么不能依赖该结果。这个反例先验证 Load 的语义，不用于声称某 GPU 省了多少带宽。

### 正确同步不代替正确算法顺序

C06 默认顺序生成红/绿，再输出其反色。切换 Consume Before Generate 后，Result 使用旧 Source；第一次若旧 Source 为初始化黑色，结果为白色。加一个后置等待不能让已经执行的消费重算。实验无需 CPU 读回，且没有使用 async compute。

### CPU 快照不包含材质顶点位移

C07 先将 Amplitude=0，点击 Bake Snapshot 观察冻结骨骼姿势；再增加 Amplitude，右侧快照仍不包含材质正弦位移。关闭 Match Depth And Shadow 后，阴影漏掉的是额外位移，骨骼动画仍在。深度实验必须先确认实际是预通道还是 CopyDepth。

### 相同图案可以有不同成本

C08 固定尺寸与运算量，比较一个全屏 Draw、多个规范化叠加层和分块 Draw。三种方案可输出近似同一图案，却改变不同工作量。先确认 Draw/视口/Blend，再判断时间变化；不能只看最终图案或单一计数。

## 3. 回答一条完整的数据链

设一个 NPR 角色流程为：动画姿态 → 主体颜色与深度 → 角色 ID → 描边读取 → 合成输出。下面是教学问题，不声称所有工程必须拆成这些 Pass。

1. 动画后的顶点来自哪里，额外材质变形发生在什么时候？
2. 哪些 Pass 必须匹配姿态、位移、裁剪和时间？
3. 哪些片元可能被深度提前拒绝，哪些结论必须用设备证据确认？
4. 颜色、深度和 ID 分别写到什么附件、使用什么格式与样本数？
5. 哪些通道必须 Clear/Load，哪些附件在最后使用后可丢弃？
6. 描边读取之前需要满足什么数据依赖，是否真需要 CPU 结果？
7. 透明合成中的 RGB 是 straight 还是预乘，目标 Alpha 之后由谁使用？
8. 最终成本可能受哪个维度限制，准备用哪组对照排除其他解释？

参考回答：先区分原始 Mesh、蒙皮结果和材质位移；多个几何 Pass 使用一致表面约定。颜色与 ID 的编码/归并规则不同，普通颜色平均不能保证 ID 正确。第一次未完全覆盖的有效读取前应有正确初始内容，后续需要的附件不能提前 DontCare。常规 GPU 资源依赖由引擎处理，CPU 读回另行设计。透明合成检查源表示、因子与排序；性能判断同时看 GPU/CPU 时间线和有针对性的变化。

## 4. 最少证据记录

| 项目 | 应记录的内容 |
| --- | --- |
| 环境 | Unity 与 URP 版本、设备/GPU、图形 API、分辨率和实际 MSAA 样本数 |
| 输入 | 场景、模式、材质参数、执行顺序、附件格式 |
| 预测 | 预计变化，以及哪些区域或数值不能确定 |
| 实际观察 | 画面、通道、实际选中的 Pass 和资源绑定 |
| 性能证据 | 固定条件下的 GPU/CPU 时间、波动范围与可用硬件计数器 |
| 结论边界 | 已验证的语义、尚未验证的实现、仍存在的替代解释 |

未测量栏留空或写“未测”，不要填预估毫秒并称实测。Frame Debugger 用于确认路径；性能采样需考虑调试工具、预热、帧率上限和温度的影响。

# D08｜从一个错误像素，追到抓帧事件与 Unity 源码

> 核心问题：画面某处不对，如何证明是哪一步导致的？本卡构造“前方物体不显示颜色，却挡住后方物体”的小场景，完成从附件内容到管线状态、Shader Pass 和源码入口的追踪。

## 1. 调试对象必须具体

像素是某张资源中一个位置的数据；最终窗口里的屏幕点可能经过缩放、抗锯齿、色彩编码和多次合成。开始分析时，至少明确：**相机、帧、资源、子资源、像素坐标和当前事件**。例如“Game Camera 的颜色附件、Mip 0、中心像素、绘制 Front 后”，比“屏幕中间是黑的”更能指导排查。

Draw 事件存在，只证明绘制命令出现在某个序列中。该事件可能没有覆盖目标像素，也可能被深度/模板测试拒绝，可能关闭颜色写入，或写入了稍后被覆盖的另一个附件。Fragment Shader 的返回值同样不等于最终存储颜色。

本文核对本地 **Unity 6.7 Beta / 6000.7、2026-06-26** 文档；URP 入口固定 Graphics `275a7f9ad9330e3cf7f3ea57a0b242a551fde291`（manifest：URP/Core **17.0.4、Unity 6000.0**）。RenderDoc 工具能力还取决于安装版本、图形 API 和捕获环境；本文没有实际捕获文件或实测截图。

## 2. 三个工具视角互相补充

| 视角 | 适合回答的问题 | 不能据此直接下的结论 |
| --- | --- | --- |
| Unity Frame Debugger | 哪个相机事件使用哪个网格、材质、Pass、关键字、目标和状态；事件前后画面如何变化 | 事件组名称不是完整原生调用栈，也不是 GPU 硬件时序 |
| Render Graph Viewer | 谁生产和消费资源，Pass 是否被裁剪，资源寿命如何连接 | 图节点不保证一对一对应原生 render pass 或实际 Draw |
| RenderDoc | 当前 API Draw 的附件、深度/混合/写掩码、输入资源及像素历史 | 调试捕获中的时间不能直接作为正常运行性能；Shader 源码和像素调试不保证可用 |

Frame Debugger 可逐步检查一帧事件；Details 还能区分使用的 Shader、Pass 和 LightMode，参见 [Unity Frame Debugger](https://docs.unity3d.com/6000.0/Documentation/Manual/FrameDebugger.html) 及本地 `Manual/frame-debugger-window-event-information.html`。

RenderDoc 查看数值时需要选择正确 Mip、数组层、面或样本；Pixel History 在支持的环境中可展示截至当前事件的修改和测试情况。参见 [RenderDoc 官方像素检查说明](https://github.com/baldurk/renderdoc/blob/v1.x/docs/how/how_inspect_pixel.rst)。这条工具文档链接是分支版本；实际操作记录中还应填写本机 RenderDoc 版本。

## 3. 完整故障实验：颜色没写，深度写了

保存下面代码为 `D08TraceLab.shader`。不需要其他自定义脚本。Shader 包含可调颜色写掩码和深度写入开关；片元程序始终返回材质颜色，没有灯光、纹理、clip 或混合干扰。

```shaderlab
Shader "Encyclopedia/D08TraceLab"
{
    Properties
    {
        _Color("Output Color", Color) = (1,0,0,1)
        [Enum(None,0,RGB,14,RGBA,15)] _ColorMask("Color Write Mask", Float) = 15
        [Toggle] _ZWrite("Depth Write", Float) = 1
    }
    SubShader
    {
        Tags { "RenderPipeline"="UniversalPipeline" "RenderType"="Opaque" "Queue"="Geometry" }
        Pass
        {
            Name "D08TraceForward"
            Tags { "LightMode"="UniversalForward" }
            Cull Off
            ZTest LEqual
            ZWrite [_ZWrite]
            ColorMask [_ColorMask]
            Blend Off
            HLSLPROGRAM
            #pragma vertex Vert
            #pragma fragment Frag
            #include "Packages/com.unity.render-pipelines.universal/ShaderLibrary/Core.hlsl"
            CBUFFER_START(UnityPerMaterial)
                float4 _Color;
                float _ColorMask;
                float _ZWrite;
            CBUFFER_END
            struct Attributes { float4 positionOS : POSITION; };
            struct Varyings { float4 positionCS : SV_POSITION; };
            Varyings Vert(Attributes i)
            {
                Varyings o;
                o.positionCS = TransformObjectToHClip(i.positionOS.xyz);
                return o;
            }
            float4 Frag(Varyings i) : SV_Target { return _Color; }
            ENDHLSL
        }
    }
}
```

### 场景设置

1. URP Forward；一个 Base Game Camera；Render Graph 开启。关闭 MSAA、动态分辨率、XR、Depth Priming、GPU Resident Drawer、后处理、SSAO、阴影和所有额外 Renderer Feature。物体不标为静态合批对象。
2. 相机位置 `(0,0,-5)`，旋转 `(0,0,0)`，透视 FOV 60，Near 0.3、Far 100，背景类型 Solid Color、颜色黑。只观察 Game 视图；不使用 Skybox。
3. 创建 Quad，命名 Front，位置 `(0,0,0)`、旋转零、缩放 `(2,2,1)`。创建第二个 Quad，命名 Back，位置 `(0,0,1)`、旋转零、缩放 `(4,4,1)`。本 Shader Cull Off 消除 Quad 朝向带来的干扰。
4. 创建两个独立材质，都使用本文 Shader。Front 红色，Color Write Mask 为 None，Depth Write 开启；Back 蓝色，RGBA 写入，Depth Write 开启。
5. 在材质 Inspector 的 Render Queue 中将 Front 设为 **2000**，Back 设为 **2001**，保证两个不透明队列的先后关系。在抓帧中再次核对真实事件顺序，不能只相信设置已经生效。

### 预测中心像素

| 时刻 | 颜色 | 深度/遮挡意义 |
| --- | --- | --- |
| 相机清除后 | 黑 | 深度为远端清除值 |
| Front 绘制后 | 仍黑 | Front 覆盖中心并通过测试，写入更近深度；颜色写掩码阻止颜色变化 |
| Back 绘制后 | 仍黑 | Back 中心比已有 Front 更远，深度测试拒绝；周围未被 Front 遮挡的区域可变蓝 |

最终应看到蓝色大区域中间留着黑色遮挡形状。黑色中心不是 Front 的片元程序返回了黑色，而是该位置保留了背景颜色。原生 GPU 可能提前拒绝 Back 片元，不能假定其 fragment 程序一定执行过。

Reversed-Z 下实际深度数值方向可能反转；Unity 的 `ZTest LEqual` 描述的是本场景所需的通常遮挡语义。抓帧中原生 compare op 要结合深度映射解释，不能仅因 API 面板显示的比较方向与 ShaderLab 字面不同就认定出错。

## 4. 用 Frame Debugger 建立证据链

打开 `Window > Analysis > Frame Debugger`，选择当前运行目标并 Enable。展开当前 Game Camera 的事件，找到 Front/Back 的真实绘制。SRP batch 或父级标记可以包含多个子事件；要下钻到相关绘制，而不是停在父组名称。

按下面的顺序记录：

1. **绘制前后的同一颜色目标**：先定位清除，再定位 Front，最后定位 Back。确认中心一直为黑，而 Back 周围变蓝。
2. **Front 的实际状态**：使用的 Shader 是 `Encyclopedia/D08TraceLab`，Pass 为 `D08TraceForward`，LightMode 为 `UniversalForward`，ColorMask 为 0，ZWrite 有效，颜色/深度附件属于当前相机。
3. **Back 的状态与几何**：颜色可写、深度测试开启，位置更远。必要时用网格视图与变换判断覆盖；不要把无颜色变化自动归因于没有提交。
4. **两个单变量修复**：只把 Front 的 Color Write Mask 改为 RGBA，中心应为红；恢复 None，再只关闭 Front 的 Depth Write，中心应为蓝。每次重新获取事件，避免拿修改前的冻结帧比较修改后的设置。

第二个修复证明“看不见的 Front 仍在写深度”是因果链的一部分。若实验不符合预测，先核对实际队列/状态、额外 Pass 和目标资源；不要直接改 Shader 返回值。

## 5. 用 RenderDoc 核对 API 状态与像素

先关闭 Frame Debugger，保存场景。安装并被 Unity 检测到的 RenderDoc 可从 Game 视图标签菜单选择 **Load RenderDoc**，再用捕获按钮抓取下一帧；此操作会重建图形设备，因此应保存修改。若入口不可用，核对当前平台/API 支持；也可从 RenderDoc 启动目标程序。参见 [Unity RenderDoc 集成](https://docs.unity3d.com/6000.0/Documentation/Manual/RenderDocIntegration.html)。

在捕获中定位相机清除与两个 Quad 的绘制。事件编号每次捕获都可能改变，用 Shader、网格、资源和状态共同识别。

| 检查点 | 本实验期望 | 不吻合时的方向 |
| --- | --- | --- |
| 输出颜色附件与深度附件 | Front/Back 作用于同一对目标的相关子资源 | 可能选错相机、中间图或事件 |
| Viewport / Scissor | 覆盖选中的中心区域 | 像素可能根本不在绘制范围内 |
| Front 颜色 write mask | 所有颜色通道关闭 | 材质属性未生效、状态被覆盖或选错 Pass |
| Front 深度 write / test | 可写且能通过中心测试 | 其他预通过、遮挡物、状态覆盖 |
| Back 深度 compare 与已有深度 | 对应中心更远且拒绝 | 变换/坐标/原始深度约定判断有误 |

在 Texture Viewer 选定颜色资源、Mip 0 和中心坐标，逐事件读取；再检查对应深度资源的变化。如果当前 API/资源支持 Pixel History，可辅助查看中心测试情况和写入历史；部分未改变颜色的绘制不一定以你预期的形式出现，**缺少一行历史不能独立证明没有 Draw 或没有深度写入**。应结合事件列表、深度资源与管线状态。

本例不需要逐指令 Shader 调试。需要追变量时，可按 Unity 文档在专门的 D3D11 调试 Shader 中加入 `#pragma enable_debug_symbols`；源代码能否展示仍取决于 API、编译和工具支持。调试符号构建与正常性能构建应分别记录，不能用一次捕获推导正式帧耗时。

## 6. 将事件对应回源码，而不是猜名称

为本实验建立以下映射：

| 观察证据 | 源码/资产落点 | 能证明什么 |
| --- | --- | --- |
| 当前相机与不透明绘制阶段 | `UniversalRenderPipeline.cs`、`UniversalRendererRenderGraph.cs` | 相机准备、图记录与阶段安排 |
| `UniversalForward` 被选择 | `DrawObjectsPass.cs` 的 ShaderTagId 列表和绘制设置 | 为什么此 Pass 可以进入常规不透明绘制 |
| Pass 名 `D08TraceForward` | 本卡 Shader 的 `Name` | 人类定位名称，不是引擎自动选择规则本身 |
| ColorMask 0、ZWrite On | 材质属性、ShaderLab 状态及最终 API 状态 | 此次绘制关闭颜色写入但仍能修改深度 |
| 中心保持黑色 | 正确颜色资源的逐事件读数 | 写入和遮挡链在目标位置的结果 |

固定入口：[UniversalRendererRenderGraph.cs](https://github.com/Unity-Technologies/Graphics/blob/275a7f9ad9330e3cf7f3ea57a0b242a551fde291/Packages/com.unity.render-pipelines.universal/Runtime/UniversalRendererRenderGraph.cs)、[DrawObjectsPass.cs](https://github.com/Unity-Technologies/Graphics/blob/275a7f9ad9330e3cf7f3ea57a0b242a551fde291/Packages/com.unity.render-pipelines.universal/Runtime/Passes/DrawObjectsPass.cs)。实际工程需要打开相同版本的包文件；事件标记到 C# 方法并非总是一对一。

`RenderStateBlock` 等机制还能覆盖 Shader 的部分状态。因此排查顺序是：源码声明帮助提出假设，捕获中的最终状态检验本次假设。公开 C# 源码之后的原生引擎、驱动及硬件细节，没有证据时停在可见边界。

## 7. 迁移到 NPR 错误像素

角色描边断裂时，先找到“第一次与预期不同的资源”：主体深度、法线、角色 ID、描边中间图，还是后处理颜色。若法线图已经缺失发丝，调整最终描边混合只是在更晚阶段补偿错误。

若差异始于几何生产，检查 Pass 标签、变形、裁剪与对象筛选；若输入图正确而轮廓结果错误，再检查采样坐标、分辨率、阈值和邻域规则；若轮廓中间图正确而最终图不对，检查合成、颜色编码、曝光及后续覆盖。

跨分辨率定位可先用像素中心 UV：`uv = ((x+0.5)/width, (y+0.5)/height)`。映射到另一张图时还需确认 Y 原点、viewport、比例和采样规则；TAA、模糊或上采样可能使一个输出像素依赖多个输入像素，不存在唯一的一对一前身。

## 8. 自测、记录模板与验证边界

1. **有 Draw 为什么没颜色？** 覆盖、测试、写掩码、目标选择及后续覆盖都可能阻止预期结果。
2. **Front 返回红色，中心为何黑？** ColorMask 0 阻止颜色写入，背景黑保留；深度仍挡住 Back。
3. **关掉 Front 深度写入后中心为何蓝？** Back 不再被 Front 更新的深度拒绝。
4. **一个图 Pass 是否对应一个 RenderDoc 事件？** 不保证，可能包含多个 Draw，也可能被裁剪或与其他图节点合并。
5. **Pixel History 没有出现某一绘制，能否立即删除该假设？** 不能，先看工具支持、资源、事件范围和实际 API 状态。

01 / THE ANSWER

它们不是只能三选一。

URP、HDRP 和虚幻的常规实时渲染，都以光栅化为重要基础；部分光照效果可以交给光线追踪。HDRP 和虚幻还提供单独的路径追踪模式。

先校准版本：Unity 6.7 目前是 Beta。截至核对日期，官方已在 2026 年 9 月 17 日宣布公测。因此本文说的是 6.7 Beta 已公布的能力，不能把它当成已发布的 6.7 LTS 最终功能清单。

特别是 URP 6.7 的 Surface Cache GI，让「URP 不支持任何光追」这个旧结论不再成立。官方 Beta 公告 · Beta 新功能说明

引擎 / 管线常规实时画面光追在其中做什么？完整画面路径追踪
Unity 6.7 URP
Beta 新能力		以光栅化为基础，配合所选光照方案。启用 Surface Cache GI 时，用光追辅助计算动态漫反射间接光；有硬件路径，也有计算着色器回退。未在此次核对资料中找到与 HDRP Path Tracing 对应的内置模式；SCGI 不等于整帧路径追踪。
Unity HDRP光栅化基础，可选实时光追效果，形成混合渲染。可为反射、阴影、环境遮蔽、间接光等效果启用光追，视功能及平台配置而定。有。Path Tracing 持续积累样本，适合高质量输出和参考画面。
虚幻引擎 UE5常规桌面渲染通常采用延迟渲染；也有前向等路径。高画质项目常结合 Lumen。Lumen 用多种追踪方法求动态间接光与反射；可选软件 / 硬件光追。有。独立 Path Tracer，常用于影视、建筑可视化和参考渲染。

依据：Unity SCGI 技术说明 · HDRP 光追 · HDRP 路径追踪 · UE 渲染路径 · Lumen · UE Path Tracer。HDRP 引用版本范围见文末。

理解这张表的关键是：“引擎支持某技术”不等于“这个项目启用了它”，更不等于“每一个像素、每一种效果都由它计算”。一款游戏可能只给反射开光追，阴影仍用阴影贴图，间接光仍读取烘焙结果。

02 / TWO DIFFERENT QUESTIONS

生成一张图，至少要回答两件事。

① 相机看到了谁？

某个像素对应红墙、白球，还是背景？球挡在墙前面时，哪个表面离相机更近？

这是可见性问题。光栅化配合深度测试，或从相机发射射线，都可以解决它。

② 看到的表面有多亮？

白球收到了灯的多少光？红墙有没有把光反射到球上？球的光滑部分映出了什么？

这是光照与光传输问题。需要知道光从哪里来，以及材质怎样散射它。

GAMES101 往往先分开教光栅化、着色和光追，便于理解算法。进入引擎后，这些知识会重新组合：先用光栅化找到表面，再从这个表面发射射线查询反射或遮挡，完全合理。

像素的颜色 ≈ 可见表面 ＋ 材质对光的响应 ＋ 到达它的光

上式是思维拆分，不是可以逐项相加的物理公式。真实着色还涉及方向、可见性、积分以及相机曝光等。

同一个房间，直接光和间接光有什么区别？

设想一盏灯、一面红墙和一个白球。灯直接照到球上，是直接光；灯先照红墙，墙把一部分偏红的光反射到球上，是间接光。所以即使球本身是白的，靠近墙的一侧也可能微微泛红。

橙色箭头：真实光能的传播方向蓝色箭头：算法查询方向
直接光：光源 → 白球 → 相机。计算球的亮度时，还要检查球与光源之间是否被遮挡；这一步可以用阴影贴图，也可以用阴影射线。

“全局光照”（Global Illumination，GI）关注物体之间相互影响的光照，尤其是间接光。GI 是要解决的问题；路径追踪、烘焙、探针或动态缓存，是解决它的不同办法。

03 / WHY → WHAT

三种方法分别擅长什么？

光栅化 Rasterization：高效地把三角形落实到像素。

WHY

游戏要持续输出画面。模型主要由三角形组成，而 GPU 极其擅长并行处理大量三角形和片元。我们需要一种能高效判断“哪些屏幕采样点被哪些三角形覆盖”的方法。

WHAT

把三角形投影到屏幕，生成覆盖的片元，再通过深度测试等步骤确定可见表面。片元随后如何变成颜色，要由着色及相关光照数据决定。

它不会仅凭三角形覆盖关系，就自动知道球背后有哪些物体能被镜子反射，也不会自动算出红墙给白球的反弹光。因此光栅化渲染器会配合阴影贴图、反射探针、烘焙、屏幕空间效果，或光线追踪。

光线追踪 Ray Tracing：沿一个方向，去问场景。

WHY

许多光照问题其实是在问：朝灯的方向有没有遮挡？沿反射方向能看到什么？光穿过玻璃后会碰到谁？这些都是沿空间方向进行查询的问题。

WHAT

从一个起点沿一个方向发出射线，求它与场景的交点，再按具体算法决定下一步。射线可以来自相机，也可以来自光栅化已经找到的表面，或场景中的采样点。

所以，“使用光追”可能仅指每个选中的表面发一条阴影射线。光追是一类技术，不能仅凭这两个字推断弹射次数、间接光质量，或整帧的生成方式。

路径追踪 Path Tracing：随机采样光的完整传播路径。

WHY

如果光能从四面八方到达一个表面，每个方向后面又可能连着更多反弹，逐一枚举所有路线是不可能的。我们需要用有限计算估计这个巨大积分。

WHAT

路径追踪用蒙特卡洛方法采样光传输路径：常见做法是从相机出发，在表面按材质与概率规则采样后续方向，并估计与光源的连接，最后对许多带权样本求平均。

路径追踪属于光线追踪。区别不能简化成“光追弹一次，路径追踪弹很多次”。传统递归光追也能有多次反射和折射；路径追踪的关键是用随机采样估计光传输积分，包括漫反射的间接光。

概念参考：PBRT 第四版：Path Tracing。这里讲的是算法原理，不是在描述某个引擎的全部实现。

光线追踪：沿射线查询场景的一大类方法
├─ 某个效果的光追：例如只计算阴影或反射
├─ 传统递归光追：例如递归处理镜面反射、折射
└─ 路径追踪：随机采样光传输路径并估计积分

看图比较：第一处可见表面，到底怎么找到？

光栅化：把三角形 A 投影到像素网格，确定覆盖关系，再做深度测试与着色。绿色投影回答“相机看到了谁”，图中没有自动求解 A 与 B 之间的光传输。

示意图不按透视比例绘制；连线用于表达数据查询关系，不代表某个引擎内部完整的执行顺序。

04 / WHY HYBRID RENDERING

为什么不直接把一切都交给路径追踪？

因为实时渲染有截止时间。60 FPS 意味着每帧约 16.7 毫秒；120 FPS 则只有约 8.3 毫秒。GPU 的几何处理、材质、光照、后处理等都要分享这段时间。CPU 工作虽然可以并行，也必须跟上帧节奏。

路径追踪只取少量样本时，不同像素碰巧采到的路径差异很大，于是出现噪点。增加样本能让估计更稳定，但需要更多求交和着色计算。同一个 60 FPS 目标，允许的路径数远比离线渲染少。

拖动看看：为什么少量样本会不稳定？

1 → 256 个样本。对简单独立采样，误差的典型尺度约随 1/√N 下降：想让它减半，往往需要约 4 倍样本。

这是人为构造的统计噪声示意，并非真实路径追踪器，也不是引擎性能或画质测试。

混合渲染的思路很直接：把有限计算花在最能改善画面的地方。先高效找到可见表面；需要查看屏幕外信息的反射、复杂遮挡等，再用射线。光追结果常结合降噪、历史帧复用和缓存，来减少本帧需要追踪的数量。

光栅化找到可见表面
得到深度、法线、材质等
→
选定光照效果光追 / 贴图 / 探针
按目标与预算组合
→
组合与重建着色、降噪、后处理
形成最终画面

这是概念流程；实际引擎会交错执行多个 Pass，也不一定全部写入同一种缓冲。

路径追踪本身并不等于“只能离线”。它可以用于实时系统，但通常需要更高硬件预算、较少样本以及强力重建。这里讨论的 HDRP Path Tracing 和 UE Path Tracer 产品模式，主要采用渐进累积，不能直接理解成所有普通游戏的默认渲染方式。

05 / UNITY

URP 与 HDRP：目标不同，工具组合也不同。

渲染管线（Render Pipeline）是把场景变成画面的一套组织方案。它规定哪些步骤要执行、哪些数据要准备、哪些效果可以组合。URP 和 HDRP 是管线产品名，不是两种与光栅化、光追并列的基础算法。

URP：让多种平台承担得起。

WHY

手机、XR 设备、主机和桌面 GPU 的能力差异很大。统一的开发体验需要可伸缩的画质与成本，而不能要求所有设备每帧都追踪大量光线。

WHAT

URP 的常规画面仍以光栅化组织。光照可以搭配实时灯光、阴影贴图、烘焙数据、探针等；前向与延迟路径负责安排几何和着色工作。

参考：URP 定位 · Unity 6.7 渲染路径说明（英文正文）。

6.7 的新增重点：Surface Cache GI Beta / 预览能力

WHY

如果门会打开、墙会被拆除、太阳会移动，预先烘焙好的间接光就很难完整响应。开发时反复烘焙也会打断调光流程。我们需要能随场景变化更新的间接光。

WHAT

SCGI 是 URP 的动态漫反射间接光方案。可把 Surface Cache 理解为“把表面附近的光照计算结果存起来并复用”。官方说明它基于 UnifiedRayTracing：可用时使用硬件光追，否则使用计算着色器回退。

回到红墙和白球：它关心的是“红墙反射出去的光怎样影响球”。它不是完整的镜面反射方案，镜面部分还可配合反射探针、SSR 等。其计算中可以包含路径采样，但缓存式 GI 与从每个相机像素进行完整路径追踪，仍是不同的渲染组织方式。

依据：Unity 图形工程师发布的 SCGI 说明与 FAQ；6.7 中的 SCGI 与 SSR 由官方 Beta 说明确认。具体开关与限制应以安装的 Beta 构建和包为准。

更准确地描述 URP 6.7：“以光栅化为基础；启用 SCGI 时，间接光阶段会使用光线追踪相关计算。”一句“URP 是纯光栅化”会遗漏这层能力；一句“URP 已经变成路径追踪引擎”又会夸大它。

HDRP：为高画质提供更多选择。

WHY

如果目标设备有更充足的预算，开发者会希望减少屏幕空间反射缺失、复杂阴影等近似带来的问题，并使用更丰富的材质与光照表现。

WHAT

HDRP 同样有光栅化的常规渲染基础。打开某项光追效果，就是在相应环节使用射线来获取更完整的场景信息，并不自动把所有着色都改成路径追踪。

例如，金属球的反射可以使用光追，而画面中哪些三角形首先可见仍由光栅化处理。是否实际启用，取决于项目设置、效果设置和平台支持。

依据：HDRP 概览 · HDRP 光追设置与能力。所核对的 HDRP 17.3 文档规定其这套光追路径使用 Windows / DirectX 12；不能据此把 URP SCGI 的计算着色器回退也当作同样限制。

HDRP Path Tracing：进入另一种输出模式。

当你明确启用 Path Tracing，HDRP 会用路径追踪统一计算受支持的光照效果，逐步积累每个像素的样本；相机移动会让累积重新开始。它很适合理解“光实际怎样在这个场景传播”，也可用于高质量静帧或录制输出。

它不是把 Ray Tracing 的质量滑块拉到最高。它改变了整幅图像光照的求解方式，且有自己支持和不支持的功能范围。

依据：Understand path tracing · Path tracing 文档入口与限制。

06 / UNREAL ENGINE, WITHOUT PREREQUISITES

虚幻也用光栅化；Lumen 是它的光照系统。

你不用先学虚幻的操作界面。只要先区分三个名称：常规渲染器负责组织画面，Lumen 解决动态间接光与反射，Path Tracer 提供路径追踪输出。

Lumen 为什么存在？

WHY

在可探索的动态世界里，太阳、灯光、角色和场景状态都会变化。开发者希望反弹光与反射跟着变化，尽量减少反复烘焙和手工补光，同时保持交互帧率。

WHAT

Lumen 是动态 GI 与反射系统。它组合屏幕空间追踪、场景追踪、光照缓存等技术。通常先利用屏幕内已有信息，再通过其他追踪方法补充；场景追踪可以使用软件光追，也可以使用硬件光追。

软件光追

在 Lumen 中，主要对距离场进行追踪。距离场记录空间位置到表面的距离，让算法沿射线逐步寻找表面。

“软件”不等于 CPU 在慢慢算。它可以运行在 GPU 上，只是不依赖专用光追硬件执行同一种求交路径。

硬件光追

借助硬件加速追踪场景中的三角形，可覆盖更广的几何类型，并改善某些反射的几何准确性。

加速的是查询能力；它不会自动替你决定用 Lumen、路径追踪还是只算阴影。

Lumen 不是 UE Path Tracer。即使 Lumen 算了多次反弹，它仍通过缓存、复用和分摊更新来满足实时预算；不能把“多次反弹”直接等同于“每像素完整路径追踪”。

依据：Epic：Lumen Technical Details。软件 / 硬件模式是否启用及默认值取决于版本、模板、平台和项目设置，不能只凭“使用 UE5”判断。

那 Nanite 又是什么？

Nanite 主要解决高几何细节怎样高效呈现的问题，是虚拟化几何系统，涉及细节选择、流送和高效光栅化等。它与 Lumen 可以协同工作，但不会因为模型使用了 Nanite，就变成路径追踪。

参考：Epic：Nanite Virtualized Geometry。

UE Path Tracer 在哪里？

这是单独的渐进式路径追踪模式，可持续累积样本，并结合 Movie Render Queue 输出高质量镜头。它适合影视、可视化，以及对照实时渲染中的近似误差。开启硬件光追、启用 Lumen、切换到 Path Tracer，是三个不同层面的决定。

依据：Epic：Path Tracer。普通游戏还可以选择其他光照方案，不是所有 UE 项目都使用 Lumen。

补充 / 从你写的 SHADER 看渲染流程 · 2026-09-26

我写的 Unity Shader，属于光栅化还是光追？

如果你写的是常见的 vert + frag 材质 Shader，这个 Pass 通常参与的是光栅化渲染流程。但你一般没有亲手实现“光栅化算法”——GPU 的光栅器负责这一步。

还没看到你的具体代码，因此这里先以普通网格材质 Shader 为例。Shader 是运行在 GPU 上的程序；它并不是“光栅化”的同义词，光追也需要 Shader。判断时要看哪个 Pass 被调用、由什么命令启动，以及代码实际做了什么。

Why：为什么我写了顶点和颜色，就能画出整个三角形？

因为你是在给引擎已有的渲染流程提供几个可编程步骤。引擎提交模型与绘制命令，GPU 在这些步骤之间完成三角形装配、裁剪、光栅化等工作。无需在每个材质 Shader 中重新写一遍“三角形覆盖了哪些像素”的算法。

What：你写的代码在这里。

  1. Unity / 渲染管线：提交网格、材质与绘制命令。
  2. 你写的顶点 Shader：vert。处理顶点，输出裁剪空间位置，并准备 UV、法线等后续需要的数据。
  3. GPU 管线与光栅器：装配、裁剪、投影相关处理，确定三角形对屏幕采样点的覆盖，生成片元并按规则插值。
  4. 你写的片元 Shader：frag。拿到片元输入后，计算颜色或写入其他渲染目标数据。
  5. GPU 输出相关步骤：深度 / 模板测试、混合、写入目标。部分测试可以提前执行。

光栅化通常发生在顶点处理之后、片元着色之前。vert 不等于光栅化，frag 也不等于光栅化：它们是光栅化渲染流程中两个可编程阶段。

例如，下面只是用来辨认阶段的代码片段，省略了结构体、ShaderLab 外壳与头文件：

#pragma vertex vert
#pragma fragment frag

Varyings vert(Attributes input)
{
    Varyings output;
    output.positionCS = TransformObjectToHClip(input.positionOS.xyz);
    return output; // 提供位置；不是在这里枚举三角形覆盖的像素
}

half4 frag(Varyings input) : SV_Target
{
    return half4(0.2, 0.7, 0.4, 1.0); // 给已经生成的片元提供颜色
}

这段 frag 连灯光都没有计算，却照样能显示有颜色的模型。说明“把形状画出来”和“计算物理光照”本来就是两件事。如果是延迟渲染，相关片元 Pass 还可能主要输出材质属性到 G-buffer，最终光照在其他 Pass 中计算。

参考：Unity 官方：URP 基础 Unlit Shader 的顶点与片元入口。代码仅展示长期通用的阶段结构，不是完整可复制的工程。

在哪里“写光栅化”？

普通 Unity 材质开发里，你通常不写光栅器，而是配置并使用它。你在 .shader 的 Pass 中写顶点 / 片元逻辑，在 ShaderLab 中用 Cull、ZTest、ZWrite、Blend 等配置相关管线状态。这些状态不是自己实现像素覆盖算法。

如果你要像 GAMES101 作业那样亲手写“包围盒遍历、点在三角形内判定、重心坐标插值”，那是在实现一个光栅器，可以作为单独的 CPU 程序或计算着色器练习；这不属于普通材质 Shader 的日常职责。

在哪里“写光线追踪”？先区分两种工作。

使用引擎已有光追

你主要设置材质和光照，并启用管线支持的效果。光线如何生成、求交、降噪等工作，通常由引擎实现。

例如 HDRP 中使用支持光追的材质与效果，不要求每位材质作者都亲手写 TraceRay。自定义材质则需满足相应光追 Pass / 材质兼容要求。

自己实现光追算法

你要决定射线从哪里发出、朝哪里走、命中后如何处理、结果存到哪里，并让 C# 或渲染管线准备场景数据和启动计算。

这已经超出“给普通模型写一个片元颜色函数”的范围。

以 Unity 常见的独立硬件光追路径为例，各部分的职责是：

不能只看扩展名，也不能只看有没有 frag。

.compute 表示通用 GPU 计算入口：它既能处理粒子，也能由你实现软件求交、光追乃至路径追踪；并不天然属于某一种。光追还可以通过内联射线查询等方式嵌入其他 Shader 阶段，具体取决于平台与 Unity 支持。

甚至可以先光栅化一个全屏三角形，再在它的 frag 中手写射线与球的求交：用于启动片元的是光栅化，片元内部生成场景图像的方法却可以是光追。因此看到 vert / frag 能识别所处阶段，不能证明函数内部没有追踪射线。

一个非常常见的误会：计算“光方向”不等于追踪光线。

max(dot(normal, lightDirection), 0) 只是根据表面朝向计算受光强弱；reflect(direction, normal) 只是计算反射方向。两者都没有回答“沿这个方向遇到了谁”。要得到这个答案，还需要场景求交、屏幕空间追踪或其他可见性数据。

若你用 Shader Graph，Base Color、Normal、Metallic、Smoothness 等节点主要描述材质。目标管线负责生成并运行相应 Pass；支持的 HDRP Graph 还可以生成光追所需代码。节点本身不把整个渲染器唯一归类为光栅化或光追。

对于普通 Unity 材质 Shader：你常写的是光栅化之前的顶点处理和光栅化之后的片元着色。只有当你或引擎额外进行射线查询，才涉及光追；是否属于路径追踪，还要看是否用路径采样来估计光传输。
07 / CLEAR THE CONFUSION

把几个常见名词放回正确的位置。

Forward、Forward+、Deferred，也是光追吗？

它们主要描述光栅化渲染中，几何和光照计算怎么组织。Forward 在绘制物体时计算光照；Deferred 通常先把可见表面的法线、材质等写入 G-buffer，再用这些数据处理光照。Forward+ 借助空间划分等手段筛选需要计算的灯光。名字中的“前向”也不是“从光源向相机追踪”。

Why：灯多不多、带宽够不够、透明物体怎么处理，都会影响效率。What：这是工作顺序与数据组织的选择，和“是否在某个环节发射射线”属于不同维度。

Unity：Rendering paths · Epic：Forward Shading Renderer

PBR 是不是意味着用了路径追踪？

不是。PBR（Physically Based Rendering）强调用较符合物理的材质与光照模型，例如能量守恒和合理的反射响应。光栅化渲染器也可以使用 PBR 材质；路径追踪器也需要材质模型。材质怎样响应光，与用什么方法估计到达它的光，是不同问题。

有反射、软阴影、红墙染色，就证明开了光追？

不能。反射可能来自反射探针、平面反射或 SSR；软阴影也可能由阴影贴图及滤波产生；颜色渗透可能已经烘焙进数据。画面呈现什么效果，不能唯一反推出计算算法。

SSR 为什么有时会在物体出屏幕后丢失反射？

SSR（Screen Space Reflections）复用当前视图的深度与颜色等信息来寻找反射。Why：这些数据已经有了，复用很划算。What：它主要查询屏幕空间可用的信息；屏幕外或被前方物体遮住的信息往往缺失，所以需要回退方案。场景光追能查询所维护的场景表示，但它也会受裁剪、距离与表示精度限制。

烘焙时用了路径追踪，游戏运行时就是路径追踪吗？

不是。算法在哪里运行、什么时候运行，很关键。烘焙可以预先通过大量采样求出光照，存成光照贴图或探针数据；游戏每帧只读取这些结果。就像提前算好一张表，查表时不需要重做全部推导。

因此，“制作阶段用路径追踪 + 运行阶段用光栅化”并不矛盾。动态物体能采样烘焙探针，也不意味着这些探针在实时重新求解全场景 GI。

RTX 显卡、硬件光追与路径追踪是什么关系？

硬件光追提供加速结构遍历、求交等能力；路径追踪是使用这些能力的一种算法。硬件不自动决定渲染算法。有硬件支持，项目仍可只用光栅化；没有专用光追单元，理论上仍可实现光追或路径追踪，只是性能与产品支持范围不同。

降噪是不是“多追踪了一些正确的光线”？

不是。Why：每帧样本少时噪声太明显。What：降噪器利用邻近像素、历史帧、法线、深度等信息，估计更稳定的结果。它可以大幅改善观感，也可能抹去细节或产生拖影；它不等于凭空获得更多真实样本。

08 / A BETTER QUESTION TO ASK

以后看一个引擎功能，先问这四句。

  1. 它解决的是可见性，还是某一类光照？例如找第一个表面，与计算反弹光，是不同任务。
  2. 它查询的是什么数据？当前屏幕、场景三角形、距离场，还是提前存好的贴图和缓存？
  3. 它什么时候计算？离线烘焙、运行时每帧更新，还是跨多帧积累？
  4. 为实时性能做了什么取舍？少样本、缓存、较粗表示、有限范围，还是降噪与历史复用？
小检查：一个 URP 6.7 场景开启了 SCGI，以下哪句最准确？
选一个答案，检查你是否区分了“渲染整帧”和“求解某种光照”。

把 GAMES101 与引擎连起来。

课上学到的三角形投影、深度测试，仍在生成现代游戏画面的第一层可见性；光线求交让引擎能查看屏幕外的场景；渲染方程与蒙特卡洛采样解释了为什么间接光难算，也解释了路径追踪的噪点。工程系统再用缓存、降噪、烘焙与时间复用，把这些方法放进毫秒级预算。

你真正要判断的，不只是“这个引擎是哪种渲染方式”，而是：这一帧的哪一部分，用什么方法，在什么时间，求出了什么信息。

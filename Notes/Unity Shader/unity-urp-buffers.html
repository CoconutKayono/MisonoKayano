01

先分清：阶段、Pass、资源、命令

渲染流程有先后关系，但 Buffer 本身没有一条统一的“出场顺序”。它们是不同阶段之间保存、传递或复用数据的容器。

同一个词经常跨层级使用。讲“光栅化之后做深度测试”，是在讲一次 Draw 的 GPU 阶段；讲“不透明之后画透明”，是在讲一帧中的 Pass；讲“先生成深度再做 SSAO”，是在讲资源依赖。这三条顺序不能直接拼成一条。

概念是什么例子
Stage / 阶段GPU 对一批输入执行的处理环节顶点着色、光栅化、片元着色、片元测试与输出
Draw / 绘制命令使用网格、Shader、状态和目标执行一次绘制画一个网格或一批实例；可在许多样本上并行
Pass / 渲染通道围绕某个目标组织的一批 Draw 或 DispatchShadowCaster、GBuffer、透明、Bloom
Resource / 资源可被写入、读取、绑定的数据存储深度附件、颜色纹理、顶点 Buffer、灯光表
CommandBuffer / 命令缓冲记录要执行的操作，不是屏幕像素设置目标、清除、Draw、Dispatch、Copy
Render Graph / 渲染图声明 Pass 与资源读写的依赖系统谁生成深度、谁消费深度、哪些结果没用
先问三个问题：这个 Buffer 存的是像素、几何／参数，还是命令？谁写它？谁必须等它写完才能读？答案比记名字更有用。

本篇使用 Universal Renderer、单个普通相机的 3D 渲染作为基线；2D Renderer、XR、相机堆叠和自定义 Renderer Feature 会增加分支。以下箭头表示数据依赖或教学上的典型顺序，虚线表示可选项。

02

Buffer 家族：按数据内容整理

图形讨论里常把所有“缓冲资源”都叫 Buffer。严格的图形 API 中，Buffer 往往是一维数据资源，Texture 是有尺寸、格式、Mip、采样规则的图像资源。所以 Color Buffer、G-buffer 经常实际是纹理或附件；不要只凭英文里有 Buffer 就当成 GraphicsBuffer。

名字存什么 / 为什么存在谁写 → 谁读典型时机 / 必需程度
Color Buffer
颜色缓冲		RGB 或 RGBA；保存当前合成的画面。HDR 时可保存大于 1 的亮度。A 是一个通道，含义取决于用途。不透明、天空盒、透明、后处理 → 后续特效或呈现贯穿整帧；可能直接是 Back Buffer，也可能是中间纹理。
Depth / Z Buffer
深度缓冲		每个样本的投影深度；让更近的可见表面遮挡后方表面。它不是颜色，也通常不是以米为单位。预通道或不透明 Draw → 深度测试；可再复制供特效使用绘制几何时绑定；是否单独预绘制取决于配置。
Stencil Buffer
模板缓冲		通常每样本 8 位整数；做区域标记、遮罩或材质分类。常与深度共用 depth-stencil 资源。带模板状态的 Draw → 后续模板比较按需；格式须支持 stencil。不是“第二个深度缓冲”。
Camera Depth Texture
相机深度纹理		供 Shader 采样的深度视图／结果；服务雾、软粒子、SSAO、深度重建等。DepthPrepass 或 CopyDepth → 屏幕空间特效在首次消费者之前可用；不保证等于当前深度附件的最新内容。
Opaque Texture
不透明颜色快照		保存透明绘制之前的场景颜色；透明材质可用它做折射。通常包括已绘制的天空盒。CopyColor → 水、玻璃或自定义 Shader按需，在透明之前获取；不会持续自动跟随 Color Buffer。
G-buffer
几何／材质缓冲组		多张屏幕纹理，保存可见表面的材质属性，供延迟灯光读取。GBuffer Pass → Deferred LightingDeferred / Deferred+；普通 Forward / Forward+ 不需要这一组。
Normal Texture
法线纹理		编码表面朝向，让特效了解几何方向；深度值本身没有完整法线。DepthNormals 等 → SSAO 等按需；延迟路径也可利用 G-buffer 的法线数据，布局依配置。
Shadow Map / Atlas
阴影深度图／图集		从灯光视角记录深度；比较接收点与最近遮挡者，判断是否在阴影里。ShadowCaster → 前向或延迟光照启用实时阴影时；它不是相机深度。
Motion Vector Texture
运动矢量纹理		RG 保存当前 UV 减上一帧 UV 的二维位移；帮助 TAA 和运动模糊。相机／对象运动矢量 Pass → 时间性特效按需求生成、在消费者前可用；URP 常规支持不透明及 Alpha Clip，透明材质不在常规覆盖中。
History Buffer
历史缓冲		保留上一帧颜色或其他历史状态；供重投影与时间累积。上一帧结果 → 本帧 TAA／时间性效果跨帧资源，不能用生命周期仅一帧的临时纹理替代。
DBuffer
贴花缓冲		保存贴花对基础色、法线、材质参数的修改，使后续表面着色能应用贴花。Decal Pass → 后续不透明表面着色可选贴花技术；D 在这里指 Decal，不是 Depth。
SSAO / LUT / Bloom / UI
效果中间纹理		分别保存遮蔽、颜色映射、小尺寸亮度图或 UI 合成结果。各效果 Pass → 光照／后处理／合成对应效果开启才出现；每种效果可有多级临时资源。
Rendering Layers
渲染层纹理		保存渲染层标识，供灯光或贴花等选择作用对象。不透明或 DepthNormals 等 → 对应效果可选；不是 Layer 的渲染先后顺序。
Hi-Z / Depth Pyramid
分层深度		多尺度深度归约，服务某些遮挡剔除／查询算法；GPU 也可能有不可见的层级 Z 元数据。深度 → 归约 → 查询不要假定每个 URP 相机都会显式生成；算法与内部硬件优化要区分。

这些是“用途”，不保证都是独立物理内存。资源可能共享附件、被图系统复用、位于 tile memory，或在不需要时完全不分配。activeColorTexture / activeDepthTexture 是“当前目标”的句柄概念，也不意味着各自新增一张纹理。

资料：URP 帧数据纹理参考 · URP：运动矢量 · URP：DBuffer 与屏幕空间贴花

MSAA Buffer 与 Resolve：为什么一张图还要“解析”？

MSAA 颜色／深度附件可以为一个像素保存多个样本，使三角形边缘的覆盖更精细。它不是把整帧以四倍分辨率重新绘制，也不保证每个样本单独运行完整片元着色。后续普通采样或呈现往往需要单样本结果，因此需要 Resolve，或采用专门的多样本读取方式。

分辨率、格式和样本数决定附件成本。举例：1920×1080 的 RGBA8 单样本颜色约 1920 × 1080 × 4 = 8.29 MB（约 7.91 MiB）；RGBA16F 是每像素 8 字节。4×MSAA 对应四份样本的理论数据量，若另保留解析目标还要再算一份。真实占用受压缩、对齐、tile 存储和资源复用影响，不能仅用这个乘法推算实际显存。

运动矢量按 URP 的约定满足 previousUV = currentUV − motionVector；它装的是位移，而不是物体世界坐标或最终颜色。

资料：URP：MSAA 与抗锯齿 · URP：运动矢量
03

整帧顺序：Forward / Forward+

前向路径的核心是：在绘制表面时计算光照，把结果直接写入颜色目标。Forward+ 改善灯光选择方式，仍然是前向着色；它不会因为“+”就自动产生 G-buffer。

先准备相机、可见对象和灯光数据；实时阴影在被光照采样之前生成。随后绘制不透明表面与 Alpha Clip 表面、天空盒，再绘制 Alpha Blend 透明物体。后处理与最终输出在后面；UI 的位置依渲染模式和配置，不宜一律画成最后一个固定 Pass。

深度预通道为什么存在？

有些效果在不透明颜色绘制之前就需要深度或法线，例如特定 SSAO / DBuffer 配置；有些配置使用 Depth Priming，为后续不透明绘制提前建立可见性。这时先画一次 DepthOnly 或 DepthNormals，后面再画颜色。否则，不透明 Draw 本身就能写深度，没必要为了“有深度缓冲”固定多画一次。

预通道可能减少昂贵的重复片元着色，也会增加顶点处理和绘制成本。它是否合算取决于材质成本、遮挡、GPU 架构、MSAA、平台和项目设置；不能简单说“开启一定更快”。Depth Priming 也可能改变后续颜色 Pass 使用的深度状态。

资料：Universal Renderer 配置参考 · Forward 与 Forward+
容易混的操作真正做什么
Depth Prepass主颜色绘制前，重绘需要包含的几何深度。
DepthNormals Prepass提前输出深度与法线；需要对应 Shader Pass。
CopyDepth复制／转换已经存在的深度，本身不重画整套网格。
Depth Priming利用提前建立的深度约束后续不透明着色，是一种优化策略。

6.7 的 Renderer 文档列出 Depth Texture Mode：After Opaques、After Transparents、Force Prepass；最早输入需求也会影响实际工作。Depth Priming 的 Auto 可使用已有预通道，Forced 可要求增加预通道；文档同时列出 Deferred、MSAA、移动端 TBDR 等不支持条件。Depth Prepass 与 Depth Priming 不能互换名称。

04

整帧顺序：Deferred / Deferred+

延迟路径先回答“这里是怎样的表面”，再回答“灯光照上去是什么颜色”。GBuffer Pass 写材质属性与深度，Deferred Lighting 读取这些信息计算光照，结果写到颜色目标。一个网格可能同时写多个颜色附件，这叫 MRT；多张附件不是多次完整重画。

路径主不透明表面Forward-only 不透明 / 透明核心差异
Forward绘制时直接计算光照前向无必需 G-buffer；灯光选择有每物体限制
Forward+绘制时直接计算光照Forward+按屏幕分区等数据挑选相关灯光
DeferredG-buffer → 延迟灯光Forward6.7 文档区分 stencil-based 延迟灯光实现
Deferred+G-buffer → 延迟灯光Forward+6.7 文档区分 cluster-based 延迟灯光实现

“Deferred”不能翻译成“所有东西都等到 G-buffer 后一起画”。普通透明颜色需要保留多层表面的贡献，而常规 G-buffer 主要保存当前可见表面的属性，因此透明仍走前向路径；某些无法完整表示在 G-buffer 中的材质也会走 Forward-only。Deferred+ 也没有把这些透明材质变成普通 G-buffer 表面。

资料：Deferred / Deferred+ 的 Pass 顺序 · Deferred 与 Deferred+ · URP 6.7：四种渲染路径

G-buffer 到底保存哪些东西？

把它理解成“每个可见像素的一份材质描述”。典型字段有基础色、材质标记、镜面或金属相关参数、遮蔽、法线、光滑度，以及与光照目标关联的发光／间接光数据。世界位置通常能由深度和相机矩阵重建，不必把一整套 XYZ 再固定存进一张纹理。

URP 的基础附件布局、可选 Depth-as-Color、ShadowMask、Rendering Layers 与准确法线编码都有具体条件。布局应按版本与启用功能核对；不要硬记“G-buffer 永远四张 RGBA8”或“每张都是最终颜色”。G-buffer 消耗空间与带宽，换取材质信息和灯光处理的分离。

资料：G-buffer 布局

6.7 的基础布局可读成：Albedo + Material Flags；Specular / Reflectivity + Occlusion；Normal + Smoothness；Emissive / GI / Lighting 目标。最后一项可以先承载发光与间接光，再累积实时光照；它与普通只读材质字段的角色不同。Depth / Stencil 另外参与可见性与分类。

05

最容易混：附件、纹理、快照与历史

Depth Attachment ≠ 自动实时更新的 Camera Depth Texture

深度测试读取当前绑定的深度附件。软粒子或屏幕空间 Shader 读取的是被绑定为采样输入的深度纹理。它们有可能来自同一资源的不同视图，也可能是预通道输出或一次复制；MSAA、图形 API 和 Render Graph 会影响实现。两个名字不同，不保证两块内存；两块内存存在，也不保证每次写入都自动同步。

因此，“我打开 Depth Texture 之后，为什么透明物体没在深度图里？”首先检查：它是否写深度、复制发生在什么时候、它有没有被相应 DepthOnly / DepthNormals Pass 包含。透明 ZWrite On 本身也不能回头修改更早生成的快照。

资料：URP 帧数据纹理参考 · Render Graph：颜色与深度副本、Pass 合并

Opaque Texture ≠ 当前屏幕颜色 ≠ History

“为什么不能直接读写当前 Color？”在同一绘制中把同一子资源既作为渲染输出又作为普通采样输入，往往不合法或需要专门机制。通常用副本或 ping-pong：读 A、写 B，下个阶段再交换。Framebuffer fetch / input attachment 只能在允许的条件下使用，不等于任意采样邻居像素。

历史纹理常采用跨帧轮换，临时纹理常在一次图执行内回收。名字里的 “buffering” 都涉及保存数据，但双缓冲交换链、后处理 ping-pong 和 TAA History 的目的不同。

Cull / 背面剔除图元的正反朝向光栅化前被剔除的图元不产生该次绘制的覆盖
裁剪 / Scissor图元在视锥中、样本在矩形范围内裁剪／光栅／片元操作阶段不等于 Alpha Clip 或深度测试
Alpha Clip / discard材质 Alpha 是否达到阈值通常在片元 Shader 中丢弃片元；常规用法不会像通过片元那样写颜色或深度
Stencil Test模板值与参考值比较片元测试；可能 early / late可按 Fail / ZFail / Pass 更新模板
Depth Test / ZTest候选深度能否通过当前已存深度的比较片元测试；可能 early / late只比较；Depth 写入由 ZWrite 等控制
Alpha Blend新旧颜色怎样合成输出合并阶段更新颜色；自身不代表要写深度
ColorMask允许改哪些颜色通道颜色输出阶段可禁用颜色写入，仍可发生深度／模板操作
Alpha-to-Coverage用 Alpha 调整 MSAA 样本覆盖多重采样覆盖／片元操作是样本覆盖技术，不等同于普通半透明混色

Early-Z 与 Late-Z：为什么示意图不能当硬件时刻表？

如果已经知道片元被前方表面挡住，GPU 可以先检测并跳过昂贵的片元着色，这就是 early reject 的价值。但“提前拒绝”与“提前写深度／模板”不是同一件事。硬件可提前做保守检测，等 Shader 确定没有丢弃、且输出深度已知后再提交结果；也可能采用 late tests。

Alpha Clip、片元 Shader 写深度、UAV／存储写入等会影响能否提前检测或提交，具体取决于 API、Shader 和硬件。不能说使用 clip 就一定彻底关闭 Early-Z，也不能说所有 GPU 都固定先 Alpha 再深度。

显式 [earlydepthstencil] 或 API 的 forced early tests 会改变保证：测试／深度模板更新可能先于 Shader 的 discard。它们不是普通材质优化的无条件开关。本篇 Alpha Clip 和数值演示采用普通 late-commit 的教学模型，不模拟这些特殊情况。

资料：D3D：earlydepthstencil 的语义 · Vulkan 规范：片元操作与 early / late tests · ShaderLab：Cull
可能的提前拒绝

光栅化 → Early Depth / Stencil Reject → 存活片元 Shader → 必要的确认与提交

可能的晚期测试

光栅化 → Shader（可输出深度／clip）→ Late Depth / Stencil → 提交

深度测试：比较，与写入分开

ZTest 决定是否通过比较；ZWrite 决定通过时是否更新深度。ZWrite Off 仍然可以参与深度测试。这正是普通透明材质常用的组合：被墙挡住，但不把玻璃当成一个完全遮住后续透明层的深度面。

状态直观含义常见用途 / 注意
ZTest LEqual候选深度 ≤ 已存深度时通过普通非反向深度示例；包含等深度片元
ZTest Less严格更小才通过相同深度失败；与 LEqual 不同
ZTest Equal等于已存值才通过可用于已建立深度的后续着色；精度与几何必须匹配
ZTest Greater / GEqual大于 / 大于等于时通过可用于特定遮挡显示；结合实际深度约定理解
ZTest Always深度比较总通过若 ZWrite On 仍可能改写深度，不等于“完全不碰深度”
ZWrite On / Off允许 / 禁止深度写入与是否混色、渲染队列、模板操作是不同控制项

为了直观，下面假设近处 0、远处 1、清除值 1。先画墙 z=0.40，再画人物 z=0.65：0.65 ≤ 0.40 为假，人物被挡住；若人物是 0.20，则通过，且 ZWrite On 时把深度改成 0.20。这些是归一化的教学值，不是距相机 0.4 米。

Reversed-Z、非线性与 Z-fighting

实际平台可使用 Reversed-Z：近处接近 1，远处接近 0，并使用相应的底层比较与清除规则。Unity 的 ShaderLab / 平台适配应与当前投影约定配合；不要仅凭“数值小”猜它更近，也不要见到 Reversed-Z 就随意把所有材质改成 Greater。

透视投影的原始深度通常非线性。做雾或软粒子距离比较时，先用 URP 对应深度采样与线性化工具，处理平台约定，例如 SampleSceneDepth 与 LinearEyeDepth；重建位置与线性距离也不是同一个操作。近平面太近、远近比过大、重叠共面表面会加剧精度问题。Z-fighting 是深度精度／几何关系问题，并不说明深度测试没开。

模板测试：整数遮罩与三条更新分支

把 Stencil 当成“贴在屏幕样本上的小标签”。它比较的是整数，不是距离。典型格式提供 8 位，即 0–255；ReadMask 选择哪些位参与比较，WriteMask 选择哪些位允许被更新。

比较：(Ref & ReadMask) Comp (Stored & ReadMask)
写入：New = (Stored & ~WriteMask) | (OpResult & WriteMask)
按实际模板位宽截断；ReadMask 与 WriteMask 各司其职。

分支触发条件该分支能做什么
Fail模板比较失败Keep / Replace / Zero / 增减 / Invert 等；不提交常规颜色
ZFail模板通过，深度比较失败可更新模板，即使本片元没有写颜色

透明度：Clip、Blend、Coverage 是三件事

“透明度测试”容易混淆。现代 URP 的 Alpha Test 通常指 Alpha Clipping：片元 Shader 根据阈值决定丢弃或保留；Alpha Blend 是把通过的片元颜色按比例混合；Alpha-to-Coverage 是调整 MSAA 样本覆盖。Alpha 值本身不会自动开启任何一种行为。

方式本质常用深度状态典型用途
Opaque表面覆盖时直接提供颜色ZTest LEqual / ZWrite On墙、地面等
Alpha ClipAlpha 低于阈值丢弃，否则按存活表面绘制常见 ZWrite On；与透明表面类型也能组合树叶、栅栏、孔洞；边缘通常是二值覆盖
Alpha Blend通过测试后把新颜色与已有颜色合成常见 ZWrite Off，仍开 ZTest玻璃、水、烟雾；需要合适排序
Alpha-to-Coverage把 Alpha 转为 MSAA 样本覆盖率视具体 Shader 与采样设置可改善某些植被边缘；不是通用透明叠层方案

Alpha Clip：孔洞应该在每个相关 Pass 中一致

// 片元 Shader 内的教学片段
clip(alpha - cutoff); // 小于 0 时丢弃；alpha == cutoff 时保留

被保留的叶片部分可以写深度与颜色，被裁掉的孔洞允许后方表面继续可见。如果只在颜色 Pass 裁剪，ShadowCaster 没裁剪，叶片会投下整张四边形的阴影；DepthOnly / DepthNormals 不一致也会造成软粒子、SSAO 或 Depth Priming 的错误遮挡。阈值、贴图和顶点变形应在相关 Pass 中保持一致。

Cout = Cs × αs + Cd × (1 − αs)
对应常见直通 Alpha RGB 混合：Blend SrcAlpha OneMinusSrcAlpha。下面的演示采用线性 RGB、关闭色调映射。

为什么普通透明不写深度，却还是会被墙挡住？

墙已经写了深度，玻璃仍做 ZTest，因此后方玻璃会失败。玻璃 ZWrite Off 是避免第一层玻璃把更远的透明贡献全部挡掉。透明通常由远到近排序，普通不透明则可更偏向从近到远以减少重复着色；队列排序也会考虑材质、批处理等因素，不保证所有三角形严格逐像素排序。

一个深度值不能表达玻璃的所有透明层。两个互相穿插的大网格，在不同像素处前后关系可能相反；只按 Renderer 排序无法完美解决。按需拆分几何、使用合适的专用透明技术，或采用 OIT 等自定义方案。普通 URP Alpha Blend 不意味着自动存在 Accumulation / Revealage Buffer。

Queue 决定 Draw 大致在哪组事件中提交，Blend 决定颜色如何合成，ZWrite 决定深度更新，RenderType 是分类标签。把 Queue 改成 Transparent 本身不会替你配置正确的混合和深度状态；Alpha Clip 也不等于“必须进入透明队列”。

到底线性还是并行？两者同时存在

依赖决定必须先完成什么；硬件与调度决定哪些工作可以重叠。因此 URP 既有必须保持结果顺序的链条，也有大量并行执行。

观察尺度有序在哪里并行在哪里
一个像素的最终颜色普通 Alpha Blend 必须保持正确合成关系不同像素／样本之间通常可分批并行处理
一个 Draw 的数据流没有顶点变换结果，不能完成相应图元的光栅化大量顶点／片元以 SIMD / SIMT 等方式处理，批次与阶段可重叠
多个 Pass 的资源依赖先写 G-buffer，再读取它做灯光；先生成深度，再读取它做 SSAO没有冲突的工作有调度空间，但未必实际同时运行
CPU 与 GPU命令提交与资源可用受同步约束CPU 可准备下一帧，同时 GPU 处理当前／更早的帧
CPU 线程 / Jobs有结果依赖的任务要等待剔除、准备数据、构建部分分区数据可采用多线程
图形与计算队列读写同一资源必须通过同步建立可见性支持的后端可尝试 async compute；实际重叠依硬件与负载
多帧与显示交换图像和资源不能在仍被使用时覆盖多帧在途与交换链让 CPU、GPU、显示系统交错工作

CPU／GPU 跨帧交错，不是一帧完整结束才开始下一帧

这会提高吞吐量，但更多排队也可能增加输入到显示的延迟。CPU 等待资源、读取 GPU 结果、VSync 或 GPU 饱和时，时间图会出现等待空隙。“CPU 帧编号”与“屏幕正在显示的帧”不必一致。

Frames in Flight 是尚在处理的帧／资源集合，交换链图像数是显示目标的数量，二者不是同一个计数。不同片元也不是永远彼此独立：导数可涉及 2×2 quad 与 helper lane；“大量并行”不表示每个像素是一个毫无协作的线程。

同一图形队列中的命令有定义好的可观察顺序与依赖规则，但 GPU 内部可以流水化、分波执行或对独立工作重叠处理。写后读（RAW）、读后写（WAR）、写后写（WAW）冲突需要正确的 barrier／同步。Barrier 的意义是建立资源使用与可见性，不是每一条都让整个 GPU 完全停住。

Async Compute：能力、请求、实际重叠分开

GPU 可能提供图形和计算队列；Unity 后端是否支持，URP / 自定义 Pass 是否请求使用，以及硬件是否有空余执行资源，是三个问题。一个 Compute Pass 也可以在图形队列上有序执行。若计算依赖深度，仍要等深度可用；其消费者仍要等计算完成。Fence / barrier 负责正确性。

6.7 的平台边界：核查时 SystemInfo.supportsAsyncCompute 官方页说明 Unity 在 DX12 实现支持，DX11、Vulkan、Metal、OpenGLES、WebGPU 返回 false，主机平台另查相应文档。Vulkan 规范支持多队列，不等于这个 Unity 版本启用了异步计算；以目标设备运行时查询为准。

异步计算并不是“把任何特效换成 Compute 就变快”。图形与计算可能争用同一批 Shader 核心、缓存或带宽；同步成本也可能抵消收益。验证实际重叠要看 GPU 时间线，不能从 Frame Debugger 的线性列表推断没有并行。

Render Graph：资源生命周期与逻辑顺序

Render Graph 先记录“某个 Pass 将读 A、写 B”，随后根据实际需求组织执行。记录一个句柄不等于马上分配纹理，更不等于 GPU 已经写完。未参与最终有效结果且允许裁剪的 Pass 可以被移除；临时资源在首次需要前分配、在最后一次使用后回收或复用。

在 tile-based GPU 上，兼容的逻辑 Raster Pass 可以合成原生 Render Pass，让附件更久留在片上 tile memory，减少外部内存带宽。Frame Debugger 中看见 GBuffer、Lighting 等逻辑步骤，不保证它们之间每次都把完整屏幕纹理写回再读回。

不要把 Render Pass 合并与 Shader 合并、Draw Call 合并或多线程并行混为一谈。合并 Pass 主要改变附件和执行组织；MRT 是一次着色输出多个附件；GPU Instancing / batching 处理的又是绘制与状态成本。

  1. 路径实验：单相机、墙、球、一个 Alpha Clip 网格、两张透明面。分别捕获 Forward+ 与 Deferred+；寻找 G-buffer 与延迟灯光，并确认透明仍在前向阶段。
  2. 快照实验：切换 Opaque Texture，检查 CopyColor 及其采样者；再切换 Depth Texture，检查 CopyDepth 或预通道。若某个 Feature 已经要求输入，开关变化未必新增同名 Pass。
  3. 预通道实验：单独启用 SSAO，并切换其深度／法线来源及 After Opaque 配置；看数据需要出现在哪个消费者之前。不要把所有 SSAO 配置画成同一个时点。
  4. 深度实验：让透明面位于墙后，ZWrite Off 时仍应被墙遮住。再在自定义材质中改变 ZWrite，对比深度附件与已生成的深度纹理是否同时变化。
  5. 模板实验：先选用可用模板位，画不写颜色的遮罩，再让内容 Comp Equal；通过 ReadMask / WriteMask 观察只改变一个位的效果。注意相机切换或下一帧初始模板状态。
  6. 裁剪一致性：让叶片使用 Alpha Clip，检查颜色、阴影、深度／法线的孔洞是否一致。错误通常来自不同 Pass 的裁剪／变形不一致。
  7. 叠层实验：交换两张透明面的排序，观察交叠颜色；再让几何互相穿插，体验对象级排序的局限。它不意味着深度测试失效。

容易误认为正确理解
深度缓冲 = 深度纹理 = 阴影图前者用于当前相机测试；第二个用于 Shader 采样；阴影图来自灯光视角。
G-buffer = 所有 GPU BufferG-buffer 是延迟路径的表面属性组，顶点／灯光／命令缓冲属于不同用途。
DBuffer = Depth BufferURP 的 DBuffer 是贴花数据。
Stencil = 透明度遮罩贴图Stencil 是整数位标签；Alpha 是材质／纹理通道，可独立使用。
透明 = 不进行深度测试常规透明仍 ZTest，只是通常不写深度。
ZTest Always = 不会改深度Always 只说明比较总通过，ZWrite On 仍可改深度。
深度失败 = 所有附件都绝不变模板 ZFail 可能更新；其他特殊 Shader 副作用另按 API 语义。
ColorMask 0 = 不绘制任何效果颜色被屏蔽，深度／模板仍可被更新。
打开 Depth Texture = 所有对象实时出现在其中取决于对象 Pass、ZWrite、生成／复制时机与资源视图。

渲染管线线性图 = GPU 单线程串行图通常画结果依赖；GPU 内部与 CPU/GPU 之间有并行。
问题 1：透明材质 ZWrite Off，为什么看不到墙后的部分？

它仍进行深度测试，墙先写入的深度使后方透明片元失败。ZWrite 控制写入，ZTest 控制比较。

问题 2：CopyDepth 后另一个 Draw 更新深度，软粒子一定立即看到新值吗？

不一定。如果粒子采样的是未更新的独立副本，它仍看到复制时的深度。核验资源视图与后续生成／复制事件。

问题 3：一个片元深度失败，模板一定保持原值吗？

不一定。模板已通过但深度失败时，执行 ZFail；若该操作写入模板且 WriteMask 允许，模板会变化。

问题 4：用 Alpha=0 的输出替代 clip，能形成正确孔洞吗？

不能保证。在不混合的材质中 RGB 仍可能覆盖；ZWrite On 时仍可能写深度。clip 是丢弃，Alpha=0 只是数值。

问题 5：两个无依赖 Pass 就一定并行吗？

不一定。没有依赖只提供调度自由；实际队列、后端支持与 GPU 资源决定能否重叠及是否更快。

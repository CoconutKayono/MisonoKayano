# A08｜纹理格式、精度、压缩与数据贴图

> 核心问题：一张看起来正确的贴图，为什么进 Unity 后会使卡通阴影边界偏移、出现块状噪声，或者占用远超文件大小的内存？
>
> 一句话结论：纹理是经过编码、量化和格式解释的数据。选择格式之前，先定义通道语义；磁盘压缩、GPU 块压缩、sRGB 转换和采样过滤分别解决不同问题。

编号 A08；阶段 A：数学、几何与资源表示。面向 Unity NPR（非真实感渲染）的颜色 Ramp、遮罩、法线和 SDF。本卡独立包含必要定义和计算方法；采样 LOD、导数与过滤的完整机制留待后续卡片。

依据本地 Unity 6.7 Beta / 6000.7 文档，构建日期 2026-06-26。以下容量公式针对普通二维纹理，不含数组层、立方体面、MSAA、稀疏驻留和驱动额外开销。目标平台是否支持具体格式，必须结合设备与构建设置检查。

## 1. 四层数据不能混成一个“图片格式”

| 层次 | 回答的问题 | 例子 |
| --- | --- | --- |
| 通道语义 | 数值代表什么 | RGB 颜色、阴影阈值、单位法线、类别编号 |
| 数值表示 | 一个通道怎样表示数值 | UNorm8、Float16 |
| GPU 格式 | GPU 怎样存储、解码数据 | RGBA8、BC5、ASTC 6×6 |
| 文件编码 | 磁盘怎样保存、分发资源 | PNG、JPEG、额外 Crunch 压缩 |

Texel 是纹理的离散样本，pixel 是目标图像中的像素；两者并不一一对应。Mip 是分辨率逐级缩小的一组图像，用于不同采样尺度。

PNG 较小，可能只是源图更容易无损压缩。导入后，同尺寸、同 GPU 格式的两张不同内容纹理，其固定格式有效载荷可以相同。Unity 的 Crunch 在 DXT/ETC 之上减少磁盘数据，加载时再解为供 GPU 使用的 DXT/ETC 数据，不进一步缩小同一底层格式的运行时有效载荷。[Unity GPU 纹理格式基础](https://docs.unity3d.com/6000.0/Documentation/Manual/texture-compression-fundamentals.html)

## 2. UNorm 的“8 位”到底意味着什么

UNorm 是无符号归一化整数。`b` 位存储整数 `q∈[0,2^b−1]`，读取后解释为 `q/(2^b−1)`。按最近值量化 `[0,1]` 内的数据 `x`：

\[
q=\operatorname{round}\bigl(x(2^b-1)\bigr),\qquad
\hat{x}=\frac{q}{2^b-1}
\]

不含额外压缩和转换时：

\[
\Delta=\frac{1}{2^b-1},\qquad
|\hat{x}-x|\leq\frac{\Delta}{2}
\]

UNorm8 的间隔是 `1/255≈0.00392157`，最大最近量化误差约 `0.00196078`。`0.5` 无法精确表示，邻近值为 `127/255` 和 `128/255`。这不是浮点 Shader 计算错了，而是输入已经离散化。

Float16 则使用符号、指数和尾数，能表达大于 1 的值，但间隔随量级变化。它与 UNorm16 不是同一种精度分布：二进制半精度在 `[1,2)` 的相邻间隔为 `2^-10`，UNorm16 在 `[0,1]` 的间隔为 `1/65535`。仅看到“16 位”不能判断误差或范围。[Microsoft 16 位浮点表示](https://learn.microsoft.com/en-us/windows/win32/direct3d11/floating-point-rules#16-bit-floating-point-rules)

本节的误差界只适用于所写的 UNorm 最近量化模型。它不涵盖块压缩误差、双线性过滤、sRGB 解码或特殊格式。

## 3. sRGB 标记会改变数据的数值

sRGB 是颜色编码曲线。对于 `[0,1]` 内编码值 `e`，其标准解码为：

\[
L(e)=\begin{cases}e/12.92&e\leq0.04045\\((e+0.055)/1.055)^{2.4}&e>0.04045\end{cases}
\]

`L(0.5)≈0.214041`。在线性色彩空间项目中，按 sRGB 纹理采样时，RGB 会进行相应解码；Alpha 不按这条颜色曲线解码。若 RGB 存的是“0.5 代表轮廓边界”的数值遮罩，开启 sRGB 就改变了算法输入。[Unity 线性数据纹理](https://docs.unity3d.com/6000.0/Documentation/Manual/linear-textures.html)

反例：原始遮罩值 `0.6` 应通过阈值 `0.5`，但 sRGB 解码后约为 `0.318547`，就不通过了。提高 Shader 运算精度无法恢复错误解释的数据。

| 数据语义 | 导入与读取原则 |
| --- | --- |
| 画出来的表面颜色、颜色 Ramp | 明确源文件的颜色编码；sRGB 源颜色在 Linear 项目中应正确解码 |
| 阈值、权重、SDF、查表系数 | 按约定读取数值，通常关闭 sRGB |
| 法线贴图 | 使用 Normal Map 导入与相应解包约定，不能把普通 RGB 颜色读取当作完整法线读取 |
| 类别或材质 ID | 避免会制造新类别值的量化、损失压缩与过滤；按算法决定整数资源或精确解码方式 |

因此不能笼统要求“所有 Ramp 都关闭 sRGB”。颜色 Ramp 与标量函数查找表具有不同语义。

## 4. GPU 块压缩按块计费

BC/ASTC 等格式把一块 texel 编码成固定字节数，使随机区域采样无需解压整幅图像。BC1 的 `4×4` 块占 8 B；BC5、BC7 的 `4×4` 块占 16 B。BC5 主要承载两个通道，不能按 RGBA 语义直接替换 BC7。[Microsoft BC 格式说明](https://learn.microsoft.com/en-us/windows/win32/direct3d11/texture-block-compression-in-direct3d-11)

ASTC 二维格式的块均为 128 bit，即 16 B；块覆盖尺寸可变。`4×4` 对应 8 bit/texel，`6×6` 约 3.56 bit/texel，`8×8` 为 2 bit/texel。块越大并不意味着任意内容质量相同，具体误差还取决于内容与编码配置。[Arm ASTC 格式说明](https://github.com/ARM-software/astc-encoder/blob/main/Docs/FormatOverview.md)

对宽高 `W,H`，块宽高 `Bw,Bh`、每块 `S` 字节：

\[
B_{level}=\left\lceil\frac{W}{B_w}\right\rceil
\left\lceil\frac{H}{B_h}\right\rceil S
\]

不足一块也必须分配一个格式块。例如逻辑尺寸 `9×7` 的 BC1 层，块数是 `3×2`，有效载荷 `48 B`；直接计算 `9×7×0.5=31.5 B` 就漏掉了边缘块。此算例解释存储公式，不保证任意 API 的纹理创建接口都接受该顶层尺寸。

无 Mip、单层 `1024×1024` 的有效载荷如下。`1 MiB=1,048,576 B`：

| 格式 | 计算 | 结果 |
| --- | --- | --- |
| R8 UNorm | `1024²×1` | 1 MiB |
| RGBA8 | `1024²×4` | 4 MiB |
| RGBA16F | `1024²×8` | 8 MiB |
| BC1 | `256²×8` | 0.5 MiB |
| BC5 / BC7 | `256²×16` | 1 MiB |
| ASTC 6×6 | `171²×16` | 467,856 B，约 0.446 MiB |

这些是从格式推导的数值，不是实际驻留显存测量。驱动对齐、元数据、CPU 副本和平台回退都可能增加占用；并非每个设备都支持表中全部格式。

## 5. Mip 的“多三分之一”有前提

若未压缩的正方形纹理每级宽高减半，面积序列为 `1,1/4,1/16,…`，完整链总量接近顶层的 `4/3`。有限链会略少；例如 `1024²` 到 `1²` 的 RGBA8 共 `5,592,404 B`。

块压缩小 Mip 仍至少占一个块，应逐级使用向上取整公式求和。非正方形纹理到某一维为 1 后也不再每级面积缩至四分之一。Mip Streaming、平台降分辨率与实际驻留层数会进一步改变运行时容量。

## 6. NPR 的边界对数据误差特别敏感

设一维遮罩函数 `v(x)` 的边界由 `v(x)=t` 定义。若局部梯度非零，输入误差 `δv` 引起的小位置误差一阶近似为：

\[
|\delta x|\approx\frac{|\delta v|}{|dv/dx|}
\]

例如以 texel 为位置单位，局部斜率为 `0.01/texel`，UNorm8 最近量化最大误差对应约 `0.196 texel` 的位置变化；斜率降为 `0.001/texel`，估算约为 `1.96 texel`。这是局部线性模型，不是对所有 SDF 的全局界限；真实距离场的归一化尺度决定梯度大小。

块压缩会带来额外的空间相关误差，卡通阈值操作会让小数值变化表现为边界跳变。远处 Mip 和视角变化又可能改变采样结果。因此“静止近看没有问题”不足以证明面部 SDF 或细线遮罩能稳定用于动画。

通道打包也有代价：一张普通纹理的 RGB 共用 sRGB 解释，其通道还共用尺寸与采样设置。把颜色和数据硬塞在一起可能造成解释冲突；选用的块压缩也未必能独立保留各通道细节。应从允许误差和目标设备出发，实测决定格式，而不是把所有贴图统一压成一种格式。

## 7. 最小实验：只读检查导入结果

保存为 `Assets/Editor/A08TextureAudit.cs`。在 Project 窗口选择一张已导入的 Texture2D，执行菜单 `Tools/Encyclopedia/A08 Audit Selected Texture`。脚本不会修改或重新导入资源。

```csharp
using UnityEditor;
using UnityEngine;

public static class A08TextureAudit
{
    [MenuItem("Tools/Encyclopedia/A08 Audit Selected Texture")]
    public static void Audit()
    {
        var texture = Selection.activeObject as Texture2D;
        if (texture == null)
        {
            Debug.LogWarning("Select an imported Texture2D in the Project window.");
            return;
        }
        string path = AssetDatabase.GetAssetPath(texture);
        var importer = AssetImporter.GetAtPath(path) as TextureImporter;
        Debug.Log($"{path}\nSize={texture.width}x{texture.height}, " +
                  $"Format={texture.graphicsFormat}, Mips={texture.mipmapCount}, " +
                  $"Readable={texture.isReadable}");
        if (importer != null)
            Debug.Log($"Type={importer.textureType}, sRGB={importer.sRGBTexture}, " +
                      $"MipsRequested={importer.mipmapEnabled}, " +
                      $"CompressionSetting={importer.textureCompression}");
        Debug.Log("This describes the current Editor texture, not a device memory measurement.");
    }
}
```

检查步骤：

1. 准备一份测试贴图副本，记录尺寸、用途、原始中点值和希望使用的目标平台。
2. 运行脚本，分清导入设置与当前 Texture 的 `graphicsFormat`；“Compressed”只是设置名称，不是具体格式。
3. 用上面的公式估算顶层和 Mip 有效载荷，与磁盘文件大小分列记录。
4. 在测试副本上比较正确/错误 sRGB 解释，以及压缩前后的边界。每次只改变一项设置。
5. 在目标设备构建中再次核对格式与效果。Editor 报告不能证明所有设备使用相同格式。

`Texture.graphicsFormat` 返回纹理对象的图形格式，见 [Unity API](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Texture-graphicsFormat.html)。本地还核对 `Manual/texture-compression-fundamentals.html` 和 `Manual/linear-textures.html`，文档根目录为 `E:\Claude Skills\学习仓库\09_Unity官方文档\Documentation\en`。

## 8. 自测与验证边界

1. PNG 缩小一半，GPU 有效载荷是否必然缩小一半？**否，必须看导入后的尺寸、格式和 Mip。**
2. RGBA16F 能否保证所有 `[0,1]` 数据比 UNorm16 更准确？**不能，精度分布不同。**
3. 为什么小尺寸块压缩层不能直接乘平均 bit/texel？**块数需要向上取整。**
4. 遮罩阈值错了，先提高 Shader 到 float 是否足够？**不够，应检查输入编码、导入格式与采样。**
5. 图中 Ramp 是颜色还是系数？**必须由资产和算法约定回答，文件扩展名不能回答。**

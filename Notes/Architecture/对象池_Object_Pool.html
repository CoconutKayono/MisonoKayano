开篇

先抓住对象池的本质

对象池（Object Pool）是一种通过复用对象，减少反复创建与销毁成本的设计模式。但这个定义只描述了它的作用，还没有揭示它的本质。

理解对象池，应该抓住三个核心问题：

  1. 对象为什么一定要销毁？如果一个对象暂时不用，能不能留下来？
  2. 对象与它所承担的工作是否必须绑定？完成一次工作，是否意味着对象的生命周期也必须结束？
  3. 谁应该管理对象的生命周期？是使用对象的业务代码，还是一个专门的资源管理者？
将对象的物理生命周期与它的业务使用周期分离，通过集中管理和复用，以空间换取时间，并控制资源分配的成本。
01 · WHAT

什么是对象池？

1. 从最普通的对象使用方式开始

假设我们正在制作一个游戏，需要不断发射子弹。最直接的实现方式是：

C# · 示意片段
public void Fire()
{
    Bullet bullet = new Bullet();

    bullet.Initialize();
    bullet.Move();

    // 工作完成后，失去对 bullet 的引用
}

这里是普通 C# 对象的示意。它在不再被引用后，可能由垃圾回收器回收，并不是立即销毁。如果是 Unity 的 GameObject，还涉及 Instantiate() 和 Destroy()。

这种方式的对象生命周期通常是：创建 → 使用 → 销毁或回收。每一次使用，都可能需要创建一个新对象。

问题是：子弹飞行结束后，对应的对象真的必须销毁吗？不一定。

我们需要结束的是这颗子弹当前承担的工作，而不一定是承载这项工作的对象本身。

例如，一颗子弹命中敌人之后：

  • 它不应该继续飞行。
  • 它不应该继续造成伤害。
  • 它不应该继续参与当前子弹的游戏逻辑。

但这不意味着它的 Transform、组件、内存等资源必须立即释放。它完全可以重置状态，等待下一次发射。

2. 对象池改变了什么？

引入对象池后，对象不再随着一次使用结束而必然销毁，而是在空闲与使用中两个状态之间转换。

对象池不是让对象永远存在，而是让对象的创建与销毁不再和每次业务使用一一对应。

3. 对象池的两个生命周期

这是理解对象池最重要的区分。

生命周期含义子弹示例
物理生命周期
Physical Lifetime		一个实际对象从创建到最终销毁、回收的过程创建实例 → 存在于内存中 → 最终销毁
逻辑使用周期
Logical Usage Lifetime		对象承担某次业务工作的过程开始发射 → 飞行 → 碰撞 → 本次发射结束

不使用对象池时，我们通常让两个生命周期近似绑定。使用对象池后，一个物理对象可以先后承担多个逻辑使用周期。

同一个 Bullet 实例子弹 A：第一次使用重置 → 子弹 B：第二次使用重置 → 子弹 C：第三次使用

子弹 A、B、C 是三次不同的业务使用，但底层完全可以是同一个对象实例。

对象池复用的是对象实例，而不是上一次业务的状态。

这也解释了为什么“重置状态”是对象池正确性中非常重要的一部分。

02 · WHY

为什么需要对象池？

1. 创建对象并不总是免费的

先区分普通 C# 对象和 Unity 游戏对象。

普通 C# 对象的创建，可能涉及内存分配、字段初始化、构造函数执行，以及未来的垃圾回收压力。

Unity 中创建一个复杂的游戏对象，还可能涉及：

  • 实例化 GameObject 及其组件。
  • 初始化组件状态。
  • 执行相关生命周期回调。
  • 建立引擎内部的数据结构。
  • 注册或更新渲染、物理等相关状态。

实际成本取决于对象结构和引擎工作量，并非每次创建都会执行上述所有操作。

垃圾回收（GC）并不是对象销毁本身，而是托管内存回收机制。Unity 的 Destroy(gameObject) 与 C# 的 GC 也不是同一个操作。

2. 问题通常不是创建一次，而是反复创建

假设某个游戏每秒生成 200 颗子弹。

200每秒发射数量
60,000持续 5 分钟的发射次数
≈ 400存活 2 秒时的稳态并发量

如果没有复用，并且每次发射都需要新建对象，那么五分钟就可能出现 60,000 次对象创建。

但如果每颗子弹的存活时间只有两秒，并且同时存在的子弹数量稳定在约 400 个，那么可以考虑复用大约这个量级的对象，而不是持续产生新实例。

对象池减少的是重复分配与初始化，并不是减少业务上实际发射的子弹数。

3. 对象池通过什么来降低成本？

可以把普通创建销毁方式的成本写为：

C普通 = C创建 ＋ C初始化 ＋ C使用 ＋ C回收

而一次命中空闲对象的池化使用，大致是：

C池化 = C获取 ＋ C重置 ＋ C使用 ＋ C归还

这里不是严格的性能方程，而是成本组成的模型。对象池将昂贵的首次创建成本摊到了后续多次使用中。

但对象池也引入了额外操作和内存保留成本。因此：对象池不保证比直接创建更快。

对于初始化成本很低的对象，使用对象池反而可能更慢；应当根据实际性能测量决定是否池化。

4. 对象池实际上做了一次资源权衡

维度直接创建与销毁对象池
创建成本使用时反复承担首次或扩容时承担
内存占用空闲对象通常可被回收主动保留空闲对象
GC 压力可能较高可以降低
状态管理较简单必须正确重置
生命周期相对直观需要明确获取与归还
性能表现可能产生频繁的开销通常更稳定，但并非必然
使用更多持续占用的内存，换取更少的重复创建、初始化与回收工作。

它追求的不只是平均速度，还可能是运行过程中的稳定性，例如降低游戏运行中因重复分配而出现的帧耗时波动。

03 · HOW

对象池如何实现？

1. 先不要考虑代码，理解对象池需要管理什么

一个最基本的对象池，需要解决四个问题：

  1. 创建（Create）：没有可用对象时，如何产生对象？
  2. 获取（Acquire / Get）：如何把一个空闲对象交给使用者？
  3. 归还（Release / Return）：如何把使用结束的对象重新放入池中？
  4. 销毁（Destroy）：对象太多或对象池结束时，如何清理对象？

为了管理这些行为，对象池一般还需要保存一个集合，用于存储暂时没有被使用的对象。

BulletPool 中的对象示例如何管理
空闲对象Bullet #1、#2、#3存放在空闲集合中
使用中的对象Bullet #4、#5可以只做计数，也可以显式追踪

需要发射子弹时，先从空闲集合获取。子弹结束飞行时，把它归还到空闲集合。这是对象池最基础的实现。

2. 对象池的状态转移

可以从状态机的角度理解对象池。对于某个对象，它有三种主要状态：

  • Available：已经创建，目前空闲，可以被获取。
  • InUse：已经被获取，正在被使用。
  • Destroyed：对象已经被销毁，不再受池管理，是终止状态。
操作前置状态后置状态
Create不存在Available 或 InUse
GetAvailableInUse
ReleaseInUseAvailable
DestroyAvailable 或 InUseDestroyed

这里描述的是概念模型，不意味着所有对象池 API 都支持从 InUse 直接执行销毁。归还时如果超出保留上限，也可能直接销毁。

对象池必须维护的不变量

假设 A 表示正在使用的对象数，I 表示空闲对象数，T 表示池仍然管理的全部存活对象数，那么正常情况下：

T = A ＋ I

而且，对同一个对象而言：

Available ∩ InUse = ∅

一个对象不可能同时处于空闲和使用状态。

如果一个对象既在空闲集合中，又正在被使用，那么对象池就出现了严重错误：另一个使用者可能取得这个仍在工作的对象。

3. Get 与 Release 究竟做了什么？

下面是概念性伪代码。

C# · 示意片段
Bullet Get()
{
    if (idleObjects.Count > 0)
    {
        Bullet bullet = idleObjects.Pop();

        // 标记对象正在使用
        return bullet;
    }

    // 无空闲对象，按策略创建新对象
    return CreateBullet();
}
Get 不是请求创建对象，而是请求获得对象的使用权。

再看 Release()：

C# · 示意片段
void Release(Bullet bullet)
{
    // 验证对象确实由本池借出

    bullet.ResetForPool();

    idleObjects.Push(bullet);
}
Release 不是请求销毁对象，而是声明本次使用已经结束，并交还使用权。

这段代码只是展示基本思想。健壮的实现还需要处理重复归还、归还不属于该池的对象、池容量已满以及并发等问题。

4. 用交互模拟理解对象的复用

04 · UNITY / C#

完整实现示例

Unity 提供了内置对象池：UnityEngine.Pool.ObjectPool<T>。它提供基于栈的复用行为，支持获取、归还、创建、销毁回调及容量管理。下面实现一个可以重复使用的子弹。

1. 子弹对象：PooledBullet.cs

PooledBullet.cs · Unity C#
using System;
using UnityEngine;

public sealed class PooledBullet : MonoBehaviour
{
    private Action<PooledBullet> _returnToPool;

    private Vector3 _direction;
    private float _speed;
    private float _remainingLife;

    private bool _inUse;

    // 每次从对象池获取后，重新初始化
    public void Launch(
        Vector3 position,
        Vector3 direction,
        float speed,
        float lifetime,
        Action<PooledBullet> returnToPool)
    {
        _returnToPool = returnToPool;

        transform.position = position;

        _direction = direction.normalized;
        _speed = speed;
        _remainingLife = lifetime;

        _inUse = true;

        gameObject.SetActive(true);
    }

    private void Update()
    {
        if (!_inUse)
            return;

        transform.position +=
            _direction * _speed * Time.deltaTime;

        _remainingLife -= Time.deltaTime;

        if (_remainingLife <= 0f)
        {
            Finish();
        }
    }

    private void OnTriggerEnter(Collider other)
    {
        if (!_inUse)
            return;

        // 此处可以添加碰撞对象过滤和伤害逻辑
        Finish();
    }

    private void Finish()
    {
        // 防止重复归还
        if (!_inUse)
            return;

        _inUse = false;

        var callback = _returnToPool;
        _returnToPool = null;

        callback?.Invoke(this);
    }

    // 清理上一次使用的业务状态
    public void ResetForPool()
    {
        _inUse = false;
        _returnToPool = null;

        _direction = Vector3.zero;
        _speed = 0f;
        _remainingLife = 0f;

        gameObject.SetActive(false);
    }
}

这里有两点特别重要。

第一，Launch() 每次都会重新设置位置、方向、速度以及生存时间。这保证借用的是干净的对象，而不是继承上一颗子弹的状态。

第二，Finish() 会先设置 _inUse = false，然后再归还。因为物理事件有可能在一次使用过程中多次触发。如果重复归还，就可能破坏对象池的状态。

2. 对象池管理者：BulletPool.cs

BulletPool.cs · Unity C#
using UnityEngine;
using UnityEngine.Pool;

public sealed class BulletPool : MonoBehaviour
{
    [SerializeField]
    private PooledBullet bulletPrefab;

    private ObjectPool<PooledBullet> _pool;

    private void Awake()
    {
        _pool = new ObjectPool<PooledBullet>(
            createFunc: CreateBullet,
            actionOnGet: null,
            actionOnRelease: OnRelease,
            actionOnDestroy: DestroyBullet,
            collectionCheck: true,
            defaultCapacity: 16,
            maxSize: 64
        );
    }

    // 对象池需要一个新实例时调用
    private PooledBullet CreateBullet()
    {
        PooledBullet bullet =
            Instantiate(bulletPrefab, transform);

        bullet.gameObject.SetActive(false);

        return bullet;
    }

    // 对象归还时重置
    private void OnRelease(PooledBullet bullet)
    {
        bullet.ResetForPool();
    }

    // 池不再保留该对象时调用
    private void DestroyBullet(PooledBullet bullet)
    {
        Destroy(bullet.gameObject);
    }

    // 对外提供发射子弹的方法
    public void Fire(
        Vector3 position,
        Vector3 direction)
    {
        PooledBullet bullet = _pool.Get();

        bullet.Launch(
            position,
            direction,
            speed: 10f,
            lifetime: 3f,
            returnToPool: _pool.Release
        );
    }

    private void OnDestroy()
    {
        _pool?.Dispose();
    }
}

示例假定子弹预制体配置了用于触发碰撞的 Collider，并满足 Unity 的物理触发条件。池和子弹由同一场景对象管理，销毁管理者时，其子对象也随 Unity 层级清理。跨场景或长期运行的对象池需要更明确的生命周期管理。

初始化顺序补充

如果预制体默认处于激活状态，Instantiate() 可能先触发 OnEnable()，再执行紧随其后的 SetActive(false)。若要求首次创建时也严格遵守“初始化后激活”，请把子弹预制体根对象保存为未激活状态，并避免在 OnEnable() 中重置刚设置的发射参数。

3. 为什么 actionOnGet 是 null？

这里没有在 actionOnGet 中激活子弹，这是刻意设计的。希望确保以下顺序：

从池中获取 → 设置位置、速度、方向等状态 → 激活 GameObject → 开始工作

如果在 actionOnGet 内部就执行 SetActive(true)，那么 OnEnable() 会在业务初始化之前运行。当 OnEnable() 依赖新的状态时，这可能引发问题。

因此，让业务初始化方法 Launch() 完成设置，并在最后激活对象。

4. 这套实现的职责划分

角色负责什么不负责什么
BulletPool对象创建、保留、归还及销毁子弹的移动和伤害规则
PooledBullet子弹行为、生命周期结束通知、业务状态重置决定池的存储策略
发射者决定何时、何地发射子弹直接创建和销毁子弹

对象池管理资源生命周期，业务对象管理自己的行为。

对象池不一定要是 MonoBehaviour，也不一定要是单例。它可以是普通 C# 类，由上层组件或系统持有。

05 · CORRECTNESS

最容易忽略的正确性问题

性能优化是对象池的目的，但保证对象的正确复用才是实现难点。

1. 归还后，对象还可以使用吗？

C# · 示意片段
Bullet bullet = pool.Get();

pool.Release(bullet);

// 危险：归还后继续操作
bullet.Damage = 100;

这是危险的。因为 Release() 后，对象已经不再属于当前使用者。这时，另一个系统可能通过 Get() 取得相同对象。如果之前的使用者继续修改，就会造成状态污染。

这涉及所有权（Ownership）与借用（Borrowing）：

  • Get() 获得的是一段使用权。
  • Release() 代表放弃这段使用权。
  • 归还后，不应再使用原引用操作对象，除非重新获得合法的使用权。

C# 普通引用本身不会自动强制执行这一约束，需要靠 API 设计、状态检查或借用句柄等机制维护。

2. 重置状态究竟应该重置什么？

假设子弹包含：

C# · 示意片段
public int Damage;
public float Speed;
public Vector3 Direction;

public Transform Target;

public event Action OnHit;

如果只关闭 GameObject，却没有清理这些字段，那么下一次使用时可能产生问题：

  • 沿用上一次的攻击目标。
  • 使用上一次的伤害数值。
  • 调用上一次注册的事件订阅者。
  • 继续执行上一次尚未结束的协程或异步回调。

这类问题称为状态泄漏（State Leakage）。正确的复用必须保证新一次使用不受到上一次业务状态的不合理影响。

Reset(S旧) → S可安全复用

但不要求把所有字段恢复成构造时的原始值。例如，Prefab 中固定不变的 Mesh、材质引用、组件配置，通常可以保留。

清理所有跨使用周期不应保留的可变状态，同时保留可以安全复用的稳定资源。

3. 异步操作会让对象池更复杂

假设对象 A 被获取后，启动一个网络请求。请求还没有完成，对象 A 已经归还对象池，随后被另一个业务重新获取。这时，旧网络请求返回，继续修改对象 A，结果新业务的数据被旧请求污染了。

即使旧请求的回调持有相同的对象引用，也不意味着它仍然有使用权。

一种常见解决方案是使用版本号（Generation）。原理是记录本次使用的标识，并在异步返回后检查标识和使用状态：

C# · 异步检查示意，独立于前面的子弹类
int version = bullet.Generation;

await SomeAsyncOperation();

if (bullet == null ||
    !bullet.IsInUse ||
    bullet.Generation != version)
{
    // 对象已销毁、已归还，或已进入新的使用周期
    return;
}

// 只有仍属于同一次使用，才允许继续处理

此处 Generation 和 IsInUse 是概念接口，前面的基础子弹类未实现它们。每次获取应分配新的版本；归还时须使租约失效，例如设为非使用状态，也可同时推进版本。仅在下次获取时更新版本、却不检查是否仍在使用，无法拦截“已归还但尚未重新借出”的旧回调。

实际实现还需要处理异步取消；Unity 对象检查和修改应在主线程进行。这种技术不局限于对象池，在 UI 请求复用、异步加载、网络任务等场景也很重要。

06 · CAPACITY

对象池应该保留多少对象？

这里需要区分两个不同的容量概念。

容量概念限制什么
最大空闲保留量
Maximum Retained Capacity		最多保留多少个空闲对象
最大总量
Maximum Total Capacity		一共最多允许存在多少个对象，包括正在使用的对象

这两个概念不是一回事。Unity 的 ObjectPool<T> 中，maxSize 限制的是池可保留的空闲对象数量，而不是所有已创建对象的并发总数。如果池已经没有空闲对象，Get() 可以继续创建新对象。

容量示意
maxSize = 64

当前：
使用中 = 100
空闲   = 0
总量   = 100

这种情况仍然可能出现。等到 100 个对象全部归还时，池最多保留 64 个空闲对象，另外 36 个会按清理策略处理。

defaultCapacity 是底层空闲集合的初始容量设置，并不意味着构造对象池时就预先创建了同样数量的子弹。

预热（Prewarming）

如果希望游戏开始时提前创建对象，就需要进行预热。

游戏加载阶段 → 创建预期数量的实例 → 全部放入空闲池 → 正式进入游戏

这相当于提前承担一部分创建成本，避免在游戏进行过程中集中分配。但预热也有缺点：

  • 增加初始加载时间。
  • 提高初始内存占用。
  • 可能创建实际不会使用的对象。

应该根据游戏实际的并发峰值和加载预算选择预热数量，而不是越多越好。

预热时若使用 Get / Release，应先连续 Get 出目标数量，再统一 Release；每次 Get 后立即 Release，往往只会反复复用同一个对象。

07 · WHEN

什么情况下应该使用对象池？

对象类型是否适合原因
大量子弹非常适合数量多、生命周期短、频繁创建
粒子特效适合反复出现，创建成本可能较高
伤害数字 UI适合大量短暂显示，组件结构重复
敌人单位视情况实例化昂贵，但状态清理较复杂
普通小型数据对象通常不必直接创建可能更简单、更快
玩家永久存档数据通常不适合生命周期较长，复用价值不明显
大型临时缓冲区适合分配成本较高，可以复用内存

尤其要避免一种思维误区：“对象池可以优化性能，所以所有对象都应该放进对象池。”

对于一个只包含两个整数的 C# 对象，直接分配可能非常便宜。引入对象池反而需要额外的访问、状态管理和存储成本。

对象池与缓存（Cache）有什么区别？

机制主要关注通常保留的价值
缓存 Cache保留某个计算结果或数据，以便下次直接使用数据或计算结果的价值
对象池 Object Pool复用承载工作的对象或资源，让下一次使用重新执行工作对象的可复用能力

它们都涉及保留资源，但关注点不同：缓存往往保留数据的价值；对象池保留对象的可复用能力。

08 · DEEPER

对象池真正解决的是资源管理问题

对象池看似只是一个性能设计模式，实际上隐含了三个更广泛的软件工程问题。

1. 资源生命周期管理

对象池需要明确：

  • 谁有权创建对象？
  • 谁可以使用对象？
  • 何时认为对象已经使用结束？
  • 谁有责任归还？
  • 谁有责任最终销毁？

如果这些责任不清楚，就容易出现忘记归还、重复归还和对象被提前销毁等问题。

2. 容量与负载管理

如果瞬间有十万个请求需要对象，该怎么办？策略可能包括：

  • 继续创建，允许弹性增长。
  • 拒绝新的请求。
  • 等待空闲对象。
  • 设置并发上限。
  • 回收或替换优先级较低的使用任务。

对于游戏子弹，也许超过视觉预算就跳过某些不重要的表现。对于服务端连接池，则可能需要排队、超时和背压。

对象池本身并不自动等于资源上限控制。上限策略需要明确设计。

3. 性能与正确性的取舍

对象池引入新的状态转换后，必须保证以下性质：

约束目的
同一个对象不能同时借给两个使用者排他使用
同一个对象不能被重复归还避免重复分配
对象必须归还到正确的池维护对象归属
归还后不能继续被旧使用者修改保证使用权边界
新一轮使用不能被上一轮状态污染保证状态隔离
对象池销毁后不能被继续正常使用保证生命周期有效

这也解释了为什么对象池不是简单的 List<GameObject> 或 Stack<T>。集合只是它的存储机制。

真正构成对象池的是围绕对象使用权、生命周期、复用规则和资源容量建立的一组约束。
09 · REVIEW

从 What、Why、How 回到本质

问题核心答案
What将对象的物理生命周期与单次业务使用周期解耦的复用机制
Why减少频繁分配、初始化和回收的开销，改善资源使用与性能稳定性
How通过创建、获取、重置、归还和销毁等操作集中管理对象
核心权衡以额外的内存占用和管理复杂度换取潜在的性能收益
正确性核心对象所有权、状态隔离和生命周期约束

最后值得记住的不是 Get() 或 Release()，而是这句话：

一项工作结束，不代表完成这项工作的资源必须销毁。

一个对象可以长期存在，却先后承担许多次相互独立的工作。对象池把这件事情变成了一套明确、可管理、可验证的机制。

接下来值得深入的三个概念

  1. RAII、IDisposable 与资源所有权：为什么 C# 中的内存、文件、连接以及 Unity 对象的生命周期管理不同？
  2. 池化对象的状态隔离与不变量：如何严格保证重复使用一个对象，不会引入上一次的残留状态？
  3. 对象池、缓存与享元模式（Flyweight）的区别：它们都涉及复用，但复用的究竟是什么？

最建议先理解第二个问题，因为它直接决定对象池能不能可靠工作。

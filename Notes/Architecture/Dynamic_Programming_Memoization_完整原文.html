WHAT · WHY · HOW

Dynamic Programming（动态规划）与 Memoization（记忆化）：从重复计算到状态复用

动态规划的本质，不是某种特殊的算法模板，而是一种组织计算的思想：将问题表示为相互依赖的子问题，并让每个不同子问题的结果尽可能只计算一次。

而 Memoization（记忆化）是实现这种思想的常见技术之一。

这两个概念与你之前学习的缓存（Cache）、依赖图（Dependency Graph）以及增量计算（Incremental Computation）有着非常紧密的联系。

我们按照 What → Why → How → 本质联系 → 设计边界 的顺序，从计算模型本身理解它们。

一、What：什么是动态规划与记忆化？

1.1 动态规划（Dynamic Programming）

动态规划，简称 DP，是一种通过定义子问题、建立子问题之间的递推关系，并复用子问题结果来求解问题的方法。

它的核心可以表达为：

定义状态→建立状态依赖→复用计算结果

比如，你需要解决问题 P。

你发现：

P=F(A,B)

其中：

A=G(C,D)
B=H(C,E)

注意：A 和 B 都依赖 C。

如果分别求解 A 和 B，那么 C 就可能被重复计算。

未复用计算：相同子问题出现在不同计算分支中

两个 C 节点代表同一个子问题被执行了两次。

复用计算：两个分支共享一个子问题结果

逻辑上只有一个 C，计算一次即可供 A、B 使用。

这就是动态规划最重要的观察之一：

递归调用可能形成一棵很大的计算树，但不同调用中真正需要求解的子问题，可能只有很少的几种。

如果能复用这些子问题的答案，就可以减少大量重复工作。

需要注意，动态规划不仅用于优化问题，也可以用于计数、可达性判断、序列匹配等具有合适递推结构的问题。

1.2 什么是 Memoization（记忆化）？

Memoization 是一种缓存计算结果的技术。

假设有一个函数：

y=f(x)

普通函数每次调用都重新计算：

f(10) → 计算 → 返回结果
f(10) → 计算 → 返回结果
f(10) → 计算 → 返回结果

使用记忆化后：

f(10) → 未命中 → 计算 → 保存结果
f(10) → 命中缓存 → 返回结果
f(10) → 命中缓存 → 返回结果

可以用下面的交互来直观理解。

记忆化函数模拟器 (Fibonacci)

当前参数的缓存状态：未缓存

函数结果—
已存状态数0
缓存命中次数0

先调用一次，再以相同参数调用，观察第二次命中缓存。这是按参数存储函数结果的简化演示。

滑块范围：0 至 20；步长：1。已存状态数包括递归中求出的子问题，命中次数包括递归中的缓存查询。

记忆化的抽象公式可以写成：

M(x)={Cache[x]如果缓存命中Cache[x]←f(x)否则计算并保存

但这里存在一个非常关键的正确性条件：

对于同一个缓存键，函数的结果必须在缓存有效期内保持一致。

例如：

int Square(int x) => x * x;

Square(5) 始终返回 25，这种函数非常适合记忆化。

但是：

int GetCurrentHealth()
{
    return player.Health;
}

如果角色生命值会发生变化，那么即使没有参数，函数返回值也可能不同。直接缓存它，就可能得到过期的数据。

这解释了为什么记忆化不仅仅是存一个 Dictionary。

它实际上隐含着一个约束：

相同的有效输入⇒相同的输出

二、Why：为什么记忆化特别适合重叠子问题？

2.1 先理解什么叫重叠子问题（Overlapping Subproblems）

所谓重叠子问题，不是说两个子问题长得相似，而是：

求解一个问题时，不同的计算路径会多次遇到同一个状态的子问题。

用经典的斐波那契数列说明。

F(n)=F(n-1)+F(n-2)

边界条件：

F(0)=0, F(1)=1

比如：

F(5)=F(4)+F(3)

继续展开：

F(4)=F(3)+F(2)
F(3)=F(2)+F(1)

你会发现，F(3)、F(2) 被多次计算。

F(5) 的递归调用树

同色节点代表重复的子问题。图中还省略了 F(2) 下方继续展开的部分。

虽然有很多函数调用，但不同的子问题实际上只有：

F(0),F(1),F(2),F(3),F(4),F(5)

也就是 6 个状态。

这里要区分两种数量：

  • 函数调用次数：原始递归展开后可能出现大量重复调用。
  • 不同子问题的数量：按状态去重之后，真正需要求解的不同问题数。

动态规划主要关心第二个数量。

2.2 没有记忆化，为什么计算量可能指数增长？

考虑最普通的实现：

long Fibonacci(int n)
{
    if (n <= 1)
        return n;

    return Fibonacci(n - 1)
         + Fibonacci(n - 2);
}

每次计算 Fibonacci(n)，都会产生两个递归分支。

其中大量子问题被不断重新展开。

对于这种朴素实现，其运行时间满足近似形式：

T(n)=T(n-1)+T(n-2)+O(1)

时间复杂度为：

T(n)=Θ(φn)

其中：

φ≈1.618

这是指数级增长，通常也可以用较宽松的 O(2n) 来描述。

关键问题不是加法很慢，而是：

程序没有区分“新的计算需求”和“已经求解过的计算需求”。

因此，相同的工作被无意义地重复执行。

2.3 使用记忆化，为什么复杂度会下降？

假设我们给每个 F(k) 都保存一次计算结果。

那么：

第一次需要 F(3)：
    计算 F(3)
    保存 F(3)

第二次需要 F(3)：
    直接读取结果

只要 F(3) 已经计算完成，不论后续哪个递归分支再次需要它，都无需重新计算。

于是：

原始调用树 ⟶ 去重后的子问题依赖图

斐波那契数列中，最多只有 n+1 个不同状态：

F(0),F(1),…,F(n)

每个状态只需要常数次转移计算。

因此：

T(n)=O(n)

这是从指数时间到线性时间的变化。

比较朴素递归实际函数调用次数与记忆化算法按不同状态计数的首次求解次数；不包括缓存查找调用。

记忆化仍会产生少量用于查询缓存的函数调用；图中绿色概念对应首次求解的不同状态数，不代表全部函数调用次数。

这里得到一个更一般的结论：

设：

  • U：真正需要求解的不同子问题数量。
  • C：每个子问题的平均计算及转移成本。

那么在缓存操作近似为常数时间且依赖无环时，记忆化算法的时间复杂度通常可以表示为：

O(U·C)

更一般地，如果将子问题表示为依赖图，图中有 V 个状态节点和 E 条需要处理的依赖边，那么在每条依赖只处理常数次时：

O(V+E)

这才是记忆化真正的价值：

它把计算成本从“展开递归时执行了多少次”转变为“有多少个不同状态，以及它们有多少需要处理的依赖”。

这也正是依赖图与动态规划在思想上的交汇点。

三、How：如何从普通递归设计出动态规划？

要理解动态规划，最重要的不是先学习 DP 数组怎么写，而是学会发现和定义状态。

我建议按照以下五个步骤思考。

3.1 第一步：定义状态（State）

状态代表一个可以被独立求解、并且答案能够被复用的子问题。

例如斐波那契：

State(n)=F(n)

这里 n 唯一确定了需要解决的问题。

因此可以用 n 作为缓存键。

但如果是背包问题，状态可能是：

State(i,c)

其中：

  • i：接下来可以考虑的物品位置。
  • c：剩余容量。

这时只使用 c 作为缓存键就是错误的，因为不同的 i 可能意味着可选物品不同，即使剩余容量相同，答案也可能不同。

状态设计的核心要求：状态必须包含所有会影响子问题答案的信息。

形式上，如果：

StateA=StateB

那么必须能够保证：

Answer(StateA)=Answer(StateB)

这里的相等指的是求解所需信息在语义上的相等，而不只是某几个字段碰巧相等。

3.2 第二步：定义状态转移（Transition）

状态转移描述当前问题如何依赖更小的子问题。

斐波那契的状态转移是：

F(n)=F(n-1)+F(n-2)

但状态转移不一定是加法。

例如：

DP(s)=min(DP(s1),DP(s2))+1

可以表示某种最少操作次数问题。

DP(s)=DP(s1)∨DP(s2)

可以表示某种可达性判断问题。

所以动态规划不局限于求最小值或最大值。

它关注的是：能否通过其他状态已经求出的结果，正确地计算当前状态。

3.3 第三步：定义终止条件（Base Case）

不能无限分解子问题。

我们需要定义一些可以直接求解的状态。

例如：

F(0)=0, F(1)=1

这两个状态不依赖其他状态。

因此，它们成为整个依赖计算的起点。

一个有效的普通动态规划递推通常需要满足：

  1. 状态含义明确。
  2. 转移关系正确。
  3. 存在可以直接求解的边界状态。
  4. 依赖能够最终到达边界，通常形成无环依赖图。

如果递归依赖存在循环，那么单纯加一个缓存并不能保证算法正确或终止。

3.4 第四步：利用记忆化避免重复计算

下面用 C# 实现记忆化。

public static long FibonacciMemo(int n)
{
    if (n < 0 || n > 92)
        throw new ArgumentOutOfRangeException(nameof(n));

    var memo = new Dictionary<int, long>
    {
        [0] = 0,
        [1] = 1
    };

    return Solve(n);

    long Solve(int k)
    {
        // 已求解过，直接复用
        if (memo.TryGetValue(k, out long cached))
            return cached;

        // 首次求解：依赖更小的子问题
        long result = Solve(k - 1) + Solve(k - 2);

        // 保存本次计算结果
        memo[k] = result;

        return result;
    }
}

这里把输入限定在 0～92，是因为更大的 Fibonacci 数值无法用有符号 long 准确表示。

请重点观察 Solve() 的行为：

Solve(k)

缓存是否包含 k？

是（命中）

直接返回结果

否（未命中）

递归计算子问题

保存并返回结果

它的执行策略可以概括为：

Solve(s)={Memo[s]已计算Combine(Solve(s1),…)尚未计算

注意，Memoization 并没有改变状态转移的数学意义，只改变了计算的执行策略。

我们仍然在计算同一个函数，得到同一个结果，只是不再重复进行已经完成的子计算。

3.5 第五步：也可以不用递归，自底向上计算

动态规划还有一种典型写法：Tabulation（制表法）。

思路是先求小问题，再求大问题：

public static long FibonacciBottomUp(int n)
{
    if (n < 0 || n > 92)
        throw new ArgumentOutOfRangeException(nameof(n));

    if (n <= 1)
        return n;

    long prev2 = 0; // F(0)
    long prev1 = 1; // F(1)

    for (int i = 2; i <= n; i++)
    {
        long current = prev1 + prev2;

        prev2 = prev1;
        prev1 = current;
    }

    return prev1;
}

为什么这也是动态规划？

因为它依然遵循同一个状态转移：

F(i)=F(i-1)+F(i-2)

不同的是，它按照依赖顺序主动计算所有必需的状态。

比较 自顶向下 + 记忆化 自底向上
计算方向 从目标状态递归寻找依赖 从边界状态逐步计算
状态计算 按需计算 按安排好的顺序计算
典型存储 Dictionary 或数组 DP 数组或滚动变量
递归调用栈 通常需要 通常不需要
适合场景 只需要部分可达状态 依赖顺序明确、状态密集
Fibonacci 时间 O(n) O(n)
Fibonacci 额外空间 O(n) 上面滚动变量实现为 O(1)

这里有一个重要认识：

记忆化与自底向上不是两种不同的数学问题求解方法，而是针对同一状态依赖关系的两种求值策略。

四、进一步理解：为什么动态规划适合解决最优化问题？

前面的 Fibonacci 只是计算一个确定的数值。

真正理解动态规划，还需要看它如何解决“最优选择”。

4.1 示例：最少硬币数量

假设有无限数量的硬币，面值分别为：

Coins={1,3,4}

现在要凑出金额 6。

希望使用的硬币数量最少。

例如：

4+1+1=6

使用了 3 枚硬币。

但：

3+3=6

只需要 2 枚。

因此正确答案是 2。

这里不能简单地每次都选择面值最大的硬币，因为局部贪心选择不一定得到全局最优解。

4.2 怎样定义动态规划状态？

令：

DP(x)=凑出金额 x 所需的最少硬币数

现在思考如何得到 DP(6)。

如果第一枚硬币选 1，那么剩余问题是：

1+DP(5)

如果第一枚硬币选 3：

1+DP(3)

如果第一枚硬币选 4：

1+DP(2)

既然目标是最小数量，那就选择这三个候选值中最小的：

DP(6)=1+min(DP(5),DP(3),DP(2))

更一般地：

DP(x)=1+minc∈Coins,c≤xDP(x-c)

边界：

DP(0)=0

无法凑出的状态记为无穷大。

这就是状态转移方程。

4.3 为什么这个状态转移是正确的？

这里涉及动态规划解决优化问题时经常要求的性质：

最优子结构（Optimal Substructure）。

假设某个凑出金额 x 的最优解，选择了面值 c 作为第一枚硬币。

那么剩余的 x-c 部分也必须使用最少的硬币。

为什么？

假设剩余部分不是最优的。

那么我们就可以用另一种硬币更少的组合替换它。

替换后，总硬币数量会进一步减少。

这与原本的解已经是最优解矛盾。

因此，最优解包含相应子问题的最优解。

这里要区分两个性质：

性质 解决什么问题
最优子结构 能否通过子问题的最优解正确构造整体最优解
重叠子问题 求解过程中是否会反复遇到相同的子问题

它们并不等价。

最优子结构主要支撑优化问题的状态转移正确性，而重叠子问题主要解释记忆化为什么能提高效率。

动态规划还有很多非优化应用，这些应用需要的是正确、可组合的递推关系，并不一定涉及“最优”这个概念。

4.4 使用记忆化实现最少硬币问题

public static int MinCoins(int[] coins, int amount)
{
    if (coins == null)
        throw new ArgumentNullException(nameof(coins));

    if (amount < 0)
        throw new ArgumentOutOfRangeException(nameof(amount));

    foreach (int coin in coins)
    {
        if (coin <= 0)
            throw new ArgumentException(
                "Coin values must be positive.");
    }

    // 比任何可行最优解都大的哨兵值
    int impossible = amount + 1;

    int?[] memo = new int?[amount + 1];

    int Solve(int remaining)
    {
        // 凑出 0 元不需要硬币
        if (remaining == 0)
            return 0;

        // 已经计算过，直接复用
        if (memo[remaining].HasValue)
            return memo[remaining].Value;

        int best = impossible;

        foreach (int coin in coins)
        {
            if (coin > remaining)
                continue;

            int subResult = Solve(remaining - coin);

            if (subResult != impossible)
            {
                best = Math.Min(best, subResult + 1);
            }
        }

        memo[remaining] = best;

        return best;
    }

    int result = Solve(amount);

    return result == impossible ? -1 : result;
}

这个示例假定金额在实际可分配数组的范围内，且 amount + 1 不溢出 int；生产代码应另行处理极端输入与资源限制。

调用：

int result = MinCoins(new[] { 1, 3, 4 }, 6);
// result == 2

观察它的三个重要特征：

  1. remaining 是状态，也是记忆化缓存键。
  2. Solve(remaining - coin) 建立子问题依赖。
  3. memo[remaining] 保存最优解，使其他计算路径能够复用。

假设目标金额为 A，硬币面值种类为 K。

最多只有 A+1 个不同状态，每个状态至多尝试 K 种硬币。

因此：

T(A,K)=O(AK)

空间复杂度，包括缓存与递归栈，为：

S(A)=O(A)

这也说明：动态规划的复杂度通常取决于状态空间的大小和转移成本，而不仅仅是递归深度。

五、直击本质：动态规划与缓存、依赖图、增量计算究竟是什么关系？

这部分是把这些知识连接起来的关键。

5.1 从依赖图理解 DP

可以把每一个状态看成一个节点：

DP(s)

如果计算状态 A 必须使用状态 B 的结果，就建立一条依赖关系：

A→B

于是整个问题变成一张状态依赖图。

对于普通无环动态规划，它是一张 DAG（有向无环图）。

这时：

  • 状态定义决定图中有哪些节点。
  • 状态转移决定节点之间的边。
  • Memoization 保存已经求解的节点结果。
  • 自底向上 DP 按照依赖先于使用者的拓扑顺序计算。
  • 最终答案来自目标节点的求值结果。

记忆化通过复用相同节点的结果，避免在不同依赖路径中重复展开它们。

5.2 与普通缓存的区别

你之前探讨过对象池与缓存，以及缓存为什么能避免重复获取或计算。

Memoization 本质上就是一种专门针对函数求值结果的缓存策略。

但两者的侧重点不同。

普通缓存可能缓存：

  • 网络请求结果。
  • 文件内容。
  • 数据库查询结果。
  • 已构建的资源。
  • 函数计算结果。

记忆化通常特指最后一种，即按有效输入缓存函数的输出。

所以我们可以说：

Memoization 是计算结果缓存的一种形式

但不能反过来说所有缓存都是 Memoization。

同时，使用了 Memoization 的程序也不一定是动态规划。

例如某个复杂数学函数被重复调用，即使内部完全没有递归子问题，也可以记忆化。

5.3 与增量计算的区别

考虑：

C=A+B
D=C×2

如果 C 已经求出，后续计算 D 时直接复用 C，这类似记忆化。

但假如 A 发生变化：

A←A'

那么 C 和 D 的旧结果就可能不再正确。

增量计算进一步关心：

当输入发生变化时，哪些已有结果仍然有效，哪些需要重新计算？

可以理解为：

记忆化关心

这个状态算过吗？

算过且有效 → 复用

增量计算关心

这个状态受影响了吗？

受影响 → 更新必要部分

因此，两者可以结合：

依赖图+记忆化+失效追踪

就能构成一种支持结果复用和选择性重算的计算系统。

不过，经典 DP 通常是在输入固定的一次求解过程中运行，并不需要处理输入持续变化的问题。

如果将 DP 的状态缓存跨越不同输入版本复用，就必须考虑正确的缓存键或失效机制。

5.4 结合 Unity 的实际场景

例如游戏中的某个技能系统需要计算：

角色基础属性
      ↓
装备属性修正
      ↓
角色最终属性
      ↓
技能伤害结果

如果装备属性、角色等级、Buff 都不变，那么技能伤害相关的纯计算结果有可能复用。

但如果角色装备发生变化，相关缓存也必须失效。

这个场景主要属于缓存与增量计算，而不必然属于动态规划。

只有当技能计算能够拆分成具有合适递推结构的状态子问题，并通过子问题结果组合求解时，才有理由把它建模为 DP。

不要因为一个系统有缓存和依赖关系，就认为它一定是动态规划。

六、什么时候应该使用 Memoization？什么时候不应该？

记忆化不是免费的。它通过增加存储和管理成本，换取重复计算的减少。

情况 是否适合记忆化 原因
同一子问题频繁出现 非常适合 重复计算可被消除
单次计算成本高 往往适合 缓存命中收益大
不存在重复子问题 通常收益较低 缓存本身有额外成本
状态空间非常大 需要权衡 缓存可能消耗大量内存
结果依赖可变外部状态 需要额外设计 可能出现过期缓存
结果依赖随机数或时间 不能直接按原参数缓存 相同参数不保证相同结果
子问题之间存在循环依赖 不能只靠普通记忆化 需要另外处理循环或求解不动点

特别需要关注三个容易犯错的地方。

6.1 缓存键不完整

例如背包状态为：

DP(i,capacity)

却只缓存：

Dictionary<int, int> memo;

其中键只有 capacity。

这样会把本来不同的状态错误地当成同一个状态。

正确的缓存键应该涵盖所有会影响结果的输入，例如：

Dictionary<(int index, int capacity), int> memo;

6.2 把可变状态当成稳定输入

例如：

int ComputeDamage(int skillId)
{
    return GetSkillPower(skillId) * player.Attack;
}

即使 skillId 相同，只要 player.Attack 改变，结果就会改变。

此时只使用 skillId 作为缓存键并不安全。

可以将攻击力或相应配置版本纳入缓存键，也可以在属性变化时失效相关缓存。

6.3 忘记递归依赖的终止性

例如错误地定义：

DP(x)=DP(x)+1

使用 Dictionary 不会自动解决这个问题。

因为第一次计算 DP(x) 时，还没有得到可以缓存的结果，递归就会再次要求计算 DP(x)。

所以普通 DP 的正确性不仅依赖缓存，还依赖一个可终止、定义良好的递推关系。

七、把整个知识体系统一起来

你可以从四个抽象层次来理解：

第一层 · 计算结构

Dependency Graph（依赖图）

描述哪个结果依赖哪个结果

第二层 · 求解模型

Dynamic Programming（动态规划）

通过正确的状态转移组合子问题结果

第三层 · 复用机制

Memoization（记忆化）

保存状态结果，避免重复求解

第四层 · 变化管理（可选扩展）

Incremental Computation（增量计算）

当输入变化时，保留有效结果并更新受影响部分

这是一种理解它们之间联系的抽象视角，并不代表这些技术必须按这样的顺序组合使用。

最终总结：只记住五句话

  1. 动态规划的核心是状态及其递推关系。 它通过复用子问题的答案，避免重复求解。
  2. 重叠子问题意味着不同计算路径重复遇到同一子问题。 这是记忆化通常能显著提速的根本原因。
  3. 记忆化是按状态缓存计算结果。 它不改变结果的数学定义，只改变计算执行方式。
  4. 动态规划的优化收益来自状态去重。 从重复展开计算树，转变为对不同状态及其依赖进行求值。
  5. 缓存正确性依赖状态完整性、结果稳定性和失效管理。 错误的缓存键会破坏整个算法的正确性。

最值得记住的统一表达式是：

状态决定什么是同一个问题转移决定如何求解问题记忆化决定是否需要重复求解

而对于你的架构学习，可以再往深一层思考：

当你发现程序重复执行某项工作时，先不要急着使用缓存，而是先问：什么信息唯一决定这项工作的结果？

这个问题迫使你识别真正的状态、依赖与计算边界。

它不仅是动态规划的起点，也是设计正确缓存、增量计算和复杂计算系统的重要基础。

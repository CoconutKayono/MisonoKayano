图（Graph）：What、Why、How，直击本质

这里的“图”指计算机科学和图论中的 Graph（图结构），而不是图片。

先给出最重要的结论：

图的本质，是将一组事物及其之间的关系显式地表示出来，使我们能够对这些关系进行查询、遍历、推理和计算。

图最值得理解的不是节点和边怎么存储，而是：为什么只要明确了事物之间的关系，就能够解决依赖计算、执行顺序、路径搜索、循环检测、影响范围分析等看似不同的问题？

一、What：图究竟是什么？

1. 图的数学定义

一个图通常表示为：

G=(V,E)

其中：

  • V：Vertex 的集合，称为顶点（Vertex），也叫节点（Node）。
  • E：Edge 的集合，称为边，描述节点之间的关系。

例如：

四个节点、四条边的无向图

对应的数学结构为：

V={A,B,C,D}
E={{A,B},{A,C},{B,D},{C,D}}

请注意：

图并不关心节点在画面上的位置，而是关心节点之间存在哪些关系。

即使改变 A、B、C、D 的位置，只要它们之间的连接关系不变，在图论意义上描述的仍然是同一个结构（准确说，是同构的图）。

因此，图首先是一个数学关系模型，其次才是可以被绘制出来的东西。

2. 节点和边到底是什么？

节点表示什么，边表示什么，完全由你建模的问题决定。

场景 节点代表 边代表
地图导航 城市、路口 道路
社交网络 用户 好友关系
游戏技能树 技能 前置解锁关系
任务调度 任务 先后依赖
编译器 代码模块 导入或调用关系
响应式 UI 数据或计算 值的依赖关系
状态机 状态 允许的状态转移
游戏寻路 可通行位置 可移动的连接

这些问题表面上没有关联。

但是将具体含义抽掉后，都能够简化成一个共同的问题：

存在哪些实体？哪些实体之间存在关系？这些关系允许我们做什么？

这就是图具有广泛适用性的原因。

3. 有向图与无向图

无向图

A 与 B 存在双向对称关系

有向图

A 指向 B，不代表 B 指向 A

对于有向图：

(A,B) ∈ E

并不意味着：

(B,A) ∈ E

例如技能树中，必须先学习技能 A 才能够学习技能 B，这种关系具有方向性。

但两名玩家互为好友，通常可以使用无向边表示。

方向不是图的绘制细节，而是关系本身的语义。

4. 带权图（Weighted Graph）

边不仅能够描述是否存在关系，还能够携带数值。

例如：

边的权重可以代表距离、时间、代价、容量等

如果权重代表距离：

  • A 到 C 的直接距离为 12。
  • A 到 B 为 5。
  • B 到 C 为 3。

那么 A → B → C 的总距离为：

5+3=8

小于直接路径的 12。

于是，图不仅表达了连接关系，还允许我们计算最优路径。

但要注意，权重并不一定是距离。它也可能代表耗时、风险、费用、网络延迟等。

5. 图的几个基本概念

概念 本质
邻接（Adjacency） 两个节点之间存在直接连接
路径（Path） 按边连续经过的一系列节点
可达性（Reachability） 是否存在从一个节点到另一个节点的路径
环（Cycle） 沿边出发，可以形成回路
入度（In-degree） 有向图中指向该节点的边数
出度（Out-degree） 有向图中从该节点指出的边数
连通性（Connectivity） 节点之间是否能够通过路径相互连接；有向图还需区分强、弱连通

这里需要特别理解可达性。

假设：

A → B → C

虽然 A 和 C 之间没有直接边，但是 A 可以通过 B 到达 C。

这意味着图可以表达两种不同层次的关系：

直接关系和通过关系链形成的间接关系。

从 A 出发沿着有向边能够到达的所有节点，构成它的可达集合。这正是依赖影响范围分析的基础。

二、Why：为什么需要图？

1. 因为很多问题的核心不是对象，而是关系

假设游戏里有四个系统：

  • 背包系统
  • 角色属性系统
  • 战斗力系统
  • UI 系统

仅仅定义四个对象，并没有解释这些系统之间究竟如何关联。

但如果我们知道：

箭头表示上游数据会影响下游结果，是数据依赖关系，而不一定是代码直接调用关系。

我们立即可以回答：

如果装备发生变化，哪些结果可能受到影响？

答案可以沿图中的边推导出来。

这就是图的一个核心价值：

把隐含在代码中的关系变成可以分析、可以操作的数据。

图不会自动消除耦合，也不会自动保证正确性，但它使依赖关系更容易被检查和管理。

2. 因为关系的组合能够产生复杂结构

考虑三种结构：

线性结构

树形结构

一般图结构

线性结构适合表达顺序。

树适合表达严格的层级。

图适合表达任意连接关系。

在通常的简单图模型中，一棵树可以被看作一种特殊的图：连通、无环。对于有向的根树，还会规定父子方向和父节点关系。

而一般图允许多个来源汇聚、一个节点影响多个目标，甚至允许形成环。

因此：

树是一类受约束的图

但并不是所有图都是树。

3. 因为图能够把不同问题转换为标准算法问题

例如：

寻找最短道路，本质是求最短路径。

判断技能能否解锁，本质是可达性和先决条件检查。

判断系统之间是否存在循环依赖，本质是环检测。

求一组任务的合法执行顺序，本质是拓扑排序。

计算某个数据变化会影响哪些计算结果，本质是从变化节点开始进行可达性遍历。

当问题被正确地建模为图后，我们可以直接使用成熟的图算法，而不必为每个业务场景从头发明解决方法。

三、How：如何在程序中表示和操作图？

1. 图的存储方式

最常见的是邻接表（Adjacency List）和邻接矩阵（Adjacency Matrix）。

假设有向图：

A → B,　 A → C,　 B → D

邻接表可以表示为：

A: [B, C]
B: [D]
C: []
D: []

例如 C#：

Dictionary<string, List<string>> graph = new()
{
    ["A"] = new() { "B", "C" },
    ["B"] = new() { "D" },
    ["C"] = new(),
    ["D"] = new()
};

邻接矩阵则把节点间的关系编码成二维矩阵：

邻接矩阵（行 → 列）
ABCD
A0110
B0001
C0000
D0000

其中 1 表示存在从行节点指向列节点的边，0 表示不存在。

对比 邻接表 邻接矩阵
空间复杂度 O(V+E) O(V2)
枚举一个节点的邻居 高效，通常 O(deg(v)) O(V)
检查指定边是否存在 取决于邻居容器 O(1)
适用场景 稀疏图 稠密图、小规模固定图

如果邻接表使用 HashSet 存储邻居，则边存在性检查的平均时间通常可以达到 O(1)。

选择哪种数据结构，取决于你经常对关系做什么操作，而不是哪一种结构更高级。

2. 遍历：图算法最基础的能力

图的许多高级算法，都建立在两个基本遍历策略之上。

BFS：广度优先搜索

先处理距离起点较近的节点，再逐层向外扩展。

A → B、C → D、E、F

核心数据结构：Queue（队列）

DFS：深度优先搜索

沿一条路径持续深入，无法继续后再回溯。

A → B → D → 返回 → C

核心数据结构：Stack（栈）或递归

BFS 常用于无权图的最短路径、层级搜索和可达性。

DFS 常用于环检测、连通分量分析和图结构探索。

采用邻接表并正确记录已经访问的节点时，两者完整遍历的时间复杂度通常都是：

O(V+E)

这里还有一个非常关键的区别：

在树的遍历中，如果从根向下，每个节点只有唯一的父路径，一般不会重复访问。

而图可能有不同路径到达同一个节点。

例如：

A → B → D
A → C → D

如果不记录访问状态，就可能多次处理 D。

如果图还存在环：

A → B → C → A

甚至可能无限遍历。

因此，图遍历必须认真处理已经访问的节点、重复路径和环。

四、图如何解决依赖计算？

这是图在软件架构、缓存、动态规划和响应式编程中的重要用途。

1. 从一个具体问题开始

假设角色有如下属性：

Attack=BaseAttack+EquipmentBonus
DPS=Attack × AttackSpeed

并且 UI 需要显示 Attack 和 DPS。

那么我们得到依赖图：

图中 A → B 的语义是：B 的结果依赖 A。箭头从前置数据指向依赖它的计算。

现在假设 EquipmentBonus 变化。

我们不需要重新计算全部数据。

只要从 EquipmentBonus 开始沿着边查找，即可得到受影响的节点：

EquipmentBonus → Attack → DPS

以及相关 UI。

而 AttackSpeed 本身不需要重新计算。

图把一个原本模糊的问题——“到底哪些数据需要更新？”——转换成了一个明确的图遍历问题。

2. 脏标记与图的关系

Dependency Graph 负责描述依赖关系。

Dirty Flag 负责描述某个结果是否需要重新计算。

二者解决的是不同的问题。

假设装备变化：

第一步，根据图进行影响传播：

EquipmentBonus: Changed
Attack:         Dirty
DPS:            Dirty
Attack UI:      Dirty
DPS UI:         Dirty

第二步，在合适的时机重新计算：

Recalculate Attack
       ↓
Recalculate DPS
       ↓
Refresh UI

但这里出现了新问题：

既然 Attack 和 DPS 都需要重新计算，谁应该先执行？

答案是先计算被依赖的节点，再计算依赖它的节点。

这就引出了拓扑排序。

3. DAG 与拓扑排序

DAG 是 Directed Acyclic Graph，即有向无环图。

它同时满足两个特性：

  • 有向：边具有方向。
  • 无环：不存在沿着有向边回到出发节点的路径。

对于一个 DAG，可以进行拓扑排序（Topological Sort）。

拓扑排序的目标是找到一个节点的线性顺序，使每一条边：

u → v

都满足：

u 出现在 v 之前

例如：

A → C,　 B → C,　 C → D

合法顺序可以是：

A → B → C → D

也可以是：

B → A → C → D

拓扑排序不要求只有一种答案，它要求依赖约束被满足。

一种常用方法是 Kahn 算法：

  1. 计算每个节点的入度。
  2. 将所有入度为 0 的节点加入队列。
  3. 取出节点，加入结果，并移除它对后续节点的入度贡献。
  4. 如果有新的入度为 0 的节点，将其加入队列，重复处理。
  5. 如果最终处理节点数小于总节点数，说明存在有向环。

这就是许多任务调度器、构建系统和依赖计算系统的基础。

五、How：使用 C# 实现一个简单依赖图

下面用一个精简的 C# 实现说明其核心工作方式。

约定：

AddEdge(A, B) 的意思是 B 依赖 A，A 发生变化可能影响 B。

using System;
using System.Collections.Generic;

public sealed class DependencyGraph
{
    // 节点 -> 依赖它的后续节点
    private readonly Dictionary<string, HashSet<string>> next
        = new();

    public void AddNode(string id)
    {
        if (!next.ContainsKey(id))
            next[id] = new HashSet<string>();
    }

    public void AddEdge(string from, string to)
    {
        AddNode(from);
        AddNode(to);
        next[from].Add(to);
    }

    // 查找变化节点及其所有受影响的后代节点
    public HashSet<string> FindAffected(string changed)
    {
        var affected = new HashSet<string>();
        if (!next.ContainsKey(changed))
            throw new ArgumentException("Unknown node", nameof(changed));

        var stack = new Stack<string>();
        stack.Push(changed);

        while (stack.Count > 0)
        {
            string current = stack.Pop();

            if (!affected.Add(current))
                continue;

            foreach (string dependent in next[current])
                stack.Push(dependent);
        }

        return affected;
    }

    // 对受影响的子图进行拓扑排序
    public List<string> TopologicalOrder(
        HashSet<string> affected)
    {
        var indegree = new Dictionary<string, int>();

        foreach (string node in affected)
            indegree[node] = 0;

        foreach (string from in affected)
        {
            foreach (string to in next[from])
            {
                if (affected.Contains(to))
                    indegree[to]++;
            }
        }

        var ready = new Queue<string>();

        foreach (var pair in indegree)
        {
            if (pair.Value == 0)
                ready.Enqueue(pair.Key);
        }

        var order = new List<string>();

        while (ready.Count > 0)
        {
            string node = ready.Dequeue();
            order.Add(node);

            foreach (string to in next[node])
            {
                if (!affected.Contains(to))
                    continue;

                indegree[to]--;

                if (indegree[to] == 0)
                    ready.Enqueue(to);
            }
        }

        if (order.Count != affected.Count)
            throw new InvalidOperationException("Dependency cycle");

        return order;
    }
}

使用方式：

var graph = new DependencyGraph();

graph.AddEdge("EquipmentBonus", "Attack");
graph.AddEdge("BaseAttack", "Attack");
graph.AddEdge("Attack", "DPS");
graph.AddEdge("AttackSpeed", "DPS");
graph.AddEdge("Attack", "AttackUI");
graph.AddEdge("DPS", "DPSUI");

// 装备变化后，找到受影响的节点
var affected = graph.FindAffected("EquipmentBonus");

// 找到合法的更新顺序
var order = graph.TopologicalOrder(affected);

foreach (var id in order)
{
    Console.WriteLine(id);
}

可能输出：

EquipmentBonus
Attack
AttackUI
DPS
DPSUI

输出顺序可能不同，但只要遵守依赖约束就是合法的。

需要注意，这段代码只负责图管理、影响范围查询和排序，没有负责真正执行计算，也没有存储属性结果。

在真实项目中，通常还需要将节点标识映射到计算函数、缓存值和脏标记。对于有环的依赖图，需要在建图时验证无环，或者采用能够处理循环依赖的专门机制。

六、图与动态规划、记忆化之间有什么关系？

这里存在一个非常值得理解的联系。

考虑斐波那契递归：

F(n)=F(n-1)+F(n-2)

如果计算 F(5)，会产生如下递归调用：

F(5)
├── F(4)
│   ├── F(3)
│   │   ├── F(2)
│   │   └── F(1)
│   └── F(2)
└── F(3)
    ├── F(2)
    └── F(1)

可以发现，F(3) 和 F(2) 被重复求值。

递归调用展开看起来像一棵树，但是如果我们按“相同子问题”合并节点，它实际上可以被理解为一张有向无环依赖图。

示意图：合并相同子问题后的依赖结构。箭头表示当前问题会递归求解哪些子问题，方向与前面增量计算例子的箭头约定相反。

这里有两个核心概念：

重叠子问题（Overlapping Subproblems）：不同的计算路径最终要求解同一个子问题。

记忆化（Memoization）：同一个子问题只计算一次，之后复用已经缓存的结果。

如果把子问题视为图中的节点，那么记忆化相当于：

当多个计算路径到达同一个节点时，复用该节点已有的结果，而不是重复展开计算。

对于 Fibonacci，朴素递归的时间复杂度是指数级的。

通过记忆化或者自底向上的动态规划，可以把时间复杂度降低到：

O(n)

因为不同的 Fibonacci 子问题只有 n+1 个（从 F(0) 到 F(n)）。

这揭示了图与动态规划之间更深层的联系：

动态规划可以理解为沿着子问题依赖关系，对每个不同子问题进行有序求值并复用结果。

但并非所有图都能直接用动态规划处理。依赖有环时，可能需要重新定义状态、打破循环依赖，或者求解不动点。

七、常见图算法：它们分别在回答什么问题？

算法 核心问题 常见用途
BFS 从起点按层搜索，哪些节点可达？ 无权最短路径、层级探索
DFS 沿路径深入能找到什么？ 环检测、连通性分析
拓扑排序 如何满足所有先后依赖？ 编译、任务调度、计算图
Dijkstra 非负权图的最短路径是什么？ 地图导航、低成本路由
A* 如何利用启发式信息优先搜索目标？ 游戏寻路
Bellman–Ford 带负权边时如何求最短路径？ 检测可达的负权环
强连通分量（SCC） 哪些节点可以相互到达？ 依赖环分析、程序分析
最小生成树（MST） 如何用最低总权重连接所有节点？ 网络铺设、线路规划

这些算法不是互相替代的关系，而是针对不同的图问题提出的不同方法。

学习图时，建议先判断自己究竟要问什么问题，再选择算法，而不是先记住一堆算法名称。

八、深入本质：图为什么能够处理复杂系统？

现在我们把抽象层次再提高一点。

1. 图把实体与关系分离了

设系统中的所有实体为：

V={v1,v2,…,vn}

将实体间的关系表示为：

E ⊆ V × V

这意味着系统不再必须将所有依赖关系写死在具体对象内部。

我们可以把关系作为独立的数据进行维护。

于是程序能够对关系本身执行算法，而不仅仅是调用对象的方法。

例如，我们能够回答：

“如果删除某个模块，会影响到哪些模块？”

“如果某个缓存失效，哪些计算结果应该重新生成？”

“如果任务 A 尚未完成，哪些任务不能执行？”

这些问题的共同点是，它们关注的是关系结构及其传播结果。

2. 图能够表达局部变化的全局影响

假设整个系统有一万个节点。

其中某个节点的变化，仅影响后续的二十个节点。

如果缺少依赖图，你可能不得不重新检查所有节点。

而有了图，就能够从发生变化的位置开始，只遍历可达的相关节点。

在邻接表上，影响范围遍历通常与实际访问的节点数和边数成正比。

对于适合进行增量更新的系统，这能够显著减少不必要的工作。

但请注意：

图只负责告诉我们可能影响谁。

Dirty Flag 负责标记哪些结果失效。

版本号可以帮助判断某份结果是否还是当前版本。

缓存负责保存可复用的结果。

调度器负责决定什么时候真正执行计算。

这几个机制经常协同工作，但不是同一个概念。

3. 有环不代表图设计错误

这是一个非常重要的辨析。

对于计算依赖图：

A 依赖 B
B 依赖 A

可能意味着循环依赖，导致无法直接拓扑排序。

但对于状态机：

Idle → Running → Idle

形成环是完全正常的，甚至是业务必需的。

对于社交网络，环同样正常。

所以：

环是否合法，不是图论单独决定的，而是由业务关系的语义决定的。

有些问题要求 DAG，有些问题天然需要一般有向图，还有些问题需要无向图。

4. 图并不自动等于依赖管理系统

一个完整的依赖管理系统还要解决：

  • 如何发现和登记依赖关系，包括运行时会变化的依赖。
  • 如何处理数据失效和缓存更新。
  • 如何保证计算过程中不会读取不一致的数据。
  • 如何处理循环依赖、重复传播和计算失败。

图只是其中的基础结构。

因此，正确的架构思考方式是：

先利用图准确建模关系，再在图上设计满足业务正确性要求的计算、缓存和调度机制。

九、最终归纳：用 What、Why、How 记住图

维度 直击本质
What 图是对实体及实体间关系的数学建模
Why 许多复杂问题的核心不是实体本身，而是实体之间的连接、依赖和路径
How 用节点和边记录关系，借助遍历、搜索、排序等算法分析和操作这些关系

还可以进一步将它压缩成三个问题：

第一层：建模

什么东西应该成为节点？什么关系应该成为边？

第二层：推理

从某个节点出发，沿着关系可以到达哪里？存在哪些约束？

第三层：计算

如何以正确的顺序和最小的必要代价完成任务？

最后需要真正建立的认知是：

图不是一个需要单独记忆的数据结构，而是一种看待系统的方法。

当你开始从“有哪些对象和方法”，转向思考“这些对象之间存在什么关系、哪些变化会沿着这些关系传播、怎样保证传播过程的正确性”时，你实际上已经开始使用图的思维理解软件系统。

沿着这个方向继续学习，最值得深入的三个专题是：

Dependency Graph（依赖图）→ DAG 与拓扑排序 → 增量计算和响应式调度。

它们能够将图论、缓存、记忆化、Dirty Flag 和软件架构联系成一套完整的知识体系。

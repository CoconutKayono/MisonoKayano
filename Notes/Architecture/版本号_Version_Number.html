版本号看起来很简单，但它在软件工程中承担着多种不同的职责。软件版本描述发布与兼容性，数据版本用来判断数据是否变化，资源版本用来检测过期引用，存档版本用来选择迁移方式，协议版本则帮助双方判断能否正确通信。

这些版本号看起来相似，背后的规则却不完全相同。

理解版本号的关键，不在于数字如何递增，而在于：为什么需要区分同一个事物在演化过程中的不同版本。

01 · What：什么是版本号？

1. 从最简单的问题开始

一个角色先有 100 点生命，受到伤害后变成 80，再次受伤后变成 50。Player 仍然是同一个 Player，但它的数据已经改变。加上版本号，我们就能区分这些状态对应的修订。

Version 1Health = 100
Version 2Health = 80
Version 3Health = 50

版本号（Version Number）是一种用于区分事物不同版本的标识符，通常按照事先约定的规则发生变化。这里的关键词是“区分”和“规则”。

版本号不一定是整数，也不一定严格按时间顺序递增。它的含义由使用场景和版本规则决定。

2. 版本号的本质：身份、状态与版本

概念回答的问题示例
Identity（身份）这是谁？PlayerId = 1001
State（状态）它现在是什么样？Health = 80
Version（版本）它处于哪个已标记的版本？Version = 2

身份区分不同事物，状态描述具体内容，版本区分演化过程中的不同修订或发布成果。我们可以把状态演化写成：

(S₀, V₀) → (S₁, V₁) → (S₂, V₂)

如果系统规定每次状态修改都递增版本号，就有 Vₙ₊₁ = Vₙ + 1。这是常见规则之一，并不是所有版本号必须遵守的数学定义。

3. 版本号和时间戳有什么区别？

标识回答的问题例子
时间戳这件事发生在什么时候？UpdatedAt = 2026-10-17 14:30:00
版本号这是哪一个版本？Version = 3

两者可以同时存在，但时间戳并不总能代替版本号：

  • 不同机器的时钟可能不一致。
  • 多次更新可能发生在时间戳精度所能区分的同一时刻。
  • 时间先后不一定等于业务版本之间的先后关系。
  • 不同分支可以在同一时间分别演化。

因此，需要可靠检测更新冲突时，通常更适合使用专门管理的版本标识。

02 · Why：为什么需要版本号？

根本问题系统需要回答什么
变化识别我上次观察之后，它是否发生了变化？
有效性判断我手中的信息、引用或资源，是否仍然有效？
兼容性判断两个不同版本的程序、系统或数据，能否相互配合？

1. 变化识别：避免丢失更新

服务端最初保存 Coins = 100。客户端 A 与 B 同时读到 100，A 希望增加 50，B 希望消费 30。如果两者各自在本地计算后直接覆盖，就可能发生：

这叫 Lost Update（丢失更新）。我们为数据增加版本号，并让写入携带“我依据的是哪个版本”。

步骤请求 / 当前数据结果
起点Coins = 100，Version = 1A、B 都读取 V1
A 提交期望 V1，写入 Coins = 150成功，数据变为 V2
B 提交期望 V1，写入 Coins = 70当前为 V2，拒绝直接覆盖

这是一种 Optimistic Concurrency Control（乐观并发控制）。版本号不负责锁定数据，也不决定如何合并冲突；它提供的关键判断是：

我准备修改的，还是不是我当初读取的那个版本？

发现冲突后，系统需要重新读取，再根据业务决定重试、合并或提示用户。拒绝过期写入本身，并不等于完成了冲突处理。

2. 有效性判断：检测过期引用

假设资源数组中，槽位 1 原本保存 Texture_B。某个系统只记住 Handle.Index = 1。后来 Texture_B 被销毁，槽位被回收，并存入 Texture_D。

时刻槽位 1旧引用持有的信息
原来Texture_BIndex = 1
回收后空闲Index = 1
复用后Texture_D仍是 Index = 1

仅凭索引，旧引用会把 Texture_D 误当作 Texture_B。这是槽位复用造成的陈旧引用问题，也属于 ABA 类问题的一种表现。

引入 Generation（代数版本号） 后，句柄由两部分组成：

Handle = (Index, Generation)

Index 定位存储位置，Generation 检查该位置是否仍然属于原来的资源实例。这里的 Generation 是槽位复用代数，与软件发布版本号的含义不同。

3. 兼容性判断：升级后还能工作吗？

尽管计算结果相同，原来调用 Add 的程序仍可能无法编译或正常运行。用户关心的不只是有没有新版本，还包括升级后已有代码能否继续工作。

因此，发布版本需要定义兼容性规则。一个有代表性的方案是 Semantic Versioning（语义化版本）。

03 · How：版本号如何设计与使用？

类型示例主要目的比较方式
发布版本2.1.3表达发布与兼容性依照版本协议排序
数据修订版本Version = 8检测并发修改、过期数据相等检查；规则允许时按序比较
资源代数版本Generation = 8检测回收复用后的旧引用相等检查

它们都叫版本，但每一类的正确性依赖不同的更新与验证规则。

1. 发布版本：Semantic Versioning

Major . Minor . Patch
字段何时递增例子
Major · 主版本公共 API 发生不兼容修改1.1.0 → 2.0.0
Minor · 次版本增加向后兼容的功能1.0.1 → 1.1.0
Patch · 修订版本进行向后兼容的错误修复1.0.0 → 1.0.1

主版本是否递增，取决于是否破坏已承诺的公共 API 兼容性，而不是“修改量有多大”。公共 API 除了方法签名，也可能包括公开承诺的行为契约。以上是稳定公共 API 下的常见规则；SemVer 中 0.y.z 用于初始开发阶段。

版本号如何比较？

1.10.0 大于 1.9.0，因为要按主、次、修订三个字段依次进行数值比较，不能把版本号当小数，也不能直接按普通字符串排序。

试一试：比较三个数值字段

1.10.0 > 1.9.0

只接受三个非负整数字段；不包含预发布标识、构建元数据或前导零。

完整 SemVer 支持预发布标识和构建元数据。alpha、beta、rc 常用于表达预发布阶段；预发布版本的优先级低于对应的正式版本，+ 后的构建元数据不参与优先级比较。

SemVer 是一种协议。使用三段数字并不自动意味着遵循 SemVer；Unity、操作系统、日期版本与 Git 提交标识可能采用其他规则。

2. 数据版本：乐观并发控制

假设数据库中有 PlayerId = 1001、Coins = 100、Version = 1。目标是：只有请求所依据的版本仍然有效，才允许更新。

关键条件是 Version = @expectedVersion。影响 1 行通常表示成功；影响 0 行可能是记录不存在，也可能是版本冲突，需要根据业务进一步处理。

这里通过增量更新示意条件写入；前面“本地计算后覆盖”的写法也能使用同样的版本条件。单纯的原子加法可以避免该字段的覆盖丢失，但无法自动验证所有依赖旧快照的业务判断。

版本检查与数据更新必须是同一个原子操作。仅增加 Version 字段，不会自动得到并发安全。

多个线程可能同时通过 if 检查。版本号提供验证依据，事务、原子条件更新或适当同步机制负责让验证与修改保持一致。数据库更新还需结合具体的事务与并发语义。

为什么不用 Boolean？

Boolean 可用于标记“是否脏”，但一个 true 无法区分后续多次修订。修订计数器提供了更多区分信息，不过版本差值不一定等于业务变更次数：一次提交可能修改多个字段。

Index 用来定位槽位，Generation 用来判断是否属于同一代资源，Resource 保存资源本身。这就是典型的 Generational Handle（代数句柄）。

Generation 解决了所有问题吗？

第一，有限宽度的计数器可能回绕。8 位无符号计数器按回绕方式递增时，会经历 254 → 255 → 0 → 1。如果代数回到某个旧值，非常古老的句柄可能重新通过校验。

实际系统可以使用足够宽的代数计数器，并按安全要求制定溢出策略，例如到达上限后永久停止复用该槽位。C# 的溢出行为还取决于 checked / unchecked 上下文，不能依赖未说明的默认行为。

第二，通过代数检查并不保证后续访问期间资源仍然存活。检查之后、实际使用之前，其他线程仍可能释放资源，因此还需要同步、借用约束或其他生命周期保证。

04 · 版本号与其他概念的关系

1. Version 与 Identity

而资源池中的 (Index = 1, Generation = 5) 与 (Index = 1, Generation = 6)，在句柄语义下可能表示两个不同资源实例。

版本是否参与身份判定，由系统规则决定。PlayerId 通常负责玩家身份，Version 负责数据修订；代数句柄常把 (Index, Generation) 整体作为资源实例身份的一部分。跨多个资源池时，还必须明确句柄属于哪个池。

2. Version 与 Revision

  • Version 强调可区分的版本，可能携带兼容性语义。
  • Revision 强调某次修订，通常用于标记修改序列。

这不是严格统一的全球定义，不同项目可能采用不同命名。要根据实际契约理解字段，而不是仅凭名字判断。

3. Version 与 Hash

内容哈希也能帮助识别变化：内容 A 计算得到 Hash X，内容 B 通常得到不同的 Hash Y。但哈希与修订计数器提供的信息不同。

维度修订计数器内容哈希
生成方式按约定递增根据内容计算
表达先后在约定作用域内通常可以通常不可以
检测修改依赖每次相关修改都正确更新受碰撞风险与内容规范化规则限制
仅凭值恢复内容不能通常不能；内容寻址还依赖存储映射
常见用途并发控制、状态修订完整性校验、内容寻址、缓存

Git 提交标识与提交内容有关，提交内容中包含父提交等信息，因而可以关联历史结构；它不是简单的递增数字。版本标识不必是自然数。

4. Version 与 Schema Version

它们都包含生命值，但结构不同。读取器可以根据 SchemaVersion 选择迁移路径：

字段表达什么
SchemaVersion数据采用哪一种结构
DataRevision同一份数据处于哪一次修订

这两个值同时存在完全合理。一次金币变化可以提升 DataRevision，而无需修改 SchemaVersion。

05 · 设计版本号时，需要遵守什么规则？

1. 明确作用域

两个玩家都有 Version = 5，并不代表他们状态相同，因为这两个版本属于不同玩家。通常需要把版本放到其所属对象的作用域内解释。

(PlayerId, Version)   /   (SlotIndex, Generation)

脱离对象、资源池或数据集的作用域，单独一个版本值通常不足以判断状态或身份。

2. 明确什么时候更新版本

操作CoinsVersion
初始值1001
只读取，不修改1001
成功消费 10902
后续操作失败并回滚902

需要预先约定：每次操作尝试递增，还是每次成功提交状态修改递增？用于并发控制的数据版本，通常希望每次受保护的数据成功修改后，都得到新的版本标识。

表中采用应用层事务内递增的约定；其他数据库生成的并发令牌可能有不同规则，例如跳号。因此不能从一个计数值推断所有业务事件。

3. 明确比较规则

3.0.0 在某个发布规则下排序高于 2.9.0，不代表它更稳定、性能更好或更适合当前项目。Generation = 10 也不比 Generation = 5 的资源更先进。

数值比较的含义来自规则。检测代数句柄是否仍有效时，关键是相等，而不是“足够大”。

4. 明确是否存在全局顺序

单个记录在统一写入点下可以形成 V1、V2、V3 的明确顺序；两个节点同时基于 V1 修改同一份数据时，则可能形成分支。

V1 · 共同起点
V2A · 节点 A 修改
V2B · 节点 B 修改
后续合并

这两次修改可能没有天然先后。单个递增数字未必足以完整描述因果关系，复杂系统会使用向量时钟、版本向量或其他逻辑时钟机制。不同机制能表达的信息也不同；例如 Lamport 时钟的数值先后不能反过来证明事件之间存在因果关系。

版本标识可以区分变化，但不保证能够描述所有变化之间的先后与因果关系。

06 · 把知识统一起来

设对象沿着状态序列演化，我们为需要区分的版本附加标识。系统再根据目标，定义这些标识的生成规则与判断方式。

版本机制它需要支持的判断例子
发布版本公共 API 兼容性约定2.1.0
数据版本快照是否过期、写入是否冲突Revision 42
资源代数引用是否仍指向同一代实例Generation 7

当一个事物可能变化，而系统需要区分变化前后的版本时，就需要版本标识机制。但不同场景不能简单混用：

  • 不能用 SemVer 的大小判断某份玩家数据是否过期。
  • 不能用资源 Generation 判断 API 是否兼容。
  • 不能仅凭 SchemaVersion 判断两次并发数据更新是否冲突。

版本号是标识。它能支持什么判断，取决于生成、更新与比较所遵守的契约。

07 · 版本号变化，一定意味着内容变化吗？

不一定。设角色原来 Health = 100、Version = 1，执行：

最终 Health 仍然是 100，Version 却变成了 2。版本可以标记一次修订、写入或生命周期事件，不必保证内容不同。

反过来，如果有人把生命值改成 80，却忘记提升版本，Version 仍然是 1，那么依赖版本检查的系统就无法可靠识别变化。

版本号的可靠性，来自系统对版本更新规则的持续遵守。数字本身不会自动提供线程安全、事务安全、引用安全或兼容性保证。

内容还可能经历 A → B → A。若只比较当前内容，起点和终点看起来相同；若每次修订都分配新版本，系统仍然可以区分它们的演化经历。这也是修订标识与内容哈希之间的重要差异。

08 · 版本号的本质

层次含义
第一层 · 标识区分事物的不同版本
第二层 · 协议约定作用域、何时变化、如何比较
第三层 · 配套机制利用版本执行冲突检测、失效校验、兼容性判断与迁移
版本标识 ＋ 版本规则 ＋ 验证机制

三者共同形成真正有用的版本方案。“版本号”是其中的信息依据，其他机制负责落实系统需要的保证。

版本号最核心的价值，是帮助系统回答：我现在面对的，是否仍然是我所期望的那个版本？

继续深入时，可以带着这四个问题

  • 为什么资源句柄需要同时保存 Index 与 Generation？
  • 为什么乐观并发通常检查版本相等，而不只是比较大小？
  • ABA 问题中，代数计数器解决了什么，还需要什么条件？
  • 为什么分布式系统中的单个整数版本号有时不够用？

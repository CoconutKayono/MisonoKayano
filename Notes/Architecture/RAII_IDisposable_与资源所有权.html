概念 · 对象、资源与责任

01What：它们究竟是什么？

1.1 什么是资源（Resource）？

资源是程序为了完成工作，需要获取、占用、使用，并在适当时候归还或释放的东西。资源可能由 .NET 托管运行时、操作系统、数据库连接池、Unity 引擎或自定义对象池管理。

资源获取方式使用完之后
托管内存new Player()GC 回收不可达对象占用的内存
文件句柄File.OpenRead()Dispose() 关闭文件
数据库连接SqlConnection.Open()关闭或归还连接
网络 Socket创建并连接 Socket关闭 Socket
互斥锁Monitor.Enter()Monitor.Exit()
Unity GameObjectInstantiate()Destroy() 或交还对象池
Unity NativeArraynew NativeArray<T>()Dispose()
Addressables 资源LoadAssetAsync()Addressables.Release()

释放操作不同，是因为资源由不同的系统管理，并且具有不同的使用契约。

1.2 对象与资源不是同一个概念

C#
var player = new Player();
var stream = File.OpenRead("save.dat");

第一行主要创建一个普通托管对象。第二行通常同时涉及一个 C# 的 FileStream 托管对象，以及与之关联的操作系统文件句柄。

.NET 托管堆FileStream 托管对象GC 管理对象内存
持有并管理文件句柄 ↓
操作系统文件句柄需要按契约及时关闭

GC 不负责理解每一种外部资源的关闭协议。.NET 文件类通常通过 SafeHandle 等机制提供遗忘释放时的后备清理，但这不意味着文件会在离开作用域时立即关闭。仍应显式释放文件。

内存回收 ≠ 资源释放。
前者关注不可达托管对象占用的内存；后者关注文件、连接、锁、原生内存等资源的使用权何时结束。

1.3 什么是资源所有权（Resource Ownership）？

所有权意味着：谁有责任决定资源何时结束使用，并执行相应的释放操作。它不等于“谁能访问这个资源”。

C#
var stream = File.OpenRead("save.dat");
var a = stream;
var b = stream;

a.Dispose();
// b 仍引用同一个托管对象，但不能继续正常使用已释放的流。

三个变量没有产生三个独立的文件句柄，也不代表三份独立的释放责任。释放影响的是引用指向的资源，而不是仅影响某个变量。

  • 过早释放：一个使用者还在使用，另一个就释放了。
  • 重复释放：多个使用者各自认为自己应该释放。
  • 资源泄漏：所有使用者都认为应该由别人释放。

1.4 什么是 RAII？

RAII = Resource Acquisition Is Initialization，资源获取即初始化。它起源于 C++，把资源生命周期与管理对象的生命周期绑定。

  1. 管理对象初始化时获取资源。
  2. 管理对象有效期间，维持其所承诺的资源有效性。
  3. 管理对象生命周期结束时，析构函数释放其拥有的资源。
C++
void ReadFile()
{
    std::ifstream file("save.dat");
    // 使用文件
} // file 在这里析构，关闭文件

对于这种局部 RAII 对象，即使作用域因为异常退出，正常栈展开也会调用已构造对象的析构函数。“自动”来自 C++ 的对象生命周期与析构规则，而不是 GC。

RAII 的目的，是让程序员不必在每一条退出路径上都依赖自己记得写释放代码。RAII 不仅限于栈对象：堆资源也可以由 std::unique_ptr 等 RAII 对象持有，释放时机由拥有者的生命周期决定。

1.5 什么是 IDisposable？

C#
public interface IDisposable
{
    void Dispose();
}

IDisposable 定义显式结束资源使用的操作。using 则将这一操作绑定到指定作用域的结束，包括正常的异常展开。

C#
using (var stream = File.OpenRead("save.dat"))
{
    // 使用文件
} // 自动调用 Dispose()
比较项C++ RAIIC# IDisposable + using
获取资源通常由构造或工厂负责构造、工厂、Open 等
释放资源析构函数Dispose()
离开作用域局部 RAII 对象自动析构using 自动调用 Dispose()
普通堆对象由明确的拥有者管理托管内存由 GC 回收
确定性释放根据管理对象生命周期实现通过 Dispose、using 等机制实现
IDisposable 是释放协议，using 是作用域清理机制。
C# 普通托管对象不会因为局部变量离开作用域就确定性析构。
动机 · 可达性不等于使用期限

02Why：为什么不能统一使用 GC？

2.1 GC 解决托管内存的可达性问题

C#
void Test()
{
    Player player = new Player();
}

假设 Player 是不持有额外资源的普通类。当对象不能再从 GC 根访问到时，它就有资格被 GC 回收。有资格回收，不等于立即回收。局部变量的词法作用域，也不等同于 GC 追踪到的实际存活区间。

不可达 ⇒ 有资格被 GC 回收
离开作用域 ⇏ 立即释放内存

对普通托管对象，这通常可以接受：运行时根据内存压力选择回收时机。但外部资源的紧缺程度，未必体现为托管堆的内存压力。

2.2 文件、连接等资源需要及时释放

文件流的托管对象可能很小，却占用一个操作系统句柄。数据库连接对象也可能很小，却占用数据库、网络和连接池资源。连接池借出额度用尽时，新操作可能等待到超时，即使托管堆仍然有很多空闲内存。

资源应当结束使用的时间，不能仅由“托管堆是否需要回收内存”来决定。

设 T_lastUse 是最后一次合法使用的时间，T_release 是实际释放或归还的时间。对于最终释放，应满足：

T_release ≥ T_lastUse
并让两者之间的延迟处于合理范围

过早释放破坏仍在进行的使用；过晚释放浪费有限资源。RAII 和显式释放协议帮助我们控制这个时序；GC 主要负责托管内存。对于共享资源，这里的“最后一次使用”是所有合法使用者的最后一次使用。

2.3 为什么 Unity 对象更特殊？

Unity 同时涉及托管内存、非托管内存，以及由 Unity C++ 引擎维护的对象和资源。后两者在内存性质上都属于非托管范畴，但所遵循的管理 API 不同。

C# 托管世界GameObject 托管包装对象持有引擎对象的关联信息
关联 ↓
Unity C++ 引擎世界原生对象及引擎数据遵循 Unity 引擎生命周期
C#
GameObject enemy = Instantiate(enemyPrefab);
enemy = null; // 只清除这个变量的引用，不等于销毁实例。

显式销毁实例应使用 Destroy(enemy)，并且应在仍持有有效引用时调用。Destroy 是销毁请求；通常实际销毁延迟到当前更新循环之后、渲染之前。

C#
GameObject enemy = Instantiate(enemyPrefab);
Destroy(enemy); // 请求 Unity 销毁原生对象
enemy = null;   // 可再清除当前变量的引用

原生对象销毁后，C# 包装对象可能仍存在。Unity 为 UnityEngine.Object 重载了空值比较，因此对象可能满足 obj == null，但 ReferenceEquals(obj, null) 仍为 false。

?. 和 ?? 检查的是托管空引用，不会使用 Unity 的重载相等运算符；不能依赖它们判断原生对象是否已销毁。

Unity 生命周期的特殊性，来自托管运行时与原生引擎之间的管理边界。

03How：如何建立正确的资源生命周期？

3.1 先确定责任，再选择释放 API

  • 谁创建或获取了资源？
  • 谁可以使用资源？
  • 谁负责结束使用？
  • 什么事件代表资源不再需要？
关系使用权与释放责任典型约定
独占所有权一个明确主体负责释放其他使用者只能借用
借用临时访问，不擅自释放不得超出约定生命周期使用
共享所有权多个使用者共同需要资源有效共享管理者协调，最后一份使用权结束后清理
所有权转移释放责任从一方交给另一方工厂返回资源，调用者负责释放

C# 普通引用并不具备类似 std::unique_ptr 的唯一所有权约束。这些关系通常依靠 API 契约、封装、命名与代码规范表达。创建者常常是初始拥有者，但也可以立即转移所有权。

3.2 文件：用 using 绑定使用范围

C#
void ReadSave()
{
    using var stream = File.OpenRead("save.dat");
    // 读取存档
} // 当前块作用域结束时 Dispose

其核心语义可以理解为 try/finally。下面针对成功获取到的非空文件流展示等价思路：

C#
var stream = File.OpenRead("save.dat");
try
{
    // 读取存档
}
finally
{
    stream.Dispose();
}

using var 在声明所在块结束时释放；using (...) { } 可以用更小的代码块精确限定使用范围。

C#
void Example()
{
    using (var stream = File.OpenRead("save.dat"))
    {
        // 只在这个代码块内使用
    }
    // 此处已调用 Dispose
}
让资源的使用范围尽可能小，让释放边界通过代码结构自然表达。

正常异常展开会执行 finally；强制终止进程等情况可能来不及运行清理代码，不能把 using 当成进程异常终止时的绝对保证。

3.3 自己开发持有资源的类

日志类自己创建文件写入器，并承担释放责任。以下为单线程使用的简单封装，展示幂等释放与已释放状态检查：

C#
using System;
using System.IO;

public sealed class LogWriter : IDisposable
{
    private StreamWriter _writer;

    public LogWriter(string path)
    {
        _writer = new StreamWriter(path);
    }

    public void Write(string message)
    {
        if (_writer == null)
            throw new ObjectDisposedException(nameof(LogWriter));

        _writer.WriteLine(message);
    }

    public void Dispose()
    {
        if (_writer == null)
            return;

        StreamWriter writer = _writer;
        _writer = null;
        writer.Dispose();
    }
}

若项目启用可空引用类型，应将该字段声明为 StreamWriter?。示例未处理并发写入和并发释放。

C#
using (var logger = new LogWriter("game.log"))
{
    logger.Write("Game Started");
    logger.Write("Player Joined");
}

这是级联释放：LogWriter.Dispose() 调用 StreamWriter.Dispose()，进而关闭它拥有的底层流并释放文件句柄。每一层管理者负责自己拥有的资源。

只持有托管的可释放对象时，通常不需要为此额外编写终结器。Dispose() 应尽量具备幂等性：重复调用不会造成额外破坏。幂等不代表线程安全。

持有 IDisposable 字段，不自动等于拥有该字段。只有拥有它，才应承担相应的级联释放责任。

3.4 不要擅自释放借来的资源

C#
public void ReadData(Stream stream)
{
    using var reader = new StreamReader(stream);
    // 默认情况下，reader.Dispose() 也会关闭底层 stream。
}

如果参数流只供临时借用，默认关闭底层流可能破坏调用者后续的操作。可以使用 leaveOpen 明确表达约定：

C#
public void ReadData(Stream stream)
{
    using var reader = new StreamReader(
        stream,
        System.Text.Encoding.UTF8,
        detectEncodingFromByteOrderMarks: true,
        bufferSize: 1024,
        leaveOpen: true
    );

    // 读取数据；reader 被释放后，stream 保持打开。
}
借用获得使用权，不自动获得销毁权。
参数传入本身不决定所有权，最终仍以 API 的明确契约为准。
连接池 · 结束使用不等于销毁实体

04Why & How：数据库连接为什么像租来的资源？

C#
using Microsoft.Data.SqlClient;

using var connection = new SqlConnection(connectionString);
connection.Open();
// 数据库操作

对于启用了连接池的 SQL Server 客户端，Dispose() 通常结束当前逻辑连接的使用，将可复用的底层物理连接归还连接池，而不是每次都真正断开网络连接。失效连接等情况可能被丢弃。

应用程序SqlConnection 持有本次使用权

Open 获取使用权 · Dispose 结束并归还

连接池管理可复用的物理连接

这与对象池的思想相通：使用者结束一次使用，并不意味着底层实体必须结束其整个生命周期。

资源结束本次使用的含义
文件句柄关闭句柄，结束文件访问
池化数据库连接归还连接池
池化游戏对象归还游戏对象池
原生内存释放对应分配
Unity 实例请求引擎销毁对象
正确的释放语义由获取方式与所有权契约决定，不能统一理解为 free 或 Destroy。

数据库事务的 Commit() 决定事务是否提交；连接的 Dispose() 决定连接使用权何时结束。释放连接不等于提交事务。

05How：Unity 中应该如何管理对象？

5.1 Instantiate 创建的 GameObject

C#
GameObject enemy = Instantiate(enemyPrefab);
// 当前系统若拥有这个实例，在适当时候：
Destroy(enemy);

若实例由对象池管理，应按池的契约归还。普通场景对象也可能由场景卸载统一销毁。需要回答的是“谁管理这个实例的生命周期”，而不只是“它是不是 GameObject”。

5.2 运行时创建的 Material 和 Texture

C#
using UnityEngine;

public class MaterialOwner : MonoBehaviour
{
    [SerializeField] private Material sourceMaterial;
    private Material runtimeMaterial;

    private void Awake()
    {
        runtimeMaterial = new Material(sourceMaterial);
        GetComponent<Renderer>().sharedMaterial = runtimeMaterial;
    }

    private void OnDestroy()
    {
        if (runtimeMaterial != null)
        {
            Destroy(runtimeMaterial);
            runtimeMaterial = null;
        }
    }
}

sourceMaterial 是外部提供的引用，当前组件不自动拥有它。runtimeMaterial 是当前组件创建的独立实例，由当前组件负责销毁。示例假设对象上存在 Renderer 且已指定来源材质。

随意销毁共享的来源材质，会影响其他使用者。这里同时隐含一项生命周期约定：其他使用者不得在拥有者销毁之后，继续依赖这个运行时材质。

5.3 OnDisable 和 OnDestroy 的职责不同

回调生命周期边界典型职责
Awake组件初始化建立组件级依赖、创建长期资源
OnEnable启用区间开始注册启用期间需要的事件
OnDisable启用区间结束取消对应事件订阅
OnDestroy组件或 GameObject 销毁清理组件拥有的长期资源
C#
private void OnEnable()
{
    GameEvents.OnGameOver += HandleGameOver;
}

private void OnDisable()
{
    GameEvents.OnGameOver -= HandleGameOver;
}

这是示意片段：GameEvents 与 HandleGameOver 由项目定义。订阅范围是“组件启用期间”，因此用 OnDisable 配对清理。如果资源在 Awake 创建并供组件整个生命周期使用，通常不应仅因禁用就销毁，除非重新启用时会重新获取。

OnDestroy 只会对曾激活过的 GameObject 调用；操作系统强制终止应用时也可能来不及执行。它不构成业务数据持久化的绝对保证。

5.4 NativeArray<T> 为什么使用 Dispose？

C#
using Unity.Collections;
using UnityEngine;

public class NativeMemoryExample : MonoBehaviour
{
    private NativeArray<int> _numbers;

    private void Awake()
    {
        _numbers = new NativeArray<int>(1024, Allocator.Persistent);
    }

    private void OnDestroy()
    {
        if (_numbers.IsCreated)
            _numbers.Dispose();
    }
}

虽然 NativeArray 在 C# 中是结构体，但底层数据位于非 GC 管理的内存中，必须按分配器和使用契约释放。示例假设销毁时没有 Job 继续使用该数组。

C#
using var numbers = new NativeArray<int>(1024, Allocator.TempJob);
// 在当前作用域内使用；离开前确保相关 Job 已完成。
  • Allocator.TempJob 分配通常要求在四帧内释放。
  • 有 Job 使用数组时，必须等待相应依赖完成，或使用带 Job 依赖的释放安排。
  • 复制 NativeArray 结构体可能形成指向同一底层分配的别名，不会自动获得独立数据或独立释放权。
  • 某个副本的 IsCreated 不能普遍证明其他别名未释放底层内存。
值类型还是引用类型，不能直接决定是否需要显式释放。

5.5 Addressables 为什么使用 Release？

C#
var handle = Addressables.LoadAssetAsync<GameObject>("Enemy");
// 等待加载完成、处理结果，并在所有相关使用结束后：
Addressables.Release(handle);

这是生命周期示意片段，省略了加载完成与失败处理。Addressables 使用引用计数管理加载操作及依赖。对获取的有效句柄，应按其契约配对释放；复制句柄不自动增加一次引用计数。

通过 Addressables.InstantiateAsync() 创建的实例，通常用 Addressables.ReleaseInstance() 结束其生命周期。若手动对 LoadAssetAsync 的结果调用普通 Instantiate，需自行确保源资源的加载句柄在相关实例使用期间保持有效。

计数归零并不一定意味着内存立刻归还，还涉及依赖和 AssetBundle 的卸载时机。Release()、Destroy() 与 GC.Collect() 处理的层次不同，不能互相替代。

5.6 临时 RenderTexture 为什么用 ReleaseTemporary？

C#
RenderTexture temporary =
    RenderTexture.GetTemporary(512, 512, 0);

try
{
    // 使用临时 RenderTexture
}
finally
{
    RenderTexture.ReleaseTemporary(temporary);
}

Unity 内部维护临时 RenderTexture 池。ReleaseTemporary() 结束本次租用，使资源可以复用；它不表示每次都必须立即销毁底层纹理。不能只看见类型是 RenderTexture，就忽略来源而统一调用 Destroy。

边界 · 三种不同的机制

06深入：Dispose、终结器与 GC 的关系

6.1 Dispose 不等于回收托管对象内存

C#
var writer = new LogWriter("game.log");
writer.Dispose();
// writer 仍可能引用这个托管对象；文件资源已按契约清理。

Dispose 结束相关资源的有效使用；托管对象的内存仍由 GC 在合适时机回收。调用 Dispose 不会自动将所有指向对象的变量设为 null，也不会直接将该对象的托管内存交还给 GC。

Dispose ≠ GC 回收

6.2 C# 的析构函数语法实际是终结器

C#
class Example
{
    ~Example()
    {
        // 终结器：不是 C++ 的确定性析构函数。
    }
}

终结器由运行时终结机制管理，调用时间不确定，也不能保证在进程异常终止时执行。不应依赖它完成及时释放。直接管理非托管句柄时，优先考虑 SafeHandle，避免自行实现复杂且脆弱的终结器。

6.3 为什么不是所有类都实现 IDisposable？

C#
public class PlayerData
{
    public int Level;
    public int Experience;
    public string Name;
}

普通数据类若没有需要显式结束的资源使用，就不必实现 IDisposable。为所有类增加 Dispose，不能自动让 GC 更高效，只会增加额外的生命周期状态与管理负担。

应区分“需要回收的托管对象”和“需要显式终止使用的资源”。一个类型可以同时涉及二者，但不一定同时涉及。

6.4 IAsyncDisposable 是什么？

C#
public interface IAsyncDisposable
{
    ValueTask DisposeAsync();
}

当清理操作需要异步等待时，可以使用异步释放协议。在支持相应 API 的 .NET 环境中，例如：

C#
await using var stream = new FileStream(
    "save.dat",
    FileMode.Create,
    FileAccess.Write,
    FileShare.None,
    bufferSize: 4096,
    useAsync: true
);
// 在此异步写入文件。

作用域结束时会等待 DisposeAsync()。区别在于清理过程允许异步等待，例如完成缓冲写入或异步关闭；不是“异步释放就由 GC 接管”。Unity 中能否采用，应根据实际版本、运行时和所用 API 的支持情况判断。

本质 · 明确所有者，控制合法使用期

09将所有概念归结为一个原则

获取资源 → 合法使用 → 结束使用
  1. 使用有效性：合法使用期间，资源必须保持有效。
  2. 释放责任：必须存在明确、有效的清理机制，避免无人负责而永久泄漏。
  3. 生命周期一致性：最终释放不能早于合法使用结束，也不能无理由地无限延后。

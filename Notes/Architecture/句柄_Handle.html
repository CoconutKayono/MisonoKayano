句柄 Handle

从间接访问出发，理解资源身份、访问契约与生命周期管理。

句柄是由某个管理系统提供的、用于标识或访问其所管理资源的凭据。它的意义来自管理系统如何解释它，而不取决于它恰好是整数、结构体还是指针状的值。

句柄是操作系统、图形学、游戏引擎、资源管理系统中非常重要的概念。理解句柄，会帮助你回答：

  • 为什么程序可以通过一个整数操作文件、纹理、窗口或对象？
  • 为什么资源已经被释放，旧句柄却可能指向另一个资源？
  • 句柄与指针、引用、ID 有什么区别？
  • 为什么句柄能够参与生命周期管理，却不等于资源所有权？
  • 为什么引擎和操作系统经常使用句柄，而不直接暴露对象？

01 / WHAT什么是句柄？

1. 从三个角色理解句柄

资源（Resource）是我们真正希望访问或操作的对象；句柄（Handle）是我们持有的、代表某个资源访问入口的值；管理系统（Manager）负责解释句柄，并执行相应操作。

例如，操作系统负责管理文件。程序希望读取文件，不必知道文件在操作系统内部的数据结构，也不需要直接访问它的内存地址。程序获得文件句柄，再把它交给操作系统。

在这个例子中：5 是句柄，文件 A 是资源，操作系统是管理者。操作系统内部维护句柄与资源之间的关系。

C · 概念调用，省略错误处理
read(5, buffer, 100);

可以理解为：“请操作系统读取句柄 5 所代表的已打开文件中的数据。”在 Linux 中，文件描述符（File Descriptor）就是一种典型的句柄式机制：open() 返回一个非负整数，供后续 read()、write() 等系统调用使用。

2. 句柄的真正本质

“句柄就是指向资源的索引”是一种常见说法，但不够全面。句柄的底层表示可能是：

  • 整数索引。
  • 包含索引与版本号的结构体。
  • 某种指针或指针状的值。
  • 操作系统或图形 API 定义的不透明标识。

索引是句柄的一种实现，不是句柄的本质。

句柄的本质，是资源使用者与资源管理者之间约定的一种间接访问机制。使用者凭借句柄请求操作资源，而不必掌握资源的内部表示。

关键在于：这个值由谁解释，以及通过什么规则解释。

3. 句柄不等于资源

int textureHandle = 42;

42 不包含纹理的像素、宽高、采样格式，也不必包含内存地址。只有管理这个句柄的系统，才能按照约定把它解释为特定资源。

int anotherHandle = textureHandle;

这里复制的是句柄数值，而不是纹理资源。这通常不会创建新纹理，也不会自动增加资源引用计数。

复制句柄、复制资源、创建新的资源访问权，是三个不同的操作。是否保活资源、是否产生独立权益，必须查看对应 API 的契约。

02 / WHY为什么需要句柄？

1. 为什么不直接持有对象？

class Texture
{
    public int Width;
    public int Height;
    public byte[] Pixels;
}

Texture texture = new Texture();

直接引用当然可以工作。引入句柄，相当于在访问路径中增加管理机制：

方式访问路径
直接访问使用者 → 对象
间接访问使用者携带句柄 → 管理机制 → 对象

这层复杂度是否值得，取决于我们是否需要以下能力。

2. 隐藏资源内部结构

如果直接暴露 Pixels，客户端就可能依赖“纹理是一个可直接修改的字节数组”。将来管理器希望把数据迁移到 GPU 显存时，这种依赖可能阻碍实现调整。

textureManager.Upload(handle, pixelData);
textureManager.Release(handle);

调用方不必知道数据是否已上传 GPU、底层内存布局、缓存策略、内部是否发生重新分配，只需要遵守公开 API 的契约。

使用者知道可以做什么，而不必知道资源在内部怎样实现。

Windows 的对象与句柄机制也体现了这一点：公开接口可以保持稳定，同时允许内部实现演进。

3. 控制访问权限

某些系统中的句柄还能代表被授予的访问权限。同一个对象可以关联不同权限的句柄：

句柄关联资源允许操作
Handle A文件 X读取
Handle B文件 X读取和写入

Windows 内核对象句柄支持这样的权限管理，也可以为同一个对象创建多个句柄。

不是所有句柄都天然具备安全控制能力。访问控制需要管理者提供相应机制，单纯使用整数作为句柄不会自动产生安全隔离。

4. 分离资源的物理位置与外部身份

在支持重定位的自定义句柄表中，资源可能从内存地址 0x1000 搬迁到 0x9000，但外部句柄仍为 7。

阶段外部句柄管理器映射
整理前7槽位 7 → 0x1000
整理后7槽位 7 → 0x9000

管理器更新映射后，调用方仍可使用原句柄。资源的访问身份，不一定要与实际内存位置绑定。这是特定句柄表设计能够提供的能力，不意味着所有句柄系统都自动支持资源搬迁。

5. 集中管理资源生命周期

假设渲染系统、战斗系统、任务系统都保存了同一个敌人的直接引用。敌人已经死亡，但普通托管对象仍可能因为强引用而留在内存中；其他系统也可能继续使用它。

如果它们持有句柄，并通过敌人管理器访问，管理器可以在敌人死亡时将记录标记为失效。后续操作得到明确的失败结果，从而阻止通过该句柄继续操作已经结束逻辑生命周期的敌人。

句柄失效不代表资源已经从内存中释放。失效的是通过该句柄访问资源的资格；资源是否销毁、何时回收，取决于管理器和实际所有权规则。

句柄也不会自动保证生命周期安全。如果管理器不验证句柄、不处理旧句柄复用，或者把原始引用暴露给外部长期保存，仍然可能发生过期访问。

03 / HOW句柄是如何工作的？

1. 最基础的实现：句柄表

先不讨论具体操作系统。我们可以自己维护一张资源表，以数组索引作为句柄：

句柄 / 索引对应资源
0Texture A
1Texture B
2Mesh C
3Audio D
C# · 示意片段，需放入相应上下文；未包含有效性检查
var resources = new List<object>();

int Create(object resource)
{
    int handle = resources.Count;
    resources.Add(resource);
    return handle;
}

object Get(int handle)
{
    return resources[handle];
}

int handle = Create(new Texture());
Texture texture = (Texture)Get(handle);
  1. 管理器创建或接收资源。
  2. 把资源放入内部表。
  3. 返回一个代表该位置的句柄。
  4. 客户端保存句柄，需要访问时再请求管理器解析。
Resolve(h) = R

h 是句柄，R 是对应资源，Resolve 是管理器的解析操作。这个模型简单，却会遇到槽位复用的问题。

2. 旧句柄为什么危险？

假设客户端持有 handle = 1，原本对应 Texture B。之后 B 被删除，管理器把槽位 1 交给新创建的 Texture D。

时刻槽位 1 的内容旧代码仍持有访问结果
初始Texture B1访问 B
删除 B空1应当失败
创建 DTexture D1错误地访问 D

这就是陈旧句柄（Stale Handle）导致的错误访问：数值看起来仍然有效，但它所代表的资源身份已经改变。它与悬空引用、ABA 问题有相似之处，但不是所有这些问题都能简单画等号。

槽位身份不等于资源实例身份。槽位可以复用，但旧资源与新资源不应该因此被认为是同一个资源。

3. 代际句柄：索引 + 代数

给每个槽位增加一个版本号，通常称为 Generation（代数、代际编号）。句柄由一个索引变成一个二元组：

Handle = (Index, Generation)

(1, 4) 表示“访问槽位 1 中第 4 代对应的资源”。资源被注销后，将槽位代数递增；下一次复用得到 (1, 5)。

旧句柄 (1, 4)

槽位 1 当前代数：5

代数不匹配 · 验证失败

新句柄 (1, 5)

槽位 1 当前代数：5，且存活

代数匹配 · 验证通过

设句柄 h = (i, g)；管理器槽位保存 Sᵢ = (Rᵢ, gᵢ, Aliveᵢ)。在同一个管理器的命名空间内，有效条件为：

Valid(h) = InRange(i) ∧ Aliveᵢ ∧ (g = gᵢ)

索引越界、槽位不存活、代数不匹配，任何一个条件不满足，句柄就无效。

代数是有限宽度的整数，不能忽略溢出循环。严格系统还需要考虑代数耗尽、管理器身份、复用策略和并发同步。

4. 一个可学习的 C# 实现

下面的实现展示索引复用、代数校验和旧句柄失效。它是单线程教学实现，不包含资源销毁策略。

C# · ResourceHandle 与 ResourceManager<T>
using System;
using System.Collections.Generic;

// 句柄只负责描述身份。
public readonly struct ResourceHandle
{
    public int Index { get; }
    public ulong Generation { get; }

    internal ResourceHandle(int index, ulong generation)
    {
        Index = index;
        Generation = generation;
    }
}

public sealed class ResourceManager<T> where T : class
{
    private sealed class Slot
    {
        public T Value;
        public ulong Generation = 1;
        public bool Alive;
    }

    private readonly List<Slot> slots = new();
    private readonly Stack<int> freeIndices = new();

    // 注册资源并返回句柄。
    public ResourceHandle Add(T resource)
    {
        if (resource == null)
            throw new ArgumentNullException(nameof(resource));

        int index;
        Slot slot;

        if (freeIndices.Count > 0)
        {
            index = freeIndices.Pop();
            slot = slots[index];
        }
        else
        {
            index = slots.Count;
            slot = new Slot();
            slots.Add(slot);
        }

        slot.Value = resource;
        slot.Alive = true;

        return new ResourceHandle(index, slot.Generation);
    }

    // 通过句柄尝试访问资源。
    public bool TryGet(ResourceHandle handle, out T resource)
    {
        resource = null;

        if (handle.Index < 0 || handle.Index >= slots.Count)
            return false;

        Slot slot = slots[handle.Index];

        if (!slot.Alive ||
            slot.Generation != handle.Generation)
            return false;

        resource = slot.Value;
        return true;
    }

    // 注销句柄，不负责销毁资源。
    public bool Remove(ResourceHandle handle)
    {
        if (handle.Index < 0 || handle.Index >= slots.Count)
            return false;

        Slot slot = slots[handle.Index];

        if (!slot.Alive ||
            slot.Generation != handle.Generation)
            return false;

        // 禁止代数循环复用。
        if (slot.Generation == ulong.MaxValue)
            throw new InvalidOperationException("Generation exhausted.");

        slot.Value = null;
        slot.Alive = false;
        slot.Generation++;

        freeIndices.Push(handle.Index);
        return true;
    }
}
C# · 使用方式；Texture 为前文的普通示例类
var manager = new ResourceManager<Texture>();

// 注册资源 A。
var oldHandle = manager.Add(new Texture());

// 注销其句柄。
manager.Remove(oldHandle);

// 注册资源 B，复用刚才的槽位。
var newHandle = manager.Add(new Texture());

bool oldValid = manager.TryGet(oldHandle, out _);
bool newValid = manager.TryGet(newHandle, out _);

// oldValid == false
// newValid == true

这个实现提供了什么？

旧句柄与新句柄可以具有相同的 Index，但只有代数匹配且存活的记录才能通过验证。默认结构体的代数为 0，而新槽位从 1 开始，因此 default(ResourceHandle) 不会匹配初始资源。

它还有哪些明确边界？

  • 注销不等于销毁：Remove() 只清除管理器引用并使句柄失效，不自动调用 Dispose()，也不会调用 Unity 的 Destroy()。
  • 原始引用仍可逸出：TryGet() 返回实际对象引用，调用方可以保存它，并在句柄失效后继续使用。需要严格控制访问时，可以让管理器直接提供操作接口。
  • 句柄限于原管理器：示例未编码管理器身份，也未使用按资源类型区分的句柄。将 A 管理器的句柄交给 B 管理器，可能错误匹配相同的索引与代数。应在 API 契约中禁止，或增加管理器标识、类型隔离等机制。
  • 代数耗尽会抛异常：当前检查发生在注销前，达到上限时该槽位仍保持原状态。更完整的系统可以允许注销，并永久停用耗尽的槽位。
  • 没有并发保证：多线程或回调重入下的访问与注销，需要另行设计同步和使用期间的保活规则。

示例保留讲解用的基本结构；若项目启用 C# 可空引用类型，需要给可能为 null 的字段与输出参数添加相应注解。

04 / COMPARISON句柄、指针、引用与 ID

这些概念容易混淆，因为它们都可能帮助我们定位某个对象，但强调的语义不同。

概念本质如何访问对象
Pointer / 指针表示内存地址的值通过相应内存模型的寻址规则访问
Reference / 引用语言提供的对象引用关系由语言与运行时处理
ID / 标识符用于区分实体的标识按应用定义的规则查找
Handle / 句柄管理系统接受的资源访问凭据交给相应管理系统解释

1. ID 强调身份，Handle 强调受管理的访问

int playerId = 1001;        // 可能只是数据库中的玩家编号。
PlayerHandle playerHandle; // 通常意味着存在对应的访问管理机制。

两者没有绝对的表示形式分界。一个 ID 完全可以同时充当句柄。区别在于它承担的职责和 API 契约，而不在于变量名称。

2. 指针与句柄不能直接画等号

指针强调“这个值按照相应内存模型表示一个地址”；句柄强调“这个值必须按照指定管理系统的规则解释”。两者即使底层表示相似，也不具有相同的使用许可。

C++ · 语义对比
// 普通指针在满足类型、生命周期等条件时可以解引用。
Resource* pointer = /* 指向有效 Resource 对象 */ nullptr;
// auto value = *pointer; // 只有 pointer 确实有效时才允许。

// 不透明句柄必须交给对应 API 使用。
// 不可以擅自把它当作 Resource 的内存地址：
// auto value = *reinterpret_cast<Resource*>(handle);

即使某种句柄以指针形式表示，也不意味着调用方可以自行解引用。Direct3D 12 的描述符句柄就是典型例子：它们类似指针，但应用必须通过 API 使用，而不能自行解引用。

3. C# 引用通常参与对象可达性管理

Enemy enemy = new Enemy();
Enemy another = enemy;

enemy 与 another 引用同一个普通托管对象。只要该对象仍通过存活的强引用保持可达，GC 就不会把它作为不可达垃圾回收。这里的“存活”以运行时实际可达性为准，并非单纯看变量的词法作用域。

EnemyHandle oldHandle = handle;

如果 EnemyHandle 只是索引和代数，那么保存它本身不意味着敌人必须继续存活。保活可能来自管理器中的强引用，或其他机制。

引用通常参与对象可达性管理，而普通数值句柄本身不保证资源存活。不同句柄可以有自己的保活契约，例如 GCHandle。

05 / LIFETIME & OWNERSHIP句柄与所有权、生命周期

必须区分以下四个问题：

概念回答的问题
Handle Validity / 句柄有效性现在还能通过这个句柄访问资源吗？
Resource Lifetime / 资源生命周期底层资源实际存在多久？
Logical Lifetime / 逻辑生命周期业务上何时认为这个对象有效？
Ownership / 所有权谁有责任决定或执行资源释放？

1. 持有句柄，就拥有资源吗？

ResourceHandle handle = manager.Add(texture);

仅从这一行代码，不能推断调用方是否拥有资源、管理器是否拥有资源、谁有权释放、复制句柄是否增加引用计数，以及句柄失效是否立刻销毁资源。这些必须由系统契约定义。

例如，Windows 中同一个内核对象可能有多个句柄。关闭其中一个句柄，不一定销毁底层对象；其他句柄可能依然有效。

2. 三种常见契约

契约句柄使用方式资源释放规则
非拥有句柄借用资源访问资格所有者负责释放
拥有句柄持有按契约必须释放的句柄权益按契约关闭或释放；未必直接销毁底层对象
引用计数句柄持有计数化的访问权益达到释放条件时回收

这些是帮助理解的语义分类，并非互斥的底层实现类别；引用计数句柄也可以承担拥有语义。

在对象池系统中，外部可能只持有敌人的非拥有句柄：

EnemyHandle enemyHandle;
enemyManager.TryApplyDamage(enemyHandle, 10);

调用方可以请求施加伤害，但不能因此决定敌人的内存何时释放。对象池或实体管理器负责资源生命周期。敌人被回收并用于下一个逻辑敌人时，原句柄应当失效。

资源实例能够被复用，不代表前一个逻辑对象的身份也能够被复用。

3. 检查有效，不等于使用期间一直安全

顺序线程 A线程 B
1检查句柄：有效
2释放资源
3使用资源：可能已失效
Valid(h, t₁) ⇏ Valid(h, t₂)

在 t₁ 有效，不代表在 t₂ 仍有效。并发安全使用可能需要互斥锁、引用计数、租约、延迟回收等机制，并确保这些机制覆盖实际使用期间。

代际句柄解决资源身份复用问题，不自动解决并发资源释放问题。

06 / IN PRACTICE操作系统、C# 与图形 API

1. 操作系统文件句柄

C · Linux 示意，省略头文件与错误处理
int fd = open("data.txt", O_RDONLY);
// 假设返回 fd == 3。

read(fd, buffer, 100);
close(fd);

open() 获得访问入口，read() 使用它访问资源，close() 关闭当前文件描述符。关闭后，整数值可能重新分配给另一个打开的文件，因此不能继续使用旧的 fd。

2. C# 的 SafeHandle

操作系统文件句柄属于非托管资源，其释放时机不等同于普通托管对象内存被 GC 回收的时机。

System.Runtime.InteropServices.SafeHandle 用于安全包装非托管句柄，并提供释放及相应的生命周期保护。通常我们直接使用已经封装好的类型：

using System.IO;

using (var stream = File.OpenRead("data.txt"))
{
    // 读取文件。
}

FileStream 提供托管文件访问接口，并负责管理底层资源。using 在正常离开作用域或异常展开时调用 Dispose()；这与托管对象内存何时由 GC 回收是两件事。

3. C# 的 GCHandle

System.Runtime.InteropServices.GCHandle 为托管对象建立特殊的 GC 句柄，常用于托管与非托管代码互操作。它并非专门管理操作系统文件句柄。

using System.Runtime.InteropServices;

object resource = new object();

GCHandle handle = GCHandle.Alloc(
    resource,
    GCHandleType.Normal
);

try
{
    object target = handle.Target;
}
finally
{
    handle.Free();
}

Normal 类型的 GCHandle 会让目标对象保持可达，直到句柄释放；Pinned 类型还可防止符合条件的对象被 GC 移动。其他类型如弱句柄具有不同语义，不能把所有 GCHandle 都理解为强保活。

机制主要目的
自定义 ResourceHandle标识和查找受管理的资源
SafeHandle安全管理特定非托管句柄
GCHandle控制托管对象的 GC 可达性或固定行为

同样叫 Handle，对生命周期提供的保证却不相同。复制 GCHandle 结构体也不会自动创建独立的新 GC 句柄，不应把副本当作可分别释放的所有者。

4. Direct3D 12 描述符句柄

D3D12_CPU_DESCRIPTOR_HANDLE
D3D12_GPU_DESCRIPTOR_HANDLE

它们定位描述符堆中的特定描述符，不直接代表纹理或缓冲区对象本身。描述符按其内容描述资源视图或其他绑定信息。

这类句柄必须按照图形 API 的约定使用，应用不能擅自解引用其内部位模式。API 允许的偏移计算也应使用设备提供的描述符增量等规则。

GPU 还有异步执行：CPU 提交命令后，GPU 可能尚未执行。GPU 仍会访问的描述符及其依赖资源，必须按照同步规则保持有效，不能仅因 CPU 已提交命令就立即复用或释放。具体期限依描述符类型与 API 契约而定。

5. Unity 与游戏对象

Unity 也有对象身份标识机制。提供 Object.GetInstanceID() 的版本中，实例 ID 用于标识内存中的对象实例，不能作为跨运行会话的稳定存档 ID。具体接口应以项目使用的 Unity 版本文档为准。

拿到对象实例标识，不等于获得对象所有权。还需要区分：

  • Destroy 是对 Unity 对象生命周期执行操作。
  • 托管引用存在，不代表相应的原生 Unity 对象仍有效。
  • 对象池自定义的句柄，应按对象池自己的有效性规则判断。

Unity 对象引用、实例 ID、自定义实体句柄，是不同的机制。

07 / TRADE-OFFS什么时候应该使用句柄？

句柄是一种手段，并非所有对象都需要它。

场景适用性原因
简单 C# 业务对象通常不需要普通引用更直接
对象池中的可复用实体很适合识别旧身份并控制访问
游戏 ECS 实体很适合通过索引与代数区分实体
跨语言、原生 API 调用很适合隐藏资源内部表示
GPU 资源、描述符管理很适合符合底层 API 的访问抽象
只需要稳定存档身份的对象不一定可能更需要持久化 ID
频繁直接修改的临时局部对象不一定额外查找可能增加复杂度

直接引用往往能避免额外的句柄解析。句柄表虽然可以非常高效，仍需要考虑查询、有效性验证、间接访问和缓存局部性等成本；实际性能取决于数据布局与访问方式。

当你需要稳定的访问接口、受控的资源身份和集中生命周期管理时，句柄才体现出它的价值。

08 / ESSENCE重新回到句柄的本质

第一层：标识

句柄是代表某个资源访问入口的值，而不是资源本身。

第二层：间接访问

使用者把句柄交给管理系统，由管理系统解释它，进行查找、验证和操作。

第三层：契约

句柄是否有效、拥有什么权限、如何复制、谁负责释放，以及是否保活资源，都由所属系统的契约决定。

Handle + Manager Contract → Controlled Resource Access

句柄 + 管理系统契约 → 受控制的资源访问

句柄把资源的使用者与资源的实际管理方式分离开来，使管理者能够在明确的规则下控制资源的访问、身份与生命周期。

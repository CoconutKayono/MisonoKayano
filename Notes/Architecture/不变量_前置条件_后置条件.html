WHAT / WHY / HOW

不变量、前置条件
与后置条件

从一次金币消费出发，理解有效状态、操作契约与程序正确性。

一个操作在什么条件下允许执行？执行之后必须保证什么？系统有哪些规则不能被破坏？

不变量（Invariant）、前置条件（Precondition）、后置条件（Postcondition）共同回答这三个问题。它们帮助我们先规定“什么才算正确”，再讨论“代码怎样实现”。

架构学习笔记 · 整理于 2026-10-17 · 示例语言：C#

01 · 先建立整体认识

假设玩家的钱包里有 100 金币，现在准备消费 30 金币。

初始状态 · 满足不变量100 金币
余额 ≥ 0，钱包处于有效状态。
↓
前置条件 · Precondition消费数量为正数，且余额足够
30 > 0，并且 100 ≥ 30，因此允许执行。
执行 Spend(30) ↓
后置条件 · Postcondition新余额 = 旧余额 − 消费数量
100 − 30 = 70。
↓
最终状态 · 继续满足不变量70 金币
余额仍然 ≥ 0，钱包仍处于有效状态。
概念关心的问题时间范围
前置条件执行之前必须满足什么？操作开始前
后置条件执行之后必须保证什么？操作结束后
不变量哪些约束必须保持成立？对象或系统约定的有效状态

02 · What：它们究竟是什么？

1. 不变量：规定什么状态是有效的

在规定的作用范围内，系统所有有效状态都必须满足的性质或约束。

例如钱包的不变量：

Balance ≥ 0

不管执行获得金币、消费金币、购买物品还是领取奖励，只要钱包处于约定的有效状态，余额就不能为负数。

余额是否有效
100有效
50有效
0有效
−10无效

余额可以从 100 变成 70。数值发生了变化，但 Balance >= 0 这个性质仍然成立。

不变量要求保持的是某种性质，不是某个具体数值。

“始终成立”需要明确作用范围。某些操作内部可以暂时经过不满足对象不变量的中间状态，但不能让依赖该不变量的其他操作观察到它，并且必须在约定的操作边界或提交点恢复约束。并发环境还需要同步或事务机制。

2. 前置条件：规定什么时候可以执行

一个操作能够按照约定正确执行，所要求的事先条件。

例如 wallet.Spend(30) 可以要求：

amount > 0
Balance ≥ amount

它们描述的是特定操作对输入和当前状态的要求。

钱包余额为 20 时，满足不变量 20 >= 0，却不满足消费 30 金币的前置条件 20 >= 30。

有效状态不代表任意操作都可以执行。

前置条件可以由调用者确保，也可以由方法内部验证；在契约意义上，它规定的是操作被正确调用的条件。

3. 后置条件：规定完成后必须兑现的承诺

如果操作在满足前置条件的情况下正常完成，执行之后必须成立的条件。

Balancenew = Balanceold − amount

后置条件通常不只是描述最终状态，还会描述执行前和执行后之间的关系。

Balance >= 0 只能说明最终余额非负；newBalance == oldBalance - amount 才能说明本次消费扣除了约定的数量。

假如消费 30 金币，余额从 100 变成了 50：不变量仍然成立，但后置条件被违反了。

满足不变量，不代表操作执行正确。

03 · Why：为什么需要区分？

因为程序的正确性包含不同的问题。考虑这段代码：

public void Spend(int amount)
{
    Balance -= amount;
}

余额为 100 时，调用 Spend(30) 得到 70，看起来没有问题。但是：

  • 调用 Spend(-30)，余额反而增加 30。
  • 余额为 20 时调用 Spend(30)，余额变成 −10。

我们描述了操作怎样执行，却没有明确什么行为才算正确。

不变量：防止非法状态

Balance >= 0 约束整个钱包。无论哪个方法修改余额，都不能让钱包在约定边界上进入负余额状态。

前置条件：划定操作的有效调用范围

amount > 0 和 Balance >= amount 说明哪些参数与状态组合允许执行消费。

后置条件：判断操作是否实现承诺

newBalance == oldBalance - amount 用于判断是否按约定扣款。即使输入合法、最终余额非负，扣款仍然可能出错。

问题对应约束
钱包出现负余额违反不变量
尝试消费负数金币不满足前置条件
消费 30，却扣除 50违反后置条件
余额非负，但扣错金额需要后置条件；仅检查不变量无法发现

三者各有职责，不能互相替代。

04 · How：在 C# 中如何应用？

下面的钱包对象通过构造函数建立不变量，通过受控的方法修改余额。

C# · Wallet.cs
using System;
using System.Diagnostics;

public sealed class Wallet
{
    public int Balance { get; private set; }

    public Wallet(int initialBalance)
    {
        if (initialBalance < 0)
            throw new ArgumentOutOfRangeException(
                nameof(initialBalance));

        Balance = initialBalance;
    }

    public void Spend(int amount)
    {
        // 前置条件 1：消费数量必须为正数。
        if (amount <= 0)
            throw new ArgumentOutOfRangeException(
                nameof(amount));

        // 前置条件 2：余额必须足够。
        if (Balance < amount)
            throw new InvalidOperationException(
                "金币余额不足");

        // 保存操作之前的状态。
        int oldBalance = Balance;

        // 执行状态转移。
        Balance -= amount;

        // 检查后置条件。
        Debug.Assert(
            Balance == oldBalance - amount);

        // 检查不变量。
        Debug.Assert(Balance >= 0);
    }
}
  1. 进入操作之前：验证前置条件。非法调用被拒绝，此时余额没有被修改。
  2. 执行状态转移：由旧余额得到新余额，完成扣款。
  3. 操作结束之后：检查后置条件和不变量，辅助发现实现错误。

示例的适用范围

Debug.Assert 是开发阶段的辅助检查，不能替代正式环境中的业务验证；在未定义 DEBUG 时，这些断言调用通常不会编入程序。

示例假设钱包没有并发修改，并把余额不足定义为异常情况。如果余额不足是正常的业务结果，可以用 TrySpend 返回失败。

契约也会随 API 的定义改变：如果 TrySpend 允许在余额不足时被正常调用，那么“余额足够”就是成功分支的条件；方法的后置条件应分别说明“成功时扣款”和“失败时余额不变”。

05 · 它们与状态、行为、转移的关系

用 S 表示旧状态，T 表示状态转移，S′ 表示新状态：

S′ = T(S)

带有输入参数时，也可以写成 S′ = T(S, input)。例如消费操作的输入就是 amount。

记号含义钱包示例
I(S)旧状态满足不变量旧余额 ≥ 0
P(S, amount)满足操作的前置条件amount > 0，且旧余额 ≥ amount
T执行状态转移扣除指定数量的金币
Q(S, S′, amount)旧、新状态满足后置关系新余额 = 旧余额 − amount
I(S′)新状态继续满足不变量新余额 ≥ 0

状态转移描述状态如何改变；前置条件、后置条件和不变量约束这种改变的正确性。

它们不必指定操作具体怎样实现，而是规定正确实现必须满足什么。消费金币可以通过对象方法、命令处理器或数据库事务实现，但业务要求的正确性约束应保持明确。

先规定正确性，再选择实现方式。

06 · 设计契约与程序正确性

这三个概念共同构成契约式设计（Design by Contract）的核心：把方法看作调用者与实现者之间的契约。

  • 调用者的责任：满足前置条件。
  • 实现者的责任：在约定条件下执行操作，并保证后置条件与相关不变量。

形式化方法中的霍尔逻辑（Hoare Logic）使用以下表达：

{ P }   C   { Q }

P 是前置条件，C 是程序，Q 是后置条件。它表示：如果执行前满足 P，程序 C 一旦正常终止，执行后就满足 Q。

这是部分正确性的表述；程序是否一定终止，还需要额外证明。

引入不变量 I，保持不变量的操作可表示为：

{ I ∧ P }   C   { I ∧ Q }

开始时既满足不变量，也满足前置条件；正常完成后，既继续满足不变量，也满足后置条件。后置条件若引用旧状态，需要用旧值记号或保存的旧状态来表达。

用钱包做一次简单推理

  1. 已知 oldBalance >= amount 且 amount > 0。
  2. 实现保证 newBalance = oldBalance - amount。
  3. 因此 newBalance >= 0，不变量得以保持。

这个推理依赖检查与扣款期间余额不被其他操作修改，以及数值运算符合约定。上述 int 消费示例在条件成立时，减法结果处于非负的可表示范围。

这些概念不仅是写代码时的约定，也可以用于推理和证明程序正确性。

07 · 实际开发中的重要细节

1. 不是每个条件都应该成为不变量

Balance >= amount 只需要针对某次消费成立。钱包允许余额为 0，也允许余额不足以支付某笔消费。

不变量约束有效状态；前置条件约束特定调用。不要把所有操作要求都塞进对象的不变量。

2. 失败时的后置条件需要另外定义

消费失败时，我们通常希望：

Balancenew = Balanceold

但失败后状态不变并非天然保证。需要通过先验证再修改、事务回滚等设计实现。涉及多个对象或数据库时，必须明确失败语义。

3. 多个对象之间也可能存在不变量

wallet.Balance          // 当前余额
statistics.TotalEarned  // 历史累计获得量

字段各自合法，不代表整体业务一致。例如“获得 10 金币”可能要求余额和累计获得量同时增加 10；这是该操作必须兑现的跨对象承诺。

能否进一步规定 Balance <= TotalEarned，取决于初始余额是否计入累计、所有入账是否被统计等业务定义，不能仅凭字段名称推断。

跨对象的约束应由能够协调这些对象的业务操作或事务维护。单靠各对象检查自身数值，无法保证整体一致。

4. 不变量不能自动解决并发问题

假设余额为 100，两个操作同时尝试消费 80。它们可能都在修改前读到 100，并通过余额检查。

if (Balance >= amount)
{
    Balance -= amount;
}

这段代码不保证“检查与扣款”是原子的。具体交错方式不同，可能出现超额扣款，也可能出现更新丢失：两次消费都被报告成功，却只扣了一次钱。

需要锁、合适的数据库事务、带条件的原子更新等机制，确保检查和更新共同满足契约。

08 · 回顾与下一步

概念本质设计时问自己
不变量有效状态必须满足的规则什么状态不允许存在？在哪些边界上必须保证？
前置条件正确执行所要求的事先条件什么输入与当前状态允许这次调用？
后置条件操作完成必须兑现的承诺成功后必须成立什么？失败时又保证什么？
不变量规定什么状态合法，前置条件规定什么时候可以执行，后置条件规定执行后必须得到什么结果。

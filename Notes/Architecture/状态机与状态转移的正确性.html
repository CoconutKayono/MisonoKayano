核心结论

先抓住两个问题

状态机的本质，是用明确的状态与转移规则，约束一个系统在什么条件下，可以从什么状态变成什么状态。

状态转移的正确性，是保证每一次被允许的转移，都不会破坏系统必须遵守的规则，并且产生符合预期的结果。

问题关注点
状态机系统允许发生哪些变化？
正确性如何证明这些变化不会让系统进入错误状态，并且符合预期？
01 / WHAT

什么是状态机？

1. 从一个任务系统理解

假设游戏中有一个任务：玩家需要击败 3 个敌人，然后领取 100 金币。这个任务可以处于四种状态：

状态英文含义
未开始NotStarted玩家尚未接受任务
进行中InProgress正在完成任务
已完成Completed达成目标，但尚未领奖
已领取Claimed已经领取任务奖励

任务不能任意切换状态。例如，未开始 → 进行中是允许的；进行中 → 已完成需要达成任务目标；已完成 → 已领取需要执行领奖；未开始 → 已领取则不允许。

任务进行中的进度可以是 0、1、2，不一定要分别定义成独立的枚举状态。可以用 Progress 表示数值，再用 Phase 表示所处阶段。

2. 状态机的数学定义

一个基础的确定性有限状态机可以抽象为：

M = (S, E, δ, s0)
符号含义
S系统可能处于的状态集合
E输入事件的集合
δ状态转移函数
s0初始状态

最关键的是状态转移函数：

s′ = δ(s, e)

给定当前状态 s 和事件 e，按照转移规则得到下一个状态 s′。

δ(NotStarted, Start) = InProgress

但是 δ(NotStarted, ClaimReward) 在这个设计中不是合法的领奖转移。实际业务通常还需要考虑进度、权限、余额等上下文数据：

s′ = δ(s, e, c)

c 表示影响转移判断的上下文数据。

定义上的说明

标准的确定性有限自动机通常使用全函数 δ。业务状态机可以使用部分转移函数；也可以对所有输入定义结果，把非法输入明确处理为“拒绝”“报告错误”或“保持原状态”。这里采用业务状态机的表述。

Phase 是阶段标签；用于正确性推导的完整状态 s 还包括 Progress、Gold 等相关数据。只看阶段枚举，无法判断所有业务约束。

02 / WHY

为什么需要状态机？

1. 不是所有状态变化都合法

假设我们直接修改状态：

C# · 教学示例
quest.Phase = QuestPhase.Claimed;

这行代码语法上可能完全正确，但业务上可能存在问题：

  • 玩家还没有接受任务。
  • 玩家还没有击败 3 个敌人。
  • 玩家没有完成领取奖励的流程。
  • 玩家已经领取过奖励。

程序能够修改一个值，不代表这个修改符合业务规则。 状态机首先用于限制非法变化。

2. 局部正确不等于整体正确

假设有三个方法：

C# · 教学示例
StartQuest();
CompleteQuest();
ClaimReward();

每个方法单独看都没有明显错误。但如果顺序变成：

C# · 教学示例
ClaimReward();
StartQuest();
CompleteQuest();

系统就可能出现问题。我们不仅要检查方法内部，还要检查：这些操作以什么顺序发生，以及当前状态是否允许执行。 状态机把隐含的调用顺序约束变成显式的转移规则。

3. 状态之间可能互相矛盾

使用三个布尔变量时：

C# · 教学示例
bool isStarted;
bool isCompleted;
bool isClaimed;

它们一共可以产生 2³ = 8 种组合，但有些组合是非法的：

C# · 教学示例
isStarted   = false;
isCompleted = false;
isClaimed   = true;

玩家没有开始任务，却已经领取奖励。用枚举表达互斥阶段，可以减少组合歧义：

C# · 教学示例
public enum QuestPhase
{
    NotStarted,
    InProgress,
    Completed,
    Claimed
}

使用 enum 不等于实现了状态机。 只有明确约束哪些事件能够导致哪些状态变化，才建立了转移规则。

03 / WHAT

什么叫状态转移的正确性？

先区分四个概念：

概念它回答的问题
不变量 · Invariant系统始终必须满足什么？
前置条件 · Precondition转移之前必须满足什么？
后置条件 · Postcondition转移成功之后必须保证什么？
转移规则 · Transition Rule什么事件和条件决定下一个状态？

1. 不变量：系统绝不能违背的约束

对于任务系统，可以规定：

  • 任务进度必须在 0～3 之间。
  • 任务已领取奖励，意味着必须已完成目标。
  • 已领取状态必须有相应的奖励发放记录。

用谓词 I 表示判断状态是否合法：

I(s) = true
0 ≤ Progress ≤ 3
Phase = Claimed ⇒ Progress = 3

这些条件必须对所有可达的有效任务状态成立。不变量可以约束单个字段，也可以约束多个字段之间的关系。

2. 前置条件：什么时候允许转移？

对于首次领取任务奖励：

Pre(s, Claim) = (Phase = Completed)

当前任务必须已经完成，否则拒绝首次领奖。前置条件约束的是操作执行之前需要满足的要求。

3. 后置条件：成功以后必须发生什么？

如果奖励为 100 金币，首次领取成功后应保证：

Phase′ = Claimed
Gold′ = Gold + 100
RewardRecorded′ = true

撇号 ′ 表示转移后的值。后置条件不仅描述结果状态，还能描述前后状态的关系：

Gold′ − Gold = 100

这比 Gold ≥ 100 更准确：它说明本次操作究竟增加了多少金币。

4. 把条件放在一起

I(s) ∧ Pre(s, e)
⇒ I(s′) ∧ Post(s, e, s′)

这表示：如果转移之前状态合法，并且满足执行条件，那么成功执行后，结果必须符合预期，而且不变量仍然成立。

公式的前提

这里的 s′ 必须是按照规定转移实际得到的后继状态。更显式的写法是：

I(s) ∧ Pre(s, e) ∧ T(s, e, s′) ⇒ I(s′) ∧ Post(s, e, s′)

T 表示一次实际转移。这个公式约束成功执行的结果，本身不证明操作一定终止，也不证明数据库提交一定成功。

04 / HOW

用 C# 实现一个具有约束的状态机

下面实现一个简化的任务状态机。为方便理解，暂时把任务状态和金币放在同一个快照中。真实项目可以分为不同模块，但跨模块更新需要单独考虑事务一致性。

1. 定义状态和事件

C# · 教学示例
using System;

public enum QuestPhase
{
    NotStarted,
    InProgress,
    Completed,
    Claimed
}

public enum QuestEvent
{
    Start,
    DefeatEnemy,
    ClaimReward
}

public record QuestSnapshot(
    QuestPhase Phase,
    int Progress,
    bool RewardRecorded,
    int Gold
);

把当前状态作为完整快照，可以直接对比转移前后的数据。此示例使用 C# 9 的 record 和 with 语法；在 Unity 中使用时，需要确认项目的编译环境支持这些语法及相关类型。

2. 实现转移函数

C# · 教学示例
public static class QuestStateMachine
{
    private const int Target = 3;
    private const int Reward = 100;

    public static QuestSnapshot Apply(
        QuestSnapshot before,
        QuestEvent evt)
    {
        // 输入状态必须满足不变量。
        Validate(before);

        QuestSnapshot after = evt switch
        {
            QuestEvent.Start
                when before.Phase == QuestPhase.NotStarted
                => before with
                {
                    Phase = QuestPhase.InProgress
                },

            QuestEvent.DefeatEnemy
                when before.Phase == QuestPhase.InProgress
                => Advance(before),

            QuestEvent.ClaimReward
                when before.Phase == QuestPhase.Completed
                => before with
                {
                    Phase = QuestPhase.Claimed,
                    RewardRecorded = true,
                    Gold = checked(before.Gold + Reward)
                },

            // 重复领奖：返回原状态，不重复增加金币。
            QuestEvent.ClaimReward
                when before.Phase == QuestPhase.Claimed
                => before,

            _ => throw new InvalidOperationException(
                "非法状态转移")
        };

        // 输出状态必须继续满足不变量。
        Validate(after);
        return after;
    }

    private static QuestSnapshot Advance(QuestSnapshot state)
    {
        int progress = Math.Min(Target, state.Progress + 1);

        return state with
        {
            Progress = progress,
            Phase = progress == Target
                ? QuestPhase.Completed
                : QuestPhase.InProgress
        };
    }

    private static void Validate(QuestSnapshot state)
    {
        if (state is null)
            throw new ArgumentNullException(nameof(state));

        // C# 枚举也可能包含未定义的整数值。
        if (!Enum.IsDefined(typeof(QuestPhase), state.Phase))
            throw new InvalidOperationException("未知任务阶段");

        if (state.Progress < 0 ||
            state.Progress > Target ||
            state.Gold < 0)
        {
            throw new InvalidOperationException(
                "数值不变量被破坏");
        }

        if (state.RewardRecorded !=
            (state.Phase == QuestPhase.Claimed))
        {
            throw new InvalidOperationException(
                "奖励状态不一致");
        }

        if ((state.Phase == QuestPhase.Completed ||
             state.Phase == QuestPhase.Claimed) &&
            state.Progress != Target)
        {
            throw new InvalidOperationException(
                "任务完成状态与进度不一致");
        }

        if (state.Phase == QuestPhase.NotStarted &&
            state.Progress != 0)
        {
            throw new InvalidOperationException(
                "未开始任务存在进度");
        }

        if (state.Phase == QuestPhase.InProgress &&
            state.Progress >= Target)
        {
            throw new InvalidOperationException(
                "进行中任务已达到完成条件");
        }
    }
}

整理时补充了空快照和未定义枚举值检查，其余核心转移逻辑与原讲解一致。

3. 用转移表核对实现

当前阶段事件 / 条件新阶段数据变化
NotStartedStartInProgress其他字段不变
InProgressDefeatEnemy，更新后进度 < 3InProgressProgress + 1
InProgressDefeatEnemy，更新后进度 = 3CompletedProgress = 3
CompletedClaimRewardClaimedGold + 100；记录奖励
ClaimedClaimRewardClaimed全部不变
其他组合不符合上述规则拒绝不产生新快照

首次领奖和重复领奖是两个分支。首次领奖的后置条件是 Gold′ = Gold + 100；重复领奖的后置条件是 s′ = s。不能把“加 100 金币”作为所有领奖请求共同的后置条件。

4. 这个实现体现了什么？

  1. 转移规则集中。 业务变化由 Apply() 计算，避免随意改动阶段。
  2. 转移条件明确。 只有 Completed 才能首次领奖。
  3. 转移前后验证不变量。 不把非法状态当作正常结果。
  4. 计算与存储分离。 Apply 只计算新快照，不写数据库，也不发送网络消息，便于测试。
实现的边界

RewardRecorded 只是快照中的标记，不能独自证明外部奖励系统已经成功发放金币；Validate 也不检查所有后置条件，例如“金币恰好增加 100”。

公开的 record 仍允许调用方自行构造快照或使用 with。这个示例没有从类型层面强制所有写入都经过状态机；实际系统需要通过封装和存储入口约束写入。

checked 用于检测金币整数溢出；发生溢出时抛出异常，不返回成功结果。异常属于本示例的失败策略。

05 / 正确性推导

正确性不只是一次转移正确

如果每次转移都符合前置条件、后置条件和不变量，那么连续执行 100 次、1000 次之后，能保证系统依然满足不变量吗？

1. 利用数学归纳法

首先，初始状态满足不变量：

I(s0) = true

其次，每一次被允许的转移都保持不变量：

I(sn) ∧ Pre(sn, e)
⇒ I(sn+1)

在后继状态按转移规则得到的前提下，可以逐步推出：

I(s0) ⇒ I(s1) ⇒ I(s2) ⇒ …

因此，在这些假设成立时，任意有限次合法转移后，不变量仍然成立。这就是归纳不变量（Inductive Invariant）的思路。

但证明要求：所有能够修改相关状态的操作都遵守这些规则。 如果其他模块可以绕过状态机直接修改 Gold 或 Phase，就不能只凭状态机的证明保证整个系统正确。

2. 安全性与活性

性质关注的问题任务系统示例
安全性 · Safety不应该发生的事情不会发生未完成不能领奖；同一奖励不能重复发放
活性 · Liveness在给定假设下，要求的进展最终发生任务完成后，玩家持续请求且系统正常处理，最终能够领奖

一个系统如果永远拒绝所有事件，可能满足某些安全性要求，但玩家永远无法完成任务。没有发生非法变化，不等于系统能够完成工作。

严格的活性要求“最终发生”，不只是“存在一条可以成功的路径”。证明活性通常还需要假设事件最终到达、处理不永久阻塞，以及调度具有适当的公平性。

06 / 执行环境

现实中的难点：并发与持久化

前面的代码假设转移按顺序执行，而且新快照能够正确保存。真实服务端未必满足这些条件。

1. 两个并发的领奖请求

请求 A
  1. 读取 Completed
  2. 判断允许领奖
  3. 向钱包发放 100 金币
请求 B
  1. 也读取 Completed
  2. 也判断允许领奖
  3. 也向钱包发放 100 金币

两个请求各自执行规则时，都可能得到合法判断。但如果各自向钱包发放奖励，就可能重复发奖。

单次转移逻辑正确，不代表多个并发转移组成的执行过程正确。

上面的纯快照函数本身并没有向外部钱包发奖。并发请求各自算出一个“金币 +100”的快照，如何提交、合并或覆盖，还取决于存储层；不能只看函数就推断最终一定重复发奖或一定不会丢失更新。

2. 原子性与并发控制

如果任务与钱包都在支持事务的同一个数据库中，一个可行流程是：

  1. 开启事务。
  2. 用锁或版本条件保护当前任务状态。
  3. 确认任务仍处于 Completed。
  4. 将任务改为 Claimed，同时增加 100 金币并登记领奖记录。
  5. 在同一事务中提交。

事务让相关数据要么全部保存，要么全部回滚；锁、条件更新或版本检查用于防止两个请求都依据同一旧状态成功提交。两类保证需要配合。

如果奖励发放跨越不同服务或数据库，单个本地事务通常不能覆盖全部操作，还需要考虑持久化消息、Outbox、幂等消费等机制。

层次保证什么
状态转移规则逻辑上允许哪些变化
并发控制多个操作不会因错误交错而破坏约束
持久化与事务提交满足规定的原子性与持久性保证

三者解决不同问题，共同影响系统正确性。

单例测试与属性测试

除了检查单个案例，还可以生成随机事件序列，反复调用转移函数，验证每次成功转移后不变量仍然成立。这是属性测试（Property-Based Testing）的一种应用。

也应检查具体后置条件，例如首次领奖恰好加 100、重复领奖完全不变、非法事件不产生新状态。仅检查不变量，可能漏掉“奖励少发”等错误。

有限测试可以帮助发现错误，但不能单凭测试证明所有可能执行过程都正确。

08 / 本质

从“变化”走向“正确的演化”

第一层：状态机是对变化的建模

一个系统的运行可以看成一连串状态：

s0 → s1 → s2 → …

状态机描述哪些变化被允许，以及变化发生的条件。

第二层：状态机是约束

它不仅描述当前处于什么阶段，还阻止不符合规则的变化。真正重要的是 Transition 规则，而不仅是 State 枚举。

第三层：正确性约束整个演化过程

合法起点 + 合法条件
+ 正确结果 + 不变量保持

涉及并发和持久化时，还必须保证逻辑上的转移能够被正确执行和保存。

状态机定义系统允许如何变化；不变量规定系统绝不能变成什么样；前置条件限制何时允许变化；后置条件规定变化后必须得到什么；并发控制和事务则帮助这些变化在真实环境中可靠地执行。

下一步可以学习什么？

Design by Contract（契约式设计）与Hoare Logic（霍尔逻辑）会进一步回答：如何从“我认为代码正确”，走向“我能基于明确条件，推导代码为什么正确”？

它们将这里的前置条件、后置条件和不变量，扩展为分析程序正确性的系统方法。

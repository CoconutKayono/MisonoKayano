这两种架构有一个非常重要的共同思想：

业务逻辑不应该被数据库、UI、Unity、网络框架等技术实现所支配。相反，技术实现应该围绕业务需要提供能力。

它们和我们之前讨论的高内聚、低耦合、信息隐藏、模块边界有直接联系。但这次，我们要再深入一步：依赖应该指向哪里？为什么依赖方向会决定软件的可维护性？

先给出本质定义。

架构 最核心的原则
Clean Architecture（整洁架构） 将业务规则置于中心，让源代码依赖指向更内层的业务策略
Hexagonal Architecture（六边形架构） 将应用与外部技术隔离，通过端口与适配器进行交互

它们高度相似，可以组合使用，但不是严格相同的架构规范。

Clean Architecture 由 Robert C. Martin 系统性阐述，Hexagonal Architecture 则由 Alistair Cockburn 提出。两者都强调业务与外部机制的隔离，但表达方式、关注重点有所不同。

01What：Clean Architecture 究竟是什么？

1. 先理解它要区分的两种东西

假设你正在开发一个游戏背包系统。

它包含两个类别的逻辑。

第一类：业务规则（Business Rules）。

例如：

  • 玩家最多持有 99 个相同道具。
  • 消耗道具时，数量不能小于零。
  • 领取过的奖励不能重复发放。

第二类：技术实现（Technical Details）。

例如：

  • 使用 MySQL、PostgreSQL 还是 SQLite。
  • 使用 Unity MonoBehaviour 还是 ASP.NET Core 接收操作。
  • 使用 Redis 还是内存字典缓存数据。
  • 如何将数据转换成 JSON。

现在思考：

如果我只是把数据库从 MySQL 换成 PostgreSQL，为什么“道具不能扣成负数”这条业务规则需要修改？

理论上，它不应该受到影响。

因为这条规则本身与数据库无关。

Clean Architecture 就是尝试在软件结构上落实这种区分。

2. Clean Architecture 的核心层次

常见的 Clean Architecture 将系统划分成下面几种职责层次。

这个图的关键不是必须有四层，也不是必须采用这种文件夹名称。

关键在于一个规则：

Dependency Rule（依赖规则）：源代码依赖指向内部，而不是让内部依赖外部。

这是 Robert C. Martin 在 The Clean Architecture（2012） 中明确提出的核心约束。

3. 什么叫依赖指向内部？

先看错误的方向。

InventoryService · 独立示意片段C# · 示意片段，需置于相应上下文
public class InventoryService
{
    private readonly MySqlInventoryRepository _repository;

    public InventoryService()
    {
        _repository = new MySqlInventoryRepository();
    }
}

InventoryService 依赖 MySqlInventoryRepository。

假设它们分别位于业务层和基础设施层：

Application
    |
    v
Infrastructure
    |
    v
MySQL

业务代码知道数据库的具体实现。

如果换成 PostgreSQL，就可能需要修改业务层。

Clean Architecture 希望将这个依赖方向反过来：

Infrastructure
       |
       v
Application
       |
       v
Domain

但这里产生一个看起来矛盾的问题：

业务需要读取数据库，如果业务代码不能依赖数据库实现，那它怎么调用数据库？

答案是：依赖倒置（Dependency Inversion）。

我们在 Application 层定义业务需要的接口：

IInventoryRepository · 独立示意片段C# · 示意片段，需置于相应上下文
public interface IInventoryRepository
{
    Task<Inventory> LoadAsync(Guid playerId);

    Task SaveAsync(Inventory inventory);
}

Application 层使用接口：

InventoryService · 独立示意片段C# · 示意片段，需置于相应上下文
public class InventoryService
{
    private readonly IInventoryRepository _repository;

    public InventoryService(IInventoryRepository repository)
    {
        _repository = repository;
    }
}

Infrastructure 层负责实现接口：

SqlInventoryRepository · 独立示意片段C# · 示意片段，需置于相应上下文
public class SqlInventoryRepository : IInventoryRepository
{
    public Task<Inventory> LoadAsync(Guid playerId)
    {
        // 使用数据库读取数据
        throw new NotImplementedException();
    }

    public Task SaveAsync(Inventory inventory)
    {
        // 使用数据库保存数据
        throw new NotImplementedException();
    }
}

现在：

  • InventoryService 只依赖 IInventoryRepository。
  • SqlInventoryRepository 依赖并实现 IInventoryRepository。
  • 数据库实现可以更换，而不必要求业务服务修改其源代码。

这才是依赖方向改变的具体机制。

02最难理解的关键：执行方向和代码依赖方向不是一回事

这是理解 Clean Architecture 的核心。

如果这一点没理解，就容易觉得所谓的依赖倒置只是“到处写接口”。

我们将两个不同概念分开。

执行方向（Runtime Call Flow）：程序运行时，谁调用谁？

源代码依赖方向（Source Code Dependency）：编写和编译某段代码时，它需要知道哪些类型或契约？

例如：

InventoryService · 独立示意片段C# · 示意片段，需置于相应上下文
public class InventoryService
{
    private readonly IInventoryRepository _repository;

    public InventoryService(IInventoryRepository repository)
    {
        _repository = repository;
    }

    public Task SaveAsync(Inventory inventory)
    {
        return _repository.SaveAsync(inventory);
    }
}

数据库实现依赖 Application 中的接口，Application 不需要引用 SQL 实现。

调用可以向外发生，但源代码依赖仍然可以指向内层。

这里依赖的是 C# 的接口和多态机制，而不是某种特殊架构框架。

03Why：为什么要这样设计？

1. 隔离变化，而不是消灭依赖

假设你的游戏最初保存到本地文件：

InventoryService
       |
       v
JsonFileStorage

后来改为数据库：

InventoryService
       |
       v
PostgreSQL

如果业务服务依赖具体存储操作，改动很可能波及业务逻辑。

如果使用抽象：

InventoryService
       |
       v
IInventoryRepository
       ^
       |
PostgreSQLRepository

就可以把存储变化主要控制在适配器和程序组装部分。

Clean Architecture 追求的不是“以后切换数据库只需要一行代码”这种过于乐观的承诺。

真实的数据库迁移可能涉及数据结构、事务语义、查询性能和迁移工具。

它能带来的合理收益是：

尽量不让纯粹的基础设施变化，迫使业务规则也发生变化。

2. 业务逻辑可以脱离 Unity 或服务器框架测试

例如游戏中的规则：

调用或规则 · 独立示意片段C# · 示意片段，需置于相应上下文
public void AddItem(int itemId, int amount)
{
    if (amount <= 0)
        throw new ArgumentOutOfRangeException(nameof(amount));

    // 校验并增加道具
}

这段规则本身不需要：

MonoBehaviour
GameObject
Transform
UnityEngine

如果把规则放在普通 C# 类中，就可以直接进行单元测试。

无需启动 Unity 场景，也无需连接数据库。

这正是 Clean Architecture 和 Hexagonal Architecture 都高度重视的能力。

3. 让业务规则成为系统中相对稳定的部分

需要特别区分：

业务规则重要，不意味着它们永远不会变化。

例如你的游戏可以改成每组道具最多堆叠 999 个。

这是真实的业务规则变化。

Clean Architecture 并不能阻止这种变化。

它想避免的是另一种情况：

只是换了网络框架、持久化实现或者 UI 技术，却不得不修改道具堆叠规则。

这里的目标是让不同原因引起的变化尽可能分离。

04What：Hexagonal Architecture 又是什么？

Hexagonal Architecture 通常翻译为六边形架构，也叫 Ports and Adapters Architecture（端口与适配器架构）。

它由 Alistair Cockburn 在 2005 年提出，参见作者的 Hexagonal Architecture 原始文章。

原始思想很明确：应用应当能够脱离具体 UI 和数据库运行，并且能够由不同的外部入口驱动。

1. 为什么叫六边形？

不是因为软件必须有六个模块、六层结构或者六个接口。

六边形只是用来表达：

应用存在一个内部与外部之间的边界，而它可以通过多个不同的交互端口与外界通信。

这个模型强调：

应用核心不需要知道是 Unity 按钮、HTTP 请求还是自动化测试触发了某个操作。

同样，它也不需要知道数据最后保存在 SQL、文件还是内存中。

2. Port（端口）是什么？

Port 是应用为了与外部交互而定义的交互契约。

可以分为两种常见方向。

类型 作用 游戏示例
Driving / Input Port（驱动端口） 外界使用它来驱动应用行为 IClaimRewardUseCase
Driven / Output Port（被驱动端口） 应用通过它请求外部提供某种能力 IPlayerStateStore

例如：

IClaimRewardUseCase · 独立示意片段C# · 示意片段，需置于相应上下文
// 外界可以使用的业务能力
public interface IClaimRewardUseCase
{
    Task<ClaimResult> ExecuteAsync(
        ClaimRewardCommand command,
        CancellationToken ct);
}

它表达的是“领取奖励”这项业务能力。

再看：

IPlayerStateStore · 独立示意片段C# · 示意片段，需置于相应上下文
// 应用需要的持久化能力
public interface IPlayerStateStore
{
    Task<PlayerState> LoadAsync(
        Guid playerId,
        CancellationToken ct);
}

它表达的是应用需要加载玩家状态，但没有决定如何加载。

要注意，Port 是架构概念，不一定必须是 C# interface。它也可以通过函数、协议等形式表达。关键在于它规定了应用边界上的交互契约。

3. Adapter（适配器）是什么？

Adapter 是连接具体外部技术和应用端口的实现。

例如：

Unity Button
    ↓
Unity Adapter
    ↓
IClaimRewardUseCase
    ↓
Application

输入适配器把 Unity 特有的操作转换成应用能够理解的命令。

对于数据库：

Application
    ↓
IPlayerStateStore
    ↑
PostgreSqlAdapter
    ↓
PostgreSQL

数据库适配器把应用的存取需求转换成具体数据库操作。

Port 规定应用需要如何交互，Adapter 负责适应外部环境。

这是整个六边形架构最重要的关系。

05Clean 和 Hexagonal 究竟有什么区别？

它们可以同时使用，并不需要二选一。

两个互补视角

Clean：层次与依赖方向。 Infrastructure / UI → Application / Use Cases → Domain，关注源代码依赖是否指向内部。

Hexagonal：边界与交互。 UI / HTTP 等输入适配器通过端口驱动核心；核心通过输出端口使用 SQL / 文件等外部能力。

更精确地比较：

维度 Clean Architecture Hexagonal Architecture
核心关注 依赖规则与职责分层 应用边界与交互端口
典型表达 同心圆 六边形及端口
内部划分 通常明确区分 Domain、Use Cases 等 不强制规定同样的内部层次
外部隔离 通过向内依赖的规则 通过 Ports & Adapters
两者关系 可以采用端口与适配器实现隔离 可以在内部采用 Clean 的分层

如果把它们组合起来，可以这样理解：

Clean Architecture 告诉你应用内部与外部的依赖应当如何组织；Hexagonal Architecture 给出一种清楚表达和实现应用交互边界的方式。

06How：C# 游戏服务端完整示例

我们设计一个简化的游戏服务端业务：

玩家获得道具时，既要增加背包数量，也要记录累计获得数量。

要求同一业务请求重复提交时，只处理一次，而且两项数据必须一起提交。

我们先采用一个可以直接理解和测试的版本，再说明如何替换为真实数据库。

依赖归属修正： GrantItemCommand 属于 Application；Domain 的 GrantOnce 只接收领域操作所需的值，不引用该应用命令。GrantItemResult 是本例内层拥有的不可变结果值。

2. Domain：只负责业务规则

PlayerState.csC# · 第六节完整源码，按项目组合编译
using System;
using System.Collections.Generic;

namespace Game.Domain;

public sealed record GrantItemResult(
    int CurrentCount,
    int TotalObtained);

public sealed class PlayerState
{
    private readonly Dictionary<int, int> _items = new();
    private readonly Dictionary<int, int> _totals = new();

    private readonly Dictionary<Guid,
        (int ItemId, int Amount, GrantItemResult Result)>
        _processed = new();

    public int GetCount(int itemId)
        => _items.GetValueOrDefault(itemId);

    public int GetTotal(int itemId)
        => _totals.GetValueOrDefault(itemId);

    public GrantItemResult GrantOnce(
        Guid operationId, int itemId, int amount)
    {
        if (operationId == Guid.Empty ||
            amount <= 0)
            throw new ArgumentException("Invalid grant request.");

        if (_processed.TryGetValue(
            operationId, out var previous))
        {
            if (previous.ItemId != itemId ||
                previous.Amount != amount)
                throw new InvalidOperationException(
                    "OperationId reused with different parameters.");

            return previous.Result;
        }

        int count = checked(
            GetCount(itemId) + amount);

        int total = checked(
            GetTotal(itemId) + amount);

        var result = new GrantItemResult(count, total);

        _items[itemId] = count;
        _totals[itemId] = total;

        _processed.Add(
            operationId,
            (itemId, amount, result));

        return result;
    }

    public PlayerState Copy()
    {
        var copy = new PlayerState();

        foreach (var (key, value) in _items)
            copy._items.Add(key, value);

        foreach (var (key, value) in _totals)
            copy._totals.Add(key, value);

        foreach (var (key, value) in _processed)
            copy._processed.Add(key, value);

        return copy;
    }
}

注意这里没有：

核心中不应出现的技术引用 · 反例C# · 示意片段，需置于相应上下文
using UnityEngine;
using Microsoft.EntityFrameworkCore;
using Npgsql;

因为它们与业务规则无关。

PlayerState 只关心道具数量、累计统计和重复操作的规则。

这里为了集中展示事务一致性，把背包、累计统计和处理记录放在一个简化的玩家状态模型里。这不是要求你必须把它们设计成同一个业务模块。实际项目可以分别拥有 Inventory、Statistics 模块，由 Application 协调同一事务。

3. Application：定义用例和端口

首先定义输入端口。

IPlayerStateStore.csC# · 第六节完整源码，按项目组合编译
using System;
using System.Threading;
using System.Threading.Tasks;
using Game.Domain;

namespace Game.Application;

public interface IPlayerStateStore
{
    Task<T> UpdateAtomicallyAsync<T>(
        Guid playerId,
        Func<PlayerState, T> update,
        CancellationToken ct);
}

UpdateAtomicallyAsync 定义了一个语义契约：

给定玩家，应用可以执行一次状态变化，成功时整体提交，失败时不得留下部分变化。

然后实现应用用例：

GrantItemUseCase.csC# · 第六节完整源码，按项目组合编译
using System.Threading;
using System.Threading.Tasks;
using Game.Domain;

namespace Game.Application;

public sealed class GrantItemUseCase : IGrantItemUseCase
{
    private readonly IPlayerStateStore _store;

    public GrantItemUseCase(IPlayerStateStore store)
    {
        _store = store;
    }

    public Task<GrantItemResult> ExecuteAsync(
        GrantItemCommand command,
        CancellationToken ct)
    {
        return _store.UpdateAtomicallyAsync(
            command.PlayerId,
            state => state.GrantOnce(
                command.OperationId, command.ItemId, command.Amount),
            ct);
    }
}

注意这三个角色的区别：

角色 职责
PlayerState 保证道具数量等业务规则
GrantItemUseCase 组织“发放道具”这个业务用例
IPlayerStateStore 规定应用所需要的原子状态保存能力

Application 不知道具体数据库，也没有亲自实现持久化。

它只声明自己的要求。

4. Infrastructure：实现输出适配器

先用内存存储来演示，方便理解和测试。

InMemoryPlayerStateStore.csC# · 第六节完整源码，按项目组合编译
using System;
using System.Collections.Generic;
using System.Threading;
using System.Threading.Tasks;
using Game.Application;
using Game.Domain;

namespace Game.Infrastructure;

public sealed class InMemoryPlayerStateStore
    : IPlayerStateStore
{
    private readonly object _gate = new();

    private readonly Dictionary<Guid, PlayerState>
        _states = new();

    public Task<T> UpdateAtomicallyAsync<T>(
        Guid playerId,
        Func<PlayerState, T> update,
        CancellationToken ct)
    {
        ct.ThrowIfCancellationRequested();

        lock (_gate)
        {
            ct.ThrowIfCancellationRequested();
            var working = _states.TryGetValue(
                playerId, out var saved)
                    ? saved.Copy()
                    : new PlayerState();

            T result = update(working);

            _states[playerId] = working;

            return Task.FromResult(result);
        }
    }
}

这里有几个重要细节。

首先，这个适配器直接依赖了 PlayerState 和 IPlayerStateStore，即外层依赖内层。

其次，它通过锁、状态副本和成功后替换的方式，模拟单进程内的一次原子状态更新。

如果 update 抛出异常，就不会替换原状态。

这个回调必须同步完成，只操作工作副本，不执行外部 I/O，也不能把可变状态引用保存到外部或作为结果泄漏。本例返回不可变 record；副本机制只撤销尚未提交的内存变化，不能撤销已经发送的网络消息或文件写入。全局锁会串行化所有玩家操作；示例在进入锁后再次检查取消，但不声称提交之后的取消能够回滚。

但这只是内存版教学实现，不是可用于多实例游戏服务端的可靠持久化方案。

真实数据库适配器需要用数据库事务、并发控制和持久化请求记录实现对应契约。单进程 lock 无法保证跨进程原子性，进程重启也会丢失内存数据。

5. Host：组装整个应用

虽然 Application 没有依赖具体存储实现，但运行时必须选择一个实现。

Program.csC# · 第六节完整源码，按项目组合编译
using System;
using System.Threading;
using Game.Application;
using Game.Infrastructure;

IPlayerStateStore store =
    new InMemoryPlayerStateStore();

IGrantItemUseCase useCase =
    new GrantItemUseCase(store);

Guid playerId = Guid.NewGuid();
Guid operationId = Guid.NewGuid();

var command = new GrantItemCommand(
    playerId,
    operationId,
    ItemId: 1001,
    Amount: 5);

var first = await useCase.ExecuteAsync(
    command, CancellationToken.None);

var second = await useCase.ExecuteAsync(
    command, CancellationToken.None);

Console.WriteLine(first);
Console.WriteLine(second);

输出：

GrantItemResult {
    CurrentCount = 5,
    TotalObtained = 5
}

GrantItemResult {
    CurrentCount = 5,
    TotalObtained = 5
}

同一个 OperationId 的第二次执行不会再增加道具，而且返回第一次处理的结果。这是历史结果重放：即使后来发生了其他操作，旧请求仍返回首次结果，不代表查询当前最新数量。

如果使用不同的 OperationId，则可以代表另一次合法的发放操作。

这个例子还没有展示游戏业务层如何验证奖励资格。在正式服务端中，客户端不能随意提交 ItemId 和 Amount 要求发放。应该先验证已经获得、可领取的奖励，再由可信的服务端流程调用 GrantItemUseCase。

刚才的设计可以抽象成：

假设我们想做一次测试。

我们完全不必启动 HTTP 服务器，也不必连接真实数据库。

只需要：

就可以测试整个用例。

08Unity 中如何应用？

这里需要特别区分 Unity 客户端和权威游戏服务端。

对于 Unity 客户端，Clean Architecture 可以用于分离游戏规则、用例和 MonoBehaviour。

例如：

Game.Domain
    Inventory.cs

Game.Application
    UseItemUseCase.cs
    IItemRepository.cs

Game.Unity
    InventoryPanel.cs
    InventoryPresenter.cs

Game.Infrastructure
    LocalInventoryRepository.cs

InventoryPanel 负责接收玩家点击。

UseItemUseCase 决定这个操作需要执行什么业务流程。

Inventory 负责确保道具的使用规则得到遵守。

LocalInventoryRepository 负责本地持久化。

Unity 的 Assembly Definition 可以控制程序集引用。在纯规则程序集的 .asmdef 中启用 No Engine References，可以取消 Unity 自动添加的 UnityEngine / UnityEditor 引用；同时应约束其他程序集引用，由 Unity 表现层引用内层。参见 Unity 官方 Assembly Definition 属性说明。

但在联网游戏中：

客户端的 UseCase 不应该代替权威服务器判定玩家获得了哪些道具。

Unity 客户端负责提交可信度有限的操作意图，例如请求领取某项奖励；服务端验证请求是否合法，决定是否改变持久化状态。

同一套架构原则可以分别应用在客户端与服务端，但它们承担的权限和数据正确性责任不同。

09设计权衡：Clean / Hexagonal 有什么代价？

这些架构不意味着每个项目都应该严格遵守四层结构，或者为每个方法创建接口。

维度 收益 代价
业务独立性 减少业务对框架、数据库的依赖 需要维护边界和数据转换
可测试性 可以通过替身独立测试业务 测试替身可能无法反映真实数据库行为
技术替换 限制外部实现变化的影响范围 实际迁移仍可能涉及语义与数据兼容问题
代码组织 明确领域、用例、适配器的职责 文件、类型、接口及间接调用增多
系统演化 有利于长期维护复杂业务 初期设计与认知成本更高

1. 不要把所有类都变成接口

下面这种设计通常没有必要：

IInventory · 独立示意片段C# · 示意片段，需置于相应上下文
public interface IInventory
{
    void AddItem(int itemId, int amount);
}

假设你只有一个 Inventory 领域对象，没有真正需要替换的实现，那么直接使用具体领域类可能更加清晰。

Clean Architecture 的重点不是依赖任何接口，而是避免让核心业务依赖不该依赖的外部技术细节。

不是每个类都需要抽象，也不是每个依赖都需要倒置。

2. 不要为了分层而分层

对于一个只有几百行代码的游戏原型：

Domain
Application
Adapters
Infrastructure
Presentation
Persistence
Contracts

可能太繁琐。

实际上你可以从：

Game.Core
Game.Unity

开始。

把纯游戏规则放在 Core，把 MonoBehaviour、资源加载等依赖 Unity 的实现放在 Unity 项目中。

随着代码规模和业务复杂度增加，再逐步引入必要的端口和适配器。

3. Clean Architecture 不能自动保证数据可靠性

例如：

调用或规则 · 独立示意片段C# · 示意片段，需置于相应上下文
await inventoryStore.SaveAsync(inventory);

await statisticsStore.SaveAsync(statistics);

即使这两个 Store 都通过接口抽象，依然可能存在第一个保存成功、第二个失败的问题。

Clean Architecture 解决的是依赖关系与职责组织的问题。

原子性、并发控制、幂等和持久化可靠性则需要专门的机制。

要满足之前的“背包增加道具、统计同时增加”的强一致性要求，仍然需要在应用层明确事务边界，并让基础设施适配器正确实现它。

4. 不要把“隔离数据库”理解成“业务必须与数据库能力无关”

这是更深入的一点。

业务可能明确要求：

  • 同一请求不能重复执行。
  • 两个数据修改必须一起提交。
  • 并发修改不能覆盖其他已提交的数据。

这些都可能是应用对持久化的真实要求。

因此，在 Application 中定义一个具备事务语义的端口是合理的。

IPlayerTransaction · 独立示意片段C# · 示意片段，需置于相应上下文
public interface IPlayerTransaction
{
    Task ExecuteAsync(
        Func<CancellationToken, Task> action,
        CancellationToken ct);
}

业务知道自己需要“原子提交”，但不需要知道底层通过 PostgreSQL 事务还是其他机制实现。

隐藏技术实现，不等于隐藏业务真正依赖的语义。

这也是我们此前示例中 UpdateAtomicallyAsync 要明确原子语义的原因。

10它们与 Modular Monolith、DDD 是什么关系？

这四种思路经常一起出现，但解决的问题不同。

概念 主要回答
Modular Monolith 整个应用如何划分成业务模块，又保持整体部署？
DDD 如何理解业务领域、建立模型和划分业务边界？
Clean Architecture 模块内部的职责与源代码依赖应该如何组织？
Hexagonal Architecture 应用如何通过端口和适配器与外界合作？

例如你可以设计一个模块化单体：

GameServer
│
├── InventoryModule
│   ├── Domain
│   ├── Application
│   └── Infrastructure
│
├── StatisticsModule
│   ├── Domain
│   ├── Application
│   └── Infrastructure
│
└── ShopModule
    ├── Domain
    ├── Application
    └── Infrastructure

整体采用 Modular Monolith。

每个模块内部借鉴 Clean Architecture。

模块与数据库、网络之间借鉴 Hexagonal Architecture。

模块的业务职责和模型划分可以借鉴 DDD。

不过，这不是唯一的合理组织方式。实际项目也可以让多个小模块共用基础设施，或减少层次；关键是依赖和所有权仍然清晰。

11直达本质：真正要记住什么？

Clean Architecture 和 Hexagonal Architecture 可以归结为三个基本判断。

什么是核心？

业务规则和业务用例是应用存在的主要理由，而具体框架与数据库是帮助它运行的手段。

依赖应当指向谁？

核心尽量不依赖具体外部技术；外部实现通过应用定义的契约提供能力。

外部如何合作？

通过明确的交互端口连接具体适配器，让业务可以独立于某个 UI、数据库或框架执行与测试。

最终可以浓缩成两句话：

Clean Architecture：让实现机制依赖业务策略，而不是让业务策略依赖实现机制。

Hexagonal Architecture：将应用看作具有明确端口的独立核心，让外部世界通过适配器连接它。

还有一个更深层的认识：

它们并不是在消除程序对数据库、UI 和外部服务的实际需要。它们是在改变这些需要如何体现在代码结构中。

应用运行时仍然需要访问数据库，但业务逻辑不必在源代码中绑定某个具体的数据库实现。

这才是两者真正精妙的地方。

DIP 与 DI 的区别： 依赖倒置原则（DIP）关心策略与实现之间的依赖关系、抽象由谁拥有；依赖注入（DI）是一种把依赖对象传入使用者的组装技术。即使通过构造函数注入一个具体 SQL 类，也未必满足向内依赖。

如果继续深入，我建议重点研究 Dependency Inversion Principle（依赖倒置原则），并区分它和 Dependency Injection（依赖注入）。因为这是整个设计最容易被误解、也最值得理解的技术基础：为什么只是把接口放在不同的地方，就能从根本上改变两个模块之间的源代码依赖方向？

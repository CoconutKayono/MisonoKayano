先给出一个核心结论：

事件的本质，是描述“某件事情发生了”这一事实。

它并不直接规定系统必须做什么，而是让系统能够知道某件事情发生了，并决定是否对此作出反应。

要真正理解事件，我们需要从三个角度研究：

  • What： 事件究竟是什么？它与状态、行为、状态转移有什么关系？
  • Why： 为什么需要事件？不使用事件会遇到什么问题？
  • How： 事件如何产生、传播、处理？在程序中如何正确使用？

01What：事件、事实与命令

1. 从现实世界理解事件

想象一个房间：

房间里有一盏灯，当前处于关闭状态。

某个人按下开关，灯变亮了。

我们可以从中区分四个概念：

概念 含义 示例
状态（State） 事物当前是什么样 灯是关闭的
事件（Event） 发生了什么 开关被按下
行为（Behavior） 事物如何行动或响应 灯的控制逻辑执行
状态转移（Transition） 状态如何发生改变 关闭 → 开启

这是一个典型过程，不是所有事件都必须造成状态变化。

注意一个非常关键的问题：

事件不等于状态发生改变。

例如：

  • 玩家在按钮区域按下输入，但按钮被禁用：物理输入可能发生，控件不一定发出点击回调，游戏状态也未必改变。
  • 玩家受到伤害，但处于无敌状态：受击事件可能发生，生命值没有改变。
  • 玩家获得道具：事件发生，并导致背包状态改变。

因此，更准确的理解是：

事件描述发生了什么；状态描述现在是什么；行为决定系统如何响应；状态转移描述变化的结果。

2. 事件是时间维度上的事实

进一步思考：

一个玩家现在拥有 100 金币。

这个状态能告诉我们什么？

只能告诉我们他当前有 100 金币。

但我们不知道：

  • 他是否刚刚获得了 50 金币？
  • 是否刚刚消费了 20 金币？
  • 是否从其他玩家那里收到了金币？

因为状态描述的是一个时刻的结果，而事件描述的是时间过程中发生的事情。

从中我们可以发现：

状态是某个时刻的描述；事件是时间线上发生的事实。

这一点非常重要，因为它解释了为什么程序设计中经常同时存在状态和事件。

状态适合回答：

现在有什么？

事件适合回答：

发生过什么？

但需要注意：一个普通的事件通知不代表事件会被永久记录。只有把事件持久化为日志或记录，才能在将来查询它。

3. 事件与命令：事实和意图的区别

这里是理解事件设计最容易混淆的地方。

考虑下面两句话：

  • 给玩家增加一个道具。
  • 玩家已经获得了一个道具。

它们看起来相似，但语义完全不同。

命令（Command） 事件（Event）
语义 请求做某事 某事已经发生
时间指向 尚未执行或正在请求 已经发生
是否可能被拒绝 可以 事实本身不需要批准
典型命名 GrantItem ItemGranted
主要作用 请求执行行为 通知或记录事实

例如：

玩家点击购买按钮：

PurchaseItemCommand

服务端检查金币是否足够。

如果金币不足，购买失败，就不应该产生 ItemPurchased 成功事件。

如果购买成功，才可以产生：

ItemPurchasedEvent

所以：

命令表达意图，事件表达事实。

当然，事件也可以描述失败，例如 PurchaseFailed，关键仍然是描述实际发生过的事情。

02Why：分离事实与响应，保留真实业务依赖

假设我们正在开发一个游戏。

玩家获得一个道具时，系统需要：

  1. 增加背包中的道具数量。
  2. 更新道具累计获取统计。
  3. 检查相关成就。
  4. 更新 UI。
  5. 播放获得道具的音效。

1. 不使用事件

最直观的方法是直接调用所有相关系统：

C# 调用／装配示意C# · 示意片段，需置于相应上下文
public void ObtainItem(string itemId)
{
    inventory.Add(itemId, 1);

    statistics.RecordItem(itemId, 1);

    achievements.CheckItem(itemId);

    inventoryUI.Refresh();

    audio.PlayItemSound();
}

这个方法完全可以正常工作。

这种写法有一个明确的设计取舍：

获得道具的业务逻辑，需要知道所有对此感兴趣的系统。

假设未来新增任务系统、教程系统、埋点系统。

那么 ObtainItem() 就要不断修改。

这里的显式依赖不一定都需要消除。若成就检查读取统计结果，原来的统计 → 成就顺序就是正确业务约束；需要分离的是无关实现知识，而不是抹去真实的前置条件。

2. 引入事件

我们可以让道具系统只完成自身的主要职责，并在成功后发布一个事实：

ItemObtained：玩家获得了道具。

其他系统根据自己的需要作出响应。独立的通知可以并列广播；依赖统计结果的成就检查，则必须有明确的先后契约。后文会逐一实现这些方案。

这样，道具系统不需要知道：

  • 成就系统如何实现。
  • UI 如何刷新。
  • 是否存在统计系统。
  • 将来是否新增其他监听者。

它只需要表达：

道具已经成功获得。

这就是事件最重要的工程价值之一：让事实的产生者与事实的观察者解耦。

不过要注意，事件并没有消除依赖，只是改变了依赖的形式。系统仍然需要约定事件的名称、含义和数据结构。

3. 更深一层：为什么这种设计成立？

一件事可能具有多个不同意义；但不同意义不等于其处理过程没有数据依赖。是否独立，应检查各步骤实际读取什么、产出什么。

例如，玩家击败 Boss：

  • 对战斗系统：敌人死亡。
  • 对任务系统：某个目标完成。
  • 对成就系统：满足了击杀条件。
  • 对 UI 系统：需要显示提示。

同一个事实，可以由多个系统从各自的角度解释。

这意味着事件有一个非常重要的特征：

事件提供事实，而不是替所有接收者决定行为。

因此，事件天然适合表达多个系统共同关心的业务事实。

03How：用 C# 实现发布、订阅与退订

从最基础的角度，事件机制通常包含三个部分：

  1. 事件产生（Emit / Publish）： 某个组件宣布事情发生了。
  2. 事件订阅（Subscribe）： 其他组件表示自己对这类事件感兴趣。
  3. 事件处理（Handle）： 事件发生后，订阅者执行响应逻辑。

这里我们使用 Unity / C# 演示。

1. 定义事件携带的信息

ItemObtainedEvent.csC# · 完整类型定义
public sealed class ItemObtainedEvent
{
    public string ItemId { get; }
    public int Amount { get; }

    public ItemObtainedEvent(string itemId, int amount)
    {
        ItemId = itemId;
        Amount = amount;
    }
}

事件数据需要回答：

  • 发生了什么？
  • 与哪些对象有关？
  • 有哪些相关信息？

在这个例子中，事件名称说明发生了道具获取，数据包含道具 ID 和数量。

实际服务端可能还需要玩家 ID、事件 ID、操作 ID 等字段。

2. 发布事件

Inventory.csC# · 完整类型定义
using System;
using System.Collections.Generic;

public sealed class Inventory
{
    private readonly Dictionary<string, int> items = new();

    public event Action<ItemObtainedEvent> ItemObtained;

    public void AddItem(string itemId, int amount)
    {
        if (amount <= 0)
            throw new ArgumentOutOfRangeException(nameof(amount));

        items.TryGetValue(itemId, out int current);

        // 修改状态
        items[itemId] = checked(current + amount);

        // 发布已经发生的事实
        ItemObtained?.Invoke(
            new ItemObtainedEvent(itemId, amount)
        );
    }
}

注意两个动作的顺序：

第一步：真正增加道具数量。

第二步：通知其他系统道具已经增加。

不能因为我们打算增加道具，就提前宣布道具已经获得成功。

3. 订阅与处理事件

ItemStatistics.csC# · 完整类型定义
using System.Collections.Generic;

public sealed class ItemStatistics
{
    private readonly Dictionary<string, int> totals = new();

    public void OnItemObtained(ItemObtainedEvent e)
    {
        totals.TryGetValue(e.ItemId, out int current);
        totals[e.ItemId] = checked(current + e.Amount);
    }
}

然后把它们连接起来：

C# 调用／装配示意C# · 示意片段，需置于相应上下文
Inventory inventory = new Inventory();
ItemStatistics statistics = new ItemStatistics();

// 订阅
inventory.ItemObtained += statistics.OnItemObtained;

// 获得道具
inventory.AddItem("Potion", 1);

// 不再需要时取消订阅
inventory.ItemObtained -= statistics.OnItemObtained;

本章三个完整类型分别保存为 ItemObtainedEvent.cs、Inventory.cs、ItemStatistics.cs。它们是普通 C# 对象；装配片段需要放进方法或合适的执行上下文，不是可单独挂载的 MonoBehaviour 脚本。示例使用目标类型 new() 语法。

在 Unity 中，如果订阅发生在 MonoBehaviour.OnEnable()，通常应在 OnDisable() 取消订阅，避免重复监听或生命周期问题。生命周期回调参考 Unity：OnDisable。

此处最值得注意的是：

Inventory 完全不知道 ItemStatistics 的存在。

它只宣布 ItemObtained。

这就完成了最简单的事件机制。Inventory 不引用 ItemStatistics 的具体类型；但订阅后的委托可以在运行时持有订阅者对象，所以仍需管理退订。Microsoft 的 C# 事件说明介绍了发布者与订阅者的角色。

04顺序从哪里来：通知依赖、数据依赖与时间耦合

1. 先检查、后统计，为何会漏解锁？

假设成就要求累计获得 10 瓶药水，玩家目前累计获得 9 瓶。又获得 1 瓶时，发布者在自身内部调用：

C# 调用／装配示意C# · 示意片段，需置于相应上下文
// 位于事件发布者内部；不代表外部可以直接 Invoke 事件
ItemObtained?.Invoke(itemEvent);

如果成就系统和统计系统都订阅这个事件，而且成就先加入调用列表：

C# 调用／装配示意C# · 示意片段，需置于相应上下文
// 顺序错误示意：Check 从 statistics 读取累计数量
inventory.ItemObtained += achievements.Check;
inventory.ItemObtained += statistics.Record;

普通 C# 多播委托在同步调用时，按调用列表顺序执行；常见的字段式 event 用 += 将处理器追加到列表。这里不是随机调度：先检查就真的可能读到旧值。规则参考 Microsoft：Using Delegates。自定义事件总线、并行调度和异步处理器则要按各自契约判断，不能套用这一保证。

结果是：成就先读到 9，判定未完成；统计随后变为 10，却没有新的成就检查。最终统计达标，成就仍未解锁。

调整订阅顺序是可行的最小方案，但规则应被集中维护。更明确的表达还包括事件优先级、分阶段派发、应用服务编排和因果事件链；选择取决于依赖结构，而不是只能二选一。

2. 通知依赖与数据依赖

通知依赖： UI 播放特效、音效播放声音、日志记录事实。如果这些处理器不依赖彼此的结果，通常适合围绕同一事实独立响应。不过“UI”“日志”的名字本身不保证独立，仍需检查实际读取和修改了什么。

数据依赖： 统计更新累计值 → 成就读取这个新值 → 判断是否完成。这里的先后次序来自业务，不是加一个事件总线就能消失的代码依赖。

把共同触发条件写成同一个事件，只说明它们都关心道具获取，不能证明它们互不依赖。

3. 结构耦合与时间耦合

结构耦合（Structural Coupling）： A 是否需要直接知道 B 的类型、接口或实现？事件可以减少直接类型引用，但双方仍依赖事件契约与装配。

时间耦合（Temporal Coupling）： A、B 是否必须按某种先后次序执行，或在某个时间点前完成？事件不会天然消除这类约束；它可能只是把原本显式的顺序藏进订阅和调度逻辑。

因此，使用事件不等于让所有系统完全独立。评价设计还应检查：业务约束是否正确表达，关键依赖是否可见，失败是否可处理，一致性是否满足要求。

05有序派发：订阅顺序、优先级与阶段

1. 固定订阅顺序：最小可行方案

对于普通的字段式 C# 事件，可以先订阅统计、后订阅成就，让同步调用列表按这个次序执行。这在单一组装入口、处理器同步执行、依赖很少且有测试约束时，是可行的方案。

它的局限是：规则附着在装配顺序上。不能只写一句“不要依赖顺序”就否定它，也不能把一次碰巧正确的注册顺序，当成整个项目都会维护的业务契约。关键流程至少应把次序集中、命名、注释并验证。

2. 事件系统支持优先级：把顺序提升为派发契约

可以用优先级解决这个顺序问题。 如果事件系统规定“高优先级先执行”，就可以让统计使用 100，成就使用 0。即使成就先注册，统计仍先运行。这里的数值只是本例约定，不是 C# 或 Unity 的内置标准。

这里指的是同一个事件的监听处理器优先级。它与消息队列中“哪些事件消息先出队”的消息优先级不同；只把 ItemObtained 这类消息提到队首，并不会自动决定统计和成就两个消费者的处理顺序。

普通 C# event / Action 没有内置的监听优先级参数；需要自己实现有序派发器，或使用明确提供这项能力的事件系统。优先级属于派发机制，不改变“事件描述事实”的语义。C# 的 event 说明给出了语言层面的事件机制。

下面是可独立编译的普通 C# 类。它明确约定：数值越大越先执行；同级按注册顺序；同步串行；监听异常向上传播并停止本轮；在本轮开始时取订阅快照。

PriorityEvent.csC# · 完整类型定义
using System;
using System.Collections.Generic;
using System.Linq;

// 单线程同步派发器；适合在 Unity 主线程内使用。
public sealed class PriorityEvent<T>
{
    private sealed class Entry
    {
        public long Id;
        public int Priority;
        public Action<T> Handler;
    }

    private readonly List<Entry> entries = new List<Entry>();
    private long nextId;

    public long Subscribe(Action<T> handler, int priority = 0)
    {
        if (handler == null)
            throw new ArgumentNullException(nameof(handler));

        nextId = checked(nextId + 1);
        entries.Add(new Entry
        {
            Id = nextId,
            Priority = priority,
            Handler = handler
        });
        return nextId;
    }

    public bool Unsubscribe(long subscriptionId)
    {
        return entries.RemoveAll(e => e.Id == subscriptionId) > 0;
    }

    public void Publish(T message)
    {
        // 数值越大越先执行；同优先级按订阅顺序。
        // 取快照，本轮内增删订阅只影响下一轮 Publish。
        Entry[] snapshot = entries
            .OrderByDescending(e => e.Priority)
            .ThenBy(e => e.Id)
            .ToArray();

        // 同步逐个调用；未捕获异常立即终止本轮。
        foreach (Entry entry in snapshot)
            entry.Handler(message);
    }
}

订阅示例故意先注册成就，再注册统计，以证明真正决定次序的是优先级：

C# 调用／装配示意C# · 示意片段，需置于相应上下文
var bus = new PriorityEvent<ItemObtainedEvent>();
var statistics = new OrderedItemStatistics();
var achievements = new ThresholdAchievements();

// 成就虽先订阅，但优先级较低。
long achievementToken = bus.Subscribe(
    e => achievements.OnItemTotalChanged(
        e.ItemId, statistics.GetTotal(e.ItemId)),
    priority: 0);

long statisticsToken = bus.Subscribe(
    e => statistics.RecordItem(e.ItemId, e.Amount),
    priority: 100);

statistics.RecordItem("Potion", 9);

// 此时调用者已确认背包获得成功；这里单独演示有序通知。
bus.Publish(new ItemObtainedEvent("Potion", 1));
// 统计先更新到 10，成就再读取 10 并解锁。

bus.Unsubscribe(achievementToken);
bus.Unsubscribe(statisticsToken);

这个例子直接读取统计，不同时订阅 statistics.ItemTotalChanged，以免同一项成就检查被两种方案重复触发。两个业务类见下一章，它们与当前派发器可以组合使用。

3. 优先级真正保证了什么？

在本例派发器中，统计同步处理成功返回后，才会调用成就，因此可保证它读到此次统计更新。但这项结论依赖几个具体条件：

  • 次序覆盖真实依赖。 统计的优先级必须高于依赖它的成就；同级仍按注册顺序，配置相反就仍会出错。用命名的优先级常量或集中配置，避免分散的神秘数字。
  • 处理器返回代表必要工作已完成。 启动后台保存任务就返回，或者使用 async void，不能用调用开始顺序证明工作完成顺序。
  • 失败策略正确。 示例遇到异常停止后续检查；若统计吞掉错误、表面成功，或派发器捕获错误后继续，成就仍可能读取旧数据。停止后续不会撤销已经完成的修改。
  • 读取的是正确的数据版本。 处理器返回若只代表“请求被接受”，或成就查询的是尚未更新的缓存、只读副本，优先级本身解决不了这些问题。

它提供的是本次同步派发内的处理次序，不自动提供跨事件排序、事务、持久化、请求去重或跨服务可靠交付。示例不支持多线程并发调用；递归 Publish 会嵌套执行，也不保证多个发布操作之间不交错。有这类需求时，应另行设计队列或按玩家串行化的执行器。

快照也有明确代价：本轮派发时退订某个处理器，它仍可能存在于当前快照中并被调用；本轮新增的订阅者只参加下一轮。这是一种约定，应按项目需要选择，而非所有事件系统都如此。

4. 异步处理：需要按序等待完成

如果统计需要异步保存，事件系统应接收返回 Task 的处理器，排序后逐个等待，而不是把异步 lambda 塞进 Action<T>。下面是异步派发器内部的机制片段，snapshot 为已按优先级排序的处理器列表：

异步优先级派发 · 机制片段C# · 示意片段，需置于相应上下文
// HandleAsync 的签名：Func<T, CancellationToken, Task>
foreach (var entry in snapshot)
{
    ct.ThrowIfCancellationRequested();
    await entry.HandleAsync(message, ct);
}

只有当 HandleAsync 的成功完成代表统计已经达到业务所需的可见性／提交要求时，后续检查才满足前提。Task.WhenAll 是并发等待，不会保证统计先完成再检查成就；不要用它实现存在数据依赖的两个步骤。async void 无法由调用者等待，其异常处理也不同，参见 Microsoft：异步返回类型。

即使单次发布内部逐个 await，多个并发 PublishAsync 仍可能交错。对同一个玩家、订单或聚合的修改，需要按键串行化，或使用数据库并发控制；这不是监听优先级能替代的。

5. 分阶段派发：让依赖比数字更清楚

当项目已有稳定的阶段，可以显式定义“更新状态 → 推导结果 → 提交 → 通知表现”。同一阶段内部允许独立处理，不同阶段之间必须等前一阶段成功结束。成就检查属于推导阶段，依赖更新阶段产出的统计。

相比给每个监听者随意填一个数字，阶段名更容易表达原因。阶段仍然是流程约束，框架必须真正实现等待、失败中止和提交边界；不能把阶段名称当作已经存在的事务。

Unity 的帧更新顺序、MonoBehaviour 脚本执行顺序与这里“同一事件的监听者优先级”属于不同层面的调度，不能自动互相替代。

06表达业务流程：编排、事件链与显式依赖图

1. 显式编排：强依赖用代码表达

C# 调用／装配示意C# · 示意片段，需置于相应上下文
public void ObtainItem(string itemId, int amount)
{
    inventory.Add(itemId, amount);

    // 先更新累计统计
    statistics.RecordItem(itemId, amount);

    // 确认统计已更新，再让成就读取新值
    achievements.CheckItem(itemId);

    // 关键业务完成后，通知表现系统
    ItemObtained?.Invoke(
        new ItemObtainedEvent(itemId, amount));
}

这段代码展示调用顺序，需要放在拥有这些依赖和事件的编排器内；此处的 inventory.Add 等接口是独立示意，与第三章的 Inventory.AddItem 是不同场景的接口示意。直接调用并不意味着架构落后。 当业务必须 A 完成后才能 B，显式编排通常更容易理解、测试和维护；仍然可以通过公开契约控制模块之间的源码依赖。

上面只有顺序，没有持久化原子性。对于关键服务端状态，如果背包、统计、成就必须整体成功，应用服务应明确同一个真实数据库事务，并确保各仓储实际加入它；成功提交后才对外通知。不能让 inventory.Add 提前广播，使监听者观察到尚未提交的中间状态。若使用 Task，也必须 await A 完成后再执行依赖它的 B。

提交后的 UI、音效失败，不代表已经提交的业务回滚；不要因此盲目重新发放道具。需要可靠交付的成功通知，还要持久化为待发送记录，见后文。

2. 因果事件链：统计完成后发布新事实

原先是 ItemObtained → Statistics.Record 与 ItemObtained → Achievements.Check 并列。现在改成一条有因果关系的链：

ItemObtained → Statistics.Record → ItemTotalChanged → Achievements.Check

成就不再猜测统计是否更新完成，而是响应“累计值已经变成多少”。下面两个普通 C# 类型用来表达统计变更与阈值解锁；它们与第三章的最小事件机制是不同示例。

OrderedItemStatistics.csC# · 完整类型定义
using System;
using System.Collections.Generic;

public sealed class OrderedItemStatistics
{
    public event Action<string, int> ItemTotalChanged;

    private readonly Dictionary<string, int> totals = new();

    public int GetTotal(string itemId)
        => totals.TryGetValue(itemId, out int value) ? value : 0;

    public void RecordItem(string itemId, int amount)
    {
        if (amount <= 0)
            throw new ArgumentOutOfRangeException(nameof(amount));

        int newTotal = checked(GetTotal(itemId) + amount);
        totals[itemId] = newTotal;

        // 状态已更新，再通知监听者这个确定的新值
        ItemTotalChanged?.Invoke(itemId, newTotal);
    }
}
ThresholdAchievements.csC# · 完整类型定义
using System.Collections.Generic;

public sealed class ThresholdAchievements
{
    private readonly HashSet<string> unlocked = new();

    public bool IsUnlocked(string achievementId)
        => unlocked.Contains(achievementId);

    public void OnItemTotalChanged(string itemId, int newTotal)
    {
        if (itemId == "Potion" && newTotal >= 10)
            UnlockAchievement("PotionCollector");
    }

    private void UnlockAchievement(string achievementId)
    {
        // 内存示例：重复检查不会重复解锁
        if (!unlocked.Add(achievementId))
            return;

        // 实际奖励发放仍需自己的幂等与持久化保障
    }
}
C# 调用／装配示意C# · 示意片段，需置于相应上下文
var statistics = new OrderedItemStatistics();
var achievements = new ThresholdAchievements();

statistics.ItemTotalChanged += achievements.OnItemTotalChanged;

statistics.RecordItem("Potion", 9);
statistics.RecordItem("Potion", 1); // 通知新累计值 10，触发解锁

// 不再需要时取消订阅；Unity 中要和订阅生命周期配对
statistics.ItemTotalChanged -= achievements.OnItemTotalChanged;

成就接收 newTotal，不必再查询统计系统。这减少了对另一个可变数据源的即时读取依赖。这里的 newTotal 是这次变化后的值，在异步系统中不一定等于处理事件时的最新值。

但这仍然只是同步内存事件的顺序示例：统计更新不等于数据库已经提交；成就处理器抛出异常不会自动撤销统计；监听缺席时也不会补发。成就解锁去重，不代表道具累计本身已经具备请求去重。跨进程还要处理事件丢失、延迟、重复和乱序。携带绝对累计值可以帮助某些投影实现幂等，但不会自动保证所有消费者正确；必要时使用事件 ID、聚合版本等，并定义去重和旧版本策略。

3. 用事件携带结果，减少查询时序依赖

方案 B 已经展示了这一点：ItemTotalChanged(itemId, newTotal) 直接携带变化后的累计值，成就不必再向统计系统查询。这与优先级可以组合使用，也可以用于异步事件。

但不能给 ItemObtained 随意附加一个未经统计模块确认的 newTotal。累计值应由拥有该状态和规则的模块产生；让背包为了通知成就而反过来计算统计，会重新引入错误的职责依赖。

绝对值也不自动等于全局最新状态。事件从 10 变到 11 后，如果消费者先收到 11、后收到 10，直接覆盖就可能倒退。应按语义选择聚合版本检查、去重或单调合并。对于只增不减的累计统计，可以考虑 max 合并；对于可能减少的余额、库存，这通常不成立。

4. 声明前置依赖，用管线或依赖图执行

如果步骤很多，且存在“成就检查必须在统计完成后，任务和 UI 又有不同依赖”的复杂关系，可以声明 Achievements depends on Statistics，由执行器检测环、做拓扑排序，并等待每个节点的前置步骤成功。

这比任意数字优先级更直接表达“为什么必须在后面”。独立节点可以并行，有依赖的节点不能提前。环意味着当前划分无法排出满足约束的次序，需要重审业务或把迭代过程显式建模。

这种设计本质上已接近业务管线或工作流引擎；它不是普通广播事件天然具备的能力。还要定义失败、重试、取消和持久化语义。对于只有两三个固定步骤的业务，显式调用通常更省成本。

5. 强一致与最终一致：明确业务真正要求

如果业务允许成就稍后解锁，统计和成就可以各自处理持久化事件，通过重试、幂等消费、按键顺序或版本约束最终收敛，并提供对账、补算或从事实记录重建的路径。UI 应能表达处理中，且不能把尚未确认的成就奖励当成已生效。

如果业务要求立即同步解锁且发奖，则应把相关步骤放进明确的一致性边界。优先级、阶段、显式编排和同步事件链都可以表达执行次序，但是否原子提交，还取决于它们是否参与同一个真实事务。跨独立数据库无法凭一次本地事务覆盖全部状态，补偿也不等价于瞬时原子回滚。

必须执行的业务处理可以由事件触发；关键是它有明确负责者、可验证的执行契约与可靠性机制。问题不在“用了事件”，而在“把关键业务寄托给没有约束的任意监听者”。

07一致性与可靠交付：次序正确还不够

不是。

执行次序、完成次序和提交可靠性必须分别设计。

1. 事件不等于异步

刚才的 C# 示例：

C# 调用／装配示意C# · 示意片段，需置于相应上下文
ItemObtained?.Invoke(e);

默认是同步调用订阅者。这里的 Invoke 位于事件发布者内部；外部订阅者不能直接调用这个 C# 事件。

因此：

  • 一个监听者执行很慢，发布者也会受到影响。
  • 监听者抛出未捕获异常，会中断这里的多播委托调用，后续监听者不会继续执行。
  • 发布者成功修改了状态，不意味着所有监听者都成功完成。

因此，这个示例中 AddItem() 抛出监听异常，并不意味着背包修改已经回滚；不应把异常简单理解为“道具肯定没加上”，再盲目重试。委托调用顺序和异常传播规则见 Microsoft：Using Delegates。

但使用消息队列或者异步事件总线时，发布和处理又可以在不同时间进行。

因此：

事件是一种语义；同步、异步、消息队列是实现或传递方式。

2. 事件不等于可靠存储

假设游戏中有两个重要的数据：

  • 背包：当前拥有多少道具。
  • 统计：累计获得多少道具。

玩家获得一个道具后，背包更新成功，但事件处理前程序崩溃。

那么就可能出现：

背包 +1，累计统计仍然没有 +1。

如果两份数据必须保持一致，单纯使用内存事件无法保证一致性。

更合适的方式可以是：

在一次数据库事务中同时更新背包和统计，全部成功才提交。

如果希望通过异步事件维护统计，则需要考虑持久化事件、Outbox、重试、幂等处理和最终一致性等问题。

这说明一个重要原则：

解耦和数据可靠性是两个不同的设计目标。不能因为使用了事件，就假设数据一定正确。

3. 提交成功之后，通知仍可能丢失

假设采用方案 B：ItemObtained → ItemTotalChanged → AchievementUnlocked。统计成功保存后，服务器在发布 ItemTotalChanged 前崩溃。重启后，统计已更新，成就却从未收到通知。

这是两个不同问题：顺序正确回答“谁必须先完成”；可靠交付回答“必须执行的后续操作会不会遗漏”。仅把事件挪到保存之后，仍留下“提交成功、尚未发布”的故障窗口。

Transactional Outbox 的常见思路是：在同一个数据库事务中提交业务变更和待发送事件，再由后台发布器投递未完成记录。若发布成功后、标记完成前崩溃，可能再次投递，所以还要设计重试、幂等消费与必要的顺序控制。它不是让多个消费者自动处于同一事务，也不等于端到端“恰好一次”。可参考 Microsoft：Transactional Outbox 实现说明；其中采用 Cosmos DB 的机制，实际项目应选用自身数据库支持的事务边界。

对这个背包、统计、成就例子：如果三者必须立即一致，应让应用服务显式编排并在同一个事务里保存，成功后再通知 UI、音效等独立表现系统。如果允许成就稍后收敛，则要把延迟、重试、幂等、补偿或重建机制作为业务设计的一部分。

事件适合传播事实；必须保持一致的业务规则，应有明确的协调者、一致性边界和失败策略，不能随意交给多个独立监听者。

先选择如何表达依赖，再选择怎样保证一致性。它们是两个设计轴，可以组合，而不是一张互斥的方案清单。

1. 如何表达执行次序？

3. 回到道具、统计与成就

如果三者必须立即一致，可以选择应用服务显式编排；也可以在一个受控的同步事件管线中，以优先级、阶段或依赖关系保证先后，并让全部关键写入参加同一事务。后者成立需要事件系统对处理完成、异常与事务参与提供清楚契约。

如果统计先完成后成就可以稍后处理，因果事件链配合可靠交付、幂等和顺序／版本控制也合理。不要把“允许延迟”误解为“可以遗漏”。

对于 UI、音效等独立表现，通常在业务完成后通知即可。实际响应若会读取其他监听者刚更新的数据，也应重新检查它们之间的依赖，而不是仅按系统名称判定独立。

10回到本质：事实、派发与业务流程

1. 事件既可以是输入，也可以是输出

答案是：都可以。

对一个系统而言：

事件可以作为输入，驱动它执行行为：

ButtonClicked → 执行购买逻辑

事件也可以作为输出，描述它已经完成的行为：

但它不是唯一模式，也不是每个事件都要经历完整的状态转移过程。

2. 事实、协作与业务约束

我们再往深层追问。

假如没有事件这个概念，系统仍然可以通过直接函数调用完成所有功能。

那为什么还要引入事件？

因为我们在设计复杂系统时，需要将两件事情区分开：

一件事发生了。

和

其他对象应该如何响应这件事。

它们并不是同一件事。

事件把“发生的事实”变成了可以独立传递、观察和处理的信息，使得不同系统可以围绕同一个事实执行不同的逻辑。

最终可以归纳为三个层次：

  • 概念本质： 事件是发生在某个时刻、具有明确含义的事实。
  • 运行本质： 事件可以作为输入，使系统决定是否执行行为或发生状态转移。
  • 架构价值： 事件将事实的产生与后续响应分离，从而支持多个系统独立协作。

最值得记住的并不是 event、Action、Invoke 这些 C# 语法，而是下面这句话：

事件回答“发生了什么”，而不是“接下来必须做什么”。

真正掌握这一点，才能判断什么时候应该直接调用方法，什么时候应该发布事件，以及什么时候需要更可靠的事务或消息机制。

事件回答发生了什么；派发契约回答怎样响应；业务流程与一致性机制回答哪些处理必须完成、失败如何恢复。

解耦不是不允许顺序，而是把事实、真实依赖和技术调度分别表达清楚。

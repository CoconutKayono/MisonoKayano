副作用的本质。

返回结果之外，还有什么发生了变化？

Side Effect7 个主题C# 示例离线交互示意

“副”不代表负面，也不代表不重要。
副作用，是返回值之外对外部世界产生的可观察影响。

VALUE / 返回值计算得到了什么
EFFECT / 外部影响除此之外改变了什么
BOUNDARY / 边界变化能否被其他地方观察

副作用的本质：一个操作在产生结果的同时，还改变了它自身返回值之外、能够被其他地方观察到的状态，或与外部世界发生了交互。

最关键的问题不是“这个操作返回了什么”，而是：

这个操作执行以后，除了返回结果，还有什么发生了变化？

01What：什么是副作用？

先看两个 C# 函数。

1. 没有副作用

纯计算 · AddC# · 示意片段，需置于相应上下文
int Add(int a, int b)
{
    return a + b;
}

调用：

调用纯计算 · 片段C# · 示意片段，需置于相应上下文
int result = Add(3, 5);

发生了什么？

  • 输入 3 和 5。
  • 计算得到 8。
  • 返回 8。
  • 没有改变函数外部的状态。

可以将它抽象为：只有输入、计算、输出，没有对外部状态的影响。

2. 有副作用

修改外部 total · AddC# · 示意片段，需置于相应上下文
int total = 0;

int Add(int a, int b)
{
    total += a + b;
    return a + b;
}

调用：

调用带副作用的计算 · 片段C# · 示意片段，需置于相应上下文
int result = Add(3, 5);

这一次发生了两件事：

  1. 函数返回 8。
  2. 函数外部的 total 增加了 8。

除了返回值，还存在一条对外部状态产生影响的路径。第二条路径就是副作用。

这里有一个特别重要的区别：

副作用不是“多做了一件事”，而是“操作对其外部产生了可观察的影响”。

例如：

局部变量 · AddC# · 示意片段，需置于相应上下文
int Add(int a, int b)
{
    int total = a + b;
    return total;
}

虽然修改了局部变量 total，但它没有影响函数外部，也不是通常意义上的副作用。

所以，状态发生变化不一定存在副作用。关键是变化是否逃逸到外部、能否被观察。

02Why：为什么叫“副作用”？

从英语理解：

  • Effect：效果、影响、结果。
  • Side：侧面的、附带的。
  • Side Effect：附带产生的影响。

这里的“副”，不是“负面”的意思。最容易误解的地方，是以为副作用就是 Bug、不好的后果或意外行为，实际上并非如此。

比如：

数据库保存 · 示意片段C# · 示意片段，需置于相应上下文
void SavePlayer(Player player)
{
    database.Save(player);
}

这个函数的主要目的就是保存玩家数据。但按照程序设计中的分类，写入数据库仍然属于副作用，因为它改变了函数外部的持久化状态。

这说明一个更深层的事实：

“主作用”与“副作用”不是严格按照业务上的重要性区分，而是相对于计算的返回结果、状态边界和外部交互来区分。

从业务角度看，保存是主要目的；从函数式编程的角度看，数据库写入是一种外部作用。

03How：副作用是如何产生的？

可以将程序中的副作用归纳成两大类。

1. 改变外部状态

修改传入对象 · AddGoldC# · 示意片段，需置于相应上下文
class Player
{
    public int Gold;
}

void AddGold(Player player, int amount)
{
    player.Gold += amount;
}

调用 AddGold 后，调用者持有的 player 对象发生了变化。即使函数没有返回值，也实际产生了影响。

常见形式包括：修改对象字段、静态变量、共享集合、单例对象等。

2. 与外部世界交互

文件与日志 · ExecuteC# · 示意片段，需置于相应上下文
void Execute()
{
    File.WriteAllText("save.txt", "100");
    Debug.Log("Saved");
}

这里存在两种副作用：

  • 文件写入：改变磁盘状态。
  • 日志输出：改变外部可观察的输出。

其他例子还有数据库写入、网络消息发送、播放声音、操作 Unity 场景对象等。

注意：读取文件、数据库、时间或随机数虽然不一定修改外部状态，但也是与外部环境的交互，会影响函数的确定性。广义的 Effect（作用）概念也会将这类操作纳入讨论。

这些代码是示意片段，需要放入相应类型或方法上下文。File 通常需引用 System.IO，Unity 日志的 Debug 来自 UnityEngine。片段中的数据库、Player、存档与事件发布接口只表达职责，不构成一套完整的购买系统。

04为什么程序设计特别关注副作用？

因为副作用会让一个操作的结果依赖于执行历史。考虑：

重复执行 · RewardC# · 示意片段，需置于相应上下文
int gold = 100;

void Reward()
{
    gold += 10;
}

gold += 10
当前金币
100
Reward() 执行次数
0

尚未修改金币。

  1. 初始状态：gold = 100

两个执行按钮调用相同逻辑；示例没有幂等保护，每次调用都会再次增加金币。这里仅模拟本地状态变化，不发送网络请求。重置恢复演示初始值。

观察到一个现象：即使执行的是同一个函数，执行次数不同，最终状态也不同。

这为什么重要？因为实际程序可能：

  • 因网络超时重试同一个请求。
  • 因事件被重复处理而再次调用函数。
  • 因并发执行出现竞态条件。
  • 因执行中途失败，导致只完成一部分副作用。

例如玩家购买道具：

部分更新风险 · PurchaseC# · 示意片段，需置于相应上下文
void Purchase(Player player)
{
    player.Gold -= 100;
    player.Items.Add("Sword");
}

假设扣除金币后，程序异常退出，此时可能发生：

  • 金币已经扣除。
  • 道具没有获得。

如果两个变更需要共同成功，就必须考虑原子性、事务或其他一致性保障。这里展示的是执行中断造成部分更新；是否跨进程保留，还取决于持久化方式。

副作用本身不是问题，真正需要管理的是：副作用执行的时机、次数、顺序，以及失败后的状态。

这也是为什么需要事务、幂等、锁、重试策略等机制。它们分别解决不同的问题，不能相互完全替代。

05如何管理副作用？

一个常用的设计思路是：将计算和副作用分离。

例如，先计算玩家购买后应该得到的结果：

计算结果 · CalculateGoldAfterPurchaseC# · 示意片段，需置于相应上下文
int CalculateGoldAfterPurchase(
    int currentGold,
    int price)
{
    return currentGold - price;
}

这个函数只计算，不修改外部状态。

然后在专门的位置执行状态变更：

提交状态修改 · PurchaseC# · 示意片段，需置于相应上下文
void Purchase(Player player, int price)
{
    int newGold =
        CalculateGoldAfterPurchase(player.Gold, price);

    player.Gold = newGold;
}

当然，这个示例只展示职责划分，实际购买还需要余额校验、并发控制和持久化保障。

为什么这样设计？因为纯计算更容易推理、测试、复用；而副作用集中在明确的位置，更容易控制什么时候执行、怎样处理失败。

但这不意味着所有函数都应该无副作用。游戏服务器必须修改玩家数据，游戏客户端必须更新画面，数据库必须写入记录。

目标从来不是消灭副作用，而是让副作用显式、可控、可验证。

06进一步：副作用、状态、事件、行为之间的关系

这些概念描述的是不同维度：

概念 关注的问题
状态（State） 现在是什么样？
行为（Behaviour） 对象能够做什么、如何响应？
事件（Event） 发生了什么？
状态转移（Transition） 状态如何从 A 变成 B？
副作用（Side Effect） 执行操作时，对外部产生了什么影响？

例如玩家领取奖励：

状态、存档与事件 · ClaimRewardC# · 示意片段，需置于相应上下文
void ClaimReward(Player player)
{
    player.Gold += 100;
    Save(player);
    PublishEvent("RewardClaimed");
}

从不同角度看：

  • ClaimReward 是一个行为。
  • 金币从 0 变为 100 是状态转移。
  • RewardClaimed 描述的是奖励已领取的事件。
  • 修改共享的 player、写入存档、发布事件，都是可能的副作用。

一个操作可以同时具有这些性质，它们并不相互排斥。

07直达本质：一个更抽象的理解

可以将操作看作：

(输入, 世界状态) ⟶ (返回结果, 新的世界状态)

无外部副作用的纯计算只需要关心输入到输出的映射：

y = f(x)

有副作用的操作，则还可能改变周围世界：

(y, S′) = F(x, S)

其中：

  • x：输入。
  • y：返回结果。
  • S：操作前的外部状态。
  • S′：操作后的外部状态。

当 S′ ≠ S，就可能存在状态修改型副作用；即使状态相同，也可能已经发生了日志输出、网络调用等外部交互。

这里的 S 是所选状态模型。相同的业务状态快照，不代表外部交互轨迹相同；如果把所有可观察输出和交互也纳入“世界”，就应在模型中一并记录。

这揭示了副作用的核心：一个操作不仅可以计算出一个值，还可以影响它所在的世界。

最后，留下一个值得深入思考的问题。假设存在两个函数：

返回值相同 · A 与 BC# · 示意片段，需置于相应上下文
int A(int x)
{
    return x + 1;
}

int B(int x)
{
    Debug.Log("Calculating...");
    return x + 1;
}

它们的返回结果完全一样。但能否在任何程序中，都将 B(x) 替换成 A(x)，并保证程序的可观察行为不变？

答案是不能，因为 B 额外产生了日志输出。

A(x) / B(x)

选择相同输入，分别调用两个函数，比较返回结果与日志。

  1. 暂无日志。

B 会在页面的演示日志中新增 Calculating...；A 不增加日志。已有日志不会因调用 A 而消失。这里只可视化输出差异，不调用真实的 Unity Debug.Log。

这就引出了副作用背后非常重要的概念：引用透明性（Referential Transparency）。讨论的不只是返回值相同，还包括替换前后的可观察行为是否保持不变。

副作用的本质不是“坏的影响”，而是“计算返回值之外，对外部世界产生的可观察影响”。

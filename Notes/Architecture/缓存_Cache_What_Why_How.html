缓存（Cache）：What、Why、How，直击本质

缓存是计算机科学中极其重要的思想。

它不仅存在于 Redis、数据库、浏览器和 CPU 中，也广泛存在于游戏开发的资源管理、UI 系统、配置系统、战斗系统以及 Unity 引擎内部。

理解缓存，最重要的不是学会 Dictionary 或 Redis 的 API，而是理解：

为什么重复获取相同的信息会产生浪费？为什么保存一份结果可以提高性能？为什么缓存又会引入数据一致性和生命周期问题？

一、What：缓存是什么？

1. 缓存的本质定义

缓存（Cache）是一种通过保存先前获取或计算的结果，在后续访问时避免重复执行高成本操作的机制。

我们可以把它抽象为：

典型的 Cache-Aside（旁路缓存）读取流程。命中时省去昂贵操作，未命中时获取并保存结果。

注意这里最关键的两个词：

  • 结果：可以是数据、对象引用、计算值、资源，也可以是某个操作的中间结果。
  • 复用：复用的是先前取得的信息或结果，而不是重复执行原先昂贵的操作。

例如，一个游戏需要计算角色的最终攻击力：

public int GetAttack()
{
    return baseAttack
        + weaponAttack
        + equipmentBonus
        + skillBonus;
}

假设角色的装备、技能和基础属性都没有变化。

第一次调用：

int attack = GetAttack();

得到 250。

第二次调用：

int attack = GetAttack();

仍然得到 250。

假设真正的计算成本很高，那么问题出现了：

如果影响计算结果的所有条件都没有变化，为什么还要重新计算？

这就是缓存要解决的问题。

我们可以在第一次计算之后，保存结果：

private int cachedAttack;

第二次访问时，只要能确认影响结果的条件没有改变，就直接返回 cachedAttack。

这就是缓存最简单的形态。

2. 缓存本质上是一种什么思想？

缓存是典型的：

用空间换时间，同时引入维护成本。

情况 空间与执行成本
没有缓存 不额外保存结果，每次重新获取、读取或者计算。
存在缓存 保存一份结果，之后尽量直接复用，降低重复访问成本。

但缓存不是单纯的空间换时间。

因为一旦保存结果，就会出现四个新的问题：

  1. 保存的结果是否还正确？
  2. 应当保存多少结果？
  3. 什么时候可以删除结果？
  4. 多个地方同时访问或修改时，如何保证正确性？

这意味着缓存是一种带有一致性约束、容量约束和生命周期管理的性能优化机制。

3. 缓存保存的究竟是什么？

缓存不局限于某一种数据结构。

缓存内容 示例 复用的内容
计算结果 角色最终战斗力 已计算的数值
查询结果 根据 ID 查询道具配置 已取得的配置
资源引用 Unity Sprite、Texture 已加载的资源
中间结果 UI 布局计算结果 已完成的计算
网络响应 服务端排行榜 已获取的数据快照
文件数据 操作系统文件缓存 已读取的数据块

理解到这里，可以得出一个更抽象的定义：

缓存不是某个具体容器，而是对重复获取成本的一种管理策略。

Dictionary 可以承载缓存，但 Dictionary 本身不是缓存。

Redis 可以作为缓存基础设施，但 Redis 本身也不等于缓存策略。

同样，一个私有变量也可以实现最简单的缓存。

关键在于：这个数据为什么被保存、如何被复用，以及在什么条件下认为它有效。

二、Why：为什么需要缓存？

1. 计算机系统中存在大量重复工作

假设 Unity 游戏中有一个道具展示界面。

每次打开界面时，需要：

  1. 根据道具 ID 查找配置。
  2. 获得道具名称、描述、图标路径。
  3. 加载对应的 Sprite。
  4. 更新 UI 显示。

如果每次都重新执行所有操作，就可能发生重复查找、重复资源加载请求以及其他不必要的工作。

注意，Unity 或 Addressables 自身可能已经具有缓存或资源复用机制，因此重复请求不一定意味着重复从磁盘加载。但调用方仍可能存在可优化的重复工作。

考虑一种有明确缓存机制的情况：

同一个道具图标被访问 4 次

访问次数 不使用应用层缓存 使用应用层缓存
首次访问 从来源获取 从来源获取，并保存结果
第 2 次 再次请求来源 读取有效缓存
第 3 次 再次请求来源 读取有效缓存
第 4 次 再次请求来源 读取有效缓存

缓存能否带来真实收益，取决于原操作是否昂贵、缓存是否命中，以及底层系统是否已经完成同等优化。

真正的问题不是“重复调用了一段代码”。

因为重复调用一个非常简单的方法可能几乎没有成本。

真正的问题是：

重复执行的操作具有不可忽略的成本，而它产生的结果又可以被安全复用。

2. 缓存为什么能够提高性能？

因为不同操作的成本存在巨大差异。

例如：

  • 访问内存中的字段通常很快。
  • 遍历大量数据可能相对较慢。
  • 读取磁盘可能涉及 IO 等待。
  • 发起网络请求可能涉及明显的延迟。

假设一次计算需要 10 毫秒，而查询已有缓存只需要 0.1 毫秒。

那么命中缓存就可能省去大部分原始计算时间。

但这需要满足两个条件：

第一，原操作足够昂贵。

如果原本只需要几纳秒，增加缓存查询反而可能拖慢性能。

第二，相同或等价的请求足够频繁。

如果某个数据只访问一次，缓存它通常没有意义，因为首次获取的成本依然需要支付，还额外承担了存储成本。

3. 缓存为什么与局部性有关？

计算机系统存在两个重要现象。

时间局部性（Temporal Locality）

一个数据刚刚被访问过，那么它在短时间内可能再次被访问。

例如，玩家打开背包，连续查看同一件装备的信息。

这种行为适合缓存。

空间局部性（Spatial Locality）

一个数据被访问后，附近的数据也可能很快被访问。

例如，CPU 读取某个数组元素，随后继续访问相邻元素。

这解释了为什么 CPU Cache 通常以 Cache Line 为单位加载一段连续内存，而不只是一个孤立变量。

因此，缓存并非随意保存数据。

它利用的是：

未来的访问请求，往往与过去的访问请求存在一定关联。

4. 缓存不一定提高性能

设：

  • H：缓存命中率。
  • Tl：缓存查找成本。
  • Th：命中后读取缓存值的额外成本。
  • Ts：从原始来源获取结果的成本。
  • Ti：未命中时将结果存入缓存的成本。

简化的平均访问时间：

Tcache = Tl + H · Th + (1 − H) · (Ts + Ti)

而不使用缓存：

Tdirect = Ts

交互实验：什么时候缓存才划算？

无缓存
10.00 ms
有缓存
2.14 ms

平均每次节省 7.86 ms，约 78.6%。

简化模型：命中读取额外成本近似为 0，插入成本固定为 0.2 ms。未计入内存、失效维护、并发协调和冷启动成本。所有时间均为教学假设。

这里将命中读取的额外成本近似为 0，插入成本设为 0.2 ms，未计入内存、失效维护和并发成本。调整参数即可观察缓存什么时候适得其反。

所以，缓存的最终目的不是提高命中率本身，而是：

在满足正确性的前提下，降低系统整体执行成本。

三、How：缓存是如何工作的？

从工程角度看，一个完整的缓存系统至少需要回答五个问题：

核心问题 对应概念
如何找到已经保存的结果？ Cache Key（缓存键）
如何判断结果是否存在？ Hit / Miss（命中与未命中）
如何判断结果是否还能使用？ Cache Invalidation（缓存失效）
缓存存满了怎么办？ Eviction Policy（淘汰策略）
谁负责更新和释放缓存？ Ownership / Lifetime（所有权与生命周期）

其中，缓存失效和生命周期管理通常比缓存查找更难设计。

1. Cache Key：如何识别结果？

一个典型的缓存结构可以表示为：

Cache : K → V

其中：

  • K：缓存键，用来识别请求。
  • V：缓存值，也就是保存的结果。

例如：

Dictionary<int, ItemConfig> itemCache;

道具 ID 是 Key。

道具配置是 Value。

当我们访问某个道具时：

if (itemCache.TryGetValue(itemId, out var config))
{
    return config;
}

缓存能够复用结果的前提是：

相同的 Key 能够标识语义上相同的结果。

但仅仅使用一个 ID，不一定足够。

假设道具名称需要根据语言切换。

GetItemName(1001, "zh-CN");
GetItemName(1001, "en-US");

如果只把 1001 当作缓存键，那么中文名称与英文名称可能发生冲突。

正确的 Key 可能应该是：

(int itemId, string language)

如果配置还允许热更新，那么还需要考虑配置版本。

这里可以得出一个重要结论：

缓存键的设计，本质上是对计算结果依赖条件的建模。

假设：

R = f(A, B, C)

如果 A、B、C 都会影响结果，那么只用 A 作为缓存键，除非存在额外的失效机制，否则就不能保证正确性。

2. Cache Hit / Miss：命中与未命中

缓存查询只有两种基本结果。

Cache Hit（缓存命中）

请求的数据已经存在，并且满足有效性要求，因此直接返回。

Cache Miss（缓存未命中）

数据不存在，或者存在但已经失效，需要重新获取。

典型流程：

public ItemConfig GetItemConfig(int itemId)
{
    if (_cache.TryGetValue(itemId, out var config))
    {
        return config;
    }

    config = LoadItemConfig(itemId);

    _cache[itemId] = config;

    return config;
}

这种由调用方在读取时检查缓存、未命中时再加载的模式，称为 Cache-Aside（旁路缓存）。

当然，生产代码还需要考虑：加载失败、空值、异常、缓存容量，以及同一 Key 被并发访问等情况。

3. Cache Invalidation：缓存失效

这是理解缓存最关键的一部分。

假设玩家攻击力由以下因素决定：

Attack = BaseAttack + WeaponAttack + BuffAttack

第一次计算：

Attack = 100 + 50 + 20 = 170

我们把 170 缓存起来。

现在玩家更换武器：

WeaponAttack = 80

正确结果应该是：

Attack = 100 + 80 + 20 = 200

但是缓存仍然保存着 170。

如果直接返回缓存，就会出现错误。

当前真实攻击力 旧缓存结果
200 170

缓存存在，但结果已经过期。

注意：

缓存存在，不意味着缓存有效。

这两个概念必须分开。

更严格地说，缓存通常需要维护一个有效性条件：

Valid(K, V, S, t)

其中：

  • K 是缓存键。
  • V 是当前缓存值。
  • S 是原始数据的状态。
  • t 是当前时间。

只有有效性条件满足时，缓存值才能按当前业务要求使用。

对于需要精确最新结果的系统，可以要求：

V = f(K, S)

对于允许短暂数据延迟的系统，也可以采用较弱的一致性要求。

所以，缓存正确性不是单纯比较两个数是否一致，而是缓存结果是否满足系统规定的一致性契约。

四、缓存失效的四种常见策略

1. 主动失效（Explicit Invalidation）

当影响结果的状态改变时，主动标记缓存无效。

public void ChangeWeapon(Weapon weapon)
{
    _weapon = weapon;
    _attackCacheValid = false;
}

下次读取攻击力时，重新计算。

优点是准确及时，而且不需要周期性重新计算。

缺点是必须找出所有会影响结果的修改路径。

如果某个修改路径忘记失效缓存，就会出现隐藏的逻辑错误。

2. TTL：基于时间的过期

TTL 全称 Time To Live。

缓存只能存活指定的时间。

例如：

10:00:00  获取排行榜，保存缓存
10:00:05  再次读取，命中
10:00:20  再次读取，命中
10:00:30  缓存到期
10:00:31  再次读取，重新获取

适合排行榜、公告、部分玩家资料等能够容忍一定延迟的数据。

但要注意：

TTL 可以限制缓存结果的复用时间窗口，但不能保证缓存期间数据绝对正确；数据实际有多旧，还取决于来源和刷新策略。

如果数据刚缓存完就发生变化，在 TTL 到期前仍然可能返回旧值。

3. Versioning：版本号校验

这是游戏开发中值得重点理解的一种方式。

思路是：

不直接记录缓存是否过期，而是记录缓存对应的是哪个状态版本。

例如：

角色属性版本 = 12
缓存计算版本 = 12

两个版本一致，缓存有效。

更换装备：

角色属性版本 = 13
缓存计算版本 = 12

两个版本不一致，重新计算。

计算完成：

角色属性版本 = 13
缓存计算版本 = 13

缓存恢复有效。

这种设计将多个状态修改操作统一为一个可检查的不变量：

CacheValid ⇔ CacheVersion = StateVersion

但前提是所有影响计算结果的状态变化，都必须推动对应版本更新。首次访问前也必须保证缓存未被误判为有效。

4. Write-Through：写穿透更新

当原始数据被修改时，同步更新缓存。

例如：

修改角色名称
    ↓
更新权威数据
    ↓
同步更新缓存
    ↓
操作完成

与主动失效相比：

  • 主动失效：删除或标记旧结果，下次再计算。
  • 同步更新：修改发生时，直接维护最新缓存结果。

如果存在多个写入方或分布式节点，还要处理写入原子性、失败及并发顺序问题。

术语补充：严格意义上的 Write-Through 通常指写请求经过缓存层，并同步写入后端存储。上面的流程强调“写入时同步维护缓存”的思想；应用代码自行双写两处，也仍需处理部分失败。它属于写入传播策略，与前面几种有效性维护方式可以组合使用。

另外还有 Write-Back（写回缓存）：先更新缓存，之后再将数据写入下层存储。

这类缓存可能临时持有尚未持久化的最新数据，因此不能直接当作“随时可丢弃的副本”。

五、How：在 Unity / C# 中实现一个正确的缓存

我们使用角色属性系统来实现。

我们的目标是：

  • 相同状态下不重复计算攻击力。
  • 属性变化后自动失效。
  • 访问时按需重新计算。
  • 不需要外部系统知道缓存的存在。

这实际上就是将缓存封装为对象内部的一个实现细节。

using System.Collections.Generic;

public sealed class CharacterStats
{
    private int _baseAttack;
    private int _weaponAttack;

    private readonly List<int> _buffs = new();

    // 真实状态的版本
    private int _stateVersion = 0;

    // 缓存对应的版本
    private int _cacheVersion = -1;

    // 上一次计算的结果
    private int _cachedAttack;

    public int Attack
    {
        get
        {
            // 状态未变化，复用结果
            if (_cacheVersion == _stateVersion)
            {
                return _cachedAttack;
            }

            // 状态已变化，重新计算
            int result = _baseAttack + _weaponAttack;

            foreach (int buff in _buffs)
            {
                result += buff;
            }

            // 保存计算结果
            _cachedAttack = result;

            // 标记缓存与当前状态一致
            _cacheVersion = _stateVersion;

            return result;
        }
    }

    public void SetBaseAttack(int value)
    {
        if (_baseAttack == value)
            return;

        _baseAttack = value;
        _stateVersion++;
    }

    public void SetWeaponAttack(int value)
    {
        if (_weaponAttack == value)
            return;

        _weaponAttack = value;
        _stateVersion++;
    }

    public void AddBuff(int attackBonus)
    {
        _buffs.Add(attackBonus);
        _stateVersion++;
    }

    public bool RemoveBuff(int attackBonus)
    {
        bool removed = _buffs.Remove(attackBonus);

        if (removed)
            _stateVersion++;

        return removed;
    }
}

示例假定单线程访问、版本计数不溢出；Buff 简化为攻击力增量，并且所有修改都通过类提供的方法完成。

我们分析这个设计。

第一步：区分权威状态与派生结果

真正的角色状态是：

_baseAttack
_weaponAttack
_buffs

缓存则是：

_cachedAttack

我们不能混淆这两者。

_cachedAttack 并不是攻击力的独立权威来源。

它只是根据其他属性计算出的派生结果。

第二步：定义缓存有效性

_cacheVersion == _stateVersion

当版本一致，表示影响攻击力的状态自上次计算以来没有变化。

第三步：让所有相关修改操作维护版本

例如：

public void AddBuff(int attackBonus)
{
    _buffs.Add(attackBonus);
    _stateVersion++;
}

这里有一个十分重要的架构思想：

所有能够改变业务状态的入口，都必须维护与该状态有关的不变量。

如果外部可以直接修改 _buffs，却没有更新版本，就会破坏这个保证。

因此，封装、信息隐藏、不变量与缓存不是彼此独立的技术。

它们之间存在直接关系：

  • 封装限制状态修改入口。
  • 不变量定义缓存正确性。
  • 版本号表示状态是否发生变化。
  • 缓存利用版本号决定是否复用结果。

这也说明为什么架构设计会直接影响缓存的可靠性。

补充：观察实际调用过程

var stats = new CharacterStats();
stats.SetBaseAttack(100);
stats.SetWeaponAttack(50);
stats.AddBuff(20);

int first = stats.Attack;   // 170：首次读取，计算并保存。
int second = stats.Attack;  // 170：版本一致，直接复用。

stats.SetWeaponAttack(80);  // 更新状态版本。
int third = stats.Attack;   // 200：版本不同，重新计算。

_cacheVersion 的初始值为 -1，而 _stateVersion 为 0，因此首次访问会计算。重复设置相同数值、移除一个并不存在的 Buff，都不会推动版本变化。

如果只有一个缓存，一个 Dirty Flag（脏标记）通常也足够。版本号在多个派生结果各自记录计算版本时尤其有用。

这里的加法用于解释机制，实际项目仍应根据计算成本决定是否缓存。

六、Eviction：为什么缓存不能无限增长？

缓存提高性能的代价之一，是占用存储空间。

假设游戏不断打开不同角色的展示界面，并将每个角色的图片、配置与某些计算结果存入缓存。

如果只增加不删除：

CacheSize(t + Δt) ≥ CacheSize(t)

在没有清理操作的情况下，缓存大小通常会持续增长，直到数据种类不再增加或系统出现资源压力。

缓存容量必须被管理。

常见淘汰策略

策略 淘汰规则 适合场景
FIFO 最早进入的优先淘汰 简单、有界的缓存
LRU 最久未被使用的优先淘汰 具有时间局部性的访问
LFU 使用频率较低的优先淘汰 热点长期稳定的数据
TTL 过期清理 超过规定时间后失效并清理 允许一定延迟的数据
容量 / 成本感知 根据内存占用及重建成本决策 大小差异明显的资源

不同策略可以组合使用，例如 LRU + TTL。

交互实验：LRU 如何淘汰数据？

容量为 3。点击键表示一次访问；命中会移到最近使用位置，未命中会插入，满额时淘汰最久未用项。

从左到右：最近使用 → 最久未用

缓存为空
建议顺序：A → B → C → A → D。最后淘汰 B。

访问 0 次 · 命中 0 次 · 未命中 0 次

LRU 的关键思想是：

用过去的访问行为，预测未来哪些缓存条目更可能再次被使用。

这只是一个启发式策略，并不能保证淘汰的就是未来最不需要的数据。

真实系统还需要考虑淘汰与过期的区别：

  • 失效（Invalidation）：数据不再满足使用条件。
  • 淘汰（Eviction）：为控制资源成本，主动移除条目。

一个条目可能完全有效，但因为长期未使用而被淘汰。

这两个概念不能混为一谈。

补充：TTL 是过期机制，单独设置 TTL 不会自动保证容量有界。过期也不意味着内存在到期瞬间被释放，还取决于惰性清理、后台清理和资源释放机制。

七、缓存与所有权、生命周期之间的关系

这是在 Unity 中使用缓存时格外重要的部分。

我们之前讨论过 Resource Lifetime 与 Logical Lifetime。

缓存恰恰可能让这两种生命周期产生冲突。

假设：

Dictionary<string, Sprite> spriteCache;

缓存保存了 Sprite 的引用。

但这里有一个问题：

这个 Sprite 究竟归谁管理？

保存引用，不等于拥有资源。

例如通过 Addressables 加载 Sprite：

  • Addressables 使用加载句柄、引用计数等机制管理资源生命周期。
  • 缓存保留 C# 的 Sprite 引用，不代表缓存已经获得独立的 Addressables 所有权。
  • 如果相关资源已被释放，缓存中还保存引用，也不能保证资源可以继续正常使用。
  • 如果缓存持有应当释放的资源句柄，又没有释放机制，则可能导致资源长期占用。

因此，要区分三个概念：

概念 主要关注
引用（Reference） 能否找到某个对象
所有权（Ownership） 谁有责任控制资源的释放
生命周期（Lifetime） 对象或资源可以安全存在多久

缓存对象的生命周期，必须满足被缓存资源的有效性约束。

换句话说：

CacheLifetime ⇏ ResourceLifetime

缓存存活，并不能证明其引用的资源仍然有效。

在 Unity 中，还要注意 UnityEngine.Object 的特殊销毁语义。

一个托管的 C# 引用可能仍然存在，但对应的 Unity 原生对象已经销毁。

因此，不能单纯使用 Dictionary 中是否存在某个 Key，就断言相关 Unity 资源仍然可用。

缓存会造成内存泄漏吗？

有可能。

更准确地说，缓存可能导致逻辑上的内存长期滞留。

例如，静态字典持续保存已经没有业务用途的对象。

这些对象仍然被强引用，因此无法按照预期释放。

这不一定是传统意义上的不可达内存泄漏，却同样会造成内存使用异常。

所以，设计缓存的时候，不能只设计“存入”。

还需要设计：

谁创建、谁维护、谁失效、谁淘汰、谁释放。

八、缓存、对象池与享元模式有什么区别？

这三个概念都包含“复用”，但它们关注的复用内容与职责不同。

维度 缓存 Cache 对象池 Pool 享元 Flyweight
核心目的 避免重复获取或计算 避免重复创建和销毁 避免重复存储相同内在状态
复用对象 已获取的结果 可重新分配的实例 可共享的状态
身份要求 通常由 Key 识别结果 借用者通常独占当前实例 多个上下文可共享同一状态
主要问题 失效、一致性、淘汰 状态重置、借还、所有权 内外部状态分离、共享安全
游戏示例 缓存道具配置 子弹 GameObject 池 多个敌人共享同一份配置

举个例子。

游戏中存在 100 个敌人，使用同一种敌人配置。

如果我们只创建一份配置并提供给所有敌人共享，这是享元思想的应用。

如果根据配置 ID 首次加载后保存，下次无需重新加载，这是缓存思想的应用。

如果我们提前创建 100 个敌人 GameObject，死亡后回收，下次生成敌人时重新使用，这是对象池思想的应用。

这三种机制可以同时存在。

例如：

敌人生成系统

↓

查询敌人配置缓存

↓

获取共享配置数据

↓

从敌人对象池借用 GameObject

↓

重置状态并初始化

缓存复用结果，对象池复用实例，享元复用可共享状态。

缓存和享元也可能重叠：一个共享配置对象可以同时通过缓存被查找和复用。

补充：对象池不也是缓存了对象吗？

从广义的“保存以备复用”来看，确实可以这样说。

区分它们时，不能只看有没有保存对象。

缓存通常希望复用“这个请求原来的结果”；对象池则让同一个实例结束上一次逻辑使用后，重置并承载下一次逻辑使用。

例如，子弹池中归还的实例，下次借出时通常不应保留上一发子弹的目标、伤害和命中状态。

因此，上面的概括是为了区分职责，并不是说缓存不能保存实例，也不是说对象池与广义缓存完全互斥。

九、从架构的角度，缓存应该放在哪里？

缓存通常不应该成为业务系统必须直接管理的细节。

例如：

InventoryUI↓ItemService↓ItemRepository↓ConfigDatabase

假设 ItemRepository 需要频繁查询配置。

可以在这一层添加缓存：

InventoryUI↓ItemService↓CachedItemRepository

↓ 命中

直接返回

↓ 未命中

ItemRepository

↓

ConfigDatabase

业务系统只依赖一个契约：

public interface IItemRepository
{
    ItemConfig GetById(int itemId);
}

它不需要关心结果来自内存缓存还是配置数据库。

这体现了信息隐藏、依赖倒置与装饰器模式等架构思想。

缓存成为可替换的技术策略，而不是散落在每个业务类中的判断。

当然，不是所有缓存都应该放在 Repository 层。

例如角色攻击力属于对象内部的派生状态，直接在角色属性对象中维护可能更自然。

关键是：

将缓存放在能够完整掌握数据依赖、有效性和生命周期的边界上。

而不是机械地认为必须设置一个全局 CacheManager。

补充：相同的方法签名并不自动保证行为透明。接口仍应明确必要的新鲜度、共享可变性和生命周期要求，缓存实现要遵守这些契约。

十、缓存系统中容易被忽略的高级问题

1. Cache Stampede：缓存击穿式并发重建

假设一个高频访问的缓存条目突然过期。

同时有 100 个请求到达。

所有请求都检查缓存，发现未命中。

于是 100 个请求同时查询数据库。

缓存本来是为了降低数据库压力，却在过期瞬间造成压力激增。

解决思路包括：

  • 同一个 Key 的未命中请求合并（Singleflight）。
  • 只让一个请求重建，其他请求等待。
  • 某些允许旧数据的场景采用 Stale-While-Revalidate。
  • 对过期时间增加适度随机抖动，避免大量条目同时失效。

在 Unity 中，多个界面同时请求同一份异步资源，也可能存在类似的重复工作。

补充：TTL 抖动主要缓解大量不同条目同时过期，不能单独解决同一个热点 Key 的并发重建。请求合并还要处理失败、取消和资源所有权。

2. Negative Caching：缓存不存在的结果

假设客户端频繁查询一个不存在的道具 ID。

每次查询都会失败。

如果只缓存成功结果，那么这些失败请求会不断重复执行。

此时可以短时间缓存“该数据不存在”的结果。

但必须区分：

  • 数据确实不存在。
  • 网络请求失败。
  • 权限不足。
  • 数据暂时不可用。

不能把所有失败统一缓存为“永久不存在”。

3. Aliasing：缓存可变对象的别名问题

假设缓存的是：

Dictionary<int, ItemConfig>

如果调用方获得 ItemConfig 后可以直接修改其字段，那么缓存中的配置也可能被同步修改，因为它们引用的是同一个实例。

这会产生问题：

系统 A 修改了返回的配置对象↓缓存对象也被改变↓系统 B 读取到意外的数据

所以缓存设计必须考虑对象是否可变。

常见处理方式包括不可变数据对象、只读接口、防御性复制以及明确的共享修改契约。

缓存的正确性不仅取决于缓存什么时候更新，还取决于缓存返回的对象能否被外部意外修改。

补充：只读接口不自动保证底层不可变；防御性复制有额外成本，嵌套可变对象可能需要深复制。

4. 并发更新与旧数据覆盖

假设一个缓存值正在异步刷新。

请求 A 读取版本 10 的数据。

请求 B 随后读取版本 11 的数据，但更早完成并更新缓存。

之后请求 A 才完成，把版本 10 写回缓存。

于是较旧的数据覆盖了较新的数据。

解决这个问题需要版本比较、条件写入、请求序列号或其他并发协调手段。

这也是为什么在异步系统中，简单的 Dictionary 并不能自动保证缓存语义正确。

补充：请求发起顺序未必等于来源数据的新旧顺序。使用请求序列号时要明确它所保证的语义；比较版本和提交结果也需要协调。线程安全容器不会自动保证这些业务操作整体正确。

补充：失效后，旧的在途计算也可能重新填回缓存

即便没有两个并发刷新请求，也可能发生：

  1. 读取任务 A 开始获取旧状态。
  2. 写入任务 B 修改权威状态，并使缓存失效。
  3. A 完成，将旧结果重新放回缓存。

可以让计算携带开始时的版本，在提交时核对当前版本。版本不匹配时，放弃旧结果或重试；检查与提交也需要协调。

失效机制必须考虑尚未完成的工作。

十一、什么时候应该使用缓存？

缓存不是所有问题的默认答案。

可以用下面这个判断流程：

缓存设计自检

  1. 是否存在不可忽略的重复成本？ 先确定耗时、调用频率、分配或 IO。
  2. 相同或等价的请求是否经常出现？ 估计可复用性和命中率。
  3. 结果的有效性要求是否明确？ 是必须最新，还是允许一定延迟？
  4. 能否发现相关依赖的变化？ 选择完整的失效、版本或作用域机制。
  5. 容量和生命周期是否可控？ 明确谁维护、谁淘汰、谁释放。
  6. 整体收益是否大于成本？ 把查询、维护、内存和并发协调一起算进去。

实际开发中，尤其在 Unity 中，应当先利用 Profiler 确认耗时、内存分配、资源加载和调用频率等真实问题，再决定缓存粒度。

例如，将一个普通字段的访问再包上一层字典查找，通常不是有价值的优化。

相反，缓存复杂布局计算、重复的配置解析结果，或昂贵查询的结果，可能非常有价值。

十二、回到本质：缓存究竟是什么？

我们可以逐层总结。

第一层：性能视角

缓存通过保存已获得的结果，降低未来重复获取该结果的成本。

第二层：数据视角

缓存引入一份可复用的数据表示，因此需要明确它与原始来源之间的一致性关系。

第三层：正确性视角

缓存是否能够使用，取决于数据依赖和有效性条件，而不是缓存容器中是否存在该数据。

第四层：架构视角

缓存是一种可封装、可替换的性能策略，必须受到业务契约、状态管理、所有权和生命周期的约束。

我认为理解缓存时，最值得记住的是下面这个抽象。

假设系统中有一项操作：

R = f(X)

我们决定不再每次执行 f，而是保存之前的结果 R。

这看起来只是一个性能优化，但实际上我们引入了新的责任：

证明旧结果仍然可以代表当前请求的正确结果。

这里的“正确”可以是严格一致，也可以是业务明确定义的可接受延迟。

因此：

缓存的本质，是在正确性约束下，对过去计算或获取结果的有条件复用。

它的难点不是如何存储数据，而是如何保证这种复用仍然成立。

建议接下来深入学习的方向

结合 Unity/C# 开发和架构设计，接下来最值得深入的三个主题是：

  1. Cache Invalidation 与依赖追踪：当一个结果依赖多个状态时，如何完整且高效地维护失效关系？
  2. Memoization（记忆化）与增量计算：什么时候应该缓存整个函数结果，什么时候只重新计算受影响的部分？
  3. 缓存一致性与并发正确性：异步加载、版本竞争、多线程访问时，如何避免旧数据覆盖新数据？

其中我最推荐先研究 Memoization 与增量计算。

因为它能够把缓存、纯函数、依赖关系、不变量和性能优化联系起来，进一步深入到一个更重要的问题：

当系统只有一小部分状态发生变化时，我们为什么要重新执行全部计算？

从结果反推条件

最弱前置条件

Weakest Precondition · WP

给定一个程序和期望的最终结果，反向推导出程序开始执行之前，必须满足的最宽松条件。

程序正确性逆向推理契约与规格C# 示例
01 / What

什么是最弱前置条件？

最弱前置条件回答的问题是：

为了保证程序执行之后一定得到我想要的结果，执行之前至少需要满足什么条件？

这是一种从结果反推条件的程序推理方法。

从一个简单的例子开始

C# · 示意语句
x = x + 3;

我们的目标是：执行结束后，x >= 10。

那么，执行之前，x 至少需要是多少？

x + 3 ≥ 10　⇒　x ≥ 7

这就是该程序相对于目标 x >= 10 的最弱前置条件。

为什么叫“最弱”？

以下条件都能保证结果：

  • x >= 10
  • x >= 8
  • x >= 7

但 x >= 7 对初始状态的限制最少。如果允许 x = 6，执行后就只有 9，无法满足目标。所以 x >= 7 是刚好足够的条件。

“弱”指限制少。
条件越弱，允许的初始状态越多；条件越强，允许的初始状态越少。
前置条件x ≥ 7
x := x + 3→
后置条件x ≥ 10
← 从后置条件出发，逆向推导 WP

程序按照从左到右的方向执行，最弱前置条件按照从右到左的方向计算。

形式化定义

wp(S, Q)
符号含义
wpWeakest Precondition，最弱前置条件
SStatement，程序或语句
QPostcondition，希望成立的后置条件
wp(S, Q)为了保证执行 S 后满足 Q，执行前必须满足的最弱条件

严格来说，在经典的全正确性语义下，wp(S, Q) 描述所有这样的初始状态：

从这些状态开始执行 S，程序能够正常终止，并且所有可能的执行结果都满足 Q。

这里不仅要求结果正确，还要求程序能够终止。本文默认把异常等执行失败排除在“正常完成”之外。

02 / Why

为什么需要最弱前置条件？

普通程序思维是正向的

写代码时，我们通常从初始状态出发，执行代码，得到结果。

C# · 示意片段
int x = 5;
x += 3;
Console.WriteLine(x); // 8

我们知道初始值，所以能够计算结果。但实际编程经常遇到相反的问题：我们知道希望得到的结果，却不知道初始状态应该满足什么条件。

把结果要求转换成执行前的要求

C# · 扣款操作
balance -= cost;

我们希望扣除费用之后，余额不能小于 0。但 balance 和 cost 都是在运行时才确定的。如何证明代码不会产生负余额？

目标 · balance′ 表示执行后的余额balance′ ≥ 0
根据程序行为balance′ = balance − cost
代入并整理balance − cost ≥ 0　⇒　balance ≥ cost

因此，在数学整数模型下，执行前只需要满足 balance >= cost，就能保证扣款后余额非负。

C# · 示意方法
public static int Spend(int balance, int cost)
{
    if (balance < cost)
        throw new InvalidOperationException("余额不足");

    return balance - cost;
}

如果业务还要求消费金额不能为负数，就还需要检查 cost >= 0。

规格说明决定了推导的目标。
最弱前置条件只会推导出保证指定后置条件所需的要求，不会自动推导出你没有声明的业务规则。

此方法用于展示检查的结构，尚未处理所有整数溢出情况；数学整数推导不能直接等同于 C# int 的全部运行时行为。

它解决的根本问题

普通测试回答：“对于我测试过的输入，程序运行结果是否符合预期？”

最弱前置条件帮助回答：“什么样的输入能够保证程序一定符合预期？”

它把“程序似乎能够正确运行”转化为可以进行数学推理的问题。

03 / How

如何计算最弱前置条件？

从后置条件开始，按照程序执行顺序的反方向，逐条计算。

规则一：赋值语句

假设程序是 x = E;，希望执行后满足 Q，那么：

wp(x := E, Q) = Q[x ← E]

这表示：将后置条件 Q 中出现的变量 x，替换为表达式 E。这里 := 表示赋值。

C#
x = x * 2;

后置条件为 x ≥ 20。替换之后：

2x ≥ 20　⇒　wp = (x ≥ 10)

这就是赋值语句最核心的计算方法。

这里假设表达式有定义，且没有溢出、异常等问题。替换涉及的 x 是后置状态中的 x；表达式 E 使用赋值前的值。

规则二：顺序执行

C#
x = x + 3;
x = x * 2;

希望最终满足 x ≥ 20。必须从最后一条语句开始推导：

最终目标 Qx ≥ 20
反推 x = x * 22x ≥ 20　⇒　x ≥ 10
反推 x = x + 3x + 3 ≥ 10　⇒　x ≥ 7

最终得到最弱前置条件 x >= 7。

wp(S₁; S₂, Q) = wp(S₁, wp(S₂, Q))
  • 执行顺序：先 S₁，再 S₂。
  • 推导顺序：先分析 S₂，再分析 S₁。

规则三：条件分支

C#
if (x >= 0)
{
    x = x + 2;
}
else
{
    x = x + 10;
}

希望最终满足 x ≥ 5。需要分别分析两个分支，并结合该分支实际被执行的条件。

情况 A：执行 if 分支

已知 x ≥ 0，要求执行后 x + 2 ≥ 5，即 x ≥ 3。结合分支条件后，仍为 x ≥ 3。

情况 B：执行 else 分支

已知 x < 0，要求执行后 x + 10 ≥ 5，即 x ≥ −5。结合分支条件，得到 −5 ≤ x < 0。

因此，整个程序的最弱前置条件为：

(x ≥ 3) ∨ (−5 ≤ x < 0)

最弱前置条件不一定是简单的连续数值范围，也可能是由多个逻辑条件组合而成的表达式。

通用公式为：

wp(if B then S₁ else S₂, Q)
= (B ⇒ wp(S₁, Q)) ∧ (¬B ⇒ wp(S₂, Q))

⇒：蕴含（如果……那么……）；∧：并且；∨：或者；¬：否定。

其本质是：每个可能被执行的分支，都必须保证最终满足后置条件。这些规则默认条件判断本身也能够正常完成。

04 / Practice

自己推导一次

给定下面的程序：

C#
x = x + 4;
x = x * 3;

后置条件为 x ≥ 30。执行之前，x 至少需要满足什么条件？

展开答案与推导

先从最后一条语句开始：

3x ≥ 30　⇒　x ≥ 10

再反推第一条语句：

x + 4 ≥ 10　⇒　x ≥ 6

因此最弱前置条件是 x >= 6。验证边界：x = 6 时，先变为 10，再变为 30，恰好满足目标；x = 5 时，最终为 27，不满足目标。

练习同样采用数学整数模型。

05 / Connection

最弱前置条件与霍尔逻辑

Hoare Logic（霍尔逻辑）使用这样的表达：

{P} S {Q}
  • P：前置条件。
  • S：程序。
  • Q：后置条件。

在通常的霍尔三元组解释中，它表示部分正确性：如果程序从满足 P 的状态开始运行且正常终止，那么结果满足 Q。

最弱前置条件进一步回答：

为了保证程序终止且满足 Q，P 究竟可以放宽到什么程度？

在全正确性语义下，可以使用以下关系判断前置条件 P 是否足够：

P ⇒ wp(S, Q)

例如，程序为 x = x + 3;，后置条件 Q 为 x >= 10，算出 wp(S, Q) 为 x >= 7。

如果声明的前置条件 P 是 x >= 8，显然：

x ≥ 8 ⇒ x ≥ 7

这个前置条件足以保证目标，但它不是最弱的，因为它不必要地排除了 x = 7 这个合法初始状态。

概念核心问题
前置条件 P我要求程序开始前满足什么？
后置条件 Q我要求程序执行后满足什么？
Hoare Logic在给定前置条件下，程序是否符合规格？
Weakest Precondition为了保证给定结果与终止，执行前最少需要满足什么？

WP 可以视为连接程序实现和程序正确性证明的一种重要工具。若只讨论部分正确性，对应的通常是后文的 WLP。

06 / Loops

循环为什么比较特殊？

前面讨论的赋值和条件分支，通常可以通过有限次反向替换求解。但循环的执行次数可能取决于输入。

C# · 假设 n 为整数
while (n > 0)
{
    n--;
}

希望最终满足 n = 0。这段程序的最弱前置条件是：

n ≥ 0
  • n > 0：循环不断递减，最终到达 0。
  • n = 0：循环不执行，结果仍然是 0。
  • n < 0：循环不执行，结果是负数，不满足目标。

对于复杂循环，我们往往无法直接枚举所有迭代过程，需要借助两个概念。

循环不变量 · Loop Invariant

在进入循环以及每次迭代的边界处都成立的性质。例如这个循环中的 n >= 0：初始满足它，每次在 n > 0 时递减，仍能保持它。

退出时，同时成立 n >= 0 和 n <= 0，因此得到 n == 0。

终止性度量 · Loop Variant

在每次迭代中严格下降、且取值于良基集合中的量。常见选择是非负整数：此例使用 n，每次迭代减少 1，且不能无限下降，从而证明循环最终结束。

严格下降且有下界，对任意实数度量并不足以保证终止；例如 1、1/2、1/4……可以无限下降。这里使用整数很关键。

足够的条件不一定就是最弱的条件。
不变量与终止性度量能够帮助证明某个前置条件足够，但通过这种方式证明出来的条件，未必就是数学意义上的最弱条件。
07 / Termination

WP 不仅关心结果，还关心终止

C# · 死循环
while (true)
{
}

即使希望的后置条件是 Q = true，经典全正确性意义下仍有：

wp(S, true) = false

因为这个程序永远不会终止，没有任何初始状态能让它正常结束。

概念保证什么
WP
Weakest Precondition		程序正常终止，并满足后置条件。
WLP
Weakest Liberal Precondition		如果程序正常终止，那么满足后置条件；不要求终止。

因此，对于这个死循环：

wp(S, true) = false
wlp(S, true) = true

WLP 为 true，是因为没有任何正常终止的执行能够违反后置条件；这并不表示程序能够完成工作。

这个区别对应程序验证中的全正确性与部分正确性。

推导依赖明确的执行模型。
在真实 C# 程序中，还需要明确如何处理整数溢出、异常、外部状态变化等情况。数学整数推导不能不加区分地直接套用到所有运行时行为。
08 / Essence

WP 到底在做什么？

可以把 WP 理解为一种严格的需求反推机制：

从后置条件 Q 出发我要保证什么结果？
根据程序 S 逆向计算执行前究竟需要满足什么？
验证实际初始状态是否满足 wp(S, Q)得到关于终止与结果的正确性保证。
不变量描述程序必须持续维护的性质。
前置条件描述程序执行之前的要求。
后置条件描述程序执行之后的要求。
Hoare Logic建立执行前、程序行为与执行后之间的逻辑关系。

Weakest Precondition 从后置条件和具体程序出发，计算出足以保证正常终止与目标结果的最宽松初始条件。

目标结果 + 程序行为
↓ 逆向推导
最弱初始条件

最弱前置条件的价值，在于将“希望程序正确”转化为“程序在什么条件下必然正确”这一可推导、可验证的问题。

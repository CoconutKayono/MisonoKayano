What / Why / How · 直达本质

契约式设计与霍尔逻辑Design by Contract & Hoare Logic

我们如何确定一段程序的行为是正确的，而不仅仅是“看起来能运行”？

前置条件 P后置条件 Q不变量 I程序正确性
  • Design by Contract（DbC）：明确规定调用者与被调用者各自承担什么责任，以及程序必须保证什么。
  • Hoare Logic（霍尔逻辑）：用数学逻辑证明，在给定条件下执行程序，能否保证得到预期结果。

核心关系

契约描述什么叫正确，
霍尔逻辑提供推理程序为何正确的方法。

01 / WHAT什么是契约式设计？

1. 契约的本质是责任与保证

假设我们有一个钱包：

C# · 最初的钱包实现
public class Wallet
{
    public int Balance { get; private set; }

    public void Withdraw(int amount)
    {
        Balance -= amount;
    }
}

我们希望这个方法能正确扣除余额。但“正确扣除”究竟意味着什么？

  • 可以扣除负数吗？
  • 可以扣除超过余额的金额吗？
  • 扣除后余额允许小于零吗？
  • 扣除成功后，余额一定减少了指定金额吗？

代码本身没有明确回答。契约式设计认为：一个方法的正确性，需要通过明确的条件来定义。通常包括三个核心概念。

P

前置条件 · Precondition

调用方法前，调用者必须满足的条件。
amount > 0 && amount <= Balance

Q

后置条件 · Postcondition

方法正常执行完成后，被调用者必须保证的条件。
Balance == oldBalance - amount

I

不变量 · Invariant

对象在规定的有效状态边界必须始终满足的条件。
Balance >= 0

可以把方法调用理解成下面的责任交换：

  1. 调用者 Caller负责满足前置条件 P。
  2. 被调用者 Callee执行方法 C。
  3. 正常执行完成被调用者保证后置条件 Q，并维护不变量 I。

调用者满足前置条件，被调用者才有义务履行相应的后置条件。

这不是说前置条件不满足时程序就应该崩溃，而是说：正常成功路径的契约不再适用。失败路径应另外定义，例如返回失败结果或抛出明确异常。

2. 契约不是注释，而是行为规范

例如我们可以写成：

C# · 带条件检查的钱包
using System;
using System.Diagnostics;

public sealed class Wallet
{
    public int Balance { get; private set; }

    public Wallet(int initialBalance)
    {
        if (initialBalance < 0)
            throw new ArgumentOutOfRangeException(
                nameof(initialBalance));

        Balance = initialBalance;
    }

    public void Withdraw(int amount)
    {
        // 前置条件
        if (amount <= 0)
            throw new ArgumentOutOfRangeException(
                nameof(amount));

        if (amount > Balance)
            throw new InvalidOperationException(
                "Insufficient balance.");

        int oldBalance = Balance;

        // 状态转移
        Balance -= amount;

        // 后置条件
        Debug.Assert(Balance == oldBalance - amount);

        // 不变量
        Debug.Assert(Balance >= 0);
    }
}

这里 oldBalance 保存操作之前的状态。我们的契约可以写成：

P : 0 < amount ≤ Balanceold
Q : Balance′ = Balanceold − amount
I : Balance ≥ 0

Debug.Assert 只是开发期间检查契约的一种手段，不等于数学证明，且通常不会在 Release 构建中执行。契约也不一定必须写成运行时断言。

另外，如果“余额不足”是正常业务情况，实际设计中可能更适合用 TryWithdraw 返回失败结果，而非将其当成程序错误。

02 / WHY为什么需要契约式设计？

1. 因为程序能够执行，不代表行为正确

下面这段代码，对于编译器来说完全合法：

C# · 语法合法的扣款
Balance -= amount;

但是编译器一般不知道：

  • 余额不得为负数。
  • 金额必须为正数。
  • 这次扣款不能影响其他账户。

这些属于业务正确性，而不是语法正确性。契约式设计的作用，就是将隐含在开发者脑海中的规则转化为明确的规范。

2. 因为需要明确错误的责任归属

假设方法收到 amount = -10。如果 Withdraw 明确要求 amount > 0，而调用者传入了 -10，说明调用者违反了约定。

反过来，如果 amount = 10、余额为 100，调用方法后余额却成为 120，说明被调用者没有履行保证。

契约因此让我们能够区分：

  • 调用方式是否正确？
  • 方法实现是否正确？
  • 数据状态是否仍然有效？

3. 因为需要控制局部正确性

大型程序的一个核心困难是：一个方法可能被几十个地方调用。如果没有契约，每个调用者都需要阅读内部实现才能判断如何正确使用它。

有契约以后，调用者只需要理解它的要求和保证，而不必知道具体实现细节。这就是契约式设计对模块边界、信息隐藏与模块组合的重要意义。

03 / WHAT什么是霍尔逻辑？

Hoare Logic 是一种用于推理程序正确性的形式逻辑体系。它最核心的表达是：

{P} C {Q}Hoare Triple · 霍尔三元组
符号含义
PPrecondition，前置条件
CCommand，待执行的程序或命令
QPostcondition，后置条件

它的标准含义是：

如果程序执行前满足 P，并且程序 C 正常终止，那么执行后的状态一定满足 Q。

注意这里的“正常终止”。标准 Hoare 三元组描述的是部分正确性（Partial Correctness），不自动保证程序一定终止。

一个最简单的例子

C# · 加法赋值
int x = 5;
x = x + 3;

我们希望证明执行后 x == 8。写成霍尔三元组：

{x = 5}   x := x + 3   {x = 8}
  1. 执行前，x = 5。
  2. 执行命令，x := x + 3。
  3. 执行后，x = 8。

这里 := 表示赋值，并非数学上的相等关系。那么问题来了：为什么我们能够断定后置条件成立？这才是霍尔逻辑真正要解决的问题。

04 / WHY为什么需要霍尔逻辑？

契约式设计告诉我们：“这个方法应当满足什么条件。”但它没有自动证明：“这个方法的实现是否真的满足这些条件。”

C# · 待证明的实现片段
void Withdraw(int amount)
{
    Balance -= amount;
}

我们声明了：

P : 0 < amount ≤ Balance
Q : Balance ≥ 0

我们如何证明，满足 P 的情况下执行代码必然满足 Q？不能仅仅因为我们写了后置条件，就认为它必然成立。我们需要进行逻辑推导，霍尔逻辑提供的就是这种推导方式。

关键思想：把程序当作状态变换来证明

设钱包原来的余额为 b，取款金额为 a。执行：

b′ = b − a

我们知道 a ≤ b。两边减去 a，得到 b − a ≥ 0。因此 b′ ≥ 0，证明完成。

{0 < a ≤ b}   b := b − a   {b ≥ 0}

注意，后置条件里的 b 指更新后的变量值。这是一项非常简单的形式化证明，但它体现了本质：

程序的正确性可以从前置条件、程序语义和逻辑规则中推导出来，而不只是依靠测试结果。

05 / HOW霍尔逻辑如何证明程序正确？

霍尔逻辑有一套推理规则。这里介绍最核心的三个。

规则一：赋值规则（Assignment Rule）

这是最基础、也是最重要的规则。假设程序是：

C# · 赋值命令
x = x + 3;

期望执行之后满足 Q：x = 8。那么执行之前需要满足什么？我们反过来思考：要让赋值后 x == 8，赋值前必须满足 x + 3 = 8，因此 x = 5。

{x = 5}   x := x + 3   {x = 8}

这种从结果向前推导所需条件的思想，称为 Weakest Precondition（最弱前置条件，WP）。

对于赋值 x := E，有：

wp(x := E, Q) = Q[E/x]Q[E/x]：把后置条件 Q 中自由出现的变量 x 替换为表达式 E。

对应的赋值公理是 {Q[E/x]} x := E {Q}。对于这里无副作用、总能求值的整数表达式，替换也给出了最弱前置条件。

交互示例：反推前置条件

下面改变目标结果和加数，观察执行前的 x 必须是多少。

最弱前置条件计算器

整数赋值：x := x + k

目标后置条件 Qx = 8
执行的命令 Cx := x + 3
最弱前置条件 Px = 5

反向替换：x + 3 = 8，因此 x = 8 − 3 = 5。

这里在数学整数范围内讨论，不考虑机器整数溢出。禁用脚本时显示默认例子。

它真正重要的地方是：我们可以先定义什么结果是正确的，再反向计算为了得到正确结果，执行前需要满足什么。这正是程序验证的基础思路之一。

规则二：顺序组合（Sequence Rule）

假设程序执行两个操作，希望最终 x = 16：

C# · 两个顺序操作
x = x + 3;
x = x * 2;

我们分别证明：

{x = 5}   x := x + 3   {x = 8}
{x = 8}   x := x × 2   {x = 16}

把它们连接：

{x = 5}   C1; C2   {x = 16}

从而得到顺序组合规则：

{P} C1 {R}   {R} C2 {Q}{P} C1; C2 {Q}

这说明一个很重要的事实：复杂程序可以通过证明各个局部操作的正确性，再利用逻辑规则组合出整体正确性。其中 R 是连接两个操作的中间条件。

规则三：循环不变量（Loop Invariant）

循环比赋值和顺序执行更复杂，因为我们不知道循环会执行多少次。例如：

C# · 求和循环
int sum = 0;

for (int i = 1; i <= n; i++)
{
    sum += i;
}

我们希望计算：

1 + 2 + ⋯ + n = n(n + 1)2

那么如何证明这个循环正确？我们需要寻找一个循环不变量，即每次进入循环条件检查时都成立的关系。以下假设 n 是非负整数。

换一种等价写法：

C# · 便于证明的等价形式
int i = 0;
int sum = 0;

while (i < n)
{
    i++;
    sum += i;
}

可以找到：

I : sum = i(i + 1)2 ∧ 0 ≤ i ≤ n

接下来检查三个方面。

第一：初始化（Initialization）

循环开始前 i = 0, sum = 0，所以不变量成立。

第二：保持（Preservation）

如果本轮开始时不变量成立，且 i < n，执行 i++ 和 sum += i 后，新的 sum 仍等于新 i 对应的前 i 项求和公式。

i′ = i + 1
sum′ = i(i + 1)2 + (i + 1) = (i + 1)(i + 2)2 = i′(i′ + 1)2
由 i < n 且 i、n 为整数，可得 0 ≤ i′ ≤ n。

第三：退出（Exit）

循环退出时 i >= n，加上不变量中的 i <= n，可得 i == n，因此 sum = n(n+1)/2。

证明循环不变量，并不意味着证明循环一定结束。

还要证明某个非负整数度量会在每轮严格减小，例如：

V = n − i

循环继续时 V > 0，每执行一轮 V 减少 1，因而循环最终终止。于是我们区分：

正确性需要证明的内容
Partial Correctness
部分正确性		如果程序正常终止，结果一定正确。
Total Correctness
完全正确性		程序一定终止，并且正常终止时结果正确。

这里的推理假设数学整数运算；实际 C# 中还需考虑溢出等机器执行语义。

06 / RELATIONSHIP契约式设计与霍尔逻辑的关系

  1. Design by Contract制定契约：明确 P、Q、I 与责任边界。
  2. Hoare Logic根据程序 C 的语义，推理或证明正确性。
  3. 实现满足契约的证据证明结论、验证结果，以及尚未覆盖的假设。
维度Design by ContractHoare Logic
核心目的规定行为与责任证明程序性质
关注重点应该保证什么为什么可以保证
核心概念前置、后置、不变量三元组、推理规则
使用方法声明契约、边界检查逻辑推导、形式化验证
是否需要数学证明不要求用于形式化证明
适用范围API、对象、模块、业务行为算法、程序、状态变换

特别注意：二者不是严格的上下层关系。契约式设计可以完全不使用霍尔逻辑；霍尔逻辑也可以用于没有显式契约的普通程序。

它们的共同基础，是用逻辑条件精确描述程序状态及其变化。

07 / HOW实际开发应该如何使用？

可以按下面这个思考顺序处理重要的业务操作。

第一步：定义合法状态

例如钱包：

I : Balance ≥ 0

第二步：定义操作的有效输入

例如取款：

P : 0 < amount ≤ Balance

第三步：定义成功后必须满足的结果

Q : Balance′ = Balanceold − amount

第四步：实现状态转移

C# · 状态赋值
Balance -= amount;

第五步：推导该实现是否满足结果

我们已知：

amount ≤ Balanceold

因而：

Balanceold − amount ≥ 0

执行后：

Balance′ = Balanceold − amount

所以：

Balance′ ≥ 0

这就证明了，在给定假设下，该操作保持余额非负的不变量。

不过，实际程序中还需要明确其他状态是否允许改变，以及并发执行、异常、中断和持久化失败等是否属于契约覆盖的行为范围。上面证明的是单次状态赋值的正确性，不是整个支付或存档系统的可靠性。

08 / CLARIFICATIONS容易产生的三个误解

误解一：有了前置和后置条件，就证明程序正确了

不对。定义契约只是提出需要满足的性质。必须通过证明、静态验证或其他检查方式，才能获得实现符合这些性质的证据。即使所有测试通过，也不等于对所有可能输入完成了数学证明。

误解二：不变量在方法执行的每一个瞬间都必须成立

不一定。对象不变量通常要求在构造完成、公开方法正常进入与退出等规定边界成立；内部实现可以在受控的中间步骤暂时打破不变量，但不能向外暴露无效状态。

而循环不变量是在循环检查点上保持的，不代表循环体每一行执行后都必须成立。

误解三：Hoare Logic 能证明任何程序绝对不会出错

不对。证明永远依赖明确的模型、前提和语义。例如只证明余额计算正确，不能自动得到并发安全、数据库事务原子性或服务器断电后数据不丢失等结论。这些性质需要额外建模和验证。

09 / ESSENCE回到本质

如果把程序看作一个状态转移：

S C⟶ S′

那么三个概念可以统一起来：

  • 前置条件 P：允许操作开始时，状态 S 需要满足什么？
  • 后置条件 Q：操作结束后，状态 S′ 必须满足什么？
  • 不变量 I：在约定的状态边界上，哪些性质必须保持？

而霍尔逻辑的核心可以用正常终止的状态关系表达：

P(S) ∧ C(S, S′) ⇒ Q(S′)对所有 S、S′ 成立；C(S, S′) 描述程序可能产生的正常终止状态转移。
Design by Contract 让正确性成为明确的约定；
Hoare Logic 让正确性成为可以严谨推理的命题。

这两个概念都在推动我们从“写出能执行的代码”，走向“知道代码满足什么性质，以及为什么满足”。

如果继续深入，最值得研究的是 Weakest Precondition（最弱前置条件）。因为它直接回答一个很实用的问题：

已经知道程序执行后必须满足什么，能否反向推导出执行前需要满足什么？

掌握这个思路之后，很多前置条件、状态转移约束以及不变量就不再只是凭经验设计，而是可以系统地推导。

Reactive Programming（响应式编程）：What、Why、How，直击本质

响应式编程（Reactive Programming）是一种重要的编程范式。它与我们之前讨论的事件系统、观察者模式、缓存、依赖追踪、增量计算、状态转移有非常紧密的联系。

理解响应式编程，最重要的不是先学习 Observable、Subscribe 或者各种响应式框架，而是理解一个根本问题：

当系统中的一个状态发生变化时，所有依赖这个状态的结果，应该如何保持正确？

响应式编程提供了一种答案：

不再要求使用者主动寻找变化、重新获取结果，而是声明依赖关系，让变化沿着依赖关系传播。

一、What：什么是响应式编程？

1.1 从最简单的问题开始

假设我们正在开发游戏。

玩家拥有三个属性：

int health = 80;
int maxHealth = 100;

float healthPercent = (float)health / maxHealth;

这里存在一个数学关系：

P = H / M

其中：

  • H：当前生命值。
  • M：最大生命值。
  • P：生命值百分比。

假设玩家受伤，生命值从 80 变成 50。

health = 50;

请思考：

healthPercent 会自动变成 0.5 吗？

不会。

因为 healthPercent 是之前计算得到的一个数值，而不是与 health 自动保持联系的数学公式。

我们必须重新计算：

healthPercent = (float)health / maxHealth;

如果游戏还需要更新：

  • 生命值文字。
  • 生命条长度。
  • 低生命值警告。
  • 屏幕红色闪烁效果。

那么还需要手动触发所有对应逻辑。

问题逐渐出现：

为什么修改一个状态，还需要手动维护所有依赖它的结果？

这就是响应式编程试图解决的问题。

1.2 命令式与响应式的区别

传统命令式编程（Imperative Programming）侧重描述：

状态变化之后，我应该执行哪些操作？

例如：

void TakeDamage(int damage)
{
    health -= damage;

    healthPercent = (float)health / maxHealth;

    healthText.text = health.ToString();
    healthBar.fillAmount = healthPercent;

    warning.SetActive(healthPercent < 0.3f);
}

在这段代码中，TakeDamage() 不仅负责修改生命值，还负责通知或更新多个依赖结果。

响应式编程则倾向于声明：

哪些结果依赖哪些状态？当依赖的状态发生变化时，应该如何更新结果？

命令式：显式安排后续更新

响应式：事先建立依赖，变化自动传播

示意图：响应式系统预先知道依赖关系。状态变化时，不必让修改状态的代码逐个寻找下游使用者。

注意，响应式编程并不是不再执行更新操作。

计算仍然需要执行，只是更新责任从业务调用者转移到了依赖传播机制。

1.3 响应式编程的本质定义

我建议使用下面这个定义来建立认知：

响应式编程是一种围绕随时间变化的数据、变化通知及其依赖关系组织程序的编程范式，使系统能够在上游数据变化时，自动传播变化并更新下游结果。

可以抽象为：

Y = f(X)

传统计算：

Y₀ = f(X₀)

这只保证计算那一刻的结果正确。

如果 X 变化，必须再次调用 f 才能得到新的 Y。

响应式编程希望建立持续有效的依赖关系：

X ⟶ f ⟶ Y

当 X 发生变化：

X₀ → X₁

系统根据预先建立的关系执行：

Y₁ = f(X₁)

因此可以把响应式计算理解为：

计算关系 + 变化感知 + 依赖传播 + 结果更新。

但要强调：响应式机制并不保证一定是最小计算量。它可能重新执行整个计算，也可能采用更细粒度的增量计算。

1.4 响应式编程的四个核心元素

核心元素 作用 例子
Source（数据源） 提供变化中的数据 玩家生命值
Dependency（依赖关系） 描述谁依赖谁 生命值百分比依赖生命值
Propagation（变化传播） 将变化传递到相关节点 生命值变化通知生命条
Reaction（响应） 计算新结果或产生效果 调整生命条显示

实际上，还需要考虑一项横切规则：订阅生命周期，即谁有权持续接收变化，以及何时停止接收。

二、Why：为什么需要响应式编程？

2.1 根本原因：状态依赖会形成网络

假设游戏中拥有以下数据：

玩家生命值
玩家最大生命值
玩家金币
玩家等级
玩家经验
玩家装备

每个数据都可能影响多个结果。

例如：

金币
 ├── 金币文字
 ├── 商品是否可购买
 ├── 商店按钮状态
 └── 任务完成状态

生命值
 ├── 生命条
 ├── 生命值百分比
 │    ├── 低血量警告
 │    └── 屏幕视觉效果
 └── 是否死亡

这里已经不再只是简单的方法调用关系，而是形成了数据依赖图（Dependency Graph）。

如果所有变化都靠手动更新，我们必须在每一个可能修改数据的入口处，记住所有相关依赖。

例如生命值可能被这些行为修改：

  • 敌人攻击。
  • 使用药水。
  • 持续恢复效果。
  • 装备属性调整。
  • 关卡特殊规则。

如果每个入口都需要同步维护生命条和其他衍生结果，就非常容易遗漏。

因此，真正的问题是：

当同一个状态存在多个修改入口和多个依赖使用者时，如何避免各个修改入口重复承担依赖维护责任？

响应式编程的解决方式是将两者解耦：

状态所有者只负责维护正确状态及其变化通知；依赖者自己声明对这个状态的关注。

2.2 轮询并不是总能解决问题

另一种方式是在 Unity 的 Update() 中不断检查：

void Update()
{
    healthBar.fillAmount =
        (float)player.Health / player.MaxHealth;
}

这属于拉取式（Pull）检查。

无论玩家生命值是否发生变化，都会执行。

响应式编程常见的模式是由上游主动推送变化（Push）：

player.HealthChanged += UpdateHealthBar;

只有生命值变化时才触发对应处理逻辑。

两者区别：

维度 轮询 Pull 变化通知 Push
触发方式 使用者主动查询 数据源主动通知
无变化时 可能仍持续检查 通常无须通知
时效性 取决于轮询频率 取决于通知与调度机制
依赖管理 使用者自行管理 可以通过订阅关系管理
复杂度 简单直接 需要处理订阅和传播

但不能得出“响应式永远比轮询快”的结论。

例如，角色位置每帧都变化，订阅、分配对象、调度和复杂事件处理可能比直接在 Update() 中计算更昂贵。

响应式首先是依赖关系的组织方式，而不是性能优化的保证。

2.3 响应式将两种变化分离

这里有个很重要的设计思想：

事实发生变化，与如何呈现或使用这个事实，是两种不同的责任。

例如：

领域层
    玩家生命值从 80 变成 50

表现层
    更新生命条

表现层
    更新文本

表现层
    显示受伤效果

生命值是游戏事实。

生命条只是这个事实的一种表现形式。

假如以后换一个 UI 设计，游戏中生命值的修改逻辑不应该跟着改变。

这正是响应式编程在 UI、游戏状态呈现和实时数据系统中特别有价值的原因。

三、How：响应式编程是如何工作的？

3.1 第一步：让普通状态具有可观察性

假设我们原本拥有一个普通变量：

private int health = 100;

外部无法直接知道它什么时候变化。

我们可以封装状态，并在状态真正变化后发出通知：

using System;

public sealed class HealthModel
{
    private int _health;

    public int Health => _health;
    public int MaxHealth { get; }

    public event Action<int> HealthChanged;

    public HealthModel(int maxHealth)
    {
        if (maxHealth <= 0)
            throw new ArgumentOutOfRangeException(nameof(maxHealth));

        MaxHealth = maxHealth;
        _health = maxHealth;
    }

    public void TakeDamage(int damage)
    {
        if (damage < 0)
            throw new ArgumentOutOfRangeException(nameof(damage));

        int next = Math.Max(0, _health - damage);

        if (next == _health)
            return;

        // 先修改真实状态
        _health = next;

        // 再发布状态变化
        HealthChanged?.Invoke(_health);
    }
}

这里发生了什么？

首先：

_health = next;

改变系统中的真实状态。

然后：

HealthChanged?.Invoke(_health);

通知依赖这个状态的其他部分。

注意先后顺序：

状态转移 → 状态提交 → 变化通知

如果反过来，订阅者收到通知后，再去读取 Health，可能得到旧值。

因此：

状态变化通知通常应该描述已经发生的事实，而不是将要发生的事实。

当然，Changing 类型的事件可以有不同的语义，但必须在接口契约中明确区分。

3.2 第二步：建立依赖关系

例如 Unity 中的生命条：

using UnityEngine;
using UnityEngine.UI;

public sealed class HealthPresenter : MonoBehaviour
{
    [SerializeField] private Image healthBar;

    private HealthModel _model;

    public void Bind(HealthModel model)
    {
        Unbind();

        _model = model;

        _model.HealthChanged += UpdateBar;

        // 初始化显示
        UpdateBar(_model.Health);
    }

    public void Unbind()
    {
        if (_model == null)
            return;

        _model.HealthChanged -= UpdateBar;
        _model = null;
    }

    private void UpdateBar(int health)
    {
        healthBar.fillAmount =
            (float)health / _model.MaxHealth;
    }

    private void OnDestroy()
    {
        Unbind();
    }
}

这个例子使用普通 C# 事件，不依赖第三方响应式框架，并假定绑定、状态修改和 UI 更新都在 Unity 主线程执行。

它已经具备最基本的响应式特征：

  • 数据源主动发出变化通知。
  • 使用者提前建立订阅关系。
  • 状态变化时触发下游响应。
  • 使用者不需要在每个伤害入口手动更新 UI。

这里尤其值得思考：

我们真的使用了“响应式编程”吗？还是仅仅使用了观察者模式？

准确地说，这是一个使用观察者模式实现的简单响应式更新机制。

它还没有体现复杂响应式系统非常重要的能力：组合和变换持续变化的数据。

接下来进入更核心的部分。

3.3 第三步：将变化理解为数据流

假设玩家生命值按下面的顺序变化：

生命值随时间变化

数据不再只是某一时刻的值，而是一系列按时间出现的值或变化。

普通变量关注：

H(t₀) = 100

响应式系统进一步关注：

H(t₀), H(t₁), H(t₂), H(t₃), …

可以将这些变化建模为一个序列：

HealthStream:

100 ─── 80 ─── 50 ─── 65 ─── ...

我们可以对整个序列声明计算规则：

HealthStream
      ↓
除以 MaxHealth
      ↓
HealthPercentStream

于是得到：

HealthStream:         100 ── 80 ── 50 ── 65

HealthPercentStream:  1.0 ─ 0.8 ─ 0.5 ─ 0.65

关键变化是：计算函数不再只作用于单个值，而是被应用到未来持续到来的值。

例如：

f(x) = x / 100

普通程序：

float result = f(80);

响应式流：

对未来的每一个 Health 值应用 f

这就引出了响应式编程中的核心操作：流变换（Stream Transformation）。

3.4 Observable、Observer、Subscription 究竟是什么？

以 Reactive Extensions（Rx）为例，有三个基础概念。

概念 本质 责任
Observable 可被订阅的值或通知序列 提供数据
Observer 序列的消费者 接收和处理通知
Subscription 订阅关系及其控制句柄 管理订阅生命周期

在 .NET 中，可以使用：

IObservable<T>
IObserver<T>
IDisposable

其中 IObserver<T> 有三个标准通知方法：

void OnNext(T value);
void OnError(Exception error);
void OnCompleted();

它们分别代表：

  • OnNext：出现一个新值。
  • OnError：流发生终止性错误。
  • OnCompleted：流正常结束。

在典型 Rx 流契约中，一旦收到 OnError 或 OnCompleted，就不应再收到后续数据。Subscribe() 返回的 IDisposable 则允许提前取消订阅。Microsoft — Observer Design Pattern、ReactiveX — Observable

请注意：Observable 不等于一个普通变量，也不等于一定包含当前值。

Observable 描述的是一种通知序列。它可能表示当前状态的连续更新，也可能仅表示瞬时事件，甚至可能是一项异步计算的结果。

3.5 第四步：使用操作符建立计算关系

下面使用 Rx.NET 风格的 C# 代码。

此示例需要项目已经安装并引用 System.Reactive，不是直接依靠 Unity 原生 API。

假设：

IObservable<int> healthStream;

我们需要监听低生命值状态：

IDisposable subscription = healthStream
    .Select(health => health / 100f)
    .Select(percent => percent < 0.3f)
    .DistinctUntilChanged()
    .Subscribe(isLowHealth =>
    {
        warning.SetActive(isLowHealth);
    });

这段代码可以拆成四层。

这里最关键的是：

我们没有编写一个手动遍历所有下游依赖的更新函数，而是在订阅时构造了一条数据处理管道。

一旦订阅关系建立，后续数据就会沿着管道传播。

常用操作符还有：

操作符 本质 典型用途
Select 将每个值映射为另一个值 生命值转换为百分比
Where 只允许符合条件的值通过 筛选特定道具事件
DistinctUntilChanged 忽略连续重复的结果 UI 状态去重
CombineLatest 合并多个输入的最新值 组合生命值与最大生命值
Merge 合并多个事件流 合并多个伤害来源
Throttle / Debounce 根据时间抑制频繁变化 输入停止一段时间后搜索
Switch 只跟踪最新的内部流 搜索时放弃旧请求结果

操作符命名与细节因库而异。例如 Rx.NET 的 Throttle 通常表现为防抖，而其他库对 throttle 的定义可能是限流，不能只凭名字判断行为。

3.6 第五步：多个依赖如何组合？

这是真正体现响应式编程价值的地方。

生命值百分比依赖两个状态：

P = H / M

如果只监听 Health，却忽略 MaxHealth，就存在缺陷。

假设：

Health = 50
MaxHealth = 100
Percent = 0.5

玩家装备一个道具：

Health = 50
MaxHealth = 200

此时正确的 Percent 应该是：

P = 50 / 200 = 0.25

即使当前生命值没有变化，也需要重新计算。

所以：

依赖关系必须覆盖决定结果的所有可变输入。

在 Rx.NET 中，可以通过 CombineLatest 实现：

var healthPercentStream =
    healthStream.CombineLatest(
        maxHealthStream,
        (health, maxHealth) =>
            maxHealth > 0
                ? (float)health / maxHealth
                : 0f
    );

CombineLatest 在每个输入都至少产生过一个值之后，会在任意输入产生新值时，使用各个输入的最新值重新计算。ReactiveX — CombineLatest

交互示例：改变任意一个依赖

范围：0 至 200 · 步长：5

范围：20 至 200 · 步长：20

派生状态：HealthPercent

50%

min(Health / MaxHealth, 1)

改变任意一个滑块，派生值和生命条会随之更新。演示中生命值允许超过最大生命值，显示比例截断为 100%。

至此，响应式编程最重要的机制已经建立：

数据源变化 → 依赖计算 → 结果传播

但实际工程远比这个公式复杂，因为我们还要面对生命周期、时序、错误、线程和一致性问题。

四、深入本质：响应式编程与事件驱动到底有什么区别？

这是非常容易混淆的问题。

4.1 事件驱动关注“发生了什么”

例如：

public event Action<int> OnDamageTaken;

当角色受到伤害：

OnDamageTaken?.Invoke(20);

事件表示：

有一件事情发生了：角色受到了 20 点伤害。

它关注的是发生过的事实。

但是，单凭这条事件，我们不能直接确定角色当前还有多少生命值。

4.2 响应式状态关注“当前是什么”

例如：

Health = 80;

这表示一个持续有效的状态。

可以将它理解为：

事件：玩家受到了 20 点伤害。

状态：玩家现在还剩 80 点生命值。

两者具有不同的时间语义。

事件往往是瞬时的，错过了可能就没有了。

状态是持续存在的，新的观察者通常需要在订阅时获取当前状态。

因此，构建响应式系统时，最好区分：

  • Event Stream（事件流）：描述发生了什么。
  • State Stream（状态流）：描述状态如何随时间变化。

例如 Rx 中，普通 Subject<T> 通常不会向新订阅者重放历史值，而 BehaviorSubject<T> 可以保存并向新订阅者提供最近的值。

这也解释了为什么之前的代码在绑定 UI 时还需要：

_model.HealthChanged += UpdateBar;
UpdateBar(_model.Health);

第一次负责接收未来变化。

第二次负责获取当前快照。

如果没有第二次初始化，UI 可能一直显示默认内容，直到生命值第一次发生变化。

4.3 事件系统与响应式编程的关系

对比 事件驱动 响应式编程
主要关注 事件的发生与处理 变化的数据及其关系
核心抽象 事件、监听器、处理器 可观察状态、流、依赖与变换
组合能力 通常需要手动编排 通常拥有丰富的组合操作
时间处理 由开发者自行实现 可以通过时间操作符表达
典型应用 领域事件、输入、系统通知 UI 绑定、实时查询、状态派生

这里没有严格的互斥关系。

事件是响应式系统的一种输入来源，观察者模式则是很多响应式实现所使用的基础机制。

响应式编程也不是完全等同于 Reactive Extensions。

从更广泛的技术分类来看，常见的响应式模型还包括响应式 UI、Signals、基于依赖图的自动计算，以及更严格的函数式响应式编程（FRP）。

这些模型共享变化传播思想，但并不具备完全相同的语义或实现方式。

五、响应式编程与缓存、依赖追踪、增量计算的关系

这一部分非常关键，因为它能够将几个概念联系起来。

5.1 它们解决的是同一个大问题的不同方面

考虑：

C = f(A, B)

我们已经计算出：

A = 10
B = 20
C = 30

然后：

A = 15

此时系统面临四个问题。

问题 相关技术
如何知道 A 改变了？ 变化通知、可观察状态
如何知道 C 依赖 A？ 依赖追踪
如何知道旧 C 已经不能使用？ 缓存失效
如何更新 C？ 重新计算、增量计算

响应式编程可以将这些技术组合起来，形成完整的变化传播机制。

5.2 使用依赖图理解

当 A 变化时，依赖图使系统能够定位需要更新的 C，再将新的 C 传播给 UI。

在这一过程中：

  • 依赖追踪决定传播路径。
  • 缓存失效决定哪些旧结果不能再被直接使用。
  • 增量计算决定是否可以利用旧结果避免完整重算。
  • 响应式机制组织变化如何触发和传播。

但注意，响应式编程不必同时实现缓存和增量计算。

一个简单的响应式流可以完全不缓存结果，每次输入变化都重新执行函数。

5.3 响应式与记忆化的区别

记忆化（Memoization）通常是：

调用 f(x)
    ↓
查询是否有缓存结果
    ↓
有：直接返回
无：执行计算并缓存

它重点关注：

相同输入是否可以复用以前的计算结果？

响应式编程更关注：

输入 X 改变
    ↓
通知依赖 X 的计算
    ↓
更新下游结果

它重点关注：

输入发生变化后，谁应该被更新？

所以它们并不冲突。

甚至可以组合使用：

响应式依赖追踪
      ↓
确定受影响计算
      ↓
记忆化 / 缓存
      ↓
决定是否需要重新计算
      ↓
更新结果

一个有用的区分方式是：

记忆化关注计算结果的复用；响应式关注变化关系的持续维护；增量计算关注已有结果变化后如何减少重算。

六、更深一步：响应式编程的正确性问题

到这里，我们已经理解基本机制。但是，从架构和系统正确性的角度看，接下来这些问题往往比 Subscribe 本身更加重要。

6.1 问题一：变化传播是否具有一致性？

考虑以下依赖图：

菱形依赖：X 同时影响 A 和 B，而 C 又依赖 A 与 B。

初始状态：

X = 1,　A = 2,　B = 2,　C = 4

现在：

X = 2

正确的新状态应该是：

A = 4,　B = 3,　C = 7

但是，假设系统采用同步逐个通知的机制：

  1. X 变化，首先更新 A，得到 A = 4。
  2. A 通知 C，C 用新的 A 和旧的 B 计算出 C = 6。
  3. X 接着更新 B，得到 B = 3。
  4. B 再次通知 C，最终 C = 7。

那么 C 曾短暂得到错误的中间结果 6。

这就是响应式系统可能出现的 Glitch（瞬时不一致）。

阶段 A B C
初始 2 2 4
A 更新后 4 2 6
B 更新后 4 3 7

如果 C 只用于最终显示，并且中间变化不可见，也许问题不大。

但如果 C 的订阅者执行：

if (C >= 6)
{
    GrantReward();
}

那么中间结果就有可能触发不应该发生的业务副作用。

这说明：

传播了变化，并不等于传播过程天然具有一致性。

需要根据具体框架和业务要求选择一致性策略。

常见解决方式有：

  • 批量更新（Batching）。
  • 事务式状态提交。
  • 按拓扑顺序重新计算依赖节点。
  • 使用同一版本的状态快照。
  • 合并重复更新，最终再统一触发副作用。

但不能认为所有 Rx 流都自动提供无 Glitch 保证。

6.2 问题二：订阅关系也有生命周期

例如：

var subscription = healthStream.Subscribe(UpdateUI);

从订阅开始，数据源可能持续持有观察者的引用。

如果 UI 已经销毁，但是订阅没有释放，可能出现：

  • 对象无法被及时回收。
  • 已经无效的 UI 继续接收消息。
  • 切换场景后发生非法访问。
  • 重复订阅导致同一逻辑执行多次。

因此，订阅本身是一种需要管理的关系资源。

private IDisposable _subscription;

private void OnDisable()
{
    _subscription?.Dispose();
    _subscription = null;
}

如果订阅是在 OnEnable() 中创建，那么通常应该在对应的 OnDisable() 中解除。

这里能够发现之前学过的几个概念之间的联系：

Subscription Lifetime ⊆ Subscriber 的有效使用期

具体的生命周期边界需要根据 UI、实体和服务的所有权关系确定。

例如长期存在的服务订阅，不一定需要在每次 UI 隐藏时解除；但界面专属订阅通常应该跟随界面生命周期。

6.3 问题三：响应式不是天然异步

很多人容易产生一个误解：

使用 Subscribe() 后，处理逻辑会自动在另一个线程执行。

这并不成立。

例如：

healthStream.Subscribe(health =>
{
    UpdateUI(health);
});

订阅回调在哪个线程执行，取决于数据源、调度器以及操作符。

一个同步发布的数据源，完全可以在触发变化的同一线程直接调用订阅者。

在 Unity 中尤其需要注意：大多数 Unity 对象和 UI API 应该在 Unity 主线程上访问。

如果生命值来自后台网络线程，通常需要明确将 UI 更新切换回主线程。

这也意味着：

响应式解决的是变化的组织与传播；线程切换和执行调度是另一个需要明确设计的问题。

6.4 问题四：当生产速度超过消费速度怎么办？

假设网络每秒产生 10,000 条消息，但是下游系统每秒只能处理 1,000 条。

如果直接无限制缓存：

生产者：10000 条/秒
       ↓
不断积累的队列
       ↓
消费者：1000 条/秒

积压会持续增加，可能最终耗尽内存。

解决这个问题需要流量控制。

典型策略有丢弃、合并最新值、限制缓存容量，或者让生产者依据消费者的处理能力调整发送速度。

其中 Backpressure（背压） 是一种重要机制：消费者向生产者表达自身还可以接收多少数据，避免无界积压。

需要区分：

  • Reactive Programming 是更广泛的编程范式。
  • ReactiveX / Rx 主要提供 Observable 及其组合操作。
  • Reactive Streams 是面向异步数据流、规定非阻塞背压协议的规范。

不能认为使用了 IObservable<T> 就自动拥有 Reactive Streams 规范中的背压保证。Reactive Streams Specification、Microsoft — Observer Design Pattern

6.5 问题五：响应式不应该破坏业务不变量

假设金币系统有一个不变量：

Gold ≥ 0

不应该让订阅者各自修改金币，形成没有统一约束的状态更新网络。

更可靠的架构是：

玩家发出购买请求
       ↓
领域服务验证
       ↓
检查金币、商品、库存
       ↓
原子地提交有效状态转移
       ↓
发布已提交的变化
       ↓
UI、提示、音效等响应

响应式非常适合处理状态派生和展示。

但是对于需要原子性、持久性、严格顺序、去重或可靠投递的关键业务，例如购买扣费、奖励发放和存档写入，不能仅仅依赖普通订阅回调来保证正确性。

这些仍然需要领域规则、事务、幂等或可靠消息机制。

七、实际工程中如何设计响应式架构？

我建议将它分为三个层次。

第一层：Authoritative State（权威状态）

保存真实游戏状态，验证命令，维护不变量，执行状态转移。

第二层：Reactive Derivation（响应式派生）

接收变化，组合多个状态，计算派生值，维护依赖关系。

第三层：Effects / Presentation（副作用与表现）

更新 UI、播放特效、展示提示，以及其他允许异步或延迟处理的响应。

它的设计思想是：

真实状态由明确的所有者维护；派生状态通过依赖关系计算；非权威性的表现效果订阅计算结果。

例如：

PlayerModel
 ├── Health
 ├── MaxHealth
 └── IsAlive（权威规则或派生状态）
         │
         ▼
Reactive ViewModel
 ├── HealthPercent
 ├── IsLowHealth
 └── HealthBarColor
         │
         ▼
Unity UI
 ├── Image.fillAmount
 ├── TMP_Text
 └── WarningEffect

这种结构有助于避免让 UI 控制真实游戏状态，也避免领域层直接依赖具体 UI 组件。

7.1 什么时候值得使用响应式编程？

场景 推荐程度 原因
生命值、金币、背包 UI 高 状态与视图之间有明确依赖
复杂表单、筛选和搜索 高 多输入组合及时间操作很方便
多个实时数据源组合 高 流组合具有明显优势
简单按钮点击 低至中 普通事件通常足够
每帧角色移动计算 视情况 可能增加调度和分配开销
购买与奖励事务 不宜单独依赖 需要额外保证业务正确性

与其问“项目是否应该采用响应式架构”，不如问：

这个模块是否存在持续变化的数据、多个相互依赖的结果，以及值得抽象出来的变化传播关系？

如果只是一个按钮触发一个函数，使用普通 C# 事件可能最直接。

如果多个状态互相组合，还需要筛选、防抖、状态派生和生命周期管理，响应式抽象的价值就会明显提高。

八、最后总结：用五个问题真正掌握响应式编程

把响应式编程归纳成以下五个问题，会比记住几十个操作符更有效。

问题 本质
What changes? 什么状态或事件会变化？
Who depends on it? 谁依赖这些变化？
How does change propagate? 变化如何传播到下游？
When is the result consistent? 什么时候可以认为结果正确且一致？
Who owns the subscription? 谁负责订阅的创建与释放？

最核心的思想，可以记成：

Reactive = Changes + Dependencies + Propagation

这不是某个框架的正式数学定义，而是帮助理解其核心机制的抽象。

再往深一层看，响应式编程实际上是在管理三个维度：

空间维度：依赖关系。 谁依赖谁，变化能够沿着哪些路径传播？

时间维度：变化序列。 变化何时发生，应该如何组合、过滤、延迟或取消？

正确性维度：状态一致性。 传播过程中是否存在旧值、乱序、重复、循环、竞争或无效订阅？

这三个维度共同决定了一个响应式系统能否正确运行。

最后，联系到之前讨论的架构设计：

命令式编程主要描述操作如何执行；声明式响应式编程主要描述随时间变化的数据之间应保持什么关系，并由机制维护这些关系。

它不是对命令式编程的全面取代，而是将变化传播这种横切责任从具体业务流程中抽离出来。

如果继续深入，我最建议研究的下一个专题是 Dependency Graph、Automatic Dependency Tracking 与 Glitch Freedom（依赖图、自动依赖追踪和无瞬时不一致性）。它能够把响应式编程、增量计算、缓存失效和状态正确性真正统一到同一个理论框架中。

参考资料：ReactiveX — Observable、Microsoft — Observer Design Pattern、Reactive Streams Specification。

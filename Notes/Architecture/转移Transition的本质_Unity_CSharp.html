WHAT / WHY / HOW

转移的本质。

变化是核心，规则约束变化，过程描述变化。

State Transition8 个主题含过程与规则补充Unity C# 示例

一次变化、它的约束、它的执行方式，是三个相关层次。
转移是变化；规则约束变化，过程描述变化。

TRANSITION / 变化从什么状态到什么状态
RULE / 约束在什么条件下可以发生
PROCESS / 执行这一次变化实际如何完成

更准确地理解“怎样变”，才能把状态组织成一个持续演化的系统。

转移（Transition）是从一种状态到另一种状态的变化；转移规则（Transition Rule）决定在什么条件下可以发生这种变化；转移过程（Transition Process）描述这种变化实际如何完成。

要真正理解转移，需要先区分三个概念：

  • 状态（State）：现在是什么样。
  • 事件（Event）：发生了什么。
  • 转移（Transition）：从一种状态到另一种状态的变化。

“状态应该如何改变”由转移规则决定；一次具体变化如何完成，由转移过程描述。三者密切相关，但并不等同。文末补充章节进一步区分这三个层次。

下面主要讨论程序设计中的状态转移（State Transition），但其原理具有普遍性。

01What：转移是什么？

想象一扇门。它有三种状态：关闭、打开、锁定。同一个对象可以在不同状态之间转移。

当门处于“关闭”状态时，收到“打开”请求，它就可能转移到“打开”状态。

我们可以抽象为：

StE⟶St+1

其中：

  • St：转移前的状态。
  • E：触发转移的事件。
  • St+1：转移后的状态。

但有一个关键问题：任何事件都能引起任何转移吗？

显然不是。例如，锁定的门不应该直接打开。

为了表达哪些变化被允许，可以定义转移规则：

T(S, E) = S′

其中 T 是转移规则，它决定在状态 S 下遇到事件 E，是否允许转移，以及转移到什么状态。

如果不满足条件，可以拒绝转移，保持原状态。

02Why：为什么需要转移？

表面上看，我们完全可以直接修改状态：

直接赋值 · 概念反例C# · 假设 State 允许外部赋值，非推荐实现
door.State = DoorState.Open;

为什么还要引入转移？因为能够赋予一个状态，不代表应该允许进入这个状态。

例如：

绕过规则 · 概念反例C# · 假设 State 允许外部赋值，非推荐实现
// 即使门已经锁定，也能被直接打开
door.State = DoorState.Open;

代码在语法上可能正确，但业务逻辑可能错误。这里的反例假设 State 允许外部赋值；后面的完整实现会通过私有 setter 禁止这种访问。

根本原因是：

状态描述当前事实，却不能独自表达状态变化的合法规则。

转移规则将合法变化显式地表达出来：

当前状态 事件或请求 结果
关闭 打开 转移到打开
关闭 上锁 转移到锁定
打开 关闭 转移到关闭
锁定 解锁 转移到关闭
锁定 打开 拒绝，保持锁定

由此获得一个重要的设计原则：

不要让外部代码随意决定对象变成什么状态，而应该由对象或状态机根据规则决定。

这样可以保证业务约束集中、明确、可测试，并减少非法状态的产生。

03How：转移如何实现？

实现转移不需要复杂的框架。它最基本只需要三个步骤：

  1. 接收事件。 例如：OpenRequested，表达“请求打开”。
  2. 检查转移条件。 当前状态允许打开吗？还有没有其他守卫条件？
  3. 提交合法的新状态。 需要时执行伴随转移的动作；若不满足规则，就拒绝并保持原状态。

使用 Unity C# 写一个简单实现：

Door.csUnity C# · 完整类型定义
public enum DoorState
{
    Closed,
    Open,
    Locked
}

public enum DoorEvent
{
    Open,
    Close,
    Lock,
    Unlock
}

public class Door
{
    public DoorState State { get; private set; }
        = DoorState.Closed;

    public bool Handle(DoorEvent e)
    {
        // 由当前状态和事件共同决定下一个状态
        DoorState? next = (State, e) switch
        {
            (DoorState.Closed, DoorEvent.Open)
                => DoorState.Open,

            (DoorState.Open, DoorEvent.Close)
                => DoorState.Closed,

            (DoorState.Closed, DoorEvent.Lock)
                => DoorState.Locked,

            (DoorState.Locked, DoorEvent.Unlock)
                => DoorState.Closed,

            _ => null
        };

        // 不存在合法转移
        if (next == null)
            return false;

        State = next.Value;
        return true;
    }
}

这里有两个值得注意的设计：

第一，State 具有私有 setter，外部代码不能任意修改状态。

第二，Handle 不只是修改变量，它定义了哪些转移允许发生。

这已经是一个最基本的有限状态机。代码中的 Door 是普通 C# 对象，可由 Unity 的 MonoBehaviour 创建并持有；它本身不需要挂到 GameObject 上。示例使用元组和 switch 表达式，需要相应的 C# 语法支持。

本例只允许代码中列出的四种转移。其他组合都返回 false，包括“已打开时再次打开”。某些系统也允许不改变状态的自转移；是否允许，应由各自规则明确规定，不能仅凭“前后状态相同”判断是否拒绝。

04深入本质：转移、事件、动作有什么区别？

假设玩家按下跳跃键：

  • 事件： 玩家按下跳跃键。
  • 条件： 玩家处于地面，并且允许跳跃。
  • 转移： 从站立转移到跳跃。
  • 动作： 施加向上的速度，播放跳跃动画。

它们之间的关系是：

(S, E)T · 满足条件⟶(S′, A)

这里的 A 表示转移时需要执行的动作或副作用。

关键在于：事件不等于转移，转移也不等于动作。

同一个事件在不同状态下，可能产生不同的转移，也可能什么都不发生。

例如玩家在空中按下跳跃键，如果游戏禁止二段跳，那么事件发生了，但不会发生新的跳跃转移。

此外，转移不一定必须由外部事件触发。计时器到期、内部条件满足，也可能触发转移。

本例 DoorEvent.Open 的含义是“打开请求”。若业务系统严格区分命令与已发生的事实，可以把请求命名为 OpenRequested，把成功结果命名为 DoorOpened；无论使用什么名字，都应先明确它代表输入还是结果。

06再深入一层：用函数描述转移规则

从更抽象的层面看，确定性的转移规则可以用一个函数描述：

T : S × E ⟶ S

意思是，将“当前状态”和“事件”作为输入，求出“下一个状态”。

这里把 S、E 分别看作状态集合与事件集合。当把拒绝请求的结果定义为“保持原状态”时，可以写成上面的总函数；如果只对合法组合定义转移结果，则是偏函数。本例的 bool 返回值额外区分“接受”和“拒绝”，避免仅凭新旧状态判断结果。

这只是最简单的模型。真实程序中，可能还需要考虑上下文、守卫条件、操作结果和转移副作用，例如：

T(S, E, C) = (S′, A)

其中 C 是上下文条件，A 是伴随转移的动作。

因此，一次转移的执行不一定只有一个简单的赋值语句，而可能包含一套受约束的业务过程。函数或规则描述允许怎样变化，执行过程才使具体变化实际发生。

对于重要的数据转移，例如“道具未领取 → 已领取”，还需要考虑并发、持久化和原子性，否则内存中的转移成功，不意味着整个业务操作已经可靠完成。

07最终总结：状态与转移的本质关系

概念 本质 关注的问题
状态 State 某个时刻的情况 现在是什么？
事件 Event 发生的事情 发生了什么？
条件 Guard 转移的约束 允许改变吗？
转移 Transition 从一种状态到另一种状态的变化 从什么状态变成什么状态？
转移规则 Transition Rule 定义允许的变化及其条件 在什么条件下可以怎样变？
转移过程 Transition Process 一次具体变化的执行过程 这次变化实际如何完成？
动作 Action 执行的操作 转移时做什么？

最后记住两个层次：

  • 从数学角度： 转移关系描述状态之间允许的变化，转移函数描述确定性的变化规则；一次转移是关系中的一个实例。
  • 从软件设计角度： 通过转移规则约束变化，通过执行过程完成一次具体的状态变化。

状态回答的是“是什么”，转移回答的是“怎样变”。

把两者结合起来，才能描述一个系统如何随着时间和事件不断演化。这正是状态机、交互系统、游戏玩法逻辑和业务流程建模的共同基础。

08补充：过程、规则与转移，严格区分

理解转移时，可以从两个不同角度观察：一个关注实际发生的变化，另一个关注变化必须遵循的约束。过程与规则密切相关，但严格来说不是同一个概念。

1. 过程（Process）：状态是怎么改变的？

过程描述实际发生了什么，以及变化如何完成。

例如，一扇门从“关闭”变成“打开”：

  1. 门最初处于关闭状态。
  2. 用户发出打开请求。
  3. 系统检查是否允许打开。
  4. 系统将状态更新为打开。
  5. 转移完成。

这是一段实际发生的过程。如果只关注状态本身，可以简化为：

S0 ⟶ S1

即：

关闭 ⟶ 打开

这里描述的是一次具体的状态变化。上面的五个步骤是帮助理解的展开，并不意味着一次转移必须具有五个步骤。

2. 规则（Rule）：状态允许怎样改变？

规则描述在什么条件下，允许或应该发生什么变化。例如：

  • 门关闭时，收到打开请求，可以转移到打开。
  • 门锁定时，收到打开请求，不允许转移到打开。
  • 门锁定时，收到解锁请求，可以转移到关闭。

可以将这些规则表达为：

T(S, E) = S′

规则本身只是定义了状态变化的关系。即使现在没有任何人打开门，这套规则依然存在。

  • 过程关注实际发生的一次变化。
  • 规则关注可能发生的变化及其条件。

3. 过程和规则是什么关系？

规则决定怎样转移，过程体现转移实际如何发生。

例如：

过程与规则 · 条件执行片段C# · 对象内部或局部上下文的示意片段
// 规则：门关闭时，才允许打开
if (state == DoorState.Closed)
{
    // 执行一次实际的状态变化
    state = DoorState.Open;
}

其中：

  • state == DoorState.Closed 是转移条件。
  • 整个 if 语句表达了一个转移规则。
  • state = DoorState.Open 是执行状态更新的操作。
  • 当这段代码在运行时成功将状态从关闭改为打开，便发生了一次状态转移。

这段代码是拥有状态修改权限的对象内部或局部上下文中的示意片段，不表示外部调用者可以绕过前面 Door.State 的私有 setter。

4. Transition 到底指过程还是规则？

Transition 的核心含义是“从一种状态到另一种状态的变化”，而不是规则本身。在不同语境下，它的侧重点有所不同：

语境 Transition 指什么
日常语言 从一种情况变成另一种情况的变化或过渡过程
数学、状态机理论 状态之间的转移关系，或者关系中的一次转移
软件设计 一次状态变化；也可能用作定义这种变化的转移规则的简称

例如在有限状态机中：

δ(关闭, 打开请求) = 打开

这里的 δ 是转移函数（Transition Function），也就是规则的数学表示。

而：

关闭 ⟶ 打开

表示一次可能的或实际发生的状态转移。两者密切相关，但不完全相同；箭头表达允许的变化还是执行轨迹中的一次变化，需要结合上下文判断。

因此，最初的表述应进一步严谨地区分为：

转移（Transition）是从一种状态到另一种状态的变化；转移规则（Transition Rule）决定在什么条件下可以发生这种变化；转移过程（Transition Process）描述这种变化实际如何完成。

还有一点值得注意：转移不一定需要多个步骤或持续一段时间。像 state = Open 这样的瞬时更新，只要完成了相应状态变化，也可以构成一次转移。

变化是转移的核心；规则约束变化，过程描述变化。

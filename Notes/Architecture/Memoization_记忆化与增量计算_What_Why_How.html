Memoization 与增量计算 · 完整阅读版

Memoization（记忆化）与增量计算（Incremental Computation）：What、Why、How，直击本质

这两个概念非常值得放在一起学习，因为它们与我们之前讨论的缓存（Cache）、状态管理、不变量、依赖关系、版本号以及数据生命周期都有密切关系。

我希望这次不仅解释它们是什么，更重要的是让你理解：

  • 为什么明明有了缓存，还需要记忆化和增量计算？
  • 记忆化复用的究竟是什么？
  • 增量计算为什么能避免重新计算？
  • 当数据发生变化时，如何知道哪些计算结果已经失效？
  • 在 Unity、C#、Lua 和实际游戏系统中，应该如何使用？

首先给出两个定义。

记忆化的本质：如果之前计算过相同的问题，就直接复用之前的答案。

增量计算的本质：当问题的一部分发生变化时，只处理变化造成的影响，尽可能复用其余计算成果。

它们解决的是两个不同层次的重复计算问题。

MemoizationIncremental Computation
同样的输入，再次出现输入的一部分改变
f(A) → 结果 X
再次 f(A) → 复用 X		已有结果 + 变化信息
→ 更新受影响的部分
避免相同输入的重复计算避免未受影响部分的重复计算

这就是全文最重要的区别：

记忆化关心的是「这个问题以前算过吗？」；增量计算关心的是「相较于上次，究竟有什么变了？」

一、What：什么是 Memoization（记忆化）？

1. 从普通计算开始理解

假设有一个函数：

C#
int Calculate(int x)
{
    return x * x + 10;
}

当我们执行：

C#
Calculate(5); // 35
Calculate(5); // 35
Calculate(5); // 35

虽然每次输入都是 5，结果都是 35，但普通函数每次都会执行表达式。

这产生了一个值得思考的问题：

既然第一次已经知道 Calculate(5) = 35，为什么第二次还要重新计算？

于是我们可以存储计算结果：

输入结果
535
874
10110

下次再遇到输入 5，直接返回保存的 35。

这种技术就叫作 Memoization（记忆化）。

2. 用数学理解其本质

对于一个确定性函数：

y = f(x)

普通计算每次都会执行 f。

记忆化则引入一个映射：

M[x] = f(x)

当请求计算时：

Memo(x) ={
M[x]如果存在已缓存的有效结果
M[x] ← f(x)否则先计算再记录

所以，记忆化实际上把函数计算转换成了：

先查询历史答案，历史答案不可用时才进行计算。

它并没有改变函数本身的数学含义，而是改变了函数的执行策略。

3. 记忆化与普通缓存是什么关系？

这里非常容易产生概念混淆。

记忆化不是与缓存完全平行的一种技术。

Memoization 是缓存技术的一种特定应用形式。

维度缓存（Cache）记忆化（Memoization）
主要复用内容已获取或计算的结果函数调用的计算结果
Key业务 Key、资源 ID、请求参数等函数输入或能够唯一决定结果的有效输入
典型用途资源加载、网络请求、数据库查询、计算避免函数重复执行
依赖管理取决于具体缓存策略必须保证相同 Key 对应的结果仍有效
两者关系更广泛的机制一种计算结果缓存策略

比如：

C#
// 缓存加载后的贴图
Texture2D GetTexture(string path);

// 记忆化某个纯计算函数
long Fibonacci(int n);

两者底层都可能使用 Dictionary。

真正决定它们属于哪一种技术的，不是用了什么容器，而是如何使用它们来复用工作成果。

另外，记忆化通常针对函数的确定性结果；缓存则可以涉及外部资源、远程数据及其时效性，这些需要不同的有效性规则。

二、Why：为什么需要记忆化？

1. 根本原因：一个复杂问题可能包含重复的子问题

普通的函数调用只关心：

给我输入，我就重新执行计算。

但实际上，很多计算任务具有一个特征：

不同的计算路径，可能会反复遇到相同的子问题。

最经典的例子是斐波那契数列：

F(n) = F(n − 1) + F(n − 2)

其中：

F(0) = 0，F(1) = 1

如果计算 F(5)，递归调用关系如下：

观察你会发现：

F(3) 被计算多次，F(2) 也被计算多次。

而且随着 n 增大，这类重复计算会迅速增多。

朴素递归的时间复杂度为：

O(φⁿ)，φ ≈ 1.618

现在我们增加记忆化：

第一次计算 F(3)，记录答案。后续需要 F(3)，不再展开整个递归树。

这样一来，每个不同的子问题至多真正计算一次。

算法时间复杂度额外空间复杂度
朴素递归O(φⁿ)O(n) 递归栈
记忆化递归O(n)O(n)
自底向上的动态规划O(n)可优化至 O(1)

注意：记忆化本身并不保证任何算法都能从指数复杂度降到线性复杂度。这里能够优化，是因为不同子问题只有 O(n) 个，而且每个问题在拿到依赖结果后只需常数时间计算。

2. 更深一层：记忆化改变了计算的时间与空间关系

通常情况下：

每次请求↓执行计算↓返回结果

记忆化则变为：

第一次请求

执行计算↓存储结果↓返回结果

后续相同请求

读取存储结果↓直接返回

其核心是一种权衡：

额外空间 + 管理开销 ⇄ 减少重复计算时间

也就是经典的空间换时间。

但这里有一个容易忽视的事实：

记忆化并不一定比重新计算快。

假设：

C#
int Square(int x) => x * x;

如果使用 Dictionary 存储结果，那么哈希计算、查询、内存访问的开销，可能比一次乘法更大。

因此：

是否适合记忆化，并不取决于能不能缓存，而取决于复用收益是否超过查询、存储与维护成本。

三、How：如何实现记忆化？

1. C# 实现一个真正的记忆化函数

C#
using System;
using System.Collections.Generic;

public sealed class FibonacciCalculator
{
    private readonly Dictionary<int, long> _memo = new()
    {
        [0] = 0,
        [1] = 1
    };

    public long Calculate(int n)
    {
        if (n < 0 || n > 92)
            throw new ArgumentOutOfRangeException(nameof(n));

        // 1. 先检查问题是否已经解决
        if (_memo.TryGetValue(n, out long result))
        {
            return result;
        }

        // 2. 没有历史答案，才真正计算
        result = Calculate(n - 1) + Calculate(n - 2);

        // 3. 记录这次计算成果
        _memo[n] = result;

        return result;
    }
}

这里限制 n <= 92，因为 F(93) 已经超出 C# long 的有效整数范围。

记忆化的执行过程可以归纳成三个动作：

查询（Lookup）

这个输入对应的答案是否已经存在？

  • 命中：直接返回。
  • 未命中：计算 → 记录 → 返回。

2. 记忆化最重要的正确性前提

现在思考一个问题。

假设有一个游戏伤害计算函数：

C#
int CalculateDamage(int skillId)
{
    return skillConfig[skillId].BaseDamage
           + player.Attack;
}

你决定为它添加记忆化，使用 skillId 作为 Key。

第一次调用：

skillId = 1001
player.Attack = 50

计算结果 = 150

假设技能基础伤害为 100。

之后玩家装备发生变化：

skillId = 1001
player.Attack = 80

正确结果 = 180
缓存结果 = 150

为什么会出现错误？

因为 skillId 没有变化，但是实际影响结果的 player.Attack 变化了。

这暴露了一个至关重要的概念：

函数的参数，不一定等于函数计算所依赖的全部输入。

在上面的代码中：

Damage = f(skillId, player.Attack, skillConfig)

而不是真正的：

Damage = f(skillId)

记忆化使用的 Key，必须足以决定结果；否则就要在相关依赖变化时使历史结果失效。

可选策略包括：

  • 把所有有效输入纳入 Key，例如技能 ID、攻击力、配置版本。
  • 在攻击力或技能配置变化时，删除对应的记忆化结果。
  • 使用依赖版本号、脏标记等机制判断历史结果是否仍然有效。

缓存命中不等于结果正确。只有依赖条件仍然成立，缓存结果才值得复用。

记忆化最容易与纯函数配合使用，原因就在这里：纯函数的结果只依赖显式输入，没有隐藏的可变状态，因此更容易确定缓存 Key。

四、What：什么是增量计算？

现在进入第二个核心概念。

记忆化解决了一个问题：

如果输入完全相同，是否可以不用重复计算？

但现实世界里还有一种更普遍的情况：

输入经常发生变化，但每次只改变其中很小的一部分。

例如一个游戏背包拥有 10 万种不同道具，每种道具有自己的数量和重量。

我们希望得到背包当前的总重量：

W = Σᵢ₌₁ⁿ qᵢwᵢ

其中：

  • qᵢ：第 i 种道具的数量。
  • wᵢ：第 i 种道具的单件重量。
  • W：背包总重量。

假设系统已经计算出：

W = 10000

然后玩家获得了一件重量为 5 的道具。

最直观的方式是重新遍历整个背包：

C#
long totalWeight = 0;

foreach (var item in items)
{
    totalWeight += (long)item.Count * item.UnitWeight;
}

假设拥有 10 万种道具，那么每次重新计算，都要遍历 10 万个条目。

但你可能会产生一个疑问：

之前已经知道总重量是 10000，现在只是增加了重量 5，为什么不能直接得到 10005？

完全可以。

W′ = W + ΔW

其中：

ΔW = 5

所以：

W′ = 10000 + 5 = 10005

这便是最简单的增量计算。

1. 增量计算的数学本质

假设原始输入为：

y = f(x)

现在输入发生变化：

x′ = x + Δx

传统重新计算：

y′ = f(x′)

增量计算尝试通过一个更新算法获得新的结果：

y′ = Update(x, y, Δx)

这意味着我们不仅利用最新输入，还利用：

  1. 原本已经完成的计算结果。
  2. 已经发生的输入变化。
  3. 必要时保留下来的中间计算状态。

如果更新规则可以表达成加法形式，就有：

y′ = y + Δy

其中 Δy 是输入变化所产生的结果变化。

但是注意：

并不是所有增量计算都能表示为简单的加减法。

对于排序、最大值、路径规划、复杂依赖计算等问题，可能需要树、堆、索引、依赖图或其他辅助状态。

增量计算的本质不是「使用加法更新数据」，而是：

利用已有计算成果和变化信息，求出新的正确结果，而不是从头执行所有工作。

2. 用可交互的例子直观理解

下面模拟一个背包。修改一种道具的数量，观察两种计算方式所需处理的条目数量。

背包总重量 · 实时模拟
道具单件重量数量小计
当前总重量
与初始重量的差值
本次处理条目

示例包含 5 种道具；比较的是参与处理的条目数，并非运行耗时。

在这个例子里：

  • 全量计算的时间复杂度为 O(n)。
  • 已知某个条目的旧值、新值时，增量更新总重量的时间复杂度为 O(1)。

对于 10 万种道具，区别会非常明显。

当然，前提是这次变更的信息可获得，并且总重量已经处于正确状态。

五、Why：为什么有了记忆化，还需要增量计算？

这是理解两者关系最重要的地方。

假设我们已经利用记忆化保存了：

CalculateTotalWeight(背包状态 A) = 10000

后来玩家增加一个道具，背包从状态 A 变成了状态 B。

我们再执行：

CalculateTotalWeight(背包状态 B)

问题出现了：

A 和 B 不是相同的输入。

因此，假如记忆化仅以整个背包状态为 Key，且只缓存过 A，那么这次就会缓存未命中，需要重新计算 B。

但增量计算不一样。

它不需要输入完全相同。

它可以利用：

已经计算的总重量：10000
本次道具重量变化：+5

直接得到：

最新总重量：10005

所以：

记忆化通过识别「相同输入」来避免计算。

增量计算通过识别「输入变化」来减少计算。

这也是为什么两者不是简单的替代关系。

记忆化有时也能通过复用不变子问题来实现部分增量效果；但只给整个问题加一个缓存，并不能自动获得高效的局部更新能力。

进一步理解：两种技术复用的是什么？

问题记忆化增量计算
核心判断这个子问题以前算过吗？哪些输入或依赖发生了变化？
复用对象历史输入对应的计算结果旧结果、未失效的中间结果及其他计算状态
输入是否允许改变可以改变，但通常只能命中已有的相同 Key主要就是处理输入改变
关键机制结果查询与保存差量更新、依赖追踪、失效传播
主要风险Key 不完整、缓存过期、内存增长漏掉变化、依赖错误、更新顺序错误
常见适用问题重复子问题、昂贵的确定性函数大数据集合局部修改、复杂派生状态

记忆化更侧重历史答案的可复用性。

增量计算更侧重变化对已有计算成果的影响范围。

六、How：如何真正实现增量计算？

实际工程中的增量计算可以分为两种非常重要的实现方式。

  1. 差量更新（Delta Update）：根据变化直接更新已有结果。
  2. 依赖追踪与局部重算（Dependency Tracking / Selective Recalculation）：确定哪些结果受到影响，只重新计算这些结果。

这两种方式都可以避免不必要的全量重算，但原理并不完全相同。

1. 第一种：差量更新

我们继续使用背包重量的例子。

下面的 C# 代码实际维护一个总重量，而不是在每次读取时遍历所有道具。

C#
using System;
using System.Collections.Generic;

public sealed class InventoryWeight
{
    private struct Item
    {
        public int Count;
        public int UnitWeight;

        public Item(int count, int unitWeight)
        {
            Count = count;
            UnitWeight = unitWeight;
        }
    }

    private readonly Dictionary<string, Item> _items = new();

    public long TotalWeight { get; private set; }

    public void SetItem(string itemId, int count, int unitWeight)
    {
        if (string.IsNullOrEmpty(itemId))
            throw new ArgumentException(nameof(itemId));

        if (count < 0 || unitWeight < 0)
            throw new ArgumentOutOfRangeException();

        // 1. 查询这个道具之前对总重量的贡献
        long oldWeight = 0;

        if (_items.TryGetValue(itemId, out Item oldItem))
        {
            oldWeight = (long)oldItem.Count * oldItem.UnitWeight;
        }

        // 2. 计算修改后的贡献
        long newWeight = (long)count * unitWeight;

        // 3. 使用差量计算新的总重量
        long nextTotal = checked(TotalWeight - oldWeight + newWeight);

        // 4. 修改原始数据
        if (count == 0)
            _items.Remove(itemId);
        else
            _items[itemId] = new Item(count, unitWeight);

        // 5. 提交更新后的总重量
        TotalWeight = nextTotal;
    }
}

它的关键不是 Dictionary，而是这一行：

C#
long nextTotal = TotalWeight - oldWeight + newWeight;

对于每次修改，我们不关心所有其他道具。

只需要知道：

  • 原本的总重量。
  • 这个道具以前贡献多少重量。
  • 现在应该贡献多少重量。

这就是增量计算的思想。

特别值得注意：SetItem 使用的是设置目标状态，而不只是一个 AddWeight(5) 方法。它会先比较旧贡献和新贡献，因此在不发生其他修改的情况下，重复设置同样的数量和重量不会重复累加。

这种设计还具有一个深层性质：它维持着一个不变量（Invariant）。

TotalWeight = Σᵢ Countᵢ × UnitWeightᵢ

如果初始状态满足这个不变量，每次操作又执行：

W′ = W − 旧贡献 + 新贡献

那么每次成功更新后，不变量仍然成立。

从本质上说，增量计算的正确性要求是：更新后的派生结果，必须等价于使用更新后的原始数据重新计算的结果。

这也是把增量计算与之前学到的契约式设计、不变量联系起来的地方。

2. 第二种：依赖追踪与局部重算

差量更新非常适合总和、计数等问题。

但更复杂的系统往往存在这样的情况：

你可以注意到，这里存在两条不同的依赖链。

如果 Buff 发生变化，究竟应该重新计算哪些内容？

依赖关系图 · 交互演示

选择发生变化的数据源，观察需要重新计算或更新的节点。

受影响节点 不受影响节点

这体现了一个更高级的思想：

当系统知道数据之间的依赖关系，就可以确定变化的影响范围。

例如 Buff 变化，只需要处理：

Buff↓最终攻击力↓战斗力↓战斗力 UI

而背包重量以及重量 UI 完全不需要重新计算。

这种机制可以理解成一个依赖图（Dependency Graph）。

在无环依赖图中，增量计算通常包含四个阶段：

  1. 发现变化（Change Detection）：确定哪些源数据发生变化。
  2. 依赖失效（Invalidation）：将受到影响的派生结果标记为不再可靠。
  3. 重新计算或差量维护（Recomputation / Delta Update）：仅更新必要的结果。
  4. 传播新结果（Propagation）：将必要的变化继续通知下游依赖。

这里尤其需要区分两个概念：

失效不等于立即重算。

一个节点被标记为失效，只意味着：

它保存的结果可能已经不能代表当前输入。

系统可以选择立即重新计算，也可以等到真正有人读取结果时再计算。

后者称为按需计算（Lazy Evaluation）。

3. C# 实现按需的局部重算

下面用 Unity 项目里常见的角色属性系统举例。

C#
public sealed class CharacterStats
{
    private readonly int _baseAttack;

    private int _equipmentBonus;
    private int _buffBonus;

    private int _cachedAttack;

    // true 表示缓存的攻击力可能已经失效
    private bool _attackDirty = true;

    public CharacterStats(int baseAttack)
    {
        _baseAttack = baseAttack;
    }

    public void SetEquipmentBonus(int value)
    {
        if (_equipmentBonus == value)
            return;

        _equipmentBonus = value;
        _attackDirty = true;
    }

    public void SetBuffBonus(int value)
    {
        if (_buffBonus == value)
            return;

        _buffBonus = value;
        _attackDirty = true;
    }

    public int Attack
    {
        get
        {
            if (_attackDirty)
            {
                _cachedAttack =
                    _baseAttack +
                    _equipmentBonus +
                    _buffBonus;

                _attackDirty = false;
            }

            return _cachedAttack;
        }
    }
}

假设执行过程是：

C#
var stats = new CharacterStats(100);

stats.SetEquipmentBonus(20);

int a = stats.Attack; // 计算得到 120
int b = stats.Attack; // 直接返回 120

stats.SetBuffBonus(30);

int c = stats.Attack; // 重新计算得到 150
int d = stats.Attack; // 直接返回 150

这里有两个机制：

  • Attack 没有变化时，重复读取直接复用结果。
  • Buff 或装备变化时，将攻击力标记为脏，只有后续需要读取时才重新计算。

严格区分的话，这个例子没有直接用差量公式维护 _cachedAttack，而是使用了缓存失效 + 按需重算。

它是局部增量计算系统的一种基础机制。如果再把攻击力、战斗力、UI 等节点组织成依赖图，就能实现整个系统的选择性重算。

4. 为什么需要版本号？

你之前已经学习过版本号（Version）和逻辑生命周期。它们恰好可以解决增量计算中的一个关键问题：

如何证明一个历史计算结果对应的仍然是当前状态？

假设：

角色属性版本 = 10
攻击力缓存版本 = 10

两者相同，说明没有检测到影响该缓存的后续变更，可以复用。

现在 Buff 改变：

角色属性版本 = 11
攻击力缓存版本 = 10

缓存版本落后，需要重新计算。

计算完成后：

角色属性版本 = 11
攻击力缓存版本 = 11

版本号所表达的并不是时间，而是：

计算结果所依赖的状态属于哪一个逻辑修订版本。

在异步计算中，它还有其他用途。

例如后台任务基于版本 10 的状态开始计算，但计算结束时角色属性已经到版本 11。

那么系统就可以检测到：

任务使用的版本：10
当前属性版本：11

→ 本次结果已经过时
→ 不应直接覆盖当前结果

需要注意，版本号必须随着所有相关依赖的有效变更而更新。版本号一致只能说明所采用的版本跟踪规则没有检测到变化，并不自动证明没有遗漏依赖。

七、进一步思考：为什么增量计算不总是简单地更新差值？

前面的背包重量例子可能让你觉得：

那以后所有数据变化，我都保存一个旧结果，然后加上差值不就行了吗？

但我们换一个问题。

假设玩家拥有五件装备，战斗力只取其中最高装备的攻击力：

MaxAttack = max(10, 20, 30, 40, 50) = 50

现在最强的装备攻击力从 50 降到 15。

如果你只保存：

当前最大攻击力 = 50
变化的装备：50 → 15

那么能不能直接计算出新的最大值？

不能。

因为新的最大值取决于其他装备的攻击力。

正确答案为：

max(10, 20, 30, 40, 15) = 40

为了高效增量更新，你可能需要额外维护排序结构、最大堆或者其他索引。

这说明：

不同计算具有不同的可增量化程度。

计算类型常见增量维护方式典型更新开销
总和 Sum减去旧贡献，加上新贡献O(1)
数量 Count根据插入或删除更新计数O(1)
平均值 Average同时维护 Sum 和 CountO(1)
最大值 Max维护有序多重集合等结构O(log n)
区间求和线段树、树状数组O(log n)
复杂依赖公式依赖图、脏标记、局部重算与受影响范围有关

复杂度是相应数据结构和操作假设下的典型值，例如哈希操作平均 O(1)。并非所有实现都能保证这些界限。

增量计算的真正难点，不是写出 old + delta。

而是识别：

为了让下一次计算变得便宜，究竟需要保存哪些中间状态？

这些额外保存的状态，有时比最终答案本身还重要。

八、Memoization、增量计算、缓存与对象池的统一理解

我们把之前学过的对象池和缓存也放在一起。

技术避免重复做什么主要复用什么
对象池（Object Pool）频繁创建、销毁或初始化对象可重新使用的对象实例
缓存（Cache）重复获取或计算已有结果数据、资源、计算结果
记忆化（Memoization）相同子问题的重复计算输入对应的历史计算结果
增量计算（Incremental Computation）输入局部变化后的不必要全量重算旧结果、未受影响的计算成果与辅助状态

这张表不是说四者完全互斥。

它们可以组合使用：

比如 Unity 中有一个复杂的排行榜系统：

  • 使用对象池复用排行榜 UI Item 的 GameObject。
  • 使用缓存保存已经加载的头像 Sprite。
  • 使用记忆化保存代价高昂、输入可确定的排名规则子计算结果。
  • 使用增量计算，在一个玩家分数变化时尽量只维护受影响的排名与 UI。

可以说，它们都属于对重复工作进行优化的思想，但在不同层次工作。

九、架构层面：增量计算为什么与状态管理密不可分？

这是我认为比具体算法更值得理解的一部分。

假设我们拥有一个系统：

源状态（Source State）↓派生状态（Derived State）↓UI / 逻辑消费者

例如：

玩家基础属性、装备、Buff↓最终攻击力↓战斗力↓角色面板 UI

最终攻击力和战斗力并不一定需要作为独立的权威源数据存在。

因为它们可以通过源状态计算得到。

这类数据称为派生状态。

增量计算则是在回答：

如何以尽可能小的代价，使派生状态始终与源状态保持一致？

这产生三个架构性要求。

1. 要有明确的数据所有权

谁可以修改 Buff？

谁可以修改装备？

如果任何模块都能够绕开接口直接修改底层字段，增量计算机制就可能完全不知道数据已经改变。

因此数据写入边界很重要。

2. 要明确依赖关系

如果最终攻击力依赖装备和 Buff，那么依赖跟踪机制必须知道这一点。

一旦遗漏依赖，结果就可能过期。

如果依赖关系动态变化，系统还需要更新依赖图，而不只是维护一张固定的表。

3. 要有可靠的更新规则与不变量

以缓存的攻击力为例：

¬dirty ⇒ cachedAttack = CalculateAttack(sourceState)

意思是：

当我们宣称缓存有效时，它必须等于依据当前权威源状态重新计算的结果。

而背包重量的增量实现要求：

TotalWeight = Σᵢ Countᵢ × UnitWeightᵢ

这些就是系统能够正确运行的核心约束。

工程上还要考虑更新事件是否重复、是否乱序、变化是否发生在多个线程、多个变更是否应该合并处理，以及是否存在循环依赖。

例如，Unity 中使用对象池复用 UI 时，还要避免上一任数据对象的事件订阅留在复用后的 UI 对象上，否则失效通知可能作用于错误的逻辑对象。

十、实际工程中如何选择？

不要因为记忆化或增量计算看起来更高级，就为所有计算都添加复杂机制。

可以按照下面的决策方式选择：

选择哪种优化策略？

相同输入反复出现，单次计算代价高
优先考虑记忆化，复用相同输入的历史答案。
大型数据集合频繁发生小范围修改
优先考虑差量更新，并保留必要的中间状态。
多个派生数据相互依赖，局部变化影响部分节点
考虑依赖追踪、脏标记与选择性重算。
计算非常便宜，或者几乎不重复
直接计算通常更简单，也可能更快。

对于 Unity 游戏开发，我尤其建议在使用这些技术时坚持三个原则：

  • 先证明计算是性能热点，而不是看到一个计算函数就想缓存它。
  • 先确定正确性不变量，再设计优化策略，否则很容易出现旧数据。
  • 对复杂增量计算定期验证，在测试中使用全量重算结果作为正确性基准，特别是在浮点误差、批量修改和异步更新场景中。

十一、最终总结：直击两个概念的本质

我们再回到最基础的数学表达式。

正常计算：

y = f(x)

Memoization：

相同输入 ⇒ 复用历史结果

Incremental Computation：

输入变化 ⇒ 复用旧成果并更新受影响部分

它们都是在利用一个事实：

新的计算请求，并不一定意味着必须重新完成之前已经做过的所有工作。

记忆化利用的是子问题的重复性。

增量计算利用的是输入变化的局部性，以及计算依赖的结构性。

而缓存、版本号、所有权、不变量、依赖图、事件、状态管理等技术，则是在帮助我们回答：

哪些结果可以复用？为什么它们仍然正确？什么时候必须更新？由谁负责维护？

如果你希望继续深入，我建议按照以下顺序学习：

  1. Dependency Graph（依赖图）与 Dirty Flag（脏标记）：计算结果如何知道自己的依赖已经变化？
  2. Reactive Programming（响应式编程）：如何把数据变化与下游更新组织成一个自动传播系统？
  3. Incremental View Maintenance（增量视图维护）：数据库为什么能在数据变化后高效维护聚合结果？
  4. Dynamic Programming（动态规划）与 Memoization：记忆化为什么常被用来解决具有重叠子问题的计算？

其中，我最建议你下一步深入的是 Dependency Graph + Dirty Flag + Versioning。

因为这三个概念结合起来，能够建立一套非常清晰的 Unity 属性系统、UI 派生状态系统乃至复杂游戏数据更新架构。

要理解这三个概念，最重要的是先区分：

架构是你实际做出的设计，模式是从实践中总结出来、可重复使用的设计经验。

架构模式和设计模式都属于“模式”，只是通常解决的问题范围不同。

我们按照 What（是什么）→ Why（为什么）→ How（如何实现），从本质逐层推导。

01架构（Architecture）

1. What：架构是什么？

架构是一个系统的重要组织结构，以及决定这个结构如何运行、如何演化的设计决策。

它主要涉及三个要素：

要素 含义 游戏开发示例
组成部分 系统由哪些重要部分构成 客户端、服务器、数据库
关系 这些部分如何协作 客户端向服务器发送请求
约束 哪些关系或行为必须遵守规则 客户端不能直接修改服务器数据库

但要注意，架构不仅是画出几个方框和箭头。

例如，“玩家的重要数据必须由服务器决定，不能由客户端自行决定”，虽然不一定表现为一个具体模块，却是一个重要的架构决策。

所以架构也包含重要原则、边界及约束。

2. Why：为什么需要架构？

因为一个复杂系统不是一个孤立的函数。

假设你要开发一款联网游戏。

你必须回答：

谁负责决定玩家拥有哪些道具？

谁负责保存数据？

客户端与服务器如何通信？

服务器发生故障时如何避免数据损坏？

这些问题无法仅靠把某个函数写正确来解决，因为它们涉及不同组成部分之间的协作关系。

架构的根本目的就是：

通过组织系统的组成部分及其关系，在给定约束下满足系统的重要需求，并控制复杂性及未来变更的成本。

其中的重要需求可能包括性能、可靠性、安全性、扩展性和可维护性。

3. How：如何设计架构？

例如，我们决定让服务器管理玩家的重要数据。

这个设计包含：

组成部分：Unity 客户端、游戏服务器、数据库。

关系：客户端通过网络调用服务器，服务器访问数据库。

约束：客户端不能绕过服务器直接修改权威的玩家数据。

这就是一种具体架构的组成部分。

但是，架构并不是一定要分成这三个部分。单机游戏可能直接由本地逻辑维护状态，并保存到本地文件。

这两种设计都是架构，只是满足的需求与约束不同。

02架构模式（Architectural Pattern）

1. What：架构模式是什么？

既然架构需要决定如何组织系统，那么一个自然的问题就是：

难道每次开发软件，都必须从零开始思考全部结构吗？

当然不需要。

人们发现，不同的软件系统经常会遇到相似的结构性问题，并且某些组织方式能够反复解决这些问题。

于是将这些成功经验抽象出来，形成了架构模式。

架构模式是针对反复出现的系统级结构问题，总结出的可重复使用的组织方案。

它通常描述：

  • 应该有哪些主要职责或组成部分。
  • 这些部分如何协作。
  • 应该遵循哪些依赖规则。
  • 这种组织方式有哪些优点、局限和适用条件。

架构模式不是完整的软件架构，而是帮助你设计架构的通用方案。

2. Why：为什么需要架构模式？

因为不同软件可能面临相同类型的问题。

例如，几乎任何带有持久化数据和用户界面的业务应用，都需要处理：

界面逻辑、业务规则、数据读写之间的关系。

你可以每次都重新设计，也可以参考已经成熟的组织方法。

架构模式的价值在于复用经过实践的设计思路，降低设计复杂度，并使架构的权衡更容易被讨论。

但它不意味着一定正确。采用某种模式，也会引入自身的约束和成本。

3. How：如何应用架构模式？

例如，我们发现 UI、业务逻辑、数据库操作混合在一起。

可以采用一种常见的架构模式：分层架构（Layered Architecture）。

它提供一种组织思路：让不同职责的代码分层协作，避免任意混合。

但具体有多少层、能否跨层调用、依赖方向如何规定，仍然需要结合需求决定。上图只是其中一种简单结构。

其他常见的架构模式还包括：

架构模式 主要组织思路
MVC 分离 Model、View、Controller 的职责
分层架构 按职责组织层及其依赖关系
事件驱动架构 使用事件组织组件之间的协作
微服务架构 将系统划分为能够独立部署的服务

这些模式甚至可以组合使用，并不一定互斥。

03设计模式（Design Pattern）

1. What：设计模式是什么？

你现在已经设计好了系统的大体结构。

但在实现内部功能时，还是会遇到很多问题。

例如：

你的游戏有很多种道具效果。

治疗道具恢复生命值，魔法道具恢复魔法值，其他道具还可能提供特殊能力。

你希望添加新效果时，不需要反复修改一个包含大量 switch 的函数。

这是一个相对局部的对象职责与协作设计问题。

人们也将这些反复出现的设计问题及其解决方法抽象出来，形成设计模式。

设计模式是针对反复出现的软件设计问题，总结出的可重复使用的解决方案。

在面向对象编程中，设计模式经常描述类、对象、接口及其协作关系。

例如策略模式、观察者模式、工厂方法模式等。

2. Why：为什么需要设计模式？

同样是为了复用设计经验，但通常处理的是更局部的问题。

例如，在不同的业务中，你都可能需要：

根据条件替换算法、在状态发生变化时通知其他对象、创建不同类型的对象。

这些需求虽然出现在不同的程序里，但背后的结构性问题可能相同。

设计模式让你可以复用解决思路，而不是每次重新发明。

另外，它也提供了一套共同语言。

当你说“这里采用策略模式”时，熟悉该模式的开发者就可以快速理解你想要表达的对象协作关系。

3. How：如何使用设计模式？

以 Unity C# 为例，使用**策略模式（Strategy Pattern）**组织不同的奖励计算规则。

假设有普通奖励和双倍奖励。

先定义一个可替换的规则接口：

IRewardStrategy.csC# · 完整类型定义
public interface IRewardStrategy
{
    int Calculate(int baseReward);
}

普通奖励：

NormalReward.csC# · 完整类型定义
public class NormalReward : IRewardStrategy
{
    public int Calculate(int baseReward)
    {
        return baseReward;
    }
}

双倍奖励：

DoubleReward.csC# · 完整类型定义
public class DoubleReward : IRewardStrategy
{
    public int Calculate(int baseReward)
    {
        return checked(baseReward * 2);
    }
}

计算器不需要知道具体是哪一种规则：

RewardCalculator.csC# · 完整类型定义
public class RewardCalculator
{
    private readonly IRewardStrategy strategy;

    public RewardCalculator(IRewardStrategy strategy)
    {
        this.strategy = strategy;
    }

    public int Calculate(int baseReward)
    {
        return strategy.Calculate(baseReward);
    }
}

在 Unity 中可以这样调用：

Game.csC# · 完整类型定义
using UnityEngine;

public class Game : MonoBehaviour
{
    void Start()
    {
        var calculator = new RewardCalculator(
            new DoubleReward()
        );

        int reward = calculator.Calculate(100);

        Debug.Log(reward); // 200
    }
}

这里的关键不是接口或类的数量。

而是：

让变化的计算规则成为可替换的对象，使调用方不必依赖某个具体规则的实现。

这就是策略模式的主要思想。

策略模式 · 离线示意

替换计算规则，调用方式保持一致

演示限定输入为非负的 Int32 整数；原 C# 计算规则没有额外规定负数奖励是否合法。双倍计算遵循 checked 的溢出边界；此处只演示计算，不发放道具或写入玩家数据。

五个完整类型可分别保存为对应文件。IRewardStrategy、两种奖励规则和 RewardCalculator 是普通 C# 类型，Game 继承 MonoBehaviour。装配入口选择具体策略，计算器通过接口使用策略；不依赖具体规则，不等于系统中没有任何地方需要选择具体实现。

当然，如果只是一个简单的倍率参数，直接用配置数据往往更简单，不一定有必要引入策略模式。

04三者到底有什么关系？

现在把三者放在同一个软件中理解。

图中的嵌套表示一个具体设计可以组合不同范围的模式，不表示所有设计模式都必须位于某个架构模式内部。

对比维度 架构 架构模式 设计模式
是什么 具体系统的重要设计 通用的系统结构方案 通用的设计问题解决方案
关注点 系统如何构成与演化 主要职责如何组织 组件或对象如何协作
抽象程度 取决于所讨论的系统 通常较高 通常较局部
是否可复用 具体架构可以借鉴 可以 可以
例子 某款游戏的实际系统架构 MVC、分层架构 策略、观察者

这里还有一个很重要的细节：

架构模式和设计模式之间没有绝对清晰的分界线。

“设计模式”也可以作为一个广义术语，涵盖架构模式。因此 MVC 有时被称为设计模式，有时被称为架构模式。

而且一个模式究竟属于架构层次还是局部设计层次，也与应用的系统范围有关。

05How：真正设计软件时，应该先做什么？

理解完概念后，更重要的是知道实际设计的顺序。

  1. 先识别需求和约束。

    软件要实现什么功能？必须保证哪些正确性、性能与可靠性要求？有哪些开发成本限制？

  2. 识别职责与边界。

    什么部分负责什么？哪些数据属于谁？什么行为应该由谁决定？

  3. 设计重要的关系和规则。

    各部分如何通信？如何依赖？数据如何流动？发生故障如何处理？这一步会逐步形成架构。

  4. 寻找合适的架构模式。

    如果遇到一个反复出现的系统结构问题，可以考虑分层架构、MVC、事件驱动等成熟方案。

  5. 在具体实现中使用适当的设计模式。

    当某些局部设计问题持续出现时，再考虑策略、观察者等模式，并通过测试和实际需求验证效果。

这不是严格的一次性瀑布流程。实际开发中经常会反复调整前面的决策。

06最终，直击本质

你可以把三个概念压缩为三个问题：

架构：这个具体系统应该如何组织，为什么这样组织？

架构模式：面对这类系统结构问题，有什么成熟的组织思路可供参考？

设计模式：面对这类反复出现的设计问题，有什么成熟的解决思路可供参考？

因此：

架构是具体的设计结果，而模式是可复用的设计知识。架构模式通常关注较大范围的结构组织，设计模式通常关注较局部的职责与协作。

还有一个值得深入的概念：抽象（Abstraction）。

为什么我们可以把不同软件的共同问题总结为一种“模式”？为什么一个接口可以代表多种实现？为什么架构图可以省略大量代码细节？

这些问题背后都涉及抽象。理解抽象之后，你对架构、模式、接口和软件设计的认识就能进一步连起来。

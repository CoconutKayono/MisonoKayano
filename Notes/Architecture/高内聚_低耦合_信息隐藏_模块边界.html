软件设计的四个基础。

高内聚、低耦合、信息隐藏与模块边界。

四个视角，共同回答一个问题：
如何让复杂性被局部管理，让变化尽可能被局部吸收？

组织内部职责共同维护什么状态和规则
控制依赖知识外界真正需要了解什么
落实所有权与契约谁有权修改，允许怎样协作

六张图直接嵌入 HTML，可离线显示并单独下载 SVG；手机上可横向滚动大图。代码保留原文内容，独立示例不应直接拼成一个工程。

这四个概念是理解软件架构非常重要的基础。

无论你学习的是 MVC、DDD、Clean Architecture、Modular Monolith，还是微服务，最终都会遇到它们。

但它们不是四条彼此独立的原则，而是在解决一个共同的问题：

一个复杂的软件系统，应该如何划分内部结构、组织依赖关系，使局部变化不会轻易破坏整个系统？

我们先用四句话抓住本质。

概念 本质问题 核心思想
Cohesion（内聚） 哪些东西应该放在一起？ 把因同一职责而需要共同维护的东西聚集起来
Coupling（耦合） 不同部分应该如何依赖？ 减少不必要的依赖，控制必要依赖的范围
Information Hiding（信息隐藏） 哪些内部知识不应该暴露？ 隐藏可能变化的设计决策，避免外部依赖它们
Module Boundary（模块边界） 如何规定不同部分的内外关系？ 明确所有权、公开契约与允许的交互方式

先看一张关系图。

这张图表示一种常见的设计思路，而不是四个概念必然发生的先后顺序。

01Cohesion：内聚

1. What：什么是内聚？

Cohesion 描述的是：

一个软件单元内部的各个组成部分，彼此有多大程度上属于同一个职责或目的。

软件单元可以是：

  • 一个函数
  • 一个类
  • 一个模块
  • 一个子系统

假设我们有一个 C# 类：

C# 示例 01 · PlayerManagerC# · 示意片段，需置于相应上下文
public class PlayerManager
{
    public void AddItem() { }

    public void RemoveItem() { }

    public void SendEmail() { }

    public void SaveGraphicsSettings() { }

    public void CalculateBattleDamage() { }
}

这些方法都和玩家有关系吗？

从很宽泛的意义上说，是的。

但这不意味着它们具有高内聚。

因为：

  • 道具变化属于背包职责。
  • 邮件发送属于邮件职责。
  • 画面设置属于配置职责。
  • 伤害计算属于战斗职责。

它们的业务目的、变化原因和维护规则都不相同。

把这些功能放在同一个类里，只是物理上的集中，并不是高内聚。

高内聚是什么样的？

C# 示例 02 · InventoryC# · 示意片段，需置于相应上下文
public class Inventory
{
    public void AddItem() { }

    public void RemoveItem() { }

    public bool HasItem() => true;

    public bool HasCapacity() => true;
}

这些方法都围绕一个明确的职责：

维护背包状态，并保证背包的业务规则。

因此，它们之间具有更强的内聚性。

关键不是方法数量少，而是它们存在共同的业务目的。

2. Why：为什么追求高内聚？

因为软件会发生变化。

假设现在修改背包规则：

原来道具没有数量上限。

现在需要限制每种道具最多持有 99 个。

如果背包规则散落在：

Shop
Battle
Quest
Mail
Inventory

那么修改这条规则时，就可能需要检查多个地方。

但如果背包规则集中在 Inventory 中：

Inventory
    AddItem()
    RemoveItem()
    HasCapacity()
    ValidateStackLimit()

那么通常只需要修改这个模块。

因此，高内聚的重要收益是：

让同一类业务变化所涉及的逻辑，尽可能集中在一个可维护的范围内。

这还能帮助开发者理解代码，因为一个模块的目的更加明确。

3. How：如何实现高内聚？

最有效的方法不是根据函数名称分组，而是寻找它们共同维护的职责、状态和规则。

例如：

C# 示例 03 · InventoryC# · 示意片段，需置于相应上下文
public sealed class Inventory
{
    private readonly Dictionary<int, int> _items = new();

    public int GetCount(int itemId)
    {
        return _items.GetValueOrDefault(itemId);
    }

    public void Add(int itemId, int amount)
    {
        if (amount <= 0)
            throw new ArgumentOutOfRangeException(nameof(amount));

        int current = GetCount(itemId);

        if (amount > 99 - current)
            throw new InvalidOperationException(
                "Stack limit exceeded.");

        _items[itemId] = current + amount;
    }

    public void Remove(int itemId, int amount)
    {
        if (amount <= 0 || GetCount(itemId) < amount)
            throw new InvalidOperationException(
                "Insufficient items.");

        _items[itemId] -= amount;
    }
}

这个类中的方法之间具有重要联系：

它们共同维护 _items，并且共同保证背包数量的合法性。

这里的内聚不仅来自它们操作同一个集合，更来自它们共同维护同一组业务规则。

内聚最容易产生的误解

高内聚不等于所有相关代码必须放在同一个类里。

例如：

InventoryModule
    Inventory
    InventoryService
    InventoryRepository
    InventoryValidator

这些类仍然可以共同组成一个高内聚的模块。

另外，同一份数据也可能参与不同职责。是否属于同一个模块，还需要结合业务规则和变化原因判断。

判断内聚性时，我建议问：

“如果这个业务职责发生变化，哪些代码通常需要一起理解和修改？”

这些代码往往有理由被组织在相近的边界内。

02Coupling：耦合

1. What：什么是耦合？

Coupling 描述的是：

两个软件单元之间存在多大程度的依赖，以及一个单元需要了解另一个单元的多少知识。

注意：

耦合不是单纯地指“A 调用了 B”。

调用是一种依赖关系，但耦合还可能来自：

  • 共享数据结构。
  • 共享可变状态。
  • 对具体实现的依赖。
  • 调用顺序的要求。
  • 对业务规则的共同假设。
  • 对数据库表结构的依赖。

来看一个例子。

C# 示例 04 · ShopServiceC# · 示意片段，需置于相应上下文
public class ShopService
{
    public void Buy(Player player, int itemId)
    {
        player.Inventory.Items[itemId] += 1;
    }
}

这里 ShopService 需要了解：

  1. Player 拥有一个 Inventory。
  2. Inventory 拥有一个 Items。
  3. Items 能通过 itemId 访问。
  4. 字典中的数值代表数量。
  5. 直接增加数量是合法的。

商店不仅依赖背包提供的能力，还依赖背包内部的具体结构与规则。

这就是比较强的实现耦合。

换一种方式：

C# 示例 05 · ShopServiceC# · 示意片段，需置于相应上下文
public class ShopService
{
    private readonly IInventoryService _inventory;

    public ShopService(IInventoryService inventory)
    {
        _inventory = inventory;
    }

    public void Buy(Guid playerId, int itemId)
    {
        _inventory.AddItem(playerId, itemId, 1);
    }
}

现在商店只需要了解公开契约：

C# 示例 06 · IInventoryServiceC# · 示意片段，需置于相应上下文
public interface IInventoryService
{
    void AddItem(Guid playerId, int itemId, int amount);
}

它不再需要知道背包使用字典、数组还是数据库。

耦合依然存在，但依赖的内容减少了。

2. Why：为什么追求低耦合？

因为依赖可能导致变化传播。

假设背包数据结构从：

C# 示例 07 · 类型、调用或表达式示意C# · 示意片段，需置于相应上下文
Dictionary<int, int>

改为：

C# 示例 08 · 类型、调用或表达式示意C# · 示意片段，需置于相应上下文
List<ItemStack>

如果商店直接访问字典：

C# 示例 09 · 类型、调用或表达式示意C# · 示意片段，需置于相应上下文
player.Inventory.Items[itemId] += 1;

商店代码可能需要修改。

但如果它只调用：

C# 示例 10 · 类型、调用或表达式示意C# · 示意片段，需置于相应上下文
_inventory.AddItem(playerId, itemId, 1);

只要公开接口和语义不变，商店就不必知道背包内部发生了什么变化。

所以低耦合的一个主要目的就是：

减少其他模块内部设计决策对当前模块造成的影响。

还有一个重要收益是测试。

如果 Shop 只依赖一个接口，那么测试 Shop 的购买流程时，可以提供一个测试替身，而不必真的启动完整背包数据库。

3. How：如何降低耦合？

常见的方法包括：

第一，依赖稳定的抽象，而不是不稳定的实现细节。

C# 示例 11 · 类型、调用或表达式示意C# · 示意片段，需置于相应上下文
// 依赖具体内部结构
inventory.Items[itemId] += amount;

// 依赖业务能力
inventory.AddItem(itemId, amount);

第二，尽量让依赖方向明确。

例如：

Shop
  ↓
Inventory.Contracts
  ↑
Inventory.Implementation

Shop 和背包实现都围绕公开契约协作。

这体现了依赖倒置思想。

第三，避免跨模块共享可变状态。

如果商店持有背包内部可变集合的引用，即使没有直接调用背包方法，也可能破坏背包的状态规则。

第四，减少不必要的知识。

例如商店只需要知道道具是否发放成功，不一定需要知道背包表的列名、堆叠算法、序列化方式。

一个非常重要的区别：低耦合不是零耦合

假设购买一件商品，必然需要增加背包道具。

那么商店和背包之间存在真实的业务关系。

你不可能通过某种架构，让这层业务关系凭空消失。

即使改成事件：

C# 示例 12 · 类型、调用或表达式示意C# · 示意片段，需置于相应上下文
eventBus.Publish(new ItemPurchased(...));

订阅者仍然需要理解 ItemPurchased 的业务含义。

也就是说：

把方法调用改成事件，并不意味着依赖消失，只是依赖的形式发生了变化。

所以，低耦合真正追求的是：

保留必要的协作关系，去掉不必要的实现依赖。

03Information Hiding：信息隐藏

这是四个概念中最容易被低估的一个。

因为很多人认为：

Information Hiding 就是把字段设置成 private，不让外界访问。

这只理解了很小的一部分。

1. What：什么是信息隐藏？

信息隐藏的核心是：

把某个模块内部的设计决策隐藏起来，让其他模块不必知道，也不必依赖这些决策。

这里真正关键的词是：

设计决策（Design Decision）。

例如背包系统，需要决定：

  • 使用 Dictionary 还是 List 存储？
  • 相同道具是否堆叠？
  • 最大堆叠数量如何检查？
  • 使用什么数据库？
  • 如何缓存玩家背包？
  • 背包数据如何序列化？

这些都是内部设计决策。

其他模块是否真的需要知道？

通常不需要。

商店真正关心的可能只是：

C# 示例 13 · 类型、调用或表达式示意C# · 示意片段，需置于相应上下文
inventory.GrantItem(playerId, itemId, amount);

而不是背包究竟如何实现道具发放。

因此，我们希望隐藏的是：

那些外界没有必要知道、而且将来可能改变的知识。

2. Why：为什么需要信息隐藏？

假设背包原来使用：

C# 示例 14 · 类型、调用或表达式示意C# · 示意片段，需置于相应上下文
public Dictionary<int, int> Items;

外部可以这样修改：

C# 示例 15 · 类型、调用或表达式示意C# · 示意片段，需置于相应上下文
player.Inventory.Items[1001] += 5;

某天你增加了新规则：

道具最大堆叠数量：99

你会遇到一个问题：

外部代码可以直接修改字典，从而绕过堆叠规则。

这意味着背包已经无法独立保证自身的数据正确性。

我们改成：

C# 示例 16 · InventoryC# · 示意片段，需置于相应上下文
public sealed class Inventory
{
    private readonly Dictionary<int, int> _items = new();

    public void AddItem(int itemId, int amount)
    {
        // 在这里检查合法性
    }
}

现在外部不能绕开 AddItem 随意修改 _items。

这带来两个好处：

  1. 外部不需要了解背包的存储方式。
  2. 背包可以控制状态变化必须遵守的规则。

第二点尤其重要。

信息隐藏不只是为了方便修改代码，也可以帮助系统维持状态不变量（Invariant）。

例如：

0 ≤ ItemCount ≤ 99

只要所有合法修改都经过受控入口，背包就可以更容易保证这个约束。

当然，这还需要考虑并发以及持久化层是否允许其他代码绕过入口。

3. How：如何实现信息隐藏？

最基本的方法是区分：

  • 对外公开的业务能力。
  • 仅内部使用的状态和实现。

例如：

C# 示例 17 · IInventoryServiceC# · 示意片段，需置于相应上下文
public interface IInventoryService
{
    void AddItem(int itemId, int amount);

    int GetItemCount(int itemId);
}

具体实现：

C# 示例 18 · InventoryServiceC# · 示意片段，需置于相应上下文
internal sealed class InventoryService : IInventoryService
{
    private readonly Dictionary<int, int> _items = new();

    public void AddItem(int itemId, int amount)
    {
        // 校验并修改内部状态
    }

    public int GetItemCount(int itemId)
    {
        return _items.GetValueOrDefault(itemId);
    }
}

外部只知道它提供什么能力。

内部可以自由改变数据结构，只要公开契约保持不变。

信息隐藏 ≠ private

假设我们写：

C# 示例 19 · InventoryC# · 示意片段，需置于相应上下文
public class Inventory
{
    private Dictionary<int, int> _items = new();

    public Dictionary<int, int> GetItems()
    {
        return _items;
    }
}

虽然 _items 是 private，但 GetItems() 把内部可变字典直接返回了。

外部仍然可以：

C# 示例 20 · 类型、调用或表达式示意C# · 示意片段，需置于相应上下文
inventory.GetItems()[1001] = -999;

这实际上破坏了信息隐藏。

再考虑：

public IReadOnlyDictionary<int, int> GetItems()

这样可以减少外部通过该接口直接修改数据的能力，但如果它返回的是底层字典的只读视图，外部仍然会观察到内部集合的实时变化；它也未必隐藏了使用字典表示物品的设计决策。只读接口也不自动保证对象不可变，或阻止调用者拿到原对象后通过具体类型恢复修改能力。

如果外部只需要查询某件道具的数量，以下接口可能更合适：

C# 示例 21 · 类型、调用或表达式示意C# · 示意片段，需置于相应上下文
public int GetItemCount(int itemId);

如果需要整个背包快照，可以返回不可变的数据传输对象，或一份独立的只读快照，并检查快照中的元素是否仍然可变。

信息隐藏的判断标准不是有没有 private，而是：

外部是否被迫了解、依赖甚至操纵你的内部实现？

04Module Boundary：模块边界

现在我们已经理解：

  • 内聚：哪些东西应该放在一起。
  • 耦合：不同部分之间如何依赖。
  • 信息隐藏：哪些知识不应该暴露。

接下来就需要一种方式将它们组织起来。

这就是模块边界。

1. What：什么是模块边界？

Module Boundary 是区分一个模块内部与外部的设计约束。

它规定：

什么属于这个模块，外界能看到什么，以及外界通过什么方式与它合作。

一个模块边界通常包含以下内容：

维度 要回答的问题
职责边界 哪些业务行为由这个模块负责？
数据边界 哪些数据由这个模块拥有和维护？
接口边界 外部通过哪些接口进行操作？
依赖边界 哪些模块允许依赖哪些模块？
一致性边界 哪些操作必须共同成功或失败？

注意，前四项可以较直接地规定模块的职责与访问限制。

而事务的一致性边界不一定与模块边界重合；一个事务完全可能涉及多个模块。

2. Why：为什么要有模块边界？

假设我们有三个系统：

Shop
Inventory
Statistics

没有明确边界时，可能发生：

C# 示例 22 · 类型、调用或表达式示意C# · 示意片段，需置于相应上下文
shop.InventoryData.Items[1001] += 1;

shop.StatisticsData.TotalObtained += 1;

这产生一个问题：

谁对数据正确性负责？

如果所有模块都能够修改任何数据，那么即使发生了错误，也很难知道哪些代码有权维护这些规则。

模块边界引入了一个非常重要的概念：

所有权（Ownership）。

例如：

  • Inventory 拥有当前道具数量的维护权。
  • Statistics 拥有累计统计数据的维护权。
  • Shop 拥有商品定价和购买规则的维护权。

拥有数据不等于其他模块不能读取它。

而是其他模块不应该随意绕过所有者来修改其数据和业务规则。

3. How：如何建立模块边界？

先从逻辑边界开始。

在 Unity/C# 中可以采用两个或更多程序集：

Game.Inventory.Contracts
    IInventoryService.cs
    InventorySnapshot.cs

Game.Inventory.Runtime
    InventoryService.cs
    InventoryRepository.cs
    Inventory.cs

Game.Shop.Runtime
    ShopService.cs

建立依赖：

Game.Shop.Runtime
        ↓
Game.Inventory.Contracts
        ↑
Game.Inventory.Runtime

在 Unity 里，可以使用 Assembly Definition（.asmdef）控制程序集引用关系。

在标准 .NET 中，可以通过 .csproj 项目引用控制依赖关系。

并且：

  • 使用 public 暴露对外契约。
  • 使用 internal 限制实现类型在程序集外的可见性。
  • 不暴露可随意修改的内部数据结构。
  • 通过架构测试防止模块出现未经允许的依赖。

但请特别注意：

程序集边界是一种实现和维护模块边界的手段，不等于模块边界本身。

即使拆成十个 DLL，如果大家仍然共享同一个可变的 PlayerData 并任意修改，业务边界仍然很弱。

反过来，即使只有一个程序集，也可以在逻辑上维持清晰的模块边界，只是编译器能提供的保护更少。同一程序集内的 internal 不会自动隔离不同模块；Host／组合根仍需要在允许的装配位置连接公开契约与具体实现。

05它们之间真正的联系是什么？

现在用你的游戏服务端场景，把这四个概念放到同一个问题中。

假设：

玩家获得五个道具。

业务上需要：

Inventory.CurrentCount += 5

Statistics.TotalObtained += 5

我们先问四个不同的问题。

问题一：这些规则应该属于谁？

这是 Cohesion 的问题。

当前背包数量与背包规则放在一起。

累计获得数量与统计规则放在一起。

这里按职责划分，是因为当前所有量和历史累计量的含义、规则及变化原因可能不同。

问题二：谁可以修改这些数据？

这是 Module Boundary 的问题。

Inventory 拥有 CurrentCount

Statistics 拥有 TotalObtained

Reward 可以请求这两个模块执行相应操作，但不应直接修改它们的内部字段。

问题三：Reward 需要知道多少内部细节？

这是 Information Hiding 的问题。

Reward 不需要知道统计模块如何存储累计数量，也不需要知道背包是否使用 Dictionary。

它只需要公开的业务操作。

问题四：Reward 与两个模块怎样合作？

这是 Coupling 的问题。

它可以依赖两个模块的公开契约，而不依赖内部实现。

例如：

C# 示例 23 · RewardServiceC# · 示意片段，需置于相应上下文
public sealed class RewardService
{
    private readonly IInventoryService _inventory;
    private readonly IStatisticsService _statistics;

    public RewardService(
        IInventoryService inventory,
        IStatisticsService statistics)
    {
        _inventory = inventory;
        _statistics = statistics;
    }

    public void GrantItem(Guid playerId, int itemId, int amount)
    {
        _inventory.AddItem(playerId, itemId, amount);
        _statistics.RecordObtained(playerId, itemId, amount);
    }
}

这个例子展示了模块之间的职责与调用关系。

示例中的 IInventoryService 在前后场景具有不同签名：有的面向单个背包，有的接收 playerId。它们是独立示意，不应拼接成一个接口定义。空方法、固定返回 true 的查询、带省略号的调用也都是占位片段。

不过，以上代码本身并不保证数据原子性。

如果背包更新成功而统计更新失败，仍然可能产生不一致。

若要求两个变更必须同时成功，应该再为整个业务操作提供事务协调，例如使用同一个数据库事务，并处理并发与重试。

这也说明了一个重要事实：

高内聚、低耦合、信息隐藏、模块边界，不能代替事务、幂等和并发控制。

它们解决的是不同的问题，可以相互配合。

06四个概念也可能产生设计上的冲突

架构设计不是把每项指标无限提高就能得到最优解。

例如，我们希望降低模块之间的耦合，于是把一项简单操作拆成多个接口、消息和事件。

原本：

inventory.AddItem(itemId, 5);

却变成：

Command
   ↓
Dispatcher
   ↓
Handler
   ↓
Event
   ↓
EventBus
   ↓
EventHandler
   ↓
Inventory

对于某些复杂场景，这种结构可能合理。

但对于一个简单项目，它也可能引入不必要的间接层和认知成本。

甚至由于流程分散，还可能损害理解整个业务操作时的内聚性。

因此，实际设计应该追求平衡。

追求 过度追求可能造成的问题
高内聚 把过多职责理解成一个大职责，形成巨型模块
低耦合 引入大量不必要的抽象与间接层
信息隐藏 隐藏过多必要能力，使外部很难正确使用模块
严格边界 产生大量跨模块协调与重复模型维护成本

最好的架构并不是接口最多、模块最独立的架构，而是以适当复杂度管理真实业务变化的架构。

07如何判断你设计得好不好？

我建议你养成一种思考习惯：

不要只问“代码应该放在哪里”，而是问“为什么这些代码应该放在一起，为什么那些代码不能随意访问它们”。

01 / COHESION

这些代码是否共同维护一个清楚的职责？

寻找共同的目的、规则和变化原因。

02 / COUPLING

另一个模块更换内部实现，我是否必须跟着修改？

检查自己依赖的是公开能力，还是内部细节。

03 / INFORMATION HIDING

外界是否知道了没有必要知道的设计决策？

特别检查可变集合、具体数据结构和实现类型。

04 / MODULE BOUNDARY

谁有权修改这些数据，谁有权决定这些规则？

检查所有权、公开契约与依赖方向。

08最终总结：直达本质

我们可以把这四个概念归结为软件设计中的四个基本问题。

  1. 高内聚：组织内部

让共同维护一项职责的状态和行为尽可能集中。

  1. 低耦合：控制关系

让不同部分只建立必要的依赖，避免依赖不需要了解的细节。

  1. 信息隐藏：隔离知识

让内部设计决策保留在内部，使外部不必因为这些决策变化而修改。

  1. 模块边界：建立约束

明确每个模块负责什么、拥有哪部分状态，以及如何对外提供能力。

它们最终都指向一个共同目标：

让软件的复杂性被局部管理，让软件的变化尽可能被局部吸收。

还有一个很值得记住的区分：

内聚关注一个单元的内部关系，耦合关注不同单元之间的关系，信息隐藏关注外部能依赖哪些知识，模块边界则规定并落实这些关系与知识的界限。

理解这四点之后，再去学习 DDD 的限界上下文、Clean Architecture 的依赖规则、微服务的服务边界，就会容易得多。因为你会发现，它们都在不同层次上回答同一个问题：

如何划分一个系统，以及如何控制划分之后各部分之间的关系？

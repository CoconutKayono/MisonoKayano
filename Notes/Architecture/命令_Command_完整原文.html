命令（Command）

What、Why、How——从本质理解命令及其架构价值

原文排版Unity / C#游戏服务端十五章完整原文

命令（Command）：What、Why、How——从本质理解命令及其架构价值

命令（Command）是软件设计中一个非常基础，却又非常重要的概念。

它不仅出现在 GoF 的 命令模式（Command Pattern） 中，还广泛存在于：

  • 游戏输入系统（Input System）
  • 状态机（State Machine）
  • 事件驱动架构（Event-Driven Architecture）
  • CQRS（命令查询职责分离）
  • 游戏服务端的业务处理
  • 操作队列、撤销与重做（Undo/Redo）
  • 分布式系统中的消息处理

这些技术表面上不同，但它们经常使用同一种思想：

将“希望系统执行什么操作”表达为一个独立的对象或消息，再由负责执行的组件决定如何处理。

先给出一个核心结论：

命令的本质，是对执行意图的显式表达。

它描述的是“我希望系统做什么”，而不是“系统已经发生了什么”，也不必描述“系统内部具体怎样做”。

例如：

TEXT
玩家点击购买按钮

命令：
PurchaseItem(PlayerId, ItemId, Quantity)

含义：
请求系统为指定玩家购买指定数量的道具。

但命令并不意味着购买已经成功。

这看似只不过把一次方法调用封装成对象，但其真正价值，在于建立一条清晰的边界：

提出意图的一方，与负责执行、验证和修改状态的一方，可以彼此分离。

一、What：命令究竟是什么？

1.1 从最原始的程序执行方式理解

假设我们开发一个 Unity 游戏。

玩家点击按钮后，角色跳跃：

C#
public class PlayerController : MonoBehaviour
{
    public Rigidbody rb;

    public void OnJumpButtonClicked()
    {
        rb.AddForce(Vector3.up * 5, ForceMode.Impulse);
    }
}

这里发生了什么？

TEXT
用户输入
   ↓
调用方法
   ↓
直接执行跳跃

这是非常正常的程序设计，并没有错误。

但是，请思考一个问题：

“玩家想跳跃”和“角色实际执行跳跃”是不是同一件事情？

显然不是。

玩家按下跳跃键，只能说明：

TEXT
玩家希望角色跳跃。

角色能否跳跃，可能取决于：

TEXT
是否处于地面？
是否正在眩晕？
是否允许二段跳？
是否处于过场动画？
是否还有体力？

因此，我们可以把整个过程拆分：

TEXT
玩家按下跳跃键
        ↓
产生跳跃意图
        ↓
检查角色是否允许跳跃
        ↓
执行跳跃
        ↓
角色状态发生变化

其中：

TEXT
产生跳跃意图

就可以用一个 Command 表示。

例如：

C#
public readonly record struct JumpCommand(int PlayerId);

这个命令没有执行任何操作。

它只是一个数据对象。

它表达：

某个玩家请求执行跳跃操作。

随后，由处理器决定如何执行。

C#
public sealed class JumpCommandHandler
{
    public void Handle(JumpCommand command, Player player)
    {
        if (player.Id != command.PlayerId)
            return;

        if (!player.CanJump)
            return;

        player.Jump();
    }
}

现在，结构变成：

TEXT
Input System
     │
     ▼
JumpCommand
     │
     ▼
JumpCommandHandler
     │
     ├── 检查执行条件
     │
     └── 调用 Player.Jump()
                  │
                  ▼
               状态改变

这引入了一个非常重要的区别：

命令代表请求，而处理器负责决定请求能否被执行。

不过要注意：这只是命令的一种实现方式。命令不一定需要独立的 Handler，也不一定必须是对象。简单的函数调用同样可以表达命令语义。

1.2 命令的抽象定义

我们可以将命令理解成：

Command = (Intent, Target, Parameters, Context)

这些字段不是所有命令都必须具备，而是常见的语义组成部分。

组成部分 含义 例子
Intent 想做什么 PurchaseItem
Target 对谁执行 PlayerId
Parameters 操作参数 ItemId、Quantity
Context 请求上下文（可选） RequestId、操作者、时间

例如：

C#
public sealed record PurchaseItemCommand(
    long PlayerId,
    int ItemId,
    int Quantity,
    string RequestId
);

它表示：

TEXT
希望执行的操作：购买道具
目标：PlayerId 对应的玩家
参数：道具 ID、购买数量
请求标识：RequestId

注意，这里还没有：

  • 检查货币是否足够
  • 扣除货币
  • 添加道具
  • 保存数据

因为这些属于执行命令的业务逻辑，而不是命令消息本身。

命令作为请求消息，可以保持为纯数据；而在 GoF 命令模式中，命令对象往往还具有 Execute() 行为。两种形式都成立，只是所关注的设计问题有所不同。

1.3 命令不等于命令模式

这是必须区分的概念。

Command（命令） 是一种语义：请求系统执行操作。

Command Pattern（命令模式） 是一种具体设计模式：把请求封装为对象，使请求能够被参数化、保存、排队或撤销等。

例如，命令模式的典型结构是：

C#
public interface ICommand
{
    void Execute();
}

public sealed class JumpCommand : ICommand
{
    private readonly Player _player;

    public JumpCommand(Player player)
    {
        _player = player;
    }

    public void Execute()
    {
        _player.Jump();
    }
}

使用：

C#
ICommand command = new JumpCommand(player);

command.Execute();

这里的命令包含了执行行为，并持有执行所需的对象引用。

与前面只有数据的 JumpCommand 不同。

两种实现可以对比：

维度 携带行为的命令对象 纯数据命令消息
核心思想 将操作封装成对象 将执行意图显式表达
执行逻辑 通常在 Execute() 内 通常在 Handler 内
依赖 可能引用具体对象 通常只包含参数和标识
常见场景 Undo/Redo、编辑器、操作队列 游戏服务端、CQRS、跨进程消息
持久化与传输 需要额外处理对象依赖 通常更容易序列化

两者不是互相排斥的技术，也没有哪一种绝对更高级。

例如，一个本地编辑器中的命令完全可以直接持有 Unity 对象引用；而一个跨网络传输的购买命令，通常更适合只携带玩家 ID、道具 ID 和数量。

二、Why：为什么需要命令？它到底解决什么问题？

命令并不是为了让代码看起来更符合设计模式。

它首先解决的是：

如何将操作的发起、表达和执行解耦，使它们能够在不同的位置、不同的时间、不同的机制下协作？

我们从几个真实的软件问题理解。

2.1 问题一：发起者和执行者紧密耦合

没有命令抽象时：

C#
public void OnPurchaseButtonClicked()
{
    if (player.Coins >= 100)
    {
        player.Coins -= 100;
        player.Inventory.Add(item);
        SaveSystem.Save();
    }
}

此时 UI 按钮知道：

TEXT
玩家的货币结构
玩家的背包结构
购买的业务规则
存档系统

问题不仅在于代码长。

更重要的是：

UI 层承担了不属于自己的业务责任。

将来购买操作可能来自：

TEXT
商城按钮
NPC 对话
自动购买功能
网络请求
测试脚本
管理员指令

如果每个入口都自己实现购买逻辑，就容易出现：

TEXT
商城按钮：
检查余额 → 扣钱 → 加道具

NPC：
检查余额 → 扣钱 → 加道具

自动购买：
检查余额 → 扣钱 → 加道具

一旦购买规则发生变化，每个入口可能都需要修改。

而引入统一的命令处理边界后：

TEXT
商城 UI ────┐
            │
NPC 对话 ───┤
            ▼
       PurchaseItemCommand
            │
测试脚本 ───┤
            │
网络请求 ───┘
            ▼
       PurchaseItemHandler
            │
            ▼
          购买规则
            │
            ▼
          修改状态

现在 UI 不需要理解如何购买。

它只负责产生购买请求。

处理器负责协调业务操作，真正的领域规则还可以进一步封装在玩家、订单或购买服务中。

这里最重要的不是创建了一个 PurchaseItemCommand 类，而是：

不同入口共享了同一套业务规则，并且 UI 不再拥有修改业务状态的责任。

2.2 问题二：请求不一定应该立即执行

假设玩家在游戏中连续输入：

TEXT
攻击
攻击
跳跃
闪避

传统调用模式可能是：

C#
player.Attack();
player.Attack();
player.Jump();
player.Dodge();

但是角色可能正在执行攻击动画。

某些输入需要：

  • 延迟执行
  • 缓冲等待
  • 被更高优先级操作替代
  • 在过期后丢弃
  • 按确定的顺序执行

如果输入直接调用行为，输入采集和行为执行就绑定在了一起。

命令允许我们把它们分离：

TEXT
输入采集
    │
    ▼
命令队列
    │
    ├── Attack
    ├── Attack
    ├── Jump
    └── Dodge
    │
    ▼
命令调度器
    │
    ├── 判断当前状态
    ├── 判断是否过期
    ├── 判断执行优先级
    └── 选择执行时机
    │
    ▼
角色行为系统

例如：

C#
Queue<ICommand> commands = new();

commands.Enqueue(new AttackCommand(player));
commands.Enqueue(new JumpCommand(player));

while (commands.Count > 0)
{
    ICommand command = commands.Dequeue();
    command.Execute();
}

上面的例子只是基本队列，真正的输入缓冲通常还需要时间戳、生命周期、优先级以及可执行条件。

但它已经体现了命令的一个重要能力：

请求可以先被保存，然后在合适的时机执行。

需要强调的是，命令只是让延迟执行成为可能，并不会自动解决输入缓冲、优先级或者状态竞争的问题。

2.3 问题三：希望记录、撤销或重放操作

例如游戏内地图编辑器：

TEXT
移动物体
旋转物体
删除物体
创建物体

如果只是直接修改 Transform：

TEXT
transform.position = newPosition;

操作完成后，系统未必知道：

TEXT
之前的位置是什么？
这次执行了什么操作？
怎么撤销？
怎么重做？

但命令可以保存操作所需要的信息。

TEXT
MoveObjectCommand
    │
    ├── Target
    ├── OldPosition
    └── NewPosition

于是：

TEXT
Execute():
    将物体移动到 NewPosition

Undo():
    将物体恢复到 OldPosition

我们就能够实现：

TEXT
执行操作
   ↓
记录命令
   ↓
撤销命令
   ↓
重做命令

这里应该理解一个重点：

撤销并不是命令天然具备的能力。

命令只是让操作拥有了独立的表示。

要支持撤销，还需要保存足够的历史状态，或者设计对应的逆操作。

例如购买游戏道具并涉及外部支付时，往往不能简单地通过“反向执行购买”实现真正的撤销。

2.4 问题四：业务操作缺少统一的执行入口

设想一个游戏服务端：

TEXT
客户端请求购买道具
    ↓
RPC
    ↓
扣除金币
    ↓
增加背包道具
    ↓
保存数据库

如果所有 RPC 都直接修改系统内部状态，可能出现：

TEXT
购买 RPC 直接改背包
奖励 RPC 直接改背包
任务 RPC 直接改背包
邮件 RPC 直接改背包

这并不一定有问题，但是当每种业务操作都涉及自己的权限校验、业务规则、幂等性与事务要求时，系统需要明确责任归属。

例如，购买操作可能必须满足以下不变量：

Coins ≥ 0
Quantity > 0

并且，对于一次成功的购买：

Coinsafter=Coinsbefore-Cost
Inventoryafter=Inventorybefore+Items

希望保证：

TEXT
要么扣钱和发放道具全部成功

要么整个购买操作不生效

命令处理器可以成为协调这些规则的统一入口：

TEXT
PurchaseItemCommand
          │
          ▼
PurchaseItemHandler
          │
          ├── 权限与请求校验
          ├── 检查业务前置条件
          ├── 执行购买领域逻辑
          ├── 持久化状态
          └── 返回执行结果

不过这里需要非常准确地区分：

命令提供的是操作边界，不自动提供事务、一致性或幂等性。

事务要靠数据库等存储机制保证，幂等性需要专门的去重设计，业务不变量仍需要由领域模型维护。

命令抽象的价值，是为这些机制提供一个明确的组织位置。

2.5 问题五：如何统一记录、测试和控制操作？

假设系统存在这些业务操作：

TEXT
PurchaseItem
ClaimReward
EquipWeapon
CompleteQuest
UpgradeSkill

如果它们有统一的命令执行边界，就可以在适当的层次加入：

TEXT
命令处理
    │
    ├── 身份验证与授权
    ├── 日志记录
    ├── 性能监控
    ├── 请求去重
    ├── 错误处理
    └── 执行业务逻辑

例如记录：

TEXT
RequestId: 10001
Command: PurchaseItem
PlayerId: 5001
ItemId: 200
Quantity: 3
Result: Success
Duration: 8ms

当玩家反馈“我购买了道具，但是没有收到物品”时，我们可以通过相关请求标识定位执行情况。

同样，测试也可以绕过 UI：

C#
var command = new PurchaseItemCommand(
    PlayerId: 1001,
    ItemId: 200,
    Quantity: 3,
    RequestId: "request-001"
);

var result = handler.Handle(command);

我们不需要模拟玩家点击 UI 才能测试购买逻辑。

但统一入口也意味着集中承担责任。一个命令总线如果不断加入业务细节，可能逐渐变成难以维护的巨型管理器。

因此，好的设计应该是：

统一执行机制，分散具体业务规则。

2.6 Why 的总结：命令真正解决的是什么？

从根本上说，命令帮助我们将一个操作拆成三个不同的概念：

Intent：意图

请求系统做什么？

Execution：执行

能不能做？什么时候做？怎样做？

Outcome：结果

成功了吗？状态发生了什么变化？

传统的直接方法调用，可能把这三个概念放在同一个位置。

命令则允许我们分别管理它们。

因此：

命令不是为了消除方法调用，而是为了让操作意图成为系统可以识别、传递、存储、调度和治理的独立概念。

这才是它真正的设计价值。

三、How：命令是如何工作的？

3.1 命令的基本执行模型

先建立最基础的模型。

TEXT
Client（发起者）
        │
        │ 创建命令
        ▼
Command（命令）
        │
        │ 发送
        ▼
Handler（处理器）
        │
        │ 校验与执行
        ▼
Domain（领域模型）
        │
        │ 修改业务状态
        ▼
Result（执行结果）

这里有四个核心角色：

角色 责任
Client 产生执行意图
Command 表达要执行的操作及参数
Handler 接收请求、协调执行过程
Domain 维护业务规则和不变量

其中，Handler 并不意味着所有业务逻辑都应该写进 Handler。

例如：

C#
public class PurchaseItemHandler
{
    public PurchaseResult Handle(PurchaseItemCommand command)
    {
        // 查找玩家
        // 查找道具
        // 检查请求是否合法
        // 调用玩家或购买领域服务
        // 保存结果
        // 返回执行结果
    }
}

而真正的规则：

TEXT
购买数量必须大于 0

玩家货币必须足够

背包容量必须允许添加

购买成功后保持业务状态一致

最好由领域模型或领域服务维护。

这使得执行流程和业务规则拥有不同的责任。

3.2 一个完整的 Unity/C# 示例：购买道具

我们从一个简化的单机游戏内购买系统开始，不引入网络、数据库和消息队列。

第一步：定义命令

C#
public readonly record struct PurchaseItemCommand(
    int ItemId,
    int Quantity
);

命令只有两个参数。

不包含：

TEXT
扣除金币的方法
添加道具的方法
保存游戏的方法

因为这些不属于请求本身。

第二步：定义执行结果

C#
public enum PurchaseStatus
{
    Success,
    InvalidQuantity,
    ItemNotFound,
    InsufficientCoins,
    InventoryOverflow
}

public readonly record struct PurchaseResult(
    PurchaseStatus Status
)
{
    public bool Success => Status == PurchaseStatus.Success;
}

为什么需要 Result？

因为：

命令表达的是请求，而不是成功的事实。

我们需要能够区分：

TEXT
请求购买
    │
    ├── 成功
    ├── 金币不足
    ├── 道具不存在
    └── 数量不合法

这些结果都来自同一个命令类型。

第三步：让领域对象维护自身状态

C#
using System.Collections.Generic;

public sealed class PlayerState
{
    private readonly Dictionary<int, int> _inventory = new();

    public int Coins { get; private set; }

    public PlayerState(int coins)
    {
        if (coins < 0)
            throw new System.ArgumentOutOfRangeException(nameof(coins));

        Coins = coins;
    }

    public PurchaseResult TryPurchase(
        int itemId,
        int quantity,
        int unitPrice)
    {
        if (quantity <= 0 || unitPrice < 0)
            return new(PurchaseStatus.InvalidQuantity);

        long cost = (long)quantity * unitPrice;

        if (cost > Coins)
            return new(PurchaseStatus.InsufficientCoins);

        _inventory.TryGetValue(itemId, out int oldCount);

        long newCount = (long)oldCount + quantity;

        if (newCount > int.MaxValue)
            return new(PurchaseStatus.InventoryOverflow);

        // 所有检查完成后，再一起修改状态。
        Coins -= (int)cost;
        _inventory[itemId] = (int)newCount;

        return new(PurchaseStatus.Success);
    }

    public int GetItemCount(int itemId)
    {
        return _inventory.GetValueOrDefault(itemId);
    }
}

注意一个非常重要的设计细节：

TEXT
// 先检查所有执行条件

// 最后才修改状态
Coins -= (int)cost;
_inventory[itemId] = (int)newCount;

为什么？

因为如果我们先扣除金币，然后才检查背包是否允许添加，就可能出现：

TEXT
金币扣除了
    ↓
背包添加失败
    ↓
状态不一致

这里的 TryPurchase() 将这两个状态修改放在同一个领域操作中。

在这个简化的单线程、内存状态示例里，它可以在所有预检查通过后完成修改。

但这并不等于获得了数据库级别的事务保障，也不意味着它可以安全处理并发请求。

第四步：创建命令处理器

C#
using System.Collections.Generic;

public sealed class PurchaseItemHandler
{
    private readonly PlayerState _player;
    private readonly IReadOnlyDictionary<int, int> _itemPrices;

    public PurchaseItemHandler(
        PlayerState player,
        IReadOnlyDictionary<int, int> itemPrices)
    {
        _player = player;
        _itemPrices = itemPrices;
    }

    public PurchaseResult Handle(PurchaseItemCommand command)
    {
        if (!_itemPrices.TryGetValue(
                command.ItemId,
                out int price))
        {
            return new(PurchaseStatus.ItemNotFound);
        }

        return _player.TryPurchase(
            command.ItemId,
            command.Quantity,
            price
        );
    }
}

注意这里的职责划分：

TEXT
PurchaseItemCommand
    负责表达购买请求

PurchaseItemHandler
    负责查找道具价格、协调购买

PlayerState
    负责维护金币与背包状态的一致性

PurchaseResult
    负责表达操作结果

处理器没有直接修改 Coins，也没有直接操作背包字典。

这是因为真正的业务规则应该有明确的所有者。

第五步：从 UI 发起命令

C#
using UnityEngine;

public sealed class ShopUI : MonoBehaviour
{
    private PurchaseItemHandler _handler;

    public void Initialize(PurchaseItemHandler handler)
    {
        _handler = handler;
    }

    public void OnBuyClicked(int itemId)
    {
        var command = new PurchaseItemCommand(
            ItemId: itemId,
            Quantity: 1
        );

        PurchaseResult result = _handler.Handle(command);

        if (result.Success)
        {
            Debug.Log("购买成功");
        }
        else
        {
            Debug.Log($"购买失败：{result.Status}");
        }
    }
}

这时 UI 只负责：

TEXT
获取玩家操作
    ↓
创建 PurchaseItemCommand
    ↓
发送给 Handler
    ↓
根据 Result 更新显示

它完全不需要理解金币和背包的内部实现。

最终结构

ShopUI

产生请求

Test

产生请求

PurchaseItemCommand

操作意图与参数

PurchaseItemHandler

协调购买过程

PlayerState.TryPurchase()

检查条件、维护状态不变量

PurchaseResult

成功或拒绝及其原因

请注意，这个例子中的 Handler 是直接调用的。

我们没有建立命令总线，也没有建立消息队列。

因为：

命令架构不要求使用复杂基础设施。

让意图与执行分离，已经获得了最核心的价值。

四、从更深层次理解：命令与状态转移是什么关系？

这是理解命令很重要的一步。

前面说过，命令是一种执行意图。

但程序最终要做的，往往是改变系统状态。

假设系统当前状态为：

S

收到一个命令：

C

系统处理之后产生新状态：

S'

我们可以将处理过程抽象为：

Handle(S,C) → (S',R)

其中：

  • S：执行前的系统状态
  • C：命令
  • S'：执行后的系统状态
  • R：执行结果

例如：

TEXT
初始状态：

Player.Coins = 500
Inventory[100] = 2

收到命令：

TEXT
PurchaseItem(
    ItemId = 100,
    Quantity = 3
)

假设单价为 100，执行成功之后：

TEXT
Player.Coins = 200
Inventory[100] = 5

于是：

Handle(S,PurchaseItem) → (S',Success)

但是如果只有 200 金币：

TEXT
命令：
购买三个单价 100 的道具

系统：
金币不足

处理结果是：

Handle(S,PurchaseItem) → (S,InsufficientCoins)

注意：

同样的命令，在不同状态下，可能产生不同结果。

我们不能把命令理解为必然发生的状态变化。

更精确地说：

命令是尝试触发某个行为或状态转移的请求。状态转移是否成立，由当前状态和业务规则决定。

4.1 命令、前置条件、后置条件与不变量

命令和契约式设计（Design by Contract）存在天然联系。

例如购买命令：

前置条件（Precondition）

TEXT
购买数量 > 0

玩家存在

道具允许购买

金币足够

后置条件（Postcondition）

假设购买成功：

TEXT
金币正确扣除

背包正确增加

返回成功结果

不变量（Invariant）

任何操作执行前后，都必须保持：

TEXT
Coins >= 0

InventoryCount >= 0

当然，这里列出的只是示例，并不是所有游戏业务都必须使用这些具体不变量。

整个过程可以理解为：

TEXT
收到命令
    │
    ▼
检查前置条件
    │
    ├── 不满足 ──→ 拒绝命令
    │
    ▼
执行领域行为
    │
    ▼
检查或保证后置条件
    │
    ▼
保持系统不变量
    │
    ▼
返回结果

如果使用 Hoare Logic，可以为成功路径写成：

\{P\} PurchaseItem \{Q\}

其中 P 表示足以保证该成功执行路径正确的前置条件，Q 表示执行后的期望状态。

但需要注意：仅有外部输入“发来了购买命令”，并不意味着 P 已经成立。实际系统还必须处理验证失败的路径。

4.2 命令和行为是不是同一个概念？

不是。

考虑：

TEXT
JumpCommand

它的含义是：

TEXT
请求跳跃

而：

C#
player.Jump();

代表实际调用跳跃行为。

区别在于：

概念 回答的问题
Command 希望系统做什么？
Behavior / Action 系统实际做什么？
State Transition 系统状态如何改变？
Result 命令执行结果是什么？

例如：

TEXT
JumpCommand
    ↓
检查 CanJump
    ↓
Player.Jump()
    ↓
Grounded → Airborne

这四个概念可以连接在一起，但不应该在理解上混为一谈。

而且并非所有命令都必须直接修改业务状态。例如发送通知、刷新外部资源等命令，可能主要产生外部副作用。

五、命令、事件、查询：三个最容易混淆的概念

这是理解 Command 最重要的知识点之一。

命令、事件和查询经常出现在相同的系统中，但它们的语义完全不同。

5.1 Command：希望发生什么

例如：

TEXT
PurchaseItemCommand

含义：

TEXT
我请求购买一个道具。

注意：

TEXT
购买可能成功
购买可能失败
购买可能暂时无法执行

因此，Command 表示一个尚未确定结果的执行意图。

5.2 Event：已经发生了什么

例如：

TEXT
ItemPurchasedEvent

含义：

TEXT
某个道具购买成功这一事实已经成立。

事件不是要求接收者决定购买是否发生。

它描述的是已经确认发生的事实。

例如：

TEXT
PurchaseItemCommand
        │
        ▼
PurchaseItemHandler
        │
        ▼
购买成功
        │
        ▼
ItemPurchasedEvent
        │
        ├── AchievementSystem
        ├── StatisticsSystem
        ├── QuestSystem
        └── AnalyticsSystem

这里的逻辑非常清晰：

  • Command 用于请求购买。
  • Handler 负责协调购买。
  • Domain 负责执行购买规则。
  • Event 用于通知其他系统购买成功。

其他系统不应该因为收到了 PurchaseItemCommand，就直接认为购买已经发生。

否则可能出现：

TEXT
玩家请求购买道具
    │
    ├── 成就系统：购买次数 +1
    │
    ├── 统计系统：消费金额 +100
    │
    └── 商城系统：余额不足，购买失败

结果就是：

购买失败了，但成就和统计已经更新。

这种错误往往源于没有区分请求与事实。

正确的设计应该让购买成功这件事先被确认，再通知依赖这一事实的系统。

如果事件需要可靠地跨服务传递，还应考虑事务提交、持久化消息和 Outbox 等机制，避免主业务提交成功而事件丢失。

5.3 Query：希望知道什么

例如：

TEXT
GetPlayerCoinsQuery

它表达：

TEXT
我想知道玩家当前有多少金币。

查询的目标是获取信息，而不是请求执行修改状态的业务操作。

将三个概念放在一起：

概念 语义 例子
Command 请求执行操作 PurchaseItem
Event 已经发生的事实 ItemPurchased
Query 请求获取信息 GetPlayerInventory

再来看一个完整过程：

TEXT
GetPlayerCoinsQuery
        │
        ▼
查询玩家金币
        │
        ▼
返回 500

PurchaseItemCommand
        │
        ▼
执行购买
        │
        ▼
成功扣除 100 金币
        │
        ▼
ItemPurchasedEvent
        │
        ├── 更新统计
        ├── 检查成就
        └── 更新任务进度

这三个概念分工十分清晰。

Query 询问状态，Command 请求改变系统，Event 描述已经发生的事实。

这里的“改变系统”是命令常见的用途，但不是硬性条件；一个命令可以被拒绝，也可能只产生外部副作用。

六、命令模式（Command Pattern）：命令为什么能支持撤销、重做？

前面主要讲的是命令的架构语义。

接下来，我们回到 GoF 命令模式。

其经典参与者包括：

TEXT
Client
    │ 创建命令
    ▼
ConcreteCommand
    │ 持有接收者
    ▼
Receiver

Invoker
    │ 调用命令
    ▼
Command.Execute()

含义是：

  • Client 负责创建和配置命令。
  • Command 定义统一的执行接口。
  • ConcreteCommand 实现某种具体命令。
  • Receiver 负责真正完成操作。
  • Invoker 决定何时调用命令。

在 Unity 中，Invoker 可以是快捷键系统、命令队列，也可以是编辑器操作历史管理器。

6.1 实现一个可以撤销的移动命令

先定义接口：

C#
public interface IUndoableCommand
{
    void Execute();
    void Undo();
}

然后实现移动命令：

C#
using UnityEngine;

public sealed class MoveCommand : IUndoableCommand
{
    private readonly Transform _target;
    private readonly Vector3 _newPosition;

    private Vector3 _oldPosition;
    private bool _captured;

    public MoveCommand(Transform target, Vector3 newPosition)
    {
        _target = target;
        _newPosition = newPosition;
    }

    public void Execute()
    {
        // 只在首次执行时捕获旧状态。
        if (!_captured)
        {
            _oldPosition = _target.position;
            _captured = true;
        }

        _target.position = _newPosition;
    }

    public void Undo()
    {
        if (!_captured)
            return;

        _target.position = _oldPosition;
    }
}

这里出现了一个重要设计：

TEXT
命令不仅记录要做什么

还可以记录撤销操作所需要的信息

接着，我们实现历史记录：

C#
using System.Collections.Generic;

public sealed class CommandHistory
{
    private readonly Stack<IUndoableCommand> _undoStack = new();
    private readonly Stack<IUndoableCommand> _redoStack = new();

    public void Execute(IUndoableCommand command)
    {
        command.Execute();

        _undoStack.Push(command);
        _redoStack.Clear();
    }

    public void Undo()
    {
        if (_undoStack.Count == 0)
            return;

        var command = _undoStack.Pop();

        command.Undo();

        _redoStack.Push(command);
    }

    public void Redo()
    {
        if (_redoStack.Count == 0)
            return;

        var command = _redoStack.Pop();

        command.Execute();

        _undoStack.Push(command);
    }
}

使用：

C#
var history = new CommandHistory();

history.Execute(
    new MoveCommand(
        transform,
        new Vector3(10, 0, 0)
    )
);

history.Undo();

history.Redo();

现在：

TEXT
初始位置：(0, 0, 0)

Execute
    ↓
位置：(10, 0, 0)

Undo
    ↓
位置：(0, 0, 0)

Redo
    ↓
位置：(10, 0, 0)

这个实现只是用于说明原理，假设命令都能够成功执行，目标对象不会被销毁，且没有其他操作在中途改变相关状态。

生产级编辑器还需要考虑失败执行、对象生命周期、历史操作冲突、组合命令等问题。

6.2 为什么命令能做到撤销？

因为原本的一次性方法调用：

TEXT
transform.position = newPosition;

已经执行完毕，没有独立的操作记录。

而命令模式把操作转变为可保存的实体：

TEXT
MoveCommand
    │
    ├── Target
    ├── OldPosition
    ├── NewPosition
    ├── Execute()
    └── Undo()

我们可以把它：

TEXT
保存
排队
执行
撤销
重做
组合

不过，命令对象化与可撤销性之间不是充分必要关系。

例如：

TEXT
SendEmailCommand

邮件一旦发送出去，我们无法真正撤回接收者已经读取的内容。

因此：

把操作表示为命令，可以为 Undo 提供基础，但不能保证每一种操作都可逆。

在无法真正逆转的业务中，通常需要补偿操作（Compensating Action），例如退款、取消订单，而不是假装原操作从未发生。

七、命令与 CQRS 是什么关系？

CQRS 的全称是：

Command Query Responsibility Segregation（命令查询职责分离）。

它的核心思想是将修改状态的操作与读取状态的操作，在设计模型上进行区分。

例如：

传统业务服务：

C#
public class PlayerService
{
    public void PurchaseItem() { }

    public void EquipItem() { }

    public int GetCoins() { return 0; }

    public Inventory GetInventory() { return null; }
}

既负责写入，也负责查询。

在 CQRS 中，我们可以将它们分成：

TEXT
                   Application
                        │
            ┌───────────┴───────────┐
            ▼                       ▼
      Command Side             Query Side
            │                       │
     PurchaseItem             GetInventory
     EquipWeapon              GetCoins
     ClaimReward              GetPlayerStats
            │                       │
            ▼                       ▼
        Write Model              Read Model

但是需要特别强调：

使用 Command 并不意味着你已经采用 CQRS。

一个普通的 Unity 项目完全可以使用：

TEXT
PurchaseItemCommand
PurchaseItemHandler

却不使用单独的查询模型。

同样，CQRS 也不要求：

  • 微服务
  • 两套数据库
  • 消息队列
  • Event Sourcing

它最基本的思想只是：

修改状态与读取状态，拥有不同的职责和模型需求。

当写入逻辑复杂、读取模型需要特殊优化时，这种分离尤其有用。

而如果你的系统非常简单，那么建立一套完整的 CQRS 基础设施可能只有复杂度，没有收益。

八、命令如何应用到游戏服务端？

这部分涉及命令在实际工程中更复杂的使用方式。

假设客户端调用：

TEXT
PurchaseItem

我们希望系统能防止重复扣款、非法请求和并发状态冲突。

一个典型的服务端执行流程可以设计成：

TEXT
Client
    │
    ▼
RPC / HTTP
    │
    ▼
Authentication
    │
    ▼
PurchaseItemCommand
    │
    ▼
PurchaseItemHandler
    │
    ├── 验证请求参数
    ├── 检查操作权限
    ├── 检查 RequestId 是否处理过
    │
    ▼
Transaction
    │
    ├── 获取并保护相关业务状态
    ├── 执行购买规则
    ├── 扣除金币
    ├── 添加道具
    ├── 保存业务状态
    └── 保存请求处理结果
    │
    ▼
Commit
    │
    ├── 返回 PurchaseResult
    └── 发布已确认的业务事件

这里至少存在三个必须认识的问题。

8.1 命令与幂等性

假设玩家请求购买一个道具：

TEXT
PurchaseItem(
    PlayerId = 1001,
    ItemId = 200,
    Quantity = 1,
    RequestId = ABC123
)

客户端因为网络超时，没有收到结果。

于是重试：

TEXT
PurchaseItem(
    PlayerId = 1001,
    ItemId = 200,
    Quantity = 1,
    RequestId = ABC123
)

如果服务端直接执行两次：

TEXT
第一次：
扣除 100 金币
获得 1 个道具

第二次：
扣除 100 金币
再次获得 1 个道具

这不是我们期望的行为。

因此，某些命令需要按请求标识实现幂等处理。

概念上：

TEXT
收到 PurchaseItemCommand
          │
          ▼
      检查 RequestId
          │
     ┌────┴─────┐
     │          │
  已处理       未处理
     │          │
     ▼          ▼
返回历史结果   执行购买
                │
                ▼
           保存处理结果
                │
                ▼
             返回结果

其目标是：

Handle(C,r) 重试多次

对于同一个逻辑请求 r，不应重复产生购买副作用。

但有一个关键陷阱：

TEXT
检查 RequestId 不存在
          ↓
执行购买
          ↓
记录 RequestId

如果两个请求并发到达，它们可能同时发现请求不存在，然后重复执行。

所以，真正的服务端实现需要数据库唯一约束、事务、锁或其他可靠的并发控制机制，并让去重记录与业务状态变更具有一致的提交语义。

给命令添加 RequestId 不等于自动实现幂等性。

它只是让系统有办法识别同一个逻辑请求。

而且 RequestId 需要限定在可信的业务范围内，并与请求内容保持一致，避免相同标识对应不同操作。

8.2 命令与事务

一次购买涉及：

TEXT
扣除金币
增加道具

业务要求：

TEXT
两个操作必须作为一个逻辑整体成功

那么，我们需要事务边界。

可以表示为：

Purchase = DebitCoins + AddItem

成功时：

Commit(DebitCoins,AddItem)

失败时：

Rollback

如果两个状态都保存在同一个支持事务的数据库中，通常可以借助数据库事务保证原子提交。

但如果金币和道具分别位于两个不同的服务中：

TEXT
WalletService
InventoryService

事情就复杂得多。

普通的本地数据库事务无法自然覆盖两个独立服务。

这时可能需要：

  • 调整聚合和事务边界
  • Saga
  • 补偿事务
  • 消息可靠投递
  • 幂等消费

这些机制解决的是一致性与分布式执行问题。

Command 可以作为一次业务操作的入口，但不能取代它们。

8.3 命令与授权

还有一个经常被忽略的问题。

假设客户端发送：

TEXT
PurchaseItemCommand(
    PlayerId: 9999,
    ItemId: 200,
    Quantity: 1
)

服务端能否只根据命令里的 PlayerId，就修改玩家 9999 的数据？

当然不能。

因为：

命令的数据表示了请求内容，不代表请求者拥有执行该操作的权限。

服务端需要根据可信的身份认证上下文判断：

TEXT
是谁发送的请求？

他是否有权操作该玩家？

命令内容是否合法？

所以应区分：

TEXT
Command：
客户端请求执行什么？

Authenticated Context：
谁被认证为请求者？

Authorization：
该请求者有没有权限执行？

将这些概念分离，有助于避免将用户输入误当成可信授权信息。

九、命令是否需要统一的 CommandBus？

这是架构实践中经常出现的争议。

假设我们已经有：

TEXT
PurchaseItemHandler
EquipWeaponHandler
ClaimRewardHandler

现在我们希望统一处理命令。

可以建立：

C#
public interface ICommand<TResult>
{
}

public interface ICommandHandler<TCommand, TResult>
    where TCommand : ICommand<TResult>
{
    TResult Handle(TCommand command);
}

例如：

C#
public sealed record EquipWeaponCommand(int WeaponId)
    : ICommand<bool>;

处理器：

C#
public sealed class EquipWeaponHandler
    : ICommandHandler<EquipWeaponCommand, bool>
{
    public bool Handle(EquipWeaponCommand command)
    {
        // 装备武器的业务操作
        return true;
    }
}

随后建立统一调度器：

TEXT
CommandBus.Send(command)
             │
             ▼
       找到对应 Handler
             │
             ▼
          Handle()
             │
             ▼
          返回 Result

这样做的好处是：

TEXT
调用方不需要知道具体 Handler

可以统一处理日志

可以统一进行校验

可以统一监控性能

但缺点也很明显：

TEXT
执行路径不再完全显式

调试时需要追踪 Handler 注册关系

抽象层数量增加

简单项目可能出现过度设计

尤其是在 Unity 项目中，直接注入具体 Handler 往往已经足够：

C#
var result = purchaseHandler.Handle(command);

不需要为了套用架构模式而建立：

TEXT
CommandFactory
    ↓
CommandDispatcher
    ↓
CommandPipeline
    ↓
CommandBus
    ↓
CommandHandlerResolver
    ↓
CommandHandler

这些抽象只有在实际解决了复杂性之后，才有存在价值。

CommandBus 不是命令的本质，也不是使用命令的必要条件。

十、Command 与其他架构概念的关系

将它和其他概念放在一起，有助于建立更完整的知识结构。

概念 核心责任 与 Command 的关系
State Machine 定义状态及合法转移 命令可以请求触发转移
Domain Model 维护业务规则与不变量 命令处理器调用领域行为
Event 描述已经发生的事实 命令成功后可能产生事件
CQRS 分离写入与读取模型 Command 通常是写入侧入口
Queue 保存并调度待处理工作 命令可以进入队列
Transaction 保证指定范围的原子操作 可包围命令导致的状态变更
Undo/Redo 回退和重做用户操作 可以用命令记录操作历史
Event Sourcing 用历史事件重建状态 命令可能产生被持久化的事件
Saga 协调跨边界长事务 可以通过命令驱动多个参与者

在这里，有两个关系特别值得深入理解。

10.1 Command 和 State Machine

假设角色有三个状态：

TEXT
Idle
Attacking
Stunned

收到命令：

TEXT
AttackCommand

不同状态可能做出不同决定：

TEXT
Idle + AttackCommand
    → Attacking

Attacking + AttackCommand
    → 缓冲、拒绝或者触发连击

Stunned + AttackCommand
    → 拒绝

也就是说：

命令提供外部刺激，状态机决定在当前状态下应如何响应。

这是非常自然的合作关系。

不过，具体的状态转移系统也可能直接接受输入枚举，而不必为每种输入建立独立的 Command 类。

10.2 Command 和 Event-Driven Architecture

例如：

TEXT
PurchaseItemCommand
         │
         ▼
购买业务处理
         │
         ▼
ItemPurchasedEvent
         │
         ├── Statistics
         ├── Achievements
         └── Quests

这一结构实现了两种解耦：

第一种：

TEXT
命令解耦：
发起者与业务执行者

第二种：

TEXT
事件解耦：
事实产生者与事实消费者

但一定要记住它们之间的区别：

命令通常针对一个明确的业务职责，由一个逻辑上的责任方决定如何处理；事件则可以被多个独立订阅者观察。

这不意味着命令一定只有一个物理消费者，也不意味着事件一定异步广播。真正关键的仍然是语义和责任所有权。

十一、为什么不能把所有操作都设计为命令？

这是非常重要的设计权衡。

假设你的代码只是：

C#
player.TakeDamage(10);

有没有必要改成：

C#
var command = new TakeDamageCommand(
    player,
    10
);

commandBus.Send(command);

答案是：不一定。

如果不存在：

TEXT
跨系统调用
统一记录
操作调度
撤销重做
消息传输
集中协调

那么直接调用方法可能更加清晰。

而且，抽象也可能隐藏重要的依赖关系。

例如：

C#
commandBus.Send(new TakeDamageCommand(...));

如果调用者根本不知道这条命令会经过哪些处理器、修改哪些状态，那么系统反而可能变得难以理解。

11.1 什么时候使用命令？

可以通过下面这个交互判断：

选择一个实际场景：

普通 UI 更新本地显示

游戏服务端购买道具

地图编辑器的移动/删除操作

单个组件内部计算伤害数值

需要排队处理的角色指令

通知其他系统道具已经购买成功

适合引入命令抽象

存在业务校验、权限、事务、幂等和统一入口等需求。纯数据命令与 Handler 很合适。

这里真正需要判断的不是“这个操作能不能封装成命令”。

理论上，大量操作都能封装成命令。

需要判断的是：

让这个操作成为独立的请求对象，是否能解决当前真实存在的变化、调度、复用或治理问题？

如果不能，就不要为了模式而增加模式。

十二、一些常见误区

误区 正确认识
命令必须有 Execute() 不必须。纯数据命令加 Handler 同样成立
发送命令就是执行成功 命令只是请求，必须区分执行结果
使用命令就一定要有 CommandBus 可以直接调用具体 Handler
Command 与 Event 是相同概念 Command 是意图，Event 是事实
Command 一定改变状态 可能被拒绝，也可能主要产生外部副作用
Command 自动支持 Undo 还需要历史状态或逆操作
Command 能保证事务一致性 需要事务机制和正确的领域边界
Command 天然幂等 需要请求标识、去重和并发控制
命令对象越多架构越先进 抽象应由实际需求决定

尤其注意：

命令既可以是一种本地设计模式，也可以是一种应用层消息。

前者强调把操作对象化，以获得操作调度和管理能力。

后者强调业务请求语义与执行边界。

不应该将它们完全混淆，也不应该认为二者只能选择其一。

十三、进一步抽象：命令的本质究竟是什么？

现在抛开 Unity、C#、设计模式以及服务器的具体实现。

假设一个系统中存在操作：

TEXT
A 想让 B 做一件事情。

最直接的方式：

TEXT
A 直接调用 B

这种方式具有几个特点：

TEXT
A 知道 B

A 需要知道调用方式

操作通常立刻发起

调用关系直接体现在代码中

如果我们把“要做的事情”单独抽象出来：

TEXT
A
│
▼
Command
│
▼
B

我们就获得了一个独立于具体发起者的操作描述。

于是系统能够回答一系列原本不容易独立回答的问题：

TEXT
这个请求是谁提出的？

它要做什么？

谁有权执行？

应该什么时候执行？

它是否已经执行过？

它是否可以被拒绝？

它执行成功了吗？

执行之后发生了什么？

但这些能力不是命令对象自动提供的。命令只是给相关机制提供了一个可识别的操作单位。

从抽象层面，可以把命令处理理解为：

Execute:(State,Command) → (State',Result,Effects)

其中：

  • State 是当前系统状态。
  • Command 是操作意图。
  • State' 是处理后的状态。
  • Result 是执行结果。
  • Effects 是可能需要发生的副作用。

例如：

TEXT
Command:
    PurchaseItem

State:
    Coins = 500
    Items = 2

Execution:
    检查购买规则
    扣除金币
    增加道具

State':
    Coins = 400
    Items = 3

Result:
    Success

Effects:
    购买成功事件
    UI 更新
    日志

当然，这个公式是概念模型，不意味着状态修改、外部副作用和结果返回都能在一个事务中原子完成。

正因为这些责任存在不同的失败机制，我们才需要明确它们之间的边界。

十四、把命令放回完整的软件架构中

最后，我们把本次涉及的概念组合起来。

TEXT
                  用户输入 / 网络请求
                          │
                          ▼
                     Command
                          │
                          ▼
                    CommandHandler
                          │
               ┌──────────┴──────────┐
               │                     │
               ▼                     ▼
          权限与请求验证          读取当前状态
               │                     │
               └──────────┬──────────┘
                          │
                          ▼
                      Domain
                          │
                   检查业务规则
                          │
                  ┌───────┴────────┐
                  │                │
                不满足            满足
                  │                │
                  ▼                ▼
              拒绝请求        执行领域行为
                  │                │
                  │                ▼
                  │           状态转移
                  │                │
                  │                ▼
                  │        事务性持久化（如需）
                  │                │
                  │                ▼
                  │          已确认的事实
                  │                │
                  │                ▼
                  │         Domain Events
                  │                │
                  │          ┌─────┴─────┐
                  │          ▼           ▼
                  │       Statistics  Achievements
                  │
                  ▼
              Failure Result

成功路径也会返回 Success Result，事件订阅者则根据事实处理后续工作。外部发布的可靠性还需要单独设计。

在这个结构中：

层次 最重要的问题
Input / RPC 请求从哪里来？
Command 请求做什么？
Handler 谁协调执行？
Domain 什么情况下允许执行？
State Transition 状态怎样改变？
Transaction 哪些变化必须共同提交？
Result 请求处理得怎么样？
Event 哪些事实已经成立？

每个概念都有自己的职责。

这也说明，真正优秀的架构并不是不断增加模式，而是将原本纠缠在一起的不同问题，放在正确的责任边界内。

十五、最终总结：What、Why、How

What：命令是什么？

命令是一个显式的执行意图。

它表达“希望系统做什么”，但不保证系统能够执行，也不保证执行成功。

命令可以是：

TEXT
一个函数调用
一个封装了 Execute() 的对象
一个由 Handler 处理的数据消息
一个进入队列等待执行的操作请求

Why：为什么需要命令？

因为一个复杂系统常常需要将：

TEXT
请求产生
请求执行
业务规则
状态改变
执行结果
后续通知

进行分离。

命令主要帮助解决发起者与执行者耦合、操作不能独立调度、重复业务入口、操作历史难以管理等问题。

它也可以为事务、授权、幂等、日志等机制提供明确的操作边界，但不能代替这些机制。

How：命令如何工作？

最基础的过程：

TEXT
创建 Command
       ↓
交给 Handler
       ↓
检查执行条件
       ↓
调用领域行为
       ↓
改变状态或产生副作用
       ↓
返回 Result
       ↓
必要时发布 Event

具体采用直接调用、命令模式、CommandBus 还是消息队列，取决于业务需求，而不是模式本身。

最值得记住的五句话

  1. Command 是意图，Event 是事实，Query 是询问。
  2. 命令与执行分离，是为了让操作拥有独立的表达与管理边界。
  3. 命令不保证成功，状态转移必须服从业务规则和不变量。
  4. Command Pattern、Command Handler、CQRS 是相关但不同层次的概念。
  5. 需要命令时使用命令，不需要时直接调用方法。抽象的价值在于解决问题，而不是增加层次。

如果继续深入，我建议沿着这一条知识路径：

Command → Command Handler → CommandBus / Middleware → CQRS → Event Sourcing → Saga

其中最值得下一步研究的是 Command 与 Event 的协作边界：为什么一个系统应该让命令负责请求改变，让领域规则决定是否改变，并让事件表达已经成立的事实。

理解这条链路，你就能把命令、状态转移、不变量、事务、事件系统以及更高级的领域架构联系起来。

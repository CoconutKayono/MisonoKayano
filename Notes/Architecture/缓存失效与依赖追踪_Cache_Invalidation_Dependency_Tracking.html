我们按照 What、Why、How，直击本质的方式来理解这两个概念。

先把它们最核心的分工说清楚：

Cache Invalidation 负责决定「哪些旧结果不能继续被信任」；Dependency Tracking 负责知道「谁可能受到变化影响」。

缓存保存了过去得到的结果，让系统不必重复完成同一份工作。但当原始数据发生变化，我们就必须回答：过去的结果，现在还能继续使用吗？如果不能，是哪些结果需要更新？

这就是缓存失效与依赖追踪要解决的问题。

一、先从一个最简单的问题开始：缓存为什么会失效？

假设我们在开发一个游戏，玩家的最终攻击力由基础攻击力与装备加成决定：

C#
int finalAttack = baseAttack + equipmentBonus;

当基础攻击力是 100、装备加成是 50 时，最终攻击力就是 150。

如果每次读取最终攻击力都重新执行计算，就存在重复工作。对于一次加法，这点成本几乎不值得关注；但如果公式需要遍历装备、Buff、技能、配置，甚至查询其他系统，计算成本就可能明显增加。

于是我们把计算结果保存下来：

C#
int cachedFinalAttack = 150;

下一次需要最终攻击力时，直接复用这个结果。

到这里，缓存完成了它的工作：用保存的结果，避免重复获取或计算。

但是，现在玩家更换了一件装备，装备加成从 50 变成了 80。

真正的最终攻击力应该变成：

100 + 80 = 180

而缓存中保存的仍然是 150。

这时，如果继续直接返回缓存，就会得到不符合当前状态的结果。

问题不在于缓存中的 150 当初算错了，而在于：

它是过去状态下的正确结果，却不一定是当前状态下的正确结果。

因此，缓存系统不仅要保存结果，还必须管理结果的有效性。

接下来就出现两个问题：

  1. **缓存失效：**什么时候不能继续直接使用这个旧结果？
  2. **依赖追踪：**装备加成变化，究竟会影响哪些结果？

二、What：Cache Invalidation 到底是什么？

2.1 失效的本质：撤销旧结果的直接复用资格

Cache Invalidation 通常译为「缓存失效」，也可以理解为让缓存失效、使缓存作废。

它的核心不是某个固定的数据结构，也不是必须调用一个名为 Invalidate() 的方法，而是：

当旧结果不再具有足够的有效性依据时，阻止系统继续无条件地复用它。

例如，装备发生变化后，系统可以把攻击力缓存标记为 Dirty，表示下次读取时需要重新计算。

这里要注意：标记失效，不一定意味着已经证明结果数值改变了。

假设最终攻击力存在上限：

C#
int finalAttack = Math.Min(baseAttack + equipmentBonus, 999);

装备加成虽然变化，但最终攻击力可能仍然是 999。系统依然可以保守地让缓存失效，因为它尚未重新验证结果。

所以，失效更准确地说是在表达：不能再仅凭原先的依据，直接信任这份缓存。

2.2 缓存失效不等于删除缓存

缓存失效之后，可以有多种处理方式。

  • 删除旧条目，下一次读取时重新获取。
  • 保留旧结果，但标记为 Dirty，下一次读取时重新计算。
  • 立即重新计算，并替换旧结果。
  • 安排稍后的批量刷新。
  • 在业务明确允许的情况下，短暂返回旧值，同时触发刷新。

这意味着：失效、删除与重新计算，是相互关联但不同的动作。

动作 处理的问题
Invalidation（失效） 旧结果还能不能按照当前规则直接复用？
Removal / Eviction（删除／淘汰） 这个缓存条目是否继续保留？
Recomputation / Refresh（重算／刷新） 怎样获得符合当前要求的新结果？

一个仍然有效的缓存，也可能因为空间不足而被淘汰；一个已经失效的缓存，也可能继续保留在内存里，等待重新计算。

2.3 有效性取决于系统要求的一致性契约

「有效」并不总是意味着与权威数据实时完全一致。

例如，战斗属性可能要求更换装备后的下一次读取必须得到新值；排行榜可能允许几秒延迟；某些 UI 可以在下一帧才更新。

因此，我们需要先明确：系统在什么时间、以什么标准要求这份缓存与源数据保持一致？

缓存是否有效，要根据它是否满足当前的一致性与新鲜度要求来判断。

实现上，也不一定只有「有效／无效」两个状态。复杂系统还可能区分未初始化、有效、脏（Dirty）、正在刷新（Refreshing）、刷新失败（Failed）等状态。

三、What：Dependency Tracking 到底是什么？

3.1 依赖的本质：一个结果的正确性受什么影响？

假设有这样一个玩家数据系统：

C#
int baseAttack = 100;
int equipmentBonus = 50;
int finalAttack = baseAttack + equipmentBonus;

我们说：

FinalAttack = f(BaseAttack, EquipmentBonus)

那么：

BaseAttack → FinalAttack
EquipmentBonus → FinalAttack

箭头的含义是：

左侧的数据发生变化，可能影响右侧计算结果。

这是一种数据依赖（Data Dependency）。

依赖追踪的本质，就是将这种原本隐含在计算过程中的关系显式记录下来，使系统能够回答：

当某个数据发生变化时，哪些派生结果可能受到影响？

3.2 为什么这是一张图，而不只是一个变量列表？

因为真实的系统经常存在多层依赖。

例如：

FinalAttack = BaseAttack + EquipmentBonus
PowerScore = FinalAttack × 10 + Defense
UI = Format(PowerScore)

这意味着最终攻击力依赖两个原始属性，战斗力又依赖最终攻击力，UI 再依赖战斗力。

现在我们修改基础攻击力：

C#
baseAttack = 120;

系统就可以顺着这张图识别受影响节点：

基础攻击力 → 最终攻击力 → 战斗力 → UI 显示

而假设我们只修改玩家昵称，最终攻击力就不应该受到影响。

这带来了一个非常重要的性能价值：

系统不需要重新计算所有数据，只需要处理可能受到变化影响的部分。

3.3 Dependency Tracking 实际上在追踪什么？

从实现角度看，核心是记录两类关系。

正向关系：我依赖谁？

例如：

说明
FinalAttack 依赖:
    BaseAttack
    EquipmentBonus

PowerScore 依赖:
    FinalAttack
    Defense

正向关系方便在计算结果时检查所有输入是否仍然有效。

反向关系：谁依赖我？

例如：

说明
BaseAttack 被以下节点依赖:
    FinalAttack

FinalAttack 被以下节点依赖:
    PowerScore

反向关系方便在原始数据发生变化时，找到需要失效的下游节点。

这也是为什么很多响应式系统都会维护订阅者集合。

Vue 的响应式机制便是一个经典例子：属性读取时记录当前计算者，属性被修改时查找依赖它的计算者；computed 在此基础上管理缓存失效和重新计算。

3.4 依赖追踪不是简单地记录谁调用了谁

这一点非常重要。

假设：

C#
int CalculateAttack(Player player)
{
    return player.BaseAttack + player.EquipmentBonus;
}

这里调用 CalculateAttack() 的函数，不一定就是计算结果的真正数据依赖。

真正影响返回值的是 BaseAttack 和 EquipmentBonus。

还要考虑这样的条件分支：

C#
int CalculateAttack(Player player)
{
    if (player.IsBerserk)
        return player.BaseAttack * 2;

    return player.BaseAttack + player.EquipmentBonus;
}

这里存在动态依赖。

当 IsBerserk == true 时，本次计算实际读取：

IsBerserk、BaseAttack

当 IsBerserk == false 时，本次计算实际读取：

IsBerserk、BaseAttack、EquipmentBonus

因此，依赖并不一定是固定不变的。运行时的分支路径可能决定当前究竟依赖哪些数据。

一旦 IsBerserk 改变，原先的依赖集合可能也需要重新建立。

这就是后面要讲的静态依赖追踪与动态依赖追踪的区别。

四、Why：为什么必须解决缓存失效和依赖追踪？

这里涉及两个看似冲突的目标：

正确性：不能使用不符合当前要求的缓存。

性能：不能因为某个数据变化，就重新计算所有缓存。

我们可以从三个反例理解。

4.1 完全不失效：正确性受到破坏

例如游戏装备系统：

玩家更换武器，但是战斗力 UI 仍然显示旧数值。

这通常不是因为战斗力公式计算错了，而是系统根本不知道何时应该重新调用这个公式。

此时缓存优化破坏了业务正确性。

4.2 所有变化都清空缓存：性能受到破坏

假设玩家有 100 个派生属性，每个属性的计算成本都不低。

但玩家只是修改了昵称。

如果我们采用：

C#
void OnPlayerDataChanged()
{
    RecalculateAll();
}

那么昵称变化也会触发攻击力、防御力、技能伤害、装备评分等全部重新计算。

这当然能够覆盖许多失效情况，但效率很低。

更准确的做法，是通过依赖关系限制重新计算范围。

4.3 每次读取都重算：缓存失去意义

有一种看起来绝对安全的方案：

C#
public int FinalAttack =>
    _baseAttack + _equipmentBonus;

对于这个简单加法，它完全合理，甚至可能比维护缓存更好。

但是当计算需要遍历数万个单位、分析复杂的状态、查询磁盘或者执行昂贵布局计算时，重复执行的成本就可能非常高。

于是，我们不希望所有读取都重新计算。

这也意味着：缓存的收益来自减少重复工作，而缓存失效的职责是防止这种复用越过正确性的边界。

4.4 这两个技术共同处理的根本矛盾

我们可以把设计目标表示为：

min（重复计算成本 + 维护依赖成本）

前提是：

缓存满足系统要求的一致性契约

也就是说，性能优化必须处在正确性的约束之下。

有两个重要判断：

失效决策 实际受影响 实际不受影响
标记失效 正确识别 过度失效，多做工作
未标记失效 漏判，可能返回旧结果 正确跳过

因此，漏判比过度失效更加危险，至少对于要求严格一致性的缓存而言是这样。

不过，并非所有场景都要求数据绝对实时。例如，游戏排行榜可以接受几秒延迟，某些 UI 允许下一帧更新。缓存策略需要根据业务的一致性要求来设计，而不是一律追求同步更新。

五、How：缓存失效究竟可以怎样实现？

缓存失效并没有唯一的实现方式。

关键问题是：

系统依靠什么证据，判断缓存还能不能继续使用？

常见有五类实现策略。

5.1 第一种：主动失效（Explicit Invalidation）

最简单的方式，就是由修改数据的代码主动通知缓存。

C#
public void SetEquipmentBonus(int value)
{
    if (_equipmentBonus == value)
        return;

    _equipmentBonus = value;

    // 装备加成改变，最终攻击力可能过期
    _attackDirty = true;
}

它的逻辑非常清楚：

数据发生变化 → 将对应缓存标记为失效。

优势是实现简单，容易理解。

问题是所有修改路径都必须正确执行失效逻辑。

例如：

C#
_equipmentBonus = 100;

如果其他代码直接修改私有字段，绕过统一方法，就可能遗漏缓存失效。

所以，这实际上又引出了一个你之前学习过的概念：信息隐藏（Information Hiding）。

信息隐藏在这里不只是为了封装代码，而是在保护一个不变量：

相关数据修改 ⇒ 缓存被正确失效

如果允许外部绕过修改入口，这个不变量就无法保证。

5.2 第二种：版本号（Versioning）

除了 Dirty Flag，还可以用版本号判断。

我们先给源数据一个版本号：

C#
private long _attackRevision = 0;
private long _cachedRevision = -1;
private int _cachedAttack;

当攻击力相关数据发生变化：

C#
_attackRevision++;

读取缓存时：

C#
public int FinalAttack
{
    get
    {
        if (_cachedRevision != _attackRevision)
        {
            _cachedAttack = _baseAttack + _equipmentBonus;
            _cachedRevision = _attackRevision;
        }

        return _cachedAttack;
    }
}

这里就不需要 isDirty 了。

系统通过版本差异判断缓存是否过期：

Valid ⇔ Vcache = Vsource

这个公式成立的前提，是版本号确实覆盖了所有相关变化，且版本标识能够可靠区分不同状态。

版本号与脏标记有不同的侧重点：

Dirty Flag 记录一种状态：这个缓存需要重新计算。

Version 记录一种历史关系：这个缓存对应哪一次源数据修订。

尤其在异步计算中，版本号可以帮助识别一个结果究竟基于哪个旧状态产生。

不过，版本号并不能自动告诉系统哪些数据相关；它仍然需要正确的依赖范围。

5.3 第三种：TTL（Time To Live）

对于服务器数据缓存，我们可能无法直接观察源数据每一次变化。

例如：

说明
缓存玩家资料，过期时间 60 秒。

读取时：

说明
当前时间 < 过期时间：
    允许继续使用缓存

当前时间 >= 过期时间：
    重新获取玩家资料

这里使用的不是精确的依赖关系，而是时间策略。

它的基本思想是：

即使不知道源数据什么时候变化，也可以限制在某段时间之后必须重新检查。

但必须注意：

TTL 不保证过期之前的数据一定正确。

例如，缓存生成后第 1 秒，数据库就更新了玩家资料，而缓存第 60 秒才到期，那么中间可能持续返回旧数据。

所以 TTL 更准确地说是一种过期策略，而不是严格的变化检测机制。

5.4 第四种：事件驱动失效（Event-driven Invalidation）

我们还可以让数据修改时发出事件：

C#
public event Action OnEquipmentChanged;

装备修改：

C#
public void ChangeEquipment()
{
    // 修改装备数据...

    OnEquipmentChanged?.Invoke();
}

监听方：

C#
equipment.OnEquipmentChanged += InvalidateAttack;

这种方法把源数据修改者与缓存维护者解耦。

但是注意：

事件是变化传播机制，并不是依赖追踪本身。

订阅事件之前，开发者仍然需要知道应该监听哪个事件。

而且，如果订阅关系缺失、事件丢失、或者事件在错误的时机发出，缓存仍可能出现一致性问题。

5.5 第五种：依赖驱动失效（Dependency-based Invalidation）

这是我们今天重点讨论的方式。

假设系统维护着这样一份关系：

当 BaseAttack 发生变化，系统根据依赖图找到受影响的节点。

它可以逐层传播失效：

BaseAttack 修改
↓
FinalAttack 标记 Dirty
↓
PowerScore 标记 Dirty
↓
PowerUI 请求更新

此时并不一定立即重算，而是等到相应结果被使用时再计算。

五种方式的适用场景可以概括如下：

机制 判断依据 典型场景
主动失效 修改代码主动标记 游戏属性、本地缓存
版本号 源版本与缓存版本比较 配置、快照、异步结果
TTL 时间是否到期 网络请求、服务端缓存
事件驱动 收到变更通知 多模块状态同步
依赖驱动 依赖图中的上游节点变化 响应式 UI、增量计算

这些方式并不互斥。一个复杂系统完全可能同时使用事件、依赖图、版本号和 TTL。

六、How：依赖追踪究竟是怎么实现的？

我们已经知道依赖追踪要回答：

谁依赖谁？数据变化又应该通知谁？

真正的实现可以分成三种思路。

6.1 显式依赖：开发者直接声明

例如：

说明
FinalAttack:
    BaseAttack
    EquipmentBonus

PowerScore:
    FinalAttack
    Defense

可以将依赖信息保存在一个映射中：

C#
Dictionary<string, List<string>> dependents;

例如：

说明
dependents["BaseAttack"] = ["FinalAttack"]

dependents["FinalAttack"] = ["PowerScore"]

当 BaseAttack 改变，系统查找对应的下游节点，并逐步失效。

这里维护的是反向依赖索引：给我一个发生变化的节点，我就能查出所有直接受它影响的节点。

这种实现适合依赖关系清晰且相对稳定的场景。

但如果新增一个新的派生属性，开发者就需要同步维护依赖定义。

6.2 动态依赖：在数据读取时自动记录

这是响应式系统非常有意思的地方。

首先假设系统有一个全局的计算上下文：

说明
CurrentComputation = null

现在需要计算 FinalAttack：

说明
CurrentComputation = FinalAttack

执行计算时：

C#
int finalAttack = ReadBaseAttack()
                + ReadEquipmentBonus();

当调用 ReadBaseAttack() 时，系统发现：

说明
当前正在计算 FinalAttack

读取了 BaseAttack

于是自动建立依赖：

说明
BaseAttack → FinalAttack

接着读取装备加成：

说明
EquipmentBonus → FinalAttack

计算结束之后：

说明
CurrentComputation = null

这样一次实际计算就建立了依赖关系。

其本质不复杂：

在计算期间，记录它读取过哪些可观察数据。

这就是许多响应式系统中的 track() 思路。

当源数据变化，再通过 trigger() 找到对应订阅者。Vue 官方对其响应式系统的说明采用了这一模型。

不过，需要特别注意两个限制。

第一，只有被追踪机制观察到的读取才会建立依赖。读取普通字段、外部文件或者没有接入追踪机制的状态，并不会自动产生依赖记录。

第二，计算可能存在条件分支。因此重新计算时，需要更新当前依赖集合，而不是永远保留所有历史依赖。

例如之前的狂暴状态：

C#
if (player.IsBerserk)
    return player.BaseAttack * 2;

return player.BaseAttack + player.EquipmentBonus;

当狂暴状态开启以后，当前计算就可能不再需要装备加成。动态依赖系统通常会在重新计算时重建或核对订阅关系，避免旧依赖长期保留。

6.3 增量计算：只重新计算受影响的节点

这是依赖追踪与缓存结合后，真正强大的地方。

我们来看一个交互示例。

交互实验：依赖变化与缓存失效（模拟）

修改原始数据，观察哪些缓存需要重算。这里使用快照比较模拟缓存失效检测，方便观察变化。

缓存状态

最终攻击力150有效

战斗力1530有效

当前缓存与输入快照一致。

这个实验揭示了三件事。

首先，改变昵称不应该影响战斗属性的缓存。其次，改变防御力可以让战斗力缓存失效，但不需要让最终攻击力缓存失效。最后，改变基础攻击力，会通过依赖链间接影响战斗力。

注意，实验中的失效状态是通过当前值与缓存快照比较得出的，因此当数值恢复原值时，状态也会恢复为有效。真正采用 Dirty Flag 的系统，一旦标脏，通常会保持脏状态直到重新验证或计算。

这代表两种不同策略：基于快照的有效性验证与基于变化通知的保守失效。

七、How：在 Unity / C# 中应该怎样实现？

我们先不构建复杂的通用响应式框架，而是实现一个容易维护、能够保证基本正确性的玩家属性缓存。

7.1 实现一个手动依赖管理的缓存

C#
public sealed class PlayerStats
{
    private int _baseAttack;
    private int _equipmentBonus;

    // 派生结果的缓存
    private int _cachedFinalAttack;

    // 初始尚未计算
    private bool _attackDirty = true;

    public int BaseAttack
    {
        get => _baseAttack;

        set
        {
            if (_baseAttack == value)
                return;

            _baseAttack = value;

            InvalidateAttack();
        }
    }

    public int EquipmentBonus
    {
        get => _equipmentBonus;

        set
        {
            if (_equipmentBonus == value)
                return;

            _equipmentBonus = value;

            InvalidateAttack();
        }
    }

    public int FinalAttack
    {
        get
        {
            if (_attackDirty)
            {
                _cachedFinalAttack =
                    _baseAttack + _equipmentBonus;

                _attackDirty = false;
            }

            return _cachedFinalAttack;
        }
    }

    private void InvalidateAttack()
    {
        _attackDirty = true;
    }
}

使用方式：

C#
var player = new PlayerStats();

player.BaseAttack = 100;
player.EquipmentBonus = 50;

Debug.Log(player.FinalAttack); // 150
Debug.Log(player.FinalAttack); // 使用缓存 150

player.EquipmentBonus = 80;

Debug.Log(player.FinalAttack); // 重新计算 180
Debug.Log(player.FinalAttack); // 使用缓存 180

这个实现非常简单，但已经包含完整的核心流程：

步骤 动作 结果
1 首次读取 计算并缓存 150
2 再次读取 复用 150
3 修改装备 标记 Dirty
4 再次读取 计算并缓存 180
5 再次读取 复用 180

不过，我希望你注意：

这不是自动依赖追踪。

我们是通过开发者自己的知识，在 BaseAttack、EquipmentBonus 的 Setter 里手动维护失效关系。

系统本身并不知道 FinalAttack 依赖什么。

但对于大多数依赖关系明确、规模不大的游戏模块，这种方案通常比引入复杂的自动依赖框架更值得优先考虑。

7.2 Lua 中也是同一个思想

在你日常使用的 Lua 环境中，可以采用相同设计。

Lua
local PlayerStats = {}
PlayerStats.__index = PlayerStats

function PlayerStats.New()
    local self = setmetatable({}, PlayerStats)

    self.baseAttack = 100
    self.equipmentBonus = 50

    self._cachedAttack = 0
    self._attackDirty = true

    return self
end

function PlayerStats:SetEquipmentBonus(value)
    if self.equipmentBonus == value then
        return
    end

    self.equipmentBonus = value
    self._attackDirty = true
end

function PlayerStats:GetFinalAttack()
    if self._attackDirty then
        self._cachedAttack =
            self.baseAttack + self.equipmentBonus

        self._attackDirty = false
    end

    return self._cachedAttack
end

return PlayerStats

但是 Lua 有一个需要格外注意的问题。

如果外部代码这样做：

Lua
player.equipmentBonus = 200

就会绕过 SetEquipmentBonus()。

因此，业务层应该统一使用修改接口。如果需要更严格地限制直接访问，可以进一步设计私有状态和受控访问接口。

缓存的正确性依赖于数据修改入口是否被真正控制住，而不是依赖所使用的编程语言。

八、Unity 内部实际上也在运用这些思想

这里有两个特别值得你关注的实际案例。

8.1 Unity UI 的 Dirty 机制

Unity uGUI 的 Graphic 类里存在这些方法：

C#
SetLayoutDirty();
SetVerticesDirty();
SetMaterialDirty();

它们分别涉及布局、顶点和材质相关的重新构建需求。

例如，在官方 uGUI 源码中，SetVerticesDirty() 会将 m_VertsDirty 设置为 true，并向 CanvasUpdateRegistry 注册图形重建需求。

SetMaterialDirty() 也使用类似机制处理材质重建。

从概念上理解：

UI 属性改变
↓
对应计算结果可能失效
↓
SetVerticesDirty / SetMaterialDirty
↓
登记需要重建的 UI 元素
↓
在后续合适阶段处理重建

这里的核心思想是：

状态变化不等于立即重新执行所有昂贵操作。

而且布局、顶点、材质具有不同的失效范围。

这不是一个覆盖所有 UI 属性的通用自动依赖追踪系统，而是 Unity UI 根据已知依赖关系执行精细化失效管理的实例。

这也解释了为什么你阅读 Unity 源码时，会反复看到各种 Dirty、Rebuild、Register。

它们往往是在解决同一组问题：什么时候结果不再有效，以及怎样组织重新计算。

8.2 Unity AssetDatabase：一个更直接的依赖追踪实例

假设你修改了一张纹理。

Unity 需要重新处理受影响的资源，但并不需要重新导入整个工程。

而资源导入结果可能依赖：

  • 源资源文件。
  • Importer 的版本和导入配置。
  • 构建目标平台。
  • 其他被引用的资源。

Unity 的 AssetDatabase 会追踪静态与动态导入依赖。如果相关依赖变化，Unity 可以触发对应资源重新导入，更新其缓存的导入结果。

例如，源纹理、导入设置等输入，共同影响导入后的纹理资源，而导入结果进一步成为运行时可使用的资源：

其中，导入结果不只依赖源纹理的字节内容，还可能依赖压缩设置、目标平台等环境数据。

这说明一个非常值得记住的观点：

依赖不仅仅是另一个对象。任何可能影响结果的数据、配置或环境条件，都可能成为依赖。

九、更深一层：Cache Invalidation 与 Dependency Tracking 最困难的地方在哪里？

前面描述的机制在单线程的小型系统中很容易实现，但真正复杂的地方出现在正确性边界。

9.1 隐式依赖：你以为只依赖 A，实际上还依赖了 B

假设游戏 UI 需要显示一段文字：

C#
string GetDisplayText(int score)
{
    return Localize("score") + score;
}

开发者可能认为缓存只依赖 score。

但事实上，Localize() 的结果还可能依赖当前语言。

因此：

DisplayText = f(Score, Language)

如果语言从中文切换到英文，但缓存只监听 Score 的变化，UI 就可能继续显示中文。

同样的情况还包括主题、字体、屏幕尺寸、权限、配置版本、时区以及服务器数据。

这也提醒我们：

缓存依赖集合必须覆盖所有能够影响结果的输入，而不是仅仅覆盖函数表面上的参数。

特别是以时间、随机数、外部状态为输入的计算，不能仅凭普通变量读取来自动追踪完整依赖。

9.2 多层依赖：变化需要正确地传递

假设：

A → B → C → D

当 A 变化时，如果只把 B 标记为 Dirty，而 C、D 仍然认为自己有效，就可能继续返回旧结果。

因此，通常需要设计两种机制之一。

第一种是主动向下游传播失效，让所有可能受影响的节点都知道上游发生变化。

第二种是在读取派生节点时，递归验证上游节点及其版本，必要时再重算。

无论采用哪一种，都要保证读取结果之前，依赖链已经得到足够验证。

另外，依赖图如果出现循环，例如 A 依赖 B、B 又依赖 A，就不能直接进行普通的递归重算。需要禁止循环、明确求值顺序，或者专门设计固定点计算等算法。

9.3 异步计算：旧计算结果覆盖新计算结果

这是实际项目中很容易出现的 Bug。

想象以下执行顺序：

虽然我们在修改数据时已经让缓存失效，但旧的异步计算仍然可能在之后完成，并把旧结果写回来。

一种解决思路是给计算任务绑定版本号。

说明
任务开始：
    记录源数据版本 v1
    根据 v1 的状态计算

任务完成：
    检查当前版本

    如果仍然是 v1：
        可以尝试提交缓存

    如果已经是 v2：
        丢弃旧计算结果

但这里需要再深入一步：

仅仅检查版本还不一定足够，因为检查之后、真正写入缓存之前，源数据仍可能变化。

严格的解决方案需要保证版本检查和提交具有合适的原子性，例如通过锁、单线程调度、条件写入或其他同步机制完成。

而且，异步任务读取的多个源数据，也应该来自一致的快照，否则即便版本检查通过，计算时读到的状态也可能不一致。

这说明：版本号不只是判断缓存是否过期，还能够帮助控制异步计算结果的有效提交。

9.4 分布式缓存：修改数据与删除缓存之间存在竞态

在 Cache-Aside 模式中，典型写入流程是：

修改数据库
↓
使对应缓存失效

微软的 Cache-Aside 设计文档也建议先更新存储、再移除缓存；如果先移除缓存，读请求可能在数据库更新前把旧值重新放入缓存。

但即使先更新数据库再删除缓存，在并发情况下仍然可能发生旧读取请求较晚写回旧数据的竞态。

因此，高一致性系统可能还需要版本校验、条件写入、协调机制或其他一致性协议。

这也说明一件事：

在分布式系统中，缓存失效不再只是设置一个布尔变量，而是多个参与者之间的状态一致性问题。

9.5 依赖追踪本身也有成本

依赖图不是免费的。

它需要保存节点与边，需要在依赖关系变化时更新索引，还需要传播失效事件。

假设一个基础属性被 10000 个派生节点依赖，那么一次修改可能引发相当大的通知成本。

因此，实际系统需要考虑依赖粒度和传播策略。

比如：

  • 是否能够把多个变化合并到同一帧处理？
  • 是否有必要按字段追踪，而不是整个对象？
  • 不再使用的 UI 是否应该解除订阅？
  • 是否有必要立即更新所有下游节点？
  • 能否只在结果真正被读取时才重新计算？

特别是 Unity 中被销毁或复用的 UI 对象，如果没有正确清理事件订阅关系，可能造成无效回调、对象滞留等生命周期问题。

这与你之前学习的对象池状态隔离、所有权和生命周期管理有直接关联：依赖订阅关系本身也是一种需要维护生命周期的资源关系。

十、从架构角度重新理解这两个概念

你可以把整个机制分为四层。

Source of Truth（权威数据）

原始数据、配置、数据库状态

↓ 建立或验证依赖
Dependency Tracking（依赖追踪）

维护「谁依赖谁」的关系

↓ 识别受影响的节点
Cache Invalidation（缓存失效）

撤销旧结果的有效性

↓ 立即、按需或批量刷新
Recomputation（重新计算）

生成满足当前一致性要求的结果

这里应该再澄清一点：这四层是一种便于理解的逻辑分工，并不意味着软件必须按照这四层实现。

例如，基于 TTL 的缓存可以完全不维护依赖图；一个响应式事件系统也可以追踪依赖，却不缓存计算结果。

换句话说：

缓存与依赖追踪是两个正交能力。它们组合起来很强大，但并不相互依存。

我们可以将它们与其他几个概念统一起来：

概念 要回答的问题
Cache 哪些结果值得保存下来复用？
Dependency Tracking 哪些状态能够影响这个结果？
Cache Invalidation 哪些条件下不能直接复用旧结果？
Dirty Flag 怎样记录需要重新计算的状态？
Versioning 结果对应源数据的哪一个修订？
Lazy Evaluation 什么时候真正执行重新计算？
Incremental Computation 怎样避免重新计算未受影响的部分？
Reactive Programming 怎样让依赖变化自动驱动后续处理？

十一、真正掌握以后，应该怎样思考一个缓存设计？

当你未来需要设计一个缓存系统时，我建议不要先问「要不要使用 Dictionary、Dirty Flag 或事件」。

先问这六个问题：

  1. 权威数据是什么？ 缓存保存的是可再生的派生结果，还是系统中唯一的真实状态？
  2. 结果依赖什么？ 是否包含隐藏的配置、运行环境、时间或外部状态？
  3. 变化如何被观察？ 是统一 Setter、事件、版本校验、运行时依赖记录，还是只能通过 TTL 近似维护？
  4. 什么时候必须恢复一致？ 是修改后立即、下一次读取、下一帧，还是允许短暂过期？
  5. 怎样避免无关计算？ 需要字段级依赖、批量更新或懒计算吗？
  6. 怎样处理生命周期与并发？ 订阅何时解除，异步旧结果能否覆盖新结果，计算失败是否会错误地把缓存标记为有效？

这六个问题回答清楚以后，具体的实现方式往往就自然浮现了。

十二、最终总结：这两个概念真正的本质

我们可以把今天所讨论的内容压缩成三个核心认识。

第一，缓存的本质是对已有结果的有条件复用。

我们之所以可以跳过某次计算，是因为相信过去的结果在当前条件下仍然能够使用。

因此缓存失效，本质上是在维护这种信任的边界。

第二，依赖追踪的本质是对变化影响范围的建模。

它把隐含在计算逻辑中的数据依赖显式化，让系统能够从一个变化定位到可能受影响的结果。

第三，两者结合的本质是增量地维护系统的一致性。

我们并不希望每次状态变化都重新构建整个世界，而是希望只重新处理那些确实可能受到影响的部分。

把它们放到你已经学过的架构知识里看，会出现一条非常清晰的脉络：

  • 不变量定义了什么必须保持正确。
  • 状态转移描述了系统如何发生变化。
  • 依赖追踪识别变化的影响范围。
  • 缓存失效阻止系统继续信任可能不正确的旧结果。
  • 增量计算以尽可能低的成本恢复所需的一致性。

最终可以归结为一句话：

Dependency Tracking 负责知道「谁可能受到影响」，Cache Invalidation 负责决定「哪些旧结果不能继续被信任」，而重新计算负责「在需要时恢复正确结果」。

如果继续深入，我建议下一步学习 Incremental Computation（增量计算）与 Reactive Programming（响应式编程），尤其是依赖图传播、拓扑排序、脏标记调度和批量更新。它们能将今天讨论的缓存机制，进一步扩展成一个完整的状态驱动计算系统。

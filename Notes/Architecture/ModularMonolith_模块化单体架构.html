Modular Monolith 的核心思想：在不把系统拆成多个独立服务的前提下，把一个大型程序组织成多个具有明确职责、边界和对外接口的模块。

它试图解决一个本质的软件工程问题：

随着系统功能不断增加，如何让局部功能的变化，尽可能不影响系统的其他部分？

下面按照 What → Why → How → 设计权衡 → C# 游戏服务端实践，逐层展开。

01What：什么是 Modular Monolith？

首先拆解名称：

  • Modular： 模块化，把系统组织成具有明确职责和边界的模块。
  • Monolith： 单体，整个应用作为一个整体构建和部署。

因此：Modular Monolith = 模块化的内部结构 + 单体化的部署方式。

模块与单体描述的是两个不同维度。

1. 单体 Monolith 到底是什么？

假设开发一个游戏服务端，包含 Inventory（背包）、Achievement（成就）、Statistics（统计）和 Shop（商店）。最开始，把它们全部放在一个服务端应用里。

一个服务端应用，一次整体部署；数据库可以是一个，也可以是多个。这是典型的单体部署结构。

单体本身并不意味着代码混乱。 一个单体程序完全可以具有优秀的类设计、接口设计和模块设计。Monolith 描述部署和运行边界，不是低质量代码的代名词。

图示的是单个应用实例；单体应用也可以整体部署多个副本，并不意味着整个系统永远只能运行一个进程。

2. 模块 Module 到底是什么？

以 InventoryModule 为例，它负责背包领域中的规则：玩家获得道具、消耗道具、判断容量、管理当前拥有的物品。

模块是一个拥有明确职责、管理自己内部状态与规则，并通过受控接口与外界交互的软件单元。

外部通过公开契约交互，不能随意访问内部数据与实现。一个模块不一定只有一个 Class，也不一定对应一个 DLL。

模块的本质不是文件夹，而是被维护和执行的职责边界。

3. 什么才算真正的模块化？

有文件夹但没有边界时，各模块仍然随意调用内部方法、访问数据，修改一个功能可能波及其他功能。具有受控边界时，模块通过公开接口合作，内部实现不成为其他模块的依赖。

模块化不要求模块完全不依赖其他模块。它要求：依赖有明确方向，而且通过被允许的边界。

这与未严格模块化的单体的区别，不是物理拆分本身，而是是否建立并维护这些约束。

02Why：为什么需要 Modular Monolith？

1. 根本问题：软件的复杂度如何随规模增长？

只有两个功能时：

Inventory
Statistics

关系可能很简单。随着功能增加：

Inventory
Statistics
Achievement
Quest
Shop
Mail
Battle
Economy
Social

如果每个系统都能直接修改其他系统的内部状态，依赖关系可能迅速增加。

假设 N 个模块之间每对都可以建立一条直接关系，潜在模块对数量为：

E = N(N − 1)2
模块数量 潜在模块对数量
5 10
10 45
20 190
50 1,225

这里计算的是无向的潜在模块对，不是实际依赖数量，也不是所有项目都会达到这个数量。若分别计算两个方向的依赖，上界模型也会不同。

它反映的是：随着规模增加，真正难管理的往往不是代码数量，而是代码之间的关系。

2. 耦合 Coupling：变化为什么会传播？

看一段游戏服务端代码：

ShopService · 直接耦合反例.NET / C# · 机制片段，非完整工程
public class ShopService
{
    public void BuyItem(Player player, int itemId)
    {
        player.Coins -= 100;

        player.Inventory.Items.Add(itemId);

        player.Statistics.TotalPurchases++;

        player.Achievements.UpdatePurchaseProgress();

        player.Quests.CheckPurchaseQuest();
    }
}

短期内它直观且可能正常运行，但商店直接了解并操作了多个系统的内部数据。

  • 背包改成堆叠存储，商店可能需要修改。
  • 成就系统改变进度计算方式，商店可能需要修改。
  • 统计记录需要持久化或额外检查，商店可能还要修改。

一个系统内部实现的变化，迫使另一个系统跟着变化。

这是耦合造成的维护成本之一。但耦合不能完全消除：只要功能需要合作，就存在某种依赖。架构要做的是控制依赖的范围和形式。

3. Modular Monolith 如何解决？

可以改成通过公开能力协作：

ShopService · 契约调用片段.NET / C# · 机制片段，非完整工程
public class ShopService
{
    private readonly IInventoryCommands _inventory;
    private readonly IStatisticsCommands _statistics;

    public async Task BuyItemAsync(
        Guid playerId,
        int itemId,
        CancellationToken ct)
    {
        // 付款校验与原子事务管理暂时省略

        await _inventory.GrantAsync(
            playerId, itemId, 1, ct);

        await _statistics.RecordPurchaseAsync(
            playerId, ct);
    }
}

商店不再知道背包用数组、字典、数据库表还是其他结构保存。它只知道：

GrantAsync · 调用示意.NET / C# · 机制片段，非完整工程
_inventory.GrantAsync(...)

这个操作请求背包模块授予物品。只要契约稳定，背包内部实现变化通常不要求商店一起改变。这是**信息隐藏（Information Hiding）**的作用。

上面的代码只演示模块交互，尚未处理购买原子性、并发与幂等；构造注入与相关接口也未完整列出。RecordPurchaseAsync 是购买统计的概念接口，后文 RecordObtainedAsync 属于获得道具场景；不要把这些独立片段直接拼成一个工程。

4. 本质：限制变化的影响范围

模块化单体不会消除复杂度与所有耦合。它希望做到：

  • 内部实现可以演化。
  • 公开契约尽可能稳定。
  • 其他模块依赖能力，而不是实现细节。
  • 减少变化向其他模块传播。

这不是 Modular Monolith 独有的思想，却是其重要基础。Shopify 曾公开介绍在大型单体内按业务领域建立边界的实践：缺少模块边界，不必总通过拆成分布式服务来解决。Shopify：Deconstructing the Monolith

03How：如何设计一个 Modular Monolith？

难点不在于创建几个项目，而在于：模块如何划分、暴露哪些能力、如何调用、数据由谁管理、跨模块操作如何保证一致性。

1. 根据业务能力划分模块，而不只是技术类型

模块 拥有什么 负责什么
Inventory 当前拥有的道具 获得、消耗、查询背包
Statistics 累计统计记录 记录获得总数、比赛次数等
Achievement 成就进度与领取状态 判断成就完成及奖励领取
Shop 商品和购买规则 商品定价、购买条件等
Rewards 奖励发放流程 组织奖励请求、避免重复发放

关键是数据与业务规则的归属：

Inventory
    CurrentItemCount = 5

Statistics
    TotalObtainedCount = 100

当前数量是背包的状态，累计获得数量是统计的状态。它们可以因同一件事变化，但不意味着必须由同一个模块管理。

划分也不必一一对应。如果两个功能始终共同变化、规则高度耦合，放在同一个模块可能更合理。依据应是业务职责、规则和变化原因，而不是每张表都建一个模块。

2. 定义公开契约 Contracts

以背包为例：

IInventoryCommands · 公开契约.NET / C# · 机制片段，非完整工程
namespace Game.Inventory.Contracts;

public interface IInventoryCommands
{
    Task GrantAsync(
        Guid playerId,
        int itemId,
        int amount,
        CancellationToken ct);

    Task ConsumeAsync(
        Guid playerId,
        int itemId,
        int amount,
        CancellationToken ct);
}

外部可以提出授予、消耗请求，但不能直接修改背包内部集合。内部则维护自己的规则：

InventoryDomain · 内部规则.NET / C# · 机制片段，非完整工程
namespace Game.Inventory;

internal sealed class InventoryDomain
{
    private readonly Dictionary<int, int> _items = new();

    public void Grant(int itemId, int amount)
    {
        if (amount <= 0)
            throw new ArgumentOutOfRangeException(nameof(amount));

        _items.TryGetValue(itemId, out int current);
        _items[itemId] = checked(current + amount);
    }
}

这是简化的内部领域逻辑，暂不涉及持久化与并发。internal 限制类型在程序集之外的可见性：

Inventory.Contracts
    IInventoryCommands     public

Inventory
    InventoryDomain        internal
    InventoryRepository    internal
    InventoryCommands      internal

其他模块只依赖契约，不需要了解领域对象如何组织。若多个模块位于同一程序集，internal 无法在它们之间形成隔离；应结合程序集、引用规则与架构测试维护边界。Microsoft：internal

3. 模块之间可以调用，但需要遵守边界

例如，Rewards 协调发放奖励，调用 Inventory API 和 Statistics API，而不依赖它们的内部类。统计模块提供：

IStatisticsCommands · 公开契约.NET / C# · 机制片段，非完整工程
namespace Game.Statistics.Contracts;

public interface IStatisticsCommands
{
    Task RecordObtainedAsync(
        Guid playerId,
        int itemId,
        int amount,
        CancellationToken ct);
}

模块之间可以直接调用并等待结果，不需要把所有操作都变成事件。这里的 Task/await 可以承载异步 I/O，但仍是调用方明确等待被调用方结果的交互。

模块化和事件驱动，是两个不同维度的设计选择。

04C# 实践：一次获得道具，同时更新背包与统计

客户端发来一个请求：

GrantItem
    PlayerId = A
    ItemId = 1001
    Amount = 5
    RequestId = XYZ

业务要求：背包增加五个道具，累计数量增加五；同一请求重试不能重复发放；关键步骤失败时不能只保存一半。

模块可以各自管理职责，但某个共同业务操作仍然可能需要一个共同事务。本节假设这是已通过授权和业务可领取校验的奖励操作，不能让客户端自由决定发奖权限。

2. 奖励模块负责协调业务流程

RewardService · 协调流程.NET / C# · 机制片段，非完整工程
internal sealed class RewardService
{
    private readonly IInventoryCommands _inventory;
    private readonly IStatisticsCommands _statistics;
    private readonly IRewardRequestStore _requests;
    private readonly ITransactionRunner _transactions;

    public RewardService(
        IInventoryCommands inventory,
        IStatisticsCommands statistics,
        IRewardRequestStore requests,
        ITransactionRunner transactions)
    {
        _inventory = inventory;
        _statistics = statistics;
        _requests = requests;
        _transactions = transactions;
    }

    public Task GrantItemAsync(
        Guid playerId,
        Guid requestId,
        int itemId,
        int amount,
        CancellationToken ct)
    {
        if (amount <= 0)
            throw new ArgumentOutOfRangeException(nameof(amount));

        return _transactions.ExecuteAsync(async token =>
        {
            // 尝试登记本次业务请求
            bool isNew = await _requests.TryInsertAsync(
                playerId, requestId, itemId, amount, token);

            if (!isNew)
            {
                // 相同 RequestId 必须代表相同业务请求
                bool matches = await _requests.MatchesAsync(
                    playerId, requestId, itemId, amount, token);

                if (!matches)
                    throw new InvalidOperationException(
                        "RequestId was reused with different parameters.");

                // 已完成的相同请求：直接作为成功处理
                return;
            }

            // 背包模块负责背包变化
            await _inventory.GrantAsync(
                playerId, itemId, amount, token);

            // 统计模块负责累计记录
            await _statistics.RecordObtainedAsync(
                playerId, itemId, amount, token);

        }, ct);
    }
}

IRewardRequestStore 是奖励模块内部的数据访问契约，负责持久化请求记录，并核对重复请求的参数。

组件 它知道什么 它不知道什么
Rewards 本次奖励要完成哪些操作 背包和统计如何存储
Inventory 如何正确增加道具 奖励流程的其他步骤
Statistics 如何维护累计数据 完整的道具发放流程
TransactionRunner 如何提交、回滚事务 什么是背包、统计、奖励

高内聚： 同一职责的规则尽量放在一起。低耦合： 尽量少了解其他模块的内部细节。

3. 事务应该如何实现？

ExecuteAsync 不能只是普通的回调包装器，必须提供真实数据库事务。使用 PostgreSQL 时，可以让同一请求作用域内的模块使用同一连接与事务。

ITransactionRunner · 事务契约.NET / C# · 机制片段，非完整工程
public interface ITransactionRunner
{
    Task ExecuteAsync(
        Func<CancellationToken, Task> action,
        CancellationToken ct);
}
PgTransactionRunner · 事务核心机制.NET / C# · 机制片段，非完整工程
public sealed class PgTransactionRunner : ITransactionRunner
{
    private readonly PgSession _session;

    public PgTransactionRunner(PgSession session)
    {
        _session = session;
    }

    public async Task ExecuteAsync(
        Func<CancellationToken, Task> action,
        CancellationToken ct)
    {
        await _session.Connection.OpenAsync(ct);

        await using var transaction =
            await _session.Connection.BeginTransactionAsync(ct);

        _session.CurrentTransaction = transaction;

        try
        {
            await action(ct);

            await transaction.CommitAsync(ct);
        }
        catch
        {
            await transaction.RollbackAsync(
                CancellationToken.None);

            throw;
        }
        finally
        {
            _session.CurrentTransaction = null;
        }
    }
}

PgSession 是请求作用域内的会话封装，包含 NpgsqlConnection 与当前 DbTransaction。背包、统计和请求记录仓储必须使用同一个会话及事务。Npgsql：Transactions

本例假设入口连接尚未打开、没有嵌套事务。它省略了会话创建释放、DI 注册、完整异常恢复与嵌套处理，展示核心机制，不是完整生产实现。真实实现还应处理连接状态、回滚异常、提交结果不确定及相应重试策略，不能仅凭方法名假设这些能力已经存在。

模块分别执行自己的 SQL：

Inventory · 增加当前数量PostgreSQL · 参数化 SQL 片段，需补充表结构与约束
-- Inventory 模块自己的数据
INSERT INTO inventory.player_items
    (player_id, item_id, quantity)
VALUES
    (@playerId, @itemId, @amount)
ON CONFLICT (player_id, item_id)
DO UPDATE SET
    quantity = player_items.quantity + EXCLUDED.quantity;
Statistics · 增加累计数量PostgreSQL · 参数化 SQL 片段，需补充表结构与约束
-- Statistics 模块自己的数据
INSERT INTO statistics.item_totals
    (player_id, item_id, total_obtained)
VALUES
    (@playerId, @itemId, @amount)
ON CONFLICT (player_id, item_id)
DO UPDATE SET
    total_obtained =
        item_totals.total_obtained + EXCLUDED.total_obtained;

SQL 由所属模块实现，RewardService 不应直接写其他模块的表。示例使用 Npgsql 支持的命名参数，不是可直接粘贴进数据库控制台的完整脚本。

rewards.requests 应有 (player_id, request_id) 唯一约束。TryInsertAsync 通过冲突安全的插入判断是否首次处理，并把参数记录放在同一事务中。唯一性竞争由数据库处理，不能只靠“先查询，再插入”。

仓储 SQL、隔离级别、等待后的可见性及必要的事务重试也必须正确实现；接口声明本身不保证并发幂等。参见 PostgreSQL：INSERT / ON CONFLICT 与 Transaction Isolation。还需按业务补充数量约束、容量检查与其他并发保护。

4. 原子性和模块化是否冲突？

不冲突：

只要全部数据变更真正参加同一个支持事务的数据库事务，即使业务属于不同模块，也可以获得其原子性保证。这通常比跨微服务协调独立数据库更直接。PostgreSQL：Transactions

三个前提不可忽略：

  1. 操作真正加入同一事务，而不是各模块独立保存。
  2. 多个数据库不能假设由普通的单数据库事务覆盖。
  3. 原子提交不等于永远不丢数据；持久性、备份、硬件故障与运维仍需单独处理。

05跨模块调用：接口还是事件？

“低耦合是不是全部使用事件最好？”答案是不一定。

1. 同步调用

模块接口 · 等待业务结果.NET / C# · 机制片段，非完整工程
await inventory.GrantAsync(...);
await statistics.RecordObtainedAsync(...);

适合流程必须知道结果、需要协调事务的情况。代价是模块间存在明确的执行依赖。这里“同步协作”指业务上等待结果，不代表底层 I/O 必须阻塞线程。

2. 事件通知

事件发布 · 交互片段.NET / C# · 机制片段，非完整工程
await inventory.GrantAsync(...);

await eventBus.PublishAsync(
    new ItemObtainedEvent(playerId, itemId, amount));

Statistics 订阅事件，奖励流程不必直接认识它。但还要回答：

  • 背包保存成功，事件发布失败怎么办？
  • 统计处理失败怎么办？
  • 事件重复处理怎么办？
  • 事件延迟时，统计是否允许暂时不一致？

可靠异步事件通常需要考虑 Transactional Outbox、持久化消息、重试与幂等消费。

需求 更直接的设计选择
道具与累计获得数量必须一起成功 同一数据库事务内协调两个模块
发送获得道具的通知 可使用异步事件
更新非关键展示统计 可考虑异步投影
必须立即获得业务结果 直接调用并等待结果通常更直接
可靠跨数据库通信 Outbox、消息处理、补偿等机制

即使使用事件，也可在同一事务中由同步处理器更新统计。事件不天然意味着异步或最终一致性。 Modular Monolith 不规定唯一通信方式。

06设计权衡：普通单体、模块化单体与微服务

维度 普通单体（未严格模块化） 模块化单体 微服务
部署 通常整体部署 整体部署 各服务可独立部署
内部边界 可能松散 有意维护明确边界 通过服务接口建立边界
通信 直接方法调用常见 受控的进程内调用 通常需要网络通信
数据管理 容易共享模型与表 强调数据归属 通常强调独立数据所有权
跨模块事务 较容易协调 同库场景较容易协调 通常更复杂
单模块独立部署扩容 不支持 不支持 可以支持
故障隔离 较弱 进程级隔离仍较弱 可具有更强隔离
运维复杂度 相对较低 相对较低 通常较高

这里“普通单体”是比较用语，特指未认真维护模块边界的单体，并非独立的严格标准。单体仍可整体横向扩容；表中讨论的是模块能否独立部署扩容。

优势

用相对简单的运行与部署模型，获得模块化设计的可维护性收益。

模块在同一进程内，方法调用通常低延迟，调试与测试较直接。业务演化时可以先调整边界，不必立刻承担服务间协议、独立部署和分布式事务。

Martin Fowler 在 Monolith First 中讨论过：业务边界尚不稳定时，先在单体内探索边界，有时比起步就拆微服务更合理。Martin Fowler：Monolith First

局限

  1. 共享进程。 严重错误、内存占用或关键资源阻塞，可能影响整个应用。
  2. 整体部署。 只改一个模块，通常仍要构建并部署整体服务端。
  3. 主动维护边界。 为方便直接引用内部实现，可能使架构退化。
  4. 过度模块化有成本。 小功能却需要很多程序集、接口与适配，可能降低效率。

目标不是模块数量最多、依赖数量最少，而是职责划分合理。

07Unity 中如何应用？

Unity 客户端也可以借鉴模块化思想，用 Assembly Definition 建立程序集级依赖边界：

Game.Inventory.Contracts.asmdef
Game.Inventory.Runtime.asmdef
Game.Shop.Runtime.asmdef
Game.Statistics.Runtime.asmdef

商店引用背包契约，而不是直接依赖内部实现。Unity：Assembly definitions

  • MonoBehaviour 衔接场景对象与 Unity 生命周期。
  • 领域类管理核心规则。
  • 公开接口负责不同功能之间的协作。
  • Composition Root（组合根）装配接口与实现。

背包界面不应直接读取商店内部结构，商店界面也不应直接修改背包内部集合。

要区分客户端模块化组织代码，与服务端数据库事务维护一致性这两类问题。前面的 PostgreSQL、Npgsql、文件作用域命名空间是 .NET 服务端示例；迁入 Unity 前需要按项目语言版本和运行环境调整，不能当作完整客户端脚本直接使用。

Modular Monolith 与 ECS、DDD、Clean Architecture 也并不天然冲突，可以在明确职责和范围的前提下组合。

09直达本质：Modular Monolith 真正控制的是什么？

软件各部分必然存在联系并需要合作。问题是：当一个部分变化时，其他部分是否必须跟着变化？

Modular Monolith 的设计答案是：

  1. 按职责划分模块： 让密切相关的状态与行为聚集。
  2. 通过契约约束依赖： 隐藏内部细节，限制变化传播。
  3. 保持单体部署： 不为逻辑隔离过早承担分布式运维成本。

通过明确的业务边界和受控依赖限制软件变化的影响范围，同时保留单体系统在部署、调试与事务协调上的简单性。

值得继续追问的不是先加更多项目，而是：为什么拆成不同类、文件夹甚至程序集后，仍可能没有真正模块化？

答案会深入到：高内聚（Cohesion）、低耦合（Coupling）、信息隐藏（Information Hiding）与模块边界（Module Boundary）。

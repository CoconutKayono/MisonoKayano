行为的本质。

在特定条件下，如何响应、做什么、产生什么结果。

Behaviour7 个主题Unity C# 示例离线行为示意

行为不只是“做一个动作”。
它描述系统在各种条件下，如何运作和响应。

STATE / 状态现在是什么样
BEHAVIOUR / 行为会如何运作
TRANSITION / 转移状态发生了什么改变

先给出一个核心定义：

行为（Behaviour）的本质，是一个事物在特定条件下，如何响应、做什么，以及产生什么结果。

更抽象地说：

状态（State）描述一个事物现在是什么样。

行为（Behaviour）描述一个事物会如何运作。

转移（Transition）描述一个事物从一个状态变成另一个状态。

这三个概念不是孤立的。理解它们的关系，是理解行为的关键。

01What：行为究竟是什么？

先不谈编程。假设我们有一扇门，它可能处于三种状态：

  • 关闭（Closed）
  • 打开（Open）
  • 锁定（Locked）

这扇门可以表现出一些行为：打开（Open）、关闭（Close）、上锁（Lock）、解锁（Unlock）。

相同的行为，面对不同的状态，产生不同的结果。

因此，行为不只是一个动作，更重要的是它背后的响应规则。可以抽象为：

(S, I)B⟶(S′, O)
符号 含义
S 当前状态（State）
I 输入（Input），也可以是触发条件
B 行为（Behaviour）
S′ 行为执行后的状态
O 输出或产生的结果（Output）

这是一个简化的行为模型。它表达的是：行为规定了系统在当前状态下，遇到输入时应该如何响应。

行为不一定改变状态。例如查询余额、拒绝开门，也可以构成行为。对于连续运动、异步任务等，行为还可能依赖时间和历史输入。

02Why：为什么需要行为这个概念？

想象游戏中存在一个玩家。我们可以描述他的状态：

玩家状态 · 字段片段C# · 示意片段，需置于相应上下文
int health = 100;
int maxHealth = 100;
bool isDead = false;

这些数据回答了：玩家目前有多少生命值？玩家是否死亡？

但是数据本身无法回答：

  • 玩家受到伤害时应该发生什么？
  • 生命值能不能低于零？
  • 死亡后还能否继续受到伤害？
  • 什么时候应该触发死亡？

这些问题属于行为规则。例如：

TakeDamage · 方法片段C# · 示意片段，需置于相应上下文
public void TakeDamage(int damage)
{
    if (isDead)
        return;

    if (damage <= 0)
        return;

    health = Mathf.Max(0, health - damage);

    if (health == 0)
        isDead = true;
}

TakeDamage 表达了玩家受到伤害时的规则。这就是为什么软件设计不仅需要状态，也需要行为。

如果只有状态而没有行为规则，任何代码都可能随意修改生命值：

任意修改状态 · 反例C# · 示意片段，需置于相应上下文
player.health = -500;
player.isDead = false;

最终可能出现生命值为负数却仍然存活的矛盾。这个反例假设字段允许外部写入；真实对象可通过访问控制与受控方法保护约束。

把规则集中到行为中，就可以维护约束。行为的重要价值，是把一个事物允许做什么、在什么条件下做、产生什么结果，组织成明确的规则。

这也是面向对象设计强调把数据与行为放在一起的原因之一。

03How：如何设计一个行为？

一个实用的思考方式是回答四个问题：

  1. 触发（Trigger）： 什么引起行为？
  2. 条件（Condition）： 什么情况下允许执行？
  3. 执行（Execution）： 具体如何处理？
  4. 结果（Result）： 最终产生什么变化或输出？

还是使用门的例子：

用 Unity C# 实现：

DoorController.csUnity C# · MonoBehaviour 完整脚本
using UnityEngine;

public enum DoorState
{
    Closed,
    Open,
    Locked
}

public class DoorController : MonoBehaviour
{
    [SerializeField] private Animator animator;

    public DoorState State { get; private set; }
        = DoorState.Closed;

    // 行为：尝试打开门
    public bool TryOpen()
    {
        // 条件
        if (State != DoorState.Closed)
            return false;

        // 状态转移
        State = DoorState.Open;

        // 对外效果
        if (animator != null)
            animator.SetBool("IsOpen", true);

        return true;
    }

    // 行为：尝试关闭门
    public bool TryClose()
    {
        if (State != DoorState.Open)
            return false;

        State = DoorState.Closed;

        if (animator != null)
            animator.SetBool("IsOpen", false);

        return true;
    }
}

这里可以识别出三个不同层次：

  • DoorState：门拥有的状态。
  • TryOpen()：规定如何响应开门请求的行为。
  • Closed → Open：成功开门后发生的状态转移。

Animator 负责播放动画，这是行为产生的一种外部效果。实际项目也可以将表现逻辑与门的业务规则进一步分离。

使用时将完整代码保存为 DoorController.cs，挂到门的 GameObject 上。如果配置 Animator，需要在 Animator Controller 中设置名称一致的布尔参数 IsOpen，并配置由它控制的动画转换。SetBool 设置参数，不代表动画已经播放完成。参见 Unity：Animator.SetBool。

本例只实现 TryOpen 和 TryClose，枚举中的 Locked 用于说明状态约束，没有实现上锁、解锁方法。返回 true 表示方法接受请求并完成了这里定义的状态更新；即使没有配置 Animator，也能返回成功。

与前几份示例放在同一 Unity 工程时，注意它们都定义了 DoorState。应使用不同命名空间，或按需要复用同一个定义，避免同名类型重复。

04Behaviour、Action、Transition、Event 到底有什么不同？

概念 它回答的问题 举例
State（状态） 现在是什么情况？ 门处于关闭
Behaviour（行为） 在各种情况下会如何响应？ 尝试开门时先检查是否处于 Closed，再决定结果
Action（动作） 执行什么具体操作？ 播放开门动画
Transition（转移） 状态发生了什么改变？ Closed → Open
Event（事件） 发生了什么值得记录或通知的事情？ DoorOpened

这些概念有关联，却不能简单地互相替代。

行为不等于状态转移

尝试开门失败仍然是一次行为响应，但状态没有改变。

行为不等于方法（Method）

方法是编程语言提供的代码组织机制；行为是系统语义上的运作方式。一个行为可以由多个方法协作实现，而一个方法也可能包含多个行为。

行为不等于事件

事件主要用于表示某件事情发生了，可以用于通知其他系统。行为则规定如何处理输入、条件及后果。

这里的 DoorOpened 是结果事件的概念示例；上面的最小代码没有声明或发送这个事件。若其他系统需要订阅，再显式增加通知机制。

05更深入：行为其实是系统在时间中的表现

假设我们观察一个角色：

如果把时间定格在 t2，你只能知道：

角色现在处于 Jump 状态。

但是如果观察整个过程，你才知道：

角色如何从静止开始奔跑、跳跃，再进入下落。

这就是状态和行为之间更深层次的关系：

状态是对某个时刻的描述；行为可以理解为系统随时间表现出来的响应规律。

一套行为规则配合初始状态和外部输入，会决定系统可能展现出什么样的状态变化和输出序列。

这也是为什么状态机（State Machine）非常适合建模游戏角色的行为：它可以明确规定各个状态下允许发生哪些转移，以及执行哪些效果。

不过状态机只是建模行为的一种方法，并不是所有行为都必须使用状态机。

06Unity 的 Behaviour 是什么意思？

Unity 中还存在一个名字就叫 Behaviour 的类。它的继承关系是：

UnityEngine.Object
    └── Component
          └── Behaviour
                └── MonoBehaviour

Unity 的 Behaviour 是一种引擎 API 类型，主要提供组件启用、禁用等能力。参见 Unity：Behaviour。

例如：

组件启用开关 · 调用片段C# · 示意片段，需置于相应上下文
playerController.enabled = false;

这可以禁用该 MonoBehaviour 组件，影响 Unity 对它的启用状态与更新调度。enabled 的意义见 Unity：Behaviour.enabled。

但 Unity 的 Behaviour 类，并不是对所有“行为”的统一理论定义。

你可以使用 MonoBehaviour 实现行为，也可以使用普通 C# 类、状态机、行为树等方式组织行为。

组件的启用开关也不等于给每个公共方法自动添加业务前置条件。如果某个业务方法只允许在组件启用时接受调用，需要明确设计相应条件。

07最终回归本质

可以把整个概念压缩到三个层次：

State：系统有什么

这里的“有什么”，指系统当前保留的状态信息，也就是“现在是什么样”。

Behaviour：系统如何运作
Transition：系统如何改变状态

行为不是简单的“做了一个动作”，而是一套决定系统如何响应和表现的规则。

设计任何一个行为时，最核心的思考不是“我要写哪个方法”，而是：

当什么事情发生时，在什么条件下，这个对象应该如何响应，产生什么结果，并且必须遵守哪些约束？

一旦这个问题明确了，代码里的方法、状态机、事件、组件，才有了真正清晰的职责。

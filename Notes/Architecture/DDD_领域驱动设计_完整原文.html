DDD（Domain-Driven Design，领域驱动设计）

What · Why · How · 设计权衡 · C# / 游戏服务端实践

DDD 是软件架构中非常值得深入理解的一种设计思想。

它与之前学习的 Modular Monolith、Clean Architecture、Hexagonal Architecture 有一个重要区别：

DDD 首先关心的不是代码如何分层、接口如何抽象，而是我们是否正确理解了要解决的业务问题，以及软件是否准确表达了这些业务规则。

先用一句话直达本质：

DDD 是一种以业务领域模型为中心的软件设计方法。它通过持续理解业务、建立共同语言、划分模型边界，并让业务规则体现在软件模型中，来管理复杂业务系统的复杂性。

它的核心不是 Entity、Repository、Aggregate 这些类应该怎么写，而是：

软件的结构和行为，应当反映业务本身的概念、规则和边界。

Eric Evans 的《Domain-Driven Design》系统化提出了这套方法。Martin Fowler 也强调，DDD 特别适合需要组织大量复杂业务规则的系统。

一、What：DDD 到底是什么？

首先理解三个词。

1. Domain：领域是什么？

领域（Domain）就是软件试图解决的某个业务问题范围。

例如你要开发一个游戏。

游戏中可能存在：

  • 背包与道具。
  • 战斗与伤害。
  • 成就和任务。
  • 商店和交易。
  • 玩家进度。
  • 排名与匹配。

这些都是游戏业务中的不同问题范围。

假设我们研究的是“玩家获得道具”。

看起来似乎只是：

TEXT
inventory[itemId] += amount;

但真正的业务问题可能包括：

  • 玩家是否有资格获得该道具？
  • 是新增一个道具实例，还是增加堆叠数量？
  • 道具是否有持有上限？
  • 同一奖励能否重复领取？
  • 发放成功后是否记录累计获得数量？
  • 背包保存成功、统计保存失败怎么办？
  • 同一个请求被客户端发送三次怎么办？

这些问题不是 C#、SQL 或 Unity 自动替你解决的。

它们是业务领域本身的规则。

DDD 希望我们首先理解这些规则，然后再决定如何将其变成软件。

2. Model：模型是什么？

模型（Model）是对现实业务进行有目的的抽象。

它并不是现实世界的完整复制品。

例如：

TEXT
public sealed class Inventory
{
    public void Grant(ItemId itemId, int amount)
    {
        // 根据背包规则发放道具
    }
}

这个 Inventory 是一个领域模型的一部分。

它没有描述真实背包的材质、形状或重量，而是表达软件所关心的业务概念和规则。

更重要的是，领域模型不等于数据结构。

一个只有数据的类：

TEXT
public class InventoryData
{
    public Dictionary<int, int> Items = new();
}

确实能够表示部分背包数据。

但它还没有表达：

  • 怎样合法地增加道具？
  • 怎样消耗道具？
  • 哪些操作被禁止？
  • 必须维护什么不变量？

如果这些规则全部散落在 UI、ShopService、RewardService 等地方，就很难形成一个有凝聚力的业务模型。

DDD 中的模型既包括数据概念，也包括行为、规则、关系、约束和业务语言。

3. Driven：什么叫驱动？

这里的“驱动”意味着：

用不断演化的领域模型指导代码结构和设计决策，而不是先由数据库表、框架或通用类结构决定业务应该如何组织。

比较两种开发思路。

技术结构先行

设计数据库表

生成数据类与 CRUD

将业务规则分散到各种 Service

领域模型驱动

理解业务场景与规则

建立业务概念、行为和边界

用代码与持久化实现领域模型

这不是说 DDD 禁止先设计数据库，也不是 CRUD 就一定不好。

区别在于：当业务规则非常复杂时，数据库结构不应该成为理解和表达业务的唯一模型。

二、Why：为什么需要 DDD？

1. 根本问题：技术结构正确，业务仍然可能错误

假设我们已经使用：

  • Clean Architecture。
  • 依赖注入。
  • Repository。
  • 数据库事务。
  • 高内聚、低耦合。

架构看起来很漂亮。

但代码是这样的：

TEXT
public void ClaimReward(Player player, int rewardId)
{
    if (player.Level >= 10)
    {
        player.Inventory.Add(1001, 5);
    }
}

技术上没有什么特别复杂的问题。

但真实的业务要求可能是：

玩家等级达到 10 级后，可以领取一次等级奖励。已经领取过的奖励不可以重复领取。

现在代码只验证了等级，却没有验证是否领取过。

再调用一次：

TEXT
ClaimReward(player, rewardId);

就会重复获得奖励。

这不是架构层次的问题，而是业务规则建模不完整。

Clean Architecture 可以让这段代码不依赖数据库。

依赖倒置可以让它不依赖具体背包实现。

但这些技术并不能自动告诉你：

“等级奖励只允许领取一次。”

这个规则必须通过理解业务才能得到。

DDD 就是把这种业务知识当作设计的中心。

2. 业务复杂度来自规则之间的关系

假设只有一条规则：

TEXT
玩家达到 10 级可以领奖。

很容易实现。

后来新增：

TEXT
达到 10 级才能领取。
每个等级奖励只能领取一次。
奖励必须根据奖励配置发放。
领取成功后更新任务。
部分道具需要检查容量。
领取过程中失败必须保证正确性。
管理员可以补发奖励。

规则开始出现组合和例外。

其中某些规则属于奖励领域，有些属于背包领域，有些涉及两个领域之间的协调。

如果不知道各自归属，代码就很容易变成：

TEXT
RewardService
    → InventoryData
    → PlayerData
    → AchievementData
    → QuestData
    → SaveManager

整个程序都知道彼此的内部数据结构。

这时候真正困难的不是如何写一个 if。

而是：

一条业务规则应该由谁负责？它需要哪些状态？什么情况下必须始终成立？哪些其他业务依赖它？

DDD 为这些问题提供了一套建模语言和设计方法。

3. 同一个词，在不同业务中可能有不同含义

再考虑一个更加根本的问题。

“道具”是什么意思？

在背包系统中：

TEXT
道具 = 玩家当前持有的资源或物品

在商店系统中：

TEXT
商品 = 可以购买的报价和交易项目

在战斗系统中：

TEXT
装备 = 参与战斗规则计算的物品

三者可能关联同一个 ItemId，但业务模型并不相同。

一个商店商品甚至可能代表包含三个道具的礼包。

如果强行让所有系统使用一个巨大的 Item 类：

TEXT
public class Item
{
    public int ItemId;
    public int Price;
    public int Attack;
    public int Defense;
    public int OwnedCount;
    public bool IsOnSale;
    public bool IsEquipped;
}

这个类很快就会承担互相不相干的职责。

不同业务的概念被错误地混合在一起。

DDD 的一个重要思想就是：

不同业务上下文，可以使用不同的模型描述看起来相同的事物。

这就引出了 DDD 的第一大部分：战略设计。

三、DDD 的两个层次：战略设计与战术设计

理解 DDD 时，最好先将它们分开。

层次 主要解决什么问题 典型概念
Strategic Design（战略设计） 大系统怎样划分业务模型和边界？ Subdomain、Bounded Context、Ubiquitous Language、Context Map
Tactical Design（战术设计） 一个边界内部怎样表达业务规则？ Entity、Value Object、Aggregate、Domain Service、Repository、Domain Event

一个常见误区是直接开始写 Entity、Aggregate、Repository，然后宣布系统采用了 DDD。

但只使用战术模式，不等于真正理解了 DDD。

Martin Fowler 特别指出，DDD 的战略设计用于应对大型领域模型的复杂性，通过多个限界上下文管理模型，并明确它们之间的关系。[2]

四、战略设计：先决定模型在哪里成立

1. Subdomain：子领域

What：子领域是什么？

一个大业务问题中，可以区分的相对独立的问题范围。

例如游戏运营可能有：

text
Game Domain
├── Combat
├── Inventory
├── Achievement
├── Commerce
└── Matchmaking

这是一种业务分析划分，不意味着必须创建五个服务或者五个 C# 程序集。

DDD 还常将子领域分为：

  • Core Domain（核心域）：构成产品核心竞争优势的部分。
  • Supporting Subdomain（支撑子域）：支撑核心业务，但不是主要竞争优势。
  • Generic Subdomain（通用子域）：很多系统都需要、差异化较低的功能。

这种分类不是永久固定的。

例如某个游戏的核心玩法可能就是独特的背包组合系统，那么 Inventory 就可能属于核心域；对于普通动作游戏，它可能只是支撑功能。

Why： 不同业务问题的重要性和复杂性不同，投入的建模精力也不应该相同。

How： 从实际业务目标、规则差异、团队知识和变化频率识别问题范围，再决定哪些值得深入建模。

2. Bounded Context：限界上下文

这是 DDD 最重要、也是最容易理解错误的概念之一。

What：限界上下文是某个领域模型具有明确、一致含义的适用边界。

我们用“商品”来理解。

Commerce Context

商业交易模型

Product

价格、库存状态、折扣、商品组合

Inventory Context

玩家持有模型

ItemStack

道具编号、持有数量、堆叠限制

通过明确契约转换彼此的概念

PurchaseResult → ItemGrant

购买结果被转换成背包能够理解的授予请求

商店中的 Product 和背包中的 ItemStack 不是同一个模型。

它们只是存在某种业务关联。

限界上下文的作用是明确：

  • 在 Commerce 中，Product 的含义是什么？
  • 在 Inventory 中，ItemStack 的含义是什么？
  • 两边的模型如何转换？
  • 哪一方有权决定什么业务事实？

限界上下文不是一个文件夹，也不天然等于微服务。

一个限界上下文可以在一个单体应用内部实现；它和子领域通常有关联，但也不是严格一一对应。

3. Ubiquitous Language：统一语言

DDD 强调开发者与业务专家使用一致的语言理解业务。

例如，团队正在讨论奖励。

最开始大家可能说：

text
玩家获得奖励。

但“获得”究竟是什么意思？

  • 奖励资格已经满足？
  • 奖励已解锁？
  • 玩家已经点击领取？
  • 奖励已成功发入背包？

这些状态不应该混为一谈。

我们可以约定：

业务术语 明确含义
Unlocked（已解锁） 满足奖励条件，允许领取
Claimed（已领取） 该奖励已经完成一次合法领取
Granted（已发放） 奖励资源已经被成功授予
Consumed（已消耗） 已持有资源被合法扣除

然后让模型表达这些概念：

C#
achievement.Unlock();
achievement.Claim();
inventory.Grant(itemGrant);
inventory.Consume(itemId, amount);

Why： 语言含糊会导致需求理解与代码实现产生偏差。

How： 与业务设计者共同确定术语及其含义，并持续反映到需求、代码、测试和文档中。

这里的“统一”不是全公司只能有一个统一模型，而是一个限界上下文内部保持一致，不同上下文可以使用不同语言与模型。

4. Context Map：上下文映射

当多个限界上下文协作时，需要明确它们之间的关系。

例如：

text
Achievement Context
       |
       | 产生可领取的奖励
       v
Reward Fulfillment
       |
       | 请求发放道具
       v
Inventory Context

要进一步决定：

  • 谁定义跨上下文契约？
  • 哪一方依赖哪一方？
  • 使用同步调用还是事件？
  • 对方模型改变时如何保护自己的模型？

DDD 中有防腐层（Anti-Corruption Layer）、客户—供应商（Customer–Supplier）、共享内核（Shared Kernel）等上下文协作模式。

这里先掌握核心即可：

战略设计的本质是在决定：系统中的哪些地方应该使用同一个模型，哪些地方不应该强行共享模型。

五、战术设计：怎样用代码表达业务规则？

战略设计解决模型应该在哪里成立。

战术设计则进一步回答：

在一个明确的业务边界内部，应该怎样表示业务对象、维护业务规则和组织业务行为？

DDD 中几个最重要的战术概念是：

概念 本质
Entity（实体） 有持续身份的领域对象
Value Object（值对象） 通过值而不是身份定义的概念
Aggregate（聚合） 共同维护一组一致性规则的对象边界
Aggregate Root（聚合根） 聚合中控制外部访问和合法状态变化的入口
Domain Service（领域服务） 不适合归属于单个实体或值对象的领域操作
Application Service（应用服务） 组织一次业务用例的执行流程
Repository（仓储） 提供领域对象的获取和持久化能力
Domain Event（领域事件） 表达领域中已发生的重要事实

这些是可选择的建模工具，不要求每个模块都完整使用一遍。

1. Entity：实体

What：实体是什么？

实体是一种通过身份而不是单纯通过属性值来区分的领域对象。

假设两个玩家都有五个金币。

text
Player A
    Coins = 5

Player B
    Coins = 5

它们的数据可能相同，但显然不是同一个玩家。

因为它们有不同的身份。

而且玩家的等级、背包、金币可以变化，玩家仍然是同一个玩家。

因此实体的核心特征是：

身份在生命周期中具有连续性，而属性可以发生变化。

Why：为什么需要实体？

因为某些业务要求我们追踪“同一个对象”随着时间发生的变化。

例如：

  • 哪个玩家领取过奖励？
  • 哪个订单已经完成？
  • 哪一把具有独立实例编号的武器已经强化？

实体让这些问题有明确的对象归属。

How：如何设计？

C#
public sealed class AchievementProgress
{
    public Guid PlayerId { get; }
    public int AchievementId { get; }

    public bool IsCompleted { get; private set; }
    public bool IsClaimed { get; private set; }

    public void Complete()
    {
        IsCompleted = true;
    }
}

一个玩家的某项成就进度，可以用：

text
(PlayerId, AchievementId)

作为业务身份。

它的 IsCompleted 和 IsClaimed 可以变化，但身份不因此改变。

在这里，Entity 不等于 Entity Framework Core 中的数据库实体类。

两者有可能映射在一起，但 DDD 的实体是一个领域概念，不是 ORM 提供的技术类型。

2. Value Object：值对象

What：值对象是什么？

值对象是一种不关心独立身份，只关心自身取值和意义的领域概念。

例如：

text
ItemGrant
    ItemId = 1001
    Amount = 5

我们并不需要区分“第一份数量为五的发放描述”和“第二份数量为五的发放描述”各自的身份。

如果它们所有有意义的属性相同，就可以被视为等价。

Why：为什么需要值对象？

假设你的方法是：

C#
GrantItem(int itemId, int amount);

其中 amount 必须大于零。

如果每次使用它都在外部检查：

C#
if (amount <= 0)
    throw new Exception();

业务约束就容易被重复实现，甚至遗漏。

我们可以让值对象在创建时建立合法性。

How：使用 C# record

C#
public sealed record ItemGrant
{
    public int ItemId { get; }
    public int Amount { get; }

    public ItemGrant(int itemId, int amount)
    {
        if (itemId <= 0)
            throw new ArgumentOutOfRangeException(nameof(itemId));

        if (amount <= 0)
            throw new ArgumentOutOfRangeException(nameof(amount));

        ItemId = itemId;
        Amount = amount;
    }
}

现在：

C#
var reward = new ItemGrant(1001, 5);

就是一份合法的道具发放描述。

而：

C#
var reward = new ItemGrant(1001, -5);

会被拒绝。

这将“不允许发放负数量道具”这一局部约束封装到了 ItemGrant。

值对象通常设计成不可变的，方便比较、传递和推理。

但值对象的规则还不能代替 Inventory 自己的规则。

例如 ItemGrant(1001, 5) 合法，不代表当前背包一定有空间容纳五个道具。

值对象保证自身合法，使用值对象的领域对象继续保证更大范围的业务规则。

3. Aggregate：聚合

这是 DDD 中最值得花精力理解的战术模式。

What：聚合是什么？

聚合是一个领域对象边界。

在这个边界内部，一组对象共同维护某些必须成立的业务约束。

聚合至少包含一个实体，作为聚合根；它也可以包含其他实体和值对象。

假设我们设计一份订单：

Order Aggregate 一致性边界

Order（Aggregate Root）

确认订单、取消订单、计算总额

OrderLine

订单项实体

Money

金额值对象

外部通过 Order 发起状态变化，由聚合根协调内部对象并维护订单规则。

例如：

text
订单总金额必须等于各订单项金额之和。

如果外部可以随便修改 OrderLine，却不更新订单总金额，那么订单就可能进入不合法的状态。

因此，由 Order 控制：

C#
order.AddLine(productId, quantity, price);

而不是允许外界随意修改内部订单项。

Why：为什么需要聚合？

因为业务系统中的状态必须维持某些条件。

这些条件叫作 Invariant（不变量）。

例如：

Order.Total=∑i=1nOrderLinei.Total

又例如：

0≤Inventory.ItemCount≤99

业务执行一次操作后，这些规则依然必须成立。

聚合帮助我们明确：

由哪些对象共同负责保证这些约束，以及哪个入口有权改变它们。

Martin Fowler 对 DDD Aggregate 的解释中特别强调：聚合不是普通集合，而是一个可以作为整体处理的领域对象单元，聚合根负责维护其完整性。[0]

How：如何决定聚合边界？

首先列出业务不变量，然后研究它们依赖的状态。

例如某个背包槽位必须满足：

text
0 ≤ 当前数量 ≤ 最大堆叠数量

如果只有修改这个槽位的操作才需要维护它，就没有必要因为玩家还拥有成就、邮箱和好友信息，而把这些对象全部塞入同一个超级聚合。

判断聚合边界时，应该问：

“哪些状态必须在同一次业务状态变化中协调，才能确保这组不变量成立？”

通常应该尽量设计较小的聚合，以避免不相关的操作争抢同一份状态或锁。Microsoft 的 DDD 指南也明确强调，应根据事务不变量设计聚合，而不是随意把关联对象放在一起。[4]

但这里要避免另一个误解：

聚合边界不等于数据库事务绝对不能跨越的边界。

DDD 常建议以一个聚合为事务修改单位，跨聚合通过事件实现协作与最终一致性。

这是有价值的设计指导，尤其是在分布式系统中。

但如果两个聚合在同一个事务型数据库内，而且真实业务要求它们必须同时提交，也可以由应用服务协调一个跨聚合事务。这需要明确设计取舍，而不是把所有涉及事务的对象强行合并成一个聚合。

4. Domain Service：领域服务

What

领域服务用于表达具有明确业务含义，但不自然属于某个实体或值对象的领域操作。

例如：

text
根据两个玩家的战力、匹配区间及组队规则，
判断一场匹配是否允许成立。

这种规则可能需要多个领域对象参与，放在其中一个玩家内部未必合理。

可以设计：

C#
public sealed class MatchEligibilityPolicy
{
    public bool CanMatch(PlayerRank a, PlayerRank b)
    {
        return Math.Abs(a.Score - b.Score) <= 100;
    }
}

这只是一个简化的匹配策略例子。

它没有数据库访问、HTTP 请求或 UI 逻辑，只表达一个领域判断。

Why

如果一个业务规则不属于任何单个实体，强行放进去可能会让实体承担不适当的职责。

领域服务为这类规则提供明确的归属。

How

首先尝试将规则放在合适的实体或值对象中。

如果规则确实跨越多个对象且不适合归属其中之一，再考虑领域服务。

不要把所有业务逻辑统统搬进 XXXDomainService，否则可能重新形成只有数据、没有行为的贫血领域模型。

5. Application Service：应用服务

这是最容易与领域服务混淆的一对概念。

它们的区别在于：

Domain Service 负责领域判断；Application Service 负责组织业务用例。

例如：

text
领取成就奖励
    ↓
加载成就进度
    ↓
验证领取规则
    ↓
加载背包
    ↓
发放道具
    ↓
原子保存数据
    ↓
返回领取结果

整个流程属于 Application Service 的职责。

但：

text
成就是否已完成？
是否可以领取？
背包是否还能容纳该道具？

这些规则应由相关领域模型或领域服务负责。

应用服务可以选择执行顺序、调用 Repository、开启事务和协调不同领域对象，但不应该成为存放所有业务规则的巨大类。

6. Repository：仓储

仓储并不是普通意义上“所有 SQL 的包装器”。

在 DDD 中，它通常提供对聚合根的获取和持久化能力，让应用通过领域概念操作聚合。

例如：

C#
public interface IAchievementRepository
{
    Task<AchievementProgress> GetAsync(
        Guid playerId,
        int achievementId,
        CancellationToken ct);

    Task SaveAsync(
        AchievementProgress progress,
        CancellationToken ct);
}

业务只知道需要加载和保存成就进度。

至于数据使用 MySQL、PostgreSQL 还是其他方式保存，不应该决定领域行为如何编写。

但是也不需要为了 DDD 而给每一张数据库表创建一个 Repository。

Repository 的边界应该服务于领域模型，而不是机械复制数据表结构。

7. Domain Event：领域事件

领域事件表达的是：

领域中某件有业务意义的事情已经发生。

例如：

C#
public sealed record AchievementRewardClaimed(
    Guid PlayerId,
    int AchievementId);

注意它描述的是过去已经发生的事实。

它不同于命令：

C#
public sealed record ClaimAchievementReward(
    Guid PlayerId,
    int AchievementId);

命令表示：

请求执行这项行为。

事件表示：

这件事情已经发生。

区别如下：

命令 Command 事件 Event
ClaimAchievementReward AchievementRewardClaimed
要求执行操作 陈述已发生的事实
可能被拒绝 表示对应事实已经成立
通常有明确的处理者 可以被多个订阅者处理

领域事件可以帮助不同聚合或上下文协作。

不过，领域事件本身不自动保证消息可靠性。

如果事件需要跨进程可靠发送，通常还需要 Outbox、可靠消息投递、幂等消费等机制。

特别要区分：领域模型产生事件，与事件什么时候能够安全地向外发布，是两件事。

六、How：在 C# 游戏服务端中实践 DDD

接下来把战略设计、实体、值对象、聚合、应用服务与仓储结合起来。

我们实现一个业务：

玩家领取已经完成的成就奖励。

业务要求：

  1. 成就必须已经完成才能领取。
  2. 同一项成就奖励只能发放一次。
  3. 道具数量不能违反背包规则。
  4. 成就领取状态与道具发放必须原子提交。
  5. 客户端重复发起领取请求时，不能重复发放道具。

这个案例能够体现 DDD 最重要的思想：谁拥有规则，谁负责保证规则。

1. 战略设计：先确定业务边界

我们把业务分为两个限界上下文：

Achievement

成就上下文

负责：

成就完成、领取资格、领取状态

Inventory

背包上下文

负责：

道具持有数量、堆叠上限、道具发放

ClaimAchievementReward（应用用例）

协调成就与背包完成一次奖励领取操作

为什么不让 Achievement 自己直接修改背包？

因为 Achievement 不拥有背包的数量和容量规则。

为什么不把成就领取判断放在 Inventory 中？

因为 Inventory 不负责决定成就是否已经完成、是否允许领取。

不同的规则拥有不同的业务归属。应用用例负责协调，而不是把它们的内部规则合并成一个大类。

2. Domain：成就聚合

先构建成就领域对象。

ItemGrant 使用前面定义的值对象。

C#
public sealed class AchievementProgress
{
    public Guid PlayerId { get; }
    public int AchievementId { get; }

    public bool IsCompleted { get; private set; }
    public bool IsClaimed { get; private set; }

    public ItemGrant Reward { get; }

    public AchievementProgress(
        Guid playerId,
        int achievementId,
        ItemGrant reward)
    {
        PlayerId = playerId;
        AchievementId = achievementId;
        Reward = reward;
    }

    public void Complete()
    {
        IsCompleted = true;
    }

    public ItemGrant? Claim()
    {
        if (!IsCompleted)
        {
            throw new InvalidOperationException(
                "Achievement is not completed.");
        }

        if (IsClaimed)
        {
            return null;
        }

        IsClaimed = true;

        return Reward;
    }
}

注意这里的重点。

C#
public ItemGrant? Claim()

这个方法不是简单修改 bool。

它表达一项完整的业务行为：

尝试领取成就奖励。

它同时保证：

  • 未完成的成就不能领取。
  • 已领取的成就不会再次发放。
  • 只有首次合法领取才返回奖励内容。

因此，Claim() 是一个具有业务意义的状态转移。

形式化地表示：

{Completed∧¬Claimed}Claim(){Claimed}

这个表达表示：在满足前置条件时，合法执行 Claim 应当使领取状态变为已领取。

如果已经领取，则当前示例返回 null，不产生新的奖励。

这里把业务规则放在领域对象内部，而不是让应用服务直接修改：

C#
achievement.IsClaimed = true;

这就是我们之前讨论过的信息隐藏和不变量维护在 DDD 中的具体应用。

3. Domain：背包聚合

背包则拥有自己的业务规则。

C#
public sealed class Inventory
{
    private readonly Dictionary<int, int> _items = new();

    public Guid PlayerId { get; }

    public Inventory(Guid playerId)
    {
        PlayerId = playerId;
    }

    public int GetCount(int itemId)
    {
        return _items.GetValueOrDefault(itemId);
    }

    public void Grant(ItemGrant reward)
    {
        int current = GetCount(reward.ItemId);

        const int maxStack = 99;

        if (reward.Amount > maxStack - current)
        {
            throw new InvalidOperationException(
                "Inventory stack limit exceeded.");
        }

        _items[reward.ItemId] =
            checked(current + reward.Amount);
    }
}

这里选择每种道具最多持有 99 个作为示意规则，实际游戏可以采用多堆叠、独立槽位或其他规则。

注意：

AchievementProgress 不需要知道背包如何检查容量。

Inventory 也不需要知道奖励来自哪个成就。

它们只需要围绕合法的 ItemGrant 协作。

这就是限界上下文与值对象配合的一种简单方式。

4. Application：协调两个聚合

现在定义仓储接口：

C#
public interface IAchievementRepository
{
    Task<AchievementProgress> GetForUpdateAsync(
        Guid playerId,
        int achievementId,
        CancellationToken ct);

    Task SaveAsync(
        AchievementProgress progress,
        CancellationToken ct);
}

public interface IInventoryRepository
{
    Task<Inventory> GetForUpdateAsync(
        Guid playerId,
        CancellationToken ct);

    Task SaveAsync(
        Inventory inventory,
        CancellationToken ct);
}

这里 GetForUpdateAsync 是我们自行定义的仓储契约，表示在事务中取得可安全更新的聚合，不是 .NET 自带的方法。

数据库适配器需要使用适当的行锁、乐观并发版本检查或等效机制完成它的并发保证。

定义事务协调接口：

C#
public interface ITransactionRunner
{
    Task<T> RunAsync<T>(
        Func<CancellationToken, Task<T>> operation,
        CancellationToken ct);
}

再定义结果：

C#
public enum ClaimRewardResult
{
    Claimed,
    AlreadyClaimed
}

实现应用用例：

C#
public sealed class ClaimAchievementRewardHandler
{
    private readonly IAchievementRepository _achievements;
    private readonly IInventoryRepository _inventories;
    private readonly ITransactionRunner _transactions;

    public ClaimAchievementRewardHandler(
        IAchievementRepository achievements,
        IInventoryRepository inventories,
        ITransactionRunner transactions)
    {
        _achievements = achievements;
        _inventories = inventories;
        _transactions = transactions;
    }

    public Task<ClaimRewardResult> ExecuteAsync(
        Guid playerId,
        int achievementId,
        CancellationToken ct)
    {
        return _transactions.RunAsync(async token =>
        {
            var achievement =
                await _achievements.GetForUpdateAsync(
                    playerId, achievementId, token);

            var reward = achievement.Claim();

            if (reward is null)
                return ClaimRewardResult.AlreadyClaimed;

            var inventory =
                await _inventories.GetForUpdateAsync(
                    playerId, token);

            inventory.Grant(reward);

            await _achievements.SaveAsync(
                achievement, token);

            await _inventories.SaveAsync(
                inventory, token);

            return ClaimRewardResult.Claimed;

        }, ct);
    }
}

仔细分析这段代码

首先：

C#
achievement.Claim();

负责成就的业务规则。

然后：

C#
inventory.Grant(reward);

负责背包的业务规则。

最后：

C#
_transactions.RunAsync(...)

负责协调持久化事务。

三个职责没有被混合起来。

如果成就未完成，业务操作被拒绝。

如果成就已经领取，直接返回 AlreadyClaimed，不会再次发放道具。

如果背包已经达到上限，Grant() 抛出异常，事务应回滚成就的领取状态变化。

只有成功完成所有数据库变更，事务才可以提交。

这段代码要真正满足上述保证，还有几个必须落实的实现条件：

  • 两个仓储必须共享同一个事务型数据库事务。
  • 事务应当在操作全部成功后提交，失败时回滚。
  • 并发领取必须受到锁或数据库并发控制保护。
  • 同一玩家、同一成就进度必须具备唯一的持久化身份。
  • AchievementProgress 与 Inventory 的状态需要正确加载、跟踪并保存，不能直接把这个领域代码当成完整的数据库实现。

这里使用跨两个聚合的单数据库事务，是因为需求明确要求领取状态与道具发放强一致，而且假设它们位于同一事务型数据库中。

这不是说 DDD 要求所有跨聚合操作都使用同一个事务。对于分布式或允许最终一致性的场景，设计会不同。

另外，AlreadyClaimed 保证的是不会重复发放，并不表示重试获得的响应内容与第一次完全一致。如果业务需要重复请求返回完全相同的原始结果，可以进一步持久化请求 ID 和执行结果。

七、这个案例中，DDD 到底发挥了什么作用？

我们把它重新对应到概念。

DDD 概念 示例中的体现
Domain 成就奖励领取业务
Bounded Context Achievement 与 Inventory
Ubiquitous Language Complete、Claim、Grant
Entity AchievementProgress
Value Object ItemGrant
Aggregate Root AchievementProgress、Inventory
Invariant 未完成不可领取、不能重复发放、背包数量上限
Application Service ClaimAchievementRewardHandler
Repository IAchievementRepository、IInventoryRepository
Transaction 协调领取状态与道具发放的原子提交

请注意，DDL、SQL、Controller、依赖注入等实现细节不在这张表里。

因为 DDD 的贡献是让我们知道业务规则应该由谁负责，以及这些规则如何被表达和维护。

持久化和运行机制仍然需要其他技术提供支持。

八、如何从零开始进行 DDD 建模？

我建议使用下面这个流程。

  1. 描述真实业务场景

    例如：玩家完成某项成就后，可以领取一次道具奖励。

  2. 发现业务术语和事实

    什么是完成？什么是领取？什么是发放？它们的区别是什么？

  3. 找出不变量

    未完成不可领取、不能重复领取、背包数量必须合法。

  4. 确定职责与模型边界

    成就负责领取资格，背包负责道具数量；明确跨上下文契约。

  5. 识别实体、值对象与聚合

    按身份、业务行为与一致性要求设计，不根据数据库表机械划分。

  6. 实现领域行为和用例

    让领域对象维护规则，由应用服务协调执行。

  7. 通过测试与业务反馈修正模型

    新增规则、发现例外时，重新审查模型和边界，而不只是继续堆 if。

如果业务复杂，还可以使用 Event Storming（事件风暴）等协作建模方法，从业务事件出发发现流程、命令、规则和边界。

例如：

text
AchievementCompleted
        ↓
RewardBecameClaimable
        ↓
玩家请求 ClaimReward
        ↓
AchievementRewardClaimed
        ↓
ItemGranted

这是一种用于讨论业务流程的概念图，并不规定这些步骤必须通过异步消息实现。

建模的重点是让团队发现：

  • 哪一步代表资格成立？
  • 哪一步代表状态已经改变？
  • 哪些操作必须原子完成？
  • 哪些事情可以延迟执行？
  • 哪些规则目前还没有明确？

领域模型是通过理解、验证、修改不断演化出来的，而不是项目开始时一次性设计完成的。

九、设计权衡：DDD 的优势和代价

维度 DDD 的价值 代价或风险
业务复杂性 将复杂规则组织成清晰的领域模型 需要花时间理解与建模
代码可维护性 让规则拥有明确的归属 模型可能因需求变化需要重构
业务沟通 减少术语歧义 需要开发者与业务人员持续沟通
数据正确性 聚合有助于集中维护不变量 聚合边界不合理会造成性能或一致性问题
系统划分 识别不同业务模型的边界 可能产生模型转换与跨上下文协调成本
测试 能直接验证领域规则 仍需要数据库、并发和集成测试
学习成本 有助于掌握复杂业务建模方法 大量概念容易被形式化滥用

1. DDD 不一定适合简单 CRUD

如果你的业务只是：

text
创建一条公告
修改公告内容
删除公告
查询公告

而且没有复杂的业务规则，可能只需要简单的数据访问和应用服务。

这时候设计十几个领域类、多个聚合和领域事件，未必会改善代码。

Microsoft 的 DDD 指南同样建议根据业务复杂性选择建模深度，而不是对所有 CRUD 功能一律应用复杂的 DDD 战术模式。[3]

2. DDD 不等于面向对象编程

实体、值对象、聚合经常使用 C# 类来实现。

但 DDD 的战略设计、领域语言和建模思想，并不要求所有逻辑必须采用面向对象风格。

你也可以使用不可变数据结构和纯函数表达领域规则。

例如：

C#
public static bool CanClaim(
    bool isCompleted,
    bool isClaimed)
{
    return isCompleted && !isClaimed;
}

只要这种设计仍然准确表达业务，模型本身就有价值。

3. DDD 不等于微服务

限界上下文可以位于同一个应用中。

例如：

text
GameServer（Modular Monolith）
│
├── Achievement Context
├── Inventory Context
├── Commerce Context
└── Combat Context

它们可以运行在同一个进程，使用同一个数据库实例，同时拥有清晰的业务边界。

没有必要因为采用 DDD 就拆成多个独立部署的服务。

4. DDD 也不会自动保证正确性

领域对象定义了合法操作，但如果数据库并发更新丢失、跨模块保存不原子，系统仍然可能出现错误。

因此完整的正确性需要多个层次共同保证：

  • 领域模型：表达并检查业务规则。
  • 应用层：正确协调业务流程。
  • 数据库：提供持久化、事务和并发约束。
  • 系统设计：处理请求重复、故障恢复和消息可靠性。
  • 测试：验证正常情况、异常情况和并发情况。

DDD 是正确性设计的重要组成部分，但不是正确性的全部。

十、DDD 与之前学习的架构之间的关系

我们将几种架构放在同一个视角比较。

名称 主要解决的问题
Modular Monolith 整个应用应该如何组织模块并保持单体部署？

十一、直达本质：DDD 真正改变的是什么？

回到最初的问题。

软件究竟为什么会变得难以维护？

其中一种重要原因是：

业务规则散落在各个技术组件中，没人能清楚地说出规则由谁负责、在哪些条件下成立、哪些状态必须一起变化。

DDD 的解法不是简单地增加类和接口。

它要求我们重新组织思考顺序：

先理解问题

业务事实是什么？真正需要保证哪些规则？

再划分模型边界

哪些概念属于同一个上下文？谁对状态和规则负责？

最后用代码落实模型

利用实体、值对象、聚合和服务表达并执行业务规则。

可以把 DDD 归结成三句话。

What： 领域驱动设计是一套通过领域模型表达、组织和演化复杂业务的软件设计方法。

Why： 因为业务复杂性的核心常常在于概念、规则、例外以及它们之间的关系，而不仅是代码数量。

How： 通过统一语言、领域分析、限界上下文和战术建模，将业务知识落实为具有清晰职责、行为和约束的软件结构。

我认为你接下来最值得深入研究的概念是 Aggregate（聚合）和 Aggregate Root（聚合根）。

因为它们把我们前面学过的高内聚、信息隐藏、模块边界、不变量、状态转移、前置条件和事务一致性连接在了一起。

尤其值得思考的一个问题是：

“一个业务操作涉及两个聚合时，应该使用一个事务，还是通过事件让它们分别完成？”

这个问题没有脱离业务要求的固定答案，而理解如何做出这个决定，正是从掌握 DDD 术语走向真正进行领域建模的重要一步。

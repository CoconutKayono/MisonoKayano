与 Logical Lifetime

资源生命周期与逻辑生命周期

同一个实例可以承载多轮生命；同一项业务也可以跨越多个资源。理解“仍然存在”与“仍然有效”的不同边界。

资源管理对象池GenerationUnity / C#

核心认识存在，不等于有效

理解这两个概念，关键在于先区分两个问题：一个资源是否仍然存在、仍被持有？某个业务身份或活动是否仍然有效？

Resource Lifetime

资源生命周期

资源从获取、创建到释放、销毁的时间区间。

关注资源的存续与可用边界。

Logical Lifetime

逻辑生命周期

业务身份、职责或操作从生效到失效的时间区间。

关注业务语义的有效边界。

资源仍然存在，不代表过去的操作仍然可以合法使用它。

一个敌人已经死亡，但承载它的对象仍在池中；一场战斗还在继续，但承载画面的旧场景资源已经被替换。

这两种情况都说明：资源的存续边界，不一定等于业务语义的有效边界。

01 · WHAT它们究竟是什么？

1. 资源生命周期：某个资源持续存在多久

这里的资源是广义概念，可以是内存、文件句柄、数据库连接、网络套接字、Unity 的 GameObject、RenderTexture，或对象池中的实例。

先说明正在观察哪个资源层级，再谈它的生命周期。

  • 文件句柄：从打开到关闭。
  • C# 托管对象：从分配到不再存活、其内存得以回收。
  • Unity 原生对象：从创建到对应原生对象被销毁。
  • 池中实例：从实例创建到最终销毁；使用者的一次获取到归还，则是单次占用或租约。

“释放”也取决于层级。归还池结束的是本次使用权，通常并不意味着底层实例被销毁。一份资源可以有多个嵌套的持有周期。

2. 逻辑生命周期：某种业务语义成立多久

Logical 强调的不是物理存在，而是某种业务身份、职责、操作或状态是否仍然成立。

  • 敌人：从生成到死亡或退场。
  • 攻击：从开始到结束。
  • UI 窗口的一次打开：从打开到关闭。
  • 异步请求：从发起到完成、取消或失效。
  • 游戏对局：从开始到结束。

这些业务概念结束后，对应的内存和底层资源不一定立即释放。

3. 两者的时间关系

示意时间线，不按真实时间比例。蓝色表示底层实例存活，绿色表示不同的业务生命。

一个资源生命周期，可以承载多个彼此独立的逻辑生命周期。

但两者并非必然包含：一个逻辑活动也可能跨越多个先后创建的资源实例。例如切换场景时重新创建 UI，或会话持续期间重新建立网络连接。

02 · WHY为什么必须区分它们？

1. 资源管理与业务管理解决不同的问题

敌人生命值归零后，业务系统需要让它死亡：不再受伤、攻击、参与目标搜索；碰撞是否继续存在，也由死亡后的玩法规则决定。这决定的是业务有效性。

资源管理器则可以将对应对象留在池中，未来再次使用，必要时才执行 Destroy。因此，敌人死亡时，真正需要的操作不一定是销毁实例。

业务系统 → 决定何时失效
资源管理器 → 决定何时释放

对象可以提前创建、延迟销毁，而不改变一轮业务生命的含义。

2. 同一个对象，可以代表不同的逻辑实体

  1. 创建 Enemy 实例 A。
  2. A 代表敌人 #1001。
  3. 敌人 #1001 死亡，A 被归还池。
  4. 再次取出 A，A 代表敌人 #2035。

C# 引用仍然指向同一个实例 A，但敌人 #1001 与敌人 #2035 是不同的业务身份。

概念回答的问题
Object Identity · 对象身份是不是同一个 C# 对象实例？
Logical Identity · 逻辑身份是不是同一个特定的敌人、同一轮业务生命？
Resource Ownership · 资源所有权谁负责管理并最终释放这个实例？
对象引用相同，不意味着它仍然代表同一个逻辑实体。

3. 有效的引用，也可能执行过期的操作

  1. 敌人 A 出现，生命值为 100。
  2. 玩家释放技能，安排 2 秒后造成伤害，回调持有 A 的引用。
  3. A 在 1 秒后死亡，被归还对象池。
  4. 同一个实例被取出，代表新敌人 B。
  5. 旧回调执行，对该实例造成 30 点伤害，结果伤害了 B。

对象没有被回收，引用也可能完全有效。这不是典型的内存访问失效，而是将资源的可访问性误认为业务操作的合法性。

CanOperate(r, l, t)
= ResourceValid(r, t)
∧ LogicalValid(l, t)
∧ BelongsTo(r, l, t)

这个简化条件要求：资源当前可用；目标逻辑生命有效；资源当前承载的正是该次逻辑生命。仅检查 enemy != null 或 enemy.IsActive，无法判断敌人是否已经换了一轮。

4. 逻辑生命也可能比单个资源更长

一次商城会话开始后，UI 对象 A 被创建；切换界面时 A 被销毁，UI 对象 B 被创建；购物车仍保留，最后商城会话才结束。

商城会话是逻辑概念，UI 是承载形式。逻辑状态可以放在独立的 Session、Model 或领域对象中，让不同的 UI 实例先后呈现。

不要把必须长期存在的业务状态，错误地绑定到一个短期资源实例上。

5. 边界混淆会产生哪些故障？

错误设计可能的后果
逻辑结束就强制销毁资源增加创建与销毁开销，无法有效池化
资源存在就认为逻辑有效已死亡敌人继续行动，关闭窗口继续接收回调
归还池时不终止逻辑活动事件、延迟任务等继续影响对象
重新使用时不重置状态上一轮生命值、Buff、目标残留
只检查引用，不检查逻辑身份旧操作作用到新实体
长期状态存放在短命资源中场景切换、UI 重建时数据丢失
逻辑结束后忘记释放独占资源文件、连接、纹理或订阅长期占用

资源生命周期错误主要破坏资源管理的正确性，逻辑生命周期错误主要破坏业务行为的正确性。它们可能互相影响，但不能简单地用同一种清理机制替代。

03 · HOW如何设计两种生命周期？

把资源的创建与销毁、逻辑的开始与结束，设计为不同的操作。

1. 首先明确四种组合状态

资源可用逻辑有效含义
是是资源为当前逻辑活动服务
是否资源闲置、缓存或等待复用
否否资源释放，逻辑活动结束
否是原资源不可用，逻辑仍有效，需要恢复或重新绑定资源

如果业务必须依赖某个特定资源，资源失效后就不能继续使用它。若业务状态与资源实现解耦，例如持久会话与临时 UI，则可以换一个资源继续运行。

2. 用两个状态机表达边界

资源生命周期由其所有者管理；逻辑生命周期由负责业务规则的对象或系统管理。两者需要协调，但含义不同。

3. 显式区分 BeginLife 与 EndLife

下面先展示最基础的 Unity/C# 示例：开始与结束一轮敌人生命，但不负责分配与销毁实例。

C# · 核心示例
using System;
using UnityEngine;

public sealed class Enemy : MonoBehaviour
{
    private bool _alive;
    private int _health;

    public bool IsAlive => _alive;

    // 开始新的一轮逻辑生命
    public void BeginLife(int health)
    {
        if (_alive)
            throw new InvalidOperationException("Enemy is already alive.");

        _health = health;
        _alive = true;
        gameObject.SetActive(true);
    }

    // 结束当前逻辑生命，不销毁实例
    public void EndLife()
    {
        if (!_alive)
            return;

        _alive = false;
        _health = 0;
        gameObject.SetActive(false);
    }

    public void TakeDamage(int damage)
    {
        if (!_alive)
            return;

        _health = Math.Max(0, _health - damage);
    }
}
C# · 核心示例
Enemy enemy = pool.Get();
enemy.BeginLife(100);  // 新的一轮逻辑生命

// ... 游戏逻辑 ...

enemy.EndLife();       // 当前业务身份失效
pool.Release(enemy);   // 放弃本轮占用，归还池

EndLife() 结束业务身份，Release() 结束使用者对实例的本轮占用。Unity 的 ObjectPool<T> 可通过获取、归还和销毁回调配置对应处理；归还时若池已满，也可能实际销毁实例。

只检查 _alive 仍有漏洞。

对象被再次使用后，_alive 又为 true，旧回调仍可能伤害新敌人。因此，状态有效并不足以证明“还是原来的那一轮”。

4. 用 Generation 区分每一轮逻辑生命

给每次 BeginLife() 分配一个新的世代号 Generation。旧回调携带第 1 轮标识，而对象当前已处于第 3 轮，即使实例可用且激活，也必须拒绝旧操作。

Handle = (Object Reference, Generation)
句柄 =（对象引用，逻辑世代）
C# · 核心示例
using System;
using UnityEngine;

public readonly struct EnemyHandle
{
    public readonly Enemy Enemy;
    public readonly long Generation;

    public EnemyHandle(Enemy enemy, long generation)
    {
        Enemy = enemy;
        Generation = generation;
    }
}

public sealed class Enemy : MonoBehaviour
{
    private long _generation;
    private bool _alive;
    private int _health;

    public EnemyHandle BeginLife(int health)
    {
        if (_alive)
            throw new InvalidOperationException("Already active.");

        _generation = checked(_generation + 1);
        _health = health;
        _alive = true;
        gameObject.SetActive(true);

        return new EnemyHandle(this, _generation);
    }

    public bool IsCurrent(EnemyHandle handle)
    {
        return _alive
            && ReferenceEquals(handle.Enemy, this)
            && handle.Generation == _generation;
    }

    public void TakeDamage(EnemyHandle handle, int damage)
    {
        if (!IsCurrent(handle))
            return;

        _health = Math.Max(0, _health - damage);
    }

    public bool EndLife(EnemyHandle handle)
    {
        if (!IsCurrent(handle))
            return false;

        _alive = false;
        _health = 0;
        gameObject.SetActive(false);
        return true;
    }
}
C# · 核心示例
// 第一轮
EnemyHandle oldHandle = enemy.BeginLife(100);
enemy.EndLife(oldHandle);

// 第二轮，复用同一个对象
EnemyHandle newHandle = enemy.BeginLife(200);

enemy.TakeDamage(oldHandle, 50); // 旧攻击：被拒绝
enemy.TakeDamage(newHandle, 50); // 当前攻击：生效

两次句柄引用相同实例，但 Generation 不同。句柄表达的是操作目标属于哪一轮逻辑生命，不只是对象在哪里。

这可以防止过期句柄（Stale Handle）错误，也与 ABA 问题有相似之处：底层位置未变，但其代表的身份已经经历变化。

管理器归还对象时，同样需要校验：只有 EndLife(handle) 成功，才允许执行 pool.Release(enemy)，否则旧退场请求可能归还已经重生的对象。

示例边界：基础版 Enemy 与句柄版 Enemy 是两个逐步演进的版本，使用时选择一个。以上展示核心机制，未实现完整的死亡流程、伤害参数校验、事件清理与池管理。

Generation 校验按 Unity 主线程串行访问理解；若多线程并发操作，“校验并修改”还需要同步。世代号必须避免重复，示例用 checked 防止溢出后静默回绕。

5. 异步任务：结束业务不等于工作已经停止

窗口打开后加载数据，关闭又重新打开；旧加载这时完成，可能把旧结果写入新一轮窗口。这与池化敌人的问题相同。

机制解决什么
Cancellation · 取消请求停止上一轮不再需要的工作
Generation / Identity · 身份校验拒绝已经过期的操作与结果
C# · 核心示例
using System;
using System.Threading;
using System.Threading.Tasks;

// 置于相应的类中
private async Task ApplyDelayedDamage(
    EnemyHandle handle,
    CancellationToken cancellationToken)
{
    try
    {
        await Task.Delay(2000, cancellationToken);
    }
    catch (OperationCanceledException)
    {
        return;
    }

    // 假设此处在 Unity 主线程执行
    if (handle.Enemy != null)
    {
        // TakeDamage 内部再次检查本轮身份
        handle.Enemy.TakeDamage(handle, 30);
    }
}

取消通常是协作式的，不能单独作为逻辑正确性的最终保障。即使工作没能及时停止，最后的身份校验仍能拒绝旧操作。

涉及 Unity API 的调用必须满足主线程要求。生产实现也应清理本轮事件订阅、效果状态、定时器与其他专属数据。

6. 不要将 Unity 回调普遍等同于业务生命周期

OnEnable / OnDisable 反映组件与对象启用状态的变化；OnDestroy 反映对象或组件的销毁阶段。禁用也可能与销毁、场景卸载或脚本重载有关。

所以不能普遍认定 OnEnable == BeginLife、OnDisable == EndLife。例如，SetActive(false) 可能只是暂停显示，不代表敌人死亡。

C# · 核心示例
BeginLife();
Suspend();
Resume();
EndLife();

对于语义严格的对象，先明确这些业务操作，再决定是否调用 SetActive()。Unity 回调可维护与启用状态相匹配的订阅、注册等，但不应无条件解释为业务出生与死亡。

调用 Destroy() 与销毁完成也有时间差：Unity 会安排稍后的实际销毁，因此一旦业务失效，就应立即拒绝相应业务操作。

7. 区分 Dispose、Lease 与 Logical Lifetime

IDisposable 是显式清理或释放资源的协议，并不天然定义业务结束规则。

C# · 核心示例
using (var stream = System.IO.File.OpenRead(path))
{
    LoadData(stream);
} // Dispose 及时释放底层资源，托管对象不一定立即被 GC 回收

Lease（租约 / 使用权周期）表示使用者暂时持有资源的权利。例如底层数据库连接先借给请求 A，A 完成后归还，再借给请求 B，最终池关闭时物理连接才被释放。

层级生命周期
物理资源底层连接从创建到释放
Lease请求对连接的一次占用
Logical请求本身从开始到完成的业务周期

一次请求可以使用多个连接，一个连接也可以先后服务很多请求。Dispose、Return、EndLife、Destroy 是不同层级的操作。具体 API 可以把其中几个动作组合起来，仍应明确它实际结束了哪个周期。

04 · 验证用不变量约束生命周期

不要仅观察程序是否“看起来正常运行”，应明确哪些条件在任何合法执行中都必须成立。

① 失效的逻辑身份不能修改业务状态

¬LogicalActive(h) ⇒ ¬CanMutate(h)

旧句柄不得改变新一轮的生命值、Buff、位置与业务状态。

② 一次租借至多有效归还一次

ReleaseCount(lease) ≤ 1

记录的是某次占用，而不是实例的整个生命。同一实例可以借还多次，但一次租借不能被重复归还。

③ 新生命不能意外继承旧状态

State_new = Initialize(Config, InitialState)

生命值、临时 Buff、目标、定时器、协程与事件订阅，都要有明确的重置或继承策略。

④ 互斥的独占租借不能重叠

ExclusiveLeaseCount(resource) ≤ 1

若资源允许共享，则改用符合共享语义的并发与引用计数规则。

⑤ 结束与释放都有明确责任方

谁调用 EndLife()？谁调用 Release()？谁最终调用 Destroy()？回答不清楚，就容易遗漏清理或重复释放。

最值得测试的场景

  • 旧回调在对象重新生成后才执行。
  • 旧句柄请求退场时，对象已属于新一轮。
  • 同一租借被重复归还。
  • 窗口关闭又打开后，旧异步结果才到达。
  • 复用对象时，旧 Buff、目标、订阅与计时器是否残留。

05 · 关联所有权、借用与两种生命周期

概念必须回答的问题
Ownership · 所有权谁拥有资源，谁最终负责释放？
Resource Lifetime所讨论的资源从何时开始存在或被持有，何时释放？
Borrowing / Lease当前谁被允许使用它，权限与占用周期何时结束？
Logical Lifetime操作属于哪一轮业务生命，何时失效？

常见复用系统中，Owner 管理资源，使用者通过借用或租约获得使用权，再利用资源承载业务活动。但所有系统不必严格按照同一种层级嵌套。

若资源 R 被连续复用 n 次，而且每次逻辑活动都依赖此特定资源，可用时间区间表达：

L₁, L₂, …, Lₙ ⊆ R

这里的包含指时间区间包含，不表示逻辑活动必须连续、相同，或资源与业务必然一一对应。若逻辑活动可以更换资源，就不能普遍套用这种包含关系。

资源生命周期定义资源的存续和可用边界；逻辑生命周期定义业务身份、职责和操作的有效边界。

设计的目标，是明确各自边界，并在越界时让该失效的操作失效，让仍可复用的资源继续发挥作用。

四个设计问题，贯穿实现

  1. 我操作的是哪一个资源层级？
  2. 我持有的是实例引用，还是某轮逻辑身份？
  3. 逻辑结束时，哪些工作、订阅和结果必须失效？
  4. 使用权结束时，谁归还资源；资源最终结束时，谁释放它？

复用的本质区别

它们都涉及复用，但复用的究竟是什么？从实例生命周期、结果有效性与状态边界，理解三种设计为什么成立。

00 / OVERVIEW核心结论

这三个概念看起来非常相似：对象池避免重复创建对象，缓存避免重复获取或计算数据，享元模式避免重复保存相同的数据。但这只是表面区别。

要真正理解它们，需要回答三个问题：复用的究竟是什么？为什么能够复用？复用之后，状态、身份与所有权发生了什么变化？

对象池解决反复使用实例的问题；缓存解决重复获得相同结果的问题；享元模式解决大量逻辑对象重复持有相同状态的问题。
比较维度对象池缓存享元模式
复用内容可再次使用的实例或资源已获取或计算的结果多个对象共有的内部状态
主要目的降低创建与销毁成本降低重复获取或计算成本减少重复状态的存储
关键机制借出、归还、重置查找、命中、失效拆分状态、共享引用
内部可变性通常允许取决于缓存契约共享部分通常应不可变
同时使用同一实例通常不能独占借给多个使用者可以，须保证共享安全正是典型用法
典型场景子弹、特效、连接池查询结果、计算结果字形数据、物品定义、材质配置

它们都可能使用 Dictionary 保存对象，也都可能减少创建次数，但数据结构相同，不代表设计目的相同。

01 / WHAT它们究竟是什么？

1.1 对象池：复用可以重新投入使用的实例

假设在游戏中发射子弹。每次发射都创建一个 Bullet，子弹消失后不再使用，下一次再创建另一个。

Bullet bullet = new Bullet();

虽然子弹的游戏状态发生了变化，但用于承载这个状态的实例未必需要销毁。对象池的思路是：将对象完成任务后的实例保留下来，清理旧状态，再交给下一个任务使用。

子弹 A 与 B 可以在不同时间使用同一个实例 P1，但不能在仍需独立状态时同时使用 P1。

  • 对象身份（Identity）：内存中这个实例是谁，例如 P1。
  • 对象状态（State）：实例当前保存什么，例如位置、速度、生命时间和伤害。

对象池保留实例身份，允许状态改变。可以将实例 P 在不同时间承担的任务写成：

任务(P, t₁) = A，　任务(P, t₂) = B

Why：为什么对象池有效？

创建对象的成本不一定等于使用对象的成本。有些对象需要分配内存、初始化组件、建立引擎资源或运行复杂构造流程。如果这些工作比重置对象昂贵，就可以通过池化降低反复创建与销毁的开销。

对象池通常减少长期运行中的分配与创建次数，不一定减少峰值内存占用。没有对象正在使用时，池也可能保留大量空闲实例。

How：如何实现？

var bullet = pool.Get();    // 借出实例

bullet.Initialize(position, velocity, damage);

// 子弹结束当前使用生命周期之后
pool.Release(bullet);       // 归还实例

内部大致是：

public sealed class ObjectPool<T> where T : class
{
    private readonly Stack<T> idle = new();
    private readonly Func<T> create;
    private readonly Action<T> reset;

    public ObjectPool(Func<T> create, Action<T> reset)
    {
        this.create = create;
        this.reset = reset;
    }

    public T Get()
    {
        return idle.Count > 0
            ? idle.Pop()
            : create();
    }

    public void Release(T item)
    {
        reset(item);
        idle.Push(item);
    }
}

这是原理示例，需要 System 与 System.Collections.Generic 命名空间。未处理重复归还、外来对象归还、最大容量、销毁策略及线程安全。

对象池成立的核心前提是：

当前使用已结束 ∧ 状态可恢复到可复用状态 ∧ 借用期间满足独占约束

如果一个子弹还在运行，就将它的实例分配给另一颗子弹，两颗子弹会冲突地修改同一位置、速度等运行时状态。

1.2 缓存：复用已经得到的结果

缓存关注的问题是：如果某个结果已经获得，下一次为什么还要重新获取？

假设计算装备升级后的基础伤害很昂贵，而相同武器、相同等级在同一配置下对应相同结果：

int damage = CalculateDamage(weaponId, level);

可以保存结果，下一次输入相同时直接返回。

缓存本质上维护映射：

Key → Value
  • Key 表示确定结果所需的输入或资源身份。
  • Value 表示对应的已获取或计算结果。

Why：为什么缓存有效？

假设计算一次伤害需要 5 毫秒，同样输入请求 100 次。不缓存的理论累计计算成本约为 100 × 5 = 500 ms。缓存后第一次计算，后续只查找。

如果查找远比计算便宜，就能降低重复工作。实际收益仍取决于命中率、查询开销和缓存管理成本。

How：如何实现？

private readonly Dictionary<(string, int), int> cache = new();

public int GetDamage(string weaponId, int level)
{
    var key = (weaponId, level);

    if (cache.TryGetValue(key, out int damage))
    {
        return damage;
    }

    damage = CalculateDamage(weaponId, level);
    cache[key] = damage;
    return damage;
}

缓存有一个关键问题：结果什么时候失效？如果装备平衡性配置改变，同一武器与等级对应的伤害也可能改变，旧值就不再正确。

Key 相同 ∧ 在当前请求条件下结果仍然有效

除了输入相同，还必须确保所有影响结果的因素已被纳入判断。例如在键中加入配置版本：

var key = (weaponId, level, balanceVersion);

不同版本使用不同缓存项。旧版本条目仍需根据容量和使用情况淘汰。

缓存真正困难的地方往往不是如何保存结果，而是如何判断旧结果还能不能使用。

1.3 享元模式：共享多个逻辑对象共有的内部状态

享元模式关注的是：多个看起来相互独立的逻辑对象，是否在重复保存完全相同的信息？

假设 1000 个同类型敌人，每个都保存：

public class Enemy
{
    public string Name;
    public float BaseSpeed;
    public int BaseDamage;

    public Vector3 Position;
    public int CurrentHp;
}

Name、BaseSpeed、BaseDamage 对同类型敌人相同；Position、CurrentHp 各不相同。这混合了两种性质不同的状态。

状态类型示例特点
内部状态
Intrinsic State		类型名称、基础伤害、基础速度不依赖某个敌人的具体使用上下文，可以共享
外部状态
Extrinsic State		位置、当前生命值随具体敌人变化，需要分别维护

内部与外部是相对于被共享的享元对象而言，不是简单指 C# 成员变量放在哪里。外部状态可以由各自的上下文对象维护，在享元需要时传给它。

Why：为什么享元模式有效？

逻辑对象的数量，不一定等于它们需要保存的独立数据副本数量。假设 N 个敌人，每份共享类型数据大小为 S，每份独立状态大小为 E，全部属于同一种类型：

M普通 = N(S + E)
M享元 ≈ S + NE
相同类型数据：NS → S

1000 份相同类型数据可以变成 1 份。若有 K 种定义，理想化共享部分约为 KS。

这里省略引用、对象头、容器等开销。C# 引用字段原本也可能已指向同一对象，例如多个 Name 字段不一定各自复制字符串内容。实际节省量取决于真正被重复存储的数据，不能仅凭字段数量推算。

How：如何实现？

先独立出可共享的内部状态：

public sealed class EnemyDefinition
{
    public string Name { get; }
    public float BaseSpeed { get; }
    public int BaseDamage { get; }

    public EnemyDefinition(
        string name,
        float baseSpeed,
        int baseDamage)
    {
        Name = name;
        BaseSpeed = baseSpeed;
        BaseDamage = baseDamage;
    }
}

让各个敌人持有定义引用，并保留自己的运行时状态：

public class Enemy
{
    public EnemyDefinition Definition { get; } // 共享引用

    public Vector3 Position;                  // 独立状态
    public int CurrentHp;

    public Enemy(
        EnemyDefinition definition,
        Vector3 position,
        int hp)
    {
        Definition = definition;
        Position = position;
        CurrentHp = hp;
    }
}
var slimeDefinition = new EnemyDefinition("Slime", 2.5f, 10);

var enemyA = new Enemy(slimeDefinition, posA, 100);
var enemyB = new Enemy(slimeDefinition, posB, 100);
var enemyC = new Enemy(slimeDefinition, posC, 100);

ReferenceEquals(enemyA.Definition, enemyB.Definition); // true
ReferenceEquals(enemyA, enemyB);                       // false
共享的是每个敌人相同的那一部分。各个敌人仍然是不同实例，拥有自己的状态与身份。

共享数据应尽可能不可变。如果将 CurrentHp 放入共享定义并由所有敌人使用，敌人 A 受伤就可能改变其他敌人的生命值。

02 / WHY为什么都是复用，却需要三种设计？

因为软件中的重复有不同形式：

重复发生在哪里具体问题对应设计
时间上实例完成任务后被丢弃，下次又创建一个功能相同的实例对象池：管理实例生命周期
工作上同一结果已计算或获取过，却再次执行相同工作缓存：改变结果获取路径
表示上大量独立对象同时持有相同信息的副本享元：调整状态组织结构

2.1 为什么不能让所有子弹共享一个对象？

bulletA = sharedBullet;
bulletB = sharedBullet;

bulletA.Position = posA;
bulletB.Position = posB;

ReferenceEquals(bulletA, bulletB); // true

两次赋值操作同一实例，第二次位置修改会覆盖第一次结果。

对象池给每颗活动子弹独立实例，等空闲后再复用。享元模式将可共享部分提取为 BulletDefinition，各子弹仍独立保存自己的 Position。

对象池按生命周期分配实例，享元模式按状态的可共享性组织数据。

2.2 缓存与享元为什么容易混淆？

Dictionary<string, EnemyDefinition> definitions;

var definition = definitions["slime"];

这是缓存还是享元？可能两者都是，也可能只是其中之一。

  • 这张表如果用于避免反复从磁盘读取定义，承担缓存职责。
  • 1000 个敌人都引用同一份定义，共享内部状态，体现享元职责。

缓存关注取得它的过程：下次是否还要重新加载？享元关注使用它的结构：1000 个敌人是否要各自保存一份定义？

缓存也可以保存计算数值、查询响应，甚至一次失败结果；这些结果未必是大量逻辑对象共同的内部状态。因此仅看到字典或同一对象被返回，无法判断设计职责。

03 / HOW在 Unity 中如何协同？

假设一个弹幕游戏每分钟发射 1000 发子弹，最多同时存在 100 发，分为 5 种类型，还要反复计算部分弹道。

对象池Bullet 实例

围绕约 100 发活动峰值配置实例复用。

缓存TrajectoryCache

相同弹道参数命中时，复用预计算结果。

享元BulletDefinition

5 种类型共享 5 份定义，保留各自运行状态。

1000 是一段时间内的发射总量，100 是同时活动峰值。池中需要多少实例主要由同时活动数量及保留策略决定，不需要为全部 1000 发分别保留实例。

3.1 对象池负责运行时实例

public class Bullet : MonoBehaviour
{
    public BulletDefinition Definition { get; private set; }

    private Vector3 velocity;
    private float lifetime;

    public void Initialize(
        BulletDefinition definition,
        Vector3 position,
        Vector3 velocity)
    {
        Definition = definition;
        transform.position = position;

        this.velocity = velocity;
        lifetime = 0f;

        gameObject.SetActive(true);
    }

    public void ResetState()
    {
        Definition = null;
        velocity = Vector3.zero;
        lifetime = 0f;

        gameObject.SetActive(false);
    }
}

Definition 是共享引用，velocity 和 lifetime 是独立状态。这里的启用安排在数据初始化之后；实际池的借出回调也要配合这个顺序。

Unity 示例需要 UnityEngine。代码展示职责分工，未包含移动、碰撞、计时归还与完整池管理。实际重置还可能涉及协程、异步回调、事件订阅、Rigidbody 速度、粒子、TrailRenderer 和碰撞状态等。

3.2 享元模式负责共享类型定义

[CreateAssetMenu(menuName = "Game/Bullet Definition")]
public class BulletDefinition : ScriptableObject
{
    [SerializeField] private float baseDamage;
    [SerializeField] private float baseSpeed;
    [SerializeField] private Sprite icon;

    public float BaseDamage => baseDamage;
    public float BaseSpeed => baseSpeed;
    public Sprite Icon => icon;
}

同类型子弹引用同一个 BulletDefinition 资源实例，避免各自复制全部配置。每颗子弹的生命时间等运行状态保留在独立实例中。

ScriptableObject 本身不是享元模式的同义词。只有承担多个逻辑对象共享内部状态的职责时，才体现享元特征。而且它在运行时并非天然不可修改，仍需通过设计约束共享配置的修改。

3.3 缓存负责昂贵的重复计算

如果弹道由固定初速度、重力与采样设置决定，可以用参数键查询预计算结果：

private readonly Dictionary<TrajectoryKey, TrajectoryData>
    trajectoryCache = new();

public TrajectoryData GetTrajectory(TrajectoryKey key)
{
    if (trajectoryCache.TryGetValue(key, out var data))
    {
        return data;
    }

    data = CalculateTrajectory(key);
    trajectoryCache.Add(key, data);
    return data;
}

TrajectoryKey 必须包含所有影响结果的必要参数：初速度、重力、采样间隔等。若用相对起点的轨迹表示，则可在使用时叠加各子弹自己的起点。

TrajectoryData 最好不可变，或通过可靠的只读接口防止被调用者意外修改。

TrajectoryKey、TrajectoryData 与 CalculateTrajectory 是说明职责的占位类型和方法，需要由项目实现。以上缓存示例按单线程访问说明原理。

04 / DEEPER VIEW身份、状态与所有权

维度对象池缓存享元模式
身份保留实例身份，反复租用按 Key 查找已有结果，不一定承诺引用身份稳定不同逻辑对象引用同一共享状态实例
状态复用前后通常需要重置命中结果必须仍有效共享部分通常不可变
所有权与使用权池管理保留与销毁，借用者暂时独占使用缓存管理条目保留与失效，底层资源释放责任另行约定多个使用者持有共享引用，最终释放责任另行约定
生命周期空闲 → 借出 → 归还 → 再次借出 / 销毁获取 → 命中 → 失效 / 淘汰 → 重新获取建立共享状态 → 多处引用 → 最终释放

这里的所有权是设计约束，C# 普通引用不会自动强制执行。共享引用也不等于共享销毁权。尤其对于 Unity 对象或其他外部资源，需要明确谁可以最终释放。

4.1 对象池正确性：状态隔离

上一次使用产生的状态，是否会影响下一次使用？

如果归还时仍订阅旧事件，下一次借出可能继续响应旧任务，造成重复处理。重置的意义是建立新旧使用生命周期之间的状态隔离；旧协程或异步回调也必须停止，或验证自己仍属于当前租用。

4.2 缓存正确性：结果有效性

当前请求条件下，原来的结果仍然正确吗？

玩家统计从 100 变为 120，而缓存仍返回 100。即使命中 Key，也可能得到过期数据。因此需要根据契约考虑失效、版本、容量、一致性和并发更新策略。

4.3 享元正确性：共享边界

哪些状态真正属于可以共同使用的部分？

将敌人当前生命值加入共享定义，会破坏敌人之间的逻辑独立性。难点是识别哪些状态可共享，哪些必须独立维护。

05 / TRADE-OFFS设计权衡：复用也有成本

技术主要收益成本和风险
对象池减少创建、销毁与分配开销状态残留、重复归还、容量管理、空闲对象占用内存
缓存降低重复计算、查询或读取成本过期数据、失效策略、额外内存、一致性与并发问题
享元减少重复持有的相同状态状态拆分复杂度、引用间接访问、共享可变状态风险

仅含两个整数的小型 C# 对象，如果构造与回收成本很低，池化可能更麻烦，甚至更慢。只会请求一次的计算结果，保存到缓存通常没有收益。

如果每个对象的数据几乎都不同，或共享部分非常小，强行拆分也可能使维护成本大于收益。应根据实际测量和需求选择。

设计的目标是找到值得消除的重复成本。复用带来的管理成本必须一并计算。

06 / DECISION GUIDE如何判断应该使用哪一个？

先描述当前遇到的重复，再核对对应的正确性前提：

反复创建、使用、销毁同类实例 → 考虑对象池确认创建成本显著、并发活动数量可估计、旧任务能结束、状态能可靠重置、借用与归还责任明确。
反复获取或计算相同结果 → 考虑缓存确认输入可作为准确的 Key、结果有效性可判断、请求有足够重复率、容量与淘汰策略可接受。
大量逻辑对象保存相同信息 → 考虑享元确认共享状态可从上下文中分离、独立状态保留在各自对象中、共享修改受到约束、节省量值得复杂度。

选择并不互斥。同一份定义可以通过缓存加载，再作为享元供多个池化实例共享。

07 / ESSENCE回到「复用」的本质

对象池：管理可再次使用的实例及其生命周期，避免频繁重新创建和销毁资源。

对象池 = 实例复用 + 生命周期管理

缓存：保存已经取得的结果，在结果仍有效时避免重复执行获取或计算。

缓存 = 结果复用 + 有效性管理

享元模式：提取并共享多个逻辑对象共有的内部状态，避免分别保存相同副本。

享元 = 状态共享 + 状态边界划分
对象池：这个实例使用结束后，能不能给下一次任务使用？
缓存：这个结果已经得到过，能不能直接返回？
享元：这些不同的逻辑对象，是否需要各自保存一份相同数据？

三者消除的重复，分别发生在生命周期、结果获取、对象结构三个层面。以复用的对象和正确性约束来识别它们，就不会被相同的数据结构迷惑。

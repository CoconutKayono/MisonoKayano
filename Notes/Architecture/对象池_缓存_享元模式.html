00 / OVERVIEW核心结论

这三个概念都涉及复用。对象池常用于降低创建与销毁成本，典型结果缓存常用于降低重复获取或计算成本，享元模式常用于减少重复状态。这些用途有重叠，不能把“对象”和“数据”当作分类边界：缓存可以保存对象，创建对象也是一种工作。

要真正理解它们，需要回答三个问题：复用的究竟是什么？为什么能够复用？复用之后，状态、身份与所有权发生了什么变化？

先澄清：对象池可以理解为广义缓存思想的一种应用。广义缓存保留已有成果以降低未来重复工作的成本；对象池进一步管理实例的借出、归还与独立使用周期。下文对比中的“缓存”，主要指典型结果缓存。三者是可组合的设计职责，并非严格互斥的分类。查看完整澄清 →

它们都可能使用 Dictionary 保存对象，也都可能减少创建次数，但数据结构相同，不代表设计目的相同。

01 / WHAT它们究竟是什么？

1.1 对象池：复用可以重新投入使用的实例

假设在游戏中发射子弹。每次发射都创建一个 Bullet，子弹消失后不再使用，下一次再创建另一个。

Bullet bullet = new Bullet();

虽然子弹的游戏状态发生了变化，但用于承载这个状态的实例未必需要销毁。对象池的思路是：将对象完成任务后的实例保留下来，清理旧状态，再交给下一个任务使用。

子弹 A 与 B 可以在不同时间使用同一个实例 P1，但不能在仍需独立状态时同时使用 P1。

  • 对象身份（Identity）：内存中这个实例是谁，例如 P1。
  • 对象状态（State）：实例当前保存什么，例如位置、速度、生命时间和伤害。

对象池保留实例身份，允许状态改变。可以将实例 P 在不同时间承担的任务写成：

任务(P, t₁) = A，　任务(P, t₂) = B

Why：为什么对象池有效？

创建对象的成本不一定等于使用对象的成本。有些对象需要分配内存、初始化组件、建立引擎资源或运行复杂构造流程。如果这些工作比重置对象昂贵，就可以通过池化降低反复创建与销毁的开销。

对象池通常减少长期运行中的分配与创建次数，不一定减少峰值内存占用。没有对象正在使用时，池也可能保留大量空闲实例。

How：如何实现？

var bullet = pool.Get();    // 借出实例

bullet.Initialize(position, velocity, damage);

// 子弹结束当前使用生命周期之后
pool.Release(bullet);       // 归还实例

内部大致是：

public sealed class ObjectPool<T> where T : class
{
    private readonly Stack<T> idle = new();
    private readonly Func<T> create;
    private readonly Action<T> reset;

    public ObjectPool(Func<T> create, Action<T> reset)
    {
        this.create = create;
        this.reset = reset;
    }

    public T Get()
    {
        return idle.Count > 0
            ? idle.Pop()
            : create();
    }

    public void Release(T item)
    {
        reset(item);
        idle.Push(item);
    }
}

这是原理示例，需要 System 与 System.Collections.Generic 命名空间。未处理重复归还、外来对象归还、最大容量、销毁策略及线程安全。

对象池成立的核心前提是：

当前使用已结束 ∧ 状态可恢复到可复用状态 ∧ 借用期间满足独占约束

如果一个子弹还在运行，就将它的实例分配给另一颗子弹，两颗子弹会冲突地修改同一位置、速度等运行时状态。

1.2 典型结果缓存：复用已经得到的有效结果

本节介绍按请求查找结果的典型缓存。缓存并不局限于数值或普通数据，也可以保存 Sprite、预制体等对象；广义缓存思想与对象池的关系见后文补充。

缓存关注的问题是：如果某个结果已经获得，下一次为什么还要重新获取？

假设计算装备升级后的基础伤害很昂贵，而相同武器、相同等级在同一配置下对应相同结果：

int damage = CalculateDamage(weaponId, level);

可以保存结果，下一次输入相同时直接返回。

这里的结果缓存可以用以下映射建模：

Key → Value
  • Key 表示确定结果所需的输入或资源身份。
  • Value 表示对应的已获取或计算结果。

Why：为什么缓存有效？

假设计算一次伤害需要 5 毫秒，同样输入请求 100 次。不缓存的理论累计计算成本约为 100 × 5 = 500 ms。缓存后第一次计算，后续只查找。

如果查找远比计算便宜，就能降低重复工作。实际收益仍取决于命中率、查询开销和缓存管理成本。

How：如何实现？

private readonly Dictionary<(string, int), int> cache = new();

public int GetDamage(string weaponId, int level)
{
    var key = (weaponId, level);

    if (cache.TryGetValue(key, out int damage))
    {
        return damage;
    }

    damage = CalculateDamage(weaponId, level);
    cache[key] = damage;
    return damage;
}

缓存有一个关键问题：结果什么时候失效？如果装备平衡性配置改变，同一武器与等级对应的伤害也可能改变，旧值就不再正确。

Key 相同 ∧ 在当前请求条件下结果仍然有效

除了输入相同，还必须确保所有影响结果的因素已被纳入判断。例如在键中加入配置版本：

var key = (weaponId, level, balanceVersion);

不同版本使用不同缓存项。旧版本条目仍需根据容量和使用情况淘汰。

缓存真正困难的地方往往不是如何保存结果，而是如何判断旧结果还能不能使用。

1.3 享元模式：共享多个逻辑对象共有的内部状态

享元模式关注的是：多个看起来相互独立的逻辑对象，是否在重复保存完全相同的信息？

假设 1000 个同类型敌人，每个都保存：

public class Enemy
{
    public string Name;
    public float BaseSpeed;
    public int BaseDamage;

    public Vector3 Position;
    public int CurrentHp;
}

Name、BaseSpeed、BaseDamage 对同类型敌人相同；Position、CurrentHp 各不相同。这混合了两种性质不同的状态。

状态类型示例特点
内部状态
Intrinsic State		类型名称、基础伤害、基础速度不依赖某个敌人的具体使用上下文，可以共享
外部状态
Extrinsic State		位置、当前生命值随具体敌人变化，需要分别维护

内部与外部是相对于被共享的享元对象而言，不是简单指 C# 成员变量放在哪里。外部状态可以由各自的上下文对象维护，在享元需要时传给它。

Why：为什么享元模式有效？

逻辑对象的数量，不一定等于它们需要保存的独立数据副本数量。假设 N 个敌人，每份共享类型数据大小为 S，每份独立状态大小为 E，全部属于同一种类型：

M普通 = N(S + E)
M享元 ≈ S + NE
相同类型数据：NS → S

1000 份相同类型数据可以变成 1 份。若有 K 种定义，理想化共享部分约为 KS。

这里省略引用、对象头、容器等开销。C# 引用字段原本也可能已指向同一对象，例如多个 Name 字段不一定各自复制字符串内容。实际节省量取决于真正被重复存储的数据，不能仅凭字段数量推算。

How：如何实现？

先独立出可共享的内部状态：

public sealed class EnemyDefinition
{
    public string Name { get; }
    public float BaseSpeed { get; }
    public int BaseDamage { get; }

    public EnemyDefinition(
        string name,
        float baseSpeed,
        int baseDamage)
    {
        Name = name;
        BaseSpeed = baseSpeed;
        BaseDamage = baseDamage;
    }
}

让各个敌人持有定义引用，并保留自己的运行时状态：

public class Enemy
{
    public EnemyDefinition Definition { get; } // 共享引用

    public Vector3 Position;                  // 独立状态
    public int CurrentHp;

    public Enemy(
        EnemyDefinition definition,
        Vector3 position,
        int hp)
    {
        Definition = definition;
        Position = position;
        CurrentHp = hp;
    }
}
var slimeDefinition = new EnemyDefinition("Slime", 2.5f, 10);

var enemyA = new Enemy(slimeDefinition, posA, 100);
var enemyB = new Enemy(slimeDefinition, posB, 100);
var enemyC = new Enemy(slimeDefinition, posC, 100);

ReferenceEquals(enemyA.Definition, enemyB.Definition); // true
ReferenceEquals(enemyA, enemyB);                       // false
共享的是每个敌人相同的那一部分。各个敌人仍然是不同实例，拥有自己的状态与身份。

共享数据应尽可能不可变。如果将 CurrentHp 放入共享定义并由所有敌人使用，敌人 A 受伤就可能改变其他敌人的生命值。

02 / WHY为什么都是复用，却需要三种设计？

因为软件中的重复有不同形式。下表从三个角度观察重复成本，这些角度可以重叠：反复创建实例也属于重复工作，对象池同样是在保留创建成果。

重复发生在哪里具体问题对应设计
时间上实例完成任务后被丢弃，下次又创建一个功能相同的实例对象池：管理实例生命周期
工作上同一结果已计算或获取过，却再次执行相同工作缓存：改变结果获取路径
表示上大量独立对象同时持有相同信息的副本享元：调整状态组织结构

2.1 为什么不能让所有子弹共享一个对象？

bulletA = sharedBullet;
bulletB = sharedBullet;

bulletA.Position = posA;
bulletB.Position = posB;

ReferenceEquals(bulletA, bulletB); // true

两次赋值操作同一实例，第二次位置修改会覆盖第一次结果。

对象池给每颗活动子弹独立实例，等空闲后再复用。享元模式将可共享部分提取为 BulletDefinition，各子弹仍独立保存自己的 Position。

对象池按生命周期分配实例，享元模式按状态的可共享性组织数据。

2.2 缓存与享元为什么容易混淆？

Dictionary<string, EnemyDefinition> definitions;

var definition = definitions["slime"];

这是缓存还是享元？可能两者都是，也可能只是其中之一。

  • 这张表如果用于避免反复从磁盘读取定义，承担缓存职责。
  • 1000 个敌人都引用同一份定义，共享内部状态，体现享元职责。

缓存关注取得它的过程：下次是否还要重新加载？享元关注使用它的结构：1000 个敌人是否要各自保存一份定义？

缓存也可以保存计算数值、查询响应，甚至一次失败结果；这些结果未必是大量逻辑对象共同的内部状态。因此仅看到字典或同一对象被返回，无法判断设计职责。

补充 / WHAT · WHY · HOW对象池不也是缓存了对象吗？

“这里我怎么感觉好像有问题？对象池不也是缓存了对象吗？我如何理解你所说的对象是避免重复创建对象？缓存是避免重复获取或计算数据？希望你给我讲透彻。”

这个质疑是成立的。对象池确实可以理解为一种广义缓存。把两者简化为“对象池复用对象，缓存复用数据”不够严谨：对象也是数据的一种组织形式，创建对象同样是一种计算或资源获取工作；缓存一个对象，也可能避免再次创建它。

真正值得区分的是：如何判断可以复用，以及复用时必须遵守什么使用契约。下面先统一理解共同思想，再区分典型对象池和典型结果缓存的协议。

补充 1 · What：广义缓存保留可复用的成果

把一次工作写成：

F(x) → y

输入 x，执行工作 F，获得成果 y。F 可以是读取图片、计算弹道、查询玩家数据，也可以是创建并初始化一个对象、申请一块资源。共同点是：获得成果需要成本。

如果成果以后还有使用价值，就可以保留它，让未来的操作利用已有成果，减少重新执行的成本。

付出成本获得成果 → 保留成果 → 未来复用

这里的成果可以是数值、文件内容、网络响应、对象实例或已建立的资源。“缓存”在这种广义解释下，是一种复用思想；“对象池”则是一种带有特殊分配规则的实例复用机制。这是一种理解视角，并不意味着所有文献对缓存与池都采用严格的包含分类。

// 第一次：付出创建成本，得到实例
Bullet bullet = Instantiate(bulletPrefab);

// 任务结束：保留创建成果，而不是销毁
bullet.ResetState();
idleBullets.Push(bullet);

// 新任务：复用已经创建的实例
Bullet reused = idleBullets.Pop();

这完全符合“获得成果—保留—再利用”的思路。对象池之所以有单独的名字，是因为实例能否借出、谁正在使用、何时归还、如何重置这些约束需要额外管理。

上面是 Unity 原理片段。假设 ResetState 会清理本次使用状态并禁用对象，idleBullets 中存在可用实例；完整实现还需处理空池和归还检查。

补充 2 · Why：复用“可用实例”与复用“有效结果”

2.1 可用（Available）与有效（Valid）不是同一件事

一颗子弹的实例仍在内存中，却正在场景中飞行。它存在，不代表可分配给下一颗独立子弹：它还被当前任务占用。

相反，缓存中的伤害值 120 如果对当前请求仍然正确，A 读取它之后，B 通常仍然可以读取。B 不需要等待 A “归还这个数字”。

比较点典型对象池典型结果缓存
主要复用条件存在满足要求的空闲、就绪实例存在适用于当前请求的有效结果
已有使用者未归还前，通常不能再作为独立实例借给别人通常仍可读取同一结果，须符合共享访问契约
使用结束结束本次使用并归还，重新变为可分配状态通常不需要归还结果
旧状态处理重置会干扰下一任务的状态保留仍有意义、仍有效的结果
关键失败实例被冲突地重复分配、旧任务状态泄漏命中却返回了不适用或过期的结果

这是典型契约的对比。缓存返回可变对象时，也要处理共享修改和并发问题；池中的连接也需要健康检查。可用性和有效性可以同时需要管理，区别在于各自突出的协议。

2.2 一个保存“答案”，一个保留“可再次工作的工具”

结果缓存的典型逻辑是：“上一次算出的答案仍然正确，所以保留下来直接使用。”例如同一装备与等级在同一规则下对应伤害 120。

对象池的典型逻辑是：“上一次任务结束了，保留能够承载新任务的实例，清除旧任务会造成干扰的状态。”借出 Bullet 时，需要的不是上一颗子弹的位置、速度或碰撞记录，而是一个可以独立运行的新任务载体。

结果缓存：保留有价值的旧结果
对象池：保留可复用的实例与资源，重置每次使用独有的状态

“答案”和“工具”是帮助理解的比喻，不是严格的类型划分。例如缓存也可以保存模板对象。对象池也不是清空全部字段：组件引用、预分配缓冲区等昂贵且安全的初始化成果，通常可以保留。

2.3 查找语义与分配语义

// 结果缓存：相同请求，取得同一个逻辑结果
Sprite a = iconCache["Icon_Sword"];
Sprite b = iconCache["Icon_Sword"];
ReferenceEquals(a, b); // 此字典直接保存并返回引用时为 true

// 对象池：两次任务分别取得独立可用的实例
Bullet first = bulletPool.Get();
Bullet second = bulletPool.Get(); // first 尚未归还
ReferenceEquals(first, second); // 正确的独占租用设计下为 false

缓存请求是在问：“Icon_Sword 对应的图片资源是什么？”对象池请求是在问：“给新任务分配一个可独立使用的实例。”

Cache.Get(k) → 当前条件下适用的结果 Vₖ
Pool.Rent() → 满足要求的某个可用实例 Pᵢ

缓存关注结果语义，并不普遍承诺每次返回同一对象引用。例如它可以反序列化或返回副本；数据更新后，同一 Key 对应的有效结果也可能改变。对象池通常不承诺拿到特定 P1 还是 P2，只保证本次分配满足契约。

没有空闲实例时，池可以创建新实例、等待归还或报告容量不足，取决于容量策略。若上一次租用已结束，下一次拿到相同实例则完全正常。

补充 3 · How：同样保存对象，如何判断设计语义？

场景 A：缓存 Sprite 对象

private readonly Dictionary<string, Sprite> iconCache = new();

public Sprite GetIcon(string iconId)
{
    if (iconCache.TryGetValue(iconId, out var icon))
        return icon;

    icon = LoadIcon(iconId);
    iconCache.Add(iconId, icon);
    return icon;
}

用户查找具有确定资源身份的图片，加载过就返回已有资源，多个 UI 可以同时引用。这里缓存的就是对象，而且同样避免了重复加载及相关创建工作。缓存的保留、失效与最终资源释放责任，需要由资源管理契约约定。

LoadIcon 是项目提供的资源加载方法。示例省略失效与容量管理，按单线程访问说明原理。

场景 B：池化 Bullet 实例

private readonly Stack<Bullet> idleBullets = new();

public Bullet GetBullet()
{
    if (idleBullets.Count > 0)
        return idleBullets.Pop();

    return Instantiate(bulletPrefab);
}

public void ReturnBullet(Bullet bullet)
{
    bullet.ResetState();
    idleBullets.Push(bullet);
}

借出时从空闲集合移除，使用结束后重置、归还。这段逻辑提供的是实例分配与归还协议。两颗仍在飞行、需要独立状态的子弹，必须获得不同实例。

该示例假设位于具备 bulletPrefab 引用的 Unity 组件中。为突出原理，省略重复归还检测、外来对象归还检查、容量和销毁策略。

场景 C：隐藏并保留一个 UI 界面

Dictionary<string, GameObject> panels;

// 关闭时保留这个界面实例
panel.SetActive(false);

// 下次打开时继续使用
panel.SetActive(true);

如果按 Key 查找并再次使用的是这个特定界面的同一个实例，可以称为实例缓存。若管理多个同类弹窗，按“取得空闲实例—使用—归还”分配，则更体现对象池的契约。

只有一个实例的池也可以是池，按类型 Key 分池也很常见。因此不能仅凭实例数量、是否有 Key、是否使用 Dictionary 或 Stack、是否调用 SetActive 来定性。

看接口背后的使用契约：是在查找特定结果，还是在给新任务分配可用实例？同一实现也可能同时承担多个职责。

补充 4 · 共同的经济思路，不同的正确性约束

它们都在用存储与管理成本，换取未来更少的重复工作。先忽略长期保留、维护和并发等额外成本，可以写成：

单次复用收益 ≈ 重新执行成本 − 复用所需成本
缓存命中收益 ≈ 重新计算 / 获取成本 − 查找与返回成本
池化复用收益 ≈ 重新创建及相关销毁成本 − 借还、重置与再初始化成本

这些是帮助分析的简化模型，实际总收益还取决于命中率、使用频率、内存保留、淘汰、扩容和管理开销。共同的成本模型，不意味着相同的正确性规则。

关注点结果缓存对象池
核心判断Valid(value, context)：此结果在当前条件下是否适用？Available(instance)：是否空闲且满足借出条件？
额外保证Key、版本与失效策略正确；共享访问符合契约重置与初始化后满足新任务前提；旧任务不再影响它
常见操作Get(key)、Set(key, value)、Invalidate(key)Rent / Get、Return / Release、Reset
管理重点容量、过期、命中率与一致性借用状态、活动数量、空闲保留与生命周期

方法名只是线索。连接池可以按目标服务器分池，带引用计数的资源缓存也可能有 Release。池也会管理容量与健康状态，缓存也会管理资源生命周期。理解它们，需要看完整协议。

补充 5 · Unity：沿着三次火球发射理解三种职责

假设每秒生成 20 个火球，同时最多有 50 个。它们使用相同预制体和类型配置，但位置、速度、目标分别独立。

对象池Fireball 实例

分配独立运行实例，结束后重置、归还、再次分配。

资源缓存FireballPrefab

保留已加载的预制体资源，减少重复加载。

享元FireballDefinition

多个火球共享同一份类型配置，独立维护自身运行状态。

发生的事件资源缓存对象池共享定义
第一次发射若未命中，加载并保留预制体若无空闲实例，创建 P1 并初始化P1 引用已有定义 D
第二次发射，第一颗仍在飞复用已加载预制体P1 正被占用，另取 P2P1、P2 同时引用 D
第一颗火球结束按保留策略继续保存资源结束旧任务、清理状态，归还 P1D 不随某颗火球的结束而重置
第三次发射仍可复用预制体可以再次借出 P1，初始化新任务状态继续共享 D

这里“最多同时 50 个”描述的是活动峰值，池保留多少实例还取决于具体策略。三者是职责示意，不要求管理器形成固定依赖顺序。

资源缓存回答“是否需要再次加载这个预制体”；对象池回答“能否复用已有空闲运行实例”；享元回答“是否需要为每颗火球复制同一份类型配置”。每一种重复的判断依据不同，但职责可以同时存在。

补充 6 · 用三个问题识别复用机制

  1. 我需要的是某个特定逻辑结果，还是一个可用实例？
    Get("PlayerAvatar") 更接近结果查找；RentBullet() 更接近给新任务分配实例。不要求缓存永远返回同一引用，也不要求池永远返回不同引用。
  2. 拿到之后，是否获得一次独立使用的权利？
    池的借用者通常有临时独占使用权，可修改本次运行状态；读取缓存通常不会自动获得修改共享值的独占权。可变对象应约定返回副本、共享修改或同步规则。
  3. 复用时，哪些旧状态应该保留，哪些必须清除？
    结果缓存保留仍有效的结果；对象池保留可复用资源并清理旧任务状态；享元的共有状态应保持稳定，不随某个使用者的独立运行而改变。

补充 7 · 修正后的定义与抽象边界

概念更准确的本质
广义缓存思想保留已有成果，以降低未来重复工作的成本
典型结果缓存根据请求条件复用仍然有效的结果，结果也可以是对象
对象池管理可借出、归还、重置的实例，使其在不同使用周期中反复承担任务
享元模式多个独立逻辑对象共享相同的内部状态，避免重复存储

它们不是严格互斥的分类：对象池可以被理解为对可复用实例的特殊缓存，享元工厂也可以利用缓存管理共享实例。但工程中区分这些名字，是为了明确各自的契约。

对象池主要维护实例的可用性与独立使用周期；结果缓存主要维护结果的有效性；享元模式主要维护共享状态的边界。

设计契约决定抽象边界。判断两个技术的关系，不只看它们做了什么操作，还要看它们维护什么约束、保证什么性质、解决什么问题。把对象放进容器再取出，既可能是缓存，也可能是池化；相同的底层操作可以承载不同的抽象。

03 / HOW在 Unity 中如何协同？

假设一个弹幕游戏每分钟发射 1000 发子弹，最多同时存在 100 发，分为 5 种类型，还要反复计算部分弹道。

对象池Bullet 实例

围绕约 100 发活动峰值配置实例复用。

缓存TrajectoryCache

相同弹道参数命中时，复用预计算结果。

享元BulletDefinition

5 种类型共享 5 份定义，保留各自运行状态。

1000 是一段时间内的发射总量，100 是同时活动峰值。池中需要多少实例主要由同时活动数量及保留策略决定，不需要为全部 1000 发分别保留实例。

3.1 对象池负责运行时实例

public class Bullet : MonoBehaviour
{
    public BulletDefinition Definition { get; private set; }

    private Vector3 velocity;
    private float lifetime;

    public void Initialize(
        BulletDefinition definition,
        Vector3 position,
        Vector3 velocity)
    {
        Definition = definition;
        transform.position = position;

        this.velocity = velocity;
        lifetime = 0f;

        gameObject.SetActive(true);
    }

    public void ResetState()
    {
        Definition = null;
        velocity = Vector3.zero;
        lifetime = 0f;

        gameObject.SetActive(false);
    }
}

Definition 是共享引用，velocity 和 lifetime 是独立状态。这里的启用安排在数据初始化之后；实际池的借出回调也要配合这个顺序。

Unity 示例需要 UnityEngine。代码展示职责分工，未包含移动、碰撞、计时归还与完整池管理。实际重置还可能涉及协程、异步回调、事件订阅、Rigidbody 速度、粒子、TrailRenderer 和碰撞状态等。

3.2 享元模式负责共享类型定义

[CreateAssetMenu(menuName = "Game/Bullet Definition")]
public class BulletDefinition : ScriptableObject
{
    [SerializeField] private float baseDamage;
    [SerializeField] private float baseSpeed;
    [SerializeField] private Sprite icon;

    public float BaseDamage => baseDamage;
    public float BaseSpeed => baseSpeed;
    public Sprite Icon => icon;
}

同类型子弹引用同一个 BulletDefinition 资源实例，避免各自复制全部配置。每颗子弹的生命时间等运行状态保留在独立实例中。

ScriptableObject 本身不是享元模式的同义词。只有承担多个逻辑对象共享内部状态的职责时，才体现享元特征。而且它在运行时并非天然不可修改，仍需通过设计约束共享配置的修改。

3.3 缓存负责昂贵的重复计算

如果弹道由固定初速度、重力与采样设置决定，可以用参数键查询预计算结果：

private readonly Dictionary<TrajectoryKey, TrajectoryData>
    trajectoryCache = new();

public TrajectoryData GetTrajectory(TrajectoryKey key)
{
    if (trajectoryCache.TryGetValue(key, out var data))
    {
        return data;
    }

    data = CalculateTrajectory(key);
    trajectoryCache.Add(key, data);
    return data;
}

TrajectoryKey 必须包含所有影响结果的必要参数：初速度、重力、采样间隔等。若用相对起点的轨迹表示，则可在使用时叠加各子弹自己的起点。

TrajectoryData 最好不可变，或通过可靠的只读接口防止被调用者意外修改。

TrajectoryKey、TrajectoryData 与 CalculateTrajectory 是说明职责的占位类型和方法，需要由项目实现。以上缓存示例按单线程访问说明原理。

04 / DEEPER VIEW身份、状态与所有权

维度对象池缓存享元模式
身份保留实例身份，反复租用按 Key 查找已有结果，不一定承诺引用身份稳定不同逻辑对象引用同一共享状态实例
状态复用前后通常需要重置命中结果必须仍有效共享部分通常不可变
所有权与使用权池管理保留与销毁，借用者暂时独占使用缓存管理条目保留与失效，底层资源释放责任另行约定多个使用者持有共享引用，最终释放责任另行约定
生命周期空闲 → 借出 → 归还 → 再次借出 / 销毁获取 → 命中 → 失效 / 淘汰 → 重新获取建立共享状态 → 多处引用 → 最终释放

这里的所有权是设计约束，C# 普通引用不会自动强制执行。共享引用也不等于共享销毁权。尤其对于 Unity 对象或其他外部资源，需要明确谁可以最终释放。

4.1 对象池正确性：状态隔离

上一次使用产生的状态，是否会影响下一次使用？

如果归还时仍订阅旧事件，下一次借出可能继续响应旧任务，造成重复处理。重置的意义是建立新旧使用生命周期之间的状态隔离；旧协程或异步回调也必须停止，或验证自己仍属于当前租用。

4.2 缓存正确性：结果有效性

当前请求条件下，原来的结果仍然正确吗？

玩家统计从 100 变为 120，而缓存仍返回 100。即使命中 Key，也可能得到过期数据。因此需要根据契约考虑失效、版本、容量、一致性和并发更新策略。

4.3 享元正确性：共享边界

哪些状态真正属于可以共同使用的部分？

将敌人当前生命值加入共享定义，会破坏敌人之间的逻辑独立性。难点是识别哪些状态可共享，哪些必须独立维护。

05 / TRADE-OFFS设计权衡：复用也有成本

技术主要收益成本和风险
对象池减少创建、销毁与分配开销状态残留、重复归还、容量管理、空闲对象占用内存
缓存降低重复计算、查询或读取成本过期数据、失效策略、额外内存、一致性与并发问题
享元减少重复持有的相同状态状态拆分复杂度、引用间接访问、共享可变状态风险

仅含两个整数的小型 C# 对象，如果构造与回收成本很低，池化可能更麻烦，甚至更慢。只会请求一次的计算结果，保存到缓存通常没有收益。

如果每个对象的数据几乎都不同，或共享部分非常小，强行拆分也可能使维护成本大于收益。应根据实际测量和需求选择。

设计的目标是找到值得消除的重复成本。复用带来的管理成本必须一并计算。

06 / DECISION GUIDE如何判断应该使用哪一个？

先描述当前遇到的重复，再核对对应的正确性前提：

反复创建、使用、销毁同类实例 → 考虑对象池确认创建成本显著、并发活动数量可估计、旧任务能结束、状态能可靠重置、借用与归还责任明确。
反复获取或计算相同结果 → 考虑缓存确认输入可作为准确的 Key、结果有效性可判断、请求有足够重复率、容量与淘汰策略可接受。
大量逻辑对象保存相同信息 → 考虑享元确认共享状态可从上下文中分离、独立状态保留在各自对象中、共享修改受到约束、节省量值得复杂度。

选择并不互斥。同一份定义可以通过缓存加载，再作为享元供多个池化实例共享。

07 / ESSENCE回到「复用」的本质

对象池：管理可再次使用的实例及其生命周期，避免频繁重新创建和销毁资源。

对象池 = 实例复用 + 生命周期管理

广义缓存：保留已有成果，以降低未来重复工作的成本。对象池可以看作这一思想的应用，但这不是要求所有术语体系都将对象池严格归为缓存子类。

典型结果缓存：根据请求条件复用仍然有效的结果，结果本身也可以是对象。

典型结果缓存 = 结果复用 + 有效性管理

享元模式：提取并共享多个逻辑对象共有的内部状态，避免分别保存相同副本。

享元 = 状态共享 + 状态边界划分
对象池：这个实例使用结束后，能不能给下一次任务使用？
缓存：这个结果已经得到过，能不能直接返回？
享元：这些不同的逻辑对象，是否需要各自保存一份相同数据？

三者分别突出实例生命周期、结果获取、状态组织三个设计维度，职责可以重叠。对象池通常维护实例的可用性与独立使用周期，结果缓存主要维护结果有效性，享元模式主要维护共享边界。

对象池确实保留了对象的创建成果。给它单独命名，是为了表达资源分配与生命周期管理契约。判断一种设计，应看它维护什么约束、保证什么性质、解决什么问题，不能只看它是否保存对象、是否减少创建次数。

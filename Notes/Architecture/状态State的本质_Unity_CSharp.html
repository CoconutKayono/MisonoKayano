状态的本质。

系统为了决定接下来该如何行动，而必须记住的过去。

State 第一性原理6 个主题Unity C# 示例本地 HTML

过去不必全部留下。
状态，保留的是对未来仍有影响的信息。

STATE / 当前状态现在保留什么信息
INPUT / 新的输入这一次发生什么
TRANSITION / 转换依照规则计算下一步

更严格地说：

状态是系统在某一时刻所保留的信息。这些信息与新的输入一起，决定系统接下来如何变化、如何响应。

我们按照 What → Why → How，从第一性原理理解它。

01What：什么是状态？

先不要把状态理解成 enum、bool 或者某个类的字段。这些只是状态的表达方式，不是状态的本质。

想象游戏里有一扇门。

交互示意 01

同一个 OpenDoor，不同的响应

输入 × 当前状态

当前状态：门已关闭。发送指令，观察响应。

同样是“打开门”的请求，是否执行、是否拒绝，需要结合当前状态判断。

假设玩家发出一个指令：

OpenDoor

同样的输入，为什么系统可能有不同的反应？

  • 门是关闭的：执行开门。
  • 门已经打开：不需要再次开门。
  • 门被锁住：拒绝打开。

因为系统除了知道玩家想做什么，还必须知道门现在是什么情况。

这个“现在的情况”，就是状态。

1. 状态是一种对过去的记忆

门为什么是打开的？因为过去发生过开门操作。

但是系统通常不必记住每一次开门动作，只需要记住：

状态表示片段C# · 概念片段，需置于相应上下文
bool isOpen = true;

过去发生的事情，被压缩成了当前的信息。

所以可以这样理解：

状态 = 过去发生的事情，对当前和未来仍然有影响的那部分信息。

这也引出了非常重要的区分：

概念 回答的问题 示例
状态 State 现在是什么情况？ 门已打开
事件 Event 发生了什么？ 玩家打开了门
输入 Input 希望系统做什么？ 请求打开门
行为 Behavior 系统能做什么？ 打开、关闭、上锁
状态转换 Transition 状态如何变化？ 关闭 → 打开

它们相互关联，但并不是一回事。

02Why：为什么需要状态？

从最简单的程序开始。

1. 没有状态的程序

一个加法函数：

无状态函数 · AddC# · 概念片段，需置于相应上下文
int Add(int a, int b)
{
    return a + b;
}

只要输入相同，输出就相同。

数学上可以写成：

y = f(x)

系统不必记住之前调用过几次 Add。

2. 有状态的程序

再看游戏中玩家受到伤害：

有状态函数 · TakeDamageC# · 概念片段，需置于相应上下文
int health = 100;

void TakeDamage(int damage)
{
    health -= damage;
}

第一次受到 20 点伤害，生命值从 100 变成 80。

第二次受到 20 点伤害，生命值从 80 变成 60。

交互示意 02

同样受到 20 点伤害，结果依赖当前 HP

存活
100/ 100
100 / 100

当前 HP = 100；输入伤害后，将基于这一次的状态计算。

遵循下文 Health 的规则：HP 不低于 0、不超过上限；死亡后普通治疗无效。“重置演示”表示重新创建一个初始生命值为 100 的对象。

为什么两次相同的输入会得到不同结果？

因为这次计算需要使用上一次计算之后留下的状态。

数学表达是：

St+1 = T(St, It)

其中：

  • St：系统当前的状态。
  • It：当前输入。
  • T：状态转换规则。
  • St+1：处理输入之后的新状态。

对于生命值系统：

HPnext = max(0, HPcurrent − Damage)

这就是有状态系统的核心。

阅读提示：这里示意确定性的转换。如果随机数、时间或网络结果影响响应，也需要把它们纳入输入、外部条件或相应状态，才能讨论相同条件下的一致响应。

过去影响未来，而状态就是连接过去与未来的桥梁。

如果没有状态，每次请求都只能依赖当前输入。你就无法仅凭一个“受到 20 点伤害”的指令，知道玩家最终还剩多少生命。

03How：程序中如何设计状态？

本质上只需要三个部分：

当前状态（State）

例如 HP = 80

输入 + 转换规则（Input + Transition）

受到 20 点伤害，HP 不小于 0

新状态（Next State）

HP = 60

我们用 Unity C# 写一个简单但合理的生命值系统。

Health.csC# · 完整类型定义

using System;

public sealed class Health
{
    public int MaxHP { get; }
    public int CurrentHP { get; private set; }

    // 通过现有状态推导，不需要额外存储
    public bool IsDead => CurrentHP == 0;

    public Health(int maxHP)
    {
        if (maxHP <= 0)
            throw new ArgumentOutOfRangeException(nameof(maxHP));

        MaxHP = maxHP;
        CurrentHP = maxHP;
    }

    public void TakeDamage(int damage)
    {
        if (damage <= 0 || IsDead)
            return;

        CurrentHP = Math.Max(0, CurrentHP - damage);
    }

    public void Heal(int amount)
    {
        if (amount <= 0 || IsDead)
            return;

        CurrentHP += Math.Min(amount, MaxHP - CurrentHP);
    }
}

注意这里的三个重要设计思想。

第一，状态需要被表达。

CurrentHP 保存当前生命值。

第二，状态的改变需要遵循规则。

外部不能随便修改 CurrentHP，而是通过 TakeDamage 和 Heal 进行修改，保证生命值不会小于 0 或超过上限。

第三，不是所有状态相关信息都需要独立存储。

例如：

派生状态 · IsDeadC# · 概念片段，需置于相应上下文
public bool IsDead => CurrentHP == 0;

既然通过 CurrentHP 就能推导出是否死亡，那么通常不必再保存一个独立的 isDead 字段。

否则就有可能出现：

矛盾状态反例C# · 概念片段，需置于相应上下文
CurrentHP = 0;
isDead = false;

同一个玩家出现了互相矛盾的信息。

这引出了实际开发中很有价值的原则：

优先保存必要的原始状态，能够可靠推导的信息就尽量推导。

04State 和 State Machine 有什么区别？

这是一个很容易混淆的地方。

State（状态）是信息；State Machine（状态机）是组织状态及其转换规则的一种模型。

例如角色可以处于：

CharacterState.csC# · 完整类型定义
public enum CharacterState
{
    Idle,
    Running,
    Jumping,
    Dead
}

状态机进一步规定：

Idle待机
Running奔跑
Jumping跳跃
Dead死亡
当前状态 → 新状态转换条件
Idle → Running / Running → Idle开始移动 / 停止移动
Idle 或 Running → Jumping满足起跳条件并收到跳跃输入
Jumping → Idle 或 Running落地后，根据是否继续移动决定
任一存活状态 → Dead生命值变为 0

这是教学用的简化模型。此处没有定义复活；实际项目也可把生命、移动和动作拆成独立的状态维度。

但不要因此认为所有状态都需要状态机。

角色的生命值、金币数量、背包道具数量都是状态。它们不一定适合用有限状态枚举来描述。

  • 数值状态：HP = 80
  • 布尔状态：isOpen = true
  • 离散状态：MovementState = Jumping
  • 复合状态：角色的 HP、位置、装备、当前动作等共同组成角色状态

状态机特别适合管理具有明确阶段、转换条件和行为约束的系统。

05更深入：怎么判断什么东西应该成为状态？

这里可以使用一个非常本质的判断标准：

如果两个系统拥有完全相同的当前信息，接下来接收到相同的输入，在相同外部条件下，能不能做出正确且一致的响应？

如果不能，说明你描述的状态可能不够完整。

例如游戏背包：

你记录了当前拥有 5 个苹果。

但游戏有一个成就：“累计获得 100 个苹果”。

那么仅仅记住现在有 5 个苹果就不够。

玩家 A 可能累计获得过 10 个，玩家 B 可能累计获得过 150 个，他们虽然有相同的背包状态，但成就系统应该做出不同的判断。

所以如果需要支持这个成就，就还必须保留累计获得数量，或者保存足以可靠计算这个数量的历史记录。

这也说明：

状态的边界取决于系统未来需要回答什么问题、执行什么行为。

另外，状态还有几个经常被混淆的概念：

概念 本质
State 系统当前保留的信息
Data 对信息的泛称，可能是状态、常量、历史记录等
Event 某个时间点发生的事实
Persistence 将信息持久化，以便系统重启后恢复
State Machine 对状态及其转换规则的建模方式

尤其要记住：状态不等于存档。

一个玩家的当前血量在内存中，也是状态；写进数据库后，它成为持久化的状态。持久化解决的是如何跨越进程重启保存或恢复信息，而状态本身解决的是系统需要记住什么。

06最终回到本质

从三个层面总结：

What：状态是什么？

状态是系统当前保留的、对后续行为有影响的信息。它可以看作与未来有关的过去的摘要。

Why：为什么需要状态？

因为系统的行为往往不能仅由当前输入决定，还取决于之前发生过什么。

How：如何实现状态？

定义需要保留的信息，并规定输入如何触发合法的状态转换；必要时使用状态机、事件、持久化等机制进行组织。

最终，你可以用这个公式理解大量软件系统：

新状态 = 转换规则(当前状态, 输入)

甚至可以进一步思考：

程序的大量工作，本质上就是读取状态、根据规则计算、更新状态，再把结果呈现出来。

MVC、状态机、响应式 UI、游戏实体系统、数据库事务，都从不同角度处理状态的组织、转换、观察或一致性问题。

理解了这一点，学习这些架构时，就不必只记它们的形式，而能开始追问：它们到底在解决状态的哪个问题？

01一句话抓住本质

MVC 把“业务是什么”“如何展示业务”“如何响应用户操作”这三件不同的事情分开。

MVC 不是某种算法，也不要求必须创建三个文件夹。它是一种围绕交互组织职责的架构模式。判断是否分离成功，要看业务、界面和操作协调分别由谁负责，以及它们之间依赖什么。

02What：MVC 是什么

MVC = Model、View、Controller。

组成 核心职责 本质 Unity 计数器中的对应物
Model（模型） 管理业务状态和业务规则 业务本身 当前数值、上限、是否允许增加
View（视图） 将状态呈现给用户 表现 文本、按钮、布局与显示格式
Controller（控制器） 接收操作意图，协调业务操作 交互协调 把“请求 +1”转成 Model 方法调用

以计数器为例：屏幕显示 0，用户点击 +1，屏幕变成 1。

用户点击 +1
    ↓
Controller 处理“增加一次”的意图
    ↓
Model 检查上限，修改数值
    ↓
View 显示更新后的数值

这个流程描述一次交互的含义，并不要求底层必须按同一种调用链实现。按钮也只是输入入口，键盘、手柄、自动化测试都可以触发同一个业务操作。

Model：业务状态与规则

Model 回答：现在是什么状态？允许发生什么变化？

在本例中，它要保证：初始值合法；计数只能通过受控方法增加；达到上限后不能继续增加。即使调用者绕过按钮，规则仍然有效。

Model 并非只能存字段。TryIncrement() 中对上限的检查，同样属于 Model 的职责。

View：状态的呈现与输入适配

View 回答：把状态显示成什么样？

它管理文本、按钮、布局、颜色等表现细节。本例也让它把 Unity 按钮回调转换成 IncrementRequested 事件，但它不决定点击后能否增加，也不直接修改业务状态。

“转发用户意图”和“决定业务处理方式”是不同职责。Unity 的 UI 控件已封装底层输入处理，没有必要为了套用三个名字再造一套按钮系统。

Controller：操作协调

Controller 回答：用户想做什么，应调用哪个业务操作？

它订阅操作意图，调用 Model。实际项目中还可能协调应用服务、导航或一次完整用例，但不应把余额、库存、伤害等领域规则全塞进 Controller。

03Why：为什么需要 MVC

假设把业务状态、持久化和显示全部写在一个按钮事件里。下面是原文反例的 Unity C# 版本，仅用于说明耦合，不是推荐实现：

CoupledCounterExample.cs反例 · 仅用于说明耦合
using TMPro;
using UnityEngine;

public sealed class CoupledCounterExample : MonoBehaviour
{
    [SerializeField] private TMP_Text label;
    private int count;

    // 可由 Inspector 的 Button.onClick 调用。
    public void OnIncrementClicked()
    {
        count++;                                      // 修改业务状态
        PlayerPrefs.SetInt("Counter.Count", count);    // 写入本地偏好数据
        PlayerPrefs.Save();                           // 持久化到磁盘
        label.text = count.ToString();                // 更新界面
    }
}

这里用 PlayerPrefs 替代原反例中示意性的 database.save，只是展示“按钮回调同时负责存储”的问题；它不代表数据库方案，也不属于后面的完整实现。API 见 PlayerPrefs.SetInt 与 PlayerPrefs.Save。

程序小时，这样写很直接。随着需求增长，可能出现：

  • 主界面和暂停面板都要显示相同数值。
  • 手机触控、键盘和手柄都要增加数值。
  • 自动化测试需要验证上限。
  • 计数不能超过 100。
  • 存档方式需要更换。

如果上限判断只写在一个按钮回调里，另一个入口就可能漏掉。如果修改界面时还要复制业务规则，业务便被绑在具体界面上。

MVC 要解决的核心问题并不是“代码太长”，而是：

不同原因导致的变化，不应该迫使不相关的代码一起变化。

变化原因 主要修改位置 说明
修改计数上限或增加规则 Model 或传入的业务配置 规则最终仍由 Model 执行
修改字体、布局、颜色 View 不需要重写计数规则
改为长按、手柄或其他输入 输入适配与 Controller 业务操作可以继续复用
更换存档方案 存储适配或应用服务 不必改动文本显示代码

这表示变化的主要落点，不承诺每次需求都只修改一个文件。例如新增“批量增加”可能同时需要按钮、操作协调和业务方法。职责分离的价值在于让每处修改有明确原因。

04How：先确定职责与依赖

原文的简化方案：Controller 主动刷新

原 JavaScript 的含义可以概括为：

Controller 接收操作
    → Model 增加计数
    → Controller 读取新状态
    → Controller 调用 View 显示

这是一种容易理解的交互组织方式。在 Web MVC 中，Controller 常常选择 View 并提供数据；在 Unity 中也能使用类似的主动刷新方式。

如果一个 Unity View 完全被动，所有显示更新都由中间协调者完成，那么按更细的 GUI 模式分类，这种结构往往更接近 MVP 的 Passive View。不能只凭类名叫 Controller 就断定它属于经典 MVC。

本文完整实现：View 观察 Model

完整示例采用另一种方式：

输入路径：
Button.onClick → CounterView 转发意图 → CounterController → CounterModel

显示路径：
CounterModel 状态变化 → Changed 事件 → CounterView 读取状态 → 更新 UI

Controller 不主动调用刷新方法。View 订阅 Model 暴露的变化事件，并通过只读接口读取最新状态。这体现了经典 MVC 中观察模型的一种思路；Unity 按钮的输入转发属于工程上的适配。

MVC 有不同实现形态。稳定的原则是分离业务与表现，而不是强行规定唯一的调用顺序。关于 MVC、观察同步及 MVP 的区分，可参考 Martin Fowler 的 GUI Architectures。

把代码依赖和运行流程分开看

下图中的箭头表示“代码中认识、引用某个类型或接口”，不是事件发生顺序：

CounterModel ──────────────→ ICounterState
CounterView ───────────────→ ICounterState、ICounterInput、Unity UI
CounterController ────────→ ICounterInput、CounterModel
CounterSceneRoot ─────────→ CounterModel、CounterView、CounterController

其中 CounterModel 和 CounterView 分别实现相应接口。Model 不引用 Unity、View 或 Controller；Controller 不引用按钮和文本；View 只持有 Model 的只读接口。

CounterSceneRoot 是装配入口：它创建对象、连接引用，并管理生命周期。装配入口认识各部分很正常，不必强行塞进 M、V、C 的某个业务角色。

05Unity C# 完整实现

示例范围与文件结构

示例使用 Unity 的 GameObject / MonoBehaviour、uGUI Button 和 TextMeshPro 文本。API 参考以 Unity 6 文档为准，不依赖 MVC 框架。

只把下面五个文件放入项目；前面的 CoupledCounterExample 是独立反例，不参与场景搭建。

Assets/Scripts/MvcCounter/
├── CounterContracts.cs
├── CounterModel.cs
├── CounterView.cs
├── CounterController.cs
└── CounterSceneRoot.cs

Model 和 Controller 是普通 C# 对象，用 new 创建。View 和场景装配入口继承 MonoBehaviour，挂在 GameObject 上。

1. CounterContracts.cs：只读状态与操作意图

CounterContracts.csUnity C# · 配套脚本
using System;

namespace MvcCounter
{
    public interface ICounterState
    {
        int Count { get; }
        int Maximum { get; }
        bool CanIncrement { get; }
        event Action Changed;
    }

    public interface ICounterInput
    {
        event Action IncrementRequested;
    }
}

ICounterState 让 View 读取状态、订阅通知，但不向它暴露修改方法。ICounterInput 让 Controller 接收意图，不需要知道输入来自 uGUI Button 还是测试对象。

接口是本例控制依赖的工具，不是 MVC 必须具备的形式要求。

2. CounterModel.cs：状态与上限规则

CounterModel.csUnity C# · 配套脚本
using System;

namespace MvcCounter
{
    public sealed class CounterModel : ICounterState
    {
        public int Count { get; private set; }
        public int Maximum { get; private set; }
        public bool CanIncrement => Count < Maximum;

        public event Action Changed;

        public CounterModel(int maximum = 100, int initialCount = 0)
        {
            if (maximum < 1)
                throw new ArgumentOutOfRangeException(nameof(maximum));

            if (initialCount < 0 || initialCount > maximum)
                throw new ArgumentOutOfRangeException(nameof(initialCount));

            Maximum = maximum;
            Count = initialCount;
        }

        public bool TryIncrement()
        {
            if (!CanIncrement)
                return false;

            Count++;
            Changed?.Invoke();
            return true;
        }
    }
}

它不知道按钮、文本、GameObject，也不知道调用来自点击还是其他系统。

规则由 Model 执行：即使某个调用者绕过 UI 连续调用，计数仍不能超过上限。只有真实的状态变化才触发 Changed，达到上限的拒绝操作不触发刷新。

这里把原文中的“达到上限就抛异常”改成 false，用于表达一种预期内的操作失败。构造参数非法则仍抛异常，因为那属于错误的对象配置。调用者如需显示拒绝提示，可以使用返回值；本例通过禁用 +1 按钮表达上限状态。

3. CounterView.cs：呈现状态、转发输入

CounterView.csUnity C# · 配套脚本
using System;
using TMPro;
using UnityEngine;
using UnityEngine.UI;

namespace MvcCounter
{
    public sealed class CounterView : MonoBehaviour, ICounterInput
    {
        [SerializeField] private TMP_Text countText;
        [SerializeField] private Button incrementButton;

        private ICounterState state;
        private bool observing;

        public event Action IncrementRequested;

        public bool IsConfigured =>
            countText != null && incrementButton != null;

        public void Bind(ICounterState newState)
        {
            StopObserving();
            state = newState;

            if (isActiveAndEnabled)
            {
                StartObserving();
                Render();
            }
        }

        private void OnEnable()
        {
            if (!IsConfigured)
            {
                Debug.LogError("CounterView 缺少文本或按钮引用。", this);
                enabled = false;
                return;
            }

            incrementButton.onClick.AddListener(ForwardIncrement);
            StartObserving();
            Render();
        }

        private void OnDisable()
        {
            if (incrementButton != null)
                incrementButton.onClick.RemoveListener(ForwardIncrement);

            StopObserving();
        }

        private void StartObserving()
        {
            if (observing || state == null)
                return;

            state.Changed += Render;
            observing = true;
        }

        private void StopObserving()
        {
            if (!observing)
                return;

            state.Changed -= Render;
            observing = false;
        }

        private void ForwardIncrement()
        {
            IncrementRequested?.Invoke();
        }

        private void Render()
        {
            if (!IsConfigured)
                return;

            if (state == null)
            {
                countText.text = "--";
                incrementButton.interactable = false;
                return;
            }

            countText.text = state.Count.ToString();
            incrementButton.interactable = state.CanIncrement;
        }
    }
}

View 做了两类适配：把 state.Count 转成文本、把 state.CanIncrement 转成按钮可用状态；把按钮点击转成操作事件。它没有计算 Count + 1，也没有自行实现 Count < 100 的业务判断。

OnEnable 订阅、OnDisable 退订，并在重新启用时主动读取最新状态。这样，即使面板隐藏期间 Model 被其他系统修改，重新打开后也能显示正确值。

Bind 同样处理订阅和首屏显示，因此不要求不同组件的 Awake / OnEnable 按某个特定先后顺序运行。方法名监听器也方便使用同一委托退订。

4. CounterController.cs：把意图映射成业务操作

CounterController.csUnity C# · 配套脚本
using System;

namespace MvcCounter
{
    public sealed class CounterController : IDisposable
    {
        private readonly ICounterInput input;
        private readonly CounterModel model;
        private bool active;
        private bool disposed;

        public CounterController(ICounterInput input, CounterModel model)
        {
            this.input = input ?? throw new ArgumentNullException(nameof(input));
            this.model = model ?? throw new ArgumentNullException(nameof(model));
        }

        public void Activate()
        {
            if (disposed)
                throw new ObjectDisposedException(nameof(CounterController));

            if (active)
                return;

            input.IncrementRequested += HandleIncrement;
            active = true;
        }

        public void Deactivate()
        {
            if (!active)
                return;

            input.IncrementRequested -= HandleIncrement;
            active = false;
        }

        private void HandleIncrement()
        {
            // 业务是否允许增加，由 Model 判断。
            // 状态变化后的界面刷新，由 View 的模型订阅触发。
            model.TryIncrement();
        }

        public void Dispose()
        {
            Deactivate();
            disposed = true;
        }
    }
}

Controller 不重复检查上限，也不直接访问文本。Activate / Deactivate 的重复调用不会重复订阅或造成重复处理。

本例没有展示拒绝操作的额外提示，因此不消费 TryIncrement() 的返回值。需要提示时，可以新增反馈接口或独立提示事件，但上限判断仍应留在 Model。

5. CounterSceneRoot.cs：创建与装配

CounterSceneRoot.csUnity C# · 配套脚本
using UnityEngine;

namespace MvcCounter
{
    public sealed class CounterSceneRoot : MonoBehaviour
    {
        [SerializeField] private CounterView view;
        [SerializeField, Min(1)] private int maximum = 100;

        private CounterModel model;
        private CounterController controller;

        private void Awake()
        {
            if (view == null || !view.IsConfigured)
            {
                Debug.LogError("请配置 CounterView 及其 UI 引用。", this);
                enabled = false;
                return;
            }

            // Inspector 的 Min 约束之外，Model 仍会验证参数。
            model = new CounterModel(maximum);
            controller = new CounterController(view, model);
            view.Bind(model);
        }

        private void OnEnable()
        {
            controller?.Activate();
        }

        private void OnDisable()
        {
            controller?.Deactivate();
        }

        private void OnDestroy()
        {
            controller?.Dispose();

            if (view != null)
                view.Bind(null);
        }
    }
}

这个 MonoBehaviour 是 Unity 场景与普通 C# 对象之间的桥梁。业务对象只在 Awake 中创建一次；隐藏再显示面板时，原 Model 继续使用，计数不会因为重新订阅而归零。

场景卸载并重新创建装配入口时，会创建新的 Model。这个示例没有实现跨场景保留或存档恢复。

场景搭建

  2. 将五个文件按上述文件名保存到 Assets/Scripts/MvcCounter/。不要把所有代码粘进同一个文件。
  3. 创建一个 Canvas，在其下创建名为 CounterPanel 的 UI 面板。
  4. 在面板内创建一个 TextMeshPro 文本，用于显示数值；再创建一个 Button，按钮文字设为 +1。

  9. 确认场景有 EventSystem，并按项目所用输入方案配置对应 UI Input Module；Canvas 需要正常的 GraphicRaycaster。进入 Play Mode。
Canvas
└── CounterPanel

    ├── CounterSceneRoot（组件）

EventSystem

预期行为

操作 预期结果
首次运行 文本显示 0，按钮可用
点击一次 显示 1
继续点击到上限 显示 100，按钮不可用
绕过 UI 调用 Model 达到上限后返回 false，数值保持 100
停用再启用 CounterPanel 保留当前数值，再次点击只增加一次
隐藏期间由其他系统修改同一个 Model 重新启用 View 时显示最新状态

最后一种情况说明重新启用时主动 Render() 的意义；当前最小场景没有提供额外的修改入口。

跟踪一次点击

1. Button.onClick 调用 CounterView.ForwardIncrement()
2. View 发出 IncrementRequested
3. Controller.HandleIncrement() 调用 Model.TryIncrement()
4. Model 检查 CanIncrement，通过后修改 Count
5. Model 发出 Changed
6. View.Render() 读取 Count 和 CanIncrement
7. 文本与按钮状态更新

这是普通 C# 事件的同步调用链。它不需要每帧在 Update() 中轮询，也没有通过事件自动创建异步任务。

07依赖与职责的准确解释

Model 不知道 View，为什么能通知 View

Model 只声明通用的 Changed 事件，并调用已注册的委托。订阅者可以是 View、日志记录器或测试对象；Model 的源码不需要引用它们的具体类型。

但“不依赖 View 的具体类型”不等于“运行时完全没有引用关系”。订阅发生后，事件委托通常会持有订阅者对象的引用，因此必须管理退订，否则长寿命 Model 可能保留已不需要的 View。

本例中，View 在 OnDisable 退订 Model；Controller 在 Deactivate / Dispose 退订输入。装配入口负责调用 Controller 的生命周期方法。

View 能不能直接读取 Model

可以。本例通过只读接口读取 Model，并在 Model 变化时刷新。把“View 绝不能接触 Model”当作所有 MVC 的固定规则并不准确。

如果采用被动 View，则可由 Presenter 或 Controller 读取 Model 再把显示数据推给 View。应先明确所用变体，再解释依赖，不能混用几种方案的规则。

禁用按钮，是不是把业务规则写进了 View

不是。View 使用的是 Model 已经计算出的 CanIncrement，并把它呈现为 Button.interactable。

真正的规则仍在 Model 中执行。按钮禁用改善交互体验；Model 的检查保证其他入口也不能违反规则。不能只依靠按钮状态保护业务约束。

Model 一定必须是普通 C#，Controller 一定不能是 MonoBehaviour 吗

都不是硬性规定。本例使用普通 C#，是为了让规则与 Unity 场景、UI 和生命周期保持较少依赖，便于独立验证。

某些实际游戏系统需要 Transform、物理或其他 Unity 能力，可以通过接口适配，或有意识地接受引擎依赖。关键是知道耦合来自哪里，而不是机械禁止某种基类。

MonoBehaviour 是 Unity 的组件与生命周期机制，不是 MVC 中的第四种业务角色。它既可承载 View，也可作为输入适配器、Controller 宿主或装配入口。

事件和接口就等于彻底解耦吗

不是。接口减少对具体实现的依赖；事件减少发布者对订阅者类型的了解。双方仍然依赖事件含义、调用时机和状态契约。

本例约定状态先修改、再同步通知；UI 相关调用发生在 Unity 主线程。若未来由后台线程或网络回调修改状态，需要先安排到合适的线程，再触发 Unity UI 更新。

为什么不直接使用一个全局 Model

全局访问方便，但也容易隐藏依赖和生命周期。本例由装配入口创建 Model 并显式传入。

多个 View 如果需要展示同一状态，可以绑定同一个 ICounterState；如果 Model 需要比单个面板活得更久，就应把它的所有权移到更长寿命的游戏会话或应用服务。本例的 Model 所有权属于当前场景装配入口。

08最容易误解的三个地方

第一，Model 不等于数据库

Model 表示业务状态和规则，可能包含领域对象、领域服务，以及与它们协作的应用逻辑。不同架构对“Model”的范围命名并不完全相同。

数据库只是持久化业务数据的一种手段。一个完全不使用数据库的离线游戏，同样有 Model。

Unity 中的 PlayerPrefs、JSON 存档或其他存储方案也不自动等同于 Model。通常可以由存储适配器负责读写，由应用服务协调保存、加载和恢复合法状态。

第二，Controller 不应该装满业务规则

例如“余额是否足够”“是否有库存”“购买后应扣多少钱”属于业务规则，应由 Model 或相应业务层负责。

Controller 可以负责“用户点击购买后发起购买用例”，但不能因为操作从这里进入，就把全部规则都写在这里。

在计数器中，Controller 决定调用 TryIncrement()；Model 决定是否允许增加。这样按钮、手柄和其他调用入口可以共享相同约束。

第三，MVC 不等于三层架构

MVC 主要解决交互界面的职责分离；表现层、业务层、数据访问层是另一个架构划分维度，两者可以同时存在。

划分方式 主要回答的问题
MVC 业务状态、显示、用户操作协调如何分工？
三层架构 表现、业务处理、数据访问如何分层？

不能简单把 Model 等同数据访问层，把 Controller 等同整个业务层，把 View 等同整个表现层。

09如何迁移到实际游戏业务

场景 Model 的规则与状态 View 的表现 Controller 的协调
生命值 当前生命、上限、伤害和恢复约束 血条、数值、受击表现 将操作或用例映射为伤害、恢复调用
商店 余额、库存、价格与购买约束 商品列表、价格、提示 发起购买用例，协调结果反馈
背包 物品数量、容量、堆叠规则 格子、图标、数量文本 把拖拽意图转换成移动或交换操作

这些是职责落点示例，不要求把每种游戏行为都塞进 UI Controller。碰撞、战斗模拟或服务器指令也可通过各自的入口调用业务逻辑。

ScriptableObject 可以用来保存定义和配置，但采用 ScriptableObject 并不会自动实现 MVC。配置资源与每局游戏的可变状态应按生命周期区分；是否写回资源也需要明确设计。

简单程序直接写在一个脚本里可能更合适。只有一个短期原型按钮时，拆出接口和装配入口未必划算；当状态共享、入口增多、规则复杂或需要独立验证时，分离职责的收益更明显。

复杂程序也可能使用 MVP、MVVM、命令模式或其他方式。模式名称服务于设计沟通，不能替代对真实依赖的判断。

10最后的本质

可以暂时忘记 MVC 这三个名字，先问三个问题：

  1. 什么是正确的业务行为？ → Model。
  2. 如何把业务状态呈现出来？ → View。
  3. 用户要做一件事，谁来协调它？ → Controller。

MVC 的核心是控制变化的传播范围，降低耦合，让业务逻辑不依附于某一种界面。

在本例中，最能证明分离有效的事实是：不创建 Canvas、不创建按钮，也可以实例化 CounterModel 并验证它绝不会超过上限。界面负责让规则可见，Controller 负责让操作抵达业务，Model 负责让业务始终正确。

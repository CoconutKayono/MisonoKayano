Dependency Graph（依赖图）与 Dirty Flag（脏标记）：What · Why · How

这两个概念是理解缓存失效、增量计算、响应式系统、游戏引擎更新机制以及构建系统的重要基础。

它们经常一起出现，但实际上解决的是两个不同的问题：

  • Dependency Graph（依赖图）：当某个数据发生变化时，究竟会影响哪些数据？
  • Dirty Flag（脏标记）：某个数据的计算结果，是否已经不能保证正确，需要重新计算？

先给出一个核心结论：

依赖图描述变化的影响范围，脏标记记录计算结果是否失效。两者结合，可以让系统只重新计算那些受到影响、并且实际需要使用的数据。

这背后有一个非常重要的设计思想：

数据发生变化，不代表必须立即重新计算所有依赖它的结果。我们可以先记录哪些结果已经失效，等真正需要时再计算。

一、What：它们究竟是什么？

1. Dependency Graph：依赖图

假设我们正在开发一个 RPG 游戏。

玩家的战斗属性由以下数据决定：

  • 基础攻击力 BaseAttack
  • 装备攻击加成 EquipmentBonus
  • 总攻击力 TotalAttack
  • 暴击伤害 CriticalDamage
  • 战斗评分 CombatPower

它们之间存在计算关系：

TotalAttack=BaseAttack+EquipmentBonus
CriticalDamage=TotalAttack × 2
CombatPower=TotalAttack+CriticalDamage

把这些依赖关系表示成图：

概念示意：箭头从被依赖的数据指向依赖它的结果。实际实现中，CombatPower 同时依赖 TotalAttack 和 CriticalDamage。

用数学语言描述：

G=(V,E)

其中：

  • V 是节点集合，每个节点代表一个数据或计算结果。
  • E 是有向边集合，每条边表示一种依赖关系。

我们约定：

A → B

表示 B 依赖 A。

如果 A 改变，那么 B 可能受到影响。

例如：

BaseAttack → TotalAttack
TotalAttack → CriticalDamage

即使 CriticalDamage 不直接读取 BaseAttack，它也存在间接依赖。

因此：

BaseAttack → TotalAttack → CriticalDamage

依赖图的价值，就是让间接影响也可以被系统追踪。

依赖图只描述数据之间的关系，本身并不规定什么时候计算、是否缓存、如何通知变化。

2. Dirty Flag：脏标记

Dirty Flag 通常只是一个布尔变量：

private bool _isDirty;

它记录的是：

当前缓存的计算结果，是否已经不能保证与最新输入一致。

状态 含义 应当如何处理
false（Clean） 缓存结果可以直接使用 返回缓存
true（Dirty） 缓存结果可能已经过期 使用前重新计算

注意这里最重要的一个区别：

Dirty 不等于计算结果一定发生了变化。

例如：

TotalAttack = BaseAttack + EquipmentBonus

初始：
BaseAttack = 10
EquipmentBonus = 5
TotalAttack = 15

随后：
BaseAttack = 12
EquipmentBonus = 3

最终 TotalAttack 仍然是 15。

但是，在输入发生变化、结果尚未重新验证时，我们仍然可以将它标记为 Dirty。

因为 Dirty 的真正含义是：

我已经不能保证旧结果依然正确，需要重新验证或计算。

它不是一个 ValueChanged 标记，而是一个 CacheMayBeInvalid 标记。

3. 依赖图与脏标记如何协作？

当 BaseAttack 改变时：

交互演示：修改输入，再读取计算结果 (模拟)

修改输入时，下游结果被视为失效，但缓存中的旧数值暂时保留。

TotalAttack15Clean
CriticalDamage30Clean
CombatPower45Clean
累计计算批次：0

当前缓存有效，可以直接使用。

这实际上包含三个相互独立的步骤：

  1. Change（变化）：源数据发生修改。
  2. Invalidate（失效）：沿依赖图将受影响的节点标记为 Dirty。
  3. Recompute（重算）：当需要结果时，重新计算并恢复 Clean 状态。

一个重要原则是：

Invalidate ≠ Recompute

失效通知和实际计算是两件不同的事。

二、Why：为什么需要它们？

1. 根本问题：计算结果之间存在因果关系

假设玩家的基础攻击力发生变化。

那么：

  • 总攻击力需要更新。
  • 暴击伤害需要更新。
  • 战斗评分需要更新。
  • 角色 UI 可能需要更新。

最直观的实现：

void SetBaseAttack(int value)
{
    baseAttack = value;

    RecalculateTotalAttack();
    RecalculateCriticalDamage();
    RecalculateCombatPower();
    RefreshUI();
}

这段代码可以正常工作。

但它带来了一个架构问题：

修改一个数据的代码，必须知道所有依赖该数据的系统。

假设以后新增：

  • 技能伤害预测
  • AI 战力评估
  • 装备推荐
  • 属性比较面板

那么 SetBaseAttack() 可能需要不断修改。

它实际上把数据变化与所有下游行为耦合在一起。

依赖图则将这些关系显式化：

BaseAttack
    ↓
TotalAttack
    ├──→ CriticalDamage
    ├──→ CombatPower
    ├──→ SkillDamage
    └──→ UI

数据变化的代码不再需要逐个调用所有相关的计算函数。

它只需要向依赖系统报告：

BaseAttack 发生了变化。

剩下的失效传播由依赖关系决定。

2. 第二个问题：重复计算

假设每一帧都要读取某个计算量很大的结果。

如果采用直接计算：

public float GetCombatPower()
{
    return CalculateCombatPower();
}

无论输入是否改变，每次读取都重新计算。

这可能很浪费。

我们可以加入缓存：

private float _cachedCombatPower;

但是缓存带来了新的问题：

什么时候应该丢弃缓存？

如果永远返回缓存，它可能变成错误数据。

如果每次都重新计算，又失去了缓存的意义。

因此需要脏标记：

public float GetCombatPower()
{
    if (_isDirty)
    {
        _cachedCombatPower = CalculateCombatPower();
        _isDirty = false;
    }

    return _cachedCombatPower;
}

这样：

  • 第一次读取：计算并缓存。
  • 第二次读取：直接返回缓存。
  • 输入发生变化：标记 Dirty。
  • 下一次读取：重新计算。
  • 此后继续读取：返回新缓存。

它解决的是：

如何在保证结果正确的前提下，避免没有必要的重复计算？

3. 第三个问题：变化很频繁，读取却不频繁

假设某个角色在一帧中连续获得了三个属性加成。

BaseAttack: 10 → 12 → 15 → 20

如果每次修改都立即重新计算整条依赖链，就会导致三次计算。

但用户可能只需要最终的攻击力：

BaseAttack = 20

使用 Dirty Flag：

第一次修改 → 标记 Dirty
第二次修改 → 仍然 Dirty
第三次修改 → 仍然 Dirty

真正读取 → 只计算一次

这就是 延迟计算（Lazy Evaluation）与变化合并（Coalescing） 的作用。

不过必须注意：这种方式适用于允许延迟更新的派生数据，不适用于要求每次变化都独立执行的业务事件，例如每次扣款、每次物品领取记录。

4. 第四个问题：不是所有数据都会受到影响

假设有两个互不相关的计算分支：

Attack ──→ Damage
HP ──────→ HealthBar

攻击力变化，不应使生命值 UI 的计算缓存失效。

这就是依赖图比“全局一个 Dirty 标记”更有价值的原因。

依赖图让系统能够定位受影响的子图，而不是重新计算整个系统。

因此，这两个技术组合起来解决的是：

如何在复杂的数据依赖关系下，维持结果正确性，同时尽量减少重复计算、无关计算与模块之间的显式耦合？

三、How：它们具体如何工作？

1. 核心算法：先传播失效，再按需重新计算

我们先不考虑代码，而是研究算法本身。

假设：

A ──→ B ──→ D
      ↑
C ────┘

其中：

B=f(A,C)
D=g(B)

如果 A 发生变化，那么需要执行两类操作。

第一阶段：失效传播（Invalidation Propagation）

A 发生变化
    ↓
找到 A 的所有直接依赖者
    ↓
B 被标记为 Dirty
    ↓
继续找到 B 的依赖者
    ↓
D 被标记为 Dirty

伪代码：

Invalidate(node):
    if node is already Dirty:
        return

    node.Dirty = true

    for each dependent of node:
        Invalidate(dependent)

这里存在一个非常重要的优化：

如果节点已经 Dirty，并且系统保证失效状态已经完整传播，那么再次遇到它时，可以停止向下传播。

例如，A 在一帧内变化了 100 次。

B 第一次被标记 Dirty 时，会继续使 D 失效。

后面 99 次修改，无须再对这条已经失效的链进行重复传播。

但这依赖于正确维护脏状态及其传播不变量。

第二阶段：按需计算（On-Demand Evaluation）

当程序请求 D 时：

Get(D)
    │
    ├── D 是 Dirty
    │
    ├── D 需要 B
    │      │
    │      ├── B 是 Dirty
    │      ├── 读取最新的 A、C
    │      ├── 重新计算 B
    │      └── B 标记为 Clean
    │
    ├── 使用最新的 B 计算 D
    ├── D 标记为 Clean
    └── 返回 D

伪代码：

Get(node):
    if node is Clean:
        return node.CachedValue

    values = []

    for each dependency of node:
        values.add(Get(dependency))

    result = node.Compute(values)

    node.CachedValue = result
    node.Dirty = false

    return result

你可以发现：

失效是沿依赖关系向下游传播的，计算则会先向上游获取有效输入，再逐层返回结果。

这正是整个机制的核心。

2. 为什么依赖图通常要求无环？

假设出现：

A ──→ B
↑     │
└─────┘

即：

A=f(B)
B=g(A)

那么计算 A，需要先计算 B。

但计算 B，又需要计算 A。

这会造成循环依赖。

在普通的按需重算系统中，通常要求图为：

DAG（Directed Acyclic Graph，有向无环图）。

其重要性质是存在拓扑顺序（Topological Order）。

对于：

A ──→ B ──→ D
      ↑
C ────┘

可能的合法计算顺序是：

A → C → B → D

或：

C → A → B → D

只要满足：

计算一个派生节点之前，先获得它所依赖节点的有效结果。

就可以保证计算顺序正确。

注意，不是所有依赖系统都禁止循环。一些系统允许反馈、迭代求解或固定点计算。但那需要额外的收敛规则，不能直接使用最简单的 DAG 计算算法。

四、C# 实现：从零构建简化依赖计算系统

下面实现一个支持自动失效传播、缓存和按需计算的小型系统。

1. 首先定义节点基类

using System;
using System.Collections.Generic;

public abstract class DependencyNode
{
    // 谁依赖当前节点
    private readonly List<DependencyNode> _dependents = new();

    private bool _dirty;

    protected DependencyNode(
        bool initiallyDirty,
        params DependencyNode[] dependencies)
    {
        _dirty = initiallyDirty;

        foreach (var dependency in dependencies)
        {
            dependency._dependents.Add(this);
        }
    }

    protected bool IsDirty => _dirty;

    protected void MarkClean()
    {
        _dirty = false;
    }

    // 当前节点的数据改变后，通知下游
    protected void InvalidateDependents()
    {
        foreach (var dependent in _dependents)
        {
            dependent.MarkDirty();
        }
    }

    private void MarkDirty()
    {
        if (_dirty)
            return;

        _dirty = true;

        InvalidateDependents();
    }
}

注意，节点保存的是 _dependents，即依赖当前节点的下游节点。

为什么？

因为当当前节点变化时，我们需要找到哪些计算结果会受到影响。

这是一种反向依赖索引。

实际上，完整的图可能同时需要两个方向：

关系 作用
Dependencies：我依赖谁 计算时获取输入
Dependents：谁依赖我 修改时传播失效

示例为了简化，只显式保存 Dependents，而通过计算委托访问依赖。

2. 定义源数据节点

public sealed class SourceNode<T> : DependencyNode
{
    private T _value;

    public SourceNode(T initialValue)
        : base(false)
    {
        _value = initialValue;
    }

    public T Get() => _value;

    public void Set(T value)
    {
        if (EqualityComparer<T>.Default.Equals(_value, value))
            return;

        _value = value;

        // 源数据始终是最新的，
        // 需要失效的是依赖它的计算结果
        InvalidateDependents();
    }
}

源数据和派生数据的区别很重要。

源数据（Source）本身不是通过当前计算图推导出来的，它就是系统中的权威输入。

例如：

SourceNode<int> baseAttack = new(10);

修改源数据，不需要把它自己标记 Dirty。

因为它保存的就是最新值。

真正失效的是依赖它的缓存结果。

3. 定义计算节点

public sealed class ComputedNode<T> : DependencyNode
{
    private readonly Func<T> _compute;

    private T _cachedValue = default!;
    private bool _computing;

    public ComputedNode(
        Func<T> compute,
        params DependencyNode[] dependencies)
        : base(true, dependencies)
    {
        _compute = compute;
    }

    public T Get()
    {
        if (!IsDirty)
            return _cachedValue;

        if (_computing)
            throw new InvalidOperationException(
                "检测到循环计算依赖");

        _computing = true;

        try
        {
            // compute 内部读取其他节点，
            // 会自动确保上游结果有效
            T result = _compute();

            _cachedValue = result;

            // 只有成功计算后才能清除脏标记
            MarkClean();

            return _cachedValue;
        }
        finally
        {
            _computing = false;
        }
    }
}

这里包含四个设计决定：

  1. 计算节点最初是 Dirty，因为还没有有效缓存。
  2. 如果 Clean，直接返回缓存。
  3. 如果 Dirty，运行计算函数，并在成功后清除标记。
  4. 如果计算中出现递归重入，抛出异常，防止无限递归计算。

这里的 _computing 只检测计算过程中的循环重入，并不等于已经对整个图完成了静态无环验证。

如果 _compute() 抛出异常，MarkClean() 不会执行，因此节点保持 Dirty。

这也符合正确性要求：失败的计算不能被当作有效结果缓存。

4. 组合成一个完整的计算图

var baseAttack = new SourceNode<int>(10);
var equipmentBonus = new SourceNode<int>(5);

// 总攻击力
var totalAttack = new ComputedNode<int>(
    () =>
    {
        Console.WriteLine("计算总攻击力");

        return baseAttack.Get()
             + equipmentBonus.Get();
    },
    baseAttack,
    equipmentBonus
);

// 暴击伤害
var criticalDamage = new ComputedNode<int>(
    () =>
    {
        Console.WriteLine("计算暴击伤害");

        return totalAttack.Get() * 2;
    },
    totalAttack
);

// 战斗评分
var combatPower = new ComputedNode<int>(
    () =>
    {
        Console.WriteLine("计算战斗评分");

        return totalAttack.Get()
             + criticalDamage.Get();
    },
    totalAttack,
    criticalDamage
);

第一次读取：

Console.WriteLine(combatPower.Get());

执行过程：

计算总攻击力
计算暴击伤害
计算战斗评分
45

第二次读取：

Console.WriteLine(combatPower.Get());

结果：

45

不会再次执行任何计算函数。

现在修改基础攻击力：

baseAttack.Set(12);

这不会立即执行计算。

但会使三个派生节点进入 Dirty 状态。

再次读取：

Console.WriteLine(combatPower.Get());

结果：

计算总攻击力
计算暴击伤害
计算战斗评分
51

注意 totalAttack.Get() 虽然被两个计算函数调用，但真正的重新计算只执行一次。

这就是依赖图、记忆化与脏标记之间的协同工作机制。

这个示例的适用边界

这是一个教学用的单线程、静态 DAG 实现，已经体现核心算法，但还不是生产级响应式框架。

它依赖以下约定：

  • 每个计算函数所读取的依赖，都应正确登记在节点的依赖列表中。
  • 计算函数应该是无副作用的，不在计算中修改其他源节点。
  • 缓存数据不应被外部绕过变更 API 随意修改。
  • 同一节点的读写遵循单线程执行模型。

如果要支持复杂动态依赖、异步计算、多线程写入或运行时重连边，需要进一步扩展。

五、深入本质：为什么 Dirty Flag 能保证正确性？

这是比实现算法更值得理解的部分。

我们可以为系统建立一个不变量（Invariant）。

对于计算节点 v，定义：

  • Cv：节点缓存的计算结果。
  • fv：节点的计算函数。
  • Dv：其依赖集合。
  • dirty(v)：节点的脏状态。

我们希望维持：

dirty(v)=false ⇒ Cv=fv(Dvcurrent)

通俗地说：

只要一个节点是 Clean，我们就应当能够相信它的缓存与当前有效输入一致。

为了维护这个不变量，必须满足三个条件。

1. 输入变化必须使受影响的下游缓存失效

假设：

A → B → C

如果 A 变化，而 C 仍然保持 Clean，那么：

C 看起来有效
但 C 可能基于旧的 B
而 B 可能基于旧的 A

此时不变量可能已经被破坏。

所以，发生变化的输入必须使所有受影响、已经缓存的后继结果失效。

注意是所有可达的下游结果，不仅仅是直接依赖者。

2. 清除 Dirty 之前必须计算出有效结果

错误做法：

_isDirty = false;
_cachedValue = Calculate();

如果 Calculate() 抛出异常，节点就会处于：

Dirty = false
Cache = 旧结果

正确做法是：

var result = Calculate();

_cachedValue = result;
_isDirty = false;

先完成计算，再提交缓存和有效状态。

更复杂的并发场景还需要版本校验或原子提交，避免计算过程中输入又发生变化。

3. 必须追踪真实的依赖关系

假设：

var damage = new ComputedNode<int>(
    () => attack.Get() + equipment.Get(),
    attack
);

这里存在隐藏错误：

计算函数读取了 equipment，但没有登记它。

当 equipment 改变时，damage 不会被标记 Dirty。

于是旧缓存仍然可能被当成最新结果。

这说明：

依赖图能够维护计算正确性，前提是依赖图本身足够准确。

这也是为什么响应式系统中会出现自动依赖收集（Automatic Dependency Tracking）。

它可以在计算期间追踪实际读取了哪些数据，并自动维护依赖关系。

六、进阶：静态依赖与动态依赖

考虑：

int Calculate()
{
    if (usePhysicalDamage)
        return physicalAttack.Get();

    return magicAttack.Get();
}

这里的依赖关系会随着条件发生变化。

当 usePhysicalDamage = true 时，真正需要的是：

PhysicalAttack → Damage

当 usePhysicalDamage = false 时：

MagicAttack → Damage

这就涉及两种设计。

方案 实现方式 代价
静态依赖图 始终记录两条攻击力依赖和条件依赖 容易实现，但可能产生不必要的失效
动态依赖图 每次计算时收集实际读取的依赖并更新边 更精确，但需要管理依赖增删与生命周期

动态依赖追踪通常采用如下过程：

开始计算 Damage
    ↓
清空或准备新依赖集合
    ↓
记录计算期间实际读取的数据
    ↓
得到新的依赖集合
    ↓
更新旧依赖和新依赖之间的差异
    ↓
提交计算结果

例如，以前订阅了 PhysicalAttack。

现在计算逻辑切换到 MagicAttack。

那么系统需要取消旧的依赖关系，并建立新的关系。

动态依赖还需要处理计算失败、执行期间依赖变化和循环依赖等问题，因此生产实现比上述伪流程更复杂。

七、Dependency Graph 与 Version（版本号）的关系

Dirty Flag 并不是唯一的缓存失效机制。

另一种常见思路是使用版本号。

例如：

private int _dataVersion;
private int _cachedVersion;

源数据每次发生变化：

_dataVersion++;

读取时检查：

if (_cachedVersion != _dataVersion)
{
    Recalculate();
    _cachedVersion = _dataVersion;
}

这叫版本校验。

它和 Dirty Flag 的区别在于：

维度 Dirty Flag Version
记录什么 是否需要重新验证 数据变化到了哪个版本
典型状态 true / false 整数或版本令牌
常见失效方式 主动传播失效 读取时比较版本
主要优势 简单、判断直接 可以区分不同变化代次
主要局限 不表达变化次数或新旧顺序 需要正确维护版本及其对应关系

两者也可以结合。

例如：

SourceA.Version = 10
SourceB.Version = 7

ComputedC 缓存时记录：

A.Version = 10
B.Version = 7

下次读取 C 时，检查 A、B 是否已经发生变化。

但这还不够完整。

如果 C 依赖的是另一个计算节点 B，那么必须先确认 B 自身的输入版本以及派生结果是否有效，才能合理判断 C 的缓存。

因此版本机制并不会自动消除对依赖关系的管理需求。

什么时候适合使用哪一种？

当数据变化较少、读取频繁，而且依赖关系明确时，脏标记传播通常很直接。

当源数据修改极其频繁，但派生数据很少读取时，主动遍历大量下游节点可能反而浪费性能。

这时可以考虑通过版本信息，在读取时懒惰地检查是否失效。

不过这并不意味着版本号一定更快。它只是把一部分维护成本从写入时转移到了读取时，仍然需要根据依赖图结构和实际访问模式做权衡。

八、Unity 中的重要应用：Transform 层级更新

用一个实际场景帮助理解。

假设场景中有：

Player
  └── Weapon
       └── Muzzle

每个对象都有一个本地变换矩阵（Local Matrix）和世界变换矩阵（World Matrix）。

计算关系为：

WorldMatrix=ParentWorldMatrix × LocalMatrix

因此：

Player.WorldMatrix
       ↓
Weapon.WorldMatrix
       ↓
Muzzle.WorldMatrix

如果 Player 移动：

Player.LocalMatrix 改变
       ↓
Player.WorldMatrix 失效
       ↓
Weapon.WorldMatrix 失效
       ↓
Muzzle.WorldMatrix 失效

但失效并不要求马上计算出三个新的世界矩阵。

可以将它们都标记 Dirty。

当渲染、物理或者其他系统真正需要 Muzzle 的世界坐标时：

Get Muzzle.WorldMatrix
       ↓
确保 Player.WorldMatrix 有效
       ↓
确保 Weapon.WorldMatrix 有效
       ↓
计算 Muzzle.WorldMatrix
       ↓
返回结果

整个过程自然遵循父节点到子节点的依赖顺序。

这是一种可以用于 Transform 层级缓存的设计模型，不代表 Unity 引擎内部一定完全按照上面的 C# 实现运作。

它也揭示了另一个问题：

如果武器在一帧中多次移动，系统没有必要每次都重新计算所有子节点的世界矩阵。

通过失效合并，可以把多次输入变化压缩为较少的实际计算。

九、实际开发最容易出现的五个问题

1. 漏掉依赖

计算读取了某个数据，却没有在图中记录它。

后果： 缓存已经过期，但系统仍然认为它是 Clean。

解决方式是显式登记完整依赖，或者使用自动依赖追踪。

2. 存在循环依赖

A 依赖 B，B 又依赖 A。

后果： 普通递归求值可能无限递归。

解决方式是在建图时检测环，或者执行时维护计算中的状态。确实需要循环求解时，应设计独立的迭代规则。

3. 可变对象绕过失效通知

例如：

var stats = statsNode.Get();

stats.Attack += 10;

如果 stats 是一个可变引用对象，这次修改可能没有通过 SourceNode.Set()。

图不会自动发现变化。

解决方式通常是让修改经过受控 API、使用不可变数据，或者引入可观察数据结构。

4. 把 Dirty Flag 当成业务事件

假设某个角色连续获得三次道具。

获得道具 A
获得道具 B
获得道具 C

Dirty Flag 可以记录：

InventoryUI 需要刷新

但它不能可靠记录：

玩家分别获得过 A、B、C

因为多次失效可能被合并为一个 Dirty 状态。

因此：

事件用于表达已经发生的业务事实；脏标记用于表达某个派生结果需要重新验证。

两者不是替代关系。

5. 不必要地构建复杂的全局依赖图

假设一个对象只有：

Width、Height → Area

直接写：

public float Area
{
    get
    {
        if (_dirty)
        {
            _cachedArea = width * height;
            _dirty = false;
        }

        return _cachedArea;
    }
}

可能就已经足够。

并不是所有缓存都需要完整依赖图。

只有当依赖关系复杂、存在多个派生层级、失效传播难以手动维护时，构建显式依赖图才会更有价值。

十、与缓存、记忆化和增量计算的关系

这几个概念可以放到同一个体系中理解：

技术 解决的问题
Cache（缓存） 保存已经获得或计算过的结果
Memoization（记忆化） 对函数输入复用对应的计算结果
Dependency Graph（依赖图） 描述一个结果依赖哪些数据
Dirty Flag（脏标记） 记录缓存结果是否需要重新验证
Cache Invalidation（缓存失效） 定义缓存何时不再可信
Incremental Computation（增量计算） 尽量复用旧工作，只更新受变化影响的部分

它们之间的关系：

输入数据发生变化Source Changed
Dependency Graph定位受影响的下游节点
Dirty Flag标记缓存结果需要重新验证
Lazy Evaluation在需要结果时触发计算
Recompute & Cache复用有效中间结果，更新失效节点

这里有一个值得特别澄清的概念：

Dirty Flag + Dependency Graph 可以构成一种增量计算系统，但不一定意味着节点内部也是增量计算的。

例如，某个节点负责对 100 万个数字求和。

如果其中一个数字发生变化：

  • 基础 Dirty Flag 实现：可能重新遍历 100 万个数字。
  • 更细粒度的增量算法：可以直接从总和中减去旧值，再加上新值。

两者都可能复用依赖图中未受影响的节点，但第二种还进一步利用变化量（Delta）更新节点内部结果。

因此，依赖图管理的是哪些部分需要更新，而真正的增量算法还能解决每个部分如何以最小代价更新。

十一、总结：真正需要建立的思维模型

把数据计算看成一个图，而不是一系列彼此独立的函数。

当输入变化时，系统面对的不是简单的“调用哪个函数”，而是三个更本质的问题：

1. 变化影响了谁？

Dependency Graph 回答依赖关系及其传递范围。

2. 哪些结果已经不能保证正确？

Dirty Flag 记录尚未完成的重新验证或计算工作。

3. 什么时候、按照什么顺序重新计算？

Lazy Evaluation、拓扑顺序和增量计算策略决定执行时机与代价。

我认为最值得记住的是下面三个原则：

原则一：依赖关系决定失效传播的范围。

原则二：失效通知与重新计算应该在概念上分离。

原则三：Clean 是系统提供的正确性承诺，而 Dirty 表示这份承诺暂时不能成立。

理解了这三个原则，你就能进一步理解响应式编程（Reactive Programming）、自动依赖追踪、电子表格的公式重算、Unity 层级变换缓存以及各种增量构建系统。

下一步适合深入的两个主题是 Topological Sorting（拓扑排序）与增量调度，以及 Reactive System（响应式系统）中的自动依赖收集。它们分别延伸了依赖图的执行顺序问题与依赖图的自动维护问题。

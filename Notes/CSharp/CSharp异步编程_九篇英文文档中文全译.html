使用 async 和 await 进行异步编程

基于任务的异步编程（Task asynchronous programming，TAP）模型，为传统的异步代码提供了一层抽象。在这个模型中，你像平常一样，将代码写成一系列语句。不同之处在于：你可以按照先完成当前步骤、再进行下一步的顺序，理解这些基于任务的代码。为了实现这种模型，编译器会进行许多代码转换，以支持各项任务的完成。某些语句可以启动工作，并返回一个表示正在进行的工作的 Task 对象；编译器必须通过转换代码来处理这些流程。基于任务的异步编程，目标是让代码读起来像一系列顺序语句，而实际执行顺序可以更复杂。执行过程取决于外部资源的分配情况，以及任务何时完成。

译者批注 原文关于 compiler 逐句处理和完成任务的措辞不够严谨。本段按上下文译为步骤之间的先后关系。编译器在编译时生成状态机等协调代码；程序运行时的任务由程序、运行时、操作系统或外部服务完成，编译器不会在运行时替你等待任务。

基于任务的异步编程模型，类似于人们为包含异步任务的流程安排步骤时所采用的方式。本文通过做早餐的步骤，说明 async 和 await 关键字如何帮助你理解包含一系列异步指令的代码。做早餐的步骤可以列成下面这样：

  1. 倒一杯咖啡。
  2. 加热平底锅，然后煎两个鸡蛋。
  3. 煎三块薯饼。
  4. 烤两片面包。
  5. 在吐司上涂黄油和果酱。
  6. 倒一杯橙汁。

如果你有烹饪经验，可能会以异步（asynchronous）的方式完成这些步骤。你先加热煎蛋的锅，然后开始煎薯饼。你把面包放进烤面包机，再开始煎鸡蛋。在流程中的每一步，你启动一项任务，然后转去处理其他已经需要你动手的任务。

做早餐很好地展示了不需要并行（parallel）的异步工作。一个人，或者一个线程，就能处理所有任务。一个人可以在上一项任务完成之前启动下一项任务，从而异步地做早餐。无论是否有人一直盯着，每项烹饪任务都能继续推进。一开始加热煎蛋的锅，你就可以开始煎薯饼；薯饼开始煎了之后，你可以把面包放入烤面包机。

对于并行算法，你需要多个人来做饭，或者多个线程。一个人煎鸡蛋，另一个人煎薯饼，依此类推。每个人专注于自己的一项任务。每个做饭的人，或者每个线程，都以同步阻塞的方式等待当前任务达到可处理的状态，例如薯饼可以翻面、面包即将从烤面包机中弹出。

考虑将同一组同步步骤写成 C# 代码语句：

C# · 原文示例，注释已译
using System;
using System.Threading.Tasks;

namespace AsyncBreakfast
{
    // 这些类为演示而特意留空，仅作为标记类，不包含属性，也没有其他用途。
    internal class HashBrown { }
    internal class Coffee { }
    internal class Egg { }
    internal class Juice { }
    internal class Toast { }

    class Program
    {
        static void Main(string[] args)
        {
            Coffee cup = PourCoffee();
            Console.WriteLine("coffee is ready");

            Egg eggs = FryEggs(2);
            Console.WriteLine("eggs are ready");

            HashBrown hashBrown = FryHashBrowns(3);
            Console.WriteLine("hash browns are ready");

            Toast toast = ToastBread(2);
            ApplyButter(toast);
            ApplyJam(toast);
            Console.WriteLine("toast is ready");

            Juice oj = PourOJ();
            Console.WriteLine("oj is ready");
            Console.WriteLine("Breakfast is ready!");
        }

        private static Juice PourOJ()
        {
            Console.WriteLine("Pouring orange juice");
            return new Juice();
        }

        private static void ApplyJam(Toast toast) =>
            Console.WriteLine("Putting jam on the toast");

        private static void ApplyButter(Toast toast) =>
            Console.WriteLine("Putting butter on the toast");

        private static Toast ToastBread(int slices)
        {
            for (int slice = 0; slice < slices; slice++)
            {
                Console.WriteLine("Putting a slice of bread in the toaster");
            }
            Console.WriteLine("Start toasting...");
            Task.Delay(3000).Wait();
            Console.WriteLine("Remove toast from toaster");

            return new Toast();
        }

        private static HashBrown FryHashBrowns(int patties)
        {
            Console.WriteLine($"putting {patties} hash brown patties in the pan");
            Console.WriteLine("cooking first side of hash browns...");
            Task.Delay(3000).Wait();
            for (int patty = 0; patty < patties; patty++)
            {
                Console.WriteLine("flipping a hash brown patty");
            }
            Console.WriteLine("cooking the second side of hash browns...");
            Task.Delay(3000).Wait();
            Console.WriteLine("Put hash browns on plate");

            return new HashBrown();
        }

        private static Egg FryEggs(int howMany)
        {
            Console.WriteLine("Warming the egg pan...");
            Task.Delay(3000).Wait();
            Console.WriteLine($"cracking {howMany} eggs");
            Console.WriteLine("cooking the eggs ...");
            Task.Delay(3000).Wait();
            Console.WriteLine("Put eggs on plate");

            return new Egg();
        }

        private static Coffee PourCoffee()
        {
            Console.WriteLine("Pouring coffee");
            return new Coffee();
        }
    }
}

如果像计算机那样逐条执行这些步骤，准备早餐大约需要 30 分钟。总时长是各项任务所需时间的总和。计算机在每条语句处阻塞，直到该语句的全部工作完成，才执行下一项任务的语句。这种方式可能耗时很长。在早餐示例中，计算机采用这种方式，会做出一顿不太令人满意的早餐。同步列表中靠后的任务，例如烤面包，只有在前面的任务完成后才开始。有些食物在早餐上桌前就已经凉了。

译者批注 这里以及后文的 30、20、15 分钟是早餐比喻和插图中的示意时间，不是代码的实测耗时。代码用 Task.Delay 模拟等待，单位为毫秒。

如果希望计算机异步执行这些步骤，就必须编写异步代码。编写客户端程序时，你希望 UI 能响应用户输入，应用不应在从网络下载数据时冻结所有交互。编写服务器程序时，你不希望阻塞本来可以处理其他请求的线程。在存在异步方案时仍使用同步代码，会妨碍你以较低成本进行横向扩展：被阻塞的线程仍然需要付出资源成本。

成功的现代应用需要异步代码。如果没有语言支持，编写异步代码需要使用回调（callback）、完成事件，或者其他会掩盖代码原本意图的手段。同步代码的优势是动作按步骤排列，容易浏览和理解。传统异步模型迫使你把注意力放在代码的异步机制上，而不是代码要完成的基本动作上。

使用 await，避免阻塞

前面的代码展示了一种不理想的编程做法：用同步代码执行异步操作。这些代码阻塞当前线程，使它无法处理其他工作。在任务运行期间，这些代码不会让出线程来处理其他事情。这种模型就像把面包放进烤面包机后，一直盯着它看。你忽略其他需要处理的事情，在面包弹出之前不开始别的任务，也不从冰箱里取出黄油和果酱。你甚至可能没发现炉灶上起火了。你希望在烤面包的同时处理其他事情，代码也是如此。

可以先更新代码，让线程在任务运行时不再阻塞。await 关键字提供一种非阻塞的方式：启动任务，并在任务完成后继续执行。早餐代码的一个简单异步版本如下：

译者批注 更准确地说，调用 FryEggsAsync 等方法会启动相应操作；await 负责等待其完成并取得结果，并不是一个通用的“启动任务”指令。若任务已经完成，await 不会暂停方法。
C# · 原文示例，注释已译
static async Task Main(string[] args)
{
    Coffee cup = PourCoffee();
    Console.WriteLine("coffee is ready");

    Egg eggs = await FryEggsAsync(2);
    Console.WriteLine("eggs are ready");

    HashBrown hashBrown = await FryHashBrownsAsync(3);
    Console.WriteLine("hash browns are ready");

    Toast toast = await ToastBreadAsync(2);
    ApplyButter(toast);
    ApplyJam(toast);
    Console.WriteLine("toast is ready");

    Juice oj = PourOJ();
    Console.WriteLine("oj is ready");
    Console.WriteLine("Breakfast is ready!");
}

代码将原来的 FryEggs、FryHashBrowns 和 ToastBread 方法体改为分别返回 Task<Egg>、Task<HashBrown> 和 Task<Toast> 对象。更新后的方法名添加了 Async 后缀：FryEggsAsync、FryHashBrownsAsync 和 ToastBreadAsync。虽然 Main 方法中没有 return 表达式，它仍会返回 Task 对象，这是有意设计的行为。更多信息见“无返回值异步函数的求值（Evaluation of a void-returning async function）”。

注意

更新后的代码尚未利用异步编程中能够缩短完成时间的关键特性。处理这些任务的总时间，与最初的同步版本大致相同。各方法的完整实现，见本文后面的最终代码版本。

把早餐例子套用到更新后的代码上：在鸡蛋或薯饼烹饪期间，线程不会阻塞，但代码仍要等当前工作完成，才启动其他任务。你依然把面包放进烤面包机，并盯着它直到面包弹出，不过现在你可以回应中途发生的其他事情。在有多份订单的餐馆里，厨师可以在一份订单烹饪期间，开始处理另一份订单。

在更新后的代码中，负责早餐的线程在等待任何已启动但尚未完成的任务时，都不会被阻塞。对于某些应用，这一个改变就足够了。你可以让应用在从网络下载数据期间继续支持用户交互。在其他场景中，你可能希望在等待前一个任务完成期间，启动其他任务。

并发启动任务

对于大多数操作，你会希望立即启动多个彼此独立的任务。当某项任务完成时，就开始处理其他已具备执行条件的工作。将这种方法用于早餐示例，可以更快地准备早餐，也能让所有食物在接近同一时间做好，从而吃到一顿热早餐。

System.Threading.Tasks.Task 类及相关类型，可以帮助你按这种思路处理正在进行的任务。这种方式让代码更接近现实中做早餐的过程。你同时开始煎鸡蛋、煎薯饼和烤面包。当某种食物需要处理时，你就转向对应任务，完成相应动作，然后等待其他需要你处理的事情。

在代码中，你启动任务，并保留表示该工作的 Task 对象。你对任务使用 await，将依赖结果的后续处理推迟到结果准备好之后。

将这些改动应用到早餐代码。第一步是在操作开始时保存对应任务，而不是直接在调用处使用 await 表达式：

C# · 原文示例，注释已译
Coffee cup = PourCoffee();
Console.WriteLine("Coffee is ready");

Task<Egg> eggsTask = FryEggsAsync(2);
Egg eggs = await eggsTask;
Console.WriteLine("Eggs are ready");

Task<HashBrown> hashBrownTask = FryHashBrownsAsync(3);
HashBrown hashBrown = await hashBrownTask;
Console.WriteLine("Hash browns are ready");

Task<Toast> toastTask = ToastBreadAsync(2);
Toast toast = await toastTask;
ApplyButter(toast);
ApplyJam(toast);
Console.WriteLine("Toast is ready");

Juice oj = PourOJ();
Console.WriteLine("Oj is ready");
Console.WriteLine("Breakfast is ready!");

这些修改还不能让早餐更快做好，因为每个任务刚启动就立即被 await。下一步是在上桌之前，将等待薯饼和鸡蛋的 await 表达式移到方法末尾：

C# · 原文示例，注释已译
Coffee cup = PourCoffee();
Console.WriteLine("Coffee is ready");

Task<Egg> eggsTask = FryEggsAsync(2);
Task<HashBrown> hashBrownTask = FryHashBrownsAsync(3);
Task<Toast> toastTask = ToastBreadAsync(2);

Toast toast = await toastTask;
ApplyButter(toast);
ApplyJam(toast);
Console.WriteLine("Toast is ready");
Juice oj = PourOJ();
Console.WriteLine("Oj is ready");

Egg eggs = await eggsTask;
Console.WriteLine("Eggs are ready");
HashBrown hashBrown = await hashBrownTask;
Console.WriteLine("Hash browns are ready");

Console.WriteLine("Breakfast is ready!");

现在你以异步方式准备早餐，大约需要 20 分钟。由于部分任务并发（concurrently）进行，总烹饪时间缩短了。

这些改动缩短了烹饪时间，改善了准备流程，却也引入了一个问题：鸡蛋和薯饼烧焦了。你一次启动所有异步任务，只在需要结果时才等待各项任务。这些代码类似于 Web 应用中的程序：它向不同的微服务发出请求，再将结果组合成一个页面。你立即发出所有请求，然后对这些任务使用 await 表达式，最后组装网页。

译者批注 “烧焦”是对现实烹饪的比喻，不意味着未被 await 的 Task 会停止推进，也不意味着晚一些 await 必然导致失败。异步操作是否继续推进，取决于它的实现。三幅英文插图仍画的是旧版 bacon（培根），而当前正文和代码改成了 hash browns（薯饼）；中文图保留原图的培根标签，避免悄悄改写原图。

通过任务支持组合

前面的改动使早餐的大部分食物能在同一时间准备好，吐司除外。制作吐司的流程，是将一个异步操作——烤面包——与同步操作——涂黄油和果酱——组合起来。这个例子说明了异步编程中的一个重要概念：

重要

将一个异步操作与之后的同步工作组合起来，得到的仍是异步操作。换句话说，如果一个操作中的任何部分是异步的，那么整个操作就是异步的。

译者批注 这里说的是整体操作的异步接口和完成时机。一个 async 方法内部仍可以包含同步执行的代码，并不是其中每条语句都自动异步执行。

在前面的修改中，你学会了使用 Task 或 Task<TResult> 对象保存正在运行的任务，并在使用结果之前等待对应任务。下一步是创建表示多个工作组合的方法。在早餐上桌之前，你希望先等待表示烤面包的任务完成，再涂黄油和果酱。

可以使用下面的代码表示这项工作：

C# · 原文示例，注释已译
static async Task<Toast> MakeToastWithButterAndJamAsync(int number)
{
    var toast = await ToastBreadAsync(number);
    ApplyButter(toast);
    ApplyJam(toast);

    return toast;
}

处理异步异常

到目前为止，代码隐含地假设所有任务都会成功完成。异步方法与对应的同步方法一样，也会抛出异常。异步异常和错误处理的目标，与异步支持的总体目标相同：最佳做法是让代码读起来像一系列同步语句。任务无法成功完成时会引发异常。调用方代码可以在对已启动任务使用 await 表达式时捕获这些异常。

对于这个过程，需要理解两个重要机制：

  • 异常如何存储在失败任务中。
  • 代码等待（await）失败任务时，异常如何被解包并重新抛出。

异步运行的代码抛出异常时，该异常会存储在 Task 对象中。Task.Exception 属性是一个 System.AggregateException 对象，因为异步工作中可能出现多个异常。抛出的异常会添加到 AggregateException.InnerExceptions 集合中。如果 Exception 属性为 null，则会创建一个新的 AggregateException 对象，并将该异常作为集合中的第一项。

失败任务最常见的情况，是 Exception 属性只包含一个异常。代码等待失败任务时，会重新抛出 AggregateException.InnerExceptions 集合中的第一个异常。因此，示例输出显示的是 System.InvalidOperationException，而不是 AggregateException。提取第一个内部异常，可以让使用异步方法尽可能接近使用对应的同步方法。如果你的场景可能产生多个异常，可以在代码中检查 Exception 属性。

高效地对任务使用 await 表达式

使用 Task 类的方法，可以改进前面代码末尾的一系列 await 表达式。其中一个 API 是 WhenAll 方法。它返回一个 Task 对象，只有当参数列表中的所有任务都完成后，这个对象才完成。下面的代码展示了该方法：

C# · 原文示例，注释已译
await Task.WhenAll(eggsTask, hashBrownTask, toastTask);
Console.WriteLine("Eggs are ready");
Console.WriteLine("Hash browns are ready");
Console.WriteLine("Toast is ready");
Console.WriteLine("Breakfast is ready!");

另一种选择是 WhenAny 方法。它返回一个 Task<Task> 对象，只要任一传入任务完成，这个对象就完成。你可以等待返回的任务，从而得知某个任务已经结束。下面的代码展示了如何使用 WhenAny 等待最先完成的任务，然后处理它的结果。处理完结果后，将该任务从传给 WhenAny 的任务列表中移除。

C# · 原文示例，注释已译
var breakfastTasks = new List<Task> { eggsTask, hashBrownTask, toastTask };
while (breakfastTasks.Count > 0)
{
    Task finishedTask = await Task.WhenAny(breakfastTasks);
    if (finishedTask == eggsTask)
    {
        Console.WriteLine("Eggs are ready");
    }
    else if (finishedTask == hashBrownTask)
    {
        Console.WriteLine("Hash browns are ready");
    }
    else if (finishedTask == toastTask)
    {
        Console.WriteLine("Toast is ready");
    }
    await finishedTask;
    breakfastTasks.Remove(finishedTask);
}

注意代码片段接近末尾处的 await finishedTask; 表达式。这一行很重要，因为 Task.WhenAny 返回的是 Task<Task>，即包含已完成任务的外层任务。当你 await Task.WhenAny 时，等待的是外层任务完成；得到的结果，是实际最先完成的那个任务。但是，要取得该任务的结果，或者确保它的异常能够正常抛出，还必须对这个已完成任务本身使用 await，这里它保存在 finishedTask 中。即使已知任务结束了，再次等待它仍然可以取得结果，或者处理导致它失败的异常。

async/await 与 ContinueWith 的比较

相比直接使用 Task.ContinueWith，async 和 await 关键字简化了语法。虽然 async/await 与 ContinueWith 在处理异步操作时具有相似的语义，但编译器不一定将 await 表达式直接转换为 ContinueWith 方法调用。编译器实际会生成经过优化的状态机（state machine）代码，提供相同的逻辑行为。这种转换显著改善了可读性和可维护性，尤其是在串联多个异步操作时。

考虑需要顺序执行多个异步操作的场景。下面比较使用 ContinueWith 和使用 async/await 实现同一逻辑的写法：

使用 ContinueWith

使用 ContinueWith 时，一系列异步操作中的每一步都需要嵌套的延续（continuation）：

C# · 原文示例，注释已译
// 使用 ContinueWith：展示串联操作时的复杂性。
static Task MakeBreakfastWithContinueWith()
{
    return StartCookingEggsAsync()
        .ContinueWith(eggsTask =>
        {
            var eggs = eggsTask.Result;
            Console.WriteLine("Eggs ready, starting bacon...");
            return StartCookingBaconAsync();
        })
        .Unwrap()
        .ContinueWith(baconTask =>
        {
            var bacon = baconTask.Result;
            Console.WriteLine("Bacon ready, starting toast...");
            return StartToastingBreadAsync();
        })
        .Unwrap()
        .ContinueWith(toastTask =>
        {
            var toast = toastTask.Result;
            Console.WriteLine("Toast ready, applying butter...");
            return ApplyButterAsync(toast);
        })
        .Unwrap()
        .ContinueWith(butteredToastTask =>
        {
            var butteredToast = butteredToastTask.Result;
            Console.WriteLine("Butter applied, applying jam...");
            return ApplyJamAsync(butteredToast);
        })
        .Unwrap()
        .ContinueWith(finalToastTask =>
        {
            var finalToast = finalToastTask.Result;
            Console.WriteLine("Breakfast completed with ContinueWith!");
        });
}

使用 async/await

同一系列操作使用 async/await 来写，读起来会自然得多：

C# · 原文示例，注释已译
// 使用 async/await：更简洁，也更容易阅读。
static async Task MakeBreakfastWithAsyncAwait()
{
    var eggs = await StartCookingEggsAsync();
    Console.WriteLine("Eggs ready, starting bacon...");
    
    var bacon = await StartCookingBaconAsync();
    Console.WriteLine("Bacon ready, starting toast...");
    
    var toast = await StartToastingBreadAsync();
    Console.WriteLine("Toast ready, applying butter...");
    
    var butteredToast = await ApplyButterAsync(toast);
    Console.WriteLine("Butter applied, applying jam...");
    
    var finalToast = await ApplyJamAsync(butteredToast);
    Console.WriteLine("Breakfast completed with async/await!");
}

为什么优先使用 async/await

async/await 方式具有以下优势：

  • 可读性：代码读起来像同步代码，更容易理解操作流程。
  • 可维护性：在操作序列中添加或删除步骤，只需要很少的代码改动。
  • 错误处理：可以自然地用 try/catch 块处理异常；使用 ContinueWith 时，则需要仔细处理失败任务。
  • 调试：使用 async/await 时，调用堆栈和调试器体验会更好。
  • 性能：编译器对 async/await 的优化，比手动编写的 ContinueWith 调用链更完善。

随着串联操作的数量增加，这些优势更加明显。单个延续用 ContinueWith 尚可处理，但包含三四个或更多异步操作的序列，会很快变得难以阅读和维护。这种模式在函数式编程中称为 monadic do-notation（单子 do 记法），可以让你以顺序、易读的方式组合多个异步操作。

异步编程的应用场景

如果代码处理的是网络数据请求、数据库访问或文件系统读写等 I/O 密集型（I/O-bound）场景，异步编程是最合适的方式。对于开销较大的计算等 CPU 密集型（CPU-bound）场景，也可以编写异步代码。

C# 在语言层面提供了异步编程模型，让你能方便地编写异步代码，无须费力组织回调，也无须迁就某个支持异步的库。这个模型遵循基于任务的异步模式（Task-based asynchronous pattern，TAP）。

了解异步编程模型

Task 和 Task<T> 对象是异步编程的核心。它们与 async 和 await 关键字配合，用来表示异步操作。在大多数情况下，无论是 I/O 密集型还是 CPU 密集型场景，这个模型都相当简单。在 async 方法内部：

  • I/O 密集型代码启动一个由 Task 或 Task<T> 对象表示的操作。
  • CPU 密集型代码通过 Task.Run 方法，在后台线程上启动操作。

在这两种情况下，一个活动的 Task 都表示一项可能尚未完成的异步操作。

关键在于 await 关键字。它将控制权交还给包含该 await 表达式的方法的调用方，最终使 UI 保持响应，或者使服务能够弹性扩展。虽然除了 async 和 await 表达式，还有其他处理异步代码的方式，但本文重点介绍语言层面的结构。

注意

本文的部分示例使用 System.Net.Http.HttpClient 类从 Web 服务下载数据。在示例代码中，s_httpClient 是 Program 类中类型为 HttpClient 的静态字段：

private static readonly HttpClient s_httpClient = new();

更多信息见本文末尾的完整示例代码。

回顾底层概念

在 C# 代码中采用异步编程时，编译器会将程序转换成状态机（state machine）。这个结构跟踪代码中的各项操作和状态，例如在到达 await 表达式时让出执行权，以及在后台工作完成时恢复执行。

从计算机科学理论的角度看，异步编程是异步 Promise 模型的一种实现。

异步编程模型中，有几个需要理解的关键概念：

  • I/O 密集型和 CPU 密集型代码都可以采用异步写法，但实现方式不同。
  • 异步代码使用 Task<T> 和 Task 对象，来表示在后台进行的工作。
    译者批注 Task 表示操作的完成情况，不一定对应后台线程。网络、文件等 I/O 的等待过程可以主要由操作系统处理。async 方法通常先在当前线程上执行，到遇到尚未完成的 await 时才让出控制权。
  • async 关键字将方法声明为异步方法，使你可以在方法体中使用 await 关键字。
  • 使用 await 时，代码暂停执行包含该表达式的方法，并将控制权交还给它的调用方，直到任务完成。
  • 只能在异步方法中使用 await 表达式。
    译者批注 这是针对一般方法体的说明。现代 C# 的顶级语句（top-level statements）也允许 await，编译器会为其生成合适的入口点；并不是必须手写一个带 async 的方法声明。

CPU 密集型示例：执行游戏计算

下一个示例中，手机游戏响应按钮事件，对屏幕上的多个角色造成伤害。伤害计算可能开销较大。如果在 UI 线程上执行计算，计算期间可能出现显示和 UI 交互问题。

最合适的处理方式，是通过 Task.Run 方法在后台线程上完成工作。操作通过 await 表达式让出执行权，并在任务完成时恢复。这样，UI 可以继续流畅运行，而工作在后台完成。

C# · 原文示例，注释已译
static DamageResult CalculateDamageDone()
{
    return new DamageResult()
    {
        // 省略的代码：
        // 
        // 执行开销较大的计算，
        // 并返回计算结果。
    };
}

s_calculateButton.Clicked += async (o, e) =>
{
    // CalculateDamageDone() 执行期间，这一行会将控制权交还给 UI。
    // UI 线程可以自由处理其他工作。
    var damageResult = await Task.Run(() => CalculateDamageDone());
    DisplayDamage(damageResult);

这段代码清楚地表达了按钮 Clicked 事件的意图。它不需要手动管理后台线程，并且以非阻塞方式完成任务。

识别 CPU 密集型和 I/O 密集型场景

前面的示例展示了如何使用 async 修饰符和 await 表达式处理 I/O 密集型与 CPU 密集型工作。每种场景的示例都说明，代码如何随操作受限的资源不同而变化。在准备实现之前，需要理解如何判断某个操作是 I/O 密集型还是 CPU 密集型。实现方式的选择可能显著影响性能，甚至导致对相关结构的误用。

编写任何代码之前，先回答两个主要问题：

问题 场景 实现方式
代码是否需要等待某个结果或动作，例如数据库返回的数据？ I/O 密集型（I/O-bound） 使用 async 修饰符和 await 表达式，不使用 Task.Run 方法。避免使用任务并行库（Task Parallel Library，TPL）。
代码是否需要执行开销较大的计算？ CPU 密集型（CPU-bound） 使用 async 修饰符和 await 表达式，并通过 Task.Run 方法将工作放到另一个线程上。这种方式解决 CPU 工作影响响应性的问题。如果工作适合并发和并行，也可以考虑使用任务并行库（Task Parallel Library）。

始终测量代码的实际执行情况。你可能发现，与多线程带来的上下文切换开销相比，这项 CPU 工作的成本还不够高。每个选择都有取舍，应选择适合具体情况的方案。

等待多个任务完成

某些场景中，代码需要并发取得多份数据。Task API 提供了一些方法，让你能够编写以非阻塞方式等待多个后台工作的异步代码：

  • Task.WhenAll 方法
  • Task.WhenAny 方法

下面的示例展示如何根据一组 userId 获取相应的 User 对象数据。

C# · 原文示例，注释已译
private static async Task<User> GetUserAsync(int userId)
{
    // 省略的代码：
    // 
    // 给定用户 ID {userId}，取得对应的 User 对象，
    // 即数据库中 Id 为 {userId} 的记录。

    await Task.Yield(); // 模拟异步数据库查询。
    return new User() { id = userId };
}

private static async Task<IEnumerable<User>> GetUsersAsync(IEnumerable<int> userIds)
{
    var getUserTasks = new List<Task<User>>();
    foreach (int userId in userIds)
    {
        getUserTasks.Add(GetUserAsync(userId));
    }

    return await Task.WhenAll(getUserTasks);
}

使用 LINQ，可以把这段代码写得更简洁：

C# · 原文示例，注释已译
private static async Task<User[]> GetUsersByLINQAsync(IEnumerable<int> userIds)
{
    var getUserTasks = userIds.Select(id => GetUserAsync(id)).ToArray();
    return await Task.WhenAll(getUserTasks);
}

虽然 LINQ 能减少代码量，但将 LINQ 与异步代码混用时需要谨慎。LINQ 采用延迟执行（deferred execution，也称 lazy execution）：如果没有立即求值，异步调用要等到序列被枚举时才会发生。

前面的示例正确且安全，因为它使用 Enumerable.ToArray 方法立即执行 LINQ 查询，并将任务存储到数组中。这样可以确保 id => GetUserAsync(id) 立即被调用，所有任务像使用 foreach 循环时一样并发启动。使用 LINQ 创建任务时，应使用 Enumerable.ToArray 或 Enumerable.ToList，以确保立即执行，并让任务并发进行。下面的示例使用 ToList() 和 Task.WhenAny，按任务完成的顺序处理它们：

C# · 原文示例，注释已译
private static async Task ProcessTasksAsTheyCompleteAsync(IEnumerable<int> userIds)
{
    var getUserTasks = userIds.Select(id => GetUserAsync(id)).ToList();
    
    while (getUserTasks.Count > 0)
    {
        Task<User> completedTask = await Task.WhenAny(getUserTasks);
        getUserTasks.Remove(completedTask);
        
        User user = await completedTask;
        Console.WriteLine($"Processed user {user.id}");
    }
}

这个示例中，ToList() 创建了支持 Remove() 操作的列表，使你能够动态移除已完成任务。当你希望结果一准备好就处理，而不是等待全部任务完成时，这种模式尤其有用。

虽然使用 LINQ 可以少写代码，但混用 LINQ 和异步代码时仍需谨慎。LINQ 使用延迟执行。除非通过调用 .ToList() 或 .ToArray() 强制遍历生成的序列，否则异步调用不会像在 foreach 循环中那样立即发生。

可以根据场景在 Enumerable.ToArray 与 Enumerable.ToList 之间选择：

  • 计划一起处理所有任务时，例如使用 Task.WhenAll，使用 ToArray()。数组适合集合大小固定的场景，效率较高。
  • 需要动态管理任务时使用 ToList()，例如使用 Task.WhenAny，在任务完成时从集合中移除它们。

异步编程的注意事项

使用异步编程时，需要留意一些细节，以防出现意料之外的行为。

在 async 方法体中使用 await

使用 async 修饰符时，方法体中应包含一个或多个 await 表达式。如果编译器没有遇到 await 表达式，方法就不会让出执行权。编译器会给出警告，但代码仍能编译，方法仍会执行。C# 编译器为这个异步方法生成的状态机没有实现任何有用的异步协调，因此整个过程效率不佳。

译者批注 async 但没有 await 的方法会同步执行；警告不妨碍编译。程序执行发生在运行时，而不是由编译器在运行时执行。原文关于“整个过程高度低效”的说法应按场景理解，不能替代性能测量。

给异步方法名添加 Async 后缀

.NET 的命名惯例是在所有异步方法名后添加 Async 后缀，以便区分同步方法和异步方法。某些不由你的代码显式调用的方法，例如事件处理程序或 Web 控制器方法，不一定需要遵循这项做法。由于它们不是由你的代码显式调用，明确标注名称就没那么重要。

仅在事件处理程序中使用 async void

事件处理程序必须声明 void 返回类型，无法像其他方法那样使用 Task 或 Task<T> 作为返回类型。编写异步事件处理程序时，需要给返回 void 的方法添加 async 修饰符。其他用途的 async void 方法不遵循 TAP 模型，并可能带来以下问题：

译者批注 这里主要指使用 void 委托签名的常见 .NET 事件处理程序。如果框架明确允许返回 Task 的处理程序，应遵循该框架的契约。
  • async void 方法抛出的异常，不能在该方法外部通过调用处的异常处理来捕获。
  • async void 方法难以测试。
  • 如果调用方没有预料到方法是异步的，async void 方法可能产生不良副作用。

谨慎使用 LINQ 中的异步 lambda

在 LINQ 表达式中编写异步 lambda 时必须谨慎。LINQ 中的 lambda 表达式采用延迟执行，意味着代码可能在意料之外的时间运行。如果代码写得不正确，在这种场景中引入阻塞任务，很容易造成死锁（deadlock）。此外，异步代码的嵌套也会让执行过程更难理解。异步与 LINQ 都很强大，但将两者结合时，应尽可能谨慎，并保持表达清楚。

以非阻塞方式等待任务

如果程序需要任务结果，应使用非阻塞的 await 表达式。为了同步等待 Task 完成而阻塞当前线程，可能造成死锁，并阻塞与上下文相关的线程。这种写法还可能需要更复杂的错误处理。下表说明如何以非阻塞方式取得任务结果：

任务场景 当前代码 替换为使用 await 的写法
取得后台任务的结果 Task.Wait 或 Task.Result await
任意一个任务完成后继续 Task.WaitAny await Task.WhenAny
所有任务完成后继续 Task.WaitAll await Task.WhenAll
经过一段时间后继续 Thread.Sleep await Task.Delay

考虑使用 ValueTask 类型

异步方法返回 Task 对象时，在某些执行路径上可能引入性能瓶颈。Task 是引用类型，因此 Task 对象在堆上分配。如果带有 async 修饰符的方法返回缓存结果，或同步完成，那么额外的分配可能在性能关键代码段中积累出显著的时间成本。如果分配发生在紧密循环中，成本可能很高。更多信息见“通用异步返回类型（generalized async return types）”。

理解何时设置 ConfigureAwait(false)

开发者经常询问何时应使用 Task.ConfigureAwait(Boolean) 的布尔参数。这个 API 可以为 Task 实例配置实现 await 表达式的状态机所使用的上下文。如果布尔参数设置不当，可能降低性能或造成死锁。更多信息见“ConfigureAwait 常见问题（ConfigureAwait FAQ）”。

译者批注 ConfigureAwait(false) 表示不要求延续恢复到此前捕获的上下文，并不表示强制换线程。需要更新 UI 的代码通常需要正确回到 UI 上下文；库代码是否使用它，要结合具体实现。

减少代码对状态的依赖

避免编写依赖全局对象状态或特定方法执行情况的代码，而应只依赖方法返回值。减少状态依赖具有许多好处：

  • 更容易理解代码。
  • 更容易测试代码。
  • 更容易混合同步与异步代码。
  • 有助于避免代码中的竞争条件（race condition）。
  • 更容易协调依赖返回值的异步代码。
  • 额外好处：能够很好地配合代码中的依赖注入（dependency injection）。

建议以实现完全或接近完全的引用透明性（Referential Transparency）为目标。这种方式可以让代码库具有可预测性、可测试性和可维护性。

以同步方式访问异步操作

某些场景中，当整个调用链无法使用 await 关键字时，你可能必须阻塞并等待异步操作。这通常发生在旧代码库中，或者需要把异步方法接入无法修改的同步 API 时。

警告

对异步操作进行同步阻塞可能导致死锁，应尽可能避免。首选方案是在整个调用链中使用 async/await。

如果必须同步阻塞并等待 Task，以下是可用方式，按推荐程度从高到低排列：

  • 使用 GetAwaiter().GetResult()。
  • 在复杂场景中使用 Task.Run。
  • 使用 Wait() 和 Result。

使用 GetAwaiter().GetResult()

如果必须同步阻塞，通常优先采用 GetAwaiter().GetResult() 模式：

译者批注 GetAwaiter().GetResult() 仍是同步阻塞。它保留异常形态，不代表解决了 UI 或同步上下文导致的死锁。此处保留原文对必须同步包装时的推荐顺序。
C# · 原文示例，注释已译
// 无法使用 await 时。
Task<string> task = GetDataAsync();
string result = task.GetAwaiter().GetResult();

这种方式：

  • 保留原始异常，不将它包装到 AggregateException 中。
  • 阻塞当前线程，直到任务完成。
  • 如果使用不慎，仍然存在死锁风险。

在复杂场景中使用 Task.Run

对于需要隔离异步工作的复杂场景：

C# · 原文示例，注释已译
// 转移到线程池，以避免上下文相关的死锁。
string result = Task.Run(async () => await GetDataAsync()).GetAwaiter().GetResult();

这种模式：

  • 在线程池线程上执行异步方法。
  • 能够帮助避免某些死锁场景。
  • 把工作调度到线程池，会增加开销。

使用 Wait() 和 Result

可以调用 Wait() 和 Result 来采用阻塞方式。不过，不建议使用这种方式，因为它会把异常包装进 AggregateException。

C# · 原文示例，注释已译
Task<string> task = GetDataAsync();
task.Wait();
string result = task.Result;

Wait() 和 Result 存在的问题：

  • 异常被包装进 AggregateException，使错误处理更复杂。
  • 死锁风险更高。
  • 代码意图不够清楚。

其他注意事项

  • 防止死锁：在 UI 应用中，或使用同步上下文（synchronization context）时，尤其要小心。
  • 性能影响：阻塞线程会降低可扩展性。
  • 异常处理：仔细测试错误场景，因为不同模式的异常行为不同。

有关给异步方法提供同步包装时的困难与注意事项，详见“是否应该为异步方法提供同步包装？（Should I expose synchronous wrappers for asynchronous methods?）”。

基于任务的异步编程模型

使用异步编程，可以避免性能瓶颈，并改善应用的整体响应性。不过，传统的异步应用编写技术可能相当复杂，导致代码难以编写、调试和维护。

C# 支持一种简化的方式，即利用 .NET 运行时异步支持的 async 编程。编译器承担了过去需要开发者完成的复杂工作，而应用仍能保持类似同步代码的逻辑结构。因此，你只需付出一小部分工作量，就能获得异步编程的各种优势。

本文概述何时以及如何使用 async 编程，并提供其他包含详细说明和示例的文章链接。

异步改善响应性

对于可能造成阻塞的活动，例如 Web 访问，异步非常重要。访问 Web 资源有时会很慢，或者发生延迟。如果这种活动在同步流程中阻塞，整个应用就必须等待。在异步流程中，应用可以继续处理不依赖该 Web 资源的其他工作，直到这个可能阻塞的任务完成。

下表展示了异步编程改善响应性的典型领域。列出的 .NET 和 Windows Runtime API 都包含支持异步编程的方法。

应用领域 包含异步方法的 .NET 类型 包含异步方法的 Windows Runtime 类型

对于需要访问 UI 线程的应用，异步尤其有价值，因为所有与 UI 有关的活动通常共享一个线程。在同步应用中，如果某个流程阻塞，其他 UI 活动也会被阻塞。应用会停止响应，你可能以为它出了故障，但它其实只是在等待。

使用异步方法时，应用仍能响应 UI 操作。例如，你可以调整窗口大小或最小化窗口；如果不想等待操作完成，也可以关闭应用。

设计异步操作时，基于 async 的方式就像多了一种“自动变速箱”选项：开发者付出更少的工作，就能获得传统异步编程的各种好处。

异步方法容易编写

C# 的 async 和 await 关键字是 async 编程的核心。利用这两个关键字，你可以使用 .NET Framework、.NET Core 或 Windows Runtime 的资源，几乎像创建同步方法一样方便地创建异步方法。使用 async 关键字定义的异步方法，称为 async 方法。

下面的示例展示了一个 async 方法。代码中的绝大部分内容应该都很熟悉。

可以从“在 C# 中使用 async 和 await 进行异步编程（Asynchronous programming with async and await in C#）”下载完整的 Windows Presentation Foundation（WPF）示例。

C# · 原文示例，注释已译
public async Task<int> GetUrlContentLengthAsync()
{
    using var client = new HttpClient();

    Task<string> getStringTask =
        client.GetStringAsync("https://learn.microsoft.com/dotnet");

    DoIndependentWork();

    string contents = await getStringTask;

    return contents.Length;
}

void DoIndependentWork()
{
    Console.WriteLine("Working...");
}

前面的示例展示了几项做法。先看方法签名：它包含 async 修饰符，返回类型为 Task<int>，更多选项见“返回类型”一节；方法名以 Async 结尾。在方法体中，GetStringAsync 返回 Task<string>，意味着等待（await）该任务后得到一个字符串，即 contents。在等待该任务之前，可以处理不依赖 GetStringAsync 所返回字符串的工作。

特别留意 await 运算符。它会暂停 GetUrlContentLengthAsync：

  • 在 getStringTask 完成之前，GetUrlContentLengthAsync 不能继续执行。
  • 与此同时，控制权返回给 GetUrlContentLengthAsync 的调用方。
  • getStringTask 完成时，执行会从这里恢复。
  • 随后，await 运算符从 getStringTask 取得字符串结果。

return 语句指定一个整数结果。等待 GetUrlContentLengthAsync 的方法会取得这个长度值。

如果在调用 GetStringAsync 与等待它完成之间，GetUrlContentLengthAsync 没有其他可以处理的工作，可以将调用和等待合并成下面的一条语句。

C# · 原文示例，注释已译
string contents = await client.GetStringAsync("https://learn.microsoft.com/dotnet");

下面这些特征说明了前面的示例为什么是 async 方法：

  • 方法签名包含 async 修饰符。

  • 按照惯例，async 方法名以 Async 后缀结尾。

  • 返回类型是以下类型之一：

    • 如果方法包含 return 语句，且返回表达式的类型为 TResult，则使用 Task<TResult>。
    • 如果方法没有 return 语句，或 return 语句不带返回表达式，则使用 Task。
    • 如果编写的是异步事件处理程序，则使用 void。
    • 其他任何具有 GetAwaiter 方法的类型。
      译者批注 要区分“一个值能被 await”和“一个类型能作为 async 方法的返回类型”。GetAwaiter 及符合要求的 awaiter 决定可等待性；自定义 async 返回类型还需满足 async method builder 协议。原文这里的简述并不完整，第四篇有进一步说明。

    更多信息见“返回类型和参数”一节。

  • 方法通常包含至少一个 await 表达式，它标记一个位置：在等待的异步操作完成之前，方法不能继续通过这个位置。与此同时，方法暂停，控制权返回给它的调用方。下一节说明暂停点会发生什么。

在 async 方法中，你用提供的关键字和类型表达想要完成的工作，编译器负责其余事项，包括跟踪暂停方法在恢复到 await 点时需要做什么。在传统异步代码中，循环、异常处理等常见流程可能很难处理。在 async 方法中，你可以基本按照同步方案的写法编写它们，从而解决这些问题。

有关早期 .NET Framework 版本中的异步方式，见“TPL 和传统 .NET Framework 异步编程”。

async 方法中会发生什么

理解异步编程时，最重要的是弄清控制流如何在方法之间转移。下面的图带你了解这个过程：

图中的数字对应下面这些步骤。流程从调用方调用 async 方法开始。

  1. 调用方法调用并等待 GetUrlContentLengthAsync 异步方法。

  2. GetUrlContentLengthAsync 创建 HttpClient 实例，并调用 GetStringAsync 异步方法，将网站内容下载为字符串。

  3. GetStringAsync 中发生某种情况，使它暂停执行。它可能需要等待网站内容下载，或者等待其他可能阻塞的活动。为避免占用资源进行阻塞，GetStringAsync 将控制权交还给调用方 GetUrlContentLengthAsync。

    GetStringAsync 返回一个 Task<TResult>，其中 TResult 为字符串。GetUrlContentLengthAsync 将这个任务赋给 getStringTask 变量。该任务表示 GetStringAsync 调用所对应的正在进行的操作，并承诺在工作完成后提供实际字符串值。

  4. 由于尚未等待 getStringTask，GetUrlContentLengthAsync 可以继续处理不依赖 GetStringAsync 最终结果的其他工作。这里通过调用同步方法 DoIndependentWork 来表示这项工作。

  5. DoIndependentWork 是同步方法。它完成工作后返回调用方。

  6. GetUrlContentLengthAsync 已经完成所有不需要 getStringTask 结果就能处理的工作。接下来它要计算并返回下载字符串的长度，但在取得字符串之前无法计算。

    因此，GetUrlContentLengthAsync 使用 await 运算符暂停自身执行，并将控制权交还给调用它的方法。GetUrlContentLengthAsync 向调用方返回 Task<int>。这个任务承诺最终提供一个整数结果，即下载字符串的长度。

    注意

    如果在 GetUrlContentLengthAsync 等待之前，GetStringAsync，也就是 getStringTask，已经完成，那么控制权仍留在 GetUrlContentLengthAsync 中。既然异步操作已经结束，不需要再等待最终结果，暂停方法然后恢复方法只会产生无用开销。

    同样的处理模式会在调用方法中继续。调用方可以先处理不依赖 GetUrlContentLengthAsync 结果的工作，再等待该结果；也可以立即等待。调用方法等待 GetUrlContentLengthAsync，而 GetUrlContentLengthAsync 等待 GetStringAsync。

  7. GetStringAsync 完成并产生字符串结果。这个字符串不会按你通常预期的方式通过 GetStringAsync 的那次调用直接返回，因为该方法在第 3 步已经返回了任务。字符串结果会存储在表示方法完成情况的任务 getStringTask 中。await 运算符从 getStringTask 取得结果，赋值语句再将它赋给 contents。

  8. GetUrlContentLengthAsync 得到字符串结果后，就可以计算长度。随后，该方法的工作也完成了，等待它的事件处理程序可以恢复。在文章所提到的完整示例中，可以看到事件处理程序取得并打印这个长度结果。如果你刚接触异步编程，请花一点时间比较同步与异步行为：同步方法完成工作后才返回，如第 5 步；async 方法在工作暂停时返回一个任务，如第 3、6 步。async 方法最终完成工作时，任务会被标记为已完成；如果存在结果，结果会存储在任务中。

API 中的异步方法

你可能想知道，在哪里能找到像 GetStringAsync 这样支持异步编程的方法。.NET Framework 4.5 及更高版本和 .NET Core 包含许多与 async、await 配合使用的成员。你可以通过成员名的 Async 后缀，以及 Task 或 Task<TResult> 返回类型识别它们。例如，System.IO.Stream 类同时包含 CopyToAsync、ReadAsync、WriteAsync 等异步方法，以及 CopyTo、Read、Write 等同步方法。

Windows Runtime 也包含许多可以在 Windows 应用中与 async、await 配合使用的方法。UWP 开发的更多信息见“线程处理和异步编程”；如果使用较早的 Windows Runtime 版本，见“异步编程（Windows 应用商店应用）”以及“快速入门：在 C# 或 Visual Basic 中调用异步 API”。

线程

async 方法的设计目标是非阻塞操作。异步方法中的 await 表达式，在等待任务运行期间不会阻塞当前线程。它会将方法的剩余部分注册为延续（continuation），然后将控制权返回给 async 方法的调用方。

async 和 await 关键字不会导致额外线程的创建。async 方法不要求多线程，因为它不会运行在属于自己的专用线程上。方法在当前同步上下文中执行，只有正在执行时才占用线程时间。可以用 Task.Run 把 CPU 密集型工作转移到后台线程，但如果流程只是等待结果可用，后台线程并不能提供帮助。

几乎在所有情况下，基于 async 的异步编程方式都优于已有方式。尤其对于 I/O 密集型操作，它比 BackgroundWorker 类更合适，因为代码更简单，也不必处理该旧方式带来的竞争条件问题。对于 CPU 密集型操作，将 async 编程与 Task.Run 结合，也比 BackgroundWorker 更合适，因为 async 将执行代码的协调细节，与 Task.Run 交给线程池的具体工作分离开来。

译者批注 异步并不会自动消除竞争条件。只要存在并发访问的共享可变状态，仍需适当的协调。原文对 BackgroundWorker 的对比不能理解为使用 async 后无需考虑任何 race condition。

async 和 await

使用 async 修饰符将方法声明为 async 方法时，会启用以下两项能力。

  • 被标记的方法可以用 await 指定暂停点。await 运算符告诉编译器，在等待的异步流程完成之前，该方法不能通过这个位置继续执行。与此同时，控制权返回给该 async 方法的调用方。

    async 方法在 await 表达式处暂停，并不意味着退出方法，finally 块不会因此执行。

  • 被标记的 async 方法本身，也可以被调用它的方法等待。

async 方法通常包含一个或多个 await 运算符，但没有 await 表达式并不会造成编译错误。如果方法没有用 await 标记暂停点，即使有 async 修饰符，它也会像同步方法一样执行。编译器会为这种方法给出警告。

返回类型和参数

async 方法通常返回 Task 或 Task<TResult>。在方法内部，对调用其他 async 方法所返回的任务使用 await 运算符。

如果方法中的 return 语句指定了类型为 TResult 的返回表达式，则将返回类型声明为 Task<TResult>。

如果方法没有 return 语句，或者 return 语句不带返回表达式，则使用 Task 作为返回类型。

也可以指定其他类型作为返回类型，前提是该类型包含 GetAwaiter 方法。ValueTask<TResult> 是这种类型的一个例子，可以从 System.Threading.Tasks.Extension NuGet 包取得。

译者批注 原文把 NuGet 包名写成 System.Threading.Tasks.Extension，但链接指向 System.Threading.Tasks.Extensions（末尾有 s）。现代 .NET 已直接提供 ValueTask，是否需要额外包取决于目标框架。

下面的示例展示如何声明和调用返回 Task<TResult> 或 Task 的方法：

C# · 原文示例，注释已译
async Task<int> GetTaskOfTResultAsync()
{
    int hours = 0;
    await Task.Delay(0);

    return hours;
}


Task<int> returnedTaskTResult = GetTaskOfTResultAsync();
int intResult = await returnedTaskTResult;
// 合并成一行。
// int intResult = await GetTaskOfTResultAsync();

async Task GetTaskAsync()
{
    await Task.Delay(0);
    // 不需要 return 语句。
}

Task returnedTask = GetTaskAsync();
await returnedTask;
// 合并成一行。
await GetTaskAsync();

每个返回的任务都表示正在进行的工作。任务封装异步流程的状态信息，并最终保存流程的结果，或者流程失败时产生的异常。

async 方法也可以返回 void。这种返回类型主要用于要求 void 返回类型的事件处理程序。异步事件处理程序常常是异步程序的起点。

返回 void 的 async 方法不能被等待；调用它的方法也无法通过调用处的异常处理捕获它抛出的异常。

译者批注 这里指调用方不能在调用 async void 的位置，用普通 try/catch 捕获该方法异步传播出的异常。方法内部仍可以自行捕获和处理异常。

async 方法不能声明 in、ref 或 out 参数，但可以调用包含这些参数的方法。同样，它不能按引用返回值，但可以调用按引用返回值的方法。

更多信息和示例见“异步返回类型（C#）”。

Windows Runtime 编程中的异步 API，采用以下某种类似任务的返回类型：

  • IAsyncOperation<TResult>，对应 Task<TResult>。
  • IAsyncAction，对应 Task。
  • IAsyncActionWithProgress<TProgress>。
  • IAsyncOperationWithProgress<TResult,TProgress>。

命名惯例

按照惯例，返回常见可等待类型——例如 Task、Task<T>、ValueTask、ValueTask<T>——的方法，其名称应以 Async 结尾。启动异步操作但不返回可等待类型的方法，不应以 Async 结尾；可以用 Begin、Start 或其他动词开头，表明它不会返回该操作的结果，也不会将该操作的异常通过返回结果传播。

如果事件、基类或接口约定要求使用其他名称，可以不遵循这一惯例。例如，不应重新命名 OnButtonClick 这类常见事件处理程序。

异步返回类型（C#）

async 方法可以使用以下返回类型：

  • Task：用于执行操作但不返回值的 async 方法。
  • Task<TResult>：用于返回值的 async 方法。
  • void：用于事件处理程序。
  • 任何具有可访问的 GetAwaiter 方法的类型。GetAwaiter 返回的对象必须实现 System.Runtime.CompilerServices.ICriticalNotifyCompletion 接口。
    译者批注 本项保留原文的 ICriticalNotifyCompletion 要求。就一般 awaitable 模式而言，awaiter 可实现 INotifyCompletion；ICriticalNotifyCompletion 是进一步的接口。自定义 async 返回类型还需要相应的 builder 支持，不能只检查 GetAwaiter。
  • IAsyncEnumerable<T>：用于返回异步流（async stream）的 async 方法。

有关 async 方法的更多信息，见“使用 async 和 await 进行异步编程（C#）”。

还有一些专门用于 Windows 工作负载的类型：

  • DispatcherOperation：用于仅限 Windows 的异步操作。
  • IAsyncAction：用于通用 Windows 平台（UWP）应用中不返回值的异步动作。
  • IAsyncActionWithProgress<TProgress>：用于 UWP 应用中报告进度但不返回值的异步动作。
  • IAsyncOperation<TResult>：用于 UWP 应用中返回值的异步操作。
  • IAsyncOperationWithProgress<TResult,TProgress>：用于 UWP 应用中报告进度并返回值的异步操作。

Task 返回类型

不包含 return 语句，或者 return 语句不带返回表达式的 async 方法，通常返回 Task。这些方法如果以同步方式实现，会返回 void。如果 async 方法使用 Task 返回类型，调用方法就可以使用 await 运算符，推迟自身完成的时间，直到被调用的 async 方法结束。

下面的示例中，WaitAndApologizeAsync 不包含 return 语句，因此返回 Task 对象。返回 Task，使 WaitAndApologizeAsync 可以被等待。Task 类型没有返回值，因此不包含 Result 属性。

C# · 原文示例，注释已译
public static async Task DisplayCurrentInfoAsync()
{
    await WaitAndApologizeAsync();

    Console.WriteLine($"Today is {DateTime.Now:D}");
    Console.WriteLine($"The current time is {DateTime.Now.TimeOfDay:t}");
    Console.WriteLine("The current temperature is 76 degrees.");
}

static async Task WaitAndApologizeAsync()
{
    await Task.Delay(2000);

    Console.WriteLine("Sorry for the delay...\n");
}
// 示例输出：
// 抱歉让你久等了……
// 
// 今天是 2020 年 8 月 17 日，星期一。
// 当前时间是 12:59:24.2183304。
// 当前温度为 76 度。

等待 WaitAndApologizeAsync 时，使用的是一条 await 语句，而不是一个产生值的 await 表达式，类似于调用返回 void 的同步方法。这里使用 await 运算符不会产生值。await 的右侧操作数为 Task<TResult> 时，表达式会产生类型为 TResult 的结果；右侧操作数为 Task 时，await 与其操作数一起构成一条不产生值的语句。

可以将调用 WaitAndApologizeAsync 与使用 await 运算符分开，如下所示。不过，请记住 Task 没有 Result 属性，对它使用 await 也不会产生值。

下面的代码将调用 WaitAndApologizeAsync 方法，与等待它返回的任务分开。

C# · 原文示例，注释已译
Task waitAndApologizeTask = WaitAndApologizeAsync();

string output =
    $"Today is {DateTime.Now:D}\n" +
    $"The current time is {DateTime.Now.TimeOfDay:t}\n" +
    "The current temperature is 76 degrees.\n";

await waitAndApologizeTask;
Console.WriteLine(output);

Task<TResult> 返回类型

如果 async 方法包含 return 语句，且返回表达式的类型是 TResult，则使用 Task<TResult> 返回类型。

下面的示例中，GetLeisureHoursAsync 包含一条返回整数的 return 语句。因此，方法声明必须指定 Task<int> 返回类型。示例中的 FromResult 调用，作为返回 DayOfWeek 的操作的占位实现。

译者批注 Task.FromResult 本身不是 async 方法；它创建一个已经成功完成、保存给定结果的 Task<T>。此处用于占位，不代表执行了真实的异步 I/O。
C# · 原文示例，注释已译
public static async Task ShowTodaysInfoAsync()
{
    string message =
        $"Today is {DateTime.Today:D}\n" +
        "Today's hours of leisure: " +
        $"{await GetLeisureHoursAsync()}";

    Console.WriteLine(message);
}

static async Task<int> GetLeisureHoursAsync()
{
    DayOfWeek today = await Task.FromResult(DateTime.Now.DayOfWeek);

    int leisureHours =
        today is DayOfWeek.Saturday || today is DayOfWeek.Sunday
        ? 16 : 5;

    return leisureHours;
}
// 示例输出：
// 今天是 2017 年 5 月 24 日，星期三。
// 今天的空闲时间：5 小时。

在 ShowTodaysInfo 中通过 await 表达式调用 GetLeisureHoursAsync 时，表达式会取得所返回任务中保存的整数，即 leisureHours 的值。更多有关 await 表达式的信息，见 await 文档。

把调用 GetLeisureHoursAsync 与使用 await 分开，可以更清楚地理解 await 如何从 Task<T> 取得结果，如下所示。调用 GetLeisureHoursAsync 而不立即等待时，会像方法声明所指示的那样返回 Task<int>。示例把任务赋给 getLeisureHoursTask。因为它是 Task<TResult>，所以包含类型为 TResult 的 Result 属性；这里 TResult 是整数类型。对 getLeisureHoursTask 使用 await 时，表达式的值就是该任务 Result 属性中的内容，这个值被赋给 ret。

重要

Result 是一个会阻塞的属性。如果在任务完成之前访问它，当前线程会一直阻塞，直到任务完成且结果可用。大多数情况下，应使用 await 取得值，而不是直接访问这个属性。

前面的示例通过读取 Result 属性来阻塞主线程，以便 Main 方法在应用退出之前，将消息打印到控制台。

C# · 原文示例，注释已译
var getLeisureHoursTask = GetLeisureHoursAsync();

string message =
    $"Today is {DateTime.Today:D}\n" +
    "Today's hours of leisure: " +
    $"{await getLeisureHoursTask}";

Console.WriteLine(message);

void 返回类型

需要 void 返回类型的异步事件处理程序，使用 void。其他不返回值的方法应返回 Task，因为返回 void 的 async 方法不能被等待。调用方必须在不等待被调用方法完成的情况下继续执行直至结束，并且不能依赖该 async 方法产生的值或异常。

返回 void 的 async 方法，其调用方无法捕获它抛出的异常。这种未处理异常很可能导致应用失败。如果返回 Task 或 Task<TResult> 的方法抛出异常，异常会存储在返回的任务中，并在该任务被等待时重新抛出。应确保可能产生异常的 async 方法返回 Task 或 Task<TResult>，并且调用方会等待它。

下面的示例展示异步事件处理程序的行为。在示例代码中，异步事件处理程序完成时必须通知主线程。这样，主线程才能在退出程序之前等待事件处理程序完成。

C# · 原文示例，注释已译
public class NaiveButton
{
    public event EventHandler? Clicked;

    public void Click()
    {
        Console.WriteLine("Somebody has clicked a button. Let's raise the event...");
        Clicked?.Invoke(this, EventArgs.Empty);
        Console.WriteLine("All listeners are notified.");
    }
}

public class AsyncVoidExample
{
    static readonly TaskCompletionSource<bool> s_tcs = new TaskCompletionSource<bool>();

    public static async Task MultipleEventHandlersAsync()
    {
        Task<bool> secondHandlerFinished = s_tcs.Task;

        var button = new NaiveButton();

        button.Clicked += OnButtonClicked1;

通用异步返回类型与 ValueTask<TResult>

async 方法可以返回任何具有可访问的 GetAwaiter 方法的类型，该方法需要返回 awaiter 类型的实例。此外，返回类型必须与 System.Runtime.CompilerServices.AsyncMethodBuilderAttribute 所指定类型上的 Task 属性返回类型相匹配，返回值类型也必须符合其 SetResult 参数的类型要求。更多信息见“编译器读取的特性”，或 C# 规范中的“Task 类型生成器模式（Task type builder pattern）”。

译者批注 这里区分两个类型关系：builder 的 Task 属性类型须对应方法声明的返回类型；builder 的 SetResult 参数类型须对应方法体 return 表达式的结果类型。例如 Task<int> 对应 SetResult(int)，不是 SetResult(Task<int>)。

这个特性与可等待表达式（awaitable expressions）相互补充；后者规定了 await 操作数的要求。通用异步返回类型使编译器能生成返回不同类型的 async 方法，并使 .NET 库得以改善性能。Task 和 Task<TResult> 是引用类型，在性能关键路径中进行内存分配，尤其是在紧密循环中反复分配，可能影响性能。支持通用返回类型，意味着可以返回轻量的值类型来代替引用类型，从而避免更多内存分配。

.NET 提供 System.Threading.Tasks.ValueTask<TResult> 结构，作为通用任务返回值的一种轻量实现。下面的示例使用该结构取得两次掷骰子的值。

C# · 原文示例，注释已译
class Program
{
    static readonly Random s_rnd = new Random();

    static async Task Main() =>
        Console.WriteLine($"You rolled {await GetDiceRollAsync()}");

    static async ValueTask<int> GetDiceRollAsync()
    {
        Console.WriteLine("Shaking dice...");

        int roll1 = await RollAsync();
        int roll2 = await RollAsync();

        return roll1 + roll2;
    }

    static async ValueTask<int> RollAsync()
    {
        await Task.Delay(500);

        int diceRoll = s_rnd.Next(1, 7);
        return diceRoll;
    }
}
// 示例输出：
// 正在摇骰子……
// 你掷出了 8。

自定义通用异步返回类型属于高级场景，面向专门环境。应考虑优先使用 Task、Task<T> 和 ValueTask<T>，它们已覆盖大多数异步代码场景。

译者批注 ValueTask 的价值主要在特定性能场景。不能把它当成总比 Task 更好的替代品；常规业务代码通常先选择 Task。

可以将 AsyncMethodBuilder 特性应用到 async 方法上，而不是异步返回类型的声明上，来覆盖该类型所使用的 builder。通常这样做是为了使用 .NET 运行时提供的另一种 builder。

使用 IAsyncEnumerable<T> 的异步流

async 方法可以返回由 IAsyncEnumerable<T> 表示的异步流。当元素通过反复异步调用分批生成时，异步流让你能够枚举从流中读取的各项数据。下面的示例展示生成异步流的 async 方法：

C# · 原文示例，注释已译
static async IAsyncEnumerable<string> ReadWordsFromStreamAsync()
{
    string data =
        @"This is a line of text.
              Here is the second line of text.
              And there is one more for good measure.
              Wait, that was the penultimate line.";

    using var readStream = new StringReader(data);

    string? line = await readStream.ReadLineAsync();
    while (line != null)
    {
        foreach (string word in line.Split(' ', StringSplitOptions.RemoveEmptyEntries))
        {
            yield return word;
        }

        line = await readStream.ReadLineAsync();
    }
}

前面的示例异步读取字符串中的行。每读取一行，代码就枚举这一行中的每个单词。调用方使用 await foreach 语句逐个枚举单词。方法需要从源字符串异步读取下一行时，就会等待。

按完成顺序处理异步任务（C#）

使用 Task.WhenAny，可以同时启动多个任务，并在它们完成时逐个处理，而不是按启动顺序处理。

下面的示例使用查询创建一个任务集合，每个任务下载指定网站的内容。在 while 循环的每次迭代中，等待 WhenAny 调用，会得到集合中最先完成下载的任务。代码将这个任务从集合中移除并处理它。循环不断重复，直到集合中没有任务。

创建异步汇总页面大小的方法

在 Main 方法下面添加 SumPageSizesAsync 方法：

C# · 原文示例，注释已译
static async Task SumPageSizesAsync()
{
    var stopwatch = Stopwatch.StartNew();

    IEnumerable<Task<int>> downloadTasksQuery =
        from url in s_urlList
        select ProcessUrlAsync(url, s_client);

    List<Task<int>> downloadTasks = downloadTasksQuery.ToList();

    int total = 0;
    while (downloadTasks.Any())
    {
        Task<int> finishedTask = await Task.WhenAny(downloadTasks);
        downloadTasks.Remove(finishedTask);
        total += await finishedTask;
    }

    stopwatch.Stop();

    Console.WriteLine($"\nTotal bytes returned:  {total:#,#}");
    Console.WriteLine($"Elapsed time:          {stopwatch.Elapsed}\n");
}

while 循环每次迭代移除一个任务。所有任务完成后，循环结束。方法首先创建并启动 Stopwatch，随后定义一个查询；查询执行时，会创建任务集合。下面的代码中，每次调用 ProcessUrlAsync 都返回一个 Task<TResult>，其中 TResult 为整数：

    from url in s_urlList

由于 LINQ 采用延迟执行，需要调用 Enumerable.ToList 才会启动每个任务。

while 循环对集合中的每个任务执行以下步骤：

  1. 等待 WhenAny 调用，以确定集合中第一个完成下载的任务。

    C# · 原文示例，注释已译

  2. 将该任务从集合中移除。

    C# · 原文示例，注释已译

  3. 等待调用 ProcessUrlAsync 返回的 finishedTask。finishedTask 变量是 Task<TResult>，其中 TResult 为整数。虽然任务已经完成，但仍要等待它来取得下载网站的长度，如下所示。如果任务失败，await 会抛出 AggregateException 中保存的第一个内部异常；直接读取 Task<TResult>.Result 属性则会抛出 AggregateException。

    译者批注 Task.WhenAny 的外层任务完成，只表示选出了一个已结束的内部任务。仍需 await 内部任务来取得结果，或者观察失败与取消。
    C# · 原文示例，注释已译
    total += await finishedTask;

异步文件访问（C#）

使用 async 特性访问文件时，可以调用异步方法，而无须使用回调，也无须将代码拆散到多个方法或 lambda 表达式中。要将同步代码改成异步代码，只需改为调用异步方法，并在代码中添加几个关键字。

可以基于以下原因，考虑为文件访问调用加入异步支持：

  • 异步能改善 UI 应用的响应性，因为发起操作的 UI 线程可以继续处理其他工作。如果 UI 线程必须执行耗时较长的代码，例如超过 50 毫秒，UI 就可能冻结，直到 I/O 完成，UI 线程才能再次处理键盘、鼠标输入及其他事件。
  • 异步通过减少线程需求，改善 ASP.NET 和其他服务器应用的可扩展性。如果应用为每个响应分配一个专用线程，同时处理一千个请求就需要一千个线程。异步操作在等待期间通常不需要使用线程，只在操作结束时短暂使用现有的 I/O 完成线程。
  • 文件访问操作在当前条件下可能延迟很低，但未来延迟可能大幅增加。例如，文件可能被移到地球另一端的服务器上。
  • 使用 async 特性带来的额外开销很小。
  • 多个异步 I/O 操作可以在不阻塞调用线程的情况下运行。

使用合适的类

本主题的简单示例展示了 File.WriteAllTextAsync 和 File.ReadAllTextAsync。如果需要精细控制文件 I/O 操作，可以使用 FileStream 类。它提供一个选项，让异步 I/O 在操作系统层面发生。在许多情况下，使用这个选项可以避免阻塞线程池线程。要启用它，请在构造函数调用中指定 useAsync=true 或 options=FileOptions.Asynchronous 参数。

如果通过直接指定文件路径来创建 StreamReader 和 StreamWriter，就不能使用这个选项。但如果向它们提供一个由 FileStream 打开的 Stream，就可以使用。即使线程池线程被阻塞，异步调用仍能让 UI 应用响应更快，因为 UI 线程在等待期间不会阻塞。

写入文本

下面的示例将文本写入文件。在每条 await 语句处，方法会立即交还控制权。文件 I/O 完成后，方法从 await 语句之后的位置继续执行。使用 await 语句的方法，在定义中带有 async 修饰符。

译者批注 原文把这里称为方法立即退出。准确含义是：在等待尚未完成的操作时，暂停该方法并返回控制权，不是方法已经彻底执行完毕。若等待的任务已完成，则直接继续。

简单示例

C# · 原文示例，注释已译
public async Task SimpleWriteAsync()
{
    string filePath = "simple.txt";
    string text = $"Hello World";

    await File.WriteAllTextAsync(filePath, text);
}

精细控制示例

C# · 原文示例，注释已译
public async Task ProcessWriteAsync()

async Task WriteTextAsync(string filePath, string text)
{
    byte[] encodedText = Encoding.Unicode.GetBytes(text);

    using var sourceStream =
        new FileStream(
            filePath,
            FileMode.Create, FileAccess.Write, FileShare.None,
            bufferSize: 4096, useAsync: true);

    await sourceStream.WriteAsync(encodedText, 0, encodedText.Length);
}

原示例中的 await sourceStream.WriteAsync(encodedText, 0, encodedText.Length);，是下面两条语句的合并写法：

C# · 原文示例，注释已译
Task theTask = sourceStream.WriteAsync(encodedText, 0, encodedText.Length);
await theTask;

第一条语句返回一个任务，并启动文件处理。第二条带有 await 的语句使方法立即交还控制权，并返回另一个任务。文件处理随后完成时，执行从 await 后面的语句恢复。

精细控制示例

文本通过缓冲区读取，在这个例子中被放入 StringBuilder。与前面的示例不同，这里的 await 求值会产生一个值。ReadAsync 返回 Task<Int32>，因此操作完成后，await 会产生一个 Int32 值 numRead。更多信息见“异步返回类型（C#）”。

C# · 原文示例，注释已译
public async Task ProcessReadAsync()
{
    try
    {
        string filePath = "temp.txt";
        if (File.Exists(filePath) != false)
        {
            string text = await ReadTextAsync(filePath);
            Console.WriteLine(text);
        }
        else
        {
            Console.WriteLine($"file not found: {filePath}");
        }
    }
    catch (Exception ex)
    {
        Console.WriteLine(ex.Message);
    }
}

async Task<string> ReadTextAsync(string filePath)
{
    using var sourceStream =
        new FileStream(
            filePath,
            FileMode.Open, FileAccess.Read, FileShare.Read,
            bufferSize: 4096, useAsync: true);

    var sb = new StringBuilder();

    byte[] buffer = new byte[0x1000];
    int numRead;
    while ((numRead = await sourceStream.ReadAsync(buffer, 0, buffer.Length)) != 0)
    {
        string text = Encoding.Unicode.GetString(buffer, 0, numRead);
        sb.Append(text);
    }

    return sb.ToString();
}

多个异步 I/O 操作

下面的示例启动多个异步写入操作。运行时会将这些操作排队；底层实现可能根据平台与配置，使用操作系统的异步 I/O 或线程池线程，因此实际并发情况取决于操作系统和硬件。

简单示例

C# · 原文示例，注释已译
public async Task SimpleParallelWriteAsync()
{
    string folder = Directory.CreateDirectory("tempfolder").Name;
    IList<Task> writeTaskList = new List<Task>();

    for (int index = 11; index <= 20; ++ index)
    {
        string fileName = $"file-{index:00}.txt";
        string filePath = $"{folder}/{fileName}";
        string text = $"In file {index}{Environment.NewLine}";

        writeTaskList.Add(File.WriteAllTextAsync(filePath, text));
    }

    await Task.WhenAll(writeTaskList);
}

精细控制示例

对于每个文件，WriteAsync 返回一个任务，并被添加到任务列表。await Task.WhenAll(tasks); 语句使方法交还控制权；所有任务的文件处理都完成后，方法恢复执行。

示例在所有任务完成后，通过 finally 块关闭全部 FileStream 实例。如果改为在 using 语句中创建每个 FileStream，流就可能在对应任务完成之前被释放。

译者批注 关键是流的生命周期必须覆盖对应异步操作。并不是 using 本身不能用于异步代码；在 using 作用域内正确 await 完所有相关工作后再离开，同样可以安全释放流。

异步方式在 I/O 尚未完成期间避免阻塞调用线程。在许多情况下，吞吐量的改善程度取决于操作系统、硬件，以及某些平台上的 .NET 运行时行为，例如线程池限制和调度。

C# · 原文示例，注释已译
public async Task ProcessMultipleWritesAsync()
{
    IList<FileStream> sourceStreams = new List<FileStream>();

    try
    {
        string folder = Directory.CreateDirectory("tempfolder").Name;
        IList<Task> writeTaskList = new List<Task>();

        for (int index = 1; index <= 10; ++ index)
        {
            string fileName = $"file-{index:00}.txt";
            string filePath = $"{folder}/{fileName}";

            string text = $"In file {index}{Environment.NewLine}";
            byte[] encodedText = Encoding.Unicode.GetBytes(text);

            var sourceStream =
                new FileStream(
                    filePath,
                    FileMode.Create, FileAccess.Write, FileShare.None,
                    bufferSize: 4096, useAsync: true);

            Task writeTask = sourceStream.WriteAsync(encodedText, 0, encodedText.Length);
            sourceStreams.Add(sourceStream);

            writeTaskList.Add(writeTask);
        }

        await Task.WhenAll(writeTaskList);
    }
    finally
    {
        foreach (FileStream sourceStream in sourceStreams)
        {
            sourceStream.Close();
        }
    }
}

使用 WriteAsync 和 ReadAsync 方法时，可以指定 CancellationToken，在操作进行中请求取消。更多信息见“托管线程中的取消”。

在一段时间后取消异步任务

如果不想一直等到异步操作完成，可以使用 CancellationTokenSource.CancelAfter 方法，在一段时间后取消操作。该方法安排一次取消请求，针对所有关联的、在 CancelAfter 表达式指定时间内尚未完成的任务。

译者批注 CancelAfter 安排的是到期后发出取消请求，不保证所有工作精确地在该时刻停止。实际响应时间取决于操作对取消的支持；已经完成的任务也不会因此变成取消状态。

本示例在“取消任务列表（C#）”中编写的代码基础上继续修改，用来下载一组网站，并显示每个网站内容的长度。

using System.Diagnostics;

class Program
{
    static readonly CancellationTokenSource s_cts = new CancellationTokenSource();

    static readonly HttpClient s_client = new HttpClient
    {
        MaxResponseContentBufferSize = 1_000_000
    };

    static readonly IEnumerable<string> s_urlList = new string[]
    {
            "https://learn.microsoft.com",
            "https://learn.microsoft.com/aspnet/core",
            "https://learn.microsoft.com/azure",
            "https://learn.microsoft.com/azure/devops",
            "https://learn.microsoft.com/dotnet",
            "https://learn.microsoft.com/dynamics365",
            "https://learn.microsoft.com/education",
            "https://learn.microsoft.com/enterprise-mobility-security",
            "https://learn.microsoft.com/gaming",
            "https://learn.microsoft.com/graph",
            "https://learn.microsoft.com/microsoft-365",
            "https://learn.microsoft.com/office",
            "https://learn.microsoft.com/powershell",
            "https://learn.microsoft.com/sql",
            "https://learn.microsoft.com/surface",
            "https://learn.microsoft.com/system-center",
            "https://learn.microsoft.com/visualstudio",
            "https://learn.microsoft.com/windows",
            "https://learn.microsoft.com/maui"
    };

    static async Task Main()
    {
        Console.WriteLine("Application started.");

        try
        {
            s_cts.CancelAfter(3500);

            await SumPageSizesAsync();
        }
        catch (OperationCanceledException)
        {
            Console.WriteLine("\nTasks cancelled: timed out.\n");
        }
        finally
        {
            s_cts.Dispose();
        }

        Console.WriteLine("Application ending.");
    }

    static async Task SumPageSizesAsync()
    {
        var stopwatch = Stopwatch.StartNew();

        int total = 0;
        foreach (string url in s_urlList)
        {
            int contentLength = await ProcessUrlAsync(url, s_client, s_cts.Token);
            total += contentLength;
        }

        stopwatch.Stop();

        Console.WriteLine($"\nTotal bytes returned:  {total:#,#}");
        Console.WriteLine($"Elapsed time:          {stopwatch.Elapsed}\n");
    }

    static async Task<int> ProcessUrlAsync(string url, HttpClient client, CancellationToken token)
    {
        HttpResponseMessage response = await client.GetAsync(url, token);
        byte[] content = await response.Content.ReadAsByteArrayAsync(token);
        Console.WriteLine($"{url,-60} {content.Length,10:#,#}");

        return content.Length;
    }
}

教程：使用 C# 和 .NET 生成并消费异步流

异步流（async streams）用于表示流式数据源。数据流通常以异步方式取得或生成元素。异步流为异步的流式数据源提供了自然的编程模型。

在本教程中，你将学习如何：

  • 创建以异步方式生成数据元素序列的数据源。
  • 以异步方式消费该数据源。
  • 为异步流支持取消和捕获上下文。
  • 判断何时应优先使用新接口和新数据源，而不是以前的同步数据序列。

先决条件

需要配置计算机，使它能够运行 .NET，包括安装 C# 编译器。Visual Studio 2022 或 .NET SDK 都提供 C# 编译器。

需要创建 GitHub 访问令牌，以访问 GitHub GraphQL 端点。为 GitHub Access Token 选择以下权限：

  • repo:status
  • public_repo

将访问令牌保存在安全位置，之后用它访问 GitHub API 端点。

警告

妥善保护个人访问令牌（personal access token）。任何持有该令牌的软件，都能以你的访问权限调用 GitHub API。

本教程假设你熟悉 C# 和 .NET，并了解 Visual Studio 或 .NET CLI 其中之一。

运行初始应用

本教程使用的初始应用代码，可以从 dotnet/docs 仓库的 asynchronous-programming/snippets 文件夹取得。

初始应用是一个控制台应用，通过 GitHub GraphQL 接口，取得 dotnet/docs 仓库中最近创建的 issues。先查看初始应用 Main 方法的以下代码：

检查实现

实现代码揭示了上一节观察到的行为为什么会发生。查看 RunPagedQueryAsync 的代码：

C# · 原文示例，注释已译
private static async Task<JArray> RunPagedQueryAsync(GitHubClient client, string queryText, string repoName, CancellationToken cancel, IProgress<int> progress)
{
    var issueAndPRQuery = new GraphQLRequest
    {
        Query = queryText
    };
    issueAndPRQuery.Variables["repo_name"] = repoName;

    JArray finalResults = new JArray();
    bool hasMorePages = true;
    int pagesReturned = 0;
    int issuesReturned = 0;

    // 最多读取 10 页，因为这些仓库很大：
    while (hasMorePages && (pagesReturned++ < 10))
    {
        var postBody = issueAndPRQuery.ToJsonText();
        var response = await client.Connection.Post<string>(new Uri("https://api.github.com/graphql"),
            postBody, "application/json", "application/json");

        JObject results = JObject.Parse(response.HttpResponse.Body.ToString()!);

        int totalCount = (int)issues(results)["totalCount"]!;
        hasMorePages = (bool)pageInfo(results)["hasPreviousPage"]!;
        issueAndPRQuery.Variables["start_cursor"] = pageInfo(results)["startCursor"]!.ToString();
        issuesReturned += issues(results)["nodes"]!.Count();
        finalResults.Merge(issues(results)["nodes"]!);
        progress?.Report(issuesReturned);
        cancel.ThrowIfCancellationRequested();
    }
    return finalResults;

    JObject issues(JObject result) => (JObject)result["data"]!["repository"]!["issues"]!;
    JObject pageInfo(JObject result) => (JObject)issues(result)["pageInfo"]!;
}

该方法首先使用 GraphQLRequest 类创建 POST 请求对象：

C# · 原文示例，注释已译
public class GraphQLRequest
{
    [JsonProperty("query")]
    public string? Query { get; set; }

    [JsonProperty("variables")]
    public IDictionary<string, object> Variables { get; } = new Dictionary<string, object>();

    public string ToJsonText() =>
        JsonConvert.SerializeObject(this);
}

这个类帮助构造 POST 请求体，并通过 ToJsonText 方法，将它正确转换成一个字符串形式的 JSON。该方法处理请求体中的换行字符，用 \，即反斜杠转义形式表示它们。

重点关注前面代码的分页算法和异步结构。GitHub GraphQL API 的详情可查阅 GitHub GraphQL 文档。RunPagedQueryAsync 按从新到旧的顺序枚举 issues。每页请求 25 个 issues，并检查响应中的 pageInfo 结构，以继续请求前一页。这遵循 GraphQL 对多页响应的标准分页支持。响应中的 pageInfo 对象包含表示是否还有前页的 hasPreviousPages 值，以及请求前一页所用的 startCursor 值。issues 位于 nodes 数组中。RunPagedQueryAsync 将这些 nodes 追加到一个包含所有页面结果的数组中。

译者批注 原文此处写的是 hasPreviousPages（复数），但同页 GraphQL 示例代码实际使用 hasPreviousPage（单数）。调用 API 时应以 schema 和代码中的字段名为准。

取得并保存一页结果之后，RunPagedQueryAsync 报告进度并检查取消状态。如果已有取消请求，就抛出 OperationCanceledException。

这段代码有几个可以改进的地方。最主要的是，RunPagedQueryAsync 必须为返回的所有 issues 分配存储空间。示例只取 250 个 issues，因为取得全部未关闭 issues 需要更多内存来保存结果。支持进度报告和取消的协议，让算法在初读时更难理解，也涉及更多类型和 API。你必须追踪 CancellationTokenSource 与关联 CancellationToken 之间的传递过程，才能理解取消在哪里被请求，又在哪里被响应。

异步流提供更好的方式

异步流及相应的语言支持解决了这些问题。生成序列的代码，现在可以在带有 async 修饰符的方法中使用 yield return 返回元素。消费异步流时，可以使用 await foreach 循环，就像用 foreach 消费其他序列一样。

这些新语言特性依赖三个新接口，它们添加于 .NET Standard 2.1，并在 .NET Core 3.0 中实现：

  • System.Collections.Generic.IAsyncEnumerable<T>
  • System.Collections.Generic.IAsyncEnumerator<T>
  • System.IAsyncDisposable

对大多数 C# 开发者来说，这三个接口应该不难理解，因为它们的行为类似于以下同步接口：

  • System.Collections.Generic.IEnumerable<T>
  • System.Collections.Generic.IEnumerator<T>
  • System.IDisposable

你可能不熟悉的一个类型是 System.Threading.Tasks.ValueTask。ValueTask 结构提供与 System.Threading.Tasks.Task 类类似的 API。出于性能考虑，这些接口使用 ValueTask。

接下来，将 RunPagedQueryAsync 转换为生成异步流的方法。首先将它的返回类型改为 IAsyncEnumerable<JToken>，并从参数列表中移除取消令牌和进度对象，如下所示：

新接口 IAsyncEnumerator<T> 继承自 IAsyncDisposable，意味着前面的循环在结束时，会以异步方式释放用于枚举该流的对象。可以将这个循环理解为类似下面的代码：

C# · 原文示例，注释已译
int num = 0;
var enumerator = RunPagedQueryAsync(client, PagedIssueQuery, "docs").GetAsyncEnumerator();
try
{
    while (await enumerator.MoveNextAsync())
    {
        var issue = enumerator.Current;
        Console.WriteLine(issue);
        Console.WriteLine($"Received {++num} issues in total");
    }
} finally
{
    if (enumerator != null)
        await enumerator.DisposeAsync();
}

System.Runtime.CompilerServices.EnumeratorCancellationAttribute 特性使编译器为 IAsyncEnumerator<T> 生成代码，将传给 GetAsyncEnumerator 的令牌，作为该参数提供给异步迭代器的方法体。在 runQueryAsync 内部，可以检查令牌状态，并在收到取消请求时停止后续工作。

译者批注 EnumeratorCancellation 把枚举器收到的取消令牌提供给迭代器，但不会自动在每一步抛异常。迭代器需要检查令牌，或把令牌继续传给支持取消的异步操作。原文此处的 runQueryAsync 与前面的 RunPagedQueryAsync 名称也不一致。

    await foreach (var issue in RunPagedQueryAsync(client, PagedIssueQuery, "docs")
        .WithCancellation(cancellation.Token))

        Console.WriteLine(issue);
        Console.WriteLine($"Received {++num} issues in total");

运行完成后的应用

再次运行应用，与初始应用的行为比较。第一页结果一准备好就会被枚举。每次请求并取得新的一页时，都能观察到停顿，然后下一页的结果会迅速被枚举。不必用 try/catch 块来处理主动停止枚举这种取消方式：调用方可以直接停止枚举集合。由于每页下载完成后异步流都会生成结果，进度清晰可见。每个返回 issue 的状态自然包含在 await foreach 循环中，无须用回调对象跟踪进度。

译者批注 主动 break 停止枚举，通常不需要靠取消异常来结束循环。但若使用令牌取消且迭代器抛出 OperationCanceledException，调用方仍需按需要处理该异常。异步流不等于从此不需要异常处理。

检查代码还能看出内存使用的改善：不再需要在枚举之前分配一个集合来保存全部结果。调用方可以决定如何消费结果，以及是否需要用于存储的集合。

分别运行初始应用和完成后的应用，可以亲自观察两种实现的差异。完成教程后，可以删除开始时创建的 GitHub 访问令牌。如果攻击者取得这个令牌，就能使用你的凭据访问 GitHub API。

本教程使用异步流，从一个分页返回数据的网络 API 中逐项读取数据。异步流也可以读取股票行情或传感器设备这类“永不结束的流”。下一项数据一可用，MoveNextAsync 调用就会返回它。

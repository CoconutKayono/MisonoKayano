Unity 6.7 调试与日志实战指南。讲清楚 Debug.Log 是否随游戏发布、为什么会影响性能，以及遇到错误时该先用什么工具。

面向 C# 初学者与独立开发者含完整日志封装核对日期：2026-09-28

版本说明：Unity 6.7 对应 6000.7；本次核查的官方手册入口标为 Beta。本文以 Unity 6 系列可核实的 API、C# 规则与常用 Mono / IL2CPP 工作流为依据；细节引用的文档版本会明确标注，不把 6.0 页面冒充 6.7 专属文档。6.7 的实验后端及平台差异，应以你所装补丁版和实际构建验证为准。

01 / 先记住这三点

会保留，会有开销，要配合使用。

BUILD普通日志通常会随代码进入构建

非 Development Build 也能执行 Debug.Log。编辑器里已经产生的 Console 历史记录，则不会自动变成游戏资源。

PERFORMANCE输出关闭了，参数可能还在算

字符串拼接、插值、函数调用发生在进入日志方法之前。高频日志还可能产生 GC、堆栈处理和输出开销。

WORKFLOW先用日志缩小范围，再用断点验明原因

能稳定复现的逻辑错误优先断点；远端、偶发和构建专属错误先留日志；卡顿和分配问题用 Profiler。

依据：Debug.Log API、Unity 官方 C# 参考实现、C# ConditionalAttribute。后文的工具选择与日志策略属于工程建议。

02 / 从源代码到玩家设备

“Debug 的内容被打包”到底指什么？

先分清四件事：日志调用代码、消息字符串、运行时生成的日志文件、用于调试的符号信息。它们不是同一份东西。

你说的“Debug 内容”普通发布构建中的行为应当如何理解
Debug.Log / LogWarning / LogError可达调用通常仍然存在，也能执行名称中有 Debug，不代表自动仅在开发环境生效。
日志中的字符串常量相关代码保留时，文本通常也会保留不要把密钥、令牌或不应公开的信息写进日志文本。编译或 IL2CPP 不是保密措施。
编辑器 Console 的旧消息不会自动打包除非你主动把日志文件放进会随包分发的资源或复制步骤中。
玩家设备上的 Player.log由游戏运行时产生，受平台与日志配置影响它是新的运行记录，不是开发时历史记录的副本。
调试器、断点、符号文件取决于平台、后端和构建设置IDE 中的断点设置不会变成自动暂停玩家游戏的代码；符号信息与日志开关要分别管理。
Debug.Assert受 UNITY_ASSERTIONS 条件符号控制普通发布构建通常不定义此符号；自定义符号或构建选项可改变结果。不能推导为整个 Debug 类都被移除。

Unity 会编译脚本；使用 IL2CPP 时还会把中间代码转换并编译为原生代码。未使用代码可能被剥离，但“游戏实际会走到的 Log”不会仅因为关闭 Development Build 就自动消失。不要用“反正打包会优化掉”代替明确的日志策略。[官方参考实现]

三个名字相近、作用不同的开关

设置 / API它决定什么它没有直接决定什么
Development Build开发构建及相应诊断能力；Unity 提供 DEVELOPMENT_BUILD 符号普通 Debug.Log 是否从源代码调用点移除
Script Debugging是否允许受支持的脚本调试器连接 Player日志是否输出到文件
Debug.isDebugBuild运行时查询：Editor 中为 true；Player 中反映开发构建状态它自身不是 #if，也不会删除周围代码

参考：Unity 条件符号、托管代码调试、Debug.isDebugBuild（6.0）、Debug.Assert。

03 / 理解成本链路

日志不是“免费的一行文字”。

一次日志可以经历下面四个阶段。实际成本受消息大小、频率、堆栈配置、后端、平台、日志接收器及编辑器状态影响，不能给出一个适用于所有项目的固定毫秒数。

① 准备消息读取属性、调用函数、拼接字符串、序列化对象；可能分配内存。
② 进入日志系统类型过滤、格式化、对象转文字，以及跨托管 / 原生边界的处理。
③ 处理堆栈视配置收集、解析调用栈；Full 还包括原生栈信息。
④ 交付输出文件、平台日志、编辑器 Console、附加接收器；可能有锁和 I/O 成本。

这个例子，即使没有输出也可能很贵

C# · 参数会先求值
Debug.unityLogger.logEnabled = false;
Debug.Log($"背包快照：{BuildInventorySnapshot()}");
// BuildInventorySnapshot() 仍会执行，插值字符串仍会构造。
// 日志系统收到 message 参数以后，才能决定是否输出。

要区分“调用者创建字符串”和“日志系统内部格式化”。例如传入现成对象时，关闭 logger 可能避免内部的 ToString()；但调用者写的 Debug.Log(BuildText())，其中 BuildText() 已经执行。值类型传入 object 参数还可能发生装箱。[Logger 参考实现]

最值得先改的情况：在 Update / FixedUpdate 中无条件输出、几百个对象同时输出、循环打印大对象、每次都带完整堆栈。举例：100 个对象 × 每秒 60 次 = 每秒 6,000 条日志。这只是频率计算，不是性能测试结果。

一次启动记录或少量状态切换日志通常更容易控制成本。不要因为日志有开销，就把所有错误线索一起清空。也不要因为在自己的电脑上“感觉流畅”，就认定目标手机没有 GC 或 I/O 压力。

Console 隐藏与 Collapse 只是显示管理

关闭 Console 面板、取消显示某一类消息、启用 Collapse 合并重复条目，都不能等同于“调用没有发生”。它们可能影响编辑器显示开销，但不是让 Player 中日志调用消失的方法。

堆栈应该按等级配置

None 不输出堆栈；ScriptOnly 提供托管脚本栈；Full 还包含原生栈。Full 更适合有针对性的调查，不适合对每条普通消息启用。[堆栈文档]

C# · 一种项目策略，不是 Unity 默认值
Application.SetStackTraceLogType(LogType.Log, StackTraceLogType.None);
Application.SetStackTraceLogType(LogType.Warning, StackTraceLogType.None);
Application.SetStackTraceLogType(LogType.Error, StackTraceLogType.ScriptOnly);
Application.SetStackTraceLogType(LogType.Exception, StackTraceLogType.ScriptOnly);

这里建议普通日志不带栈，低频错误按诊断需要保留脚本栈。官方文档对发布版本的堆栈更保守，强调避免其成本；是否为线上错误保留堆栈，是需要测量和权衡的项目决策。关闭堆栈不等于关闭消息，设置 ScriptOnly 也不保证每个平台都有完整文件名和行号。

04 / 运行时过滤与编译期移除

怎样让不需要的日志真正少做事？

做法未输出时，消息参数还计算吗？适合用途
logEnabled = false会，调用之前先求值临时关闭该 logger；会连带影响经它发送的警告、错误、显式异常日志
日志封装方法内部 if传进来的参数已经计算了过滤输出，不能回收调用者已付出的成本
调用点外部 if条件为 false 时，不计算分支内的消息运行时等级、分类开关；仍会检查条件
#if UNITY_EDITOR || DEVELOPMENT_BUILD未定义符号时，不计算；这段源代码不参与该次编译日志和整段诊断专用准备工作
[Conditional(...)] 封装条件不满足时，直接 C# 调用及其参数求值会被省略统一的开发日志方法，避免到处写预处理指令
可交互 · C# 语义演示

切换写法，看“没打印”之前发生了什么

这是编译 / 求值规则的示意，不执行 Unity，也不测量毫秒数。假设常规符号配置、普通直接 C# 调用、日志类型允许且输出通道可用。

写法 A：调用点外部判断

C# · 运行时阻止消息构造
if (Debug.isDebugBuild)
{
    Debug.Log($"背包快照：{BuildInventorySnapshot()}");
}

正式 Player 中条件为 false 时不会进入分支，消息也不会构造；但这是运行时判断，不能把它当作“代码与字符串必定不在构建产物中”的保证。Editor 中该属性总是 true。

写法 B：把整段诊断代码条件编译掉

C# · 适合多行准备工作
#if UNITY_EDITOR || DEVELOPMENT_BUILD
string snapshot = BuildInventorySnapshot();
Debug.Log(snapshot);
#endif

UNITY_EDITOR 只用于编辑器编译；要在开发 Player 中也保留，加入 DEVELOPMENT_BUILD。不要直接拿 DEBUG 当作 Unity Development Build 的同义词。项目自定义符号、预编译 DLL 的编译过程都可能不同。[条件符号参考]

不要把业务操作放进可移除的日志参数里。
GameLog.Dev($"奖励：{GrantReward()}"); 是错误设计：日志调用被省略后，发奖也可能不执行。先完成业务操作，再记录结果。反过来，仅为日志服务的昂贵计算也不要提前放在条件之外。
05 / 一个够用的起点

开发日志按构建移除，发布诊断按等级保留。

把下面代码保存为 GameLog.cs，放在普通运行时脚本目录中，不要放在 Editor 文件夹。这是基础封装：不包含日志文件轮转、上传、复杂过滤或线程队列。它仍使用 Unity 的日志输出通道。

GameLog.cs · 完整代码
using System.Diagnostics;
using UnityEngine;
using Debug = UnityEngine.Debug;
using Object = UnityEngine.Object;

public static class GameLog
{
    // 两个 Conditional 是“或”：任一符号存在就保留调用。
    [Conditional("UNITY_EDITOR")]
    [Conditional("DEVELOPMENT_BUILD")]
    public static void Dev(string message, Object context = null)
    {
        Debug.Log(message, context);
    }

    // 发布版本仍保留；应只记录必要、低频的信息。
    public static void Warning(string message, Object context = null)
    {
        Debug.LogWarning(message, context);
    }

    public static void Error(string message, Object context = null)
    {
        Debug.LogError(message, context);
    }

    public static void Exception(System.Exception exception,
                                 Object context = null)
    {
        Debug.LogException(exception, context);
    }
}
调用示例 · 放在你自己的业务方法中
// 正式构建未定义两个符号时，整个直接调用及插值都被省略。
GameLog.Dev($"[Combat] target={targetId} damage={damage}", this);

// 严重问题仍然留下可定位的记录。
GameLog.Error($"[Save] code=WRITE_FAILED slot={slotId}", this);

Conditional 的准确含义

它让编译器根据调用方编译时的符号决定是否发出调用，并不等于把整个方法定义从程序集里删除。被省略的直接调用不执行参数求值，但参数仍需要通过类型检查；被修饰的方法须返回 void。反射、预编译插件与跨程序集编译需要单独考虑。[C# 官方规则]

该封装只影响你改成 GameLog.Dev 的调用，不会自动处理第三方插件或仍然直接调用的 Debug.Log。开发日志在 Editor / 开发构建里依然有成本；正式日志方法也不应在每帧重复输出。

发布版本临时诊断：先判断，再准备内容

C# · 不要在封装内部才做昂贵日志的开关判断
// diagnosticsEnabled 是项目自己管理的 bool 开关。
// 只有确实需要时才临时启用，并控制频率、范围和持续时间。
if (diagnosticsEnabled &&
    Debug.unityLogger.IsLogTypeAllowed(LogType.Log))
{
    Debug.Log($"[Inventory] {BuildInventorySnapshot()}");
}

已在编译期移除的开发日志不能靠运行时开关“复活”。如果需要让客服包或测试包动态启用诊断，必须提前保留受控调用路径。不要把全量详细日志长期默认打开。

一个不依赖猜测的验证办法

在项目副本中，用一个每调用一次就增加计数的 BuildText() 作为日志参数；分别测试直接日志、调用点 if、Conditional。关闭 logger 后用 Inspector 或调试器看计数，再构建一个非开发 Player 验证输出。预期正是上面的交互演示。计数递增只作为教学探针；业务代码不要依赖日志参数的副作用。

06 / 按问题选择工具

日志、断点、Profiler，分别回答不同的问题。

从广义上说，写日志也是调试。这里把“调试器”特指 IDE 里的断点、单步、变量检查和调用栈。它们的区别在于你能获得什么证据，以及是否改变程序运行的时机。

遇到的情况先用什么接下来做什么
每次点击按钮都算错伤害断点 / 条件断点检查输入、分支和中间值；找到第一次偏离预期的位置
偶尔断线，暂停后不再复现有时间与请求 ID 的日志重建事件先后关系；在可控环境再用断点确认逻辑
玩家机器才会报错玩家日志、版本与设备信息建立相同配置，再用开发 Player 附加调试
只在打包后失败该 Player 的日志核查路径、平台 API、资源、剥离和初始化时序；调试实际 Player
卡顿、帧率下降、GC 峰值Profiler定位 CPU / GPU / 分配来源，再验证优化前后变化
应用直接退出或原生崩溃崩溃报告、原生栈与对应符号区分引擎、驱动、原生插件与脚本线索；最后一条日志未必是根因
编译失败，无法进入 Play首条编译错误与编译输出先修语法、类型和引用；运行时断点帮不了尚未编译成功的代码

日志：还原“发生过什么”

保留时间线、输入摘要、状态切换与错误码。适合程序继续运行时观察，也适合测试者提交问题。

限制：只能看到预先记录的内容；日志本身也会改变耗时和线程时序。

断点：检查“现在为什么这样”

暂停在关键行，查看局部变量、字段、分支和完整调用链，不必猜测应该打印哪个值。

限制：暂停可能造成网络超时、打乱多线程竞争，使问题消失或出现新现象。

建议的默认路线：能本地稳定重现，就尽早用断点；不能稳定重现，先设计少量有信息量的日志；描述中出现“慢、卡、掉帧、内存涨”，就加入 Profiler，而不是只凭日志时间戳估算。
07 / 从报错走到根因

一套可重复的排错流程。

  1. 把问题描述成可验证的差异

    写清“预期是什么、实际是什么、如何触发”。记录 Unity 完整版本号、游戏版本、平台、脚本后端和构建类型。把“背包坏了”改成“加载旧存档后，第一次打开背包时报空引用”。

  2. 找到最早的相关错误

    先保存原日志，再清理 Console 重现。不要只看最后一条：后续错误可能是前一个初始化失败的连锁结果。需要暂停在报错附近可用 Error Pause；需要准确停在异常抛出点，配置 IDE 的异常断点。

  3. 读堆栈，定位到项目代码

    从异常类型与消息开始，再找到最靠近出错位置的项目代码帧。不要停留在 Unity 内部入口；也不要误以为日志所在行就是最初造成坏状态的行。

  4. 提出一个能被证伪的假设

    例如“读档回调早于 UI 初始化”。在两个事件边界加带请求 ID、状态、帧号的日志；或在赋值点和访问点设置断点。一次只验证一个主要猜测。

  5. 缩小复现范围

    减少场景对象、插件与输入步骤；用最小场景或最小存档复现。比较工作正常和失败时的具体差异，避免同时改五个设置后失去因果关系。

  6. 修复状态或契约，再回归

    修复漏绑引用、错误生命周期、无效数据或并发顺序；确认原复现步骤和相邻边界条件都通过。清理临时刷屏日志，保留必要诊断，再用原先出错的平台与正式构建验证。

实战：点“背包”时出现 NullReferenceException

原始代码 · 假设 bagPanel 上有背包 UI 组件
public void OpenBag()
{
    bagPanel.SetActive(true);
    bagPanel.GetComponent<BagView>().Refresh();
}

第二行出错可能是没有 BagView 组件；第一行出错可能是 bagPanel 未绑定或对象已被销毁。一个长链条只告诉你“某个环节不对”，无法凭空知道是哪一个。

  1. 双击错误进入对应行，在访问前打断点，检查 bagPanel 以及 GetComponent<BagView>() 的结果。Unity 对象还要考虑“托管引用存在，但底层对象已经销毁”的情况。
  2. 回到 Prefab / 场景检查引用，确认组件在预期对象上，是否在场景切换后仍持有旧对象。再看是谁负责初始化、调用是否过早。
  3. 如果只有玩家构建会出现，记录场景名、对象标识、打开请求编号和初始化状态，再复现同一版本。不要只打印“111”“222”。
BagOpener.cs · 带配置校验的完整示例
using UnityEngine;

public sealed class BagOpener : MonoBehaviour
{
    [SerializeField] private GameObject bagPanel;

    public void OpenBag()
    {
        if (bagPanel == null)
        {
            GameLog.Error(
                $"[UI] code=BAG_PANEL_MISSING " +
                $"scene={gameObject.scene.name} owner={name}", this);
            return;
        }

        bagPanel.SetActive(true);
    }
}

这个示例演示明确校验与错误信息，实际项目还需要实现自己的 BagView 校验和刷新逻辑。加 null 判断只是把失控的异常变成可解释的失败；如果引用本来就必须存在，最终仍要修复漏绑或生命周期问题。用户连续点击可能重复报错，实际系统可在发现配置错误后禁用入口，或按错误码与对象做限流。

LogError、Exception 和 Assert 不要混用

操作含义代码会怎样继续
Debug.LogError(...)记录错误级别消息它本身不等于 throw；后续代码通常继续。需要退出当前方法时显式 return。
throw new ...抛出异常，改变控制流沿调用栈寻找匹配 catch；不能用“打印红字”代替这个语义。
Debug.LogException(ex)把已有异常交给日志系统记录不是重新抛出。catch 后是否恢复、退出或继续抛出，需要自己决定。
Debug.Assert(condition)检查开发时应成立的假设条件失败时记录 Assert；可能在构建中被条件省略，不能代替必须执行的数据校验。

不要用 try { ... } catch { } 吞掉所有错误。能够恢复时明确恢复；不能恢复而需要上层处理时使用 throw; 保留原异常传播信息。也避免在每一层重复记录同一个异常。[LogError] [Assert]

08 / 断点入门

把 IDE 连到真正出错的 Unity 实例。

EDITOR

在编辑器中调试

  1. 安装并启用 IDE 对 Unity 的支持：Visual Studio 的 Unity 工具、Rider 的 Unity 支持，或 VS Code 的 Unity 扩展。
  2. 在 Preferences → External Tools 中配置脚本编辑器；需要断点时确认 Editor 的代码优化处于 Debug 模式。
  3. 在 IDE 使用“Attach to Unity / Attach Unity Debugger”等 Unity 专用连接入口，选择对应项目的 Editor。
  4. 在将执行的代码行设置断点，再回 Unity 进入 Play 并触发问题。
PLAYER

在打包的游戏中调试

  1. 打开 File → Build Profiles，选择目标平台。
  2. 勾选 Development Build 与 Script Debugging，再构建运行。
  3. 启动阶段就出错时，可以启用 Wait For Managed Debugger，让脚本等待连接。
  4. 在 IDE 选择该 Player 实例。Editor 同时开着时，确认没有连接错进程。

菜单文字会随 IDE 和平台变化。这里基于 Unity 6.0 官方调试流程；Mono 与 IL2CPP 支持该类托管调试，Web 平台不适用同一套 C# 调试器流程。6.7 实验后端应另外核实支持情况。

暂停以后，优先看这四样

  • Locals / Watch：输入参数、对象字段和中间结果是否符合预期。Watch 中调用方法或访问带副作用的 getter，可能执行额外逻辑。
  • Call Stack：谁调用了当前方法？是不是一个你没想到的事件回调或重复订阅？
  • Step Over / Step Into / Step Out：逐行跨过、进入或离开方法。先观察关键分支，不必从启动开始逐行走完整个项目。
  • 条件断点与异常断点：只在特定实体或异常类型发生时停住。条件表达式也有成本，在高频路径上要谨慎。
断点是空心的，或者一直不命中，检查什么？

确认连接的是正确 Editor / Player；代码确实执行；本地源代码与运行构建一致；Player 开启了 Script Debugging；符号信息与二进制匹配；相关代码没有被 #if 排除。远程设备再检查网络可达性。不要只靠反复重启 IDE 猜测。

Error Pause 就是异常断点吗？

不是。Console 的 Error Pause 是编辑器遇到错误消息时暂停 Play Mode；IDE 异常断点可以在异常抛出时中断并检查调用栈与局部变量。普通 Debug.LogError 不会凭空生成一个被 throw 的异常。

建议保留构建号、平台、场景、时间、会话 / 请求标识、操作、结果和简短错误码。帧号适合对照主线程事件，但不能当作跨设备时钟。日志应避免密码、令牌、完整个人资料与巨量存档内容；必要时只记录脱敏摘要。文件落在玩家机器上，不等于已经上传给开发者。

没有日志，按这个顺序查

  1. 代码路径是否实际执行，是否被 #if / Conditional / 等级开关排除。
  2. 是否关闭了 Debug.unityLogger.logEnabled，或更换了 logHandler；项目和插件可能在启动时修改它。
  3. 是否看错了 Editor / Player、版本或 Company / Product 对应目录；是否有多个游戏实例。
  4. 检查平台的日志选项与启动参数、文件写入条件。普通发布包没有消息，不能直接证明“Unity 自动移除了 Log”。

要自己保存日志时，别让日志系统成为故障源

可用 Application.logMessageReceived 或 Application.logMessageReceivedThreaded 接收回调，但接收到回调不代表已经持久化或上传。Threaded 回调可能来自不同线程并并发调用；使用有界、线程安全的缓冲队列，并避免在其中访问主线程专用 Unity API。不要在日志回调里再次调用 Debug.Log，以免递归。完整日志系统还应处理大小上限、轮转和退出时未写出的尾部记录。[线程日志回调]

10 / 测量，而不是猜测

怀疑 Debug 拖慢游戏，怎样验证？

  1. 固定测试条件

    使用相同设备、场景、游戏数据和操作路径。先预热；避免把首次加载、着色器编译或编辑器忙碌混进日志成本。

  2. 在目标 Player 上抓 Profiler

    开发构建可连接 Unity Profiler。观察 CPU 时间线、脚本耗时、GC Alloc 和相关输出路径；确认瓶颈属于 CPU、GPU、分配还是等待。不要仅凭 Editor 的帧率判断最终体验。

  3. 逐项比较，分离成本

    A：原始日志；B：只关闭 logger；C：通过条件编译移除调用及准备工作。保持其余配置一致。若 B 仍有开销而 C 改善明显，就继续调查消息准备和分配。

  4. 按测到的原因改

    把逐帧记录改成状态变化记录；对重复错误按错误码去重 / 限流；减少大对象序列化；只在需要的日志类型上保留堆栈。比较帧时间分布和尖峰，不只看平均 FPS。

  5. 回到正式构建复验

    开发构建、脚本调试和 Deep Profiling 都会影响测量条件。最终在非开发构建与目标设备上确认体验和平台可用指标；不要把开发包测出的绝对数字当作正式包保证。

Unity 建议在目标设备上分析：Profiling on your target device。上述 A/B/C 对比是本文建议的排查实验，并非某个 Unity 版本的性能基准。

日志计时有用，但范围有限。它能帮助观察网络请求和业务事件的大致时序；一旦目标是毫秒级热点或每帧 GC，就需要 Profiler / 标记点等测量工具。不要在被测循环内大量打印计时结果，因为测量过程本身会干扰结果。

日志用途开发阶段正式发布的建议

12 / 常见误区与资料

最后澄清几个容易混淆的说法。

“不勾 Development Build，就不会有 Debug 日志。”

不成立。普通 Debug.Log 调用没有因为这个复选框自动被条件移除。是否输出还由执行路径、日志过滤和平台输出配置共同决定。

“Debug.unityLogger.logEnabled = false 是零成本优化。”

不成立。它能省掉该 logger 后续的很多处理，但调用者的消息构造与参数计算可能已经完成。它还会影响经该 logger 发送的 LogError / LogException 等消息，并非保证关闭一切引擎或原生崩溃输出的总开关。

“换成 print 就更轻量，也不怕打包。”

不是。MonoBehaviour.print 是日志的便利入口，不是绕过日志成本的特殊通道。应从调用频率、消息准备和构建策略上处理。

“Assert 可以替代空引用检查或输入校验。”

不能。断言调用可能随条件符号消失；正式环境必须执行的输入校验、存档验证和恢复逻辑应写成正常代码。Debug.Assert 与 UnityEngine.Assertions.Assert 的具体失败行为也不要混为一谈。

“Debug.DrawLine / DrawRay 也和 Log 完全一样吗？”

不同。它们用于开发时的可视化诊断，不是 Player.log 文本记录；显示受视图和 Gizmos 等条件影响。不能从“没看到线”推导为“准备坐标等计算没有成本”。本文的打包结论主要针对日志调用，不把 Debug 类的所有 API 一概而论。

“断点没改变代码，所以不会影响运行结果。”

暂停可能触发超时或改变线程竞争顺序。遇到时序问题，应减少干扰，先保存事件时间线，再通过可控复现和专门的并发分析确认原因。

“关闭错误日志，游戏就不会报错了。”

只是可能看不到错误。异常、坏状态和失败的业务操作仍然存在。处理根因、明确恢复方式，再决定记录多少信息。

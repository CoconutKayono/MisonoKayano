如果你要找“某种服务”，通常用 Type；如果要找“配置里名字为 fireball 的技能”，用 string；如果系统已经给技能分配了编号，就用 int。这些字典都能获得接近常数时间的平均查找，但它们的语义、常数开销与维护成本不同。

01

先回答：你到底要区分什么？

Dictionary<TKey, TValue> 表示从键到值的映射。选择 TKey，实际上是在决定：什么情况下，两次查询应该指向同一条记录？

要表达的身份合适的键Unity 中的例子主要边界
一种类型Type服务容器、消息类型 → 处理器、组件类型 → 对象池相同类型共用一个键；不会自动匹配父类
一个文本名称string配置名称、资源别名、命令名拼写、大小写与字符串长度
一个业务编号int物品 ID、实体 ID、配置表主键唯一性和生命周期由业务保证
一个固定类别enum伤害类型、状态种类集合由代码定义；持久化时明确数值
某个具体对象对象实例 / 稳定实例 ID某个敌人的仇恨值引用相等还是值相等？对象何时失效？
运行期的类型编号Type → int类型槽位、内部组件索引增加注册与缓存机制；不能天然跨进程复用

“类的类型”和“类的对象”不是同一个键

C# · 放在方法内；Player 是普通 C# 类
Player a = new Player();
Player b = new Player();

// 类型作键：a、b 都是 Player，因此落在同一个键上。
var byType = new Dictionary<Type, int>();
byType[a.GetType()] = 10;
byType[b.GetType()] = 20; // 覆盖上面的值

// 实例作键：若 Player 未自定义相等性，则 a、b 是两个不同键。
var byInstance = new Dictionary<Player, int>();
byInstance[a] = 10;
byInstance[b] = 20;      // 保留两条记录

如果 Player 实现了 IEquatable<Player> 或重写了 Equals/GetHashCode，实例键的行为就可能改变。例如两个不同实例，只要它们的业务 ID 相同，也可以被认为是同一个键。不要在入表后修改影响相等性或哈希值的字段。

依据：Dictionary 的相等比较器与键约束、Object.Equals。

02

字典并不是从头遍历所有键

① 计算哈希比较器根据 key 计算哈希码。
→
② 定位桶把哈希码映射到较小的桶索引。
→
③ 检查候选检查哈希码与键的相等性，确定匹配项。

这是理解复杂度的概念模型。具体桶布局、哈希处理和优化随 .NET / Mono / IL2CPP 版本而变，但“用哈希缩小候选范围，再确认键相等”的思路不变。

相等 ⇒ 哈希相同

正确的比较器必须遵守这个约定。

哈希相同 ≠ 相等

不同键可以发生哈希碰撞，仍需比较键本身。

桶相同 ≠ 哈希相同

桶数量有限，不同哈希码也可能进入同一个桶。

Dictionary<int, T> 也要做哈希表查找，它并不是直接用整数下标访问数组。即使两个整数的哈希码不同，也可能进入同一个桶。

不要把 GetHashCode() 当作唯一 ID。如果将 Dictionary<Type, T> 改成 Dictionary<int, T>，然后用 type.GetHashCode() 当键，你就丢掉了原始类型之间的相等性检查。不同类型一旦得到相同哈希码，会被当成同一个整数键。

依据：GetHashCode 的相等约定、碰撞和持久化限制。

03

Type：当“类型本身”就是身份

Type 是 System.Type。typeof(AudioService) 得到音频服务这个类型的描述对象；service.GetType() 得到对象的实际运行时类型。获取类型不等于扫描全部成员，也不等于进行字符串类型名解析。

C# · 声明类型与实际类型
Animal animal = new Dog();

Type declared = typeof(Animal); // Animal
Type actual   = animal.GetType(); // Dog

// 以下也是不同的 Type 键：
// typeof(List<int>)
// typeof(List<string>)
// typeof(List<>)             // 泛型类型定义

Dictionary<Type, ...> 按类型相等性查找。存入 typeof(Dog) 后，用 typeof(Animal) 查询不会自动命中。继承或接口匹配属于你要额外实现的规则；如果每次遍历所有注册类型并调用 IsAssignableFrom，这层搜索就可能是 O(n)。

一个适合起步的类型服务容器

下面的容器选择“按注册时指定的 T”存储。每个类型键对应一个对象；重复注册会覆盖。它用于普通托管服务，读写由单一线程负责。

C# · 完整定义，可放进 TypeServices.cs
using System;
using System.Collections.Generic;

public sealed class TypeServices
{
    private readonly Dictionary<Type, object> items =
        new Dictionary<Type, object>();

    public void Set<T>(T value) where T : class
    {
        if (value == null)
            throw new ArgumentNullException(nameof(value));

        items[typeof(T)] = value;
    }

    public bool TryGet<T>(out T value) where T : class
    {
        object raw;
        if (items.TryGetValue(typeof(T), out raw))
        {
            value = (T)raw;
            return true;
        }

        value = null;
        return false;
    }

    public void Clear()
    {
        items.Clear();
    }
}
C# · 方法中的调用示例
var services = new TypeServices();
services.Set<IAudioService>(new AudioService());

IAudioService audio;
bool found = services.TryGet<IAudioService>(out audio); // true

AudioService concrete;
bool foundConcrete = services.TryGet<AudioService>(out concrete); // false
// 注册在接口键下，不会自动额外注册到实现类键下。

为什么不用 typeof(T).Name 代替 Type？两个不同命名空间中的类可以都叫 Player；不同程序集也可能定义同名类型。Type 保留真实类型身份，短名字字符串则可能把它们混为一谈。若需要稳定的存档标识，应显式设计业务 ID 和版本迁移，而不是依赖容易随重构变化的类型名。

依据：System.Type、GetType 返回实际运行时类型。容器代码为本文示例。

04

string：适合来自数据和人的名称

资源别名、配置名称、控制台命令，本来就以文本出现。此时字符串是自然的接口；强行转换成类型通常会让配置与代码耦合。

C# · 技能名 → 冷却时间
var cooldowns = new Dictionary<string, float>(StringComparer.Ordinal)
{
    ["fireball"] = 2.5f,
    ["dash"] = 0.8f
};

float seconds;
if (cooldowns.TryGetValue("fireball", out seconds))
{
    // 使用 seconds
}

// 如果业务规定不区分大小写，创建时改用：
// new Dictionary<string, float>(StringComparer.OrdinalIgnoreCase);

对程序标识符，显式使用 Ordinal 或 OrdinalIgnoreCase 可以表达清楚比较规则。大小写规则应在系统边界决定；不要在每次查询时随手调用 ToLower()，让额外的字符处理和潜在字符串分配混入热路径。

字符串为什么不是“绝对 O(1)”？

设键长为 L。常见实现计算字符串哈希需要处理字符，按 O(L) 建模；字符串相等比较最坏也可能检查 O(L) 个字符。因此，“相对于条目数量 n，平均查找 O(1)”与“考虑字符串长度 L，平均查找 O(L)”可以同时成立。

如果键长度有固定上限，可以把 L 当常数。不要假设字符串驻留、同一个字符串引用或 const string 一定让每次字典查找跳过哈希计算；这些实现细节应在具体运行时确认。

避免的是不必要的工作。已经存在的字符串作为键，并不意味着每次查询都产生 GC。常见问题是循环里拼接 "enemy_" + id、格式化或转换大小写后再查找。能在加载阶段解析成稳定 ID，就不必每帧重复解析。

依据：微软字符串比较建议、字符串哈希的实现与稳定性限制。O(L) 为按字符处理成本建立的算法模型，不是耗时实测。

05

int 与 enum：编号清晰，比较便宜

C# · 已有业务 ID 时直接使用
var itemNames = new Dictionary<int, string>();
itemNames[1001] = "治疗药水";
itemNames[2048] = "铁剑";

// 类型固定的分类，用 enum 更容易读懂。
// 声明放在类外，或作为嵌套类型：
// public enum DamageKind { Physical = 1, Fire = 2, Ice = 3 }
var resistance = new Dictionary<DamageKind, float>();
resistance[DamageKind.Fire] = 0.25f;

整数哈希和相等比较通常很便宜，也没有字符串拼写问题。普通泛型字典的 int 键不需要为了存储而装箱；但这不等于整个操作绝不分配内存，字典首次分配和扩容仍会分配内部数组。

整数需要一个明确的编号来源：数据库主键、配置表 ID、显式枚举值，或运行时分配器。若用来保存游戏或通信，必须保证不同运行、客户端和版本对编号有一致解释。枚举若作为协议字段，应明确数值并保留旧值的意义。

整数很密集时，是否还需要字典？

C# · 有效范围固定，ID 是连续槽位
// 前提：合法 ID 为 0 到 255，并且已检查越界和空槽位。
var values = new object[256];
values[7] = "Fireball";
object value = values[7]; // 直接下标访问，O(1)，不做键哈希

数组适合密集、可控的索引范围。若只有 100 个物品，ID 却分布在 1 到 10 亿之间，按最大 ID 分配数组会浪费巨大空间，这时字典更合适。数组空间取决于槽位范围 R，即 O(R)；字典容量合理时主要随条目数 n 增长，即 O(n)，两者还需另算值对象占用。

06

Type → int：优化究竟在哪里？

把类型映射成整数，并不会自动把复杂度从 O(n) 变成 O(1)，因为类型字典原本就能平均 O(1) 查找。它的价值通常在于把类型解析移到初始化阶段，让频繁执行的路径只使用缓存的编号或槽位。

每次查询走的路径主要工作判断
Type → 值一次类型字典查询简单，通常足够
Type → int → 值一次类型字典 + 一次整数字典查询两次哈希表查找，可能更慢
缓存的 int → 值一次整数字典查询可能减少常数开销
缓存的 int → 数组槽位一次索引访问绕过哈希表；要求范围可控

方案 A：初始化时取得 ID，后续直接复用

下面的注册表给每个类型分配一个非负、连续的运行期编号。泛型入口和动态 Type 入口使用同一份映射，避免同一个类型从不同入口获得不同 ID。

C# · 完整定义，可放进 RuntimeTypeIds.cs
using System;
using System.Collections.Generic;

public static class RuntimeTypeIds
{
    private static readonly object Gate = new object();
    private static readonly Dictionary<Type, int> Ids =
        new Dictionary<Type, int>();

    // 动态 Type 入口：每次调用仍会查字典。
    public static int Get(Type type)
    {
        if (type == null)
            throw new ArgumentNullException(nameof(type));

        lock (Gate)
        {
            int id;
            if (Ids.TryGetValue(type, out id))
                return id;

            id = Ids.Count;
            Ids.Add(type, id);
            return id;
        }
    }

    // 泛型入口：缓存初始化之后只读静态字段。
    public static int Get<T>()
    {
        return Cache<T>.Id;
    }

    private static class Cache<T>
    {
        public static readonly int Id = Get(typeof(T));
    }
}
C# · 初始化与查询分开
// 初始化 / 注册阶段：
int audioId = RuntimeTypeIds.Get<AudioService>();
var servicesById = new Dictionary<int, object>();
servicesById[audioId] = new AudioService();

// 高频查询：直接复用 audioId。
object service;
bool found = servicesById.TryGetValue(audioId, out service);

// 动态入口与泛型入口取得相同 ID：
bool sameId = RuntimeTypeIds.Get(typeof(AudioService)) == audioId;

方案 B：用泛型静态字段保存每个 T 的编号

上面 Cache<T> 已经实现了这个方案。Cache<AudioService> 与 Cache<InputService> 各自拥有一份静态字段，因此每个 T 只需要在缓存初始化时注册。后续 Get<T>() 读取对应字段；具体调用和泛型访问开销仍受编译后端影响。

若类型只在运行时作为变量出现，例如 Type type，它不能直接写成 Get<type>()。此时可以在对象或注册记录上保存 Get(type) 的返回值，之后复用整数。

这是运行期编号，不是存档或网络协议。编号取决于注册顺序，重启后可能改变。示例只增加映射，不提供单独清空接口；如果清空 Ids，而 Cache<T>.Id 仍保留旧值，新分配的 ID 就可能与旧缓存冲突。

  • 锁保护的是注册表。它不让另一个 Dictionary<int, object> 自动变成线程安全容器。
  • 密集 ID 是全局的。某个子系统只使用少数类型时，全局编号对应的大数组仍可能浪费空间。
  • 对象类型与整数键的对应关系需要封装。裸露的 Dictionary<int, object> 允许把错误对象写入某个类型 ID；想保留类型安全，应提供 Set<T>/TryGet<T> 一类入口。
  • 先测收益再承担复杂度。额外注册表、同步、生命周期和调试成本，都应计入选型。

依据：每个闭合泛型类型拥有自己的静态成员。映射实现、调用路径分析和使用边界为本文设计。

07

时间复杂度：把三个维度分开

记 n 为当前条目数、L 为字符串长度、c 为一次查找检查的候选数。先忽略扩容，可以用下面的模型理解一次查找：

查找成本 ≈ 哈希成本 + 定位桶成本 + 检查 c 个候选的成本

哈希分布合理、桶容量随数据量增长时，平均 c 很小，得到相对 n 的平均 O(1)。严重碰撞时，c 可能达到 n。O(1) 描述增长趋势，不代表 1 次操作、1 纳秒，或任何情况下都一样快。

先假设键的哈希与相等比较都是 O(1)

操作平均 / 常见情况最坏情况或边界
TryGetValue / ContainsKeyO(1)严重碰撞时 O(n)
索引器读取 / 更新已有键O(1)严重碰撞时 O(n)；读取缺失键会抛异常
Add / 插入新键平均摊还 O(1)单次扩容或严重碰撞可达 O(n)
RemoveO(1)严重碰撞时 O(n)
遍历 / ContainsValue通常按 O(n) 理解还受内部待扫描槽位数影响；删过大量数据后可能大于当前 Count
Count 属性O(1)读取维护好的计数，不重新遍历
数组合法下标访问O(1)无哈希碰撞；前提是数组已分配

平均讨论哈希分布下的查找成本；摊还把偶尔昂贵的扩容分摊到一连串插入上。平均摊还 O(1) 不保证某一帧的某次插入没有明显耗时。

再把键本身的处理成本算进去

键 / 路径典型平均查找模型需要保留的前提
int / 常见 enumO(1)常数成本的比较与合理哈希分布
普通运行时 Type通常按 O(1) 建模类型已取得；不包含额外反射扫描或字符串解析
string考虑键长时通常为 O(L)相对 n 平均 O(1)；所有键长至多 L 时，碰撞最坏可按 O(nL) 上界理解
每次 Type → int → 字典平均 O(1) + O(1) = O(1)大 O 一样，但比一次查询多一段工作
已缓存 ID → 数组O(1)初次注册、分配与扩容另计
自定义键 / 自定义比较器O(H + cE) 的保守模型H 为哈希成本，E 为一次比较成本；比较器可能做任意复杂的工作

O(nL) 是字符串比较参与碰撞处理时的保守上界，不是每次碰撞都会完整比较 L 个字符。哈希码预筛、长度差异与字符早停都可能降低实际工作量。

动手看：为什么碰撞会改变查找成本？

教学模型：依次插入整数 0…n−1，桶内新条目放在前面，然后查找最早插入的键 0。桶数 B = n/2。此图只展示候选访问次数，不模拟 .NET 的具体布局，也不提供性能实测。

绿色标记为目标键 0。均匀模式中，n 与桶数一起增长，所以目标桶始终只有 2 个候选；极端碰撞时，目标桶包含全部 n 个候选。实际字典还会先检查候选哈希码，不一定对每个候选调用完整的键相等比较。

依据：Add 的扩容与复杂度、Dictionary 的哈希表模型。碰撞上界与演示是根据哈希表模型推导，未声称任何 Unity 平台的固定速度排名。

08

放进 Unity 后，还要留意什么？

① 查一次就拿到结果

C# · 避免命中时重复查键
// ContainsKey 命中后再使用索引器，会查两次。
// if (dict.ContainsKey(key)) Use(dict[key]);

// 更直接：
if (dict.TryGetValue(key, out var value))
{
    Use(value);
}

如果依赖在初始化后不会变化，甚至可以缓存最终服务对象或组件引用，在 Update 中直接使用。场景切换、替换服务或销毁对象时，同时处理缓存失效。

② 预估容量，把准备工作放在初始化阶段

C# · 预计约 1,000 条记录
var entities = new Dictionary<int, object>(1000);
// 预留容量不等于已经插入 1000 条记录：entities.Count 仍是 0。

避免每帧重建字典、拼接键和批量触发扩容。预留过大的容量也会浪费内存；应根据场景规模选择。

③ Inspector 序列化与运行时查找是两件事

本文示例均按运行时容器设计。Unity 2022.3 / 6000.0 的内置序列化不直接支持普通字典，常见做法是序列化列表并在加载时建字典，或使用自定义序列化。较新版本文档已经出现字典序列化支持，应按项目实际版本核对支持的键值类型与比较器规则，不能把旧版本限制当作永久结论。

版本依据：Unity 2022.3 SerializeField、Unity 6000.0 自定义序列化、Unity 6000.6 序列化文档入口。

④ 关闭 Domain Reload 时，静态状态可能保留

如果进入 Play Mode 时关闭 Domain Reload，静态字典和泛型静态缓存可能沿用上次状态。对普通服务缓存，要在合适生命周期清理失效引用；对本文的类型 ID 方案，应让注册表与所有编号缓存保持同一生命周期。不要只把计数器归零或只清空映射，留下旧的泛型缓存。

依据：Unity Domain Reloading 与静态状态。

⑤ 测真实 Player，区分准备成本与查询成本

用 Unity Profiler 在目标设备、实际脚本后端和构建配置上比较。Editor / Mono 中的结果不能直接代表设备上的 IL2CPP。记录 Unity 版本、平台、键数量、字符串长度、命中比例以及构建配置。

  • 分别测初始化 / 注册、已有键命中、缺失键、插入和扩容。
  • 预热泛型缓存；同时单独记录首次调用成本，避免把它藏掉。
  • 对比完整路径：直接 Type、每次 Type 转 ID、缓存 ID、数组槽位。
  • 计时区间避免 Debug.Log 和无关分配；消费查询结果，防止优化器消除无用工作。
  • 同时查看 CPU 与 GC Alloc。本文不提供未经测量的“int 快几倍”结论。

默认选择：类型服务先用 Dictionary<Type, ...>；文本入口用 Dictionary<string, ...> 并明确比较规则；已有业务 ID 就用 Dictionary<int, ...>。只有热路径数据支持时，再考虑缓存 ID 或密集数组。

09

用五个问题，检验你是否真的理解

有 100 个 Enemy 对象，用 typeof(Enemy) 作键能保存 100 份独立状态吗？

不能，它们共用同一个类型键。可用实例或业务实例 ID 作键；如果要按类型分组，可以让值是 List<Enemy>，即一个类型键对应一组对象。

Dictionary<int, T> 是 O(1)，所以一定比 Type 快吗？

不能这样推断。普通 Type 键也通常按平均 O(1) 建模；常数成本、比较器、缓存局部性、字典规模与后端都会影响结果。更不能忽略为得到 int 而进行的额外查询。

既然字典内部也计算哈希，为什么我不能直接用 type.GetHashCode()？

字典保留原始 Type，发生碰撞时还能区分不同类型。你只保存哈希码作为整数键，就丢失了这层区分能力。应使用保留原始键的字典，或有唯一性保障的编号分配器。

连续插入很多键平均很快，为什么某一帧仍然可能卡一下？

插入可能触发内部数组扩容和数据迁移。平均摊还 O(1) 允许某次操作是 O(n)。可以预估容量，把批量构建放在加载阶段，并用 Profiler 确认卡顿来源。

我把 Type 映射成 int，为什么性能反而下降？

先检查是不是每次都做 typeToId[type] 再查整数字典；这会形成两次查找。还要检查动态入口上的锁、首次泛型初始化以及额外的内存访问。把 ID 缓存到调用方后再比较，或直接缓存最终对象。

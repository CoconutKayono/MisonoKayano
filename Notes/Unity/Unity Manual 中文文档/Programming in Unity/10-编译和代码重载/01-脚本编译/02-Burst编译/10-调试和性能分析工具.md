# 调试和性能分析工具

> 原文：[Debugging and profiling tools](https://docs.unity3d.com/6000.7/Documentation/Manual/burst/debugging-profiling-tools.html)

以下章节介绍如何在 Editor 和 Player 构建中调试和分析 Burst 编译的代码。

> **提示**：尝试调试 Burst 编译的代码之前，请按照 [[01-在Unity中调试CSharp代码]] 中的步骤，为 Editor 或 Player 构建启用脚本调试。虽然理论上在脚本编译模式设为 Release 时也可以调试 Burst 编译的代码，但实际并不可靠。例如，断点可能被跳过，Locals 窗口也可能不显示变量。

## 在 Editor 中调试 Burst 编译的代码

在 Editor 中调试 Burst 编译的代码时，可以使用 Managed Debugger 或 Native Debugger。本节介绍这两种方式。

### 附加 Managed Debugger

可以附加 Visual Studio 或 JetBrains Rider 等 Managed Debugger。这与调试 Unity 项目中普通托管 C# 代码时使用的调试器类型相同。

在 Burst 编译的代码中设置断点并附加 Managed Debugger 后，Unity 会自动为该代码路径禁用 Burst，使你可以调试代码的托管版本。移除该代码路径中的所有断点后，Unity 会重新为该代码路径启用 Burst。

### 附加 Native Debugger

可以附加 Visual Studio 或 Xcode 等 Native Debugger。附加之前，需要禁用 Burst 优化。可以通过以下方式之一完成：

- 在 Editor 的 Burst 菜单中使用 **Native Debug Mode Compilation** 设置（**Jobs > Burst > Native Debug Mode Compilation**）。**重要**：此设置会禁用所有 Job 的优化，从而影响 Burst 代码的性能。如果只想为特定 Job 禁用优化，请使用下面的另一种方式。
- 在 Job 上添加 `Debug = true` 标志；这会仅对该 Job 禁用优化并启用调试：

```csharp
[BurstCompile(Debug = true)]
public struct MyJob : IJob
{
    // ...
}
```

> **提示**：Player 构建会采用 `Debug` 标志，因此也可以用这种方式调试 Player 构建。

要将 Native Debugger 附加到 Unity Editor 进程，请参阅“Native 调试”。

## 在 Player 构建中调试 Burst 编译的代码

由于 Unity 构建 Player 代码的方式，需要告诉调试工具符号的位置。将调试工具指向包含 `lib_burst_generated` 文件的文件夹，该文件夹通常位于 `Plugins` 文件夹中。

要在 Player 构建中调试 Burst 编译的代码，需要将 Native Debugger（例如 Visual Studio 或 Xcode）附加到 Player 进程。开始之前，需要完成以下准备：

- 启用符号生成。可以通过以下任一方式完成：
  - 构建 Player 之前启用 **Development Build** 选项；或
  - 在 [[08-Burst AOT设置参考]] 中启用 **Force Debug Information** 选项。
- 禁用 Burst 优化。可以通过以下任一方式完成：
  - 在 [[08-Burst AOT设置参考]] 中禁用 **Enable Optimizations** 选项。**重要**：此设置会禁用所有 Job 的优化，从而影响 Burst 代码的性能。如果只想为特定 Job 禁用优化，请使用下面的另一种方式。
  - 在 Job 上添加 `Debug = true` 标志；这会仅对该 Job 禁用优化并启用调试：

```csharp
[BurstCompile(Debug = true)]
public struct MyJob : IJob
{
    // ...
}
```

要将 Native Debugger 附加到 Player 进程，请参阅“Native 调试”。

## Native 调试

按照前面针对 [[#在 Editor 中调试 Burst 编译的代码|Editor]] 或 [[#在 Player 构建中调试 Burst 编译的代码|Player 构建]] 的说明，正确设置 Native 调试。然后附加 Visual Studio 或 Xcode 等 Native Debugger。

### Native 调试限制

- Native Debugger 无法发现 `Entity.ForEach` 中的 lambda 捕获，因此无法检查由这些捕获产生的变量。
- 使用 [`[StructLayout(LayoutKind=Explicit)]`](https://docs.microsoft.com/en-us/dotnet/api/system.runtime.interopservices.layoutkind?view=net-6.0) 且存在重叠字段的结构体，会显示为隐藏其中一个重叠字段的结构体。

嵌套类型会使用 C/C++ 风格进行命名空间限定，如下例所示：

```csharp
namespace Pillow
{
    public struct Spot
    {
        public struct SubSpot
        {
            public int a;
            public int b;
        }
        public int a;
        public int b;
        public SubSpot sub;
    }
```

在本例中，如果要在调试器的监视窗口中转换指针，可以使用 `Pillow::Spot::SubSpot` 引用 `SubSpot`。

### 基于代码的断点

Burst 通过 [`System.Diagnostics.Debugger.Break`](https://docs.microsoft.com/en-us/dotnet/api/system.diagnostics.debugger.break?view=net-6.0) 方法支持基于代码的断点。该方法会在代码中生成调试陷阱。必须将调试器附加到代码，以便调试器拦截该中断。无论是否附加调试器，断点都会触发。

Burst 会添加用于跟踪局部变量、函数参数和断点的信息。如果调试器支持条件断点，建议优先使用条件断点，而不要在代码中添加断点，因为只有在附加调试器时条件断点才会触发。

## 分析 Burst 编译的代码

可以使用 Instruments 或 Superluminal 等性能分析工具分析 Player 构建中的 Burst 编译代码。由于 Unity 构建 Player 代码的方式，需要告诉性能分析工具符号的位置。将工具指向包含 `lib_burst_generated` 文件的文件夹，该文件夹通常位于 `Plugins` 文件夹中。

### Unity Profiler 标记

为了改进 Unity Profiler 获取的数据（无论 Burst 编译的代码是在 Editor 中运行，还是在已附加的 Player 中运行），可以在 Burst 代码中调用 `new ProfilerMarker("MarkerName")` 创建 Unity Profiler 标记：

```csharp
[BurstCompile]
private static class ProfilerMarkerWrapper
{
    private static readonly ProfilerMarker StaticMarker = new ProfilerMarker("TestStaticBurst");

    [BurstCompile(CompileSynchronously = true)]
    public static int CreateAndUseProfilerMarker(int start)
    {
        using (StaticMarker.Auto())
        {
            var p = new ProfilerMarker("TestBurst");
            p.Begin();
            var result = 0;
            for (var i = start; i < start + 100000; i++)
            {
                result += i;
            }
            p.End();
            return result;
        }
    }
}
```

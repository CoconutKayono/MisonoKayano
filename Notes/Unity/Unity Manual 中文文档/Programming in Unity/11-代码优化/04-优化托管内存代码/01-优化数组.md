# 优化数组

> 原文：[Optimizing arrays](https://docs.unity3d.com/6000.7/Documentation/Manual/performance-optimizing-arrays.html)

以下页面概述了使用[数组](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/builtin-types/arrays)时，如何通过示例来提升代码性能。

## 将数组作为方法参数传递

有时，编写一个创建新数组、向数组填充值，然后返回数组的方法会很方便。但是，如果反复调用此方法，每次调用都会分配新的内存。

下面的示例代码展示了一个每次调用都会创建数组的方法：

```csharp
// 错误的 C# 脚本示例：每次调用 RandomList 方法时，
// 都会分配一个新数组
using UnityEngine;
using System.Collections;

public class ExampleScript : MonoBehaviour {
    float[] RandomList(int numElements) {
        var result = new float[numElements];

        for (int i = 0; i < numElements; i++) {
            result[i] = Random.value;
        }

        return result;
    }
}
```

避免每次调用都分配内存的一种方式，是利用数组属于引用类型这一事实。可以修改作为参数传入方法的数组，并且方法返回后修改结果仍然保留。可以按如下方式改写上面的示例代码：

```csharp
// 良好的 C# 脚本示例：此版本的方法接收一个用于填充的数组
// 可以缓存并重复使用该数组，以避免反复产生临时分配
using UnityEngine;
using System.Collections;

public class ExampleScript : MonoBehaviour {
    void RandomList(float[] arrayToFill) {
        for (int i = 0; i < arrayToFill.Length; i++) {
            arrayToFill[i] = Random.value;
        }
    }
}
```

此代码会用新值替换数组的现有内容。这种工作流要求调用代码完成数组的首次分配，但该函数在调用时不会产生新的垃圾。之后再次调用此方法时，可以重新填充同一个数组，而不会在托管堆上产生新的分配。

## 避免重复访问返回数组的 Unity API

数组产生意外分配的一个原因，是反复访问返回数组的 Unity API。所有返回数组的 Unity API 每次访问时都会创建该数组的新副本。如果代码访问这类 API 的频率超过必要程度，就会影响应用程序的性能。

例如，下面的代码在每次循环迭代中都会创建 `vertices` 数组的四个副本。每次访问 `.vertices` 属性时都会发生分配：

```csharp
// 错误的 C# 脚本示例：此循环每次迭代都会创建 vertices 数组的 4 个副本
void Update() {
    for(int i = 0; i < mesh.vertices.Length; i++) {
        float x, y, z;

        x = mesh.vertices[i].x;
        y = mesh.vertices[i].y;
        z = mesh.vertices[i].z;
        // ...

        DoSomething(x, y, z);
    }
}
```

无论循环迭代多少次，都可以将这段代码重构为只分配一次数组。为此，应在循环开始前获取 `vertices` 数组：

```csharp
// 更好的 C# 脚本示例：只创建一个 vertices 数组副本，
// 并使用这个副本进行处理
void Update() {
    var vertices = mesh.vertices;

    for(int i = 0; i < vertices.Length; i++) {
        float x, y, z;

        x = vertices[i].x;
        y = vertices[i].y;
        z = vertices[i].z;

        // ...

        DoSomething(x, y, z);
    }
}
```

更理想的方式，是维护一个缓存并在帧与帧之间重复使用的 `List`，然后在需要时使用 [`Mesh.GetVertices`](https://docs.unity3d.com/6000.7/Documentation/ScriptReference/Mesh.GetVertices.html) 向其中填充顶点。

```csharp
// 最佳 C# 脚本示例：只创建一个 vertices 数组副本，
// 并使用这个副本进行处理
List<Vector3> m_vertices = new List<Vector3>();

void Update() {
    mesh.GetVertices(m_vertices);

    for(int i = 0; i < m_vertices.Length; i++) {

        float x, y, z;

        x = m_vertices[i].x;
        y = m_vertices[i].y;
        z = m_vertices[i].z;

        // ...

        DoSomething(x, y, z);
    }
}
```

一次访问会分配数组的属性，其 CPU 性能影响并不高；但是，在紧密循环中反复访问会形成 CPU 性能热点。反复访问还会扩大[托管堆](https://docs.unity3d.com/6000.7/Documentation/Manual/performance-managed-memory-introduction.html)。

这个问题在移动设备上很常见，因为 [`Input.touches`](https://docs.unity3d.com/6000.7/Documentation/ScriptReference/Input-touches.html) API 的行为与上面的示例类似。项目中也经常存在类似下面的代码：每次访问 `.touches` 属性时都会发生分配：

```csharp
// 错误的 C# 脚本示例：每次访问 Input.touches 时都会返回一个数组
for ( int i = 0; i < Input.touches.Length; i++ ) {
   Touch touch = Input.touches[i];

    // …
}
```

为了改进这一点，可以将数组分配提升到循环条件之外：

```csharp
// 更好的 C# 脚本示例：这里仅访问一次 Input.touches
Touch[] touches = Input.touches;

for ( int i = 0; i < touches.Length; i++ ) {

   Touch touch = touches[i];

   // …
}
```

下面的代码将前一个示例转换为不分配内存的 `Touch` API：

```csharp
// 最佳 C# 脚本示例：Input.touchCount 和 Input.GetTouch 完全不会分配内存
int touchCount = Input.touchCount;

for ( int i = 0; i < touchCount; i++ ) {
   Touch touch = Input.GetTouch(i);

   // …
}
```

> [!NOTE]
> 属性访问（`Input.touchCount`）仍然放在循环条件之外，以节省调用该属性 getter 方法所产生的 CPU 开销。

### 替代性的非分配 API

一些 Unity API 有不会产生内存分配的替代版本。条件允许时，应使用这些版本。下表给出了分配型 API 及其非分配替代版本的示例：

| 分配型 API | 非分配 API 替代版本 |
| --- | --- |
| [`Physics.RaycastAll`](https://docs.unity3d.com/6000.7/Documentation/ScriptReference/Physics.RaycastAll.html) | [`Physics.RaycastNonAlloc`](https://docs.unity3d.com/6000.7/Documentation/ScriptReference/Physics.RaycastNonAlloc.html) |
| [`Animator.parameters`](https://docs.unity3d.com/6000.7/Documentation/ScriptReference/Animator-parameters.html) | [`Animator.parameterCount`](https://docs.unity3d.com/6000.7/Documentation/ScriptReference/Animator-parameterCount.html) 和 [`Animator.GetParameter`](https://docs.unity3d.com/6000.7/Documentation/ScriptReference/Animator.GetParameter.html) |
| [`Renderer.sharedMaterials`](https://docs.unity3d.com/6000.7/Documentation/ScriptReference/Renderer-sharedMaterials.html) | [`Renderer.GetSharedMaterials`](https://docs.unity3d.com/6000.7/Documentation/ScriptReference/Renderer.GetSharedMaterials.html) |

通常，如果某个方法返回数组，就往往存在一个可以传入数组、从而避免分配的 API 版本。

## 使用零长度数组的静态实例

有些开发团队更倾向于：当返回数组的方法需要返回空集合时，返回空数组而不是 `null`。这种编码模式在许多托管语言中都很常见，尤其是 C# 和 Java。

当方法要返回零长度数组时，返回预先分配的零长度数组静态实例，比反复创建空数组更高效。

## 对大型数组使用 NativeArray 或其他原生容器

Unity 的[垃圾回收器](https://docs.unity3d.com/6000.7/Documentation/Manual/performance-garbage-collector.html)是一种启发式垃圾回收器，这意味着它会将任何大小等于指针的字段视为指针。垃圾回收器会检查遇到的每一个指针和引用。

当使用大型数组（超过 10,000 个元素）时，垃圾回收器可能会把大型数组解释为需要检查的一长串指针，这会增加内存压力并减慢垃圾回收器的运行速度。

脚本 VM 还必须为大型数组在托管堆上分配大块空间，这会增加随机值看起来像托管堆内存地址范围内有效地址的可能性。大型数组也是造成托管堆碎片化的重要因素。

如果需要分配这么长的数组，可以考虑使用 Unity 核心 API 中 [`Unity.Collections`](https://docs.unity3d.com/6000.7/Documentation/ScriptReference/Unity.Collections.html) 命名空间中的集合类型（包括 [`NativeArray`](https://docs.unity3d.com/6000.7/Documentation/ScriptReference/Unity.Collections.NativeArray_1.html)），以及 [Unity Collections 包](https://docs.unity3d.com/Packages/com.unity.collections@latest)中的数据结构。除此之外，这些集合还兼容[Job System](https://docs.unity3d.com/6000.7/Documentation/Manual/job-system.html)和 Burst。

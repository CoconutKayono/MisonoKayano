# .NET API 兼容级别

> 原文：[API compatibility levels for .NET](https://docs.unity3d.com/6000.7/Documentation/Manual/dotnet-profile-support.html)

Unity 支持两种项目代码可以针对其进行编译的 .NET API Compatibility Level。你选择的 Compatibility Level 决定 C# 代码可以使用哪些 .NET 类库：

- **.NET Standard 2.1**：由 .NET Foundation 发布的 .NET Standard 2.1，是默认的 API Compatibility Level。
- **.NET Framework**：由 Microsoft 发布的 .NET Framework 4.8，并额外包含 .NET Standard 2.1 的 API。

> [!NOTE]
> CoreCLR Scripting Backend 只支持 .NET Standard。

## 设置 API Compatibility Level

在 Unity Editor 中选择 **Edit > Project Settings**，打开 **Player** 页签，进入 **Other Settings > Configuration**，然后在 **Api Compatibility Level** 下拉菜单中选择目标级别。也可以在代码中调用 `PlayerSettings.SetAPICompatibilityLevel` 设置它。

## 选择 API Compatibility Level

对于新项目，一般优先选择 .NET Standard，原因包括：

- .NET Standard 的 API 范围更小，实现也更小，因此可以减小最终可执行文件的大小。
- .NET Standard 的跨平台支持更好，代码更有可能在所有平台上正常运行。虽然某些平台并不完全支持 .NET Standard，但 .NET Framework 选项对跨平台兼容性的帮助更小。`.NET Framework` Profile 包含 .NET Standard Profile 的全部 API，以及一些只在少数平台上可用、甚至没有任何平台实现的额外 API。
- 所有 .NET Runtime 都支持 .NET Standard，因此使用 .NET Standard 时，代码可以运行在更多 Runtime 环境中，例如 .NET Framework、.NET Core、Xamarin 和 Unity。
- .NET Standard 会将更多错误提前到编译期。某些 .NET Framework API 在编译期可用，但在部分平台上的实现会在 Runtime 抛出异常。

如果需要支持较早的现有应用程序，.NET Framework API Compatibility Level 可能更有用。

## Managed Plug-in

Managed Plug-in 是在 Unity 外部使用 Visual Studio 等工具创建，并编译为动态链接库（DLL）的 .NET 程序集。两种 API Compatibility Level 都可以使用 Managed Plug-in，但支持程度取决于 Plug-in 编译时针对的 API Level。由于 .NET Framework 的 API 范围比 .NET Standard 更大，如果项目针对 .NET Standard，可能无法支持所有针对 .NET Framework 编译的 Plug-in。

| Managed Plug-in 的编译目标 | .NET Standard 2.1 | .NET Framework 4.x |
| --- | --- | --- |
| .NET Standard（任意版本） | 支持 | 支持 |
| .NET Framework（任意版本） | 有限支持 | 支持 |
| .NET Core（任意版本） | 不支持 | 不支持 |

## 第三方 .NET 类库

只使用在各种 Unity 配置和平台上经过充分测试的第三方 .NET 类库。

Mono Scripting Backend 的 Just-in-Time（JIT）编译允许应用程序 Runtime 动态生成 C# / .NET Intermediate Language（IL）代码；IL2CPP Scripting Backend 使用 Ahead-of-Time（AOT）编译，不支持动态代码生成。

这一点对于第三方类库很重要，因为它们可能为 JIT 和 AOT 编译使用不同的代码路径，也可能依赖动态生成的代码。关于 Runtime 生成代码的更多信息，请参阅 Microsoft 的 `ModuleBuilder` 文档。

第三方类库的 JIT 和 AOT 代码路径在性能特征上可能有显著差异。AOT 通常能缩短启动时间，因此适合大型应用，但需要把编译后的代码放入二进制文件，会增加文件大小；AOT 在开发期间的构建时间也更长。JIT 会根据运行平台在 Runtime 调整代码，这可能提升运行时性能，但可能增加应用启动时间。因此，建议同时在 Editor 和目标平台上对应用进行 Profile。

评估第三方类库时，应考虑：

- 兼容性：类库可能与某些 Unity 平台或 Scripting Backend 不兼容。
- 性能：类库在 Unity 中的性能特征可能与其他 .NET Runtime 差异很大。
- AOT 二进制大小：类库的依赖数量可能显著增加 AOT 二进制文件大小。

## .NET System 类库

Unity 支持许多平台，并可能根据平台使用不同的 Scripting Backend。`.NET System` Namespace 中的类库在某些情况下需要平台专用实现才能正常工作。虽然 Unity 尽可能支持 .NET 生态，但明确不支持以下行为：

- Unity 不保证不同版本 Unity 的 .NET System 类库具有固定的性能或内存分配行为。
- Unity 通常不会修复 .NET System 类库中的性能回退。
- Unity 不支持 `System.Drawing` 类库，也不保证它能在所有平台上工作。

> [!TIP]
> 在所有目标平台上 Profile .NET System 类库的使用情况，因为其性能特征可能受到 Scripting Backend、.NET 版本和 API Compatibility Level 的影响。

## Transport Layer Security（TLS）1.2

`UnityWebRequest` API 和所有 .NET Framework Web API 在除 Web 外的所有平台上完全支持 TLS 1.2。Web 平台改用应用运行所在浏览器以及 Web Server 的安全设置。平台专用的本地证书存储在可用时会自动验证 TLS 证书；如果无法访问证书存储，Unity 会使用内置的根证书存储。

## 使用第三方程序集时

即使程序集在 Editor 中编译通过，也不代表它能在所有 Player 平台运行。检查程序集的目标 framework、引用的 DLL 以及目标平台是否提供对应 API。如果项目使用 .NET Framework 4.8 中的平台专用 API，构建到受限平台时可能出现缺失 API 或加载失败。

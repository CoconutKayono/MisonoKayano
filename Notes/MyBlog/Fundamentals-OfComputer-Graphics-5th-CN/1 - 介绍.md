# 1 介绍

术语 _计算机图形学_（computer graphics）描述任何使用计算机创建（create）和处理（manipulate）图像的方法。本书介绍创建各类图像所需的算法与数学工具，涵盖逼真的视觉效果（visual effects）、信息技术插图（information-technology illustration）以及精美的计算机动画（computer animation）。图形可以是二维或三维的；图像既可以完全由计算机合成，也可以通过处理照片生成。本书聚焦于底层的算法与数学，尤其是用于生成三维物体与场景合成图像的那部分。

事实上，从事计算机图形学工作就难免需要了解特定的硬件（hardware）、文件格式（file format），通常还要熟悉一两个图形 API（见 1.3 节）。计算机图形学是一门快速演进的学科，因此上述知识的具体细节如同移动的靶子，总是处于变化之中。有鉴于此，本书将尽最大努力避免依赖任何特定的硬件或 API。我们鼓励读者结合相关软件 API 的文档和硬件环境来学习本书内容。所幸，计算机图形学领域已具备足够的标准化，本书讨论的术语与概念应当能够较好地映射到绝大多数环境中。

本章定义一些基本术语，提供一些历史背景，并给出与计算机图形学相关的更多信息来源。

## 1.1 CG 的应用领域（Application Areas）

对任何学科强行分类都难免引发争议，不过大多数从业者会认可以下计算机图形学的主要领域：

1. 建模（modeling）：用数学规范描述形状（shape）与外观（appearance）属性，使其能够存储于计算机中。
2. 渲染（rendering）：该术语源自美术，指从三维几何模型生成着色图像（shaded image）的过程。
3. 动画（animation）：通过图像序列制造运动错觉（illusion of motion）的技术。

此外还有许多与之相关的领域，只是它们是否属于 CG 的范畴尚有争议：

1. 用户交互（user interaction）：处理输入设备（如鼠标、数位板）、应用程序、图像对用户的反馈以及其他感官反馈之间的接口。
2. 虚拟现实（virtual reality）：致力于让用户沉浸于三维虚拟世界之中。这通常至少需要立体显示（stereoscopic display）以及对头部运动的实时响应；真正的虚拟现实还应提供声音与力反馈（force feedback）。
3. 可视化（visualization）：借助视觉显示帮助用户洞悉复杂信息。
4. 图像处理（image processing）：对二维图像进行处理与操作。
5. 三维扫描（3D scanning）：利用测距技术生成实测的三维模型。
6. 计算摄影（computational photography）：综合运用 CG、计算机视觉（computer vision, CV）和图像处理方法，实现新的摄影成像能力。

## 1.2 主要应用（Major Applications）

1. 游戏（games）：越来越多地使用复杂的三维模型和渲染算法。
2. 卡通（cartoons）：通常直接对三维模型进行渲染。许多传统二维卡通使用由三维模型渲染出的背景，这样可以实现视点的连续移动，而无需耗费大量美术人力。
3. 视觉特效（visual effects）：几乎涵盖了所有类型的计算机图形技术。几乎每部现代电影都使用数字合成（digital compositing）将背景与单独拍摄的前景叠加；许多电影还借助三维建模与动画来创建合成的环境、物体乃至角色。
4. 动画电影（animated films）：使用了大量与视觉特效相同的技术，但目标并不一定是逼真的画面。
5. 计算机辅助设计与制造（CAD/CAM）：这些领域利用计算机技术设计零件与产品，再以这些虚拟设计指导制造过程。
6. 模拟（simulation）：可以看作高保真的视频游戏。这类模拟对驾驶等安全关键领域的初始训练非常有用，也适用于真实场景中过于昂贵或危险而难以物理复现的训练，例如某些消防情形。
7. 医学影像（medical imaging）：例如，计算机断层扫描（computed tomography, CT）数据集由大量三维矩形密度值数组构成。计算机图形学被用于生成着色图像，帮助医生从这些数据中提取最显著的信息。
8. 信息可视化（information visualization）：为未必具有“自然”视觉形态的数据创建图像。例如，十只股票的价格随时间变化的趋势并无直观的视觉形态，但巧妙的绘图技术可以帮助人们发现此类数据中的模式。

## 1.3 图形 API（Graphics APIs）

应用程序编程接口（application programming interface, API）是执行一组相关操作的标准函数集合。图形 API 则是这样一组函数：例如将图像和三维表面绘制到屏幕上。每个图形程序都需要使用两个相互关联的 API：

1. 用于视觉**输出**的图形 API；
2. 用于从用户处获取**输入**的用户界面 API。

目前图形 API 与用户界面 API 主要有两种范式：

1. 集成式（integrated）：如 Java，其图形与用户界面工具包以集成、可移植的软件包形式提供，完全标准化，并作为语言的一部分得到官方支持。
2. 以 Direct3D 和 OpenGL 为代表：绘图命令是绑定到 C++ 等语言的软件库的一部分，而用户界面软件则是独立的实体，可能因系统而异。

在后一种模式下，虽然编写可移植的简单程序比较棘手，但仍可使用可移植库来封装系统特定的用户界面代码。

## 1.4 图形管线（Graphics Pipeline）

几何管线（geometric pipeline）是一种专门的软件/硬件子系统，能够高效地绘制三维图元（primitive）。这类系统通常针对共享顶点的三维三角形的处理进行优化。管线中的基本操作将三维顶点位置映射到二维屏幕位置，并对三角形进行着色，使其看起来真实，并以正确的“从后到前”（back-to-front）顺序呈现。尽管高效的绘制顺序曾是 CG 中最重要的问题之一，如今它几乎已经被一种特殊的内存缓冲区——Z 缓冲（Z-buffer）——以“蛮力”方式解决。

CG 管线中的几何操作几乎可以完全在四维坐标空间中进行，该空间由三个传统几何坐标和一个有助于透视的齐次坐标（homogeneous coordinate）组成。这些四维坐标借助 4×4 矩阵和四维向量进行操作。因此，图形管线中包含大量用于高效处理和组合这些矩阵与向量的机制。这个四维坐标系是计算机科学中最精妙、最优美的结构之一，无疑也是学习计算机图形学时必须跨越的最大智力障碍。

渲染速度在很大程度上取决于所绘制三角形的数量。因此，在许多实时应用中，人们愿意以牺牲几何细节为代价来换取渲染速度。此外，从远处观察模型时，只需更少的三角形即可维持相同的视觉质量，即细节层次（level of detail, LOD）。

## 1.5 数值问题（Numerical Issues）

幸运的是，几乎所有现代计算机都遵循 IEEE 浮点标准（IEEE floating-point standard），这使得程序员可以放心地对许多数值运算的结果做出假设（这句话的意思是：**IEEE浮点标准为浮点数运算提供了一套“通用语言”，让程序员不用再为不同硬件上的计算结果不一致而提心吊胆**）。关于 IEEE 浮点，只有少数要点特别重要：

1. IEEE 浮点中有三个“特殊值”：
   1. 正无穷（infinity，$\infty$）：一个大于其他所有数字的有效数。
   2. 负无穷（$-\infty$）：一个小于其他所有数字的有效数。
   3. 非数（not a number, NaN）：由结果未定义的操作（如零除以零）产生的无效数字。

![](https://pic1.zhimg.com/80/v2-f9b4b188452bc9a79e6e0a4571218788_720w.webp)

IEEE 浮点的设计者做出了一些对程序员十分友好的决定，其中许多都与上述三个特殊值有关，用来处理除以零之类的异常；而在大多数情况下，其结果可以忽略不计（例如非零实数除以无穷大）：
$$+ a / (+\infty) = +0$$

另一些涉及无穷大的运算结果与人们的直觉一致（未定式返回 NaN，其余结果正常）：
$$\infty + \infty = +\infty$$
$$\infty - \infty = NaN$$

关于 NaN 的规则：

1. 任何包含 NaN 的算术表达式，其结果都是 NaN；
2. 任何涉及 NaN 的布尔表达式，其结果都是 false。

此外，IEEE 标准最实用的部分之一是关于除以零的规则。有了这些规则，程序员就无需再花大量精力编写条件判断语句来事先检查运算的合法性，例如：
$$+a / +0 = +\infty$$

> 注：根据 IEEE 754 标准，为保证程序的健壮性（robustness），浮点运算中除以零默认返回无穷大（此处将 0 视作无穷小量）；但在整数运算中，除以零仍会抛出异常。

## 1.6 效率（Efficiency）

让代码更高效并没有捷径可走，效率来自细致的权衡取舍。程序员应当更关注内存访问模式（memory access pattern），而不是运算次数，因为内存的速度远慢于处理器。

可以参考以下工作流来提高代码效率：

1. 以最直接的方式编写代码：需要中间结果时就地计算，而不是预先存储。
2. 在优化模式下编译。
3. 使用性能分析工具（profiler）找出关键瓶颈。
4. 检查数据结构，寻找提高局部性（locality）的方法：尽可能使数据单元的大小与目标架构的缓存/页面大小相匹配。
5. 如果性能分析显示瓶颈出在数值计算上，请检查编译器生成的汇编代码，并重写源代码以解决发现的问题。

这些步骤中第一步最为重要。大多数“你以为的优化”只会让代码更难读，并不会让程序运行得更快。此外，花在过早优化（premature optimization）上的时间，通常更适合用来修复错误或添加功能。另外，一些老式技巧（如用整数运算代替浮点运算）也未必能真正提升性能，因为现代计算机处理两者的速度已相差无几。

## 1.7 设计并编写图形程序（Designing and Coding Graphics Programs）

本节介绍一些常见的图形编程策略。

### 1.7.1 类的设计（Class Design）

任何图形程序的关键，都在于为几何实体（如向量与矩阵）和图形实体（如 RGB 颜色与图像）提供良好的类或例程，它们应当尽可能简洁而高效。下面谈谈几个基本类：

1. vector2：二维向量类，存储 x 与 y 分量。应将这两个分量存放在长度为 2 的数组中，以便支持下标索引；还应提供向量加、向量减、点积（dot product）、叉积（cross product）、标量乘和标量除等运算。
2. vector3：三维向量类，存储 x、y、z 分量；应具备 vector2 的全部运算，此外还提供叉积。
3. hvector：具有四个分量的齐次向量（homogeneous vector）。
4. rgb：存储三个分量的 RGB 颜色类；还应提供 RGB 加法、RGB 减法、RGB 乘法、标量乘和标量除运算。
5. transform：4×4 矩阵类；应包含矩阵乘法，以及将矩阵应用于位置（position）、方向（direction）和表面法向量（surface normal）的成员函数。
6. image：RGB 像素的二维数组，并带有输出图像的操作。

此外，你可能希望（也可能不希望）为区间（interval）、标准正交基（orthonormal basis）和坐标架（coordinate frame）建立相应的类。

### 1.7.2 单精度与双精度浮点数（Single vs. Double Precision Floating Points）

现代计算机体系结构表明，降低内存占用并保持连续的内存访问是提高效率的关键，这提示我们使用单精度（single precision）数据。然而，为了避免数值问题，双精度（double precision）运算更为稳妥。具体取舍取决于程序本身。

### 1.7.3 图形程序的调试（Debugging Graphics Programs）

随着经验的积累，程序员使用传统调试器（debugger）的次数会越来越少。原因之一是，对复杂程序使用这类调试器比对简单程序困难得多；另一个原因是，最棘手的错误往往是概念性错误，而遍历变量值很容易耗费大量时间却依然发现不了问题所在。

1. 科学的方法（the scientific method）
   在图形程序中，有一种传统调试的替代方法：先创建一幅图像，然后观察它的问题所在；再针对问题的成因提出假设，并加以验证。这种方法有时非常有效，关键在于我们不必找出错误的值或确定自己的概念错误，而只需通过实验逐步缩小概念错误的范围。
   > 大致思路：提出假设，然后一步步缩小错误原因的范围。

2. 将图像作为调试输出（images as debugging output）
   图形程序中最简单的输出就是图像。如果想了解某个变量在针对每个像素的计算过程中的取值，可以临时修改程序，把该值直接写入输出图像，并跳过其余本应完成的计算。如果怀疑某个值偶尔超出有效范围，可以让程序在超出时写入亮红色像素。其他常用技巧还包括：用醒目的颜色绘制不应可见的背面，按对象的 ID 号着色，或按像素的计算量着色。

3. 使用调试器（using debuggers）
   一个有用的技巧是为 bug“设置陷阱”：在怀疑有问题的代码之前加入一条语句，使其仅在可疑情况下执行，例如 `if x = 126 and y = 247 then print("problem comes here!")`，甚至可以在该 print 语句上设置断点。当程序崩溃时，传统调试器对精确定位崩溃位置很有帮助；随后应从崩溃点开始回溯，利用断言（assertion）和重新编译逐步找到出错之处。这些断言应当保留在程序中，以便将来排查新引入的错误。

4. 数据可视化调试（data visualization for debugging）
   通常很难弄清程序究竟在做什么，因为它在最终出错之前已经计算了大量中间结果。解决办法同样如此：绘制精美的图表和插图，以理解数据的含义。例如，在光线追踪器（ray tracer）中，你可以编写代码将光线树（ray tree）可视化，从而直观地看到哪些光线路径对一个像素产生了贡献。为可视化程序内部状态而投入的编码时间，在日后优化程序时也会得到回报——它能让你更好地理解程序的行为。

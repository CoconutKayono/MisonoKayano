# Unity 文档迁移到 Obsidian

把用户指定的 Unity Manual 或 Scripting API 页面逐页翻译为中文 Obsidian 文档。这里的“完成”指每个页面的正文已经从对应官方网络页面实际读取并翻译，而不是只建立目录或写摘要；翻译是唯一内容变更，原文格式和内容必须保留。

## 适用范围与来源

- 只处理用户指定入口页及其同一文档分支；入口页目录中的子页面、子集和子集的子页面都要递归展开。
- 以用户指定版本的 Unity 官方网络页面为唯一来源，通常是 `https://docs.unity3d.com/6000.7/Documentation/Manual/...` 或 `https://docs.unity3d.com/6000.7/Documentation/ScriptReference/...`。本地 Unity 文档、已有 Markdown、缓存页面、旧迁移结果和本地索引均禁止作为正文、声明、参数、链接清单、页面顺序或翻译依据；本地文件只能作为最终写入目标。
- 每个页面都必须单独请求其对应的官方 URL，不能只请求父页后根据父页表格或已有本地文件补写子页。父页表格只能用于发现候选链接，子页的实际内容、重载、章节、示例和相关资源必须以子页官方 URL 的正文为准。
- 请求原 URL 后检查 HTTP 状态、canonical URL、版本和页面内容。遇到 404 先检查官方 canonical、重定向和 URL 大小写（Unity 页面存在大小写敏感情况），确认官方页面确实不存在后才在进度表标记“源站异常”。
- 每个 Markdown 文件必须保留对应的 `原文：[标题](官方 URL)`；目录入口和文档内部跳转必须使用本地 Obsidian 链接。
- 翻译边界优先级最高：严格保留官方页面的标题层级、段落顺序、章节名称、声明、重载、参数、返回值、描述、列表、表格、代码、示例、相关资源和链接。只翻译说明性自然语言；不得补写摘要、解释、结论、占位内容或非官方章节，不得合并、拆分、重排、删减或改写原文内容。

## 1. 建立并维护迁移清单

先递归读取官方入口页和所有属于该分支的官方目录链接，建立一行对应一个本地 Markdown 页面的清单。至少记录：稳定 ID、原文标题、官方 URL、官方父页面、官方阅读顺序、本地路径、状态、图片数和异常说明。清单中的标题、URL、父子关系和顺序都必须来自官方网络页面，不能从本地目录反推。

默认使用：

`Notes/Unity/Unity官方文档迁移进度.md`

状态必须反映真实证据：

- `待执行`：尚未完成正文迁移。
- `已完成`：正文、图片、链接、导航和网络来源均已审计通过。
- `源站异常`：已按 URL/canonical/大小写规则检查，但官方页面确实不可访问；记录检查结果，不得用模板冒充完成。

目录数量、文件存在、HTTP 200 或“代理完成”都不能单独把页面标为 `已完成`。

## 2. 设计本地树和顺序

根据官方网页阅读顺序使用数字前缀，标题和文件名翻译为中文，不添加“`-中文文档`”后缀。例如：

```text
00-相机.md
01-相机简介.md
02-相机视图/
  00-相机视图.md
  01-相机视图简介.md
```

- 有子页面的目录必须有 `00-*.md` 本地索引。
- 如果发现已有编号、中文名或目录结构与官方顺序不一致，先修正文件名，再一次性修复父索引、子索引、正文链接、导航和进度表，不能留下旧路径。
- 只有影响理解的技术术语保留英文，例如 `Camera`、`URP`、`Render Texture`、`Camera Stack`、API 名称、菜单路径、组件名和 Inspector 属性；普通标题与描述直接翻译成中文。
- 页面正文不得因为适配 Obsidian 而新增官方原文没有的“文档导航”、上一页/下一页、目录、译者说明或总结。只有用户明确要求本地导航时，才能在正文之外添加导航，并且不得改变原文主体的顺序和内容。

## 3. 从网络正文逐页搬运并翻译

对清单中的每个页面，必须再次按该页面自己的官方 URL 获取 HTML，定位官方正文容器，逐项迁移实际内容：

- 标题层级、段落、步骤、列表、表格、提示/警告、折叠内容和相关资源。
- C#、Shader、命令、API、类名、方法名、属性名、菜单路径和代码结构保持可用的英文原文；说明文字翻译为自然准确的中文。
- 不得只搬标题、页面简介、目录说明、搜索摘要或自拟要点。若官方页面有多个正文小节，必须全部出现；代码块不能被省略或改写成概述。
- 必须完整读取描述区域中的所有连续段落，包括紧跟首段之后的补充说明、限制条件、注意事项、返回值语义和示例引导语；不能只保留描述区域的第一段。示例区域中的每个官方代码块都必须按原顺序保留。
- Scripting API 页面必须保持官方页面的顺序和结构：每个重载/签名都要在其自己的“声明”后紧跟对应的参数、返回值和描述；不能把多个重载的声明集中到页面顶部，也不能把多个重载合并成摘要。属性、方法、静态方法、消息、运算符等分类必须按官方父页的分类分别保留。
- 看到现有文件中的 `TODO`、`未拉取原文`、占位说明或明显模板，必须重新按原文 URL 拉取并覆盖为真实正文；不能因为文件已经存在或目录完整而跳过。
- 页面间引用若属于本次分支，建立对应本地文件并改为本地链接；真正属于外部相关资源的链接保留为官方外链。

页面顶部格式：

```markdown
> 原文：[Original title](https://docs.unity3d.com/...)
```

## 4. 图片和媒体

解析网络 HTML 中的所有正文图片，解析相对 URL 时以官方页面 URL 为基准，下载原始文件到该文档目录下的 `图片/`（或该分支统一约定的本地图片目录），并改用相对路径：

```markdown
![图片说明](图片/example.png)
```

每个图片引用都要检查本地文件存在、文件非空且扩展名正确。下载失败必须记录原 URL 和原因；不能只留下图片标题、远程占位符或假路径后把页面标成完成。

## 5. 本地索引与 Obsidian 链接

索引表使用本地文件链接：

```markdown
| 页面 | 说明 |
| --- | --- |
| [[01-相机简介]] | 介绍 Camera 的基本工作方式。 |
| [[02-相机视图/00-相机视图]] | 介绍相机视图相关内容。 |
```

硬性规则：

- 表格中的链接禁止使用 `[[目标|显示文字]]`，因为内部 `|` 会被 Markdown 解析为列分隔符；使用不带别名的 `[[目标]]`。
- 索引表不能直接链接官方 URL；官方 URL 放在目标页面的 `原文：` 行或相关资源区域。
- 目录表保持清晰的两列“页面/说明”，修复时删除残留的英文表头、错误转义和混入表格的 `|`。
- 目标路径必须按当前 Markdown 文件的相对位置解析，并实际指向存在的文件或子目录的 `00-*.md`。

## 6. 本地导航（仅在用户明确要求时）

用户明确要求本地导航时，每篇页面底部才按完整阅读顺序加入：

```markdown

---

## 文档导航

- 上一页：[[上一页]]
- 目录：[[00-当前目录]]
- 下一页：[[下一页]]
```

边界页可以写“无”或链接到用户指定分支的下一个目录，但必须保持导航格式。导航不能替代或穿插官方正文。`---` 的前后必须各空一行；正文与分隔线、分隔线与标题之间都不能紧贴。

## 7. 并行处理边界

只有用户明确允许并行/子任务时才拆分工作。按不重叠的页面批次分配写入范围；子任务不要同时修改进度表、公共索引或同一目录的导航。主任务负责合并路径、维护进度表，并对所有产物做独立网络审计。子任务报告不能代替文件和网络证据。

## 8. 逐页审计和全量验证

单页完成后立即审计：

1. `原文` URL 与官方页面对应，HTTP/canonical/版本正确；重新请求该 URL，不得使用本地页面代替。
2. 正文小节、段落、列表、表格、代码和图片与该官方页面逐项对照，没有摘要或 TODO。
3. 父子链接、分类、阅读顺序和导航都与官方网页重新读取的链接关系一致；不能仅依据本地文件存在来判断链接正确。
4. 所有本地图片、Obsidian 链接和导航目标可解析。
5. 文件名、编号、父索引和进度表路径一致，且这些关系能由官方网页清单追溯。

然后运行全量校验：

```powershell
powershell -ExecutionPolicy Bypass -File .codex/skills/unity-docs-to-obsidian/scripts/validate_obsidian_docs.ps1 -Root Notes/Unity/Camera
```

按实际目录替换 `Notes/Unity/Camera`；必要时分别校验 `Notes/Unity/脚本`、`Notes/Unity/游戏对象` 和总目录。若校验失败，先修复再汇报。

最终报告至少给出：清单总数、已完成数、待执行数、源站异常数、验证器结果，以及仍需人工判断的页面。只有逐页审计和全量验证都通过，才能把迁移报告为完成。
